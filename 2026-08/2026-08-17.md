## 00:03 - dbt Analyses: Version-Controlled Ad-Hoc SQL Without Materialization

dbt's `analyses/` folder lets you write SQL queries that are compiled by dbt — with full access to `ref()`, `source()`, and Jinja — but are **never materialized** as database objects. They're for exploratory queries, one-off audits, or documentation-level SQL that you want under version control without cluttering your warehouse.

### How It Works

Any `.sql` file placed in the `analyses/` directory (configured via `analysis-paths` in `dbt_project.yml`) is compiled when you run `dbt compile`. The compiled output lands in `target/compiled/<project>/analyses/`. You can then copy that SQL and run it in your warehouse client.

```sql
-- analyses/revenue_audit.sql
-- Find orders where total doesn't match line items

select
    o.order_id,
    o.total_amount                          as header_total,
    sum(li.unit_price * li.quantity)        as line_item_total,
    o.total_amount - sum(li.unit_price * li.quantity) as discrepancy
from {{ ref('fct_orders') }} o
join {{ ref('fct_order_line_items') }} li using (order_id)
group by 1, 2
having header_total != line_item_total
order by abs(discrepancy) desc
```

Running `dbt compile --select analyses/revenue_audit` produces fully resolved SQL with real table names — no manual find-and-replace needed.

### When to Use Analyses

| Use case | Better choice |
|---|---|
| Ad-hoc investigation saved for later | `analyses/` |
| Repeatable logic consumed by a model | Macro or staging model |
| Data quality check that fails a run | Singular test in `tests/` |
| Business metric exposed to BI tools | Mart model or semantic layer |

### Practical Tips

- **Namespace by theme**: `analyses/finance/`, `analyses/ops/` keeps large projects tidy.
- **Add a comment block**: Explain the business question the query answers — future teammates will thank you.
- **Pair with `dbt docs`**: Analyses appear in `dbt docs generate` output, making them discoverable without digging through the file tree.
- **CI-friendly**: Because analyses are compiled but not run, they validate that `ref()` targets exist and Jinja renders correctly without touching production data.

Analyses are a lightweight way to make your team's tribal SQL knowledge auditable, reviewable, and always in sync with the rest of your dbt DAG.

## 05:05 - dbt Incremental Strategies: Choosing the Right Approach for Your Warehouse

Incremental models are dbt's answer to processing only new or changed data instead of rebuilding an entire table on every run. The `incremental_strategy` config tells dbt *how* to merge that new data in — and the right choice has a significant impact on both correctness and performance.

### The Four Core Strategies

**`append`** — simply inserts new rows, never touches existing ones. Fast and safe, but only correct when rows are immutable (event logs, raw click streams). Duplicate rows will appear if the same data is loaded twice.

**`delete+insert`** — deletes rows in the target that match the new batch's partition, then inserts the new batch. Atomic within a partition, avoids duplicates, and works well on partition-pruning warehouses like BigQuery and Spark.

**`merge`** — issues a SQL `MERGE` (upsert) statement matching on `unique_key`. Updates matching rows, inserts new ones. The most flexible strategy and the default on Snowflake and Databricks, but can be expensive on very wide tables.

**`insert_overwrite`** (BigQuery / Spark) — atomically replaces entire partitions. Extremely fast at scale because it skips row-level comparison entirely. Requires a well-defined partition column.

### Strategy by Warehouse

| Warehouse | Default strategy | Common alternative |
|---|---|---|
| Snowflake | `merge` | `delete+insert` |
| BigQuery | `merge` | `insert_overwrite` |
| Databricks / Spark | `merge` | `insert_overwrite` |
| Redshift | `append` | `delete+insert` |
| DuckDB | `delete+insert` | `append` |

### Configuration Example

```sql
-- models/fct_events.sql
{{
  config(
    materialized='incremental',
    incremental_strategy='delete+insert',
    unique_key='event_date',        -- partition key for delete+insert
    partition_by={
      "field": "event_date",
      "data_type": "date"
    }
  )
}}

select
    event_date,
    event_type,
    count(*) as event_count
from {{ source('raw', 'events') }}

{% if is_incremental() %}
  where event_date >= (select max(event_date) from {{ this }})
{% endif %}

group by 1, 2
```

### Key Decision Points

- **Immutable events, no late arrivals** → `append`
- **Late-arriving data within known partitions** → `delete+insert` or `insert_overwrite`
- **Row-level updates (e.g. SCD Type 1)** → `merge` with `unique_key`
- **Massive tables where partition replacement is cheap** → `insert_overwrite`

Always test your incremental model with `dbt run --full-refresh` periodically to verify the full-refresh result matches your incremental output — drift between the two signals a logic bug in your `is_incremental()` filter.

## 10:03 - dbt Model Contracts: Enforcing Schema Stability Across Your DAG

Introduced in dbt v1.5, **model contracts** let you declare a model's expected schema as a first-class commitment — column names, data types, and constraints — and have dbt enforce that contract at build time. They're the difference between hoping downstream consumers don't break and *guaranteeing* they won't.

### Why Contracts Matter

Without contracts, a model's output schema is whatever the SQL happens to produce. A column rename, type change, or accidental removal silently breaks every downstream model, BI report, and reverse-ETL job that depends on it. Contracts turn that implicit agreement into an explicit, version-controlled one.

### Defining a Contract

Contracts live in your `.yml` files alongside the model definition:

```yaml
# models/marts/fct_orders.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true          # dbt will fail if the schema doesn't match
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: unique
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
      - name: total_amount
        data_type: numeric
      - name: status
        data_type: varchar
```

When `enforced: true`, dbt compares the compiled model's output columns against the contract before materializing. A mismatch — wrong type, missing column, extra undeclared column — raises a build error.

### Supported Constraints

| Constraint type | What it enforces |
|---|---|
| `not_null` | Column cannot contain NULLs |
| `unique` | All values must be distinct |
| `primary_key` | Composite or single-column PK (warehouse-level) |
| `foreign_key` | FK relationship to another table |
| `check` | Arbitrary SQL expression (warehouse-dependent) |

Note: constraint *enforcement* at the database level depends on whether your warehouse supports it (Snowflake and BigQuery enforce `not_null`; most don't enforce `unique` natively). dbt always enforces at compile time regardless.

### Model Versions and Contracts Together

Contracts pair naturally with **model versioning** (also v1.5+). When you need to make a breaking change, bump the version instead of editing in place:

```yaml
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 1          # legacy consumers keep using v1
      - v: 2          # new schema with contract enforced
        config:
          contract:
            enforced: true
```

Downstream models can pin to `ref('fct_orders', v=1)` until they're ready to migrate, giving you a controlled deprecation window instead of a big-bang migration.

### Best Practices

- **Start with public marts**: apply contracts to models consumed by BI tools or external teams first — that's where breakage is most costly.
- **Declare all columns explicitly**: contracts require every column to be listed; treat this as an opportunity to document each one with a `description`.
- **Use `dbt compile` in CI**: contract violations surface at compile time, so you catch them in a pull request before any data moves.
- **Pin `data_type` to warehouse-native types**: use `bigint` not `int64` on Snowflake, `varchar` not `string` on Redshift — dbt normalizes some aliases but explicit types are safer.

## 15:02 - dbt Snapshots: Capturing Slowly Changing Dimensions with SCD Type 2

dbt snapshots are purpose-built for tracking how records change over time — classic Slowly Changing Dimension Type 2 (SCD2) behavior. Instead of overwriting a row when a source record changes, a snapshot appends a new version and timestamps both the old and new rows, giving you a full audit trail.

### How Snapshots Work

Snapshot files live in the `snapshots/` directory and use a special `{% snapshot %}` block. On each `dbt snapshot` run, dbt compares incoming source rows against the existing snapshot table and either:

- **Inserts** a new row for records that changed (closing the previous row's `dbt_valid_to`)
- **Inserts** a new row for brand-new records
- Leaves unchanged records alone

dbt automatically manages four metadata columns: `dbt_scd_id`, `dbt_updated_at`, `dbt_valid_from`, and `dbt_valid_to` (NULL means the row is current).

### Example: Snapshotting Customer Records

```sql
-- snapshots/customers_snapshot.sql
{% snapshot customers_snapshot %}

{{
  config(
    target_schema='snapshots',
    unique_key='customer_id',
    strategy='timestamp',
    updated_at='updated_at',
    invalidate_hard_deletes=True
  )
}}

select
    customer_id,
    email,
    plan_tier,
    billing_country,
    updated_at
from {{ source('crm', 'customers') }}

{% endsnapshot %}
```

Run it with:

```bash
dbt snapshot                       # process all snapshots
dbt snapshot --select customers_snapshot   # just this one
```

### Timestamp vs. Check Strategy

| Strategy | When to use | How it detects changes |
|---|---|---|
| `timestamp` | Source has a reliable `updated_at` column | Compares `updated_at` to `dbt_updated_at` |
| `check` | No reliable timestamp; any column change counts | Compares a list of `check_cols` row by row |

```sql
-- check strategy example
{{
  config(
    strategy='check',
    unique_key='customer_id',
    check_cols=['email', 'plan_tier', 'billing_country']
  )
}}
```

Use `check_cols='all'` to watch every column, but be aware this is slower on wide tables.

### Querying Snapshots Downstream

Reference a snapshot in a model with `ref()` just like any other node:

```sql
-- models/marts/dim_customers.sql
select
    customer_id,
    email,
    plan_tier,
    dbt_valid_from,
    dbt_valid_to,
    dbt_valid_to is null as is_current
from {{ ref('customers_snapshot') }}
```

Filter to current state with `where dbt_valid_to is null`, or point-in-time queries with `where '2025-06-01' between dbt_valid_from and coalesce(dbt_valid_to, '9999-12-31')`.

### Practical Tips

- **`invalidate_hard_deletes: True`**: when a row disappears from the source, dbt closes its snapshot row instead of leaving it open as "current" forever — crucial for correctness.
- **Snapshot frequently**: snapshots only capture the state at run time; if a record changes and reverts before the next snapshot, the intermediate state is lost.
- **Keep snapshots thin**: snapshot only the columns you need to track; join to the full source record at query time to keep the snapshot table lean.
- **Never `dbt run` a snapshot**: snapshots have their own command (`dbt snapshot`) and are not processed by `dbt run` — a common source of confusion for new users.
