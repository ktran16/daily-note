## 00:02 - [Data Engineering] Spark Data Skew: Diagnosing and Fixing the Straggler Task

A Spark job where 199 of 200 tasks finish in seconds and one runs for 40 minutes is not slow — it is skewed. One partition holds far more rows than the rest, and since a stage completes only when its slowest task does, that single straggler sets your wall clock and your cluster bill.

**Diagnosing.** In the Spark UI, open the stage and look at the task duration and shuffle-read-size distribution. If the max is orders of magnitude above the 75th percentile, you have skew. Confirm the culprit key:

```sql
SELECT customer_id, COUNT(*) AS n
FROM events
GROUP BY customer_id
ORDER BY n DESC
LIMIT 20;
```

Usually you'll find a sentinel: `NULL`, `-1`, `'unknown'`, or a genuine whale account absorbing 30% of the rows.

**Fix 1 — Broadcast the small side.** If the dimension fits in executor memory (roughly under a few hundred MB), broadcasting eliminates the shuffle entirely, so skew stops mattering:

```python
from pyspark.sql.functions import broadcast
fact.join(broadcast(dim_customer), "customer_id")
```

**Fix 2 — Let AQE handle it.** Adaptive Query Execution splits oversized shuffle partitions at runtime. On Spark 3.x it's on by default, but verify the thresholds actually trigger:

```python
spark.conf.set("spark.sql.adaptive.enabled", True)
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", True)
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", 5)
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")
```

AQE only rescues sort-merge joins on shuffled data — it will not help a skewed `groupBy` on a single key.

**Fix 3 — Salting.** When the hot key is real and both sides are large, spread it across N buckets and explode the small side to match:

```python
from pyspark.sql import functions as F
N = 50
left  = fact.withColumn("salt", (F.rand() * N).cast("int"))
right = (dim.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N)]))))
left.join(right, ["customer_id", "salt"])
```

You pay an N-fold increase in the small side's size — keep N just large enough to flatten the histogram.

**Fix 4 — Filter first.** Nulls that will never match belong outside the join. `WHERE customer_id IS NOT NULL` before the shuffle is often the entire fix, and it costs nothing.

Always re-check the task histogram after the change: skew fixes that "look right" but move the imbalance elsewhere are common.

## 05:03 - [Data Analytics] Funnel Analysis in SQL: Ordered Steps, Time Windows, and Honest Denominators

Most "funnel" queries are wrong in the same way: they count `COUNT(DISTINCT user_id)` per event type and divide. That silently credits a user who viewed checkout on Monday and had signed up in March, and it counts steps that happened *out of order* as conversions.

A correct funnel needs three things: a **per-user anchor**, an **ordering constraint**, and a **time window**.

**The pattern.** Anchor each user at their first step-1 event, then look for the earliest later step that follows it within the window:

```sql
WITH anchored AS (
  SELECT user_id, MIN(event_at) AS t0
  FROM events
  WHERE event_name = 'view_product'
    AND event_at >= DATE '2026-08-01'
  GROUP BY user_id
),
steps AS (
  SELECT
    a.user_id,
    MIN(e.event_at) FILTER (WHERE e.event_name = 'add_to_cart')     AS t1,
    MIN(e.event_at) FILTER (WHERE e.event_name = 'begin_checkout')  AS t2,
    MIN(e.event_at) FILTER (WHERE e.event_name = 'purchase')        AS t3
  FROM anchored a
  JOIN events e
    ON e.user_id = a.user_id
   AND e.event_at >  a.t0
   AND e.event_at <= a.t0 + INTERVAL '7 days'
  GROUP BY a.user_id
)
SELECT
  COUNT(*)                                             AS s0_viewed,
  COUNT(*) FILTER (WHERE t1 IS NOT NULL)               AS s1_carted,
  COUNT(*) FILTER (WHERE t1 < t2)                      AS s2_checkout,
  COUNT(*) FILTER (WHERE t1 < t2 AND t2 < t3)          AS s3_purchased
FROM steps;
```

The `t1 < t2 < t3` chain is what enforces order. Drop it and users who hit `purchase` via a saved link — never touching cart — inflate your checkout conversion.

**Read the numbers two ways.** Given 100,000 / 24,000 / 18,500 / 12,900:

- *Step-to-step*: 24.0% → 77.1% → 69.7%. Tells you **where** to fix.
- *Overall from top*: 24.0% → 18.5% → 12.9%. Tells you **what it's worth**.

Reporting only the second hides that add-to-cart, at 24%, is the real leak.

**Two traps.** First, the window truncates: on 2026-08-23 a user anchored on 08-20 still has 4 days left, so recent cohorts look worse than they are — cut the anchor range at `today - 7 days`. Second, strict funnels punish legitimate backtracking; if users routinely re-enter earlier steps, measure *any* ordered occurrence rather than the first, or your product looks broken when it isn't.
