## 00:03 - dbt Macros: Writing Reusable SQL Logic with Jinja

Macros are one of dbt's most powerful features — they let you write reusable SQL logic using Jinja templating, so you stop copying and pasting the same patterns across dozens of models.

### Why Macros Matter

Without macros, you might duplicate fiscal year calculations, date spine logic, or surrogate key generation across every model that needs them. A bug in the pattern means hunting down every copy. With macros, you fix it once.

### Writing Your First Macro

Macros live in the `macros/` directory and use the `{% macro %}` Jinja block:

```sql
-- macros/cents_to_dollars.sql
{% macro cents_to_dollars(column_name) %}
    ({{ column_name }} / 100.0)::numeric(18, 2)
{% endmacro %}
```

Call it from any model like a function:

```sql
-- models/fct_orders.sql
select
    order_id,
    {{ cents_to_dollars('amount_cents') }} as amount_dollars,
    {{ cents_to_dollars('shipping_cents') }} as shipping_dollars
from {{ ref('stg_orders') }}
```

### Macros with Default Arguments

```sql
-- macros/generate_surrogate_key.sql
{% macro generate_surrogate_key(field_list) %}
    {{ dbt_utils.generate_surrogate_key(field_list) }}
{% endmacro %}

-- Or write your own:
{% macro surrogate_key(columns) %}
    md5(
        concat_ws('|',
            {% for col in columns %}
                coalesce(cast({{ col }} as varchar), '')
                {%- if not loop.last %}, {% endif %}
            {% endfor %}
        )
    )
{% endmacro %}
```

Usage in a model:

```sql
select
    {{ surrogate_key(['user_id', 'event_date']) }} as event_sk,
    user_id,
    event_date
from {{ ref('stg_events') }}
```

### Using `is_incremental()` Inside Macros

Macros can reference the `is_incremental()` context, making them useful for building dynamic WHERE clauses:

```sql
{% macro incremental_filter(date_column, lookback_days=3) %}
    {% if is_incremental() %}
        where {{ date_column }} >= (
            select dateadd(day, -{{ lookback_days }}, max({{ date_column }}))
            from {{ this }}
        )
    {% endif %}
{% endmacro %}
```

```sql
-- models/fct_sessions.sql
{{ config(materialized='incremental', unique_key='session_id') }}

select * from {{ ref('stg_sessions') }}
{{ incremental_filter('session_started_at', lookback_days=7) }}
```

### Cross-Database Macros with `adapter.dispatch`

dbt supports multiple warehouses (Snowflake, BigQuery, Redshift, DuckDB...). Use `adapter.dispatch` to write warehouse-specific implementations under a single macro name:

```sql
-- macros/get_current_timestamp.sql
{% macro get_current_timestamp() %}
    {{ return(adapter.dispatch('get_current_timestamp')()) }}
{% endmacro %}

{% macro snowflake__get_current_timestamp() %}
    convert_timezone('UTC', current_timestamp())
{% endmacro %}

{% macro bigquery__get_current_timestamp() %}
    current_timestamp()
{% endmacro %}

{% macro default__get_current_timestamp() %}
    now()
{% endmacro %}
```

Now `{{ get_current_timestamp() }}` works correctly on any platform.

### Key Tips

- **Keep macros focused**: one responsibility per macro. Don't build a macro that does five things — compose smaller macros instead.
- **Document with `{% docs %}`**: macro arguments can be documented in schema YAML files.
- **Use `dbt-utils`**: the package already provides `generate_surrogate_key`, `date_spine`, `star`, `pivot`, and more. Install before reinventing the wheel.
- **Test macro output**: wrap macro calls in an analysis or singular test to inspect the generated SQL with `dbt compile`.

```bash
# See what SQL a model compiles to (macros expanded)
dbt compile --select fct_orders
cat target/compiled/my_project/models/fct_orders.sql
```

Macros are the backbone of a well-DRY dbt project — invest in them early and your team will thank you later.

## 05:08 - dbt Python Models: Running Python in Your Warehouse

Since dbt 1.3, you can write models in Python instead of SQL. Python models run natively inside your warehouse (Snowflake, BigQuery, Databricks, Spark) — no external Python runtime required. They're ideal when SQL simply isn't expressive enough: ML feature engineering, statistical transforms, or operations that need pandas/scikit-learn.

### When to Use Python Models

- **ML preprocessing**: normalizing, encoding, or scaling features before training
- **Complex array/JSON manipulation** that's painful in SQL
- **Calling Python libraries**: pandas, scikit-learn, numpy, etc.
- **Avoiding multiple CTEs** for iterative logic that's cleaner in procedural code

Stick to SQL models for standard transformations — Python models are slower to compile and run, and harder to test with dbt's generic tests.

### Writing a Python Model

Python models live in `models/` with a `.py` extension. Each file must define a `model(dbt, session)` function that returns a DataFrame:

```python
# models/fct_ml_features.py
import pandas as pd
from sklearn.preprocessing import StandardScaler

def model(dbt, session):
    # Reference upstream dbt models exactly like {{ ref() }} in SQL
    orders = dbt.ref("stg_orders").to_pandas()
    customers = dbt.ref("stg_customers").to_pandas()

    df = orders.merge(customers, on="customer_id", how="left")

    # Feature engineering
    df["days_since_signup"] = (
        pd.Timestamp.utcnow() - pd.to_datetime(df["signup_date"])
    ).dt.days

    scaler = StandardScaler()
    df["order_value_scaled"] = scaler.fit_transform(df[["order_total"]])

    return df[["customer_id", "days_since_signup", "order_value_scaled"]]
```

### Configuration

Configure Python models the same way as SQL models — in the `config()` block or `dbt_project.yml`:

```python
def model(dbt, session):
    dbt.config(
        materialized="table",
        packages=["scikit-learn==1.4.0"],  # Snowflake: declare packages here
    )
    ...
```

On **Snowflake**, packages are pulled from the Anaconda channel via the `packages` config key. On **BigQuery**, use `requirements.txt`-style declarations in your project. On **Databricks**, the session is a Spark session — return a Spark DataFrame instead of pandas.

### Accessing Sources

Use `dbt.source()` just like `{{ source() }}` in SQL:

```python
raw = dbt.source("raw_events", "clicks").to_pandas()
```

### Limitations

- **No Jinja templating** inside `.py` files — use `dbt.config(vars=...)` to pass variables
- **Slower than SQL** — materialize as `table` (incremental support is limited and warehouse-dependent)
- **Generic tests still work** — `unique`, `not_null`, and custom tests apply to Python model outputs just like SQL model outputs
- **No streaming** — Python models run as batch jobs

### When Python Beats SQL

A good rule of thumb: if you're writing more than 3 nested window functions or a recursive CTE just to compute something that's 5 lines of pandas, reach for a Python model. Keep the DAG clean by having the Python model output a clean, typed table that downstream SQL models can reference normally.

```bash
# Run just your Python model
dbt run --select fct_ml_features

# Python models compile too — inspect the generated code
dbt compile --select fct_ml_features
```

Python models let you bring the full power of the Python data ecosystem into your dbt DAG without leaving the project structure, lineage tracking, or testing framework you already rely on.

## 10:03 - dbt Model Versioning: Managing Breaking Changes Without Breaking Consumers

Introduced in dbt 1.5, **model versioning** gives you a structured way to evolve a model's schema without immediately breaking every downstream consumer. Instead of silently changing a column name and hoping nobody notices, you publish a new version alongside the old one, let consumers migrate at their own pace, and deprecate the old version when it's safe.

### The Problem It Solves

When a widely-used model like `fct_orders` needs a breaking change — renaming `total_cents` to `amount_usd`, dropping a column, changing a join key — you face a painful choice: make the change and break everything, or keep the old column forever as dead weight. Model versioning offers a third option.

### Defining Versions in YAML

Mark a model as versioned by adding a `versions` block in its schema YAML:

```yaml
# models/fct_orders.yml
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 1
        deprecation_date: "2026-10-01"
      - v: 2
```

Then create versioned SQL files following dbt's naming convention:

```
models/
  fct_orders_v1.sql   # or fct_orders.sql with defined_in: fct_orders
  fct_orders_v2.sql
```

Alternatively, use `defined_in` to point to a differently-named file:

```yaml
versions:
  - v: 1
    defined_in: fct_orders   # maps to models/fct_orders.sql
  - v: 2
    defined_in: fct_orders_v2
```

### Referencing Versioned Models

Consumers use `ref()` with an optional `version` argument:

```sql
-- Pin to v1 while you migrate
select * from {{ ref('fct_orders', version=1) }}

-- Or use the latest_version automatically (no version arg needed)
select * from {{ ref('fct_orders') }}
```

When `latest_version: 2` is set, `ref('fct_orders')` without a version always resolves to v2. Downstream models still pinned to v1 get a deprecation warning during `dbt run` once `deprecation_date` is set.

### Column-Level Versioning with `include` / `exclude`

v2 often shares most columns with v1. Instead of duplicating SQL, define shared columns via `include`/`exclude` in the YAML:

```yaml
versions:
  - v: 1
    columns:
      - include: all
        exclude: [amount_usd]   # v1 uses total_cents, not amount_usd
  - v: 2
    columns:
      - include: all
```

This lets dbt validate that each version exposes exactly the columns you declare, catching schema drift at `dbt parse` time.

### Running and Selecting Versioned Models

```bash
# Run only v2
dbt run --select fct_orders.v2

# Run all versions
dbt run --select fct_orders

# Run the latest version only
dbt run --select fct_orders.latest
```

### Deprecation Workflow

1. **Ship v2** alongside v1 with no `deprecation_date` on v1 yet.
2. **Notify consumers** — the lineage graph shows every model referencing v1.
3. **Set `deprecation_date`** on v1; dbt emits warnings during runs for any model still using it.
4. **After the date passes**, delete the v1 SQL file and remove it from the YAML. Consumers that haven't migrated will get a hard compile error, which is the intended forcing function.

### Key Constraints

- Versioning requires a **model contract** (`contract: {enforced: true}`) on at least the latest version — dbt enforces the column list and types at build time.
- Only models with a `latest_version` key are considered "versioned"; everything else behaves as before.
- Works with all materializations (table, incremental, view, ephemeral).

Model versioning transforms breaking changes from a cross-team coordination nightmare into a managed, traceable migration — an essential pattern for any dbt project serving multiple downstream teams or external BI tools.

## 15:04 - dbt Sources: Declaring Raw Tables, Freshness Checks, and Why `source()` Beats Hardcoding

Every dbt project eventually needs to read from raw tables loaded by an ETL pipeline — Fivetran, Airbyte, Kafka, custom scripts. The choice between hardcoding `raw.salesforce.accounts` vs using `{{ source('salesforce', 'accounts') }}` seems cosmetic at first, but it unlocks lineage tracking, automated freshness monitoring, and a single place to manage your raw layer.

### Defining Sources in YAML

Sources live in `.yml` files anywhere under `models/` (typically a `sources.yml` per schema):

```yaml
# models/staging/salesforce/sources.yml
version: 2

sources:
  - name: salesforce
    database: raw
    schema: salesforce
    description: "Raw Salesforce data loaded by Fivetran"
    tables:
      - name: accounts
        description: "CRM accounts, one row per Salesforce Account object"
        columns:
          - name: id
            description: "Salesforce Account ID"
            tests:
              - unique
              - not_null
          - name: name
            tests:
              - not_null
      - name: opportunities
      - name: contacts
```

Reference in a staging model:

```sql
-- models/staging/salesforce/stg_salesforce__accounts.sql
select
    id                as account_id,
    name              as account_name,
    industry,
    annual_revenue,
    created_date::date as created_date
from {{ source('salesforce', 'accounts') }}
```

This ties `stg_salesforce__accounts` to `raw.salesforce.accounts` in the DAG — the lineage view now shows the edge from the raw source into your staging model.

### Source Freshness: Alerting on Stale Ingestion

The real power comes from freshness checks. Add `loaded_at_field` and `freshness` thresholds to any table:

```yaml
sources:
  - name: salesforce
    database: raw
    schema: salesforce
    loaded_at_field: _fivetran_synced   # column dbt reads to determine last load time
    freshness:
      warn_after: {count: 12, period: hour}
      error_after: {count: 24, period: hour}
    tables:
      - name: accounts
      - name: opportunities
        # Override freshness per-table if SLA differs
        freshness:
          warn_after: {count: 6, period: hour}
          error_after: {count: 12, period: hour}
      - name: contacts
        freshness: null   # Explicitly disable for this table
```

Run freshness checks independently (no model compilation needed):

```bash
dbt source freshness

# Target specific sources only
dbt source freshness --select source:salesforce
dbt source freshness --select source:salesforce.opportunities
```

dbt queries `max(_fivetran_synced)` from each table, compares it to the current timestamp, and reports `pass`, `warn`, or `error`. Results write to `target/sources.json` so your orchestrator can consume them.

### Integrating Freshness into CI/CD

Run freshness checks before `dbt run` in your pipeline to catch stale sources before building downstream models on bad data:

```bash
# Fail the pipeline if any source is stale
dbt source freshness && dbt build
```

In dbt Cloud, freshness failures surface in the job run UI alongside model failures, and you can configure separate notification channels per source.

### Source Tests vs Model Tests

Sources support the same generic tests as models. The key difference: source tests catch bad data **at ingestion**, before it contaminates your staging or mart layer. Run them explicitly:

```bash
dbt test --select source:salesforce
```

### `source()` vs Hardcoding — Why It Matters

| Hardcoded `raw.salesforce.accounts` | `{{ source('salesforce', 'accounts') }}` |
|---|---|
| Invisible in lineage DAG | Full upstream → downstream lineage |
| No freshness monitoring | `dbt source freshness` works |
| Schema rename = grep across all files | One `schema:` change in YAML |
| No centralized docs/tests | Tests & descriptions co-located |

### Overriding Schema per Environment

Use `generate_schema_name` or `dbt_project.yml` variable overrides to point sources at different schemas in dev vs prod without changing the YAML:

```yaml
# dbt_project.yml
vars:
  salesforce_schema: "{{ env_var('SALESFORCE_SCHEMA', 'salesforce') }}"
```

```yaml
# sources.yml
sources:
  - name: salesforce
    schema: "{{ var('salesforce_schema') }}"
```

Sources are the foundation of a well-structured dbt project — declare them explicitly, test them at the boundary, and monitor their freshness so a broken Fivetran sync doesn't silently flow stale data into your production dashboards.
