## 00:03 - [Data Engineering] Snowflake Micro-Partitions: Why Your Clustering Key Isn't Pruning

Snowflake has no user-defined partitions. It splits every table into **micro-partitions** — immutable, columnar blocks of ~50–500 MB uncompressed (16 MB compressed on average) created in insertion order. Each block stores per-column min/max, distinct counts, and null counts in metadata. Query pruning is just this: the optimizer reads that metadata, skips blocks whose min/max range can't satisfy your predicate, and never touches the storage.

That means **performance is a function of how correlated your filter column is with insert order**, not of any DDL you wrote.

Diagnose before you touch anything:

```sql
SELECT SYSTEM$CLUSTERING_INFORMATION('analytics.fct_orders', '(order_date)');
```

The key field is `average_overlaps` — how many micro-partitions share a value range for that column. Near 0 means excellent pruning. In the hundreds means nearly every block must be scanned. Confirm with the actual query: run it, then check Query Profile's *TableScan* node for "partitions scanned / partitions total". If you scanned 9,800 of 10,000 partitions, no clustering key is active on the column you filtered by.

Three fixes, cheapest first:

1. **Load in sorted order.** `INSERT ... ORDER BY event_date` or sorted staged files gives natural clustering for free. This alone solves most cases.
2. **Cluster on low-cardinality-first expressions.** `CLUSTER BY (event_date, customer_id)` works; `CLUSTER BY (uuid)` is useless — every block spans the whole range. For high-cardinality keys, truncate: `CLUSTER BY (TO_DATE(ts), LEFT(user_id, 4))`.
3. **Automatic Clustering only when reads justify it.** It's a background serverless service billed by credits consumed re-writing partitions. A table rewritten hourly by DML will churn continuously; check `AUTOMATIC_CLUSTERING_HISTORY` before enabling it broadly.

The silent killer: wrapping the filter column in a function. `WHERE DATE_TRUNC('month', order_ts) = '2026-08-01'` defeats min/max pruning entirely. Rewrite as a range — `WHERE order_ts >= '2026-08-01' AND order_ts < '2026-09-01'` — and the same query can drop from a full scan to a handful of partitions.

## 05:03 - [Data Analytics] Gaps-and-Islands: Finding Consecutive Runs in SQL

"Gaps-and-islands" is the classic pattern for collapsing consecutive rows into ranges (**islands**) or finding the missing stretches (**gaps**). It shows up everywhere: consecutive login streaks, contiguous status periods, uninterrupted subscription spans, sequential ID ranges.

**The core trick: the difference of two row numbers is constant within an island.**

Say a user logged in on these dates and you want their streaks:

```sql
WITH logins AS (
  SELECT user_id, login_date FROM daily_logins
),
grouped AS (
  SELECT
    user_id,
    login_date,
    -- subtract a dense sequence from the date; consecutive days share one value
    DATEADD(
      day,
      -ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date),
      login_date
    ) AS grp
  FROM logins
)
SELECT
  user_id,
  MIN(login_date) AS streak_start,
  MAX(login_date) AS streak_end,
  COUNT(*)        AS streak_length
FROM grouped
GROUP BY user_id, grp
ORDER BY user_id, streak_start;
```

**Why it works:** for consecutive dates, `login_date` and `ROW_NUMBER` both increase by 1 each row, so `date - row_number` stays fixed. The moment a day is skipped, the date jumps but the row number doesn't, producing a new `grp` value. Grouping on `grp` collapses each run.

For an integer sequence, use `id - ROW_NUMBER()` directly. For **status islands** (collapse adjacent rows with the same status), subtract two row numbers instead:

```sql
ROW_NUMBER() OVER (PARTITION BY device ORDER BY ts)
- ROW_NUMBER() OVER (PARTITION BY device, status ORDER BY ts) AS grp
```

Rows keep the same `grp` only while `status` is unchanged and contiguous.

**Finding gaps** is the complement — compare each row to the next with `LEAD`:

```sql
SELECT id + 1 AS gap_start, next_id - 1 AS gap_end
FROM (
  SELECT id, LEAD(id) OVER (ORDER BY id) AS next_id FROM tickets
) t
WHERE next_id - id > 1;
```

**Practical notes:** dedupe first if a "day" can appear twice (`GROUP BY` or `DISTINCT`), or the row-number arithmetic drifts. For calendar gaps that include days with *zero* rows, join against a date spine before applying the pattern — the sequence trick only sees rows that exist.

## 10:03 - [ML & AI] Target Encoding High-Cardinality Categoricals Without Leaking

One-hot encoding falls apart when a column has 50,000 ZIP codes or merchant IDs. **Target encoding** replaces each category with the mean target value for that category — one column instead of 50,000. It is also the single easiest way to leak your label into your features.

**The naive version is broken.** If a merchant appears once and that transaction was fraud, its encoding becomes 1.0 — a perfect predictor of a row the model is about to be trained on. Validation looks great; production collapses.

Two fixes, and you need both.

**1. Smoothing** pulls rare categories toward the global mean:

```
encoded = (n · mean_category + m · mean_global) / (n + m)
```

`n` is the category's row count; `m` is a smoothing weight (10–50 is typical, tune it). Worked example — global churn rate 0.20, plan "Z" has 3 customers of whom 2 churned:

- Raw: 2/3 = **0.667** (wild overfit on 3 rows)
- Smoothed, m=20: (3·0.667 + 20·0.20) / 23 = 6/23 = **0.261**

With 3,000 rows instead of 3, the same 0.667 barely moves: (3000·0.667 + 4) / 3020 = 0.664. Smoothing only bites where the evidence is thin, which is exactly right.

**2. Out-of-fold computation.** Each row's encoding must come from folds that exclude it:

```python
from sklearn.model_selection import KFold
import numpy as np

def oof_target_encode(x, y, m=20, n_splits=5, seed=0):
    prior, out = y.mean(), np.zeros(len(y))
    for tr, va in KFold(n_splits, shuffle=True, random_state=seed).split(x):
        stats = y.iloc[tr].groupby(x.iloc[tr]).agg(['sum', 'count'])
        enc = (stats['sum'] + m * prior) / (stats['count'] + m)
        out[va] = x.iloc[va].map(enc).fillna(prior).values
    return out
```

Fit the *full-data* encoding map separately and apply it to test/production rows; unseen categories fall back to the prior.

**Sanity check:** if a single categorical column jumps your CV AUC by 0.15, you are looking at leakage, not a feature. Also prefer CatBoost's ordered target statistics or plain frequency encoding when you want this handled for you.

## 15:04 - [Crypto & Business] Stablecoin Peg Mechanics: What Actually Holds $1

A stablecoin's ticker says $1. What *enforces* it is a redemption path, and the three main designs enforce it very differently.

**Fiat-backed (USDC, USDT).** The issuer holds T-bills and cash, and lets approved institutions mint/redeem 1:1. That redemption right is the whole mechanism. If USDC trades at $0.985 on an exchange, an authorized participant buys 10M tokens for $9.85M, redeems with the issuer for $10M, and pockets $150K. That arbitrage is what drags the price back. Kill the redemption path and the peg goes with it: in March 2023, USDC fell to ~$0.87 when $3.3B of its reserves sat in a failed bank over a weekend and redemptions paused. It recovered within days — once redemptions reopened.

**Crypto-collateralized (DAI-style).** You lock volatile collateral and borrow against it, overcollateralized — typically 150%+. Lock $15,000 of ETH, mint 10,000 DAI. If ETH drops so your ratio falls below the liquidation threshold, a keeper repays your debt, seizes the collateral, and takes a penalty (often 8-13%). Overcollateralization is the buffer; liquidation is the enforcement.

**Algorithmic / undercollateralized.** Backed by a companion token the protocol prints on demand. UST let you always swap 1 UST for $1 of newly minted LUNA. When UST slipped below peg in May 2022, holders redeemed, LUNA supply exploded, LUNA's price collapsed, and each redemption required minting more — a reflexive spiral that erased ~$40B in days. The backing was the thing being sold.

**Practical checks before holding any of them:**
- Who can redeem at par, and in what size? Retail-inaccessible redemption is a weaker peg for you than for a market maker.
- What's the reserve composition and attestation cadence? Short-duration T-bills ≠ commercial paper ≠ "an affiliated token."
- Is yield being paid? Sustained double-digit yield on a "stable" asset is compensation for a risk somebody has priced.
