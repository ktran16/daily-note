## 00:03 - [Data Engineering] Snowflake Micro-Partitions: Why Your Clustering Key Isn't Pruning

Snowflake has no user-defined partitions. It splits every table into **micro-partitions** — immutable, columnar blocks of ~50–500 MB uncompressed (16 MB compressed on average) created in insertion order. Each block stores per-column min/max, distinct counts, and null counts in metadata. Query pruning is just this: the optimizer reads that metadata, skips blocks whose min/max range can't satisfy your predicate, and never touches the storage.

That means **performance is a function of how correlated your filter column is with insert order**, not of any DDL you wrote.

Diagnose before you touch anything:

```sql
SELECT SYSTEM$CLUSTERING_INFORMATION('analytics.fct_orders', '(order_date)');
```

The key field is `average_overlaps` — how many micro-partitions share a value range for that column. Near 0 means excellent pruning. In the hundreds means nearly every block must be scanned. Confirm with the actual query: run it, then check Query Profile's *TableScan* node for "partitions scanned / partitions total". If you scanned 9,800 of 10,000 partitions, no clustering key is active on the column you filtered by.

Three fixes, cheapest first:

1. **Load in sorted order.** `INSERT ... ORDER BY event_date` or sorted staged files gives natural clustering for free. This alone solves most cases.
2. **Cluster on low-cardinality-first expressions.** `CLUSTER BY (event_date, customer_id)` works; `CLUSTER BY (uuid)` is useless — every block spans the whole range. For high-cardinality keys, truncate: `CLUSTER BY (TO_DATE(ts), LEFT(user_id, 4))`.
3. **Automatic Clustering only when reads justify it.** It's a background serverless service billed by credits consumed re-writing partitions. A table rewritten hourly by DML will churn continuously; check `AUTOMATIC_CLUSTERING_HISTORY` before enabling it broadly.

The silent killer: wrapping the filter column in a function. `WHERE DATE_TRUNC('month', order_ts) = '2026-08-01'` defeats min/max pruning entirely. Rewrite as a range — `WHERE order_ts >= '2026-08-01' AND order_ts < '2026-09-01'` — and the same query can drop from a full scan to a handful of partitions.

## 05:03 - [Data Analytics] Gaps-and-Islands: Finding Consecutive Runs in SQL

"Gaps-and-islands" is the classic pattern for collapsing consecutive rows into ranges (**islands**) or finding the missing stretches (**gaps**). It shows up everywhere: consecutive login streaks, contiguous status periods, uninterrupted subscription spans, sequential ID ranges.

**The core trick: the difference of two row numbers is constant within an island.**

Say a user logged in on these dates and you want their streaks:

```sql
WITH logins AS (
  SELECT user_id, login_date FROM daily_logins
),
grouped AS (
  SELECT
    user_id,
    login_date,
    -- subtract a dense sequence from the date; consecutive days share one value
    DATEADD(
      day,
      -ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date),
      login_date
    ) AS grp
  FROM logins
)
SELECT
  user_id,
  MIN(login_date) AS streak_start,
  MAX(login_date) AS streak_end,
  COUNT(*)        AS streak_length
FROM grouped
GROUP BY user_id, grp
ORDER BY user_id, streak_start;
```

**Why it works:** for consecutive dates, `login_date` and `ROW_NUMBER` both increase by 1 each row, so `date - row_number` stays fixed. The moment a day is skipped, the date jumps but the row number doesn't, producing a new `grp` value. Grouping on `grp` collapses each run.

For an integer sequence, use `id - ROW_NUMBER()` directly. For **status islands** (collapse adjacent rows with the same status), subtract two row numbers instead:

```sql
ROW_NUMBER() OVER (PARTITION BY device ORDER BY ts)
- ROW_NUMBER() OVER (PARTITION BY device, status ORDER BY ts) AS grp
```

Rows keep the same `grp` only while `status` is unchanged and contiguous.

**Finding gaps** is the complement — compare each row to the next with `LEAD`:

```sql
SELECT id + 1 AS gap_start, next_id - 1 AS gap_end
FROM (
  SELECT id, LEAD(id) OVER (ORDER BY id) AS next_id FROM tickets
) t
WHERE next_id - id > 1;
```

**Practical notes:** dedupe first if a "day" can appear twice (`GROUP BY` or `DISTINCT`), or the row-number arithmetic drifts. For calendar gaps that include days with *zero* rows, join against a date spine before applying the pattern — the sequence trick only sees rows that exist.
