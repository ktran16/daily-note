## 00:03 - dbt Model Contracts: Enforcing Schema at Build Time

**What are Model Contracts?**

Introduced in dbt v1.5, model contracts let you declare the exact schema a model must produce — column names, data types, and constraints — and have dbt enforce those expectations at build time rather than discovering mismatches downstream.

Without contracts, a refactor that renames a column silently breaks downstream models and dashboards. With a contract, that same refactor fails loudly at `dbt run` before it can do damage.

**Enabling a Contract**

Add `contract: {enforced: true}` to a model's config and fully declare your columns in `schema.yml`:

```yaml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_total
        data_type: numeric
      - name: ordered_at
        data_type: timestamp
```

When you run `dbt run`, dbt compares the compiled query's output schema against the declared columns. If any column is missing, extra, or has a wrong type, the run fails immediately with a clear error.

**Constraints**

Constraints are hints to the database (or enforced by dbt, depending on adapter support):

| Constraint | dbt enforces | DB enforces |
|---|---|---|
| `not_null` | ✓ (via test) | depends |
| `primary_key` | ✓ (via test) | depends |
| `unique` | ✓ (via test) | depends |
| `check` | ✗ | adapter-specific |
| `foreign_key` | ✗ | adapter-specific |

Adapters like Snowflake, BigQuery, and Postgres have varying levels of constraint enforcement — check your adapter docs.

**Contracts and Versioned Models**

Contracts shine most when combined with **model versioning** (`version: 2` in model config). Consumers pin to a specific version (`ref('fct_orders', v=2)`), and contracts guarantee that version's schema is stable. When you need a breaking change, you publish a new version (`v=3`) and migrate consumers on your own timeline.

**Best Practices**

- Enable contracts on **public models** shared across teams or used by BI tools first.
- Pair contracts with `meta.owner` so there's a clear point of contact when a contract violation is caught in CI.
- Run `dbt compile` locally to catch contract violations before pushing to CI.
- Don't try to contract ephemeral models — contracts require a materialization that persists to the warehouse (`table`, `incremental`, or `view`).

Model contracts are a lightweight way to treat your dbt models as published APIs rather than moving targets, making cross-team collaboration much safer.

## 05:04 - dbt Snapshots: Tracking Slowly Changing Dimensions

**What are Snapshots?**

dbt snapshots implement **Type 2 Slowly Changing Dimensions (SCD2)** — they capture how a row looked at any point in time by appending a new record whenever the source data changes, rather than overwriting it. This lets you answer questions like "what was this customer's status last quarter?" without building a custom CDC pipeline.

**Defining a Snapshot**

Snapshots live in the `snapshots/` directory and use a `{% snapshot %}` block:

```sql
{% snapshot orders_snapshot %}

{{
  config(
    target_schema='snapshots',
    unique_key='order_id',
    strategy='timestamp',
    updated_at='updated_at',
  )
}}

select * from {{ source('raw', 'orders') }}

{% endsnapshot %}
```

Run with `dbt snapshot`. dbt adds four metadata columns to the snapshot table:

| Column | Meaning |
|---|---|
| `dbt_scd_id` | Unique surrogate key for each snapshot row |
| `dbt_updated_at` | When dbt last processed this record |
| `dbt_valid_from` | When this version of the row became active |
| `dbt_valid_to` | When this version expired (`NULL` = current) |

**Two Strategies**

- **`timestamp`** — compares `updated_at` (or any timestamp column). Most reliable; requires the source to maintain an accurate updated-at field.
- **`check`** — compares a list of columns (`check_cols`) directly. Catches changes even without an updated-at field, but runs a row-by-row comparison so it can be slower at scale.

```sql
-- check strategy example
{{
  config(
    strategy='check',
    unique_key='customer_id',
    check_cols=['status', 'plan_tier', 'region'],
  )
}}
```

**Querying Snapshots**

To get only the current record for each key, filter where `dbt_valid_to` is null:

```sql
select *
from {{ ref('orders_snapshot') }}
where dbt_valid_to is null
```

To reconstruct state as of a specific date:

```sql
select *
from {{ ref('orders_snapshot') }}
where dbt_valid_from <= '2025-12-31'
  and (dbt_valid_to > '2025-12-31' or dbt_valid_to is null)
```

**Best Practices**

- Always snapshot from **source tables**, never from other dbt models — snapshots need the raw, unfiltered record.
- Schedule `dbt snapshot` **before** `dbt run` so downstream models always see the freshest history.
- Use the `invalidate_hard_deletes=true` config to mark rows as expired when they disappear from the source, instead of leaving them open indefinitely.
- Keep `unique_key` as the natural business key (e.g., `order_id`), not a surrogate — snapshots generate their own surrogate via `dbt_scd_id`.

Snapshots are the cleanest way to preserve history in a warehouse without writing custom ETL, and they compose naturally with incremental models and marts built on top of them.
