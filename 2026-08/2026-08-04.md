## 00:03 - dbt Model Contracts: Enforcing Schema at Build Time

**What are Model Contracts?**

Introduced in dbt v1.5, model contracts let you declare the exact schema a model must produce — column names, data types, and constraints — and have dbt enforce those expectations at build time rather than discovering mismatches downstream.

Without contracts, a refactor that renames a column silently breaks downstream models and dashboards. With a contract, that same refactor fails loudly at `dbt run` before it can do damage.

**Enabling a Contract**

Add `contract: {enforced: true}` to a model's config and fully declare your columns in `schema.yml`:

```yaml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_total
        data_type: numeric
      - name: ordered_at
        data_type: timestamp
```

When you run `dbt run`, dbt compares the compiled query's output schema against the declared columns. If any column is missing, extra, or has a wrong type, the run fails immediately with a clear error.

**Constraints**

Constraints are hints to the database (or enforced by dbt, depending on adapter support):

| Constraint | dbt enforces | DB enforces |
|---|---|---|
| `not_null` | ✓ (via test) | depends |
| `primary_key` | ✓ (via test) | depends |
| `unique` | ✓ (via test) | depends |
| `check` | ✗ | adapter-specific |
| `foreign_key` | ✗ | adapter-specific |

Adapters like Snowflake, BigQuery, and Postgres have varying levels of constraint enforcement — check your adapter docs.

**Contracts and Versioned Models**

Contracts shine most when combined with **model versioning** (`version: 2` in model config). Consumers pin to a specific version (`ref('fct_orders', v=2)`), and contracts guarantee that version's schema is stable. When you need a breaking change, you publish a new version (`v=3`) and migrate consumers on your own timeline.

**Best Practices**

- Enable contracts on **public models** shared across teams or used by BI tools first.
- Pair contracts with `meta.owner` so there's a clear point of contact when a contract violation is caught in CI.
- Run `dbt compile` locally to catch contract violations before pushing to CI.
- Don't try to contract ephemeral models — contracts require a materialization that persists to the warehouse (`table`, `incremental`, or `view`).

Model contracts are a lightweight way to treat your dbt models as published APIs rather than moving targets, making cross-team collaboration much safer.

## 05:04 - dbt Snapshots: Tracking Slowly Changing Dimensions

**What are Snapshots?**

dbt snapshots implement **Type 2 Slowly Changing Dimensions (SCD2)** — they capture how a row looked at any point in time by appending a new record whenever the source data changes, rather than overwriting it. This lets you answer questions like "what was this customer's status last quarter?" without building a custom CDC pipeline.

**Defining a Snapshot**

Snapshots live in the `snapshots/` directory and use a `{% snapshot %}` block:

```sql
{% snapshot orders_snapshot %}

{{
  config(
    target_schema='snapshots',
    unique_key='order_id',
    strategy='timestamp',
    updated_at='updated_at',
  )
}}

select * from {{ source('raw', 'orders') }}

{% endsnapshot %}
```

Run with `dbt snapshot`. dbt adds four metadata columns to the snapshot table:

| Column | Meaning |
|---|---|
| `dbt_scd_id` | Unique surrogate key for each snapshot row |
| `dbt_updated_at` | When dbt last processed this record |
| `dbt_valid_from` | When this version of the row became active |
| `dbt_valid_to` | When this version expired (`NULL` = current) |

**Two Strategies**

- **`timestamp`** — compares `updated_at` (or any timestamp column). Most reliable; requires the source to maintain an accurate updated-at field.
- **`check`** — compares a list of columns (`check_cols`) directly. Catches changes even without an updated-at field, but runs a row-by-row comparison so it can be slower at scale.

```sql
-- check strategy example
{{
  config(
    strategy='check',
    unique_key='customer_id',
    check_cols=['status', 'plan_tier', 'region'],
  )
}}
```

**Querying Snapshots**

To get only the current record for each key, filter where `dbt_valid_to` is null:

```sql
select *
from {{ ref('orders_snapshot') }}
where dbt_valid_to is null
```

To reconstruct state as of a specific date:

```sql
select *
from {{ ref('orders_snapshot') }}
where dbt_valid_from <= '2025-12-31'
  and (dbt_valid_to > '2025-12-31' or dbt_valid_to is null)
```

**Best Practices**

- Always snapshot from **source tables**, never from other dbt models — snapshots need the raw, unfiltered record.
- Schedule `dbt snapshot` **before** `dbt run` so downstream models always see the freshest history.
- Use the `invalidate_hard_deletes=true` config to mark rows as expired when they disappear from the source, instead of leaving them open indefinitely.
- Keep `unique_key` as the natural business key (e.g., `order_id`), not a surrogate — snapshots generate their own surrogate via `dbt_scd_id`.

Snapshots are the cleanest way to preserve history in a warehouse without writing custom ETL, and they compose naturally with incremental models and marts built on top of them.

## 10:03 - dbt Incremental Models: Building Efficient Large-Scale Pipelines

**Why Incremental?**

Rebuilding a full table on every `dbt run` is fine for small models, but at millions of rows it becomes slow and expensive. Incremental models solve this by processing only **new or changed records** and merging them into the existing table, making runs faster and warehouse costs lower.

**Basic Pattern**

Set `materialized='incremental'` and add an `{% if is_incremental() %}` filter that limits the query to recent data on subsequent runs:

```sql
{{ config(
    materialized='incremental',
    unique_key='event_id'
) }}

select
    event_id,
    user_id,
    event_type,
    occurred_at
from {{ source('raw', 'events') }}

{% if is_incremental() %}
  -- only process rows newer than the latest row already in the table
  where occurred_at > (select max(occurred_at) from {{ this }})
{% endif %}
```

`{{ this }}` refers to the model's own table in the warehouse. On the **first run** `is_incremental()` is false, so the full dataset is loaded. On every subsequent run, only the filtered rows are processed.

**Incremental Strategies**

dbt supports several merge strategies, set via `incremental_strategy`:

| Strategy | Behavior | Best for |
|---|---|---|
| `append` | Insert new rows only, no dedup | Immutable event logs |
| `merge` | Upsert using `unique_key` | Mutable records (orders, users) |
| `delete+insert` | Delete matched rows, re-insert | Late-arriving data corrections |
| `insert_overwrite` | Overwrite entire partitions | Partitioned tables (BigQuery) |

```sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge',
    merge_update_columns=['status', 'updated_at']  -- only update these cols on match
) }}
```

`merge_update_columns` is a powerful option — it prevents overwriting stable columns (like `created_at`) when the row already exists.

**Handling Late-Arriving Data**

A common gotcha: using `max(occurred_at)` as the cutoff will miss events that arrive late. Add a **lookback window** to re-process the last few hours or days:

```sql
{% if is_incremental() %}
  where occurred_at > (
    select dateadd('hour', -3, max(occurred_at)) from {{ this }}
  )
{% endif %}
```

Pair this with `unique_key` and `merge` strategy so re-processed duplicates are upserted rather than duplicated.

**Full Refresh**

To rebuild the full table from scratch (e.g., after a logic change), run:

```bash
dbt run --select my_model --full-refresh
```

This bypasses `is_incremental()` and recreates the table entirely. Useful after backfilling source data or changing the `unique_key`.

**Best Practices**

- Always define a `unique_key` when using `merge` — without it, dbt appends duplicates.
- Test your incremental filter logic by running `dbt run --full-refresh` and comparing row counts to a fresh build.
- Use `on_schema_change='append_new_columns'` to automatically handle new columns added to the source without a full refresh:
  ```sql
  {{ config(on_schema_change='append_new_columns') }}
  ```
- For very high-volume tables on BigQuery or Spark, combine incremental with **partitioning** (`partition_by`) so the engine scans only the relevant partitions rather than merging across the whole table.

Incremental models are the primary lever for scaling dbt projects — once you understand the filter pattern and strategy options, you can handle billions of rows as efficiently as thousands.

## 15:03 - dbt Macros & Jinja: Writing Reusable SQL Logic

**What are Macros?**

Macros are Jinja-templated functions that let you write reusable SQL fragments, apply DRY principles across models, and generate dynamic SQL at compile time. They live in the `macros/` directory and are called with `{{ macro_name(...) }}` inside models, tests, and other macros.

Think of macros as SQL functions — but evaluated by dbt before the query hits your warehouse, so they add zero runtime overhead.

**A Simple Macro**

```sql
-- macros/cents_to_dollars.sql
{% macro cents_to_dollars(column_name) %}
  round({{ column_name }} / 100.0, 2)
{% endmacro %}
```

Call it in a model:

```sql
select
    order_id,
    {{ cents_to_dollars('amount_cents') }} as amount_dollars
from {{ ref('stg_orders') }}
```

dbt compiles this to plain SQL before sending it to the warehouse — no macro overhead at query time.

**Macros with Default Arguments**

```sql
{% macro date_trunc(datepart, date, default_datepart='day') %}
  date_trunc('{{ datepart | default(default_datepart) }}', {{ date }})
{% endmacro %}
```

Jinja's `default()` filter lets you make arguments optional with sensible fallbacks.

**Cross-Database Macros**

One of the biggest macro use cases is abstracting away warehouse-specific SQL. dbt itself uses this pattern internally for adapter dispatching:

```sql
{% macro generate_surrogate_key(field_list) %}
    {{ return(adapter.dispatch('generate_surrogate_key', 'dbt_utils')(field_list)) }}
{% endmacro %}
```

For your own cross-database logic, use `target.type`:

```sql
{% macro safe_divide(numerator, denominator) %}
  {% if target.type == 'bigquery' %}
    safe_divide({{ numerator }}, {{ denominator }})
  {% else %}
    case when {{ denominator }} = 0 then null
         else {{ numerator }}::float / {{ denominator }}
    end
{% endif %}
{% endmacro %}
```

**Generating Models Dynamically**

Macros can return full SQL blocks, enabling meta-programming patterns:

```sql
-- macros/union_relations.sql
{% macro union_tables(tables) %}
  {% for table in tables %}
    select *, '{{ table }}' as source_table
    from {{ ref(table) }}
    {% if not loop.last %} union all {% endif %}
  {% endfor %}
{% endmacro %}

-- usage in a model
{{ union_tables(['stg_events_us', 'stg_events_eu', 'stg_events_apac']) }}
```

**`run_query` for Metadata-Driven Logic**

The `run_query` macro executes a SQL statement during compilation and returns the result — useful for building dynamic column lists:

```sql
{% macro get_column_values(table, column) %}
  {% set query %}
    select distinct {{ column }} from {{ table }} order by 1
  {% endset %}
  {% set results = run_query(query) %}
  {% if execute %}
    {% set values = results.columns[0].values() %}
    {{ return(values) }}
  {% endif %}
{% endmacro %}
```

The `{% if execute %}` guard is essential — it prevents the macro from running during `dbt compile` (parse phase) when no warehouse connection exists.

**Calling Macros from `dbt run-operation`**

You can invoke a macro directly from the CLI without a model:

```bash
dbt run-operation my_macro --args '{"schema": "staging", "dry_run": false}'
```

This is handy for administrative tasks like dropping stale schemas, granting permissions, or seeding lookup tables.

**Best Practices**

- Keep macros **focused** — one macro, one job. Avoid macros that do too many things.
- Always guard warehouse-specific branches with `target.type` or use `adapter.dispatch` for proper adapter overrides.
- Use `{% if execute %}` when calling `run_query` to avoid parse-time errors.
- Prefer `dbt-utils` package macros (`generate_surrogate_key`, `safe_add`, `union_relations`) over reinventing them — they're tested across adapters.
- Document macros in `schema.yml` under a `macros:` key with `arguments:` blocks so `dbt docs generate` picks them up.

Macros are where dbt goes from "SQL runner" to "SQL framework" — once you're comfortable with them, you'll stop copying boilerplate across models and start building a reusable macro library your whole team benefits from.

## 19:04 - dbt Tests: Generic & Singular

**Why Tests Matter**

dbt's testing framework lets you assert data quality expectations directly in your project — without a separate testing tool. Failed tests surface in CI before bad data reaches dashboards or downstream consumers. Tests run with `dbt test` and integrate naturally with `dbt build` (which runs models, tests, seeds, and snapshots in dependency order).

**Generic Tests**

Generic tests are reusable assertions applied to columns via `schema.yml`. dbt ships four out of the box:

```yaml
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - unique
          - not_null
      - name: status
        tests:
          - accepted_values:
              values: ['placed', 'shipped', 'returned', 'cancelled']
      - name: customer_id
        tests:
          - relationships:
              to: ref('dim_customers')
              field: customer_id
```

| Test | What it checks |
|---|---|
| `unique` | No duplicate values in the column |
| `not_null` | No NULL values in the column |
| `accepted_values` | All values belong to the declared list |
| `relationships` | Every FK value exists in the referenced table |

**Writing Custom Generic Tests**

When the built-in four aren't enough, write your own in `tests/generic/`. A generic test is a macro that returns a SQL query — if the query returns any rows, the test fails:

```sql
-- tests/generic/not_negative.sql
{% test not_negative(model, column_name) %}

select {{ column_name }}
from {{ model }}
where {{ column_name }} < 0

{% endtest %}
```

Apply it like any built-in test:

```yaml
- name: order_total
  tests:
    - not_negative
```

**Singular Tests**

Singular tests are one-off SQL files in the `tests/` directory. Each file is a query — if it returns rows, the test fails. They're ideal for complex assertions that don't generalize:

```sql
-- tests/assert_revenue_never_decreases.sql
-- Fails if any day's revenue is lower than the previous day's

with daily_revenue as (
    select
        date_trunc('day', ordered_at) as day,
        sum(order_total)              as revenue
    from {{ ref('fct_orders') }}
    group by 1
)
select
    curr.day,
    curr.revenue,
    prev.revenue as prev_revenue
from daily_revenue curr
join daily_revenue prev
    on curr.day = dateadd('day', 1, prev.day)
where curr.revenue < prev.revenue * 0.5   -- flag >50% day-over-day drop
```

**Test Severity & Thresholds**

Tests can be `warn` instead of `error`, and can tolerate a configurable number of failures:

```yaml
- name: email
  tests:
    - not_null:
        config:
          severity: warn          # don't fail the run, just warn
    - unique:
        config:
          severity: error
          error_if: ">10"         # fail only if more than 10 duplicates
          warn_if: ">0"           # warn for any duplicates below the error threshold
```

**Storing Test Failures**

Use `--store-failures` to persist failing rows to a schema for inspection:

```bash
dbt test --store-failures --target-path target/
```

Or set it project-wide in `dbt_project.yml`:

```yaml
tests:
  +store_failures: true
  +schema: test_failures
```

Each failed test writes its rows to a table in the `test_failures` schema, so you can query exactly which records violated the assertion — invaluable for debugging data quality issues in production.

**Best Practices**

- Apply `unique` + `not_null` to every primary key column — these are the minimum baseline for any model.
- Run `dbt build` in CI instead of `dbt run && dbt test` — it runs tests immediately after each model and stops early if a model's tests fail, preventing bad data from propagating to downstream models.
- Use `severity: warn` for soft assertions (e.g., coverage metrics) and `severity: error` for hard data quality gates (e.g., referential integrity).
- Scope tests to performance-sensitive models with `--select` to speed up CI: `dbt test --select tag:critical`.
- Pair `store_failures: true` with a Slack/PagerDuty alert so on-call gets notified the moment a critical test fails in production.

A well-tested dbt project treats data quality as a first-class concern — the same way software engineers treat unit tests — making the pipeline trustworthy and refactoring safe.
