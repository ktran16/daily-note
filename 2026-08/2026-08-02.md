## 00:03 - dbt Node Selection Syntax: Targeting Exactly What You Need

dbt's `--select` flag is one of its most powerful features, letting you run, test, or compile any slice of your DAG without touching the rest. Mastering selection syntax turns slow, full-project runs into fast, surgical operations.

### Basic Selection

```bash
# Run a single model
dbt run --select my_model

# Run all models in a folder
dbt run --select models/marts/

# Run all models with a tag
dbt run --select tag:nightly
```

### Graph Operators

The real power comes from graph traversal operators:

```bash
# Run my_model and all its upstream dependencies (+)
dbt run --select +my_model

# Run my_model and everything downstream of it (trailing +)
dbt run --select my_model+

# Both upstream and downstream (2 hops each side)
dbt run --select 2+my_model+2

# Everything downstream of the staging layer
dbt run --select models/staging/+
```

### Intersection and Exclusion

You can combine selectors with spaces (union) or commas (intersection), and exclude nodes with `--exclude`:

```bash
# Union: run staging OR marts models
dbt run --select models/staging/ models/marts/

# Intersection: models tagged 'finance' that are also in marts/
dbt run --select tag:finance,models/marts/

# Exclude specific models from a broad selection
dbt run --select models/marts/ --exclude my_heavy_model
```

### State-Based Selection

State-based selection is the key to **Slim CI** — only running what changed relative to a previous production artifact:

```bash
# Run models modified since the last production run
dbt run --select state:modified+ --state ./prod-artifacts/

# Test only new or changed models
dbt test --select state:modified --state ./prod-artifacts/
```

This requires a `manifest.json` from a prior run. In CI, download the production manifest before running dbt, then pass it via `--state`.

### Selecting by Method

dbt supports explicit method prefixes for fine-grained targeting:

```bash
# By resource type
dbt run --select resource_type:snapshot

# By config property
dbt run --select config.materialized:incremental

# By source
dbt test --select source:salesforce

# By exposure (run all models feeding a specific exposure)
dbt run --select +exposure:weekly_revenue_report
```

### Practical Tip: Combine for CI Speed

A solid CI pipeline pattern:

```bash
# 1. Download prod manifest.json
# 2. Run only changed models and their children
dbt run --select state:modified+ --state ./prod-artifacts/ --target ci
# 3. Test only the models you just ran
dbt test --select state:modified+ --state ./prod-artifacts/ --target ci
```

This can cut CI run times by 80%+ on large projects. Pair it with `dbt build` (which runs + tests in dependency order) for even cleaner pipelines:

```bash
dbt build --select state:modified+ --state ./prod-artifacts/
```

Understanding selection syntax pays dividends daily — it's the difference between waiting 20 minutes for a full project run and getting results in 2.

## 05:03 - dbt Model Contracts: Enforcing Schema Guarantees at Build Time

dbt model contracts let you declare the exact schema a model must produce — column names, data types, and constraints — and enforce them before the model's downstream consumers can be broken. Introduced in dbt 1.5, contracts shift schema validation from a reactive "we noticed something broke" to a proactive "the build fails if the contract is violated."

### Enabling a Contract

Contracts are enabled per-model in its `config` block or `schema.yml`:

```yaml
# schema.yml
models:
  - name: dim_customers
    config:
      contract:
        enforced: true
    columns:
      - name: customer_id
        data_type: integer
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_name
        data_type: varchar
        constraints:
          - type: not_null
      - name: created_at
        data_type: timestamp
```

When `enforced: true`, dbt will compile the model and compare the actual output columns against the declared schema. If any column is missing, has the wrong type, or an undeclared column appears, the run fails with a clear error — before any downstream models execute.

### Supported Constraints

dbt supports several constraint types (adapter support varies):

| Constraint      | Description                              |
|-----------------|------------------------------------------|
| `not_null`      | Column cannot contain NULL values        |
| `primary_key`   | Unique, not null identifier              |
| `unique`        | All values must be distinct              |
| `foreign_key`   | References a column in another model     |
| `check`         | Custom SQL expression must be true       |

```yaml
- name: order_status
  data_type: varchar
  constraints:
    - type: check
      expression: "order_status in ('pending', 'shipped', 'delivered', 'cancelled')"
```

### Contracts and Versioned Models

Contracts become especially valuable when combined with **model versioning**. When you version a model (`v1`, `v2`), you can enforce that each version exposes a stable, documented contract. Downstream refs pin to a version and trust its contract:

```sql
-- downstream model safely pinning to v1 contract
select * from {{ ref('dim_customers', v=1) }}
```

### What Contracts Don't Do

Contracts validate structure, not data quality. A column declared `not_null` in the contract won't automatically fail if NULLs appear in the data — you still need dbt tests for that. Think of contracts as a schema-level guarantee ("the column exists and is the right type") and tests as a data-level guarantee ("the values are what we expect").

### When to Use Contracts

Contracts shine in two scenarios:

1. **Shared models with many consumers** — any schema drift is caught before it cascades to dozens of downstream models or BI tools.
2. **Cross-team interfaces** — when the data team owns `dim_customers` but the analytics team writes against it, a contract is the formal API between them.

Start by adding contracts to your most-referenced mart models. The upfront schema declaration doubles as documentation and the enforcement catches regressions that column-level tests alone would miss.

## 10:03 - dbt Macros & Jinja: Writing Reusable SQL Logic

Jinja templating is the layer that turns dbt from a SQL runner into a programmable data transformation framework. Macros are reusable Jinja functions you define once and call anywhere — across models, tests, and other macros — eliminating copy-paste and centralizing logic that would otherwise drift out of sync.

### Defining a Macro

Macros live in the `macros/` directory. A simple example — a macro that generates a `CASE` expression for classifying revenue:

```sql
-- macros/classify_revenue.sql
{% macro classify_revenue(column_name) %}
  case
    when {{ column_name }} >= 10000 then 'enterprise'
    when {{ column_name }} >= 1000  then 'mid-market'
    else 'smb'
  end
{% endmacro %}
```

Call it in any model with `{{ classify_revenue('total_revenue') }}`. dbt compiles this to the full `CASE` expression before sending SQL to your warehouse.

### Jinja Fundamentals in dbt

| Syntax | Purpose |
|--------|---------|
| `{{ expr }}` | Render a value or macro call |
| `{% statement %}` | Control flow: `if`, `for`, `set` |
| `{# comment #}` | Comment stripped at compile time |

```sql
-- Dynamic column list with a for loop
select
  order_id,
  {% for metric in ['revenue', 'quantity', 'discount'] %}
    sum({{ metric }}) as total_{{ metric }}
    {% if not loop.last %},{% endif %}
  {% endfor %}
from orders
group by order_id
```

### Macro Arguments and Defaults

Macros support positional and keyword arguments with defaults:

```sql
{% macro date_spine(start_date, end_date, interval='day') %}
  {{ dbt_utils.date_spine(
      datepart=interval,
      start_date=start_date,
      end_date=end_date
  ) }}
{% endmacro %}
```

Call it as `{{ date_spine("'2024-01-01'", "'2024-12-31'") }}` (day) or override: `{{ date_spine("'2024-01-01'", "'2024-12-31'", interval='month') }}`.

### The `run_query` Macro

`run_query` executes a SQL statement during compilation and returns the result as an Agate table — useful for dynamic logic:

```sql
{% macro get_active_tenants() %}
  {% set query %}
    select tenant_id from {{ ref('dim_tenants') }} where is_active = true
  {% endset %}
  {% set results = run_query(query) %}
  {% if execute %}
    {{ return(results.columns['tenant_id'].values()) }}
  {% endif %}
{% endmacro %}
```

The `{% if execute %}` guard prevents the query from running during `dbt compile` or `dbt parse`, when no warehouse connection is needed.

### Adapting to Multiple Warehouses

Macros can branch on `target.type` for cross-warehouse compatibility:

```sql
{% macro current_timestamp() %}
  {% if target.type == 'bigquery' %}
    current_timestamp()
  {% elif target.type == 'snowflake' %}
    convert_timezone('UTC', current_timestamp())
  {% else %}
    now()
  {% endif %}
{% endmacro %}
```

This pattern is exactly how `dbt-utils` and other packages implement warehouse-agnostic helpers — and how you can build your own portable macro library.

### Practical Tips

- **Namespace your macros** with a project prefix (`my_project_classify_revenue`) to avoid collisions with installed packages.
- **Use `log()` for debugging**: `{{ log("Processing: " ~ my_var, info=true) }}` prints during runs without affecting SQL output.
- **Avoid logic in models**: push complex conditional SQL into macros so models stay readable and the logic is testable in one place.
- **Test macro output** with `dbt compile --select my_model` — inspect `target/compiled/` to verify the generated SQL before running it.

## 15:02 - dbt Snapshots: Tracking Slowly Changing Dimensions

dbt snapshots capture the historical state of mutable source data over time, implementing **Slowly Changing Dimension Type 2 (SCD2)** automatically. Instead of overwriting rows when source data changes, snapshots append new rows and stamp each record with valid date ranges — giving you a full audit trail of how data looked at any point in time.

### How Snapshots Work

Snapshots live in the `snapshots/` directory and use a special `snapshot` block:

```sql
-- snapshots/snap_customers.sql
{% snapshot snap_customers %}

{{
  config(
    target_schema='snapshots',
    unique_key='customer_id',
    strategy='timestamp',
    updated_at='updated_at',
  )
}}

select * from {{ source('raw', 'customers') }}

{% endsnapshot %}
```

Run with `dbt snapshot`. On first run, dbt loads all rows and adds metadata columns. On subsequent runs, it compares source records against the snapshot table and:
- **Inserts** new rows for records that changed (with `dbt_valid_from` = now)
- **Closes** the old version (sets `dbt_valid_to` = now)
- **Leaves unchanged** records untouched

### Snapshot Metadata Columns

dbt automatically adds four columns to every snapshot table:

| Column | Description |
|--------|-------------|
| `dbt_scd_id` | Unique surrogate key for each snapshot row |
| `dbt_updated_at` | When this snapshot row was last evaluated |
| `dbt_valid_from` | When this version of the record became active |
| `dbt_valid_to` | When this version expired (`NULL` = current record) |

### Two Snapshot Strategies

**`timestamp`** — uses an `updated_at` column in the source. More reliable and performant since dbt only processes changed rows:

```yaml
strategy: timestamp
updated_at: updated_at
```

**`check`** — compares a list of columns for any change. Use when the source has no reliable timestamp:

```yaml
strategy: check
check_cols: ['status', 'email', 'plan_tier']
# or: check_cols: all  (compares every column)
```

### Querying Snapshot History

To get the current state of all customers:

```sql
select * from {{ ref('snap_customers') }}
where dbt_valid_to is null
```

To reconstruct what the data looked like on a specific date:

```sql
select * from {{ ref('snap_customers') }}
where '2025-06-01' between dbt_valid_from and coalesce(dbt_valid_to, '9999-12-31')
```

### Practical Tips

- **Run snapshots before other models** in your pipeline — downstream mart models should ref the snapshot table so they always have fresh history.
- **Avoid `select *` in the snapshot query** if the source schema changes frequently; explicitly listing columns prevents unexpected snapshot rebuilds.
- **Snapshots are append-only** — dbt never deletes rows from the snapshot table, even if the source row is deleted. Handle deletions explicitly with a `is_deleted` flag in your source if needed.
- Keep snapshot queries **simple and flat**; save complex transformations for downstream models that ref the snapshot.
