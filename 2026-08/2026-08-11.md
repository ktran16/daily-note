## 00:05 - dbt Project Structure: The Staging → Intermediate → Marts Layering Pattern

A well-structured dbt project is one of the highest-leverage investments you can make. The **three-layer architecture** — staging, intermediate, and marts — gives your project a consistent mental model, makes onboarding fast, and keeps SQL maintainable as the codebase grows.

### The Three Layers

**1. Staging (`models/staging/`)**

Staging models are thin 1:1 wrappers over raw source tables. Their only job is to clean and standardize: rename columns to consistent conventions, cast data types, and apply basic filtering (e.g. exclude test records). No joins, no business logic.

```sql
-- models/staging/stg_orders.sql
with source as (
    select * from {{ source('ecommerce', 'orders') }}
),
renamed as (
    select
        id              as order_id,
        customer_id,
        created_at      as ordered_at,
        status,
        amount_cents / 100.0 as amount
    from source
    where _fivetran_deleted = false
)
select * from renamed
```

Staging models are typically materialized as **views** — they're cheap to recompute and serve as a stable interface over raw data.

**2. Intermediate (`models/intermediate/`)**

Intermediate models contain reusable business logic that doesn't belong in a final mart. Think of these as the "workspace" layer — joining staging models, computing aggregates, or applying shared transformations that multiple marts will depend on.

```sql
-- models/intermediate/int_orders_with_customer.sql
select
    o.order_id,
    o.ordered_at,
    o.amount,
    c.customer_name,
    c.email,
    c.country
from {{ ref('stg_orders') }} o
left join {{ ref('stg_customers') }} c using (customer_id)
```

Intermediate models are often **ephemeral** (no materialized table) or **views**, unless downstream fan-out makes materializing them worthwhile.

**3. Marts (`models/marts/`)**

Marts are the final, consumer-facing models — wide, denormalized tables optimized for BI tools or downstream APIs. They aggregate intermediate models into clearly named outputs organized by business domain.

```
models/
  marts/
    finance/
      fct_orders.sql
      dim_customers.sql
    marketing/
      fct_campaigns.sql
```

Marts are usually materialized as **tables** or **incremental** models to guarantee fast query performance for end users.

### Why This Structure Works

- **Staging = source of truth for raw data** — one canonical cleaning point per source table.
- **Intermediate = reusable logic** — prevents copy-paste SQL drift across mart models.
- **Marts = business contract** — what stakeholders and BI tools point at; changes here should be deliberate.

### Key Convention: Always Use `ref()` and `source()`

Never hard-code schema or table names. Use `{{ source() }}` only in staging models, and `{{ ref() }}` everywhere else. This keeps the DAG accurate and enables dbt's node selection, defer, and CI features to work correctly.

A clean layer boundary makes it obvious where a bug lives (data quality → staging, business rule → intermediate, presentation → mart) and dramatically speeds up debugging in large projects.

## 05:03 - dbt Incremental Models: Strategies and When to Use Each

Incremental models are the most powerful materialization in dbt — they process only new or changed rows rather than rebuilding the full table, making them essential for large datasets. But choosing the right **incremental strategy** matters a lot.

### The Four Core Strategies

**1. `append` (default on most adapters)**

Inserts new rows only — never updates or deletes existing rows. Use this for immutable event logs where records never change after insertion.

```sql
{{ config(materialized='incremental', incremental_strategy='append') }}

select * from {{ source('events', 'raw_clicks') }}
{% if is_incremental() %}
  where event_time > (select max(event_time) from {{ this }})
{% endif %}
```

**2. `delete+insert`**

Deletes matching rows from the target table, then re-inserts them. Avoids duplicates caused by late-arriving data updates. Requires specifying a `unique_key`.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='delete+insert',
    unique_key='order_id'
) }}
```

**3. `merge` (most common for updates)**

A true SQL `MERGE` — matches on `unique_key`, updates changed rows, inserts new ones. Supported on BigQuery, Snowflake, Databricks, and Redshift (via `merge`). The safest strategy when source records can be updated.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='order_id',
    merge_update_columns=['status', 'updated_at']  -- only update specific columns
) }}
```

**4. `insert_overwrite`**

Replaces entire partitions rather than individual rows. Most efficient on partitioned BigQuery or Spark tables — drops and rewrites whole date partitions atomically.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={'field': 'event_date', 'data_type': 'date'}
) }}
```

### Choosing the Right Strategy

| Situation | Strategy |
|---|---|
| Append-only events, no updates | `append` |
| Late-arriving data, partition-level rewrites | `delete+insert` or `insert_overwrite` |
| Records can be updated (e.g. order status) | `merge` |
| Large partitioned tables on BigQuery/Spark | `insert_overwrite` |

### The `on_schema_change` Safety Net

When you add or remove columns from an incremental model, dbt's default is to fail. Configure `on_schema_change` to control this:

```sql
{{ config(
    materialized='incremental',
    on_schema_change='sync_all_columns'  -- append new columns automatically
) }}
```

Options: `ignore` (default), `fail`, `append_new_columns`, `sync_all_columns`.

Always run a full refresh after major schema changes: `dbt run --full-refresh -s my_model`.

## 10:03 - dbt `run-operation`: Running Macros Directly from the Command Line

`dbt run-operation` lets you invoke any macro in your project or installed packages directly from the CLI — without building a model. It's the go-to tool for database maintenance, ad-hoc utility tasks, and macro debugging.

### Basic Syntax

```bash
dbt run-operation <macro_name> --args '{"arg1": "value1", "arg2": "value2"}'
```

Args are passed as a YAML or JSON string. The macro executes in the dbt context with full access to `run_query()`, `ref()`, `source()`, adapters, and all other Jinja globals.

### Common Use Cases

**1. Database Maintenance**

Run `VACUUM` or `ANALYZE` on Redshift tables after large incremental runs:

```sql
-- macros/vacuum_table.sql
{% macro vacuum_table(schema, table) %}
  {% set query %}
    VACUUM {{ schema }}.{{ table }};
    ANALYZE {{ schema }}.{{ table }};
  {% endset %}
  {% do run_query(query) %}
  {{ log("Vacuumed " ~ schema ~ "." ~ table, info=True) }}
{% endmacro %}
```

```bash
dbt run-operation vacuum_table --args '{"schema": "analytics", "table": "fct_orders"}'
```

**2. Creating or Dropping Database Objects**

Set up audit tables, sequences, or schemas that dbt doesn't manage as models:

```sql
{% macro create_audit_schema() %}
  {% set query %}
    CREATE SCHEMA IF NOT EXISTS audit;
    GRANT USAGE ON SCHEMA audit TO role_read_only;
  {% endset %}
  {% do run_query(query) %}
{% endmacro %}
```

```bash
dbt run-operation create_audit_schema
```

**3. Debugging Macros Interactively**

Print resolved values to check macro logic without a full `dbt run`:

```sql
{% macro debug_date_spine(start, end) %}
  {{ log("Start: " ~ start ~ ", End: " ~ end, info=True) }}
  {{ log(modules.datetime.date.today(), info=True) }}
{% endmacro %}
```

```bash
dbt run-operation debug_date_spine --args '{"start": "2024-01-01", "end": "2024-12-31"}'
```

**4. Running dbt-utils Macros Directly**

```bash
# Drop schema and all its objects
dbt run-operation drop_schema_if_empty --args '{"schema_name": "dbt_dev_ktran"}'

# Grant access using dbt-utils grant_select_on_schemas
dbt run-operation grant_select_on_schemas --args '{"schemas": ["analytics"], "role": "reporter"}'
```

### Important Limitations

- `run-operation` **does not participate in the DAG** — no `ref()` dependencies are resolved or materialized. It runs the macro in isolation.
- Side effects (DDL, DML) execute immediately; there's no dry-run mode.
- Output is only visible if you call `{{ log(..., info=True) }}` or `{{ print(...) }}` inside the macro. Return values are discarded.
- In dbt Cloud, `run-operation` runs can be triggered via the API or scheduled as a separate job — useful for recurring maintenance tasks separate from your main dbt build.

### Practical Pattern: Pair with `on-run-end`

For maintenance that should run automatically after every build, register the macro in `dbt_project.yml`:

```yaml
on-run-end:
  - "{{ vacuum_recent_tables() }}"
```

Use `run-operation` for one-off or environment-specific invocations, and `on-run-end` for routine post-build steps.
