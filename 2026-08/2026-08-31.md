## 00:04 - [Data Engineering] The Three Fact Table Types: Transaction, Periodic Snapshot, Accumulating Snapshot

Most modeling arguments ("should this be one table or three?") dissolve once you name the *fact type*. Kimball identifies three, and they answer different questions. Picking the wrong one is why analysts end up writing 200-line window functions in the BI tool.

**1. Transaction fact — one row per event, at the moment it happens.**

Grain: "one row per order line." Additive across every dimension, append-only, and the easiest to build incrementally.

```sql
-- fct_order_lines
select
    order_line_id,          -- degenerate dimension
    order_date_key,
    customer_key, product_key, store_key,
    quantity,
    extended_amount,        -- fully additive
    discount_amount
from {{ ref('stg_order_lines') }}
```

Use it when the question is "how much happened?" It cannot answer "what was the balance on March 3rd?" without an expensive running sum.

**2. Periodic snapshot — one row per entity per fixed interval, whether or not anything happened.**

Grain: "one row per account per day." Rows exist even for inactive accounts, so the table is dense and predictable in size (`entities × periods`). Balances here are **semi-additive**: you can sum across accounts, never across dates — average or take the last value instead.

```sql
-- fct_account_daily_balance
select d.date_key, a.account_key,
       coalesce(b.balance, 0) as balance   -- semi-additive
from dim_date d
cross join dim_account a
left join daily_balances b
       on b.account_key = a.account_key and b.date_key = d.date_key
where d.date_key between a.opened_date_key and current_date
```

**3. Accumulating snapshot — one row per pipeline instance, *updated in place* as it advances.**

Grain: "one row per order." Multiple date foreign keys, one per milestone, plus lag measures. This is the right shape for funnels and SLA reporting.

```sql
select order_id,
       ordered_date_key, picked_date_key, shipped_date_key, delivered_date_key,
       datediff('day', ordered_date, shipped_date) as days_to_ship
```

Because rows mutate, build it with `incremental_strategy='merge'` and a `unique_key`, not `append`. That mutability is the tell: if the fact's row is ever revised after insertion, you are in case 3 — model it deliberately rather than bolting `update` statements onto a transaction table.

**Rule of thumb:** transaction facts for *what occurred*, periodic snapshots for *what the state was*, accumulating snapshots for *how long it took*. Many warehouses need all three over the same source — that is not duplication, it is three grains serving three questions.

## 05:03 - [Data Analytics] Gaps and Islands: Finding Streaks and Sessions in SQL

"How many users logged in 7 days straight?" and "split this clickstream into sessions" look like different questions. They're the same problem: **gaps and islands** — grouping rows that are consecutive by some rule, and finding where the runs break.

### The row-number difference trick

For dense sequences (dates, integers), subtract a row number from the value. Within a consecutive run the difference is constant, so it becomes a free group key.

```sql
WITH daily AS (
  SELECT DISTINCT user_id, activity_date FROM events
),
grouped AS (
  SELECT user_id, activity_date,
         activity_date
           - (ROW_NUMBER() OVER (PARTITION BY user_id
                                 ORDER BY activity_date))::int AS grp
  FROM daily
)
SELECT user_id,
       MIN(activity_date) AS streak_start,
       MAX(activity_date) AS streak_end,
       COUNT(*)           AS streak_days
FROM grouped
GROUP BY user_id, grp
HAVING COUNT(*) >= 7;
```

Walk it through for dates `08-01, 08-02, 08-03, 08-07, 08-08`. Row numbers are 1–5, so `grp` is `07-31, 07-31, 07-31, 08-03, 08-03` — two islands, of 3 and 2 days. Note the `DISTINCT`: duplicate rows per day silently inflate the row number and shatter your streaks.

### The LAG + running-sum trick

When "consecutive" means a tolerance rather than adjacency — a 30-minute session timeout — flag each run's first row and take a running sum.

```sql
WITH flagged AS (
  SELECT user_id, event_ts,
         CASE WHEN event_ts - LAG(event_ts) OVER w > INTERVAL '30 minutes'
                OR LAG(event_ts) OVER w IS NULL
              THEN 1 ELSE 0 END AS is_new_session
  FROM events
  WINDOW w AS (PARTITION BY user_id ORDER BY event_ts)
)
SELECT user_id, event_ts,
       SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY event_ts
                                 ROWS UNBOUNDED PRECEDING) AS session_num
FROM flagged;
```

This generalizes to price-change runs, uptime intervals, and contract renewals — anywhere "same as previous" defines a boundary.

### The gaps half

Islands are what exists; gaps are what's missing, and missing rows can't be windowed over. Join a date spine first (`generate_series` in Postgres/DuckDB), then the same patterns find the runs of NULLs.

**Cost note:** both patterns are one sort per partition, no self-join. The classic correlated-subquery version is O(n²) — on 10M rows that's the difference between seconds and never finishing.

## 10:04 - [ML & AI] Imbalanced Data: Fix the Threshold Before You Touch the Sampler

The reflex on a 1%-positive dataset is to reach for SMOTE. Usually that's the third-best lever, applied first.

Three separate things get conflated:

1. **Resampling** (SMOTE, undersampling) — changes the training distribution.
2. **Class weights** (`class_weight='balanced'`, `scale_pos_weight`) — reweights the loss.
3. **Decision threshold** — where you cut `predict_proba` into a label.

Imbalance rarely breaks the model's *ranking*. It breaks the *threshold*. A gradient-boosted model on 200k rows with 2k positives may separate classes well — ROC-AUC 0.94 — while `predict()` at the default 0.5 flags 20 rows and recalls 1% of fraud. The signal is there; you're reading it at the wrong cut point.

**Worked example.** Fraud model, calibrated. Missing fraud costs $200; a manual review costs $5. The cost-optimal threshold is

```
t* = C_fp / (C_fp + C_fn) = 5 / (5 + 200) ≈ 0.024
```

Not 0.5. Moving the cut from 0.5 to 0.024 on the model above took recall from 1% to ~62% at ~11% precision — 1,240 caught frauds ($248k) against ~11,000 reviews ($55k). No retraining, no synthetic rows.

```python
from sklearn.metrics import precision_recall_curve
import numpy as np

p = model.predict_proba(X_val)[:, 1]
prec, rec, thr = precision_recall_curve(y_val, p)
# expected cost at each candidate threshold
cost = [(200 * ((p < t) & (y_val == 1)).sum()) + (5 * ((p >= t) & (y_val == 0)).sum())
        for t in thr]
best = thr[int(np.argmin(cost))]
```

**Why the other two come later.** SMOTE interpolates between minority neighbors — meaningless across one-hot columns, and it invents points in regions no real fraud occupies. Both SMOTE and class weights inflate predicted probabilities, so a model that was calibrated stops being calibrated, and the cost formula above no longer applies without a recalibration pass (`CalibratedClassifierCV` on a held-out fold).

**Order of operations:** tune the threshold on a validation set against real costs → try `scale_pos_weight` if the minority is so rare the trees never split on it → resample last, and only if it measurably beats both. Report PR-AUC throughout, not accuracy.
