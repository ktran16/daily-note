## 00:02 - dbt Hooks: Running SQL Before and After Your Models

**Hooks** are SQL statements (or lists of them) that dbt executes at specific points in the run lifecycle. They're the escape hatch for operations that don't fit inside a model's SELECT — granting permissions, logging run metadata, managing transactions, or calling stored procedures.

### The Four Hook Types

| Hook | When it runs |
|---|---|
| `on-run-start` | Once, before any nodes in a `dbt run` / `dbt build` |
| `on-run-end` | Once, after all nodes complete (even if some failed) |
| `pre-hook` | Before each individual model is built |
| `post-hook` | After each individual model is built |

### Project-Level Hooks (`on-run-start` / `on-run-end`)

Declare these in `dbt_project.yml`. A common use case: populate an audit table with run metadata.

```yaml
# dbt_project.yml
on-run-start:
  - "CREATE TABLE IF NOT EXISTS audit.dbt_runs (run_id VARCHAR, started_at TIMESTAMP, env VARCHAR)"
  - "INSERT INTO audit.dbt_runs VALUES ('{{ invocation_id }}', CURRENT_TIMESTAMP, '{{ target.name }}')"

on-run-end:
  - "UPDATE audit.dbt_runs SET finished_at = CURRENT_TIMESTAMP WHERE run_id = '{{ invocation_id }}'"
```

`{{ invocation_id }}` is a dbt-provided Jinja variable — a UUID unique to each `dbt run` invocation. `{{ target.name }}` gives you the active profile target (e.g. `prod`, `dev`).

### Model-Level Hooks (`pre-hook` / `post-hook`)

The most common use of `post-hook` is granting SELECT access to a BI role after a table is rebuilt:

```yaml
# dbt_project.yml — applies to every model in the marts/ folder
models:
  my_project:
    marts:
      +post-hook:
        - "GRANT SELECT ON {{ this }} TO ROLE reporter"
```

`{{ this }}` resolves to the fully qualified relation the model just built (e.g. `analytics.marts.fct_orders`).

You can also apply hooks inside a model's `config()` block for one-off cases:

```sql
-- models/marts/fct_orders.sql
{{
  config(
    materialized='table',
    post_hook=[
      "GRANT SELECT ON {{ this }} TO ROLE reporter",
      "GRANT SELECT ON {{ this }} TO ROLE analyst"
    ]
  )
}}

SELECT ...
```

### Using Macros in Hooks

For anything beyond a one-liner, extract the logic into a macro:

```sql
-- macros/grant_select.sql
{% macro grant_select(role) %}
  GRANT SELECT ON {{ this }} TO ROLE {{ role }}
{% endmacro %}
```

```yaml
# dbt_project.yml
models:
  my_project:
    marts:
      +post-hook: "{{ grant_select('reporter') }}"
```

This keeps `dbt_project.yml` readable and puts SQL logic where it belongs — in a versioned, testable macro file.

### Snowflake-Specific: Use `grants` Config Instead of Hooks

For Snowflake, dbt has a first-class `grants` config block that's cleaner than a raw `post-hook` for permission management:

```yaml
models:
  my_project:
    marts:
      +grants:
        select: ['reporter', 'analyst']
```

dbt handles the GRANT/REVOKE diffing automatically — it adds grants for new roles and revokes ones that were removed. The `grants` config is idempotent; raw SQL hooks are not.

### Key Pitfalls

**Hooks run even on failed models.** A `post-hook` on a model that errored still executes (with `{{ this }}` pointing to the pre-existing relation, if any). Guard with `{{ results }}` in `on-run-end` if you need conditional logic:

```sql
-- Only log if something actually ran
{% if results | selectattr("status", "equalto", "success") | list %}
  INSERT INTO audit.successful_runs VALUES (...)
{% endif %}
```

**Transaction scope:** In warehouses that use transactions (Postgres, Redshift), pre/post hooks run inside the model's transaction by default. Use `in_transaction: false` in the hook config if you need DDL statements to auto-commit:

```yaml
+post-hook:
  - sql: "GRANT SELECT ON {{ this }} TO reporter"
    transaction: false
```

Hooks are a sharp tool — reach for them when dbt's declarative config isn't enough, and prefer the `grants` config or dbt's built-in features wherever they exist.

## 05:03 - dbt Snapshots: Tracking Slowly Changing Dimensions (Type 2 SCDs)

**Snapshots** are dbt's built-in mechanism for capturing how rows in a source table change over time — the classic data warehousing problem known as a **Type 2 Slowly Changing Dimension (SCD2)**. Instead of overwriting rows when source data changes, snapshots preserve a full history with `dbt_valid_from` / `dbt_valid_to` timestamps.

### Why Snapshots Exist

Most source tables only show the *current* state of a record. If a customer's `email` or `plan_tier` changes, the old value is gone. Snapshots fix this by periodically checking for changes and inserting new history rows when something is different.

### Snapshot File Structure

Snapshots live in the `snapshots/` directory (configurable in `dbt_project.yml`) and use a `{% snapshot %}` block:

```sql
-- snapshots/orders_snapshot.sql
{% snapshot orders_snapshot %}

{{
  config(
    target_schema='snapshots',
    unique_key='order_id',
    strategy='timestamp',
    updated_at='updated_at'
  )
}}

SELECT
  order_id,
  customer_id,
  status,
  amount,
  updated_at
FROM {{ source('raw', 'orders') }}

{% endsnapshot %}
```

Run snapshots with: `dbt snapshot`

### Two Snapshot Strategies

**1. `timestamp` (preferred)**  
dbt compares the `updated_at` column to detect changes. Requires the source table to have a reliable updated-at column.

```yaml
strategy: 'timestamp'
updated_at: 'updated_at'
```

**2. `check`**  
dbt hashes a list of columns and flags a change if the hash differs. Use this when the source has no reliable timestamp.

```yaml
strategy: 'check'
check_cols: ['status', 'amount', 'customer_id']
# or check_cols: 'all'  — checks every column
```

`check` is more expensive — it computes and compares row hashes — but it's the only option for sources without an `updated_at`.

### What dbt Adds Automatically

After the first `dbt snapshot` run, dbt adds four metadata columns to the snapshot table:

| Column | Meaning |
|---|---|
| `dbt_scd_id` | Unique surrogate key for each snapshot row |
| `dbt_updated_at` | Timestamp when this snapshot row was last written |
| `dbt_valid_from` | When this version of the row became active |
| `dbt_valid_to` | When this version was superseded (`NULL` = current row) |

### Querying Snapshot History

To get the full history of order status changes:

```sql
SELECT
  order_id,
  status,
  dbt_valid_from,
  dbt_valid_to
FROM {{ ref('orders_snapshot') }}
WHERE order_id = 1001
ORDER BY dbt_valid_from
```

To get the **current** state only:

```sql
SELECT *
FROM {{ ref('orders_snapshot') }}
WHERE dbt_valid_to IS NULL
```

### Snapshot Best Practices

**Snapshot source data, not transformed data.** Point snapshots at raw/staging tables. If you snapshot a model that itself filters rows, deleted source rows will look like "unchanged" records — the deletion is invisible to dbt.

**Invalidate deleted rows with a sentinel.** dbt doesn't automatically handle hard deletes. A common pattern: use a `LEFT JOIN` to tag deleted rows before snapshotting, or use the `invalidate_hard_deletes` config (available in dbt ≥ 1.2):

```yaml
config(
  ...
  invalidate_hard_deletes=True
)
```

With this flag, rows that disappear from the source query get their `dbt_valid_to` set to the current snapshot timestamp.

**Run snapshots on a dedicated, frequent schedule.** The snapshot cadence determines your temporal resolution. A daily snapshot misses intra-day changes; hourly is safer for fast-moving data.

**Don't `ref()` a snapshot in another snapshot.** dbt doesn't enforce ordering between snapshot nodes the way it does for models — you can end up with a stale upstream snapshot feeding a downstream one.

Snapshots are one of dbt's most underused features. Teams that rely on them avoid building fragile CDC pipelines from scratch and get auditable, queryable history with minimal configuration.

## 10:03 - dbt Model Contracts: Enforcing Schema Guarantees at Build Time

Introduced in **dbt 1.5**, **model contracts** let you declare the exact shape a model must produce — column names, data types, and constraints — and have dbt verify that shape before the model is promoted. Think of it as a type signature for your SQL: if the query violates the contract, the build fails before downstream consumers ever see bad data.

### Enabling a Contract

Add the `contract` block to your model's `config()` or `schema.yml` entry:

```yaml
# models/schema.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: status
        data_type: varchar
      - name: order_total
        data_type: numeric
```

When `enforced: true`, dbt will:
1. Compile the model's SELECT.
2. Compare the returned column names and data types against the contract.
3. Fail the build if anything doesn't match — before the results land in your warehouse.

### Contracts vs. Tests: Know the Difference

| | Contracts | Tests (`not_null`, `unique`, etc.) |
|---|---|---|
| **When it runs** | At model build time | After the model is built (`dbt test`) |
| **What it checks** | Schema shape (names, types) | Data values (nulls, uniqueness, ranges) |
| **Failure mode** | Build is aborted | Model exists, test fails separately |

Contracts catch *structural* problems; tests catch *data quality* problems. Use both.

### Warehouse Support for Constraints

Not all databases enforce every constraint type at the warehouse level. dbt documents this in its adapter matrix, but the common breakdown:

- **Snowflake / BigQuery / Redshift:** `not_null` is enforced; `primary_key` and `unique` are *not enforced* by the warehouse but are documented as metadata.
- **Postgres / DuckDB:** `not_null`, `primary_key`, and `unique` are all warehouse-enforced.

For warehouses that don't enforce a constraint natively, dbt still *documents* it in the relation's metadata — useful for BI tools and data catalogs that read column-level metadata.

### A Practical Pattern: Contracts on Public Models

Contracts shine at **model boundaries between teams**. If a mart model is consumed by 10 downstream dashboards and 3 other dbt projects, a contract guarantees that refactoring the model's internals can never silently change its output shape. Pair contracts with dbt's **model versions** (`versions:` in `schema.yml`) to manage breaking changes gracefully — bump the version, keep the old contract alive, and give consumers time to migrate.

```yaml
# schema.yml — versioned model with contract
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 2
        config:
          contract:
            enforced: true
      - v: 1
        defined_in: fct_orders_v1  # legacy file kept for migration period
```

Contracts are the right tool when a model is a stable public API. For internal, rapidly-evolving models, they add overhead without much benefit — reserve them for the layer your stakeholders actually touch.

## 15:03 - dbt Packages: Extending dbt with dbt-utils and the Package Hub

**dbt packages** are reusable collections of models, macros, tests, and seeds that you install into your project — the npm/pip of the dbt ecosystem. The canonical source is the [dbt Package Hub](https://hub.getdbt.com/), and the most widely used package by far is **dbt-utils**.

### Installing Packages

Declare packages in `packages.yml` at the project root (create the file if it doesn't exist):

```yaml
# packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.0
  - package: calogica/dbt_expectations
    version: 0.10.4
  - git: https://github.com/your-org/internal-dbt-package
    revision: main
```

Then install them:

```bash
dbt deps
```

dbt writes installed packages to the `dbt_packages/` directory. Commit `packages.yml`; add `dbt_packages/` to `.gitignore`.

### Key dbt-utils Macros

**`generate_surrogate_key`** — creates a consistent hashed surrogate key from one or more columns (handles NULL-safe concatenation automatically):

```sql
SELECT
  {{ dbt_utils.generate_surrogate_key(['order_id', 'line_item_id']) }} AS surrogate_key,
  order_id,
  line_item_id,
  product_id
FROM {{ ref('stg_order_items') }}
```

**`date_spine`** — generates a complete date series between two dates, essential for filling gaps in time-series data:

```sql
WITH date_series AS (
  {{ dbt_utils.date_spine(
      datepart="day",
      start_date="cast('2024-01-01' as date)",
      end_date="current_date"
  ) }}
)
SELECT
  d.date_day,
  COALESCE(o.revenue, 0) AS revenue
FROM date_series d
LEFT JOIN daily_revenue o ON d.date_day = o.order_date
```

**`pivot`** — turns row values into columns without writing verbose CASE WHEN blocks:

```sql
SELECT *
FROM (
  {{ dbt_utils.pivot(
      column='status',
      values=['pending', 'shipped', 'delivered', 'cancelled'],
      agg='count',
      then_value='order_id'
  ) }}
  FROM {{ ref('stg_orders') }}
  GROUP BY customer_id
)
```

**`union_relations`** — unions a list of relations with schema alignment (fills missing columns with NULL):

```sql
{{ dbt_utils.union_relations(
    relations=[
      ref('events_2023'),
      ref('events_2024'),
      ref('events_2025')
    ]
) }}
```

### Generic Tests from dbt-utils

dbt-utils ships several generic tests that extend dbt's built-in `not_null` / `unique`:

```yaml
# schema.yml
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - dbt_utils.not_empty_string
          - dbt_utils.expression_is_true:
              expression: "> 0"
              column_name: order_total
      - name: status
        tests:
          - accepted_values:
              values: ['pending', 'shipped', 'delivered', 'cancelled']
          - dbt_utils.not_constant  # fails if the column has only one distinct value
```

### Package Pinning Strategy

Always pin to an **exact version** in production (`version: 1.3.0`), not a range. dbt-utils occasionally introduces breaking macro changes between minor versions, and a `dbt deps` on a range can silently pull a version that breaks your build. Review the package's CHANGELOG when upgrading, and test in a dev environment first.

Packages are the fastest way to get battle-tested SQL patterns into your project. Prefer them over hand-rolling common utilities — `dbt-utils` alone has been tested across Snowflake, BigQuery, Redshift, Postgres, DuckDB, and Databricks, and its macros handle adapter-specific dialect quirks you'd otherwise discover the hard way.
