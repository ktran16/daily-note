## 00:03 - dbt Exposures: Documenting Downstream Consumers in Your DAG

**Exposures** let you declare *what uses your dbt models* — dashboards, ML models, notebooks, APIs — so that lineage doesn't stop at the warehouse boundary. They appear in `dbt docs` as downstream nodes, making impact analysis instant: "if I change `fct_orders`, which Looker dashboards break?"

### Defining an Exposure

Exposures live in any `.yml` file (commonly `models/exposures.yml`):

```yaml
version: 2

exposures:
  - name: weekly_revenue_dashboard
    label: "Weekly Revenue Dashboard"
    type: dashboard          # dashboard | notebook | analysis | ml | application
    maturity: high           # low | medium | high
    url: https://bi.example.com/dashboards/42
    description: >
      Executive dashboard tracking weekly revenue, refund rates, and
      cohort retention. Refreshes nightly at 02:00 UTC.

    depends_on:
      - ref('fct_orders')
      - ref('dim_customers')
      - ref('fct_refunds')

    owner:
      name: Analytics Team
      email: analytics@example.com
```

### Why Exposures Matter

**Impact analysis** — run `dbt ls --select +weekly_revenue_dashboard` to see every upstream model the dashboard depends on, or `dbt ls --select fct_orders+` to discover every exposure that would be affected by a change to `fct_orders`.

**Freshness SLAs** — set `maturity: high` on production-critical exposures so reviewers know breakage is urgent.

**Docs lineage graph** — `dbt docs generate && dbt docs serve` renders exposures as terminal nodes in the DAG, giving stakeholders full end-to-end lineage from raw source to the dashboard they open each morning.

### Querying Exposure Metadata

Exposures are included in `manifest.json` under the `exposures` key, so you can query them programmatically:

```python
import json

manifest = json.load(open("target/manifest.json"))
for key, exp in manifest["exposures"].items():
    print(exp["name"], "->", exp["depends_on"]["nodes"])
```

### Best Practices

- **One file per domain** (`marketing_exposures.yml`, `finance_exposures.yml`) keeps ownership clear.
- Always set `owner.email` — when a model breaks at 3 AM, on-call needs to know who to page.
- Use `url` for BI tools; link to the specific dashboard, not the tool's home page.
- Prefer `type: ml` for feature stores or model-serving pipelines so data scientists can trace their training data lineage.

Exposures are low-effort, high-value documentation that turns your dbt project from a collection of SQL files into a complete data lineage map.

## 05:03 - dbt Hooks: Running SQL Before and After Your Models

**Hooks** let you execute arbitrary SQL at specific points in the model lifecycle — before a model runs (`pre-hook`) or after it completes (`post-hook`). They're the escape hatch for anything dbt doesn't handle natively: granting permissions, logging audit trails, managing transactions, or refreshing materialized views.

### Configuring Hooks

Hooks can be set at three levels of scope, each narrowing the target:

**Project-level** (`dbt_project.yml`) — applies to all models in a path:

```yaml
models:
  my_project:
    marts:
      +post-hook:
        - "GRANT SELECT ON {{ this }} TO ROLE reporter"
        - "GRANT SELECT ON {{ this }} TO ROLE analyst"
```

**Model config block** — applies to a single model:

```sql
{{ config(
    materialized='table',
    pre_hook="BEGIN TRANSACTION",
    post_hook="COMMIT"
) }}

SELECT ...
```

**`.yml` file config** — useful when you want hooks alongside other model metadata:

```yaml
models:
  - name: fct_orders
    config:
      post_hook: "CALL refresh_materialized_view('fct_orders_mv')"
```

### The `{{ this }}` Variable

Inside hook SQL, `{{ this }}` resolves to the fully-qualified relation being built (`database.schema.model_name`). Always use it instead of hardcoding names so hooks work across environments.

### Common Use Cases

| Use Case | Hook Type | Example SQL |
|---|---|---|
| Grant permissions | `post-hook` | `GRANT SELECT ON {{ this }} TO ROLE bi_users` |
| Audit logging | `post-hook` | `INSERT INTO audit.model_runs VALUES (...)` |
| Transaction control | `pre-hook` / `post-hook` | `BEGIN` / `COMMIT` |
| Drop temp tables | `post-hook` | `DROP TABLE IF EXISTS tmp_staging` |
| Refresh downstream MV | `post-hook` | `CALL refresh_mv('{{ this }}_summary')` |

### Hooks vs. `dbt run-operation`

Hooks fire **automatically** as part of `dbt run`, tied to specific models. Use `run-operation` when you want to invoke a macro on-demand from the CLI without it being bound to a model execution. For recurring, model-scoped side effects, hooks are the right tool.

Hooks are additive — multiple hooks at different config levels all execute; dbt does not replace parent hooks with child ones. Scope them carefully to avoid duplicating grants or inserts across every model in your project.

## 10:03 - dbt Model Contracts: Enforcing Schema Guarantees

**Model contracts** (introduced in dbt v1.5) let you declare a binding schema for a model — column names, data types, and constraints — that dbt enforces at build time. Think of them as a typed interface between your model and its consumers: downstream teams can rely on the contract without inspecting the SQL.

### Enabling a Contract

Add `contract: {enforced: true}` to any model's config, then fully specify every column:

```yaml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: unique
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_total
        data_type: numeric
      - name: status
        data_type: varchar
```

When the contract is enforced, dbt compares the model's compiled output columns against the declared schema **before** writing to the warehouse. If any column is missing, mistyped, or out of order (on some adapters), the run fails with a clear error — no silent drift.

### Supported Constraints

| Constraint | Warehouse enforcement |
|---|---|
| `not_null` | Platform-level (where supported) |
| `unique` | Platform-level (where supported) |
| `primary_key` | Platform-level (where supported) |
| `foreign_key` | Platform-level (where supported) |
| `check` | Platform-level (where supported) |

Snowflake, BigQuery, and Redshift each have different DDL support; dbt documents which constraints are enforced vs. informational per adapter. Even purely informational constraints appear in `dbt docs`, communicating intent to consumers.

### Contracts + Access Modifiers

Contracts pair naturally with `access: public` models. A model exposed to other dbt projects or teams should carry a contract — it's the difference between a vague promise ("fct_orders probably has order_id") and a verifiable guarantee that breaks the build the moment someone renames a column.

### What Contracts Don't Replace

Contracts check shape, not values. You still need dbt **tests** (`not_null`, `accepted_values`, `relationships`) to validate row-level data quality. Use contracts for structural guarantees and tests for business-logic correctness — they're complementary, not redundant.
