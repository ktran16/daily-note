## 00:03 - dbt Exposures: Documenting Downstream Consumers in Your DAG

**Exposures** let you declare *what uses your dbt models* — dashboards, ML models, notebooks, APIs — so that lineage doesn't stop at the warehouse boundary. They appear in `dbt docs` as downstream nodes, making impact analysis instant: "if I change `fct_orders`, which Looker dashboards break?"

### Defining an Exposure

Exposures live in any `.yml` file (commonly `models/exposures.yml`):

```yaml
version: 2

exposures:
  - name: weekly_revenue_dashboard
    label: "Weekly Revenue Dashboard"
    type: dashboard          # dashboard | notebook | analysis | ml | application
    maturity: high           # low | medium | high
    url: https://bi.example.com/dashboards/42
    description: >
      Executive dashboard tracking weekly revenue, refund rates, and
      cohort retention. Refreshes nightly at 02:00 UTC.

    depends_on:
      - ref('fct_orders')
      - ref('dim_customers')
      - ref('fct_refunds')

    owner:
      name: Analytics Team
      email: analytics@example.com
```

### Why Exposures Matter

**Impact analysis** — run `dbt ls --select +weekly_revenue_dashboard` to see every upstream model the dashboard depends on, or `dbt ls --select fct_orders+` to discover every exposure that would be affected by a change to `fct_orders`.

**Freshness SLAs** — set `maturity: high` on production-critical exposures so reviewers know breakage is urgent.

**Docs lineage graph** — `dbt docs generate && dbt docs serve` renders exposures as terminal nodes in the DAG, giving stakeholders full end-to-end lineage from raw source to the dashboard they open each morning.

### Querying Exposure Metadata

Exposures are included in `manifest.json` under the `exposures` key, so you can query them programmatically:

```python
import json

manifest = json.load(open("target/manifest.json"))
for key, exp in manifest["exposures"].items():
    print(exp["name"], "->", exp["depends_on"]["nodes"])
```

### Best Practices

- **One file per domain** (`marketing_exposures.yml`, `finance_exposures.yml`) keeps ownership clear.
- Always set `owner.email` — when a model breaks at 3 AM, on-call needs to know who to page.
- Use `url` for BI tools; link to the specific dashboard, not the tool's home page.
- Prefer `type: ml` for feature stores or model-serving pipelines so data scientists can trace their training data lineage.

Exposures are low-effort, high-value documentation that turns your dbt project from a collection of SQL files into a complete data lineage map.

## 05:03 - dbt Hooks: Running SQL Before and After Your Models

**Hooks** let you execute arbitrary SQL at specific points in the model lifecycle — before a model runs (`pre-hook`) or after it completes (`post-hook`). They're the escape hatch for anything dbt doesn't handle natively: granting permissions, logging audit trails, managing transactions, or refreshing materialized views.

### Configuring Hooks

Hooks can be set at three levels of scope, each narrowing the target:

**Project-level** (`dbt_project.yml`) — applies to all models in a path:

```yaml
models:
  my_project:
    marts:
      +post-hook:
        - "GRANT SELECT ON {{ this }} TO ROLE reporter"
        - "GRANT SELECT ON {{ this }} TO ROLE analyst"
```

**Model config block** — applies to a single model:

```sql
{{ config(
    materialized='table',
    pre_hook="BEGIN TRANSACTION",
    post_hook="COMMIT"
) }}

SELECT ...
```

**`.yml` file config** — useful when you want hooks alongside other model metadata:

```yaml
models:
  - name: fct_orders
    config:
      post_hook: "CALL refresh_materialized_view('fct_orders_mv')"
```

### The `{{ this }}` Variable

Inside hook SQL, `{{ this }}` resolves to the fully-qualified relation being built (`database.schema.model_name`). Always use it instead of hardcoding names so hooks work across environments.

### Common Use Cases

| Use Case | Hook Type | Example SQL |
|---|---|---|
| Grant permissions | `post-hook` | `GRANT SELECT ON {{ this }} TO ROLE bi_users` |
| Audit logging | `post-hook` | `INSERT INTO audit.model_runs VALUES (...)` |
| Transaction control | `pre-hook` / `post-hook` | `BEGIN` / `COMMIT` |
| Drop temp tables | `post-hook` | `DROP TABLE IF EXISTS tmp_staging` |
| Refresh downstream MV | `post-hook` | `CALL refresh_mv('{{ this }}_summary')` |

### Hooks vs. `dbt run-operation`

Hooks fire **automatically** as part of `dbt run`, tied to specific models. Use `run-operation` when you want to invoke a macro on-demand from the CLI without it being bound to a model execution. For recurring, model-scoped side effects, hooks are the right tool.

Hooks are additive — multiple hooks at different config levels all execute; dbt does not replace parent hooks with child ones. Scope them carefully to avoid duplicating grants or inserts across every model in your project.

## 10:03 - dbt Model Contracts: Enforcing Schema Guarantees

**Model contracts** (introduced in dbt v1.5) let you declare a binding schema for a model — column names, data types, and constraints — that dbt enforces at build time. Think of them as a typed interface between your model and its consumers: downstream teams can rely on the contract without inspecting the SQL.

### Enabling a Contract

Add `contract: {enforced: true}` to any model's config, then fully specify every column:

```yaml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: unique
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_total
        data_type: numeric
      - name: status
        data_type: varchar
```

When the contract is enforced, dbt compares the model's compiled output columns against the declared schema **before** writing to the warehouse. If any column is missing, mistyped, or out of order (on some adapters), the run fails with a clear error — no silent drift.

### Supported Constraints

| Constraint | Warehouse enforcement |
|---|---|
| `not_null` | Platform-level (where supported) |
| `unique` | Platform-level (where supported) |
| `primary_key` | Platform-level (where supported) |
| `foreign_key` | Platform-level (where supported) |
| `check` | Platform-level (where supported) |

Snowflake, BigQuery, and Redshift each have different DDL support; dbt documents which constraints are enforced vs. informational per adapter. Even purely informational constraints appear in `dbt docs`, communicating intent to consumers.

### Contracts + Access Modifiers

Contracts pair naturally with `access: public` models. A model exposed to other dbt projects or teams should carry a contract — it's the difference between a vague promise ("fct_orders probably has order_id") and a verifiable guarantee that breaks the build the moment someone renames a column.

### What Contracts Don't Replace

Contracts check shape, not values. You still need dbt **tests** (`not_null`, `accepted_values`, `relationships`) to validate row-level data quality. Use contracts for structural guarantees and tests for business-logic correctness — they're complementary, not redundant.

## 15:03 - dbt `dispatch` and Adapter Macros: Writing Cross-Database SQL

**Adapter macros** let you write macro implementations that behave differently depending on the target warehouse (Snowflake, BigQuery, Redshift, DuckDB, etc.), while callers use one clean interface. The `adapter.dispatch()` function is the mechanism that makes this possible — and it's how dbt-utils ships macros that work everywhere.

### How `dispatch` Works

When you call `{{ adapter.dispatch('my_macro', 'my_package')() }}`, dbt resolves the implementation in this priority order:

1. **`<adapter>__my_macro`** in the calling project (e.g., `snowflake__my_macro`)
2. **`default__my_macro`** in the calling project
3. **`<adapter>__my_macro`** in `my_package`
4. **`default__my_macro`** in `my_package`

This lets you override any package's macro for your specific adapter without forking the package.

### Writing a Cross-Database Macro

Define a default implementation plus adapter-specific overrides:

```sql
-- macros/generate_surrogate_key.sql

-- Default fallback (generic SQL)
{% macro default__generate_surrogate_key(field_list) %}
    md5(
        cast(
            concat_ws('-', {% for field in field_list %}
                coalesce(cast({{ field }} as varchar), '_null_')
                {%- if not loop.last %}, {% endif %}
            {% endfor %}) as varchar
        )
    )
{% endmacro %}

-- Snowflake override: use SHA2 for better distribution
{% macro snowflake__generate_surrogate_key(field_list) %}
    sha2(
        concat_ws('|', {% for field in field_list %}
            coalesce(cast({{ field }} as varchar), '_null_')
            {%- if not loop.last %}, {% endif %}
        {% endfor %})
    )
{% endmacro %}

-- BigQuery override: use TO_HEX(MD5(...))
{% macro bigquery__generate_surrogate_key(field_list) %}
    to_hex(md5(
        concat({% for field in field_list %}
            coalesce(cast({{ field }} as string), '_null_')
            {%- if not loop.last %}, '|', {% endif %}
        {% endfor %})
    ))
{% endmacro %}

-- Dispatcher — this is what callers invoke
{% macro generate_surrogate_key(field_list) %}
    {{ return(adapter.dispatch('generate_surrogate_key', 'my_project')(field_list)) }}
{% endmacro %}
```

Usage in a model:

```sql
SELECT
    {{ generate_surrogate_key(['order_id', 'line_item_id']) }} AS surrogate_key,
    order_id,
    line_item_id,
    product_id
FROM {{ ref('stg_order_items') }}
```

### Overriding a Package Macro for Your Adapter

If `dbt_utils.safe_divide` doesn't handle your warehouse's quirks, you can override it **without** changing the package. In your project's `dbt_project.yml`:

```yaml
dispatch:
  - macro_namespace: dbt_utils
    search_order: ['my_project', 'dbt_utils']
```

Then define `redshift__safe_divide` (or any adapter prefix) in your project's `macros/` folder. dbt will find your version first when running on Redshift.

### Naming Conventions for Adapter Prefixes

| Adapter | Prefix |
|---|---|
| Snowflake | `snowflake__` |
| BigQuery | `bigquery__` |
| Redshift | `redshift__` |
| DuckDB | `duckdb__` |
| Spark / Databricks | `spark__` |
| Postgres | `postgres__` |

### When to Use `dispatch`

- **Package authors** — any macro that touches DDL, date functions, or string functions needs dispatch because SQL dialects vary widely.
- **Multi-warehouse teams** — if your dev environment uses DuckDB and production uses Snowflake, dispatch keeps your macros honest across both.
- **Overriding third-party behavior** — pin a package version but patch one macro's behavior for your adapter without forking.

The `dispatch` pattern is what separates a fragile, warehouse-specific macro library from one that travels with your team as your infrastructure evolves.

## 19:02 - dbt `run_query` and the `execute` Flag: Querying the Warehouse Inside Macros

**`run_query`** is a dbt macro that lets you execute a SQL statement against the warehouse *during* a dbt run and return the results as an Agate table. Combined with the `execute` flag, it unlocks dynamic macro logic: checking if a partition exists, reading config rows from a lookup table, or generating model SQL based on live warehouse state.

### The `execute` Flag

dbt compiles and runs macros in two phases:

1. **Parse/compile phase** — dbt reads all files, builds the DAG, resolves `ref()` and `source()`. No warehouse connection exists yet.
2. **Execute phase** — dbt actually runs models. The warehouse is live.

`run_query` can only work in the execute phase. Wrapping it in `{% if execute %}` prevents it from being called during compilation (where it would error or return `None`):

```sql
{% macro get_max_timestamp(table_name) %}
    {% if execute %}
        {% set query %}
            SELECT MAX(updated_at) FROM {{ table_name }}
        {% endset %}
        {% set results = run_query(query) %}
        {% set max_ts = results.columns[0].values()[0] %}
        {{ return(max_ts) }}
    {% else %}
        {{ return(none) }}
    {% endif %}
{% endmacro %}
```

### Reading Query Results

`run_query` returns an [Agate](https://agate.readthedocs.io/) table. The most common patterns for extracting values:

```sql
{% set results = run_query("SELECT id, name FROM ref('dim_config') WHERE active = TRUE") %}

-- Get all values from the first column as a list
{% set id_list = results.columns['id'].values() %}

-- Get a single scalar value
{% set first_name = results.rows[0]['name'] %}

-- Iterate over rows
{% for row in results %}
    -- row['id'], row['name']
{% endfor %}
```

### Practical Example: Dynamic Column List from a Config Table

Suppose you store column-level config in a seed (`seeds/column_config.csv`) and want to build a pivot dynamically:

```sql
-- macros/get_pivot_columns.sql
{% macro get_pivot_columns(category) %}
    {% if execute %}
        {% set query %}
            SELECT column_name
            FROM {{ ref('column_config') }}
            WHERE category = '{{ category }}'
            ORDER BY sort_order
        {% endset %}
        {% set results = run_query(query) %}
        {{ return(results.columns['column_name'].values()) }}
    {% else %}
        {{ return([]) }}
    {% endif %}
{% endmacro %}

-- models/mart/fct_pivoted_metrics.sql
{% set columns = get_pivot_columns('revenue') %}

SELECT
    date_trunc('month', event_date) AS month,
    {% for col in columns %}
    SUM(CASE WHEN metric_name = '{{ col }}' THEN value ELSE 0 END) AS {{ col }}
    {%- if not loop.last %},{% endif %}
    {% endfor %}
FROM {{ ref('int_metrics') }}
GROUP BY 1
```

### Using `run_query` in Pre/Post-Hooks

You can also call macros that use `run_query` from hooks — the execute phase is already active when hooks fire:

```yaml
# dbt_project.yml
models:
  my_project:
    marts:
      +post-hook: "{{ log_model_run(this) }}"
```

```sql
{% macro log_model_run(relation) %}
    INSERT INTO audit.model_run_log (model_name, run_at, row_count)
    SELECT
        '{{ relation.name }}',
        CURRENT_TIMESTAMP,
        COUNT(*)
    FROM {{ relation }}
{% endmacro %}
```

### Key Gotchas

- **Always guard with `{% if execute %}`** — a bare `run_query` at the top level will crash during `dbt compile` or `dbt parse`.
- **Results are in-memory** — Agate tables are Python objects; don't use `run_query` to pull millions of rows. Use it for config lookups and scalar aggregates only.
- **Avoid circular dependencies** — if your macro queries a model to drive another model's SQL, you've created a build-order dependency that the DAG can't see. Query seeds or external tables instead.
- **`dbt ls` also compiles macros** — the `{% if execute %}` guard is essential for any CLI command that doesn't open a warehouse connection.

`run_query` bridges the gap between static SQL generation and data-driven macro logic, enabling patterns that would otherwise require a separate orchestration step.
