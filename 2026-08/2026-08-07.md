## 00:02 - dbt Unit Tests: Testing SQL Logic Without Live Data

Introduced in **dbt 1.8**, unit tests let you verify the SQL logic inside a model by providing mock input data and asserting the expected output — all without touching your warehouse. They complement data tests (which validate data quality at runtime) by catching transformation bugs during development.

### Why Unit Tests Matter

Traditional dbt tests run against real warehouse rows, so a bug in your SQL may only surface when live data is already affected. Unit tests let you:
- Test edge cases with handcrafted inputs (nulls, negatives, boundary values)
- Iterate fast with deterministic, local-only runs
- Document exactly what each model is supposed to do

### Anatomy of a Unit Test

Unit tests live in your YAML files alongside schema definitions:

```yaml
# models/orders.yml
unit_tests:
  - name: test_orders_total_calculation
    model: orders
    given:
      - input: ref('stg_order_items')
        rows:
          - {order_id: 1, item_price: 10.00, quantity: 3, discount: 0.10}
          - {order_id: 1, item_price: 5.00,  quantity: 2, discount: 0.00}
    expect:
      rows:
        - {order_id: 1, total_revenue: 37.00}  # (10*3 * 0.9) + (5*2) = 27 + 10
```

Your SQL model (`models/orders.sql`) might look like:

```sql
select
    order_id,
    round(
        sum(item_price * quantity * (1 - discount)),
        2
    ) as total_revenue
from {{ ref('stg_order_items') }}
group by order_id
```

### Running Unit Tests

```bash
# Run all unit tests
dbt test --select test_type:unit

# Run unit tests for a specific model
dbt test --select orders --test-type unit

# Run during a full build
dbt build --select orders
```

### Mocking Sources and Seeds

You can also mock `source()` references and seeds, not just `ref()`:

```yaml
given:
  - input: source('raw', 'events')
    rows:
      - {event_id: 'abc', event_type: 'click', created_at: '2024-01-01'}
```

### Key Limitations and Tips

- Unit tests currently require the warehouse to **compile** the SQL, but not to **execute** it against real data (behavior varies slightly by adapter — BigQuery and Snowflake run the mocked SQL directly).
- Keep inputs minimal — you only need the columns your model actually references.
- Unit tests are not a replacement for data tests; use both. Unit tests validate *logic*, data tests validate *data*.
- Use `overrides` to mock `var()`, `env_var()`, or even `run_started_at` for time-sensitive models:

```yaml
overrides:
  vars:
    is_backfill: false
  env_vars:
    MY_ENV: production
```

Unit tests turn your dbt project into a properly test-driven codebase — write the test first, watch it fail, fix the SQL, watch it pass.

## 05:03 - dbt `defer` and `--state`: Build Against Production Without Rebuilding Everything

One of the most powerful (and underused) dbt development features is **`defer`** — a flag that lets you run a single model in development while pulling all upstream dependencies from a **production run**, skipping the cost of rebuilding your entire DAG locally.

### The Problem It Solves

Suppose you're tweaking `fct_orders`, which depends on 15 upstream models. Without `defer`, a local `dbt run --select fct_orders+` rebuilds all 15 upstreams in your dev schema first — slow, expensive, and often unnecessary.

With `defer`, dbt reads production-run artifacts and resolves upstream `ref()` calls to the **production tables** instead of your dev schema. You only build what you actually changed.

### Basic Usage

```bash
# 1. Download production artifacts to a local directory
#    (from dbt Cloud, CI, or a shared S3/GCS bucket)
mkdir -p ./prod-artifacts
# place manifest.json and run_results.json inside

# 2. Run your model, deferring upstreams to prod
dbt run \
  --select fct_orders \
  --defer \
  --state ./prod-artifacts
```

dbt compares your project's `manifest.json` against the production one. Any upstream model that **already exists in prod and hasn't changed** is skipped — your dev schema borrows from prod transparently.

### `--favor-state` for Modified Upstreams

By default, if an upstream was modified locally it gets rebuilt. `--favor-state` forces dbt to always prefer the production version, even for changed models:

```bash
dbt run --select fct_orders --defer --state ./prod-artifacts --favor-state
```

Useful when you want to isolate your change from upstream experiments a colleague is running.

### Checking What Would Be Deferred

Before running, preview which nodes would be deferred vs. built locally:

```bash
dbt ls \
  --select fct_orders+ \
  --defer \
  --state ./prod-artifacts \
  --output json | jq '.[]'
```

Deferred nodes appear with a note that they resolve to the production relation.

### Getting Production Artifacts

| Platform | How to get `manifest.json` + `run_results.json` |
|---|---|
| dbt Cloud | Download from the latest successful job run via the API or UI |
| dbt Core + CI | Upload artifacts as CI artifacts; download in dev scripts |
| Shared storage | `dbt run` writes to `./target/`; copy to S3/GCS after each prod run |

### Combining with Slim CI

`defer` pairs naturally with Slim CI's `--select state:modified+`:

```bash
# CI: only build models changed in this PR, defer everything else to prod
dbt build \
  --select state:modified+ \
  --defer \
  --state ./prod-artifacts
```

This means your CI pipeline only touches what changed, cutting build times dramatically on large projects.

### Key Rules to Remember

- `defer` requires both `manifest.json` **and** `run_results.json` in the `--state` directory.
- It only defers nodes that **exist** in the production state. New models (not yet in prod) are always built locally.
- Works with `dbt run`, `dbt test`, `dbt build`, and `dbt compile`.
- Your dev `profiles.yml` target still controls **where your local models land** — defer only affects *upstreams*, not the model you're developing.

`defer` is the single biggest productivity multiplier for developers working on large dbt projects — pair it with a CI job that publishes artifacts after every prod run and you get near-instant dev cycles.

## 10:03 - dbt Node Selection Syntax: Targeting Exactly What You Need

dbt's **node selection syntax** is one of its most powerful ergonomic features. The `--select` (or `-s`) and `--exclude` flags let you pinpoint any slice of your DAG — a single model, a subtree, a tag group, or a path-based subset — so every `dbt run`, `dbt test`, and `dbt build` only touches what matters.

### The Basic Operators

| Syntax | Meaning |
|---|---|
| `model_name` | Exactly that model |
| `+model_name` | The model **and all its ancestors** (upstreams) |
| `model_name+` | The model **and all its descendants** (downstreams) |
| `+model_name+` | Both directions — the full connected subgraph |
| `model_name+1` | The model and one layer of direct parents |
| `model_name+2` | The model and two layers of parents |

```bash
# Build fct_orders and everything it depends on
dbt run --select +fct_orders

# Build fct_orders and everything downstream of it
dbt run --select fct_orders+

# Only fct_orders itself
dbt run --select fct_orders
```

### Method-Based Selectors

You can select by metadata, not just name:

```bash
# All models with a specific tag
dbt run --select tag:nightly

# All models in a directory path
dbt run --select models/marts/finance/

# All models using a specific materialization
dbt run --select config.materialized:incremental

# All models that failed in the last run
dbt run --select result:error --state ./target

# All models changed vs. a prior state (Slim CI)
dbt run --select state:modified+ --state ./prod-artifacts

# All models downstream of a specific source
dbt run --select source:raw_events+
```

### Set Operations: Union, Intersection, Exclusion

Combine selectors with spaces (union), commas (intersection), or `--exclude`:

```bash
# Union: models tagged nightly OR in the finance folder
dbt run --select tag:nightly models/marts/finance/

# Intersection: models tagged nightly AND in the finance folder
dbt run --select "tag:nightly,models/marts/finance/"

# Exclude specific models from a broader selection
dbt run --select marts/ --exclude fct_orders fct_returns
```

### The `@` Operator for Testing

The `@` prefix selects a model **plus all its ancestors and all tests on those ancestors** — ideal when you want to run a model's full test suite including its upstreams:

```bash
dbt test --select @fct_orders
```

### Selecting Sources and Exposures

```bash
# Select a specific source table
dbt source freshness --select source:stripe.payments

# Select all models feeding a specific exposure
dbt run --select +exposure:monthly_revenue_report
```

### Practical CI/CD Pattern

Combining selectors produces tight CI builds:

```bash
# In CI: build only changed models and their downstream dependents,
# run all tests on those models and their direct parents
dbt build \
  --select state:modified+ \
  --defer \
  --state ./prod-artifacts
```

### Listing What Would Be Selected (Dry Run)

Before running, verify your selection with `dbt ls`:

```bash
dbt ls --select +fct_orders --output json | jq -r '.[].unique_id'
```

This shows every node dbt would touch, without executing anything — essential for sanity-checking complex selectors before a production run.

Mastering the selection syntax lets you turn a 40-minute full DAG run into a 3-minute targeted build. It's the difference between a dbt project that's fast to iterate on and one that slows your team down.

## 15:04 - dbt Grants: Automatically Managing Database Permissions

When dbt builds a model it creates a relation in your warehouse — but by default only the dbt service account can read it. Every other role that needs access must be granted manually, which quickly becomes a maintenance headache as your project grows. **dbt grants** solve this by letting you declare access control directly in your dbt config, so permissions are applied (and re-applied) automatically every time a model is built.

### Declaring Grants in `dbt_project.yml`

Apply grants project-wide using the `grants` config key:

```yaml
# dbt_project.yml
models:
  my_project:
    +grants:
      select: ['reporter', 'analyst_role']

    marts:
      +grants:
        select: ['reporter', 'analyst_role', 'executive_role']
```

Every model under `marts/` will grant `SELECT` to all three roles after each build.

### Overriding Grants per Model

You can override at the model level in `schema.yml` or in the model file's config block:

```yaml
# models/schema.yml
models:
  - name: fct_orders
    config:
      grants:
        select: ['reporter', 'finance_role']
```

Or directly in SQL:

```sql
-- models/fct_orders.sql
{{ config(
    materialized='table',
    grants={'select': ['reporter', 'finance_role']}
) }}

select ...
```

### How Grant Application Works

dbt applies grants **after** the relation is created or replaced. The behavior depends on the materialization:

| Materialization | When grants are applied |
|---|---|
| `view` | After `CREATE OR REPLACE VIEW` — grants must be reapplied on every run |
| `table` | After `CREATE TABLE AS SELECT` — same, reapplied each full rebuild |
| `incremental` | Only on the **first** build (when the table is created); subsequent runs skip re-granting by default |
| `ephemeral` | N/A — ephemeral models don't create relations |

For incremental models, dbt tracks whether the relation already exists. If it does, grants are skipped to avoid locking. You can force re-granting with `--full-refresh`.

### The `copy_grants` Flag (Snowflake)

On Snowflake, replacing a view or table drops and recreates it, which **revokes all existing grants**. Use `copy_grants: true` to carry forward the old relation's grants to the new one:

```yaml
# dbt_project.yml
models:
  +copy_grants: true
  +grants:
    select: ['reporter']
```

With `copy_grants`, Snowflake's `CREATE OR REPLACE ... COPY GRANTS` syntax is used, so existing permissions survive rebuilds. This is almost always what you want on Snowflake.

### Append vs. Replace Grant Behavior

By default dbt uses **append** semantics — it adds the configured roles but never revokes others. If you want to enforce an exact set of grantees (removing anyone not listed), you can set the adapter-level behavior in your profile or use the `on_schema_change` approach in combination with custom post-hooks. Most teams find append semantics sufficient.

### Practical Pattern: Tiered Access by Layer

A common pattern is to expose different layers to different roles:

```yaml
models:
  my_project:
    staging:
      +grants:
        select: ['dbt_developer_role']   # only devs see raw staging

    marts:
      +grants:
        select: ['reporter', 'bi_tool_role']  # BI tools read from marts

    finance:
      +grants:
        select: ['reporter', 'bi_tool_role', 'finance_team_role']
```

This enforces data access tiers purely through dbt config — no manual `GRANT` statements, no runbook, no drift.

### Checking What Was Granted

After a run, dbt logs the grant statements it executed. You can also audit with your warehouse's permission views (e.g., `INFORMATION_SCHEMA.OBJECT_PRIVILEGES` on Snowflake, `pg_roles` on Redshift/Postgres).

dbt grants are supported on Snowflake, BigQuery, Databricks, Redshift, and Postgres as of dbt 1.2 — check your adapter's changelog for any version-specific nuances.

## 19:03 - dbt Snapshots: Tracking Historical Changes with Type 2 SCD

Most source systems only store the *current* state of a record — update a customer's email and the old one is gone. **dbt snapshots** solve this by implementing a **Slowly Changing Dimension Type 2 (SCD2)** pattern: every time a source row changes, dbt adds a new versioned row in your snapshot table and closes out the previous one with an end timestamp.

### The Snapshot File

Snapshots live in the `snapshots/` directory and use a `{% snapshot %}` block instead of a plain `select`:

```sql
-- snapshots/orders_snapshot.sql
{% snapshot orders_snapshot %}

{{
    config(
        target_schema='snapshots',
        unique_key='order_id',
        strategy='timestamp',
        updated_at='updated_at'
    )
}}

select * from {{ source('raw', 'orders') }}

{% endsnapshot %}
```

Run with `dbt snapshot`. dbt reads the source, diffs against the snapshot table, and writes new versioned rows for anything that changed.

### The Two Snapshot Strategies

| Strategy | Config | When to use |
|---|---|---|
| `timestamp` | `updated_at='col'` | Source table has a reliable `updated_at` column |
| `check` | `check_cols=['col1','col2']` or `check_cols='all'` | No `updated_at` — dbt hashes the specified columns to detect changes |

```sql
-- check strategy example
{{
    config(
        strategy='check',
        check_cols=['status', 'email', 'plan'],
        unique_key='customer_id',
        target_schema='snapshots'
    )
}}
```

Use `check_cols='all'` with caution on wide tables — hashing every column is expensive and noisy (audit timestamps can trigger false changes).

### The Columns dbt Adds Automatically

Every snapshot table gets four dbt-managed metadata columns:

| Column | Meaning |
|---|---|
| `dbt_scd_id` | Surrogate key unique to each version row |
| `dbt_updated_at` | When dbt last touched this row |
| `dbt_valid_from` | When this version became active |
| `dbt_valid_to` | When it was superseded (`NULL` = currently active) |

To query only current records:

```sql
select *
from {{ ref('orders_snapshot') }}
where dbt_valid_to is null
```

To reconstruct state at a point in time:

```sql
select *
from {{ ref('orders_snapshot') }}
where '2024-06-01' between dbt_valid_from and coalesce(dbt_valid_to, '9999-12-31')
```

### Snapshot Scheduling and Performance Tips

- **Run snapshots frequently** — the longer the gap between snapshot runs, the higher the chance you miss a short-lived intermediate state (a record created and deleted between two runs won't appear).
- **Snapshot before your dbt run** — put `dbt snapshot` first in your pipeline so downstream models always see the freshest historical data.
- **Narrow your source query** — don't snapshot columns you don't need. Fewer columns = faster hash comparisons with the `check` strategy.
- **Partition the snapshot table** on `dbt_valid_from` in warehouses that support it (BigQuery, Databricks) to keep point-in-time queries fast as the table grows.

### Common Gotcha: Hard Deletes

By default, dbt snapshots don't detect **hard deletes** — if a row disappears from the source, its snapshot row just stays open (`dbt_valid_to = NULL`) forever. Enable delete detection with `invalidate_hard_deletes`:

```sql
{{
    config(
        strategy='timestamp',
        updated_at='updated_at',
        unique_key='order_id',
        target_schema='snapshots',
        invalidate_hard_deletes=True
    )
}}
```

With this flag, dbt closes out rows whose `unique_key` no longer appears in the source query on each snapshot run.

Snapshots are dbt's built-in answer to "what did this data look like last Tuesday?" — a question that's surprisingly hard to answer without them.
