## 00:03 - dbt Macros & Jinja: Writing Reusable SQL Logic

dbt's superpower over plain SQL is Jinja templating — and macros are how you turn repeated patterns into named, reusable functions. A macro is just a Jinja `{% macro %}` block stored in the `macros/` directory that any model, test, or other macro can call.

### Why Macros Matter

Copy-pasting SQL is the fastest route to inconsistency. When the same transformation logic lives in 15 models, fixing a bug or changing a business rule means 15 edits and 15 chances to miss one. Macros collapse that to a single definition.

### Anatomy of a Macro

```jinja
{# macros/cents_to_dollars.sql #}
{% macro cents_to_dollars(column_name, scale=2) %}
    round({{ column_name }} / 100.0, {{ scale }})
{% endmacro %}
```

Call it in any model:

```sql
-- models/marts/fct_orders.sql
select
    order_id,
    {{ cents_to_dollars('order_total_cents') }}        as order_total,
    {{ cents_to_dollars('shipping_cost_cents', 4) }}   as shipping_cost
from {{ ref('stg_orders') }}
```

dbt compiles this to plain SQL before running — `{{ cents_to_dollars('order_total_cents') }}` becomes `round(order_total_cents / 100.0, 2)`.

### Macros with Conditional Logic

Macros can contain full Jinja control flow, making them powerful for cross-warehouse compatibility:

```jinja
{# macros/safe_divide.sql #}
{% macro safe_divide(numerator, denominator) %}
    {% if target.type == 'bigquery' %}
        ieee_divide({{ numerator }}, {{ denominator }})
    {% elif target.type == 'snowflake' %}
        iff({{ denominator }} = 0, null, {{ numerator }} / nullif({{ denominator }}, 0))
    {% else %}
        case when {{ denominator }} = 0 then null
             else {{ numerator }}::float / {{ denominator }}
        end
    {% endif %}
{% endmacro %}
```

### Generating Repetitive SQL with `for` Loops

Macros shine when you need to generate columns dynamically:

```jinja
{# macros/union_relations.sql — generate a union across date-partitioned tables #}
{% macro date_spine_union(start_year, end_year, table_prefix) %}
    {% for year in range(start_year, end_year + 1) %}
        select *, {{ year }} as year_partition
        from {{ table_prefix }}_{{ year }}
        {% if not loop.last %} union all {% endif %}
    {% endfor %}
{% endmacro %}
```

### Using `run_query()` for Metadata-Driven Generation

The `run_query()` built-in executes SQL during compilation and returns results you can loop over — enabling fully dynamic model generation:

```jinja
{# macros/get_column_list.sql #}
{% macro get_column_list(relation) %}
    {% set column_query %}
        select column_name
        from information_schema.columns
        where table_name = '{{ relation.identifier }}'
        order by ordinal_position
    {% endset %}

    {% set results = run_query(column_query) %}
    {% if execute %}
        {{ return(results.columns[0].values()) }}
    {% else %}
        {{ return([]) }}
    {% endif %}
{% endmacro %}
```

The `{% if execute %}` guard is essential: during parsing dbt evaluates macros without connecting to the database, so `run_query()` returns nothing. Wrapping logic in `execute` prevents null-pointer errors at parse time.

### Key Jinja Concepts for dbt

| Concept | Syntax | Purpose |
|---|---|---|
| Variable | `{% set x = 5 %}` | Store a value |
| Output | `{{ x }}` | Render to SQL |
| Comment | `{# ignored #}` | Not rendered |
| For loop | `{% for i in list %}` | Iterate |
| If/else | `{% if condition %}` | Conditional logic |
| Caller reference | `{{ caller() }}` | Wrap a caller's block (advanced) |

### Organizing Macros

- **Keep macros focused**: one transformation per macro, named after what it does (`cents_to_dollars`, not `money_stuff`).
- **Namespace with packages**: if you publish macros in a package, prefix them (`my_pkg.cents_to_dollars`) to avoid name collisions with dbt-utils or other packages.
- **Document in schema.yml**: macros support `arguments` blocks in `schema.yml` — dbt docs will render them just like column descriptions.
- **Test macro output**: test macels indirectly by writing a model that calls the macro and running dbt's built-in tests against it; `dbt-utils`'s `equality` test is handy for regression-checking compiled SQL changes.

Macros are the boundary between a dbt project that copies SQL and one that engineers it — learning them well is what separates a dbt practitioner from a dbt power user.

## 05:03 - dbt Node Selection Syntax: Graph Operators for Targeted Runs

One of dbt's most underrated features is its **node selection syntax** — a mini-language that lets you run precisely the models you care about without touching the rest of the DAG. Mastering it pays dividends in both local development and CI/CD pipelines.

### Basic Selectors

```bash
# Run a single model
dbt run --select orders

# Run everything in a directory (recursive)
dbt run --select models/marts/

# Run by tag
dbt run --select tag:finance

# Run by materialization type
dbt run --select config.materialized:incremental

# Run by source
dbt run --select source:salesforce
```

### Graph Operators

The real power comes from **graph operators** that traverse the DAG:

| Operator | Meaning | Example |
|---|---|---|
| `+` prefix | All upstream ancestors | `+orders` |
| `+` suffix | All downstream dependents | `orders+` |
| `n+` | N levels up/down | `2+orders` |
| `@` prefix | Upstream + downstream of parents | `@orders` |

```bash
# Run orders and everything it depends on
dbt run --select +orders

# Run orders and everything that depends on it
dbt run --select orders+

# Run orders, its parents, and everything that depends on those parents
dbt run --select @orders

# Only go 2 levels upstream
dbt run --select 2+orders
```

### Set Operators for Combining Selectors

```bash
# Union (space-separated): models in finance tag OR marts/
dbt run --select tag:finance models/marts/

# Intersection: models that are BOTH incremental AND in finance
dbt run --select "config.materialized:incremental,tag:finance"

# Exclusion: everything in marts/ EXCEPT anything tagged pii
dbt run --select models/marts/ --exclude tag:pii
```

### Practical CI/CD Pattern: Slim CI

The most impactful use of selectors in production is **slim CI** — only running models changed in a PR:

```bash
# Fetch production state manifest
dbt ls --select state:modified+ --state ./prod-manifest/

# Run only modified models and their downstream dependents
dbt run --select state:modified+ --state ./prod-manifest/
dbt test --select state:modified+ --state ./prod-manifest/
```

This compares your current code against a `manifest.json` from the last production run, skipping unchanged models entirely. On large projects this can cut CI runtime from 30+ minutes to under 5.

### Wildcard and Package Selectors

```bash
# All models whose name starts with "stg_"
dbt run --select "stg_*"

# Models from a specific installed package
dbt run --select package:dbt_utils
```

**Key tip:** Use `dbt ls --select <selector>` before `dbt run` to preview which nodes will be selected — it's a dry-run that prints the list without executing anything, invaluable for validating complex selectors.

## 10:02 - dbt Snapshots: Tracking Slowly Changing Dimensions

Most analytics tables capture a point-in-time state — but business questions often require history: *What was this customer's status last quarter? When did this order move to "shipped"?* dbt **snapshots** solve this by implementing a Type 2 Slowly Changing Dimension (SCD) pattern automatically, adding audit columns to track when rows changed.

### How Snapshots Work

A snapshot queries a source table and, on each run, compares current rows against the previously stored snapshot. Changed rows get their `dbt_valid_to` timestamp closed out and a new row is inserted for the current state. Unchanged rows are left alone.

### Snapshot File Structure

Snapshots live in the `snapshots/` directory (configurable in `dbt_project.yml`) and use a special `{% snapshot %}` block:

```sql
-- snapshots/orders_snapshot.sql
{% snapshot orders_snapshot %}

{{
    config(
        target_schema='snapshots',
        unique_key='order_id',
        strategy='timestamp',
        updated_at='updated_at',
        invalidate_hard_deletes=True
    )
}}

select
    order_id,
    customer_id,
    status,
    total_amount,
    updated_at
from {{ source('ecommerce', 'orders') }}

{% endsnapshot %}
```

Run with: `dbt snapshot`

### Two Snapshot Strategies

**1. Timestamp strategy** — uses a column that tracks when the row last changed. Fastest and preferred when available:

```sql
config(
    strategy='timestamp',
    updated_at='updated_at'    -- column that increments on any change
)
```

**2. Check strategy** — hashes a set of columns and detects changes by comparing hashes. Use when no reliable `updated_at` column exists:

```sql
config(
    strategy='check',
    check_cols=['status', 'shipping_address', 'total_amount']
    -- or check_cols='all' to hash every column
)
```

### Audit Columns dbt Adds Automatically

| Column | Description |
|---|---|
| `dbt_scd_id` | Surrogate key unique to each snapshot row |
| `dbt_updated_at` | When dbt last processed this row |
| `dbt_valid_from` | When this version of the row became active |
| `dbt_valid_to` | When this version expired (`null` = current row) |

### Querying Snapshot History

```sql
-- Current state only
select * from {{ ref('orders_snapshot') }}
where dbt_valid_to is null;

-- State as of a specific date
select * from {{ ref('orders_snapshot') }}
where dbt_valid_from <= '2026-01-01'
  and (dbt_valid_to > '2026-01-01' or dbt_valid_to is null);

-- Full history for one order
select order_id, status, dbt_valid_from, dbt_valid_to
from {{ ref('orders_snapshot') }}
where order_id = 12345
order by dbt_valid_from;
```

### Hard Deletes

By default, rows deleted from the source remain "current" in the snapshot (since dbt never sees them again). Setting `invalidate_hard_deletes=True` tells dbt to detect missing rows and close them out with a `dbt_valid_to` timestamp on the next snapshot run — critical for accurate current-state queries.

### Best Practices

- **Snapshot raw sources, not cleaned models.** Snapshots should sit as close to the source as possible; run cleaning transformations downstream in models that `ref()` the snapshot.
- **Run snapshots before models** in your orchestration pipeline — models that depend on snapshot data need the freshest history.
- **Avoid `check_cols='all'`** on wide tables: it hashes every column including irrelevant metadata fields, creating false positives and bloating history.
- **Partition or cluster snapshot tables** in your warehouse on `dbt_valid_to` and `unique_key` — current-state queries filtering on `dbt_valid_to is null` benefit enormously from this.

Snapshots are one of dbt's most powerful features for analytical use cases — once you've built SCD history into your warehouse, time-travel queries that once required custom ETL pipelines become straightforward SQL.
