# Daily Notes - 2026-08-14

## 00:06 - dbt Access Modifiers: Controlling Model Visibility with public, protected, and private

Introduced in dbt v1.7, **access modifiers** let you declare whether a model is part of your team's public API, internal-only, or somewhere in between. They solve a real pain point: as dbt projects grow — especially in multi-project setups — it becomes hard to know which models are safe to `ref()` from another project and which are internal implementation details that could change without notice.

### The Three Levels

| Access | What it means |
|---|---|
| `public` | Any project can `ref()` this model. It's part of your stable, documented API. |
| `protected` | Only models in the **same project** can `ref()` it. The default for all models. |
| `private` | Only models in the **same group** (within the same project) can `ref()` it. |

### Setting Access in YAML

```yaml
# models/marts/schema.yml
models:
  - name: fct_orders
    access: public          # safe for cross-project ref()
    description: "Core orders fact table — stable API"

  - name: int_orders_enriched
    access: private         # internal to the 'orders' group only
    group: orders
```

```yaml
# models/marts/schema.yml — defining a group
groups:
  - name: orders
    owner:
      name: Data Engineering
      email: data-eng@company.com
```

### Cross-Project References

In a downstream project, you can only `ref()` a model flagged as `public`:

```sql
-- downstream project: analytics
select *
from {{ ref('finance', 'fct_orders') }}   -- project_name, model_name
```

If you accidentally try to `ref()` a `protected` or `private` model from outside its scope, dbt raises a hard error at parse time — no more "it works until someone refactors it."

### Why This Matters

- **Encapsulation at scale.** Teams can freely refactor `private` staging and intermediate models without worrying about breaking consumers in other projects.
- **Explicit contracts.** Marking a model `public` is a social and technical commitment to stability — pair it with a [model contract](https://docs.getdbt.com/docs/collaborate/govern/model-contracts) to enforce column types and names.
- **Governance.** `groups` with named owners make it clear who to contact when an upstream model changes.

### Practical Advice

- Default everything to `protected` (the dbt default) — only promote to `public` deliberately.
- Use `private` inside a group to hide messy intermediate logic that supports a public mart model.
- Combine `access: public` with `contract: enforced: true` for models that other teams depend on — the contract prevents accidental schema drift.
- In monorepo setups without cross-project refs, access modifiers still add value as **documentation** of intended stability and ownership.
