## 00:06 - dbt Access Modifiers: Controlling Model Visibility with public, protected, and private

Introduced in dbt v1.7, **access modifiers** let you declare whether a model is part of your team's public API, internal-only, or somewhere in between. They solve a real pain point: as dbt projects grow — especially in multi-project setups — it becomes hard to know which models are safe to `ref()` from another project and which are internal implementation details that could change without notice.

### The Three Levels

| Access | What it means |
|---|---|
| `public` | Any project can `ref()` this model. It's part of your stable, documented API. |
| `protected` | Only models in the **same project** can `ref()` it. The default for all models. |
| `private` | Only models in the **same group** (within the same project) can `ref()` it. |

### Setting Access in YAML

```yaml
# models/marts/schema.yml
models:
  - name: fct_orders
    access: public          # safe for cross-project ref()
    description: "Core orders fact table — stable API"

  - name: int_orders_enriched
    access: private         # internal to the 'orders' group only
    group: orders
```

```yaml
# models/marts/schema.yml — defining a group
groups:
  - name: orders
    owner:
      name: Data Engineering
      email: data-eng@company.com
```

### Cross-Project References

In a downstream project, you can only `ref()` a model flagged as `public`:

```sql
-- downstream project: analytics
select *
from {{ ref('finance', 'fct_orders') }}   -- project_name, model_name
```

If you accidentally try to `ref()` a `protected` or `private` model from outside its scope, dbt raises a hard error at parse time — no more "it works until someone refactors it."

### Why This Matters

- **Encapsulation at scale.** Teams can freely refactor `private` staging and intermediate models without worrying about breaking consumers in other projects.
- **Explicit contracts.** Marking a model `public` is a social and technical commitment to stability — pair it with a [model contract](https://docs.getdbt.com/docs/collaborate/govern/model-contracts) to enforce column types and names.
- **Governance.** `groups` with named owners make it clear who to contact when an upstream model changes.

### Practical Advice

- Default everything to `protected` (the dbt default) — only promote to `public` deliberately.
- Use `private` inside a group to hide messy intermediate logic that supports a public mart model.
- Combine `access: public` with `contract: enforced: true` for models that other teams depend on — the contract prevents accidental schema drift.
- In monorepo setups without cross-project refs, access modifiers still add value as **documentation** of intended stability and ownership.

## 05:07 - dbt Packages: Extending Your Project with dbt-utils, dbt-expectations, and the Hub

dbt packages let you pull in pre-built macros, tests, and models from the community, avoiding reinventing the wheel. They live in **packages.yml** at the project root and are installed with `dbt deps`.

### Installing Packages

```yaml
# packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.0

  - package: calogica/dbt_expectations
    version: 0.10.4

  - package: dbt-labs/dbt_codegen
    version: 0.13.0
```

Run `dbt deps` to install into the `dbt_packages/` directory (add it to `.gitignore`).

### dbt-utils: The Swiss Army Knife

`dbt-labs/dbt_utils` is the most-used package in the ecosystem. Highlights:

```sql
-- Generate a surrogate key from multiple columns
select
    {{ dbt_utils.generate_surrogate_key(['order_id', 'line_number']) }} as order_line_id,
    order_id,
    product_id
from {{ ref('stg_order_lines') }}
```

```sql
-- Pivot rows to columns dynamically
{{ dbt_utils.pivot('status', dbt_utils.get_column_values(ref('stg_orders'), 'status')) }}
```

```yaml
# Generic tests from dbt-utils
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - dbt_utils.not_empty_string
          - dbt_utils.expression_is_true:
              expression: "total_amount >= 0"
```

### dbt-expectations: Great Expectations, dbt-Style

`calogica/dbt_expectations` ports many Great Expectations checks into dbt generic tests:

```yaml
models:
  - name: fct_revenue
    columns:
      - name: revenue
        tests:
          - dbt_expectations.expect_column_values_to_be_between:
              min_value: 0
              max_value: 1000000
          - dbt_expectations.expect_column_values_to_not_be_null

    tests:
      - dbt_expectations.expect_table_row_count_to_be_between:
          min_value: 1000
          max_value: 10000000
      - dbt_expectations.expect_table_columns_to_match_ordered_list:
          column_list: ["order_id", "customer_id", "revenue", "created_at"]
```

### dbt-codegen: Bootstrapping Schema Files

`dbt-labs/dbt_codegen` auto-generates YAML boilerplate from existing database tables or sources — a huge time-saver when onboarding new models:

```bash
# Generate source YAML for a database schema
dbt run-operation generate_source --args '{"schema_name": "raw_salesforce"}'

# Generate model YAML for an existing model
dbt run-operation generate_model_yaml --args '{"model_names": ["stg_orders", "stg_customers"]}'
```

### Finding Packages

Browse the [dbt Hub](https://hub.getdbt.com) for community packages. You can also reference Git repos directly:

```yaml
packages:
  - git: "https://github.com/your-org/internal-dbt-package.git"
    revision: "v1.2.0"   # tag, branch, or SHA
```

### Best Practices

- **Pin exact versions** in `packages.yml` — minor package updates can introduce breaking changes.
- **Commit `packages.yml`, never `dbt_packages/`** — treat installed packages like `node_modules`.
- Run `dbt deps` in CI before `dbt build` so packages are always fresh relative to the lock.
- Prefer a small number of well-maintained packages over many; each adds a dependency surface.

## 10:04 - dbt Documentation: doc blocks, `dbt docs generate`, and Building a Living Data Dictionary

dbt's built-in documentation system turns your YAML descriptions into a searchable, auto-generated data catalog — complete with DAG lineage. The key insight: docs live **in the repo**, next to the code, so they're versioned and reviewed like any other change.

### The Three Layers of dbt Docs

1. **Inline YAML descriptions** — quick one-liners on models and columns.
2. **Doc blocks** — long-form Markdown stored in `.md` files, referenced by name.
3. **`dbt docs generate` + `dbt docs serve`** — compile everything into a static site.

### Inline YAML Descriptions

```yaml
# models/marts/schema.yml
models:
  - name: fct_orders
    description: "One row per order. Grain: order_id."
    columns:
      - name: order_id
        description: "Surrogate key — SHA256 of (source_system, source_order_id)."
      - name: status
        description: "Current fulfillment status. Values: pending, shipped, delivered, cancelled."
```

Short descriptions belong inline. For anything that needs context, examples, or caveats — use a doc block.

### Doc Blocks: Reusable Markdown Descriptions

Create `.md` files anywhere in your `models/` tree. dbt finds them automatically.

```markdown
<!-- models/marts/docs.md -->
{% docs fct_orders %}
The `fct_orders` model is the central fact table for the orders domain.

**Grain:** one row per order (`order_id`).

**Important caveats:**
- Cancelled orders are included. Filter on `status != 'cancelled'` for revenue metrics.
- `total_amount` is in USD regardless of the originating currency; conversion uses the
  daily rate at order creation time.

**Refresh cadence:** runs hourly via the `orders` dbt job in dbt Cloud.
{% enddocs %}

{% docs order_status %}
Fulfillment lifecycle status. Possible values:

| Value | Meaning |
|---|---|
| `pending` | Payment captured, not yet picked |
| `shipped` | Left the warehouse |
| `delivered` | Confirmed by carrier |
| `cancelled` | Voided before shipment |
{% enddocs %}
```

Reference them in YAML with `{{ doc("block_name") }}`:

```yaml
models:
  - name: fct_orders
    description: "{{ doc('fct_orders') }}"
    columns:
      - name: status
        description: "{{ doc('order_status') }}"
```

The same doc block can be referenced across multiple models — write the definition once and reuse it on every column that shares the same vocabulary.

### Generating and Serving the Docs Site

```bash
# Compile docs + write catalog.json (queries the warehouse for column types)
dbt docs generate

# Spin up a local web server at http://localhost:8080
dbt docs serve
```

The generated site includes:
- A **DAG lineage graph** — click any model to see its upstream sources and downstream consumers.
- Full **column-level metadata** pulled from `catalog.json` (warehouse introspection).
- Rendered **Markdown descriptions** with the doc block content.
- **Test coverage** — which columns have tests attached.

### Deploying Docs in dbt Cloud

In dbt Cloud, enable **"Generate docs on run"** in the job settings. The artifact is hosted at your account's docs URL and updates after every successful job run — no manual step needed.

### Best Practices

- **Require descriptions on public models.** Add a `warn_if` or `error_if` rule in `dbt_project.yml`:
  ```yaml
  models:
    your_project:
      marts:
        +required_docs: true   # dbt v1.9+ feature; use a custom macro in earlier versions
  ```
- **Write for the consumer, not the author.** Describe what the column *means* and when to filter it, not how it was computed.
- **Doc blocks > inline** for anything shared across models or longer than one sentence.
- Commit `manifest.json` and `catalog.json` as CI artifacts so you can diff doc coverage between branches.

## 15:04 - dbt Snapshots: Tracking Slowly Changing Dimensions Over Time

dbt **snapshots** solve a common analytics problem: source tables get updated in place, erasing history. Snapshots record each version of a row as it changes, letting you ask "what did this record look like on date X?" — exactly what you need for SCD Type 2 dimensions like `dim_customers` or `dim_accounts`.

### How Snapshots Work

dbt runs your snapshot query, compares the result to the previously snapshotted records, and inserts new rows for anything that changed. Each snapshot table gains four dbt-managed metadata columns:

| Column | Meaning |
|---|---|
| `dbt_scd_id` | Unique key for each historical record version |
| `dbt_updated_at` | Timestamp when this version was written by dbt |
| `dbt_valid_from` | When this version became active |
| `dbt_valid_to` | When this version was superseded (`NULL` = current) |

### Defining a Snapshot

Snapshots live in a `snapshots/` directory (configurable in `dbt_project.yml`).

```sql
-- snapshots/snap_customers.sql
{% snapshot snap_customers %}

{{
    config(
        target_schema='snapshots',
        unique_key='customer_id',
        strategy='timestamp',
        updated_at='updated_at'
    )
}}

select
    customer_id,
    name,
    email,
    plan_tier,
    status,
    updated_at
from {{ source('crm', 'customers') }}

{% endsnapshot %}
```

Run with `dbt snapshot`. dbt merges changes into the snapshot table on each run.

### Two Invalidation Strategies

**`timestamp`** — recommended when the source has a reliable `updated_at` column. dbt detects a change when `updated_at` is newer than the last snapshot.

```sql
strategy='timestamp',
updated_at='updated_at'
```

**`check`** — compares a list of columns for any change. Use when the source has no reliable timestamp.

```sql
strategy='check',
check_cols=['email', 'plan_tier', 'status']
-- or check_cols='all' to compare every column (slower)
```

### Querying Snapshot History

```sql
-- Current state of all customers
select * from {{ ref('snap_customers') }}
where dbt_valid_to is null;

-- What plan was customer 42 on at the start of Q1 2026?
select plan_tier
from {{ ref('snap_customers') }}
where customer_id = 42
  and dbt_valid_from <= '2026-01-01'
  and (dbt_valid_to > '2026-01-01' or dbt_valid_to is null);
```

### Important Gotchas

- **Snapshots depend on run frequency.** If a row changes and reverts between two snapshot runs, dbt sees no change at all. Run snapshots at least as often as your source data changes.
- **Hard deletes are invisible by default.** If a row disappears from the source, the snapshot row stays open (`dbt_valid_to = NULL`). Use the `invalidate_hard_deletes: true` config to close those rows automatically (dbt 1.5+).
- **Don't ref() a snapshot from a staging model.** Build downstream dimensions by ref()-ing the snapshot in a mart model, keeping transformation logic separate from history capture.
- **Schema changes break snapshots.** Adding or dropping columns in the source requires a snapshot rebuild. Plan source schema changes carefully and version your snapshots.

### Best Practices

- Keep snapshot queries **narrow** — select only the columns you actually care about tracking, not `select *`.
- Store snapshots in a dedicated schema (`snapshots`) separate from staging/marts so they're clearly distinguished in the warehouse.
- Pair each snapshot with a downstream `dim_*` model that applies business logic on top of the raw history (filtering, renaming, joining).
- Add a `meta.owner` and description in `snapshots/schema.yml` — snapshot tables live a long time and ownership matters.
