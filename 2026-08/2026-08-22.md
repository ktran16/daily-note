## 00:04 - [Data Engineering] Late-Arriving Data: Watermarks, Lookback Windows, and Restatement

Events rarely reach your warehouse in the order they happened. A mobile app buffers offline for six hours; a partner API replays yesterday's batch; a Kafka consumer lags during a deploy. The result is the same: a row whose **event time** is Monday lands in your pipeline on Wednesday. If your incremental logic only looks at what's new, that row is silently lost.

**The core distinction is event time vs. processing time.** Partition and aggregate by event time (when it happened), but *select* new work by processing time (when you received it). Conflating them is the root cause of most silent data loss.

**Streaming: watermarks.** Flink and Spark Structured Streaming use a watermark — a moving assertion that "no events older than T will arrive." It bounds how long window state is held open:

```sql
-- Flink SQL: tolerate 15 minutes of out-of-orderness
CREATE TABLE clicks (
  user_id    BIGINT,
  event_time TIMESTAMP(3),
  WATERMARK FOR event_time AS event_time - INTERVAL '15' MINUTE
) WITH ('connector' = 'kafka', ...);
```

Anything later than the watermark is dropped or diverted to a side output. Set it too tight and you lose data; too loose and state (and cost) balloons. Always route late events somewhere rather than discarding them.

**Batch: lookback windows.** In dbt, the naive incremental filter is the bug:

```sql
{% raw %}{{ config(materialized='incremental', unique_key='event_id') }}

select * from {{ source('raw', 'events') }}
{% if is_incremental() %}
  -- BAD:  where event_time > (select max(event_time) from {{ this }})
  -- GOOD: reprocess a trailing window so late rows get merged
  where event_time >= dateadd(day, -3, (select max(event_time) from {{ this }}))
{% endif %}{% endraw %}
```

The trailing window plus `unique_key` (a merge) makes reprocessing idempotent — re-running updates rows instead of duplicating them. Size the window from measured lateness, not intuition:

```sql
select percentile_cont(0.999) within group (order by
  datediff(hour, event_time, ingested_at)) as p999_lag_hours
from raw.events where ingested_at > current_date - 30;
```

**Beyond the window, restate.** For arrivals later than your lookback, run a targeted backfill of affected partitions. Store `ingested_at` on every row so you can always answer "which days changed since yesterday's run?" — that column is what makes correction possible at all.

## 05:03 - [Data Analytics] Window Frames: Why Your Moving Average Is Wrong

Most analysts write `OVER (ORDER BY ...)` and never think about the frame clause. That default is where two very common bugs live.

**Bug 1: the default frame counts ties, not rows.** With `ORDER BY` and no frame, SQL uses `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, and under `RANGE`, "current row" means *all peer rows with the same ORDER BY value*.

```sql
with t(id, amt) as (values ('a',10),('b',10),('c',20))
select id, amt,
  sum(amt) over (order by amt)                                as range_default,
  sum(amt) over (order by amt rows unbounded preceding)       as rows_frame
from t order by amt;
```

| id | amt | range_default | rows_frame |
|----|-----|---------------|------------|
| a  | 10  | **20**        | 10 |
| b  | 10  | **20**        | 20 |
| c  | 20  | 40            | 40 |

A running total that repeats itself on ties is almost never what you wanted. If you're ranking or accumulating row-by-row, say `ROWS` explicitly.

**Bug 2: `ROWS n PRECEDING` counts rows, not days.** A "7-day moving average" written as `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` silently becomes a 7-*observation* average. On a table with missing days it reaches too far back:

```sql
-- daily sales: 08-01=100, 08-02=200, 08-04=400  (no row for 08-03)
select d, amt,
  avg(amt) over (order by d rows between 2 preceding and current row)  as by_rows,
  avg(amt) over (order by d
                 range between interval '2 days' preceding
                           and current row)                            as by_range
from sales order by d;
```

At `08-04`, `by_rows` averages 100/200/400 = **233.3**, silently including a sale from three days outside the intended window. `by_range` averages 200/400 = **300**, exactly the 08-02→08-04 calendar window. Postgres 11+ and DuckDB support interval-offset `RANGE` directly. Not every engine does — BigQuery's `RANGE` frames take numeric offsets only, so there you order by an integer day number (`unix_date(d)`) and write `RANGE BETWEEN 6 PRECEDING AND CURRENT ROW`. Check your engine before assuming.

**Rule of thumb:** use `ROWS` when you mean *N records* (last 5 transactions), `RANGE` with an interval when you mean *N units of time*. And if you need a true trailing-7-day denominator including zero-activity days, join to a date spine first — no frame clause can invent rows that aren't there.

## 10:02 - [ML & AI] ROC-AUC vs PR-AUC: Why Your Fraud Model Looks Better Than It Is

ROC-AUC is the default reported metric in most notebooks. On imbalanced problems it is also the most flattering one, and that flattery hides real cost.

**The two curves plot different denominators.**

- ROC plots TPR = TP/(TP+FN) against FPR = FP/(FP+TN)
- PR plots Precision = TP/(TP+FP) against Recall = TP/(TP+FN)

The difference is `TN`. ROC's x-axis divides false positives by the count of *true negatives* — which, in an imbalanced problem, is enormous. PR never touches TN at all.

**Worked example.** 10,000 transactions, 100 of them fraud (1% prevalence). At some threshold your model flags 200 and catches 50 of the frauds:

| | Predicted + | Predicted − |
|---|---|---|
| **Actual +** | TP = 50 | FN = 50 |
| **Actual −** | FP = 150 | TN = 9,750 |

- Recall = 50/100 = **0.50**
- FPR = 150/9,900 = **0.0152** — looks like a rounding error
- Precision = 50/200 = **0.25** — three out of every four alerts your fraud team opens are innocent

Same confusion matrix, two very different stories. ROC says "1.5% false positive rate, excellent." PR says "75% of your analysts' time is wasted." The analyst queue cares about precision, not FPR.

**Baselines differ too.** A random classifier gets ROC-AUC ≈ 0.5 regardless of prevalence. Its PR-AUC equals the prevalence — here, 0.01. So a PR-AUC of 0.30 on a 1%-positive problem is a 30× lift, not a bad score. Never compare PR-AUC across datasets with different base rates; the floor moves.

```python
from sklearn.metrics import roc_auc_score, average_precision_score

roc = roc_auc_score(y_true, y_score)          # baseline 0.5
pr  = average_precision_score(y_true, y_score) # baseline = y_true.mean()
print(f"ROC-AUC {roc:.3f} | PR-AUC {pr:.3f} (base {y_true.mean():.3f})")
```

Use `average_precision_score`, not `auc(recall, precision)` — the latter interpolates linearly between points, which is optimistically wrong for PR curves.

**Rule of thumb:** if the positive class is rare *and* the cost of acting on a false positive is real (an analyst opens a case, a customer gets blocked), report PR-AUC. Keep ROC-AUC only when both classes matter symmetrically, or when you need a metric that stays stable as prevalence shifts between train and production.

## 15:02 - [Crypto & Business] MEV: How Transaction Ordering Quietly Taxes Your Swaps

When you submit an Ethereum transaction, it doesn't execute immediately. It sits in a public mempool where anyone can read it, and a block builder decides the order of the ~150 transactions that land. **Maximal Extractable Value (MEV)** is the profit available from choosing that order — and a chunk of it comes out of ordinary users' pockets.

**The sandwich, with numbers.** You swap 10 ETH for USDC on a constant-product pool holding 1,000 ETH / 3,000,000 USDC. You set slippage tolerance to 2%, meaning you'll accept any output above ~29,100 USDC. A searcher sees your pending transaction and:

1. **Front-runs**: buys ETH first, pushing the price up.
2. **Your swap executes** at the worsened price — you receive 29,150 USDC instead of the ~29,700 you'd have gotten alone.
3. **Back-runs**: sells the ETH back into the pool at the elevated price.

The searcher pockets roughly the difference minus gas. Your transaction *succeeded* and stayed inside your slippage tolerance, so nothing looks wrong. That 2% you set was not a safety limit — it was a budget you authorized someone to spend.

**Not all MEV is predatory.** Arbitrage between venues and liquidation of undercollateralized loans are also MEV, and both are load-bearing: they keep prices aligned and lending protocols solvent. Sandwiching is the extractive tail.

**Practical mitigations:**

- **Tighten slippage.** On a deep pool, 0.1–0.5% is usually enough. A failed transaction costs gas; a sandwiched one costs principal.
- **Use a private mempool** (MEV-protected RPC endpoints route transactions straight to builders, skipping the public mempool). Several wallets default to this now.
- **Split large orders** or use venues with batch auctions, which settle many trades at one uniform clearing price so ordering within the batch has no value.
- **Check the trade preview**, not the slippage setting — the quoted minimum-received is the number that binds.

Structurally, Ethereum's proposer-builder separation exists partly to make this competition transparent: builders bid for blockspace, and the value surfaces as validator revenue rather than hidden rents.

## 19:03 - [PC Hardware] SSD Buying: Why DRAM Cache and SLC Behavior Matter More Than Gen5 Sequential Numbers

Marketing sells SSDs on peak sequential throughput. That number describes the least common workload on a desktop.

**The tiers, in real terms**

| Tier | Sequential | Random 4K (QD1) | Where it shows up |
|---|---|---|---|
| HDD 7200rpm | ~200 MB/s | ~0.7 MB/s | Bulk/archive only |
| SATA SSD | ~550 MB/s | ~35 MB/s | Still fine for most tasks |
| NVMe Gen3 | ~3,500 MB/s | ~60 MB/s | Sweet spot for value |
| NVMe Gen4 | ~7,000 MB/s | ~75 MB/s | Mainstream today |
| NVMe Gen5 | ~14,000 MB/s | ~80 MB/s | Big files, heavy heat |

Note the right column barely moves. Random small-file I/O at low queue depth dominates boot, app launch, and compile times — and Gen5 is only marginally better there than Gen3. The jump you *feel* is HDD → SSD. Everything after is diminishing.

**Two specs that actually differentiate drives**

1. **DRAM cache.** DRAM-less drives store the flash translation table in NAND and borrow system RAM (HMB). They benchmark fine empty; they degrade sharply when the drive is 80%+ full or under sustained mixed I/O. For a boot drive, prefer DRAM-equipped.
2. **SLC cache exhaustion.** Consumer TLC/QLC drives write to a fast pseudo-SLC region, then collapse to native speed. A 2TB TLC drive may hold ~7 GB/s for 200 GB, then drop to 1.5 GB/s. QLC can fall to **80–150 MB/s** — slower than a SATA SSD. If you routinely move 100 GB+ (video, game installs, dataset shuffling), read a sustained-write review, not a CrystalDiskMark screenshot.

**Endurance and headroom**

TBW ratings run roughly 600 TBW per TB on TLC. At 50 GB/day that's ~30 years — endurance is rarely the limiter. Free space is: keep 10–20% unallocated so garbage collection and the SLC cache have room.

**Practical picks:** DRAM-backed Gen4 TLC for the OS drive, a cheap high-capacity QLC or SATA drive for a media library, HDD only for cold bulk. Check `smartctl -a /dev/nvme0` for `Percentage Used` and `Data Units Written` before trusting a used drive.
