## 00:03 - [Data Engineering] Idempotent Backfills in Airflow: Designing Tasks You Can Safely Re-run

A backfill is just your DAG run many times over past intervals. It only works if every task is **idempotent** — running it twice for the same interval leaves the warehouse in the same state as running it once. Most backfill horror stories (duplicated rows, doubled revenue) are idempotency bugs, not Airflow bugs.

**Rule 1: never use wall-clock time.** `datetime.now()` makes a task produce different output on every re-run. Use the interval Airflow hands you:

```python
@task
def load_orders(data_interval_start, data_interval_end):
    # bound the read by the interval, not by "today"
    df = extract(f"""
        SELECT * FROM source.orders
        WHERE updated_at >= '{data_interval_start}'
          AND updated_at <  '{data_interval_end}'
    """)
```

Half-open `[start, end)` bounds matter: closed-on-both-ends windows double-count rows landing exactly on the boundary.

**Rule 2: replace, don't append.** Delete-then-insert scoped to the partition is the simplest idempotent write:

```sql
DELETE FROM analytics.orders WHERE order_date = '{{ ds }}';
INSERT INTO analytics.orders SELECT ... WHERE order_date = '{{ ds }}';
```

Better, if your warehouse supports it, is an atomic partition swap (`INSERT OVERWRITE` on Spark/BigQuery, `ALTER TABLE ... EXCHANGE PARTITION` on Iceberg) so readers never see the gap between delete and insert. A blind `INSERT` is the classic non-idempotent write — re-run it and you have duplicates with no way to tell which copy is real.

**Rule 3: make side effects safe.** Writing files to `s3://.../orders/dt={{ ds }}/part-0.parquet` overwrites cleanly. Writing to `part-{uuid}.parquet` accumulates garbage across retries. Emails, Slack alerts, and payment calls are *not* idempotent — guard them behind a check or keep them out of backfilled tasks entirely.

**Running the backfill:**

```bash
airflow dags backfill orders_daily \
  --start-date 2026-07-01 --end-date 2026-07-31
```

Set `max_active_runs=1` on the DAG if downstream tables can't tolerate concurrent writes to the same partition; raise it when partitions are truly independent and you want the backfill to finish this decade.

Test idempotency before you need it: run one task twice and assert the row count is unchanged.

## 05:03 - [Data Analytics] Gaps-and-Islands in SQL: Finding Streaks and Missing Ranges

"How long is each user's login streak?" and "which days did this sensor go silent?" are the same problem wearing different hats. The pattern that solves both is called **gaps-and-islands**, and the trick is one line of arithmetic.

### Islands: consecutive runs

If a sequence has no gaps, its values increase in lockstep with `ROW_NUMBER()`. Subtract one from the other and every row in the same run collapses to an identical constant — a free grouping key.

```sql
WITH activity AS (
  SELECT DISTINCT user_id, activity_date FROM events
),
grouped AS (
  SELECT user_id, activity_date,
         activity_date
           - (ROW_NUMBER() OVER (PARTITION BY user_id
                                 ORDER BY activity_date))::int AS grp
  FROM activity
)
SELECT user_id,
       MIN(activity_date) AS streak_start,
       MAX(activity_date) AS streak_end,
       COUNT(*)           AS streak_days
FROM grouped
GROUP BY user_id, grp
ORDER BY streak_days DESC;
```

Walk through a user active Mar 1, 2, 3, 7, 8. Row numbers are 1–5, so `grp` is `Feb 28, Feb 28, Feb 28, Mar 3, Mar 3` — two islands, of 3 and 2 days. The dates inside `grp` are meaningless; only their equality matters.

### Gaps: the space between

Gaps fall out of `LEAD` on the same deduplicated set:

```sql
SELECT user_id, activity_date + 1 AS gap_start, next_date - 1 AS gap_end
FROM (
  SELECT user_id, activity_date,
         LEAD(activity_date) OVER (PARTITION BY user_id
                                   ORDER BY activity_date) AS next_date
  FROM activity
) t
WHERE next_date > activity_date + 1;
```

### Islands over a changing attribute

For "how long did each server stay in each status," use the difference of *two* row numbers — one partitioned by entity, one also by status:

```sql
ROW_NUMBER() OVER (PARTITION BY server_id ORDER BY ts)
  - ROW_NUMBER() OVER (PARTITION BY server_id, status ORDER BY ts) AS grp
```

Three pitfalls: **dedupe first** (two rows on the same date silently split a streak), truncate timestamps to your grain before applying it, and remember this finds gaps in *observed* data — if you need "days with zero activity" relative to a calendar, join a date spine first.

## 10:03 - [ML & AI] Probability Calibration: When 0.8 Should Actually Mean 80%

A classifier's `predict_proba` output is not a probability just because it lives in [0,1]. If your model says 0.8 for 100 loans, roughly 80 should default — otherwise every downstream decision built on that number (expected-value thresholds, risk-adjusted pricing, triage queues) is wrong, even when AUC looks great. **Ranking quality and calibration are independent properties.** A model can rank perfectly and still be systematically overconfident.

**Who miscalibrates, and how:**
- **Boosted trees (XGBoost/LightGBM)**: pushed toward 0 and 1 — logloss training with many rounds sharpens scores past the truth.
- **SVMs / naive Bayes**: naive Bayes is wildly overconfident because it double-counts correlated features.
- **Deep nets**: overconfident, worse with more capacity.
- **Logistic regression / plain random forests**: usually the closest to calibrated out of the box (RF is under-confident at the extremes — averaging pulls toward the middle).

**Measuring it.** Bin predictions and compare mean predicted vs. observed rate. Expected Calibration Error is the weighted average gap:

$$\text{ECE} = \sum_{b} \frac{n_b}{N} \left| \text{acc}(b) - \text{conf}(b) \right|$$

Worked example — three bins, 1000 samples: bin [0.7,0.8) has 200 samples, mean prediction 0.75, actual rate 0.60 → gap 0.15. Bin [0.8,0.9): 300 samples, pred 0.85, actual 0.70 → gap 0.15. Bin [0.9,1.0]: 500 samples, pred 0.95, actual 0.82 → gap 0.13. ECE = (0.2)(0.15) + (0.3)(0.15) + (0.5)(0.13) = **0.14**. The model is ~14 points overconfident on average — fatal if you're pricing risk.

**Fixing it.** Fit a post-hoc map from raw score to calibrated probability, on data the model never trained on:

```python
from sklearn.calibration import CalibratedClassifierCV, calibration_curve
from sklearn.metrics import brier_score_loss

# 'sigmoid' = Platt scaling (parametric, good for <1k samples)
# 'isotonic' = monotonic step fit (nonparametric, needs ~1k+, can overfit)
cal = CalibratedClassifierCV(base_model, method="isotonic", cv=5)
cal.fit(X_train, y_train)

p = cal.predict_proba(X_test)[:, 1]
print(brier_score_loss(y_test, p))          # lower = better; combines calibration + sharpness
prob_true, prob_pred = calibration_curve(y_test, p, n_bins=10)
```

**Two traps.** Calibrating on training predictions does nothing — the model already fits them, so use `cv=` or a held-out split. And if you resampled to fix class imbalance (SMOTE, undersampling), your probabilities are shifted to the *resampled* prior; calibrate against the true base rate or divide out the shift.

Track **Brier score** alongside AUC. AUC tells you the ordering is right; Brier tells you the numbers are usable.
