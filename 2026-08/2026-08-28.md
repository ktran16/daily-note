## 00:03 - [Data Engineering] The Small File Problem: Compaction and File Layout in Iceberg and Delta

Streaming ingestion and frequent micro-batch writes create a quiet killer: thousands of tiny Parquet files. Each one costs a metadata lookup, an object-store GET with its own latency, and a task slot in Spark. A table with 200k files of 1 MB each scans far slower than the same 200 GB in 1,000 files of 200 MB — same bytes, 200x the overhead.

**Diagnose first.** Iceberg exposes metadata tables:

```sql
SELECT file_path, file_size_in_bytes, record_count
FROM db.events.files
ORDER BY file_size_in_bytes ASC LIMIT 20;

-- Rough health check
SELECT COUNT(*) AS files, AVG(file_size_in_bytes)/1024/1024 AS avg_mb
FROM db.events.files;
```

If `avg_mb` is well under ~100, you have a layout problem. Delta's equivalent is `DESCRIBE DETAIL db.events` (`numFiles`, `sizeInBytes`).

**Compact.** Iceberg ships a rewrite procedure; run it on recent partitions rather than the whole table:

```sql
CALL catalog.system.rewrite_data_files(
  table => 'db.events',
  strategy => 'sort',
  sort_order => 'tenant_id, event_ts',
  where => 'event_date >= current_date - INTERVAL 3 DAYS',
  options => map('target-file-size-bytes','536870912',
                 'min-input-files','5')
);
```

Delta's counterpart is `OPTIMIZE db.events WHERE event_date >= ... ZORDER BY (tenant_id)`.

**Then clean up.** Compaction *adds* files — the old ones stay for time travel. Reclaim storage only after your longest-running reader and rollback window have passed:

```sql
CALL catalog.system.expire_snapshots('db.events', TIMESTAMP '2026-08-21 00:00:00', 100);
CALL catalog.system.remove_orphan_files(table => 'db.events', older_than => TIMESTAMP '2026-08-21 00:00:00');
```

**Prevent, don't just repair.** Over-partitioning is the usual root cause: partitioning by `event_ts` at hour granularity across 500 tenants guarantees tiny files. Prefer daily partitions plus Iceberg hidden partitioning (`days(event_ts)`) and let sort order handle selectivity. For streaming writers, trade latency for size — a 5-minute commit interval produces 60x fewer files than 5 seconds.

Schedule compaction as a first-class orchestrated job with its own SLA, not a thing someone remembers to run after the dashboard gets slow.

## 05:03 - [Data Analytics] Deduplication in SQL: QUALIFY, Deterministic Tie-Breakers, and the Silent Row Loss

Every warehouse has a table where "one row per customer" is a lie — CDC replays, retried API loads, and late-arriving corrections all leave duplicates. The classic fix is `ROW_NUMBER()`, but the way most people write it quietly drops or duplicates rows.

**The standard pattern.** On Snowflake, BigQuery, and DuckDB you can skip the subquery entirely with `QUALIFY`:

```sql
SELECT *
FROM raw.orders
QUALIFY ROW_NUMBER() OVER (
          PARTITION BY order_id
          ORDER BY updated_at DESC, ingested_at DESC, _file_row_id DESC
        ) = 1;
```

On Postgres or MySQL 8, wrap it instead:

```sql
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY order_id
    ORDER BY updated_at DESC, ingested_at DESC, _file_row_id DESC) AS rn
  FROM raw.orders
)
SELECT * FROM ranked WHERE rn = 1;
```

**The bug: non-deterministic ordering.** If you order only by `updated_at` and two rows share the same second, the engine picks either one — and picks differently on each run. A table with 4.2M orders where 0.3% of `order_id`s have a timestamp tie means ~12,600 rows can flip between builds, so your daily revenue total drifts by a few hundred dollars with no code change. Always end the `ORDER BY` with something unique (a surrogate key, file+row offset, or `_airbyte_raw_id`). That third column is not decoration; it is what makes the query reproducible.

**Pick the right function.** `ROW_NUMBER` returns exactly one row per key. `RANK` returns *all* tied rows — using it here reintroduces the duplicates you were removing. `DISTINCT` only helps when entire rows are identical, which CDC output rarely is.

**Verify before you trust it.** Cheap assertion that survives refactors:

```sql
SELECT order_id, COUNT(*) AS n
FROM analytics.orders_deduped
GROUP BY 1 HAVING COUNT(*) > 1;
```

Zero rows, or the model is wrong. Also compare `COUNT(DISTINCT order_id)` in source vs. target — they must match exactly. If the deduped count is *lower*, your partition key is too coarse and you are deleting real orders, not duplicates.
