## 00:02 - dbt Custom Schema Resolution: Controlling Where Models Land with `generate_schema_name`

By default, dbt builds models into a single schema (your `target.schema` from `profiles.yml`). But real projects need finer control — staging models in `analytics_staging`, marts in `analytics_marts`, and so on. dbt's `generate_schema_name` macro is the hook that makes this possible.

### The Problem

Without customization, a model with `schema: marts` configured in `dbt_project.yml` or a model's config block gets built into `<target_schema>_marts` in development — not just `marts`. This is actually intentional: dbt namespaces schemas per developer to prevent collisions.

```yaml
# dbt_project.yml
models:
  my_project:
    staging:
      +schema: staging
    marts:
      +schema: marts
```

In dev (`target.schema = dbt_alice`), this produces:
- `dbt_alice_staging.stg_orders`
- `dbt_alice_marts.fct_orders`

In prod (`target.schema = analytics`), it produces:
- `analytics_staging.stg_orders`
- `analytics_marts.fct_orders`

### Overriding the Default Behavior

If you want production to use exact schema names (no prefix), override `generate_schema_name` in `macros/`:

```sql
-- macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) -%}
  {%- set default_schema = target.schema -%}

  {%- if custom_schema_name is none -%}
    {{ default_schema }}

  {%- elif target.name == 'prod' -%}
    {{ custom_schema_name | trim }}

  {%- else -%}
    {{ default_schema }}_{{ custom_schema_name | trim }}

  {%- endif -%}
{%- endmacro %}
```

Now in prod, `schema: marts` resolves to exactly `marts`. In dev it still gives `dbt_alice_marts`, keeping developers isolated.

### Per-Model Schema Configuration

You can also set schema inline in a model's config block:

```sql
-- models/marts/fct_orders.sql
{{ config(schema='marts') }}

select ...
```

### Generating Custom Database Names

The same pattern applies to databases via `generate_database_name`:

```sql
{% macro generate_database_name(custom_database_name, node) -%}
  {%- if custom_database_name is none -%}
    {{ target.database }}
  {%- else -%}
    {{ custom_database_name | trim }}
  {%- endif -%}
{%- endmacro %}
```

### Key Takeaways

- dbt's default schema naming (`<target>_<custom>`) protects dev environments from collision.
- Override `generate_schema_name` in a macro to use exact names in production.
- Always gate the override on `target.name == 'prod'` so dev isolation is preserved.
- The built-in `dbt_utils.generate_schema_name_for_env` macro from `dbt-utils` provides this pattern out of the box — check it before writing your own.

## 05:03 - dbt Mesh & Cross-Project References: Scaling dbt Across Teams

As data teams grow, a single monolithic dbt project becomes a bottleneck — slow CI, merge conflicts, and unclear ownership. **dbt Mesh** (introduced in dbt v1.6) solves this by letting multiple dbt projects share models across project boundaries using cross-project `ref()`.

### The Core Idea

In a traditional single-project setup, all models live together. With dbt Mesh, you split them into **producer** projects and **consumer** projects:

- **Producer project** (e.g., `platform`) owns foundational models and explicitly publishes certain models as **public**.
- **Consumer project** (e.g., `finance_analytics`) references those public models without duplicating the underlying SQL.

### Making a Model Public

In the producer project, mark a model's access level in its `.yml` file:

```yaml
# models/marts/fct_orders.yml  (in the "platform" project)
models:
  - name: fct_orders
    access: public          # visible to other projects
    config:
      contract:
        enforced: true      # public models should have contracts
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
```

Access levels: `private` (same folder), `protected` (same project, the default), `public` (cross-project).

### Referencing Across Projects

In the consumer project, declare the producer as a dependency in `dependencies.yml`:

```yaml
# dependencies.yml  (in the "finance_analytics" project)
projects:
  - name: platform
```

Then reference the public model using the two-argument form of `ref()`:

```sql
-- models/finance/revenue_summary.sql  (in "finance_analytics")
with orders as (
    select * from {{ ref('platform', 'fct_orders') }}
),

revenue as (
    select
        order_date,
        sum(order_total) as daily_revenue
    from orders
    group by 1
)

select * from revenue
```

dbt resolves `ref('platform', 'fct_orders')` to the physical location of `fct_orders` in the warehouse — no data copying required.

### Model Contracts Are Essential

Cross-project `ref()` is only safe when the producer's schema is stable. That's why public models should always have **model contracts** (`contract: enforced: true`) with declared column names and data types. If the producer breaks the contract, the build fails immediately rather than silently corrupting downstream consumers.

### Governance with Groups

Pair public access with **groups** to assign clear ownership:

```yaml
groups:
  - name: platform_team
    owner:
      slack: "#platform-data"

models:
  - name: fct_orders
    group: platform_team
    access: public
```

This lets `dbt-project-evaluator` and dbt Cloud surface which team owns which models across your entire mesh.

### Key Takeaways

- Split large projects by domain — each team owns their project and publishes only what downstream teams need.
- Use `access: public` + `contract: enforced: true` together; a public model without a contract is a liability.
- Cross-project `ref('project', 'model')` resolves at the warehouse level — no ETL, no duplication.
- dbt Mesh works with both dbt Cloud (where the metadata hub is managed) and dbt Core (using `dbt ls --output json` to generate artifacts that consumers read).

## 10:03 - dbt Hooks: Running SQL Before and After Your Models

dbt hooks let you execute arbitrary SQL at key points in a run — before a model builds, after it builds, or around the entire `dbt run` invocation. They're the escape hatch for anything dbt doesn't handle natively: granting permissions, logging run metadata, enabling warehouse features, or managing transient objects.

### Four Hook Types

| Hook | Scope | When it fires |
|---|---|---|
| `pre-hook` | Model / seed / snapshot | Before the model's SQL executes |
| `post-hook` | Model / seed / snapshot | After the model's SQL executes successfully |
| `on-run-start` | Project | Once at the start of `dbt run` / `dbt build` |
| `on-run-end` | Project | Once at the end of `dbt run` / `dbt build` |

### `on-run-start` and `on-run-end` in `dbt_project.yml`

Use these for project-wide setup and teardown:

```yaml
# dbt_project.yml
on-run-start:
  - "call audit.begin_run('{{ run_started_at }}', '{{ invocation_id }}')"

on-run-end:
  - "call audit.end_run('{{ invocation_id }}', {{ results | length }} )"
  - "grant usage on schema {{ target.schema }} to role reporter"
```

`results` is a special context variable available only in `on-run-end` — it's a list of result objects (one per node) you can iterate over to log failures or counts.

### `pre-hook` and `post-hook` on Models

Set them in a model's config block or in `dbt_project.yml`:

```sql
-- models/marts/fct_orders.sql
{{ config(
    materialized='table',
    post_hook=[
        "grant select on {{ this }} to role analytics_reader",
        "insert into audit.model_log (model, built_at) values ('{{ this }}', current_timestamp)"
    ]
) }}

select ...
```

`{{ this }}` resolves to the fully-qualified relation name (`database.schema.model`) so hooks always target the right table, even when schema names vary by environment.

### Project-Level `pre-hook` / `post-hook`

Apply hooks to entire model folders via `dbt_project.yml`:

```yaml
models:
  my_project:
    marts:
      +post-hook:
        - "grant select on {{ this }} to role bi_tool"
```

The `+` prefix means the config cascades to all models in the folder and subfolders.

### Using Macros in Hooks

Hooks accept any Jinja expression, including macro calls:

```sql
-- macros/grant_select.sql
{% macro grant_select(role) %}
  grant select on {{ this }} to role {{ role }}
{% endmacro %}
```

```yaml
models:
  my_project:
    marts:
      +post-hook: "{{ grant_select('analytics') }}"
```

This keeps hooks DRY — one macro, applied everywhere.

### Hooks vs. Operations

For one-off administrative tasks, `dbt run-operation` is cleaner. Hooks shine when the action is tightly coupled to the model lifecycle (e.g., granting permissions on every build) rather than a standalone operation.

### Key Takeaways

- Use `on-run-start` / `on-run-end` for project-wide bookkeeping (audit logs, schema grants).
- Use `pre-hook` / `post-hook` for per-model work (row-level grants, post-load transformations).
- `{{ this }}` in a hook always refers to the current model's fully-qualified name.
- Chain multiple hooks as a YAML list — dbt runs them in order.
- Hook failures cause the model run to fail, so keep hook SQL simple and idempotent.

## 15:03 - dbt `--defer` and State: Slimming CI Runs and Saving Developer Time

One of dbt's most underused features is **state-based selection** — the ability to compare your current project against a previous run's manifest and only execute what actually changed. Combined with `--defer`, it dramatically cuts CI time and eliminates the need for developers to build every upstream model locally.

### The Problem

In a large dbt project, `dbt build` might take 45 minutes. Running the full DAG on every pull request wastes time and compute. Developers who only changed one model shouldn't wait for hundreds of unrelated models to rebuild.

### How `--state` Works

dbt compares your current project to a `manifest.json` from a previous run (usually production). You reference that artifact with `--state`:

```bash
# Run only models that changed compared to production
dbt run --select state:modified+ --state ./prod-artifacts

# Build only modified models AND their downstream dependents
dbt build --select state:modified+ --state ./prod-artifacts
```

The `state:modified` selector catches:
- Models whose SQL changed
- Models whose config changed (materialization, schema, tags, etc.)
- Models whose upstream dependencies changed
- Models with new or changed tests

The `+` suffix (like `state:modified+`) extends selection to all downstream dependents of modified nodes, ensuring you don't test a changed model in isolation without also rebuilding what depends on it.

### `--defer`: Reference Prod for Unbuilt Upstream Models

`--defer` tells dbt to resolve unselected upstream `ref()` calls to their production equivalents instead of failing because those models don't exist in your dev schema:

```bash
# Build only the changed model; resolve upstream refs to prod tables
dbt build \
  --select state:modified+ \
  --state ./prod-artifacts \
  --defer
```

Without `--defer`, running a downstream model in isolation would fail because its upstream table doesn't exist in `dbt_alice` (your dev schema). With `--defer`, dbt transparently reads from the prod table for unbuilt upstream models, and writes outputs to your dev schema.

### Setting Up the Workflow

1. **Download the production manifest in CI** before running dbt:

```bash
# Example: fetch from S3 where dbt Cloud or your CD pipeline uploads it
aws s3 cp s3://my-dbt-artifacts/prod/manifest.json ./prod-artifacts/manifest.json
```

2. **Run only modified nodes**:

```bash
dbt build \
  --select state:modified+ \
  --state ./prod-artifacts \
  --defer \
  --target ci
```

3. **Upload the new manifest** after a successful production run so the next CI comparison is fresh:

```bash
aws s3 cp ./target/manifest.json s3://my-dbt-artifacts/prod/manifest.json
```

### Other Useful State Selectors

| Selector | What it matches |
|---|---|
| `state:new` | Models that don't exist in the prior state |
| `state:modified` | Models changed since the prior state |
| `state:modified.body` | Only SQL body changed (not config) |
| `state:modified.configs` | Only config changed |
| `state:old` | Models that existed in prior state but not now |

### Key Takeaways

- `--state` + `state:modified+` limits CI runs to only what changed — a 45-minute full run becomes a 3-minute targeted run.
- `--defer` fills in unbuilt upstream models with their production equivalents, making selective builds safe.
- Store `manifest.json` in a persistent location (S3, GCS, dbt Cloud artifact storage) and download it at the start of every CI run.
- dbt Cloud handles this automatically via its **Slim CI** feature — it fetches the production manifest and applies `--defer` without manual setup.

## 19:05 - dbt Packages & dbt-utils: Extending Your Project with Community-Built Macros

dbt has a thriving package ecosystem that lets you pull in reusable macros, models, and tests without reinventing the wheel. Packages are declared in `packages.yml` at the root of your project and installed with `dbt deps`.

### Installing Packages

```yaml
# packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: 1.3.0
  - package: calogica/dbt_expectations
    version: 0.10.4
  - package: dbt-labs/audit_helper
    version: 0.12.0
```

Run `dbt deps` to download them into the `dbt_packages/` directory (add this to `.gitignore`).

### dbt-utils: The Essential Toolkit

**dbt-labs/dbt_utils** is the most widely used dbt package. Key macros:

**`generate_surrogate_key`** — creates a consistent hashed primary key from multiple columns, replacing brittle `md5()` casts:

```sql
select
    {{ dbt_utils.generate_surrogate_key(['order_id', 'product_id']) }} as order_item_key,
    order_id,
    product_id,
    quantity
from {{ ref('stg_order_items') }}
```

**`star`** — selects all columns from a relation while excluding specific ones — avoids `select *` without listing every field:

```sql
select
    {{ dbt_utils.star(from=ref('stg_orders'), except=['_loaded_at', '_file_name']) }}
from {{ ref('stg_orders') }}
```

**`date_spine`** — generates a continuous date series, essential for filling gaps in time-series reporting:

```sql
{{ dbt_utils.date_spine(
    datepart="day",
    start_date="cast('2023-01-01' as date)",
    end_date="current_date"
) }}
```

**Generic tests from dbt-utils:**

```yaml
# schema.yml
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - dbt_utils.not_empty_string
          - dbt_utils.expression_is_true:
              expression: "total_amount >= 0"
```

### dbt_expectations: Data Quality at Scale

**calogica/dbt_expectations** ports Great Expectations-style assertions into dbt:

```yaml
- name: order_amount
  tests:
    - dbt_expectations.expect_column_values_to_be_between:
        min_value: 0
        max_value: 100000
    - dbt_expectations.expect_column_values_to_not_be_null
```

### Best Practices

- **Pin exact versions** in `packages.yml` to keep builds reproducible across environments.
- **Run `dbt deps` in CI** before `dbt build` — never commit the `dbt_packages/` folder.
- **Check hub.getdbt.com** for the full package registry; many adapters (Snowflake, BigQuery, Spark) have adapter-specific utility packages.
- Avoid over-relying on packages for logic that belongs in your own macros — keep core business logic under your project's control.
