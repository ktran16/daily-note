## 00:02 - dbt Semantic Layer & MetricFlow: Define Metrics Once, Query Everywhere

The **dbt Semantic Layer** (powered by MetricFlow) lets you define business metrics in your dbt project and expose them through a consistent interface — so every BI tool, notebook, or API query against those metrics produces the same number.

### Why It Matters

Without a semantic layer, "monthly revenue" gets defined differently in Looker, Tableau, and a data scientist's ad-hoc query. The semantic layer centralizes that logic in version-controlled YAML.

### Core Concepts

**Semantic Model** — describes a physical table/view (your dbt model) along with its entities (join keys), dimensions, and measures:

```yaml
# models/marts/semantic_model_orders.yml
semantic_models:
  - name: orders
    model: ref('fct_orders')
    entities:
      - name: order_id
        type: primary
      - name: customer_id
        type: foreign
    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day
      - name: status
        type: categorical
    measures:
      - name: order_total
        agg: sum
        expr: amount
      - name: order_count
        agg: count_distinct
        expr: order_id
```

**Metric** — a named calculation derived from one or more measures:

```yaml
metrics:
  - name: revenue
    type: simple
    label: "Total Revenue"
    type_params:
      measure: order_total

  - name: revenue_growth_wow
    type: derived
    label: "Revenue Growth WoW"
    type_params:
      expr: (revenue - revenue_offset) / revenue_offset
      metrics:
        - name: revenue
        - name: revenue
          offset_window: 1 week
          alias: revenue_offset
```

### Querying with the CLI

Use `mf query` (MetricFlow CLI) to validate metrics locally before wiring up a BI tool:

```bash
# Simple metric with a time dimension
mf query --metrics revenue --group-by metric_time__month

# Two metrics + categorical dimension
mf query \
  --metrics revenue,order_count \
  --group-by metric_time__week,order__status \
  --limit 10
```

### Key Metric Types

| Type | Use Case |
|------|----------|
| `simple` | Single measure, no formula |
| `ratio` | Numerator / denominator (e.g., conversion rate) |
| `derived` | Formula over other metrics (e.g., growth %) |
| `cumulative` | Running total over a window or all time |

### Best Practices

- **One semantic model per grain**: match each semantic model to a single fact table at a consistent granularity.
- **Use `label` fields**: these become display names in connected BI tools — write them for end users, not engineers.
- **Validate early**: run `mf validate-configs` in CI to catch broken metric references before they reach production.
- **Dimension reuse**: shared dimensions (like `customer_region`) should live in their own semantic model and be joined via entities, not duplicated.

The semantic layer works with dbt Cloud's Semantic Layer API and connects directly to tools like Tableau, Hex, and Mode — eliminating metric drift across your organization.

## 05:03 - dbt Seeds: Managing Static Reference Data in Your Project

**Seeds** are CSV files that dbt loads directly into your warehouse as tables. They're ideal for small, slow-changing reference data that doesn't live in a source system — country codes, product category mappings, cost center lookups, and similar data.

### When to Use Seeds (and When Not To)

**Good use cases:**
- Static lookup tables (ISO country codes, status code mappings)
- Small manual reference data updated infrequently (< a few thousand rows)
- Test fixtures for development environments

**Avoid seeds for:**
- Large datasets (use `dbt source` + a proper ingestion tool instead)
- Data that changes daily (operational overhead quickly outweighs convenience)
- Sensitive data (CSV files live in your repo — don't store PII or credentials)

### Creating a Seed

Place a CSV in the `seeds/` directory of your project:

```
seeds/
  country_codes.csv
  product_categories.csv
```

```csv
# seeds/country_codes.csv
country_code,country_name,region
US,United States,North America
GB,United Kingdom,Europe
JP,Japan,Asia Pacific
DE,Germany,Europe
```

Run `dbt seed` to load it into your warehouse. dbt creates a table named after the file (e.g., `country_codes`) in your target schema.

### Configuring Seeds in `dbt_project.yml`

```yaml
seeds:
  my_project:
    # Put seeds in a dedicated schema
    +schema: reference

    country_codes:
      # Override column types — dbt infers from CSV but you can enforce
      +column_types:
        country_code: varchar(2)
        country_name: varchar(100)

    product_categories:
      +schema: product_reference
      +tags: ["product", "reference"]
```

### Using Seeds in Models

Reference seeds the same way you reference models — with `ref()`:

```sql
-- models/marts/fct_orders_enriched.sql
select
    o.order_id,
    o.customer_id,
    o.amount,
    cc.country_name,
    cc.region
from {{ ref('fct_orders') }} o
left join {{ ref('country_codes') }} cc
    on o.country_code = cc.country_code
```

Using `ref()` (not a hardcoded schema path) ensures seeds appear in your DAG and dbt handles cross-environment schema resolution automatically.

### Adding Tests to Seeds

Seeds support the same schema tests as models. Define them in a YAML file:

```yaml
# seeds/schema.yml
version: 2

seeds:
  - name: country_codes
    description: "ISO 3166-1 alpha-2 country codes with region mapping"
    columns:
      - name: country_code
        tests:
          - not_null
          - unique
      - name: region
        tests:
          - not_null
          - accepted_values:
              values: ["North America", "Europe", "Asia Pacific", "Latin America", "Africa"]
```

Run `dbt test --select country_codes` to validate the seed data after loading.

### Best Practices

- **Keep seeds small**: if a CSV exceeds ~1,000 rows or changes frequently, model it as a source with a proper ingestion pipeline.
- **Use `+schema: reference`**: isolate seeds in a dedicated schema so analysts know they're static reference data, not transformed facts/dims.
- **Version-control your CSVs**: seeds live in Git — treat changes to them like code changes (review, test, deploy).
- **Run `dbt seed --full-refresh`** when you need to drop and recreate the table (e.g., after removing columns or changing primary keys).
- **Document with descriptions**: seeds often contain domain knowledge; descriptions in YAML make that knowledge discoverable in `dbt docs`.

## 10:03 - dbt Incremental Models: Efficiently Processing Large Datasets

**Incremental models** are dbt's answer to the "I don't want to rebuild my entire 10-billion-row table every run" problem. Instead of a full table rebuild, dbt only processes new or changed rows and appends/merges them into the existing table.

### How It Works

When you add `materialized='incremental'` to a model, dbt changes its behavior:

- **First run**: builds the full table (same as `table` materialization)
- **Subsequent runs**: filters the query to only new/changed records, then upserts or appends them

```sql
-- models/marts/fct_events.sql
{{ config(
    materialized='incremental',
    unique_key='event_id'
) }}

select
    event_id,
    user_id,
    event_type,
    occurred_at,
    properties
from {{ source('raw', 'events') }}

{% if is_incremental() %}
  -- Only process rows newer than the latest record already in the table
  where occurred_at > (select max(occurred_at) from {{ this }})
{% endif %}
```

`{{ this }}` refers to the model's own table in the warehouse. The `is_incremental()` macro returns `true` only on incremental runs, so the `where` clause is skipped on the initial full build.

### Incremental Strategies

The `incremental_strategy` config tells dbt how to merge new data with existing data:

| Strategy | How It Works | Best For |
|----------|-------------|----------|
| `append` | INSERT only, no deduplication | event streams with no updates |
| `merge` | MERGE statement (upsert) | tables with updates (requires `unique_key`) |
| `delete+insert` | DELETE matching rows, then INSERT | adapters without native MERGE |
| `insert_overwrite` | Overwrite specific partitions | BigQuery/Spark partitioned tables |

```yaml
{{ config(
    materialized='incremental',
    unique_key='event_id',
    incremental_strategy='merge',
    merge_update_columns=['event_type', 'properties']  -- only update these cols
) }}
```

### Handling Late-Arriving Data

A pure `max(timestamp)` filter misses late-arriving events. Use a lookback window instead:

```sql
{% if is_incremental() %}
  where occurred_at >= (
    select dateadd('hour', -3, max(occurred_at))
    from {{ this }}
  )
{% endif %}
```

This reprocesses the last 3 hours on every run, catching events that arrived out of order while keeping runtime manageable.

### Partitioning for Performance

On BigQuery, pair incremental models with partition filters to avoid full-table scans:

```sql
{{ config(
    materialized='incremental',
    unique_key='event_id',
    incremental_strategy='insert_overwrite',
    partition_by={
        'field': 'occurred_at',
        'data_type': 'timestamp',
        'granularity': 'day'
    },
    require_partition_filter=true
) }}
```

### Full Refresh

Run `dbt run --full-refresh --select fct_events` to rebuild the table from scratch — useful when your filter logic changes or you need to reprocess historical data. The `is_incremental()` block is bypassed and the table is dropped and rebuilt.

### Best Practices

- **Always set `unique_key`** with `merge` strategy — without it, you'll get duplicate rows.
- **Test your filter logic**: add a `dbt test` that checks for unexpected duplicates after each run (`dbt-utils.unique_combination_of_columns`).
- **Keep lookback windows small but safe**: too short misses late data; too long kills performance. Tune based on your pipeline's SLA.
- **Avoid `select *` in incremental models**: schema changes upstream won't surface until a `--full-refresh`, which can cause silent data gaps.
- **Monitor row counts**: a sudden drop in incremental rows often means your filter is broken, not that traffic slowed down.
