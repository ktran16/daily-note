## 00:02 - dbt `defer` and `--state`: Running Slim CI Without a Full Warehouse Clone

One of the most powerful but underused dbt features is **slim CI** — running only the models that changed in a pull request rather than rebuilding your entire project on every commit. The `--defer` flag and `--state` selector make this possible.

### The Problem

In a large project, `dbt build` can touch hundreds of models and cost significant time and money on every CI run. Most PRs only change a handful of models, yet the whole DAG rebuilds anyway.

### How `--state` Selection Works

`--state` lets you compare the current project against a previously compiled **manifest** (`manifest.json`). dbt uses this manifest to detect what changed.

```bash
# Run only models modified in this PR (and their downstream dependents)
dbt build --select state:modified+ --state ./prod-manifest/
```

The `state:modified` selector catches:
- Models whose SQL changed
- Models whose `schema.yml` config changed
- Models with new or removed tests
- Any upstream ancestor that changed (propagated via `+`)

### How `--defer` Works

`--defer` tells dbt: "for any model I'm *not* running, resolve its `ref()` to the **production** version instead of expecting it in the dev schema."

```bash
dbt build \
  --select state:modified+ \
  --state ./prod-manifest/ \
  --defer \
  --target ci
```

Without `--defer`, if `model_c` depends on `model_a` and you only changed `model_c`, dbt would fail because `model_a` doesn't exist in your CI schema. With `--defer`, dbt reads `model_a` from prod — no rebuild needed.

### Setting Up the Prod Manifest

The manifest is just the `manifest.json` generated by any dbt run. In GitHub Actions:

```yaml
- name: Download prod manifest
  run: |
    dbt ls --target prod --output path   # just to trigger a compile
    # Or pull from your artifact store / dbt Cloud API:
    curl -H "Authorization: Token $DBT_CLOUD_API_KEY" \
      "https://cloud.getdbt.com/api/v2/accounts/$ACCOUNT_ID/runs/$PROD_RUN_ID/artifacts/manifest.json" \
      -o prod-manifest/manifest.json

- name: Run slim CI
  run: |
    dbt build \
      --select state:modified+ \
      --state prod-manifest/ \
      --defer \
      --target ci
```

### `state:modified` vs `state:new`

| Selector | What it catches |
|---|---|
| `state:modified` | SQL or config changed |
| `state:new` | Model didn't exist in the prior manifest |
| `state:modified+` | Changed models + all downstream dependents |
| `state:modified+1` | Changed models + only direct children |

### Key Considerations

- **Freshness**: the prod manifest must be recent; a stale one misses changes since the last prod run.
- **Schema drift**: if deferred models have schema changes in prod not yet in your branch, tests might behave unexpectedly.
- **dbt Cloud**: if you use dbt Cloud, the "Slim CI" job type handles manifest fetching automatically via the API — no manual artifact download needed.

### Why This Matters

Slim CI can cut CI run times by 80–95% on large projects. It also reduces warehouse costs since you're only materializing the delta, not the full DAG. Combined with `--defer`, dev environments become much cheaper because developers only build what they're actively working on.

## 05:03 - dbt Hooks: Running SQL Before and After Your Models

dbt **hooks** let you execute arbitrary SQL at specific points in the model lifecycle — before a model runs, after it completes, or around every dbt operation. They're the escape hatch for warehouse-level actions that don't fit cleanly into model SQL.

### The Four Hook Types

| Hook | Scope | Runs when |
|---|---|---|
| `pre-hook` | model or project | Before each model materializes |
| `post-hook` | model or project | After each model materializes |
| `on-run-start` | project | Once at the start of `dbt run/build` |
| `on-run-end` | project | Once after all models complete |

### Granting Permissions After Materialization

The most common use case: grant `SELECT` to a BI role every time a model rebuilds.

```yaml
# models/schema.yml or dbt_project.yml
models:
  my_project:
    marts:
      +post-hook:
        - "GRANT SELECT ON {{ this }} TO ROLE reporter"
```

`{{ this }}` is a Jinja variable that resolves to the fully-qualified table name (`database.schema.model_name`) at runtime.

### Logging Audit Rows

Track when each model ran by inserting into an audit table:

```yaml
# dbt_project.yml
models:
  +post-hook:
    - "INSERT INTO audit.dbt_run_log (model, run_at)
       VALUES ('{{ this.name }}', CURRENT_TIMESTAMP)"
```

### Applying Row-Level Security Policies (Snowflake)

```yaml
models:
  sensitive:
    +post-hook:
      - "ALTER TABLE {{ this }}
         ADD ROW ACCESS POLICY row_policy ON (user_id)"
```

### Project-Level Hooks with `on-run-start` / `on-run-end`

These run once per invocation — useful for creating temp tables, setting session parameters, or sending notifications:

```yaml
# dbt_project.yml
on-run-start:
  - "ALTER SESSION SET QUERY_TAG = 'dbt_run'"
  - "CALL sp_lock_audit_table()"

on-run-end:
  - "CALL sp_unlock_audit_table()"
  - "INSERT INTO audit.run_summary
       SELECT '{{ invocation_id }}', CURRENT_TIMESTAMP, {{ results | length }}"
```

`{{ results }}` in `on-run-end` is a list of all model run results — you can filter for failures, successes, or skips.

### Hooks on Specific Models Only

Override project-level defaults in a model's config block:

```sql
-- models/marts/orders.sql
{{ config(
    materialized='table',
    post_hook=[
        "GRANT SELECT ON {{ this }} TO ROLE analyst",
        "GRANT SELECT ON {{ this }} TO ROLE data_science"
    ]
) }}

SELECT ...
```

### Important Caveats

- **Hooks run inside the same transaction** as the model (where the warehouse supports transactions). If the hook fails, the whole model rolls back.
- **`on-run-end` hooks still run even if some models fail.** Use `{{ results }}` to conditionally act only on successes.
- **Avoid business logic in hooks.** They're for infrastructure concerns (grants, policies, logging). Model SQL is easier to test and version.
- **dbt Cloud Semantic Layer and dbt Mesh**: if you expose models cross-project, post-hook grants become critical — downstream consumers need access to the physical tables, not just the dbt abstraction.

Hooks are a small feature with a large blast radius: a misconfigured `pre-hook` that drops a table will fire on every run. Keep them simple, idempotent, and well-commented.

## 10:03 - dbt Exposures: Documenting How Your Data Is Consumed Downstream

dbt models don't live in a vacuum — dashboards, ML models, and applications consume them. **Exposures** let you declare those downstream consumers directly in your dbt project, making them first-class citizens in your DAG and documentation.

### What Is an Exposure?

An exposure is a YAML declaration that describes something *outside* dbt that depends on your dbt models. It could be a Looker dashboard, a Tableau workbook, a Python ML pipeline, an API endpoint, or a Streamlit app.

```yaml
# models/exposures.yml
exposures:
  - name: weekly_revenue_dashboard
    type: dashboard
    maturity: high
    url: https://bi.company.com/dashboards/weekly-revenue
    description: >
      Executive dashboard showing weekly and MTD revenue by region and product.
      Used in the Monday leadership review.
    owner:
      name: Analytics Team
      email: analytics@company.com
    depends_on:
      - ref('fct_orders')
      - ref('dim_customers')
      - ref('dim_products')
```

### Exposure Types

dbt recognizes these built-in types (you can also use custom strings):

| Type | Use case |
|---|---|
| `dashboard` | BI tool dashboards (Looker, Tableau, Metabase) |
| `notebook` | Jupyter / Databricks notebooks |
| `analysis` | Ad-hoc SQL queries or reports |
| `ml` | Machine learning models or feature pipelines |
| `application` | Operational apps, APIs, or data products |

### Maturity Levels

The `maturity` field signals how stable or production-ready the exposure is:

```yaml
maturity: low     # experimental / prototyping
maturity: medium  # in active development
maturity: high    # stable, production-critical
```

This is metadata only — dbt doesn't enforce anything based on maturity — but it's invaluable for communicating risk to stakeholders.

### Why Exposures Matter

**1. Impact analysis via the DAG.** In `dbt docs`, exposures appear as leaf nodes at the end of your lineage graph. You can immediately see which dashboards or apps are affected when a model changes.

```bash
# Rebuild everything a dashboard depends on
dbt build --select +exposure:weekly_revenue_dashboard
```

**2. Targeted CI.** Run only the models that a specific exposure needs:

```bash
dbt build --select +exposure:weekly_revenue_dashboard --defer --state prod-manifest/
```

**3. Better documentation.** `dbt docs generate` includes exposure pages with owner contact, URL, description, and lineage — so data consumers know what feeds their tool and who to contact when something breaks.

**4. Cross-functional communication.** Declaring a `maturity: high` exposure with a BI dashboard URL makes it obvious that a model is production-critical, not just "probably used somewhere."

### A Complete Exposure with Multiple Dependents

```yaml
exposures:
  - name: churn_prediction_model
    type: ml
    maturity: medium
    url: https://mlflow.company.com/experiments/churn-v3
    description: >
      XGBoost churn model retrained weekly. Features are pulled from the
      feature store which reads from dbt marts.
    owner:
      name: Data Science Team
      email: datascience@company.com
    depends_on:
      - ref('fct_user_events')
      - ref('fct_subscriptions')
      - ref('dim_users')
      - source('feature_store', 'user_demographics')
```

Note: exposures can depend on both `ref()` models and `source()` tables.

### Querying Exposures in Selection Syntax

```bash
# All models feeding into any exposure
dbt ls --select +exposure:*

# Only models feeding a specific exposure
dbt ls --select +exposure:weekly_revenue_dashboard

# Models used by high-maturity exposures (requires dbt 1.5+)
dbt ls --select +exposure:*,config.maturity:high
```

### Best Practices

- **One exposure file per domain** (e.g., `models/marketing/exposures.yml`, `models/finance/exposures.yml`) keeps things organized as the project grows.
- **Declare the most critical consumers first.** Even one exposure per high-stakes dashboard pays dividends during incident response — you can instantly answer "what does this model feed?"
- **Keep URLs current.** A stale URL is worse than no URL because it erodes trust in your docs.
- **Use `owner.email`** so on-call engineers know who to ping when a model feeding that exposure fails.

Exposures are the lightest-weight way to connect your dbt project to the real world. They cost minutes to write and pay back in faster incident triage, smarter CI targeting, and documentation that actually reflects how data flows end-to-end.

## 15:03 - [Crypto & Business] CAC, LTV, and Payback: The Three Numbers That Decide If Growth Kills You

Spending money to acquire customers is only rational if those customers pay you back faster than your cash runs out. Three metrics govern that, and they must be computed together — any one alone is misleading.

### CAC (Customer Acquisition Cost)

Fully-loaded sales and marketing spend divided by *new* customers acquired in the same window. Include salaries, tooling, and commissions — not just ad spend.

```
Q3 S&M spend:        $300,000  (ads $180k + 2 AEs $100k + tools $20k)
New customers:              60
CAC = 300,000 / 60      = $5,000
```

Common error: dividing by *total* customers instead of new ones, which flatters CAC dramatically.

### LTV (Lifetime Value)

Gross-margin-weighted, not revenue-weighted. For subscriptions:

```
ARPA (monthly)          = $500
Gross margin            = 80%   -> $400/mo contribution
Monthly logo churn      = 2%    -> avg lifetime = 1/0.02 = 50 months
LTV = 400 x 50          = $20,000
```

That 80% matters. A business with 40% margin on the same revenue has half the LTV — which is why hardware and services businesses can't spend like SaaS companies.

### Payback Period

```
CAC Payback = CAC / monthly gross-margin contribution
            = 5,000 / 400 = 12.5 months
```

LTV:CAC here is 4:1 — healthy by the common 3:1 rule of thumb. But payback is what determines whether you need financing. At 12.5 months, every customer you sign is a 12.5-month cash hole. Sign 60 in a quarter and you're down $300k before the first cohort breaks even. Companies die at 4:1 LTV:CAC with 24-month payback while surviving at 3:1 with 6-month payback.

### The Traps

- **Churn assumptions**: LTV divides by churn, so a 2% vs 3% monthly churn estimate swings LTV by 33%. Early-stage companies rarely have enough history to know theirs — cap the lifetime at 36 months rather than extrapolating.
- **Blended vs paid CAC**: organic signups hide expensive paid channels. Segment them.
- **Annual prepay** changes everything: collecting 12 months upfront can turn a 12-month payback into immediate cash-positive acquisition, which is why annual discounts exist.

## 19:03 - [PC Hardware] PSU Sizing: Transient Spikes, Efficiency Curves, and Why the Wattage on the Box Lies

Power supply sizing is where most builders either overspend by 400W or quietly build an unstable machine. The useful mental model is not "add up TDPs" — it's **sustained load plus transient headroom**.

### Sustained load is smaller than you think

Add the real numbers, not the marketing ones:

| Component | Typical sustained draw |
|---|---|
| Mid-range CPU (65–105W TDP class) | 90–160W under all-core load |
| High-end CPU (125–170W TDP class) | 200–280W |
| Mid-range GPU (e.g. 200W class) | 200–220W |
| High-end GPU (350–450W class) | 350–475W |
| Motherboard + RAM + fans | 40–70W |
| Each NVMe SSD | 5–9W (peak, not idle) |
| Each 3.5" HDD | 6–9W running, ~25W spin-up surge |

A high-end gaming build realistically lands at 600–750W sustained. That does **not** mean a 750W unit is correct.

### Transients are the real sizing constraint

Modern GPUs draw microsecond-to-millisecond spikes far above their rated board power — historically 1.5–2× on some designs. A 450W card can momentarily pull 800W+. A PSU whose over-current protection trips on that spike shuts the system off instantly, and the symptom looks exactly like a bad GPU or bad RAM: black screen mid-game, no error, no log entry.

Two ways to handle it:
- **ATX 3.x / 3.1 units** are specified to ride out 200% excursions for 100µs without tripping. This is the actual reason to prefer them, far more than the 12V-2x6 connector.
- **Older ATX 2.x units** need roughly 1.5× your GPU's rated power in headroom instead.

### The efficiency curve

80 Plus ratings are measured at 20%, 50%, and 100% load. Efficiency peaks near 50%:

| Rating | ~50% load efficiency (115V) |
|---|---|
| Bronze | 85% |
| Gold | 90% |
| Platinum | 92% |
| Titanium | 94% (and ≥90% at 10% load) |

The gap between Gold and Platinum is ~2 points. At 300W average draw for 4 hours a day, that's roughly 9 kWh a year — a rounding error on your bill. **Buy Gold for the build quality tier it signals, not for the electricity savings.** Titanium earns its price only in an always-on homelab idling at low load, where its 10%-load rating actually matters.

### Practical sizing rule

Take sustained load, then:
- ATX 3.x unit → add ~30% → round up to the next standard size
- ATX 2.x unit → size so the PSU's rating is ≥ sustained load + (0.5 × GPU rated watts)

A 750W ATX 3.1 Gold unit covers nearly every single-GPU consumer build through several upgrade cycles.

### What actually matters more than wattage

- **OEM platform, not brand.** Brands rebadge; look up who builds the specific model and what the review-bench ripple and hold-up-time numbers are.
- **Single +12V rail** on modern units avoids per-rail OCP surprises.
- **Warranty length is a proxy for capacitor quality** — 10–12 years signals a platform the manufacturer expects to survive; 3–5 years signals it won't.
- **Never reuse modular cables between PSUs**, even same-brand. Pinouts differ between platforms and a mismatch puts 12V onto a ground pin. This kills hardware immediately.
- **Seat the 12V-2x6 connector until it clicks.** Partial insertion is the documented cause of melted connectors, not the standard itself.

### Debugging a suspected PSU problem

Random shutdowns under load with no BSOD, no event log, and no thermal throttling point at power delivery. Before RMA'ing anything, cap the GPU's power limit to 70% (`nvidia-smi -pl <watts>` on Linux, or the vendor tuning utility) and retest. If stability returns, you've confirmed transients — not a defective card.
