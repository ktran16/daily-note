## 00:03 - dbt Documentation: doc() Blocks, Schema Descriptions, and the Docs Site

Good documentation is the difference between a data warehouse people trust and one people fear. dbt makes it easy to embed documentation directly in your project and auto-generate a browsable, searchable site.

### Three Layers of dbt Documentation

**1. Inline descriptions in `schema.yml`**

The simplest form — add a `description` directly to a model, column, or source:

```yaml
models:
  - name: orders
    description: "One row per order placed through the e-commerce platform."
    columns:
      - name: order_id
        description: "Surrogate key for the order, generated via dbt-utils."
      - name: status
        description: "Current fulfillment status: pending, shipped, or delivered."
```

These descriptions render in the docs site and are accessible via `{{ model.description }}` in macros.

**2. `doc()` blocks for rich, reusable descriptions**

For longer documentation or prose shared across multiple models, use `docs` blocks stored in `.md` files:

```markdown
{% docs order_status %}
The `status` column tracks fulfillment progress through the pipeline:

| Value     | Meaning                            |
|-----------|------------------------------------|
| pending   | Payment received, not yet shipped  |
| shipped   | In transit to customer             |
| delivered | Confirmed delivery                 |
| returned  | Item sent back, credit issued      |

Source of truth is the `fulfillment_events` table updated by the warehouse system.
{% enddocs %}
```

Reference it in `schema.yml`:

```yaml
columns:
  - name: status
    description: "{{ doc('order_status') }}"
```

This keeps descriptions DRY — update the `.md` file once and every model referencing it picks up the change.

**3. Generating and serving the docs site**

```bash
dbt docs generate   # compiles docs into target/catalog.json
dbt docs serve      # opens a local web server at localhost:8080
```

The site shows the full DAG as an interactive lineage graph, column-level metadata, test coverage, and source freshness status.

### Best Practices

- **Document at the grain**: describe what one row represents, not just column names.
- **Commit `manifest.json`** (not `catalog.json`) for Slim CI comparisons — `catalog.json` is warehouse-state and shouldn't live in git.
- **Use `docs` blocks for shared definitions** like business logic or status enums that multiple models reference.
- **Tag undocumented models** with `dbt list --select tag:needs_docs` by combining tags and a CI check requiring descriptions on public models.
- In dbt Cloud, docs are auto-published after each production job run and accessible to stakeholders without running anything locally.

A documented dbt project acts as a living data dictionary — far more accurate than a wiki that drifts out of sync the moment the underlying SQL changes.

## 05:02 - dbt defer: Using Production Artifacts for Faster Local Development

`dbt defer` lets developers reference production-built models instead of rebuilding the entire DAG from scratch. It saves significant time and warehouse costs during development by "deferring" upstream dependencies to already-existing production objects.

### The Problem It Solves

Without `defer`, running a model that sits 10 hops deep in your DAG means rebuilding all 10 upstream models in your dev environment — expensive and slow. With `defer`, dbt uses the production version of anything you haven't changed.

### How It Works

`defer` requires a **production manifest** (`manifest.json`), which records what was built last time the production job ran. You point dbt at that artifact and it resolves `ref()` calls to the production schema for any model not in your current selection.

```bash
# Download the production manifest first (from dbt Cloud artifacts or S3)
dbt run --select my_model+ --defer --state ./prod-artifacts/
```

dbt resolves the dependency graph like this:
- Models **in your selection** → built in your dev schema
- Models **not in your selection** → resolved to production equivalents

### Practical Setup

**Step 1: Fetch the production manifest**

In dbt Cloud, artifacts are accessible via the API:
```bash
dbt-cloud artifact download --run-id <prod_run_id> --artifact manifest.json \
  --output-path ./prod-artifacts/
```

Or pull from S3/GCS where your CI uploads them:
```bash
aws s3 cp s3://my-dbt-artifacts/prod/manifest.json ./prod-artifacts/
```

**Step 2: Run with defer**

```bash
# Run only changed models and their downstream dependents
dbt run --select state:modified+ --defer --state ./prod-artifacts/

# Run a single model, deferring everything upstream
dbt run --select orders --defer --state ./prod-artifacts/
```

**Step 3: Test with defer**

```bash
dbt test --select orders --defer --state ./prod-artifacts/
```

### `--favor-state` Flag

By default, if a model exists in both dev and prod, dbt uses the dev version. The `--favor-state` flag reverses this — always prefer the production artifact unless the model is explicitly selected:

```bash
dbt run --select orders --defer --favor-state --state ./prod-artifacts/
```

This is useful when your dev schema has stale or partial data you don't want polluting downstream tests.

### Combining with `state:modified`

The real power comes from pairing `defer` with state-based selection:

```bash
# Only run what changed since the last production run, defer everything else
dbt build --select state:modified+ --defer --state ./prod-artifacts/
```

This pattern is also the foundation of **Slim CI** — run only changed models in pull requests, using prod as the baseline, dramatically cutting CI runtime.

### Caveats

- **Schema drift**: if you rename or drop a column in prod that a deferred model references, you'll get a runtime error in dev — same as prod would.
- **Seeds and snapshots** don't fully support `defer`; it's primarily for models and tests.
- **dbt Cloud** automates artifact management and can inject `--defer --state` into dev runs transparently via the "defer to production" environment setting.

`defer` is one of the highest-leverage dbt features for large projects — it turns a full-DAG rebuild into a targeted, fast iteration loop.

## 10:03 - dbt Variables: Dynamic Configuration with var() and --vars

dbt variables let you parameterize models, macros, and configurations so the same code behaves differently across environments, runs, or use cases — without changing any SQL.

### Defining Variables

Variables are declared in `dbt_project.yml` under the `vars` key:

```yaml
vars:
  # Project-wide defaults
  start_date: '2020-01-01'
  environment: 'dev'
  payment_methods: ['credit_card', 'paypal', 'bank_transfer']
```

These are defaults; they can always be overridden at run time.

### Using `var()` in Models and Macros

Reference a variable inside any Jinja context with `var('name')` or `var('name', default)`:

```sql
-- models/orders.sql
select *
from {{ ref('raw_orders') }}
where created_at >= '{{ var("start_date") }}'
  and payment_method in (
    {{ "'" + var('payment_methods') | join("', '") + "'" }}
  )
```

The optional second argument provides a fallback so the model still compiles when the variable isn't set:

```sql
where region = '{{ var("target_region", "global") }}'
```

### Overriding at Run Time with `--vars`

Pass variables on the command line to override project defaults for a single run:

```bash
# Single variable
dbt run --vars 'start_date: 2024-01-01'

# Multiple variables (YAML dict syntax)
dbt run --vars '{start_date: 2024-01-01, environment: prod}'

# From CI — useful for dynamic date windows
dbt run --select fct_events --vars "start_date: $(date -d '7 days ago' +%Y-%m-%d)"
```

`--vars` always wins over `dbt_project.yml` defaults, which is what makes it safe to keep sensible dev defaults and override them in production jobs.

### Environment-Specific Defaults via Profiles

Combine variables with profile targets to get per-environment behavior without logic sprawl:

```yaml
# dbt_project.yml
vars:
  is_full_refresh: false
  lookback_days: 3       # dev default: small window

# In your CI/production job, override:
# dbt build --vars '{lookback_days: 90, is_full_refresh: true}'
```

Then in a model:

```sql
{% if var('is_full_refresh') %}
  select * from {{ ref('raw_events') }}
{% else %}
  select * from {{ ref('raw_events') }}
  where event_date >= dateadd('day', -{{ var('lookback_days') }}, current_date)
{% endif %}
```

### Variables in `dbt_project.yml` Configurations

Variables can also drive model configurations, not just SQL logic:

```yaml
models:
  my_project:
    marts:
      +materialized: "{{ 'table' if var('environment') == 'prod' else 'view' }}"
```

This renders models as tables in production and cheap views in development — without touching a single model file.

### Scoping Variables to Packages

If you use dbt packages, you can scope variables to avoid name collisions:

```yaml
vars:
  dbt_utils:
    surrogate_key_treat_nulls_as_empty_string: true
  my_project:
    start_date: '2020-01-01'
```

### Best Practices

- **Always provide defaults** via `dbt_project.yml` so models compile locally without needing `--vars`.
- **Name variables clearly** — `lookback_days` beats `n` or `days`.
- **Avoid overusing variables for logic branching** — if a model behaves wildly differently per variable, consider splitting it into two models.
- **Document your variables** in `dbt_project.yml` comments so the next developer knows what each one controls and what values are valid.

Variables are lightweight but powerful — they let you write one model that serves dev, staging, and prod without duplication or environment-specific branches in git.

## 15:03 - dbt Semantic Layer and MetricFlow: Defining Metrics Once, Querying Everywhere

The **dbt Semantic Layer** (powered by MetricFlow) lets you define business metrics centrally in your dbt project and query them consistently across any downstream tool — BI platforms, notebooks, or APIs — without re-implementing the same calculation in a dozen places.

### The Problem It Solves

Without a semantic layer, "revenue" means different things in Looker, Tableau, and a Python notebook. Each analyst hard-codes their own filters, grain, and aggregation logic. The semantic layer makes one definition the truth for everyone.

### Core Concepts

**Semantic Models** — wrappers around dbt models that declare entities, dimensions, and measures:

```yaml
# models/semantics/sem_orders.yml
semantic_models:
  - name: orders
    model: ref('fct_orders')
    entities:
      - name: order_id
        type: primary
      - name: customer_id
        type: foreign
    dimensions:
      - name: created_at
        type: time
        type_params:
          time_granularity: day
      - name: status
        type: categorical
    measures:
      - name: order_count
        agg: count
        expr: order_id
      - name: revenue
        agg: sum
        expr: amount_usd
```

**Metrics** — derived from measures; can be simple, ratio, cumulative, or derived:

```yaml
metrics:
  - name: revenue
    type: simple
    label: "Total Revenue (USD)"
    type_params:
      measure: revenue

  - name: average_order_value
    type: ratio
    label: "Average Order Value"
    type_params:
      numerator: revenue
      denominator: order_count

  - name: revenue_growth_mom
    type: derived
    label: "Revenue Growth MoM"
    type_params:
      expr: (revenue - revenue_prior) / revenue_prior
      metrics:
        - name: revenue
        - name: revenue
          offset_window: 1 month
          alias: revenue_prior
```

### Querying the Semantic Layer

With dbt Cloud, use the **Semantic Layer APIs** or the `mf` (MetricFlow) CLI:

```bash
# CLI query
mf query --metrics revenue,order_count \
         --group-by metric_time__month,customer__region \
         --where "metric_time >= '2024-01-01'" \
         --limit 100

# Output: clean tabular results, no SQL needed
```

Or query directly in Python via the `dbt-sl-sdk`:

```python
from dbtsl import SemanticLayerClient

client = SemanticLayerClient(
    environment_id=123,
    auth_token="<token>",
    host="semantic-layer.cloud.getdbt.com"
)

results = client.query(
    metrics=["revenue", "order_count"],
    group_by=["metric_time__month"],
)
```

BI tools like Tableau, Looker, and Mode can connect natively to the dbt Semantic Layer via JDBC/ADBC, pulling metric definitions without any custom SQL.

### Saved Queries

Pre-define common metric+dimension combinations for fast access:

```yaml
saved_queries:
  - name: monthly_revenue_by_region
    label: "Monthly Revenue by Region"
    query_params:
      metrics:
        - revenue
        - order_count
      group_by:
        - metric_time__month
        - customer__region
```

### Best Practices

- **Model at the grain of your measures** — `fct_orders` at the order grain, not pre-aggregated.
- **Use `entities` to enable joins** across semantic models; MetricFlow handles the SQL join logic automatically.
- **Version your metrics** by adding a `label` and `description` — these surface in BI tools and act as documentation.
- **Start simple**: define a handful of core metrics before expanding; a semantic model with 50 measures is hard to maintain.
- **Semantic Layer requires dbt Cloud** for the hosted API; dbt Core users can use MetricFlow locally via `mf query` but won't get the BI tool integrations.

Centralizing metric definitions in dbt means analysts stop arguing about numbers and start acting on them.

## 19:03 - dbt Model Contracts: Enforcing Schema Guarantees Across Your DAG

A **model contract** is a formal promise about a model's public interface — its columns, data types, and constraints. dbt enforces contracts at build time, catching breaking changes before they silently corrupt downstream models.

### Why Contracts Matter

Without contracts, a developer can rename a column, change a data type, or drop a field in an upstream model and not discover the downstream breakage until tests fail hours later — or worse, in production. Contracts make the interface explicit and machine-verifiable.

### Defining a Contract

Add a `contract` block to any model's YAML config:

```yaml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true       # fails the build if the schema drifts
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: foreign_key
            to: ref('dim_customers')
            to_columns: [customer_id]
      - name: order_date
        data_type: date
        constraints:
          - type: not_null
      - name: amount_usd
        data_type: numeric(18,2)
      - name: status
        data_type: varchar(50)
```

When `enforced: true`, dbt compares the compiled model's actual output schema against the declared columns and types. If anything is missing or mismatched, the run fails with a clear error before any data is written.

### Constraint Types

| Constraint | Behavior | Adapter Support |
|---|---|---|
| `not_null` | Column must not contain NULLs | Universal |
| `unique` | All values must be distinct | Universal |
| `primary_key` | Implies not_null + unique | Most warehouses |
| `foreign_key` | References another model's column | BigQuery, Snowflake, others |
| `check` | Custom SQL expression (`expr: amount > 0`) | Snowflake, Postgres |

Note: constraint enforcement varies by adapter. Some warehouses (e.g. BigQuery) support `not_null` natively; others only log a warning. Check adapter-specific docs.

### Model-Level Constraints

You can also define constraints at the model level (not tied to a specific column):

```yaml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    constraints:
      - type: primary_key
        columns: [order_id]
      - type: check
        name: positive_amount
        expression: "amount_usd >= 0"
```

### Contracts and Access Modifiers

Model contracts pair naturally with dbt's **access** system. Mark a model `public` to signal it's a stable API others depend on, and enforce a contract to back that promise:

```yaml
models:
  - name: fct_orders
    access: public          # other teams' projects can ref() this model
    config:
      contract:
        enforced: true
```

A `protected` or `private` model is internal scaffolding — contracts there are optional. Reserve `enforced: true` for public models that serve as cross-team boundaries.

### Column-Level Documentation with Contracts

Because you must enumerate all columns in a contract, it naturally doubles as documentation. Add `description` to each column entry — you get schema enforcement and a data dictionary in one place:

```yaml
columns:
  - name: amount_usd
    data_type: numeric(18,2)
    description: "Total order value in US dollars, tax and shipping inclusive."
    constraints:
      - type: not_null
```

### Best Practices

- **Enforce contracts on public/shared models** first — that's where schema drift causes the most cross-team pain.
- **Be explicit with numeric precision** (`numeric(18,2)` not just `numeric`) — type mismatches in aggregations often come from implicit casting.
- **Combine contracts with `dbt build`** in CI so the enforced schema check runs before downstream models execute.
- **Don't over-constrain internal staging models** — contracts add friction; reserve that friction for stable interfaces.
- **Treat a contract change like an API version bump**: communicate it in a PR, give downstream consumers time to adapt, and bump the model version if dbt's versioning system is in use.

Model contracts shift schema governance left — instead of discovering breakage in production, you catch it in the PR pipeline where it's cheapest to fix.
