# Daily Notes - 2026-08-08

## 00:03 - dbt Documentation: doc() Blocks, Schema Descriptions, and the Docs Site

Good documentation is the difference between a data warehouse people trust and one people fear. dbt makes it easy to embed documentation directly in your project and auto-generate a browsable, searchable site.

### Three Layers of dbt Documentation

**1. Inline descriptions in `schema.yml`**

The simplest form — add a `description` directly to a model, column, or source:

```yaml
models:
  - name: orders
    description: "One row per order placed through the e-commerce platform."
    columns:
      - name: order_id
        description: "Surrogate key for the order, generated via dbt-utils."
      - name: status
        description: "Current fulfillment status: pending, shipped, or delivered."
```

These descriptions render in the docs site and are accessible via `{{ model.description }}` in macros.

**2. `doc()` blocks for rich, reusable descriptions**

For longer documentation or prose shared across multiple models, use `docs` blocks stored in `.md` files:

```markdown
{% docs order_status %}
The `status` column tracks fulfillment progress through the pipeline:

| Value     | Meaning                            |
|-----------|------------------------------------|
| pending   | Payment received, not yet shipped  |
| shipped   | In transit to customer             |
| delivered | Confirmed delivery                 |
| returned  | Item sent back, credit issued      |

Source of truth is the `fulfillment_events` table updated by the warehouse system.
{% enddocs %}
```

Reference it in `schema.yml`:

```yaml
columns:
  - name: status
    description: "{{ doc('order_status') }}"
```

This keeps descriptions DRY — update the `.md` file once and every model referencing it picks up the change.

**3. Generating and serving the docs site**

```bash
dbt docs generate   # compiles docs into target/catalog.json
dbt docs serve      # opens a local web server at localhost:8080
```

The site shows the full DAG as an interactive lineage graph, column-level metadata, test coverage, and source freshness status.

### Best Practices

- **Document at the grain**: describe what one row represents, not just column names.
- **Commit `manifest.json`** (not `catalog.json`) for Slim CI comparisons — `catalog.json` is warehouse-state and shouldn't live in git.
- **Use `docs` blocks for shared definitions** like business logic or status enums that multiple models reference.
- **Tag undocumented models** with `dbt list --select tag:needs_docs` by combining tags and a CI check requiring descriptions on public models.
- In dbt Cloud, docs are auto-published after each production job run and accessible to stakeholders without running anything locally.

A documented dbt project acts as a living data dictionary — far more accurate than a wiki that drifts out of sync the moment the underlying SQL changes.
