## 00:03 - dbt Variables & `env_var()`: Managing Configuration Across Environments

One of dbt's most powerful (and underused) features is its layered variable system. Understanding `var()` and `env_var()` lets you write a single codebase that adapts cleanly to dev, staging, and production without manual edits.

### `var()`: Project-Level Variables

Define defaults in `dbt_project.yml` and override at runtime:

```yaml
# dbt_project.yml
vars:
  start_date: '2020-01-01'
  is_test_run: false
  my_schema: 'analytics'
```

Reference in any model or macro with `{{ var('start_date') }}`:

```sql
-- models/orders.sql
select *
from {{ source('raw', 'orders') }}
where created_at >= '{{ var("start_date") }}'
{% if var("is_test_run") %}
  limit 1000
{% endif %}
```

Override at the CLI for quick dev iterations:

```bash
dbt run --vars '{"is_test_run": true, "start_date": "2024-01-01"}'
```

### `env_var()`: Pulling in OS Environment Variables

Use `env_var()` for secrets and environment-specific values that shouldn't be hardcoded:

```yaml
# profiles.yml
my_warehouse:
  target: dev
  outputs:
    dev:
      type: snowflake
      account: "{{ env_var('SNOWFLAKE_ACCOUNT') }}"
      user: "{{ env_var('SNOWFLAKE_USER') }}"
      password: "{{ env_var('SNOWFLAKE_PASSWORD') }}"
      database: "{{ env_var('DBT_DATABASE', 'analytics_dev') }}"  # second arg = default
```

The optional second argument makes `env_var()` safe when the variable might not be set (e.g., local dev with sensible defaults).

### Practical Pattern: Environment-Aware Schema Routing

```yaml
# dbt_project.yml
vars:
  target_schema: "{{ env_var('DBT_TARGET_SCHEMA', target.schema) }}"
```

```sql
-- macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) %}
  {% if custom_schema_name %}
    {{ custom_schema_name | trim }}
  {% else %}
    {{ var('target_schema') | trim }}
  {% endif %}
{% endmacro %}
```

### Variable Precedence (highest to lowest)

1. `--vars` CLI flag (runtime override)
2. `vars:` block in `dbt_project.yml`
3. Package-level `vars:` (if consuming a package)
4. `var('key', 'default')` inline default

### Key Gotchas

- **Variables are not secrets.** `var()` values appear in compiled SQL and logs — use `env_var()` for passwords and tokens.
- **`env_var()` is resolved at parse time**, not run time. This means CI systems must have the env var exported before `dbt compile` or `dbt run`.
- Avoid complex Jinja logic inside `dbt_project.yml` vars — keep them simple strings or booleans and do the branching inside macros or models.

## 05:03 - dbt Groups & Access Modifiers: Controlling Model Visibility Across Projects

Introduced in dbt Core 1.5, **groups** and **access modifiers** let you declare which models are part of a team's "public API" versus internal implementation details. This is the foundation for **dbt Mesh** — connecting multiple dbt projects together safely.

### The Problem They Solve

In a large monorepo, any model can `ref()` any other model. This creates invisible dependencies — a marketing analyst accidentally builds on a staging model that the data engineering team refactors weekly. Groups and access let you enforce boundaries without splitting into separate repos prematurely.

### Defining a Group

Groups are declared in a YAML file (typically alongside your models):

```yaml
# models/finance/_finance.yml
groups:
  - name: finance
    owner:
      name: Finance Analytics Team
      email: analytics@finance.example.com
```

### Assigning Models to a Group with Access Levels

```yaml
# models/finance/_finance.yml
models:
  - name: stg_invoices
    group: finance
    access: private        # only models in the 'finance' group can ref this

  - name: int_revenue_daily
    group: finance
    access: protected      # models in this project can ref it, but not other dbt projects

  - name: fct_revenue
    group: finance
    access: public         # any project (including downstream consumers) can ref this
```

The three access levels:

| Level | Who can `ref()` it |
|---|---|
| `private` | Only models in the **same group** |
| `protected` | Any model in the **same dbt project** (default) |
| `public` | Any model in **any project** (required for cross-project `ref`) |

### Cross-Project References (dbt Mesh)

Once a model is marked `public`, a downstream project can reference it by adding it as a dependency in `dependencies.yml`:

```yaml
# dependencies.yml (in the consuming project)
projects:
  - name: finance_project
```

Then reference it with the project-scoped syntax:

```sql
-- models/marketing/fct_campaign_roi.sql
select
    c.campaign_id,
    r.revenue,
    c.spend,
    r.revenue / nullif(c.spend, 0) as roi
from {{ ref('marketing', 'fct_campaigns') }} c
left join {{ ref('finance_project', 'fct_revenue') }} r  -- cross-project ref
    on c.date_day = r.date_day
```

### Enforcement at Parse Time

If a model outside the `finance` group tries to `ref('stg_invoices')` (which is `private`), dbt raises a parse-time error:

```
Compilation Error
  Node model.marketing.fct_campaigns attempted to ref model.finance.stg_invoices,
  which is private to the finance group.
```

This gives you guardrails without runtime surprises.

### Best Practices

- **Start with `protected`** (the default) — only promote to `public` when a model is stable enough to be a contract.
- **Pair `public` models with model contracts** (`constraints:`) so downstream consumers can rely on column types and not-null guarantees.
- **One group per domain team** — finance, marketing, product. Avoid one global group that defeats the purpose.
- Use `private` aggressively for staging and intermediate models — they're implementation details, not APIs.

## 10:03 - dbt Snapshots: Tracking Historical Change with Type-2 SCDs

dbt snapshots capture point-in-time history for mutable source records. Every time you run `dbt snapshot`, dbt compares the current state of a source table against the previously snapshotted state and appends a new row for any record that changed — giving you a full audit trail without writing custom CDC logic.

### When to Use Snapshots

Use snapshots when source systems overwrite records in place (e.g., a CRM updates `status` on an order row) and you need to answer questions like "what was this order's status last Tuesday?"

### Defining a Snapshot

Snapshots live in the `snapshots/` directory and use a special `{% snapshot %}` block:

```sql
-- snapshots/orders_snapshot.sql
{% snapshot orders_snapshot %}

{{
  config(
    target_schema='snapshots',
    unique_key='order_id',
    strategy='timestamp',
    updated_at='updated_at',
    invalidate_hard_deletes=True
  )
}}

select * from {{ source('raw', 'orders') }}

{% endsnapshot %}
```

### Snapshot Strategies

| Strategy | How it works | Use when |
|---|---|---|
| `timestamp` | Compares `updated_at` column to detect changes | Source has a reliable `updated_at` timestamp |
| `check` | Compares a list of columns for any value change | No reliable timestamp; specify `check_cols` |

```sql
-- check strategy example
{{
  config(
    strategy='check',
    check_cols=['status', 'amount', 'customer_id']
  )
}}
```

Or use `check_cols='all'` to diff every column (expensive on wide tables).

### Snapshot Metadata Columns

dbt automatically adds four columns to every snapshot table:

| Column | Description |
|---|---|
| `dbt_scd_id` | Unique ID for each snapshot row (hash of key + hash of row) |
| `dbt_updated_at` | When this snapshot row was last written |
| `dbt_valid_from` | Timestamp when this version of the record became active |
| `dbt_valid_to` | Timestamp when this version was superseded (`NULL` = current) |

### Querying Snapshots

To get the **current** state of all records:

```sql
select * from {{ ref('orders_snapshot') }}
where dbt_valid_to is null
```

To reconstruct state **as-of a specific date**:

```sql
select * from {{ ref('orders_snapshot') }}
where '2025-12-31' between dbt_valid_from and coalesce(dbt_valid_to, '9999-12-31')
```

### Hard Deletes

By default, rows deleted from the source are left in the snapshot with `dbt_valid_to = NULL` — they appear as still-current. Setting `invalidate_hard_deletes=True` (as above) closes those rows by setting `dbt_valid_to` to the current snapshot time.

### Key Best Practices

- **Run snapshots before your models** — `dbt snapshot && dbt run` — so downstream models always see the freshest history.
- **Don't filter source data** inside the snapshot query (e.g., no `WHERE status != 'deleted'`). Filtering hides deletes and corrupts history.
- Keep snapshots in a dedicated schema (e.g., `snapshots`) separate from your marts to make permissions and retention policies easier to manage.
- Avoid wide `check_cols='all'` on large tables; it forces a full row hash comparison on every run.

## 15:03 - dbt Exposures: Documenting Downstream Consumers in Your DAG

dbt's DAG shows how raw sources flow through staging and mart models — but it stops at your last model. **Exposures** extend the lineage graph to include the dashboards, reports, ML models, and applications that consume your dbt outputs. They're YAML-only metadata that cost nothing to maintain yet dramatically improve data observability.

### Why Exposures Matter

Without exposures, you have no automated way to answer: "If I change `fct_orders`, which Looker dashboards break?" With exposures, `dbt docs generate` draws that final edge in the DAG, and `dbt ls --select +exposure:*` tells you exactly which models feed a given consumer.

### Defining an Exposure

Exposures live in any YAML file under `models/` (convention: `models/exposures.yml`):

```yaml
# models/exposures.yml
version: 2

exposures:
  - name: weekly_revenue_dashboard
    label: Weekly Revenue Dashboard        # human-friendly display name
    type: dashboard                         # dashboard | notebook | analysis | ml | application
    maturity: high                          # low | medium | high
    url: https://bi.example.com/dashboards/42
    description: >
      Executive dashboard showing weekly revenue trends, top customers,
      and region breakdowns. Refreshes every Monday at 06:00 UTC.
    owner:
      name: Revenue Analytics Team
      email: revenue-analytics@example.com
    depends_on:
      - ref('fct_orders')
      - ref('dim_customers')
      - ref('fct_revenue_daily')
```

### Exposure Types

| `type` | Typical use case |
|---|---|
| `dashboard` | BI tool dashboard (Looker, Tableau, Metabase) |
| `notebook` | Jupyter / Hex notebook for ad-hoc analysis |
| `analysis` | SQL analysis or one-off report |
| `ml` | Machine learning model consuming dbt outputs |
| `application` | Operational app reading from your warehouse |

### Using Exposures for Impact Analysis

Find all models that feed a specific exposure:

```bash
# All ancestors of the revenue dashboard
dbt ls --select +exposure:weekly_revenue_dashboard

# Run only the models the dashboard depends on
dbt run --select +exposure:weekly_revenue_dashboard
```

This is powerful in CI: you can run `dbt test --select +exposure:weekly_revenue_dashboard` to validate only the models that actually affect production-facing consumers before merging.

### Maturity Signals Freshness Expectations

The `maturity` field is metadata only (dbt doesn't enforce it), but it communicates SLA expectations to consumers:

```yaml
maturity: high    # schema is stable, changes go through review
maturity: medium  # actively developed; breaking changes with notice
maturity: low     # experimental; schema may change without warning
```

Pair `high`-maturity exposures with **model contracts** (`constraints:` + `access: public`) on their upstream models to actually enforce those guarantees.

### Exposures in the Docs Site

After `dbt docs generate && dbt docs serve`, exposures appear as nodes in the lineage graph with their owner, URL, and description. You can click from a mart model and immediately see which dashboards depend on it — a huge win for impact analysis during refactors.

### Best Practices

- **Add exposures at project setup** — before the first dashboard is built, not after. Retrofitting is tedious.
- **Use `url:`** whenever possible so developers can navigate directly to the consumer from the docs site.
- **One exposure per logical consumer** — don't create one exposure for "all Looker dashboards." Granularity makes `--select` useful.
- **Pair with freshness tests** on sources: if source data goes stale, exposures tell you which dashboards are immediately affected.
- Automate exposure generation for large BI platforms using the BI tool's API + a script that writes the YAML — maintaining hundreds of exposures by hand doesn't scale.

## 19:03 - dbt build: The All-In-One Command for Safe, Ordered Execution

`dbt build` is the command you should reach for in production. It runs **seeds → snapshots → models → tests** in a single DAG pass, enforcing your entire dependency order and halting downstream work the moment a test fails.

### What `dbt run` Can't Do

`dbt run` only executes models. To get full coverage you'd stitch together:

```bash
dbt seed && dbt snapshot && dbt run && dbt test
```

The problem: this runs all seeds, then all snapshots, then all models, then all tests — as four sequential phases. A test failure on `stg_orders` doesn't stop `fct_revenue` from building on top of it. You discover broken data after it's already materialized in marts.

### How `dbt build` Is Different

`dbt build` interleaves execution with the DAG. For every node it visits, it runs the node and immediately runs any associated tests before moving downstream:

```
Seed: raw_country_codes   ✓
  └─ Test: not_null(code) ✓
Model: stg_orders         ✓
  ├─ Test: not_null(order_id)     ✓
  └─ Test: accepted_values(status) ✗  ← STOPS HERE
     Model: fct_revenue            (skipped — upstream test failed)
```

No corrupted marts. No silent propagation of bad data.

### Node Selection Works Identically

All the selectors you know from `dbt run` carry over:

```bash
# Build only the finance subdirectory and its descendants
dbt build --select finance.*+

# Build a specific model and everything it depends on
dbt build --select +fct_orders

# Build only what changed vs. a production manifest (Slim CI)
dbt build --select state:modified+ --defer --state ./prod-artifacts/
```

### Fail-Fast vs. Keep-Going

By default, a test failure marks the failing node and skips all direct descendants, but sibling branches keep running. Use `--fail-fast` to abort the entire run on the first failure — useful in local development when you want immediate feedback:

```bash
dbt build --fail-fast
```

### Excluding Node Types

You can exclude specific resource types if you don't want them in a given run:

```bash
# Build models and tests, but skip seeds and snapshots
dbt build --exclude resource_type:seed resource_type:snapshot
```

This is handy when seeds are large static files that rarely change and you load them separately.

### When to Use What

| Command | Use when |
|---|---|
| `dbt run` | You want to iterate on models only during development |
| `dbt test` | You want to run tests without re-materializing anything |
| `dbt build` | **CI/CD pipelines and production runs** — always |
| `dbt build --select +<model>` | You changed one model and want to rebuild just its subgraph safely |

### The Golden Production Pattern

```bash
# In your CI job or orchestration DAG
dbt build \
  --select state:modified+ \
  --defer \
  --state ./artifacts/prod \
  --target prod
```

This builds only modified models and their descendants (Slim CI), borrows unmodified model results from production (defer), runs associated tests inline, and stops the moment anything fails. It's the most resource-efficient and safest way to ship dbt changes.
