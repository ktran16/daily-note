## 00:04 - [Data Engineering] Schema Evolution and Compatibility Modes: Changing Contracts Without Breaking Consumers

A streaming topic is a contract between a producer you control and consumers you often don't. Schema evolution is the discipline of changing that contract without a 3 a.m. deserialization storm. A Schema Registry (Confluent, Apicurio, AWS Glue) enforces it: producers register a schema, get back an ID, and prepend that ID to each message. Consumers fetch the writer schema by ID and reconcile it against their own reader schema.

**The compatibility modes are the whole game.** Set them per subject:

| Mode | Allowed change | Upgrade first |
|---|---|---|
| `BACKWARD` (default) | Delete a field; add an **optional** field | Consumers |
| `FORWARD` | Add a field; delete an **optional** field | Producers |
| `FULL` | Only add/remove optional fields | Either |
| `NONE` | Anything | Pray |

`BACKWARD` means a *new* reader can read *old* data — which is why it's the default: you upgrade consumers first, then producers, and history stays readable. Note the asymmetry that trips people up: adding a required field is backward-*incompatible*, because old records have nothing to supply for it.

**The fix is almost always a default.** In Avro, a field with a default is optional:

```json
{"name": "signup_channel", "type": ["null", "string"], "default": null}
```

Without `"default"`, that same field breaks every old record. In Protobuf, all fields are optional by construction — but **never reuse a field number**. Reserve retired ones:

```protobuf
message OrderEvent {
  reserved 4, 7;
  reserved "legacy_status";
  string order_id = 1;
  int64  amount_cents = 2;
}
```

**Enforce it in CI, not in prod.** Check the candidate schema against the registry before merge:

```bash
curl -X POST -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data @candidate.json \
  http://registry:8081/compatibility/subjects/orders-value/versions/latest
# {"is_compatible": false}  -> fail the build
```

Three rules that survive contact with reality: renaming is delete-plus-add (use Avro `aliases` if you must), widening types is safe while narrowing is not (`int` → `long` yes, the reverse no), and a breaking change means a **new topic or a versioned subject** — not a compatibility downgrade to `NONE`.

## 05:03 - [Data Analytics] Reading a Query Plan: Estimated vs Actual Rows Is the Only Number That Matters

Most "slow query" tickets are solved by one habit: run `EXPLAIN (ANALYZE, BUFFERS)` and hunt for the node where the planner's row estimate diverges from reality. The optimizer picks join algorithms and index strategies from estimates. Get the estimate wrong by 1000x and it will confidently choose a nested loop that runs 4 million times.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.region, count(*)
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'shipped'
  AND o.created_at >= date '2026-08-01'
GROUP BY c.region;
```

Read the output inside-out — the deepest indented node runs first — and compare the two halves of each line:

```
Nested Loop  (cost=0.42..18902 rows=41 width=18)
             (actual time=0.08..9412.55 rows=38417 loops=1)
  ->  Seq Scan on orders o  (rows=41) (actual rows=38417 loops=1)
        Filter: (status = 'shipped' AND created_at >= '2026-08-01')
        Rows Removed by Filter: 2104883
  ->  Index Scan using customers_pkey on customers c
        (actual time=0.002..0.002 rows=1 loops=38417)
```

**The tell is `rows=41` vs `actual rows=38417`.** The planner expected 41 shipped orders, so a nested loop (probe the customer index 41 times) looked cheap. It probed 38,417 times instead — `loops=38417` is the smoking gun. With a truthful estimate it would have chosen a hash join and finished in ~200 ms.

Why the bad estimate? Postgres multiplies the two filter selectivities as if `status` and `created_at` were independent. They aren't: recent orders are disproportionately `'shipped'`. The fix is to tell it about the correlation:

```sql
CREATE STATISTICS orders_status_date (dependencies)
  ON status, created_at FROM orders;
ANALYZE orders;
```

**Three habits worth keeping:**
- Always use `ANALYZE` — plain `EXPLAIN` shows guesses only, never actuals.
- `actual time` is cumulative and **per loop**; total cost of that node is `actual time × loops`.
- `Rows Removed by Filter: 2104883` on a seq scan is an index invitation — here, a partial index on `(created_at) WHERE status = 'shipped'`.

Chase the largest estimate/actual ratio first. Fix that one node and the rest of the plan usually reshapes itself.
