## 00:03 - [Data Engineering] Data Vault 2.0: Hubs, Links, and Satellites

Kimball optimizes for query ergonomics. Data Vault optimizes for **absorbing change without refactoring** — useful when you integrate many source systems that keep changing shape. It splits every entity into three node types:

- **Hub** — the business key and nothing else. One row per distinct key, ever.
- **Link** — a relationship between two or more hubs. Also insert-only.
- **Satellite** — the descriptive attributes hanging off a hub or link, versioned over time.

The payoff: adding a new source system means adding satellites, never altering existing tables. Everything is insert-only, so loads are parallelizable and idempotent.

```sql
-- hub_customer: the immutable business key
select
    md5(upper(trim(customer_code)))       as customer_hk,
    upper(trim(customer_code))            as customer_code,
    min(loaded_at)                        as load_ts,
    'salesforce'                          as record_source
from {{ ref('stg_salesforce__customers') }}
group by 1, 2

-- sat_customer_salesforce: attributes + change hash
select
    md5(upper(trim(customer_code)))                    as customer_hk,
    loaded_at                                          as load_ts,
    md5(concat_ws('||', name, tier, coalesce(region,''))) as hashdiff,
    name, tier, region,
    'salesforce'                                       as record_source
from {{ ref('stg_salesforce__customers') }}
```

The **hashdiff** is the trick that makes satellite loads cheap: hash the descriptive columns, and only insert a row when the incoming hashdiff differs from the current one for that key. No column-by-column comparison, no updates.

```sql
{{ config(materialized='incremental', unique_key=['customer_hk','load_ts']) }}
...
{% if is_incremental() %}
where not exists (
    select 1 from {{ this }} t
    where t.customer_hk = s.customer_hk
      and t.hashdiff   = s.hashdiff
      and t.load_ts    = (select max(load_ts) from {{ this }} x
                          where x.customer_hk = s.customer_hk)
)
{% endif %}
```

**The catch:** a Vault is not a query layer. Answering "revenue by tier last month" means joining a hub, two links, and three satellites with point-in-time logic. You still build Kimball-style marts on top — the Vault is the integration layer, the marts are the interface. Budget for both, or don't adopt it.

Use it when you have many overlapping sources and hard auditability requirements. For a single-source warehouse, it is pure overhead.

## 05:03 - [Data Analytics] DuckDB: Query Parquet and DataFrames Without a Warehouse

Most ad-hoc analysis does not need a warehouse. DuckDB is an in-process OLAP engine — `pip install duckdb`, no server, no cluster — that reads Parquet and CSV files directly and runs vectorized columnar SQL over them.

**Query files in place.** No load step, no `CREATE TABLE`:

```python
import duckdb

duckdb.sql("""
    SELECT country, date_trunc('month', order_ts) AS mth,
           count(*) AS orders, sum(amount) AS gmv
    FROM read_parquet('s3://bucket/orders/year=*/month=*/*.parquet',
                      hive_partitioning = true)
    WHERE order_ts >= '2026-01-01'
    GROUP BY ALL
    ORDER BY mth
""").df()
```

Two things make this fast. **Projection pushdown**: only the three referenced columns are decoded, so a 40-column table costs ~7% of its bytes. **Predicate pushdown**: Parquet row groups carry min/max stats per column, so groups whose `order_ts` range falls entirely before 2026 are skipped without decompression. On a 50M-row, 12 GB dataset, a filtered three-column aggregate typically touches a few hundred MB. With `hive_partitioning`, whole directories are pruned from the file list before a single byte is read.

**Replacement scans** let SQL see your Python variables by name — no registration, no copy:

```python
import pandas as pd
sessions = pd.read_csv("sessions.csv")

duckdb.sql("""
    SELECT user_id, count(*) AS n
    FROM sessions            -- the pandas DataFrame, referenced directly
    GROUP BY user_id HAVING n > 5
""").df()
```

This works for pandas, Polars, and Arrow tables. Round-tripping through Arrow is zero-copy, so it is genuinely cheaper than the equivalent `groupby` on a wide frame — and you get real SQL semantics (window functions, `QUALIFY`, `GROUP BY ALL`, full joins) instead of chained method calls.

**Three habits worth adopting:**

- `SUMMARIZE tbl` — one statement returns per-column min, max, approx distinct, null %, and quartiles. Best first look at unfamiliar data.
- Convert CSV once: `COPY (FROM read_csv('raw/*.csv')) TO 'data.parquet' (FORMAT parquet, COMPRESSION zstd)`. Repeat queries then get pushdown instead of re-parsing text.
- `SET memory_limit='8GB'` — DuckDB spills joins and sorts to disk, so a 30 GB aggregation completes on a laptop. It will be slow, not OOM.

**Where it stops:** single-writer, no concurrency, no access control. It is an analyst's tool and an embedded engine — not a shared serving layer.

## 10:03 - [ML & AI] Hybrid Retrieval and Reciprocal Rank Fusion: Merging BM25 and Vector Search

Pure vector search is the default RAG retriever, and it quietly fails on the queries users actually type. Embeddings capture semantics but blur exact tokens — error codes, SKUs, function names, version numbers. Ask for `ERR_2041` and a dense retriever cheerfully returns three passages about "error handling best practices." BM25 (keyword/lexical) nails those and fails at paraphrase. The fix is to run both and fuse the results.

**The naive fusion is wrong.** Normalizing and adding raw scores (`0.7*cosine + 0.3*bm25`) requires the two score distributions to be comparable. They are not: cosine sits in a narrow band near 0.8, BM25 is unbounded and scales with document length and corpus statistics. The weights end up tuned to one corpus and break on the next.

**Reciprocal Rank Fusion** throws away the scores and keeps only the ranks:

```
RRF(d) = Σ_lists  1 / (k + rank_list(d))     # k ≈ 60, rank is 1-indexed
```

Worked example with three candidates, k=60:

| doc | BM25 rank | dense rank | RRF score |
|-----|-----------|------------|-----------|
| A   | 1         | 20         | 1/61 + 1/80 = **0.0289** |
| B   | 3         | 2          | 1/63 + 1/62 = **0.0320** |
| C   | 2         | 15         | 1/62 + 1/75 = **0.0295** |

Final order is B, C, A. Document B wins without being first in *either* list — that is the behavior you want. Agreement across independent retrievers is stronger evidence than a single confident vote.

The `k` constant controls how sharply top ranks dominate. At k=0, rank 1 scores 1.0 and rank 2 scores 0.5 — a cliff. At k=60, the rank-1-to-rank-2 gap is 1/61 − 1/62 ≈ 0.00026, so a single retriever's top hit cannot steamroll the other list.

```python
from collections import defaultdict

def rrf(ranked_lists, k=60):
    scores = defaultdict(float)
    for lst in ranked_lists:                    # each: [doc_id, ...] best-first
        for rank, doc_id in enumerate(lst, start=1):
            scores[doc_id] += 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

rrf([["A", "C", "B"], ["B", "C", "A"]])
```

**Practical shape:** retrieve top-50 from each retriever, fuse, then rerank the top-20 with a cross-encoder before sending ~5 chunks to the model. RRF is cheap and hyperparameter-free; the cross-encoder is where precision actually comes from.
