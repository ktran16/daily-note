## 00:02 - [Data Engineering] Fact Table Grain: The Decision That Makes or Breaks a Dimensional Model

Kimball's first rule of dimensional modeling is to **declare the grain before anything else**. The grain is a one-sentence statement of what a single row means — "one row per order line item" or "one row per policy per day." Get it wrong and every downstream metric quietly double-counts.

The classic failure: a fact table joined to a many-to-many dimension without an intervening bridge. Suddenly `sum(revenue)` inflates because each order row fans out across three sales reps. The fix is never a `DISTINCT` in the BI layer — it's fixing the grain.

**The three fact table types**

| Type | Grain | Additivity |
|---|---|---|
| Transaction | One row per event | Fully additive |
| Periodic snapshot | One row per entity per period | Semi-additive (never sum across time) |
| Accumulating snapshot | One row per process instance, updated in place | Milestone dates + lags |

Semi-additivity is where dashboards lie. An account balance snapshot can be summed across accounts but not across days — summing 30 daily balances gives a meaningless number. Encode that in the semantic layer, don't trust analysts to remember it.

**Declaring grain explicitly in dbt**

```sql
-- models/marts/fct_order_lines.sql
-- GRAIN: one row per order_line_id (an order's individual line item)
select
    ol.order_line_id,
    ol.order_id,
    dc.customer_key,
    dp.product_key,
    cast(o.ordered_at as date) as order_date,
    ol.quantity,
    ol.extended_amount          -- additive
from {{ ref('stg_order_lines') }} ol
join {{ ref('stg_orders') }}     o  using (order_id)
join {{ ref('dim_customers') }}  dc on dc.customer_id = ol.customer_id
                                   and o.ordered_at >= dc.valid_from
                                   and o.ordered_at <  dc.valid_to   -- SCD2 point-in-time
join {{ ref('dim_products') }}   dp on dp.product_id  = ol.product_id
```

Then enforce it, so the grain is a test rather than a comment:

```yaml
models:
  - name: fct_order_lines
    columns:
      - name: order_line_id
        tests: [unique, not_null]
    tests:
      - dbt_utils.expression_is_true:
          expression: "extended_amount >= 0"
```

Two habits worth keeping: build facts at the **lowest grain available** (you can always aggregate up, never down), and join dimensions on surrogate keys with validity ranges so historical facts keep the dimension attributes that were true *at event time* — not today's values.

## 05:03 - [Data Analytics] Cohort Retention Curves: Building the Triangle and Reading It Honestly

A retention curve answers "of the users who first showed up in month N, what share came back in month N+k?" Two things make or break it: anchoring every user to their **own** first-activity date, and refusing to plot cells that haven't had time to happen yet.

Start by pinning the cohort, then measure activity relative to it:

```sql
WITH first_seen AS (
  SELECT user_id,
         DATE_TRUNC('month', MIN(event_at)) AS cohort_month
  FROM events
  GROUP BY user_id
),
activity AS (
  SELECT f.cohort_month,
         f.user_id,
         DATE_TRUNC('month', e.event_at) AS active_month
  FROM events e
  JOIN first_seen f USING (user_id)
  GROUP BY 1, 2, 3
)
SELECT cohort_month,
       (EXTRACT(YEAR FROM active_month) - EXTRACT(YEAR FROM cohort_month)) * 12
         + (EXTRACT(MONTH FROM active_month) - EXTRACT(MONTH FROM cohort_month)) AS period_number,
       COUNT(DISTINCT user_id) AS actives,
       COUNT(DISTINCT user_id)::float
         / MAX(COUNT(DISTINCT user_id)) OVER (PARTITION BY cohort_month) AS retention
FROM activity
GROUP BY 1, 2
ORDER BY 1, 2;
```

`MAX(...) OVER (PARTITION BY cohort_month)` grabs period 0 as the denominator without a second scan — period 0 is always the largest cell, since every later period is a subset of the cohort.

**The censoring trap.** Run this on 2026-08-27 and your July cohort has a period-1 value computed from a *partial* August. If July's true month-1 retention is 40%, a 27-days-in read might show 36% — and someone will report "retention is falling." Filter it out explicitly:

```sql
WHERE active_month + INTERVAL '1 month' <= DATE_TRUNC('month', CURRENT_DATE)
```

Three more rules worth enforcing: retention must be **monotonically comparable across cohorts at the same period_number** (compare down columns, never across rows); decide up front whether you mean *classic* retention (active in exactly period k) or *rolling* (active in period k or later) — they diverge by 10–15 points by month 6; and always show cohort size next to the percentage. A 92% month-3 retention on a 12-user cohort is noise, not a win.

## 10:04 - [ML & AI] Detecting Drift with PSI: The Number That Tells You to Retrain

A deployed model degrades silently. Accuracy metrics need labels, and labels arrive weeks late — so the first line of monitoring is **input drift**: has the distribution of a feature moved away from what the model trained on?

The workhorse metric is **Population Stability Index (PSI)**. Bin a feature (usually into deciles of the *training* distribution), then compare bin proportions:

```
PSI = Σ (actualᵢ − expectedᵢ) · ln(actualᵢ / expectedᵢ)
```

It's the symmetrized KL divergence (Jeffreys divergence) over discrete bins — which is why it's always ≥ 0 and penalizes movement in either direction.

**Worked example.** Train quartiles are 25% each by construction. This week's traffic lands 10/20/30/40:

| Bin | Expected | Actual | Contribution |
|---|---|---|---|
| 1 | 0.25 | 0.10 | (−0.15)·ln(0.40) = 0.137 |
| 2 | 0.25 | 0.20 | (−0.05)·ln(0.80) = 0.011 |
| 3 | 0.25 | 0.30 | (0.05)·ln(1.20) = 0.009 |
| 4 | 0.25 | 0.40 | (0.15)·ln(1.60) = 0.071 |

**PSI = 0.228.** Note how bin 1 alone contributes 60% of the total — PSI is dominated by *relative* shrinkage in small bins, so always log per-bin contributions, not just the scalar.

The industry rule of thumb (from credit scoring, where PSI originated):

- **< 0.10** — no meaningful shift
- **0.10 – 0.25** — moderate; investigate
- **> 0.25** — significant; retrain or roll back

```python
import numpy as np

def psi(expected, actual, bins=10, eps=1e-6):
    # Bin edges from the TRAINING distribution, not the combined data
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected)
    a = np.histogram(actual, edges)[0] / len(actual)
    e, a = np.clip(e, eps, None), np.clip(a, eps, None)  # avoid log(0)
    return float(np.sum((a - e) * np.log(a / e)))
```

**Three traps.** (1) The `eps` clip is not cosmetic — an empty production bin gives `ln(0) = −inf` and a meaningless alarm; consider merging bins below ~1% instead. (2) PSI on a *feature* is not PSI on the *prediction*. Score drift is the better early alarm because it aggregates all features through the model's own weighting. (3) Input drift ≠ concept drift. The P(y|x) relationship can rot while every input distribution sits at PSI 0.02 — you still need a delayed-label backtest to catch that.

Alert on prediction PSI, page on it weekly, and treat feature-level PSI as the diagnostic you open *after* the alarm fires.
