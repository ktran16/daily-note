## 00:03 - dbt Sources: Declaring, Testing, and Monitoring Freshness

Raw data lands in your warehouse from external systems — application databases, event streams, third-party APIs. dbt **sources** give you a first-class way to declare those raw tables, test them, and monitor how stale they're getting.

### Declaring a Source

Define sources in a `sources.yml` (or inside any `schema.yml`) file in your models directory:

```yaml
# models/staging/sources.yml
version: 2

sources:
  - name: stripe
    database: raw_prod
    schema: stripe
    tables:
      - name: payments
        description: "Raw payments from Stripe webhooks"
        columns:
          - name: id
            tests:
              - unique
              - not_null
          - name: amount
            tests:
              - not_null
```

### Referencing a Source in a Model

Use `{{ source('source_name', 'table_name') }}` instead of hard-coding the schema and table:

```sql
-- models/staging/stg_stripe__payments.sql
select
    id          as payment_id,
    amount,
    currency,
    status,
    created_at
from {{ source('stripe', 'payments') }}
```

This keeps your raw table references DRY — change the schema or database once in `sources.yml` and every model updates automatically. It also wires the source into the lineage DAG so `dbt docs generate` shows where your data originates.

### Source Freshness

dbt can alert you when source data stops arriving on time. Add a `loaded_at_field` (a timestamp column) and `freshness` thresholds:

```yaml
      - name: payments
        loaded_at_field: _fivetran_synced
        freshness:
          warn_after: {count: 6, period: hour}
          error_after: {count: 24, period: hour}
```

Run `dbt source freshness` (or `dbt build --select source:stripe`) to check all sources. dbt queries `max(loaded_at_field)` and compares it against wall-clock time — no custom SQL needed.

### Practical Tips

- **Namespace by source system**: `stripe`, `salesforce`, `fivetran_postgres` keeps schemas easy to trace.
- **Stage every source**: build one thin `stg_<source>__<table>.sql` model per raw table. Never reference `source()` from a mart model directly.
- **Test at the boundary**: put `not_null`, `unique`, and `accepted_values` tests on sources so bad raw data fails fast, before it propagates downstream.
- **Use `generate_schema_name`**: if raw tables live in a non-standard schema per environment, override the macro rather than duplicating source definitions.

## 05:04 - dbt Tests: Generic and Singular Data Quality Enforcement

dbt's testing framework lets you encode data quality expectations directly in the project, so every `dbt test` run validates that your models and sources hold up to contract. There are two test flavors: **generic tests** (reusable, config-driven) and **singular tests** (custom SQL queries that should return zero rows on success).

### Generic Tests

Generic tests apply to columns or models via `schema.yml` and run the same logic across many nodes. dbt ships with four built-in generics:

```yaml
# models/schema.yml
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - unique
          - not_null
      - name: status
        tests:
          - accepted_values:
              values: ['placed', 'shipped', 'delivered', 'cancelled']
      - name: customer_id
        tests:
          - relationships:
              to: ref('dim_customers')
              field: customer_id
```

- **`unique`** — asserts no duplicate values in the column.
- **`not_null`** — asserts no NULL values exist.
- **`accepted_values`** — asserts every value belongs to a defined list.
- **`relationships`** — asserts referential integrity against another model (a foreign key check).

Run them with `dbt test --select fct_orders` or as part of `dbt build`.

### Singular Tests

Singular tests are plain SQL files in the `tests/` directory. dbt runs each one and **fails if any rows are returned** — write your query to return rows that represent violations:

```sql
-- tests/assert_revenue_never_negative.sql
select
    order_id,
    revenue
from {{ ref('fct_orders') }}
where revenue < 0
```

If this returns zero rows, the test passes. Any row returned is a failure. Singular tests shine for multi-column or cross-model logic that generic tests can't express:

```sql
-- tests/assert_shipping_after_order.sql
select
    order_id,
    ordered_at,
    shipped_at
from {{ ref('fct_orders') }}
where shipped_at < ordered_at  -- physically impossible: shipped before ordered
```

### Configuring Test Severity

Not all failures are equal. Use `warn` severity to alert without blocking pipelines:

```yaml
- name: email
  tests:
    - not_null:
        config:
          severity: warn         # logs a warning; doesn't fail the run
          warn_if: ">= 10"       # only warn if 10+ rows fail
          error_if: ">= 100"     # fail the run only if 100+ rows fail
```

This is useful during initial data onboarding where some NULLs are expected while the upstream is being remediated.

### Custom Generic Tests with dbt-utils

The `dbt-utils` package ships a library of additional generic tests:

```yaml
- name: created_at
  tests:
    - dbt_utils.not_null_proportion:
        at_least: 0.95     # at least 95% of rows must be non-null
- name: revenue
  tests:
    - dbt_utils.expression_is_true:
        expression: ">= 0"
```

Install dbt-utils by adding it to `packages.yml` and running `dbt deps`.

### Storing Failures for Debugging

Pass `--store-failures` to persist failing rows to a table for inspection:

```bash
dbt test --store-failures --select fct_orders
```

Each test gets its own table in a `dbt_test__audit` schema (e.g., `dbt_test__audit.fct_orders_unique_order_id`), so you can query the exact offending rows without re-running the test.

### Practical Tips

- **Test sources, not just models** — `unique` and `not_null` on source columns catch bad raw data before it propagates downstream.
- **Tag slow tests** with `config: {tags: ['slow']}` and exclude from CI with `--exclude tag:slow`, reserving them for nightly runs.
- **Name singular tests descriptively** — `assert_shipping_after_order.sql` is self-documenting; `test1.sql` is not.
- **Run tests in `dbt build`** — unlike `dbt run` + `dbt test` separately, `dbt build` runs tests for each model immediately after it builds, failing fast before downstream models waste compute on bad data.
