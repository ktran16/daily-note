## 00:03 - dbt Unit Tests: Testing Model Logic with Mock Data

Introduced in **dbt 1.8**, unit tests let you verify your SQL transformation logic using small, inline datasets — no warehouse data required. This closes a long-standing gap: previously, you could only test *data quality* (generic/singular tests), not whether your SQL logic itself is correct.

### Why Unit Tests Matter

Before unit tests, catching a bug in a `CASE` expression or a join condition meant running the model against real data and inspecting the output. Unit tests let you pin expected behavior directly in your YAML, making regressions immediately visible.

### Anatomy of a Unit Test

```yaml
# models/staging/schema.yml
unit_tests:
  - name: test_order_status_label
    model: stg_orders
    given:
      - input: ref('raw_orders')
        rows:
          - { order_id: 1, status: 'placed' }
          - { order_id: 2, status: 'shipped' }
          - { order_id: 3, status: 'returned' }
    expect:
      rows:
        - { order_id: 1, status_label: 'Pending' }
        - { order_id: 2, status_label: 'In Transit' }
        - { order_id: 3, status_label: 'Returned' }
```

The `given` block provides mock inputs (replacing `ref()` or `source()` calls), and `expect` defines what the model should output. dbt compiles the model against your mocks and diffs the result.

### Running Unit Tests

```bash
# Run all unit tests
dbt test --select "test_type:unit"

# Run unit tests for a specific model
dbt test --select stg_orders,test_type:unit
```

### Key Behaviours to Know

- **Overrides are scoped**: The mock data only replaces the declared `input` — other upstream refs still resolve normally unless also mocked.
- **Column subset**: You only need to declare columns relevant to the test; dbt infers the rest from the model definition.
- **Works with macros**: If your model calls a macro (e.g., `dbt_utils.safe_divide`), the macro is still compiled — unit tests exercise the final SQL, not a stub.
- **Not a replacement for data tests**: Unit tests validate logic; generic/singular tests validate real data quality. Use both.

### When to Write One

Write a unit test whenever your model contains branching logic (`CASE WHEN`, `IFF`, `COALESCE` with fallback chains), date arithmetic, or a complex join condition where a subtle error could silently produce wrong numbers. That's where unit tests pay for themselves fastest.
