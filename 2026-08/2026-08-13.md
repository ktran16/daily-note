## 00:03 - dbt Unit Tests: Testing Model Logic with Mock Data

Introduced in **dbt 1.8**, unit tests let you verify your SQL transformation logic using small, inline datasets — no warehouse data required. This closes a long-standing gap: previously, you could only test *data quality* (generic/singular tests), not whether your SQL logic itself is correct.

### Why Unit Tests Matter

Before unit tests, catching a bug in a `CASE` expression or a join condition meant running the model against real data and inspecting the output. Unit tests let you pin expected behavior directly in your YAML, making regressions immediately visible.

### Anatomy of a Unit Test

```yaml
# models/staging/schema.yml
unit_tests:
  - name: test_order_status_label
    model: stg_orders
    given:
      - input: ref('raw_orders')
        rows:
          - { order_id: 1, status: 'placed' }
          - { order_id: 2, status: 'shipped' }
          - { order_id: 3, status: 'returned' }
    expect:
      rows:
        - { order_id: 1, status_label: 'Pending' }
        - { order_id: 2, status_label: 'In Transit' }
        - { order_id: 3, status_label: 'Returned' }
```

The `given` block provides mock inputs (replacing `ref()` or `source()` calls), and `expect` defines what the model should output. dbt compiles the model against your mocks and diffs the result.

### Running Unit Tests

```bash
# Run all unit tests
dbt test --select "test_type:unit"

# Run unit tests for a specific model
dbt test --select stg_orders,test_type:unit
```

### Key Behaviours to Know

- **Overrides are scoped**: The mock data only replaces the declared `input` — other upstream refs still resolve normally unless also mocked.
- **Column subset**: You only need to declare columns relevant to the test; dbt infers the rest from the model definition.
- **Works with macros**: If your model calls a macro (e.g., `dbt_utils.safe_divide`), the macro is still compiled — unit tests exercise the final SQL, not a stub.
- **Not a replacement for data tests**: Unit tests validate logic; generic/singular tests validate real data quality. Use both.

### When to Write One

Write a unit test whenever your model contains branching logic (`CASE WHEN`, `IFF`, `COALESCE` with fallback chains), date arithmetic, or a complex join condition where a subtle error could silently produce wrong numbers. That's where unit tests pay for themselves fastest.

## 05:04 - dbt `store_failures` and `store_failures_as`: Persisting Failed Test Rows for Debugging

When a dbt test fails, the default output is just a count: "Got 47, expected 0." You know something broke, but you don't know *which rows* broke or why. `store_failures` solves this by materializing the failing rows into a table in your warehouse, giving you a SQL-queryable artifact to investigate.

### Enabling `store_failures`

Set it globally in `dbt_project.yml`, per test in `schema.yml`, or override per-run with a flag:

```yaml
# dbt_project.yml — enable for all tests
tests:
  +store_failures: true
  +schema: dbt_test_failures   # optional: dedicated schema
```

```yaml
# schema.yml — enable for one test
models:
  - name: fct_orders
    columns:
      - name: customer_id
        tests:
          - not_null:
              store_failures: true
          - relationships:
              to: ref('dim_customers')
              field: customer_id
              store_failures: true
```

```bash
# CLI flag — store all failures for this run only
dbt test --store-failures
```

### Querying the Failure Table

dbt names failure tables after the test, in the configured schema. After running, you can inspect:

```sql
-- Snowflake / BigQuery / Redshift example
SELECT *
FROM analytics_dbt_test_failures.not_null_fct_orders_customer_id
LIMIT 100;
```

The table contains the actual failing rows — whatever columns the underlying test SQL selects — making it straightforward to trace back to the source problem.

### `store_failures_as` (dbt 1.7+)

By default, failures are stored as tables. With `store_failures_as` you can choose `view` or `ephemeral` instead:

```yaml
tests:
  +store_failures: true
  +store_failures_as: view   # cheaper; reflects current data on each query
```

Use `view` when you want failures to always reflect the latest data without accumulating stale rows from previous runs. Use `table` (the default) when you need to snapshot failures at a point in time for comparison or audit.

### Practical Tips

- **Dedicated schema**: Always set `+schema: dbt_test_failures` (or similar) so failure tables don't clutter your production schema.
- **CI vs. local**: Enable `store_failures` in your CI environment where failures are hardest to debug interactively. Locally, skipping it keeps runs faster.
- **Combine with `warn_if` / `error_if`**: You can demote a test to a warning but still store failures for later review, so a noisy test doesn't block your pipeline while you still capture evidence.

```yaml
- name: order_amount
  tests:
    - dbt_utils.expression_is_true:
        expression: ">= 0"
        store_failures: true
        warn_if: ">10"
        error_if: ">100"
```

`store_failures` turns dbt's test output from a scoreboard into a debugging tool — especially valuable for `relationships` and custom singular tests where the failing rows themselves reveal the fix.

## 10:03 - dbt Artifacts: manifest.json, run_results.json, and catalog.json Explained

Every dbt command writes structured JSON artifacts to the `target/` directory. These files are the backbone of state-based CI, observability tooling, and cross-project lineage — worth understanding even if you never open them directly.

### The Three Core Artifacts

**`manifest.json`** — produced by `dbt compile`, `dbt run`, `dbt test`, and most other commands. Contains the full compiled DAG: every node (model, test, snapshot, seed, source, exposure, metric), its SQL, resolved config, and dependency graph.

**`run_results.json`** — produced after any execution command. Records the outcome (`success`, `error`, `skip`, `warn`), wall-clock timing, rows affected, and the raw adapter response for each node that ran.

**`catalog.json`** — produced by `dbt docs generate`. Introspects the warehouse and stores column-level metadata: data types, row counts, and descriptions. Powers the docs site's column explorer.

### Slim CI with `--state`

The most practical use of artifacts is **slim CI** — running only models that changed relative to the last production run:

```bash
# Download the production manifest into a known path first
# Then in CI:
dbt run  --select "state:modified+" --state prod-artifacts/
dbt test --select "state:modified+" --state prod-artifacts/
```

`state:modified+` matches any model whose compiled SQL or config changed, *plus* all its downstream dependents. On large projects this can cut CI wall time from 60 minutes to under 5.

### Reading `run_results.json` Programmatically

```python
import json, pathlib

results = json.loads(pathlib.Path("target/run_results.json").read_text())
for r in results["results"]:
    if r["status"] not in ("success", "pass"):
        print(f"FAILED: {r['unique_id']}")
        print(f"  reason: {r.get('message', 'no message')}")
```

This pattern is useful in GitHub Actions to post a structured failure summary as a PR comment instead of making reviewers parse raw logs.

### Key Practices

- **Always upload artifacts as CI job artifacts.** Even if you don't use `--state` today, persisting the manifest enables slim CI and state comparison later with zero rework.
- **`dbt compile` is enough to produce `manifest.json`.** You don't need to execute any SQL — useful for validating project structure in a pre-merge check without touching the warehouse.
- **Check `metadata.dbt_schema_version`** before parsing artifacts in custom tooling; the schema evolves across dbt versions and a version mismatch will silently produce wrong results.
- **dbt Cloud stores artifacts automatically** per job run and exposes them via the Discovery API, enabling cross-project lineage and dashboard-level freshness checks without any manual upload step.
