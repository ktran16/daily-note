## 00:02 - [Data Engineering] Airflow Deferrable Operators: Stop Burning Worker Slots on Waiting

A sensor that polls an S3 prefix for four hours occupies a worker slot for four hours while doing essentially nothing. Run 50 of them and your pool is exhausted by tasks that are 99.9% `sleep()`. Deferrable operators fix this by moving the waiting off the worker entirely.

**How it works.** A deferrable task runs its setup logic on a worker, then raises `TaskDeferred` with a *trigger* — a small async object. The worker slot is released and the task goes to `deferred` state. The trigger runs in the **triggerer** process, a single asyncio event loop that can host thousands of concurrent waits cheaply. When the trigger fires, the scheduler re-queues the task on a worker, which resumes at the named callback method.

```python
from airflow.triggers.temporal import TimeDeltaTrigger
from airflow.sensors.base import BaseSensorOperator
from datetime import timedelta

class WaitForPartition(BaseSensorOperator):
    def execute(self, context):
        if self._partition_exists(context["ds"]):
            return                       # fast path: never defer
        self.defer(
            trigger=TimeDeltaTrigger(timedelta(minutes=5)),
            method_name="execute_complete",
        )

    def execute_complete(self, context, event=None):
        # Worker picks the task back up here — re-check, re-defer if needed.
        if not self._partition_exists(context["ds"]):
            self.defer(trigger=TimeDeltaTrigger(timedelta(minutes=5)),
                       method_name="execute_complete")
```

Most built-in operators expose this as a flag — no custom code needed:

```python
S3KeySensor(task_id="wait_raw", bucket_key="s3://lake/raw/{{ ds }}/_SUCCESS",
            deferrable=True, poke_interval=300, timeout=60 * 60 * 6)
```

Or globally in `airflow.cfg`: `[operators] default_deferrable = True`.

**Three gotchas.**

1. **`execute_complete` can run on a different worker.** Nothing from `execute()` survives except what you pass through `trigger_kwargs` or XCom. Instance attributes are gone.
2. **Triggers must be serializable and truly async.** A trigger that calls a blocking `boto3` client stalls the whole triggerer event loop — every other deferred task in the process stops. Use async clients or `run_in_executor`.
3. **You need a triggerer running.** No `airflow triggerer` process means deferred tasks hang forever. Run at least two for HA.

**When not to bother:** waits shorter than the ~1–2s defer/resume overhead. Below roughly 30 seconds, plain polling is cheaper.

## 05:04 - [Data Analytics] Peeking at A/B Tests: How Daily Dashboard Checks Inflate False Positives

You launch an experiment, plan for 20,000 users per arm, and check the dashboard every morning. On day 6 the p-value dips below 0.05, so you ship. You just ran a test whose real false-positive rate is nowhere near 5%.

**The mechanism.** A fixed-horizon significance test guarantees α = 5% for *one* look at a *predetermined* sample size. Each additional look is another chance for random noise to cross the threshold. The test statistic wanders; you're stopping the moment it wanders far enough.

Simulating two identical arms (true conversion 10% for both, so every "win" is a false positive), stopping early whenever |z| > 1.96:

| Looks | False positive rate |
|---|---|
| 1 (fixed horizon) | 4.8% |
| 5 | 13.9% |
| 10 | 18.9% |
| 20 | 24.6% |

Checking daily for three weeks means **1 in 4 A/A tests declares a winner.** That's the source of experiments that "win" but never show up in the quarterly numbers.

```python
import numpy as np
rng = np.random.default_rng(7)
N, P, LOOKS = 20_000, 0.10, 10
cps = [N * (i + 1) // LOOKS for i in range(LOOKS)]
fp = 0
for _ in range(12_000):
    ca = np.cumsum(rng.random(N) < P)
    cb = np.cumsum(rng.random(N) < P)      # same true rate — no real effect
    for c in cps:
        xa, xb = ca[c - 1], cb[c - 1]
        pp = (xa + xb) / (2 * c)
        z = (xb - xa) / c / np.sqrt(pp * (1 - pp) * 2 / c)
        if abs(z) > 1.96:
            fp += 1
            break
print(fp / 12_000)   # ~0.19
```

**What to do instead.** Pick one of these:

- **Fixed horizon, one look.** Compute sample size up front and don't decide until you hit it. Simplest, and enough for most teams.
- **Alpha spending** (O'Brien–Fleming, Pocock). Pre-register K interim looks and spend α across them — early boundaries are strict (|z| > 4 at look 1), the final one is near 1.96.
- **Always-valid inference** (mSPRT, confidence sequences). Sequential-by-design, so you can stop any time; the price is roughly 20–40% more samples for the same power.

**Guardrail:** monitoring for *harm* (error rates, latency, revenue crashes) is different — peek freely there. The multiple-comparison tax only applies to the decision you're trying to make.
