## 00:03 - dbt Incremental Model Strategies: Choosing the Right `incremental_strategy`

Incremental models are dbt's answer to processing only new or changed data instead of rebuilding entire tables on every run. The `incremental_strategy` config is the key lever — and choosing the wrong one can lead to duplicate data, slow jobs, or excessive warehouse costs.

### The Four Core Strategies

**1. `append` (default on some adapters)**

Inserts new rows only. Never deduplicates, never updates. Best for immutable event streams where you're certain rows won't change.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='append',
    unique_key='event_id'
) }}

select * from {{ source('raw', 'events') }}
{% if is_incremental() %}
where event_timestamp > (select max(event_timestamp) from {{ this }})
{% endif %}
```

Risk: if your pipeline replays events, you'll get duplicates.

---

**2. `merge` (recommended default for most cases)**

Performs an upsert: updates existing rows that match `unique_key`, inserts new rows. Requires adapter support (Snowflake, BigQuery, Databricks, Redshift ≥RA3).

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='order_id',
    merge_update_columns=['status', 'updated_at']   -- only update these columns
) }}

select
    order_id,
    status,
    updated_at
from {{ source('raw', 'orders') }}
{% if is_incremental() %}
where updated_at > (select max(updated_at) from {{ this }})
{% endif %}
```

`merge_update_columns` is a powerful optimization — it avoids overwriting columns like `created_at` that should stay immutable.

---

**3. `delete+insert`**

Deletes matching rows by `unique_key`, then inserts. Useful when `merge` isn't supported or when you need to re-process partitions cleanly. Common on Redshift and older Postgres setups.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='delete+insert',
    unique_key='date_day'   -- typically a partition column
) }}
```

Works well when `unique_key` is a date partition — you delete the whole day, then re-insert.

---

**4. `insert_overwrite` (partition-based)**

Replaces entire partitions instead of row-level merging. Fastest strategy for large datasets on BigQuery and Spark — no row-level comparison needed.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={
        'field': 'event_date',
        'data_type': 'date',
        'granularity': 'day'
    }
) }}

select
    date(event_timestamp) as event_date,
    user_id,
    event_type
from {{ source('raw', 'events') }}
{% if is_incremental() %}
where date(event_timestamp) >= date_sub(current_date(), interval 3 day)
{% endif %}
```

The lookback window (3 days here) is critical — it handles late-arriving data without requiring a full scan.

---

### Strategy Selection Guide

| Strategy | Duplicates Safe | Updates Rows | Partition-Level | Best For |
|---|---|---|---|---|
| `append` | No | No | No | Immutable event streams |
| `merge` | Yes | Yes | No | Orders, users, dim tables |
| `delete+insert` | Yes | Yes (via delete) | Optional | Redshift, Postgres |
| `insert_overwrite` | Yes | Yes (partition) | Yes | Large fact tables on BQ/Spark |

### Key Best Practices

- Always test your incremental filter logic by running `dbt run --full-refresh` and comparing row counts.
- Add `on_schema_change='sync_all_columns'` to handle column additions gracefully without a full refresh.
- For `merge`, keep `unique_key` indexed or clustered — unindexed merges on large tables are expensive.
- Use `{{ this }}` (not hardcoded table names) so the model works across environments automatically.

## 05:03 - dbt Semantic Layer & MetricFlow: Defining Metrics Once, Querying Everywhere

### The Problem It Solves

Without a semantic layer, metric definitions live scattered across dashboards, notebooks, and ad-hoc SQL. "Monthly Revenue" means one thing in Looker, something slightly different in a data science notebook, and a third thing in an executive spreadsheet. The dbt Semantic Layer centralizes metric definitions in your dbt project so every tool queries the same logic.

### How It Works

The dbt Semantic Layer is built on **MetricFlow**, dbt's open-source metric framework. You define **semantic models** and **metrics** in YAML, then query them via a standard interface (JDBC, Python SDK, or native BI integrations). MetricFlow generates the SQL dynamically based on the dimensions and time grains you request.

### Defining a Semantic Model

A semantic model sits on top of a dbt model and declares its measures, dimensions, and entities:

```yaml
# models/marts/semantic_models/orders.yml
semantic_models:
  - name: orders
    model: ref('fct_orders')
    description: "Order-level facts"

    entities:
      - name: order
        type: primary
        expr: order_id
      - name: customer
        type: foreign
        expr: customer_id

    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day
      - name: status
        type: categorical

    measures:
      - name: order_count
        agg: count
        expr: order_id
      - name: revenue
        agg: sum
        expr: order_total
      - name: avg_order_value
        agg: average
        expr: order_total
```

### Defining Metrics

Metrics reference measures from semantic models:

```yaml
metrics:
  - name: monthly_revenue
    type: simple
    type_params:
      measure: revenue
    filter: |
      {{ Dimension('orders__status') }} = 'delivered'

  - name: revenue_growth_mom
    type: derived
    type_params:
      expr: (revenue - revenue_prev_month) / revenue_prev_month
      metrics:
        - name: revenue
        - name: revenue
          offset_window: 1 month
          alias: revenue_prev_month

  - name: cumulative_revenue_ytd
    type: cumulative
    type_params:
      measure: revenue
      window: unbounded
      grain_to_date: year
```

### Querying with the MetricFlow CLI

```bash
# Query a metric with dimensions and time grain
mf query \
  --metrics monthly_revenue \
  --group-by metric_time__month,status \
  --start-time 2025-01-01 \
  --end-time 2025-12-31

# Validate all semantic model definitions
mf validate-configs

# List available metrics
mf list metrics

# Preview the SQL MetricFlow generates (without running it)
mf query --metrics monthly_revenue --group-by metric_time__month --explain
```

The `--explain` flag is invaluable during development — it shows the exact SQL MetricFlow will send to the warehouse, so you can verify the joins and aggregations are correct before they hit production.

### Three Metric Types

| Type | Use Case | Example |
|------|----------|---------|
| `simple` | Single measure, optional filter | Total revenue from delivered orders |
| `ratio` | Numerator / denominator measures | Conversion rate (orders / sessions) |
| `derived` | Expression over other metrics | MoM growth, margin percentage |
| `cumulative` | Running total over a window | YTD revenue, rolling 30-day signups |

### BI Integrations

The Semantic Layer exposes metrics through a standard JDBC/ADBC interface, meaning major BI tools can query dbt metrics natively:

- **Tableau**: via the dbt Semantic Layer connector
- **Looker**: via the dbt extension
- **Hex / Mode / Observable**: via the Python SDK (`dbtsl`)
- **Any SQL tool**: via the Semantic Layer JDBC endpoint

```python
# Python SDK example
from dbtsl import SemanticLayerClient

client = SemanticLayerClient(
    environment_id=12345,
    auth_token="your-token",
    host="semantic-layer.cloud.getdbt.com"
)

with client.session():
    df = client.query(
        metrics=["monthly_revenue"],
        group_by=["metric_time__month"],
    )
```

### Best Practices

- **One semantic model per grain.** Don't mix order-level and customer-level facts in the same semantic model — MetricFlow needs a clean, consistent grain to build joins.
- **Use `entities` for all join keys.** Declaring entities (primary/foreign) tells MetricFlow how to safely join semantic models when a query spans multiple grains.
- **Define `time_granularity` at the lowest grain available.** Declare `day`; MetricFlow handles roll-up to `week`, `month`, `quarter`, `year` automatically.
- **Test metric SQL with `--explain` before deploying.** Derived metrics involving offsets or ratio divisions can produce unexpected SQL — always verify.
- **Keep filters in metric definitions, not upstream models.** A metric filter (`filter: status = 'delivered'`) is explicit and auditable; pre-filtering in the model hides business logic from readers.

The Semantic Layer shifts metrics from implicit, scattered SQL to an explicit, version-controlled interface — the same shift dbt made for models five years ago, now applied to the aggregation layer above them.
