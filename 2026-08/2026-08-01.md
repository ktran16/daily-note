## 00:03 - dbt Incremental Model Strategies: Choosing the Right `incremental_strategy`

Incremental models are dbt's answer to processing only new or changed data instead of rebuilding entire tables on every run. The `incremental_strategy` config is the key lever — and choosing the wrong one can lead to duplicate data, slow jobs, or excessive warehouse costs.

### The Four Core Strategies

**1. `append` (default on some adapters)**

Inserts new rows only. Never deduplicates, never updates. Best for immutable event streams where you're certain rows won't change.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='append',
    unique_key='event_id'
) }}

select * from {{ source('raw', 'events') }}
{% if is_incremental() %}
where event_timestamp > (select max(event_timestamp) from {{ this }})
{% endif %}
```

Risk: if your pipeline replays events, you'll get duplicates.

---

**2. `merge` (recommended default for most cases)**

Performs an upsert: updates existing rows that match `unique_key`, inserts new rows. Requires adapter support (Snowflake, BigQuery, Databricks, Redshift ≥RA3).

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='order_id',
    merge_update_columns=['status', 'updated_at']   -- only update these columns
) }}

select
    order_id,
    status,
    updated_at
from {{ source('raw', 'orders') }}
{% if is_incremental() %}
where updated_at > (select max(updated_at) from {{ this }})
{% endif %}
```

`merge_update_columns` is a powerful optimization — it avoids overwriting columns like `created_at` that should stay immutable.

---

**3. `delete+insert`**

Deletes matching rows by `unique_key`, then inserts. Useful when `merge` isn't supported or when you need to re-process partitions cleanly. Common on Redshift and older Postgres setups.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='delete+insert',
    unique_key='date_day'   -- typically a partition column
) }}
```

Works well when `unique_key` is a date partition — you delete the whole day, then re-insert.

---

**4. `insert_overwrite` (partition-based)**

Replaces entire partitions instead of row-level merging. Fastest strategy for large datasets on BigQuery and Spark — no row-level comparison needed.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={
        'field': 'event_date',
        'data_type': 'date',
        'granularity': 'day'
    }
) }}

select
    date(event_timestamp) as event_date,
    user_id,
    event_type
from {{ source('raw', 'events') }}
{% if is_incremental() %}
where date(event_timestamp) >= date_sub(current_date(), interval 3 day)
{% endif %}
```

The lookback window (3 days here) is critical — it handles late-arriving data without requiring a full scan.

---

### Strategy Selection Guide

| Strategy | Duplicates Safe | Updates Rows | Partition-Level | Best For |
|---|---|---|---|---|
| `append` | No | No | No | Immutable event streams |
| `merge` | Yes | Yes | No | Orders, users, dim tables |
| `delete+insert` | Yes | Yes (via delete) | Optional | Redshift, Postgres |
| `insert_overwrite` | Yes | Yes (partition) | Yes | Large fact tables on BQ/Spark |

### Key Best Practices

- Always test your incremental filter logic by running `dbt run --full-refresh` and comparing row counts.
- Add `on_schema_change='sync_all_columns'` to handle column additions gracefully without a full refresh.
- For `merge`, keep `unique_key` indexed or clustered — unindexed merges on large tables are expensive.
- Use `{{ this }}` (not hardcoded table names) so the model works across environments automatically.

## 05:03 - dbt Semantic Layer & MetricFlow: Defining Metrics Once, Querying Everywhere

### The Problem It Solves

Without a semantic layer, metric definitions live scattered across dashboards, notebooks, and ad-hoc SQL. "Monthly Revenue" means one thing in Looker, something slightly different in a data science notebook, and a third thing in an executive spreadsheet. The dbt Semantic Layer centralizes metric definitions in your dbt project so every tool queries the same logic.

### How It Works

The dbt Semantic Layer is built on **MetricFlow**, dbt's open-source metric framework. You define **semantic models** and **metrics** in YAML, then query them via a standard interface (JDBC, Python SDK, or native BI integrations). MetricFlow generates the SQL dynamically based on the dimensions and time grains you request.

### Defining a Semantic Model

A semantic model sits on top of a dbt model and declares its measures, dimensions, and entities:

```yaml
# models/marts/semantic_models/orders.yml
semantic_models:
  - name: orders
    model: ref('fct_orders')
    description: "Order-level facts"

    entities:
      - name: order
        type: primary
        expr: order_id
      - name: customer
        type: foreign
        expr: customer_id

    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day
      - name: status
        type: categorical

    measures:
      - name: order_count
        agg: count
        expr: order_id
      - name: revenue
        agg: sum
        expr: order_total
      - name: avg_order_value
        agg: average
        expr: order_total
```

### Defining Metrics

Metrics reference measures from semantic models:

```yaml
metrics:
  - name: monthly_revenue
    type: simple
    type_params:
      measure: revenue
    filter: |
      {{ Dimension('orders__status') }} = 'delivered'

  - name: revenue_growth_mom
    type: derived
    type_params:
      expr: (revenue - revenue_prev_month) / revenue_prev_month
      metrics:
        - name: revenue
        - name: revenue
          offset_window: 1 month
          alias: revenue_prev_month

  - name: cumulative_revenue_ytd
    type: cumulative
    type_params:
      measure: revenue
      window: unbounded
      grain_to_date: year
```

### Querying with the MetricFlow CLI

```bash
# Query a metric with dimensions and time grain
mf query \
  --metrics monthly_revenue \
  --group-by metric_time__month,status \
  --start-time 2025-01-01 \
  --end-time 2025-12-31

# Validate all semantic model definitions
mf validate-configs

# List available metrics
mf list metrics

# Preview the SQL MetricFlow generates (without running it)
mf query --metrics monthly_revenue --group-by metric_time__month --explain
```

The `--explain` flag is invaluable during development — it shows the exact SQL MetricFlow will send to the warehouse, so you can verify the joins and aggregations are correct before they hit production.

### Three Metric Types

| Type | Use Case | Example |
|------|----------|---------|
| `simple` | Single measure, optional filter | Total revenue from delivered orders |
| `ratio` | Numerator / denominator measures | Conversion rate (orders / sessions) |
| `derived` | Expression over other metrics | MoM growth, margin percentage |
| `cumulative` | Running total over a window | YTD revenue, rolling 30-day signups |

### BI Integrations

The Semantic Layer exposes metrics through a standard JDBC/ADBC interface, meaning major BI tools can query dbt metrics natively:

- **Tableau**: via the dbt Semantic Layer connector
- **Looker**: via the dbt extension
- **Hex / Mode / Observable**: via the Python SDK (`dbtsl`)
- **Any SQL tool**: via the Semantic Layer JDBC endpoint

```python
# Python SDK example
from dbtsl import SemanticLayerClient

client = SemanticLayerClient(
    environment_id=12345,
    auth_token="your-token",
    host="semantic-layer.cloud.getdbt.com"
)

with client.session():
    df = client.query(
        metrics=["monthly_revenue"],
        group_by=["metric_time__month"],
    )
```

### Best Practices

- **One semantic model per grain.** Don't mix order-level and customer-level facts in the same semantic model — MetricFlow needs a clean, consistent grain to build joins.
- **Use `entities` for all join keys.** Declaring entities (primary/foreign) tells MetricFlow how to safely join semantic models when a query spans multiple grains.
- **Define `time_granularity` at the lowest grain available.** Declare `day`; MetricFlow handles roll-up to `week`, `month`, `quarter`, `year` automatically.
- **Test metric SQL with `--explain` before deploying.** Derived metrics involving offsets or ratio divisions can produce unexpected SQL — always verify.
- **Keep filters in metric definitions, not upstream models.** A metric filter (`filter: status = 'delivered'`) is explicit and auditable; pre-filtering in the model hides business logic from readers.

The Semantic Layer shifts metrics from implicit, scattered SQL to an explicit, version-controlled interface — the same shift dbt made for models five years ago, now applied to the aggregation layer above them.

## 10:03 - dbt Snapshots: Tracking Historical Change with Type 2 SCDs

### What Snapshots Solve

Most source tables reflect only the current state of a record. When a customer changes their plan from `starter` to `pro`, the old row is simply overwritten — and the history is gone. dbt Snapshots solve this by capturing row-level changes over time and storing them as a **Slowly Changing Dimension Type 2 (SCD2)** table, where each version of a record gets its own row with `dbt_valid_from` and `dbt_valid_to` timestamps.

### Defining a Snapshot

Snapshots live in the `snapshots/` directory and use the `{% snapshot %}` block:

```sql
-- snapshots/customer_snapshot.sql
{% snapshot customer_snapshot %}

{{
    config(
        target_schema='snapshots',
        unique_key='customer_id',
        strategy='timestamp',
        updated_at='updated_at',
        invalidate_hard_deletes=True
    )
}}

select
    customer_id,
    email,
    plan,
    status,
    updated_at
from {{ source('app_db', 'customers') }}

{% endsnapshot %}
```

Run it with:

```bash
dbt snapshot
# or target a specific snapshot
dbt snapshot --select customer_snapshot
```

### Two Snapshot Strategies

**1. `timestamp` (recommended)**

Compares the `updated_at` column. A row is considered changed if its `updated_at` is newer than the last snapshot capture. Requires your source table to have a reliable `updated_at` column.

```yaml
strategy: timestamp
updated_at: updated_at
```

**2. `check`**

Hashes a list of columns and flags a change if any column value differs. Use when there's no `updated_at` column — but be careful, it's slower (full row hash comparison) and sensitive to null handling.

```yaml
strategy: check
check_cols:
  - email
  - plan
  - status
# or check_cols: all  (hashes every column)
```

### What the Output Table Looks Like

| customer_id | plan | dbt_scd_id | dbt_updated_at | dbt_valid_from | dbt_valid_to |
|---|---|---|---|---|---|
| 42 | starter | abc123 | 2025-01-01 | 2025-01-01 | 2025-06-15 |
| 42 | pro | def456 | 2025-06-15 | 2025-06-15 | null |

- `dbt_valid_to = null` means the row is the current version.
- `dbt_valid_from` / `dbt_valid_to` let you reconstruct state at any point in time.

### Querying Point-in-Time State

```sql
-- What plan was customer 42 on during Q1 2025?
select *
from {{ ref('customer_snapshot') }}
where customer_id = 42
  and dbt_valid_from <= '2025-03-31'
  and (dbt_valid_to > '2025-03-31' or dbt_valid_to is null)
```

A common helper macro to get "state as of a given date" for an entire snapshot:

```sql
-- models/marts/customers_as_of.sql
{% set as_of_date = var('as_of_date', 'current_date') %}

select * from {{ ref('customer_snapshot') }}
where dbt_valid_from <= {{ as_of_date }}
  and (dbt_valid_to > {{ as_of_date }} or dbt_valid_to is null)
```

### `invalidate_hard_deletes`

By default, if a row disappears from the source, the snapshot keeps it open (`dbt_valid_to = null`) — it has no way to know the row was deleted. Setting `invalidate_hard_deletes=True` makes dbt close out those rows with the current timestamp:

```sql
{{ config(
    ...
    invalidate_hard_deletes=True
) }}
```

Use this when source deletes are meaningful business events (e.g., a cancelled account), not just soft deletes managed by a `status` column.

### Key Best Practices

- **Run snapshots before your models.** Snapshots capture source state; if you run models first, you may read stale data. Add snapshots to your orchestration DAG upstream of the models that reference them.
- **Don't transform in snapshots.** Keep snapshot SQL minimal — just select the columns you need to track. Put business logic in downstream models that `{{ ref() }}` the snapshot.
- **Use `target_schema` to isolate snapshots.** Storing them in a dedicated schema (e.g., `snapshots`) keeps your marts schema clean and makes permissions easier to manage.
- **Test `dbt_valid_to is null` for current records.** Add a `not_null` test on a derived column or use a generic test in your snapshot YAML to assert exactly one current row per `unique_key`.
- **Beware of late-arriving updates.** If your source backfills `updated_at` for old records, the timestamp strategy will re-snapshot those rows as if they changed today — potentially creating false history. Validate source data quality before relying on snapshots for auditing.

## 15:02 - dbt Model Contracts: Enforcing Schema Guarantees in Your Pipeline

### What Model Contracts Are

dbt model contracts (introduced in dbt Core 1.5) let you declare the exact schema a model must produce — column names, data types, and constraints — and have dbt enforce that contract at build time. If the model's output doesn't match, the run fails before bad data reaches downstream consumers.

Think of it as a compile-time type check for your data warehouse: the contract is the interface your model promises to uphold, independent of its implementation.

### Enabling a Contract

Contracts are defined in the model's `.yml` file under `config`:

```yaml
# models/marts/fct_orders.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true   # enables contract enforcement

    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key   # enforced in SQL, not just tests
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: foreign_key
            to: ref('dim_customers')
            to_columns: [customer_id]
      - name: order_date
        data_type: date
        constraints:
          - type: not_null
      - name: order_total
        data_type: numeric
      - name: status
        data_type: varchar
```

When `enforced: true`, dbt compares the model's actual output schema against the declared columns **before** swapping it into production (during the table build). If a column is missing, has the wrong type, or a constraint is violated, the run errors out.

### Constraint Types

| Constraint | Enforced In Warehouse | Description |
|---|---|---|
| `not_null` | Yes (most adapters) | Column cannot contain nulls |
| `primary_key` | Varies | Uniqueness + not null at DB level |
| `foreign_key` | Varies | Referential integrity at DB level |
| `unique` | Varies | No duplicate values |
| `check` | Varies | Custom SQL predicate (e.g., `amount > 0`) |
| `custom` | Adapter-specific | Raw DDL passed through |

Not all adapters enforce all constraints in the database — Snowflake, for example, supports `not_null` but treats `primary_key` and `foreign_key` as metadata-only (unenforced). Check your adapter's docs for what gets enforced vs. documented.

### Using `check` Constraints

For business-rule validation directly in DDL:

```yaml
columns:
  - name: discount_pct
    data_type: numeric
    constraints:
      - type: check
        expression: "discount_pct >= 0 and discount_pct <= 100"
```

### Contracts and Versioned Models

Model contracts shine brightest alongside **model versioning** (also dbt 1.5+). When you version a model, each version can have its own contract, and downstream `ref()` calls pin to a specific version:

```yaml
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 1
        config:
          contract:
            enforced: true
      - v: 2
        config:
          contract:
            enforced: true
```

Downstream models use `ref('fct_orders', version=1)` to stay on the stable interface while v2 is developed in parallel — no breaking changes until consumers opt in.

### Best Practices

- **Enable contracts on public, cross-team models first.** Models consumed by BI tools or other teams are the highest-risk surface for schema drift. Start there.
- **Pair contracts with `access: public`.** The dbt access config (`public` / `protected` / `private`) signals which models are intended for external use; contracts make that promise enforceable.
- **Don't over-specify.** You don't need to list every internal staging column. Focus on columns that external consumers depend on.
- **Use `data_type` strings your adapter understands.** `bigint` works in Postgres and Snowflake; BigQuery uses `INT64`. Keep adapter-specific types in mind to avoid false failures.
- **Run `dbt compile` before `dbt run`** in CI to catch contract mismatches early — dbt validates the declared vs. inferred schema at compile time on supported adapters.

Model contracts are the bridge between "dbt as a transformation tool" and "dbt as a data platform" — they let teams publish stable, versioned interfaces that downstream consumers can rely on without reading the source SQL.
