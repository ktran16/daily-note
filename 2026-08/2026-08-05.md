## 00:03 - dbt Materializations: Choosing Between View, Table, Incremental, and Ephemeral

Every dbt model has a **materialization** — the strategy dbt uses to persist (or not persist) results in the warehouse. Picking the right one has a direct impact on query performance, build time, and cost.

### The Four Core Materializations

**1. `view` (default)**
The model SQL becomes a database view. Nothing is stored; the query runs on demand every time the view is queried. Best for lightweight transformations close to the raw source.

```yaml
# dbt_project.yml
models:
  my_project:
    staging:
      +materialized: view
```

**2. `table`**
dbt drops and recreates the table on every `dbt run`. Results are stored physically, so downstream queries are fast. Ideal for mid-layer transformations that are expensive to recompute but change fully each run.

```yaml
models:
  my_project:
    marts:
      +materialized: table
```

**3. `incremental`**
dbt only processes new or changed rows, appending or merging them into an existing table. This is the right choice for large event tables where a full rebuild every run is cost-prohibitive.

```sql
-- models/fct_events.sql
{{ config(materialized='incremental', unique_key='event_id') }}

SELECT *
FROM {{ ref('stg_events') }}

{% if is_incremental() %}
  WHERE created_at > (SELECT MAX(created_at) FROM {{ this }})
{% endif %}
```

The `is_incremental()` block is skipped on a first run or a `--full-refresh`, so the filter only applies when the table already exists.

**4. `ephemeral`**
The model is never written to the warehouse — it compiles into a CTE and is inlined wherever it's referenced. Zero storage cost, but it can bloat complex SQL and is invisible in the warehouse for debugging.

```yaml
models:
  my_project:
    intermediate:
      +materialized: ephemeral
```

### Decision Guide

| Scenario | Recommended Materialization |
|---|---|
| Thin rename/cast of a source | `view` |
| Full nightly rebuild, moderate size | `table` |
| Billions of rows, append-only events | `incremental` |
| Shared subquery logic, not queried directly | `ephemeral` |

### Key Tip: Override Per Model

Project-level defaults can always be overridden with a `config()` block inside the model file:

```sql
{{ config(materialized='table') }}

SELECT ...
```

This makes your intent explicit and searchable — prefer it for any model that deviates from the folder default.

### Common Mistake

Using `incremental` for a model where rows are frequently updated but not tracked with a reliable `unique_key`. Without a proper key, dbt can't detect changes and you end up with duplicates. Always pair `incremental` with a `unique_key` and validate it with a `not_null` + `unique` test on that column.

## 05:03 - dbt Seeds: Loading Static Reference Data into Your Warehouse

**Seeds** are CSV files that dbt loads directly into your warehouse as tables. They're the right tool for small, slowly-changing reference datasets — things like country codes, cost center mappings, or status label lookups — that live better in version control than in a separate ingestion pipeline.

### Project Layout

Place CSV files under the `seeds/` directory:

```
my_project/
├── seeds/
│   ├── country_codes.csv
│   └── cost_centers.csv
```

Run `dbt seed` to load them. dbt creates a table in your target schema for each file, named after the file.

### Referencing a Seed in a Model

Use `ref()` exactly like you would for a model — dbt tracks the dependency and ensures the seed is loaded before any model that uses it:

```sql
-- models/marts/fct_orders.sql
SELECT
    o.order_id,
    o.country_code,
    c.country_name
FROM {{ ref('stg_orders') }} o
LEFT JOIN {{ ref('country_codes') }} c
    ON o.country_code = c.code
```

### Controlling Column Types

dbt infers column types from the CSV, but inference can go wrong for columns that look numeric but should be strings (e.g. ZIP codes, product codes). Override types explicitly in `dbt_project.yml`:

```yaml
seeds:
  my_project:
    country_codes:
      +column_types:
        code: varchar(10)
        dial_prefix: varchar(5)
```

### Practical Tips

**Schema separation:** Keep seeds in their own schema so they don't clutter your marts or staging layers:

```yaml
seeds:
  my_project:
    +schema: reference
```

This creates tables under `<target_schema>_reference` (e.g. `analytics_reference.country_codes`).

**Full refresh behavior:** `dbt seed` always does a full drop-and-recreate. There's no incremental mode for seeds — keep files small (a few thousand rows at most) and use a proper ingestion tool for anything larger.

**Testing seeds:** Seeds support the same generic tests as models. Add `not_null` and `unique` to your seed's YAML schema to catch corrupt CSV data before it propagates:

```yaml
# seeds/schema.yml
version: 2
seeds:
  - name: country_codes
    columns:
      - name: code
        tests:
          - not_null
          - unique
```

### When Not to Use Seeds

- Data that changes daily or is fetched from an API → use a loader (Fivetran, Airbyte, etc.)
- Large lookup tables (millions of rows) → load via pipeline, model as a source
- Data containing PII → CSVs in version control are visible to everyone with repo access

## 10:03 - dbt Exposures: Documenting Downstream Data Consumers in Your DAG

**Exposures** let you declare the real-world artifacts that depend on your dbt models — dashboards, reports, ML models, or third-party apps — and surface them as first-class nodes in the dbt DAG. This closes the lineage loop: instead of the graph stopping at your mart tables, you can see exactly which Tableau workbook or Python model consumes a given table.

### Defining an Exposure

Exposures live in any `.yml` file (typically `models/exposures.yml`):

```yaml
version: 2

exposures:
  - name: weekly_revenue_dashboard
    type: dashboard
    maturity: high
    url: https://bi.company.com/dashboards/revenue
    description: >
      Executive dashboard tracking weekly and monthly revenue by region.
      Owned by the Finance Analytics team.
    owner:
      name: Finance Analytics
      email: finance-analytics@company.com
    depends_on:
      - ref('fct_orders')
      - ref('dim_customers')
      - ref('dim_dates')
```

`type` accepts `dashboard`, `notebook`, `analysis`, `ml`, or `application`. `maturity` (`low`, `medium`, `high`) signals how production-ready the exposure is.

### Why It Matters

**Impact analysis:** When you run `dbt ls --select fct_orders+`, the exposure appears as a downstream node. Before you rename or restructure `fct_orders`, you immediately see which dashboards will break.

**Docs site:** `dbt docs generate` renders exposures in the lineage graph with their owner and URL, making the data catalog useful to non-engineers like analysts and product managers.

**CI checks:** You can test exposures with `dbt build --select +weekly_revenue_dashboard` — this runs all upstream models and their tests, confirming the full data path to that artifact is healthy before deploying.

### Practical Tips

- **One exposure per artifact.** Don't create a single giant "BI Tools" exposure; granularity makes impact analysis meaningful.
- **Keep `owner` current.** Stale ownership is worse than no ownership — a wrong email sends alerts into a void.
- **Use `maturity: low`** for exploratory notebooks or prototypes so consumers know not to build on top of them.
- **Pair with model contracts** on the tables an exposure depends on. If `fct_orders` has a contract enforcing column types, your dashboard is insulated from accidental schema changes upstream.

Exposures are lightweight to add and dramatically improve the operational picture of who uses your data — making them one of the highest-ROI documentation steps in a maturing dbt project.

## 15:04 - dbt Slim CI: Running Only What Changed in Your CI Pipeline

Running every model on every pull request is expensive and slow. **Slim CI** solves this by using dbt's state-based selection to build and test only the models that changed relative to a production baseline — turning a 30-minute full run into a 2-minute targeted one.

### The Core Idea

dbt can compare the current project state against a compiled artifact from a previous run (typically the last successful production deployment). The `state:modified` selector identifies nodes whose definitions have changed; the `+` suffix adds their downstream dependents.

```bash
# Only build models that changed AND everything downstream of them
dbt build --select state:modified+ --defer --state ./prod-artifacts
```

`--defer` is the companion flag: for any model *not* selected (i.e. unchanged upstream dependencies), dbt reads results from the production environment instead of rebuilding them in CI. Your CI job runs against real production data without rebuilding the whole pipeline.

### Where the Artifacts Come From

dbt writes two artifact files after every successful run:
- `manifest.json` — the compiled graph of all nodes
- `run_results.json` — which nodes ran and their outcomes

For Slim CI, you need the production `manifest.json` available at CI time. The typical setup:

**dbt Cloud (built-in):** Use the `Defer to production` toggle in a CI job. dbt Cloud automatically fetches the production environment's latest manifest — no manual artifact handling needed.

**dbt Core / self-hosted:** Upload `manifest.json` to object storage (S3, GCS, etc.) at the end of every production run, then download it at the start of CI:

```bash
# In your CI pipeline (e.g. GitHub Actions)
- name: Download production manifest
  run: aws s3 cp s3://my-bucket/dbt-artifacts/manifest.json ./prod-artifacts/manifest.json

- name: Run Slim CI
  run: dbt build --select state:modified+ --defer --state ./prod-artifacts
```

### Handling Schema Isolation

CI jobs should build into a dedicated schema so they don't pollute production tables. Set the target schema via an environment variable:

```yaml
# profiles.yml
my_project:
  target: ci
  outputs:
    ci:
      type: bigquery
      dataset: "{{ env_var('DBT_DATASET', 'dbt_dev') }}"
      # ... other connection params
```

In CI, set `DBT_DATASET=dbt_ci_pr_{{ PR_NUMBER }}`. Clean up the schema after the job completes.

### Freshness Check Optimization

Combine Slim CI with source freshness checks scoped to only the sources your changed models actually use:

```bash
dbt source freshness --select state:modified+
dbt build --select state:modified+ --defer --state ./prod-artifacts
```

### What Doesn't Get Caught

Slim CI misses **indirect breakage**: if an unchanged model's behavior changes because its upstream source changed schema, `state:modified` won't flag it. Supplement with a nightly full run against production to catch drift that Slim CI can't see.

The key habit: always store and version your production `manifest.json`. Without a reliable baseline artifact, Slim CI falls back to a full run — defeating the whole purpose.

## 19:04 - dbt Model Contracts: Enforcing Schema Stability for Critical Tables

A **model contract** is a formal declaration of a model's expected schema — its columns, data types, and constraints. When a contract is active, dbt enforces it at compile time and (for supported adapters) at the database level. Any model change that breaks the declared interface fails the run before it touches production data.

### Why Contracts Matter

Without contracts, a developer can rename a column, drop a field, or change a type and not discover the breakage until a downstream dashboard throws an error — potentially hours or days later. Contracts move that failure left, into the CI pipeline, where it's cheap to catch.

### Defining a Contract

Contracts are declared in the model's `.yml` file:

```yaml
# models/schema.yml
version: 2

models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
      - name: total_amount
        data_type: numeric
      - name: status
        data_type: varchar
```

With `enforced: true`, dbt will:
1. Verify that every declared column exists in the model's SELECT output.
2. Verify that column order matches the declaration (required for some adapters).
3. Push `NOT NULL` and `PRIMARY KEY` constraints to the database if the adapter supports it (BigQuery, Snowflake, Redshift, Databricks).

### The Contract Enforcement Moment

dbt checks contracts **during compilation**, before SQL reaches the warehouse. If the model's query returns a column that isn't in the contract, or omits a declared column, the run fails immediately with a clear error:

```
Contract violation: model 'fct_orders' is missing column 'total_amount'
```

This means you can use `dbt parse` or `dbt compile` in a pre-merge CI step to catch violations without running any SQL at all.

### Contracts and Versioning

Model contracts pair naturally with **model versioning** (`versions:` in the schema). When you need a breaking schema change, you create a new version of the model instead of mutating the existing one. Consumers pin to `ref('fct_orders', v=1)` and migrate to `v=2` on their own schedule — no surprise breakage.

```yaml
models:
  - name: fct_orders
    versions:
      - v: 1
      - v: 2
    config:
      contract:
        enforced: true
```

### Practical Guidelines

- **Apply contracts to mart/consumption-layer models first.** These are the tables dashboards and external tools query directly — the highest-impact place for stability guarantees.
- **Don't start with `data_type` on every column.** dbt's type checking is adapter-specific and can be noisy during initial rollout. Start by enforcing column *presence* and add type constraints incrementally.
- **Use contracts as living documentation.** A `.yml` file with a full contract is the most reliable schema reference for downstream consumers — more trustworthy than a wiki page that drifts.
- **Combine with exposures.** If an exposure declares `depends_on: ref('fct_orders')`, and `fct_orders` has a contract, you get end-to-end traceability: the contract protects the schema, the exposure documents who relies on it.
