## 00:03 - dbt Materializations: Choosing Between View, Table, Incremental, and Ephemeral

Every dbt model has a **materialization** — the strategy dbt uses to persist (or not persist) results in the warehouse. Picking the right one has a direct impact on query performance, build time, and cost.

### The Four Core Materializations

**1. `view` (default)**
The model SQL becomes a database view. Nothing is stored; the query runs on demand every time the view is queried. Best for lightweight transformations close to the raw source.

```yaml
# dbt_project.yml
models:
  my_project:
    staging:
      +materialized: view
```

**2. `table`**
dbt drops and recreates the table on every `dbt run`. Results are stored physically, so downstream queries are fast. Ideal for mid-layer transformations that are expensive to recompute but change fully each run.

```yaml
models:
  my_project:
    marts:
      +materialized: table
```

**3. `incremental`**
dbt only processes new or changed rows, appending or merging them into an existing table. This is the right choice for large event tables where a full rebuild every run is cost-prohibitive.

```sql
-- models/fct_events.sql
{{ config(materialized='incremental', unique_key='event_id') }}

SELECT *
FROM {{ ref('stg_events') }}

{% if is_incremental() %}
  WHERE created_at > (SELECT MAX(created_at) FROM {{ this }})
{% endif %}
```

The `is_incremental()` block is skipped on a first run or a `--full-refresh`, so the filter only applies when the table already exists.

**4. `ephemeral`**
The model is never written to the warehouse — it compiles into a CTE and is inlined wherever it's referenced. Zero storage cost, but it can bloat complex SQL and is invisible in the warehouse for debugging.

```yaml
models:
  my_project:
    intermediate:
      +materialized: ephemeral
```

### Decision Guide

| Scenario | Recommended Materialization |
|---|---|
| Thin rename/cast of a source | `view` |
| Full nightly rebuild, moderate size | `table` |
| Billions of rows, append-only events | `incremental` |
| Shared subquery logic, not queried directly | `ephemeral` |

### Key Tip: Override Per Model

Project-level defaults can always be overridden with a `config()` block inside the model file:

```sql
{{ config(materialized='table') }}

SELECT ...
```

This makes your intent explicit and searchable — prefer it for any model that deviates from the folder default.

### Common Mistake

Using `incremental` for a model where rows are frequently updated but not tracked with a reliable `unique_key`. Without a proper key, dbt can't detect changes and you end up with duplicates. Always pair `incremental` with a `unique_key` and validate it with a `not_null` + `unique` test on that column.
