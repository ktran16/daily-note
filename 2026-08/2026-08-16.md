## 00:03 - dbt Tags: Organizing Models for Targeted Runs and Selective Scheduling

Tags in dbt are lightweight metadata labels you attach to models, sources, seeds, snapshots, or tests. They unlock surgical `--select` expressions so you can run exactly the subset of your project that a job or workflow needs — no more, no less.

### Defining Tags

Tags can live at the project level (in `dbt_project.yml`), the directory level, or on individual nodes in YAML config blocks:

```yaml
# dbt_project.yml — apply a tag to every model in a folder
models:
  my_project:
    marts:
      finance:
        +tags: ["finance", "daily"]
    marts:
      marketing:
        +tags: ["marketing", "hourly"]
```

```yaml
# models/marts/finance/fct_revenue.yml — node-level tag
models:
  - name: fct_revenue
    config:
      tags: ["finance", "daily", "critical"]
```

You can also set tags inline in a model's config block:

```sql
{{ config(tags=["finance", "daily"]) }}

select ...
```

### Selecting by Tag

Use the `tag:` selector method to target specific subsets at runtime:

```bash
# Run every model tagged "daily"
dbt run --select tag:daily

# Run finance models that are also tagged "critical"
dbt run --select tag:finance,tag:critical

# Test only models tagged "hourly"
dbt test --select tag:hourly

# Build the "critical" subgraph and all its downstream dependents
dbt build --select tag:critical+
```

### Common Tag Strategies

| Tag Pattern | Purpose |
|---|---|
| `daily`, `hourly`, `weekly` | Scheduling cadence — each job selects its own slice |
| `finance`, `marketing` | Domain ownership — teams run their own models |
| `critical` | SLA-sensitive models — prioritize in alerts and retries |
| `pii` | Compliance — identify models touching sensitive columns |
| `slow` | Expensive queries — exclude from developer previews |

### Listing Tags Programmatically

Use `dbt ls` to inspect which nodes carry a tag before running:

```bash
dbt ls --select tag:finance --output name
```

### Practical Scheduling Pattern

In orchestrators like Airflow or dbt Cloud, map one job per cadence tag rather than maintaining explicit model lists. When a new model is built, adding `tags: ["hourly"]` to its config automatically enrolls it in the hourly job — no orchestration change required. This keeps jobs self-maintaining as the project grows.

**Key takeaway:** Tags are a low-friction way to create logical groupings that survive refactoring. Prefer them over brittle path-based selectors (`models/marts/finance/...`) when the grouping is logical (ownership, cadence, criticality) rather than structural.

## 05:03 - dbt `on_schema_change`: Handling Column Drift in Incremental Models

When an incremental model's SELECT query gains, loses, or renames columns, dbt has to decide what to do with the already-existing table. The `on_schema_change` config controls that decision — getting it wrong silently drops data or fails builds at the worst moment.

### The Four Options

```yaml
# models/marts/fct_events.yml
models:
  - name: fct_events
    config:
      materialized: incremental
      unique_key: event_id
      on_schema_change: append_new_columns   # ← the key setting
```

| Value | Behavior |
|---|---|
| `ignore` | **Default.** New columns in SELECT are silently dropped; the table schema never changes. Safe but lossy. |
| `fail` | Raise a hard error if the column set differs at all. Use when schema drift is always a bug. |
| `append_new_columns` | Add columns that appear in SELECT but are missing from the table; fill them `NULL` for historical rows. Never removes columns. |
| `sync_all_columns` | Mirror SELECT exactly: add missing columns and **drop columns no longer in SELECT**. Destructive — use with care. |

### Why `ignore` Quietly Loses Data

```sql
-- Original model
select event_id, user_id, event_type from raw.events

-- After adding a new column:
select event_id, user_id, event_type, session_id from raw.events
```

With `on_schema_change: ignore` (the default), `session_id` is present in the query result but absent from the physical table schema. dbt inserts rows using positional matching against the existing columns — `session_id` values are discarded without any warning. You only notice when a downstream report queries a column that was never actually written.

### The Recommended Pattern

Use `append_new_columns` as your project default for incremental models. It's non-destructive and surfaces new columns automatically without a full refresh:

```yaml
# dbt_project.yml — set project-wide default
models:
  my_project:
    +on_schema_change: append_new_columns
```

Override to `fail` for models where column changes should always be reviewed (e.g., models feeding ML pipelines or contracts):

```sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    on_schema_change='fail'
) }}
```

### When You Still Need `--full-refresh`

`on_schema_change` handles column additions and (with `sync_all_columns`) removals, but it cannot restate historical rows with new column values. If a new column should be populated for all existing rows — not just `NULL` — you still need a full refresh after adding the column to the source logic.

**Key takeaway:** Set `on_schema_change: append_new_columns` as your project default. It keeps incremental builds from silently discarding new columns while staying non-destructive. Reserve `fail` for schema-sensitive models and only reach for `sync_all_columns` when you explicitly intend to remove old columns from the table.

## 10:04 - dbt Model Contracts: Enforcing Schema Guarantees for Downstream Consumers

A dbt **model contract** lets you declare an explicit, binding schema for a model — column names, data types, and constraints — that dbt verifies at build time. Contracts are the handshake between the model's author and everyone downstream: if the contract is broken, the build fails before bad data ever reaches consumers.

### Why Contracts Matter

Without a contract, a model's schema is implicit. Renaming a column, changing a type, or reordering SELECT columns is a silent breaking change that only surfaces when a downstream BI tool or pipeline throws a runtime error. Contracts make those changes visible at CI time, not incident time.

### Enabling a Contract

Add `contract: {enforced: true}` to the model's config, then declare every column with its data type:

```yaml
# models/marts/fct_orders.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
      - name: total_amount
        data_type: numeric
      - name: status
        data_type: varchar
```

dbt compiles the contract into DDL-level constraints (on supported adapters) and validates that the SELECT output column names and types match exactly. Any mismatch raises an error before the model is materialized.

### What dbt Checks

| Check | Details |
|---|---|
| Column name match | Every declared column must appear in SELECT; extra undeclared columns are allowed |
| Data type match | Types are compared after adapter-specific normalization (e.g., `varchar` vs `text`) |
| Constraints | `not_null` and `primary_key` are enforced at the DB level where the adapter supports it |

### Constraints Reference

```yaml
constraints:
  - type: not_null          # column cannot be NULL
  - type: unique            # all values must be distinct
  - type: primary_key       # not_null + unique, marks the natural key
  - type: foreign_key
    to: ref('dim_customers')
    to_columns: [customer_id]
  - type: check
    expression: "total_amount >= 0"
```

Not all constraint types are enforced by all adapters. dbt will warn on unsupported constraints rather than silently ignoring them.

### Model-Level Constraints

You can also declare constraints at the model level for multi-column keys:

```yaml
models:
  - name: fct_order_items
    config:
      contract:
        enforced: true
    constraints:
      - type: primary_key
        columns: [order_id, line_item_id]
    columns:
      - name: order_id
        data_type: bigint
      - name: line_item_id
        data_type: int
```

### Contracts and Versioning

Contracts pair naturally with **model versioning** (`versions:` in YAML). When you break a contract by changing a column type or removing a column, bump the version instead of mutating the existing contract. Downstream consumers pin to a version and migrate on their own schedule.

```yaml
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 1          # deprecated but still queryable as fct_orders_v1
      - v: 2          # current contract lives here
```

**Key takeaway:** Enable contracts on models that serve external consumers — BI tools, reverse ETL, ML pipelines, or other dbt projects via cross-project refs. They shift breaking-change detection from runtime incidents to CI failures, and they document the schema guarantee in a machine-readable, version-controlled form that lives next to the model itself.

## 15:03 - dbt Profiles and Targets: Configuring Multi-Environment Connections

The `profiles.yml` file is dbt's connection configuration layer — it maps profile names to warehouse credentials and defines **targets** (named connection contexts like `dev`, `staging`, and `prod`). Understanding it is essential for running dbt Core locally and for structuring CI/CD pipelines correctly.

### File Location and Structure

`profiles.yml` lives at `~/.dbt/profiles.yml` by default (outside the project repo, to keep credentials out of version control). Each profile groups one or more targets:

```yaml
# ~/.dbt/profiles.yml
my_project:
  target: dev          # the default target when --target is omitted
  outputs:
    dev:
      type: snowflake
      account: "{{ env_var('SNOWFLAKE_ACCOUNT') }}"
      user: "{{ env_var('SNOWFLAKE_USER') }}"
      private_key_path: ~/.ssh/snowflake_key.p8
      role: TRANSFORMER_DEV
      database: ANALYTICS_DEV
      warehouse: COMPUTE_WH_DEV
      schema: "dbt_{{ env_var('DBT_USER', 'local') }}"
      threads: 4

    prod:
      type: snowflake
      account: "{{ env_var('SNOWFLAKE_ACCOUNT') }}"
      user: "{{ env_var('SNOWFLAKE_SVC_USER') }}"
      private_key_path: /secrets/snowflake_key.p8
      role: TRANSFORMER_PROD
      database: ANALYTICS
      warehouse: COMPUTE_WH_PROD
      schema: dbt_prod
      threads: 16
```

### Key Design Decisions

**Per-developer schemas** (`schema: "dbt_{{ env_var('DBT_USER', 'local') }}"`) give each developer their own isolated sandbox in the warehouse. No two developers clobber each other's models.

**Threads** control parallelism. More threads means faster runs but higher warehouse concurrency load. `4` is a safe default for dev; `16+` works for large CI or prod jobs.

**Credential isolation**: Never hardcode secrets — always use `env_var()`. This keeps `profiles.yml` shareable as a template while secrets stay in environment variables or a secrets manager.

### Switching Targets at Runtime

```bash
# Use the prod target for a one-off run
dbt run --target prod --select tag:critical

# dbt Cloud and CI: set DBT_TARGET env var to override
export DBT_TARGET=staging
dbt build
```

### Validating Your Connection

```bash
dbt debug               # tests the active target connection
dbt debug --target prod # tests a specific target
```

`dbt debug` is the first command to run when a new developer sets up their environment — it catches missing env vars, bad credentials, and network issues before any model runs.

### Profiles in dbt Cloud

dbt Cloud replaces `profiles.yml` entirely with its Connection UI. You define credentials in the project settings, and dbt Cloud injects them at runtime. If you're on dbt Cloud, `profiles.yml` is only needed for running dbt Core locally against the same warehouse.

**Key takeaway:** Use `env_var()` for all secrets, give each developer a personal schema via `DBT_USER`, and keep `profiles.yml` out of version control. Commit a `profiles.yml.example` template to the repo instead so new contributors know exactly what to configure.
