## 00:03 - dbt Tags: Organizing Models for Targeted Runs and Selective Scheduling

Tags in dbt are lightweight metadata labels you attach to models, sources, seeds, snapshots, or tests. They unlock surgical `--select` expressions so you can run exactly the subset of your project that a job or workflow needs — no more, no less.

### Defining Tags

Tags can live at the project level (in `dbt_project.yml`), the directory level, or on individual nodes in YAML config blocks:

```yaml
# dbt_project.yml — apply a tag to every model in a folder
models:
  my_project:
    marts:
      finance:
        +tags: ["finance", "daily"]
    marts:
      marketing:
        +tags: ["marketing", "hourly"]
```

```yaml
# models/marts/finance/fct_revenue.yml — node-level tag
models:
  - name: fct_revenue
    config:
      tags: ["finance", "daily", "critical"]
```

You can also set tags inline in a model's config block:

```sql
{{ config(tags=["finance", "daily"]) }}

select ...
```

### Selecting by Tag

Use the `tag:` selector method to target specific subsets at runtime:

```bash
# Run every model tagged "daily"
dbt run --select tag:daily

# Run finance models that are also tagged "critical"
dbt run --select tag:finance,tag:critical

# Test only models tagged "hourly"
dbt test --select tag:hourly

# Build the "critical" subgraph and all its downstream dependents
dbt build --select tag:critical+
```

### Common Tag Strategies

| Tag Pattern | Purpose |
|---|---|
| `daily`, `hourly`, `weekly` | Scheduling cadence — each job selects its own slice |
| `finance`, `marketing` | Domain ownership — teams run their own models |
| `critical` | SLA-sensitive models — prioritize in alerts and retries |
| `pii` | Compliance — identify models touching sensitive columns |
| `slow` | Expensive queries — exclude from developer previews |

### Listing Tags Programmatically

Use `dbt ls` to inspect which nodes carry a tag before running:

```bash
dbt ls --select tag:finance --output name
```

### Practical Scheduling Pattern

In orchestrators like Airflow or dbt Cloud, map one job per cadence tag rather than maintaining explicit model lists. When a new model is built, adding `tags: ["hourly"]` to its config automatically enrolls it in the hourly job — no orchestration change required. This keeps jobs self-maintaining as the project grows.

**Key takeaway:** Tags are a low-friction way to create logical groupings that survive refactoring. Prefer them over brittle path-based selectors (`models/marts/finance/...`) when the grouping is logical (ownership, cadence, criticality) rather than structural.

## 05:03 - dbt `on_schema_change`: Handling Column Drift in Incremental Models

When an incremental model's SELECT query gains, loses, or renames columns, dbt has to decide what to do with the already-existing table. The `on_schema_change` config controls that decision — getting it wrong silently drops data or fails builds at the worst moment.

### The Four Options

```yaml
# models/marts/fct_events.yml
models:
  - name: fct_events
    config:
      materialized: incremental
      unique_key: event_id
      on_schema_change: append_new_columns   # ← the key setting
```

| Value | Behavior |
|---|---|
| `ignore` | **Default.** New columns in SELECT are silently dropped; the table schema never changes. Safe but lossy. |
| `fail` | Raise a hard error if the column set differs at all. Use when schema drift is always a bug. |
| `append_new_columns` | Add columns that appear in SELECT but are missing from the table; fill them `NULL` for historical rows. Never removes columns. |
| `sync_all_columns` | Mirror SELECT exactly: add missing columns and **drop columns no longer in SELECT**. Destructive — use with care. |

### Why `ignore` Quietly Loses Data

```sql
-- Original model
select event_id, user_id, event_type from raw.events

-- After adding a new column:
select event_id, user_id, event_type, session_id from raw.events
```

With `on_schema_change: ignore` (the default), `session_id` is present in the query result but absent from the physical table schema. dbt inserts rows using positional matching against the existing columns — `session_id` values are discarded without any warning. You only notice when a downstream report queries a column that was never actually written.

### The Recommended Pattern

Use `append_new_columns` as your project default for incremental models. It's non-destructive and surfaces new columns automatically without a full refresh:

```yaml
# dbt_project.yml — set project-wide default
models:
  my_project:
    +on_schema_change: append_new_columns
```

Override to `fail` for models where column changes should always be reviewed (e.g., models feeding ML pipelines or contracts):

```sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    on_schema_change='fail'
) }}
```

### When You Still Need `--full-refresh`

`on_schema_change` handles column additions and (with `sync_all_columns`) removals, but it cannot restate historical rows with new column values. If a new column should be populated for all existing rows — not just `NULL` — you still need a full refresh after adding the column to the source logic.

**Key takeaway:** Set `on_schema_change: append_new_columns` as your project default. It keeps incremental builds from silently discarding new columns while staying non-destructive. Reserve `fail` for schema-sensitive models and only reach for `sync_all_columns` when you explicitly intend to remove old columns from the table.
