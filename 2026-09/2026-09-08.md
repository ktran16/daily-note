## 00:03 - [Data Engineering] Idempotent Backfills: Why Your Retry Doubled Yesterday's Revenue

A task retried is a task run twice. Airflow retries on failure, Dagster retries, and someone always re-runs a backfill "just to be safe." If the write is a plain `INSERT`, every one of those doubles rows — and the failure is silent, because nothing errored. You find it weeks later when revenue looks 2x on one day.

The fix is not "retry less." It is making the write **idempotent**: running it N times leaves the same state as running it once.

### The unit of idempotency is a partition, not a row

Pick a partition key that matches your schedule — usually the logical date — and make each run *replace* its own partition:

```sql
-- One transaction. Never an INSERT alone.
BEGIN;
DELETE FROM analytics.fct_orders WHERE order_date = '{{ ds }}';
INSERT INTO analytics.fct_orders
SELECT ... FROM staging.orders WHERE order_date = '{{ ds }}';
COMMIT;
```

Snowflake, BigQuery, and Databricks all wrap this in a single statement:

```sql
-- BigQuery / Databricks / Spark SQL
INSERT OVERWRITE TABLE analytics.fct_orders
PARTITION (order_date = '{{ ds }}')
SELECT ... FROM staging.orders WHERE order_date = '{{ ds }}';
```

In dbt this is `insert_overwrite`, and it is the strategy to reach for whenever a run owns whole partitions:

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={'field': 'order_date', 'data_type': 'date'}
) }}

select * from {{ ref('stg_orders') }}
{% if is_incremental() %}
  where order_date >= date_sub(current_date(), interval 3 day)
{% endif %}
```

The 3-day lookback is deliberate: it re-derives the last three partitions every run, so late-arriving rows land without a manual backfill.

### The rule that actually breaks people

**Never use `current_date()` or `now()` in transformation logic.** A task for 2026-09-01 that reruns today must produce what it produced on 2026-09-01 — otherwise a backfill of 90 days writes 90 copies of *today*. Take the logical date from the orchestrator (`{{ ds }}`, Dagster's partition key) and pass it in.

Same reason `MERGE` beats `INSERT` for row-level upserts: it needs a real unique key, and if that key isn't unique, `MERGE` errors loudly instead of duplicating quietly. That is the trade you want.

## 05:04 - [Data Analytics] RFM Segmentation: Why NTILE Silently Scrambles Your Frequency Score

RFM scores every customer on **R**ecency, **F**requency, and **M**onetary value, usually 1–5 each, then concatenates them (`545`, `111`) into segments like "Champions" or "At Risk". The standard recipe reaches for `NTILE(5)` on all three. That is correct for two of them and quietly wrong for the third.

`NTILE(n)` splits rows into equal-sized buckets **by row count, ignoring ties**. Recency and monetary are near-continuous — few exact duplicates, so the cuts land where you'd expect. Frequency is not. In a typical 50,000-customer retail table, ~31,000 bought exactly once. `NTILE(5)` wants 10,000 per bucket, so those identical one-time buyers get spread across buckets 1, 2, 3 and part of 4. Two customers with byte-identical behavior receive different scores, and the split point is arbitrary — reload the table and a customer moves segments without doing anything.

Check for that tie mass before you trust any `NTILE`:

```sql
SELECT frequency, COUNT(*) AS customers
FROM base GROUP BY 1 ORDER BY 1 LIMIT 10;
```

**Rule of thumb: if any single value holds more than `1/n` of the rows, `NTILE(n)` will split it.** Use explicit thresholds there instead.

```sql
WITH base AS (
  SELECT customer_id,
         DATE_DIFF(DATE '2026-09-08', MAX(order_date), DAY) AS recency_days,
         COUNT(*)         AS frequency,
         SUM(order_total) AS monetary
  FROM orders
  WHERE order_date >= DATE '2025-09-08'   -- fixed 12-month window
  GROUP BY customer_id
)
SELECT customer_id, recency_days, frequency, monetary,
       6 - NTILE(5) OVER (ORDER BY recency_days) AS r_score,  -- reversed: recent = 5
       NTILE(5) OVER (ORDER BY monetary)         AS m_score,
       CASE WHEN frequency >= 10 THEN 5
            WHEN frequency >=  6 THEN 4
            WHEN frequency >=  3 THEN 3
            WHEN frequency  =  2 THEN 2
            ELSE 1 END                           AS f_score
FROM base;
```

Two details that bite later: **reverse recency** (`6 - NTILE`), because low days-since-purchase is *good* and raw `NTILE` scores it 1; and **anchor the window to a fixed date**, not `CURRENT_DATE`, so a rerun of last month's segmentation reproduces last month's segments instead of today's.

## 10:04 - [ML & AI] PCA: Standardize First, or You Have Only Ranked Your Columns by Unit

PCA finds the directions of **maximum variance**. Variance carries units, and units are arbitrary — so PCA on unscaled data answers "which column has the biggest numbers?" rather than "which directions carry the structure?"

Take a table with `age` (std ≈ 12 years) and `salary` (std ≈ 30,000 dollars). Their variances are 144 and 900,000,000. PC1 comes back as essentially `1.000 × salary + 0.000013 × age`, and `explained_variance_ratio_` reports 0.99999 — a number that looks like a triumph and means nothing. Now store salary in thousands: variance drops to 900, age is suddenly competitive, and PC1 rotates. **If restating a column in different units changes your components, the components were about units.**

Standardize first, and do it inside the pipeline so the scaler and the PCA fit on training folds only:

```python
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.decomposition import PCA
from sklearn.linear_model import LogisticRegression

# n_components as a float = keep enough PCs to explain that much variance
pipe = make_pipeline(StandardScaler(), PCA(n_components=0.95), LogisticRegression())
pipe.fit(X_train, y_train)

pca = pipe.named_steps["pca"]
print(pca.n_components_, pca.explained_variance_ratio_.cumsum()[-1])
```

On standardized data every feature contributes variance 1, so total variance = number of features. A PC with eigenvalue below 1 explains less than one original column — a rough floor for "worth keeping."

Three things PCA does not do:

- **It is unsupervised.** It never sees `y`. A low-variance direction can be the one that predicts; dropping it to save 5% of variance can cost most of your signal. Verify by CV score, not by variance retained.
- **It does not give interpretable features.** PC1 is a dense mix of every column. Reporting "PC1 matters" tells a stakeholder nothing — use permutation importance on the original columns instead.
- **It rarely helps trees.** Gradient boosting splits on axis-aligned thresholds; rotating the axes into dense linear combinations usually makes those splits worse, not better. PCA pays off for distance- and gradient-based models — k-NN, k-means, SVMs, linear models — where correlated inputs and raw dimensionality genuinely hurt.

## 15:04 - [Crypto & Business] Salary Negotiation: Why the Base Number Is the Only One That Compounds

Most negotiation advice is about nerve. The useful part is arithmetic: base salary is the anchor that every other number keys off, so a one-time win compounds for as long as you stay.

**The compounding case.** Two offers, $145k and $160k, both with 3.5% annual raises. Over ten years:

| | Year 1 | Year 10 | 10-yr total |
|---|---|---|---|
| $145k offer | $145,000 | $197,620 | $1,701,052 |
| $160k offer | $160,000 | $218,064 | $1,877,023 |

The $15k gap becomes **$175,971** — because raises are percentages of a bigger base. A 5% 401(k) match adds ~$8,800 more in employer contributions on top, before any growth on it. And your next employer will ask what you make now, so the gap tends to travel with you.

**What actually moves the number.** Three mechanics matter more than script-reading:

1. **Don't name the first figure.** "I'd rather hear the band you've budgeted for this level" is a complete answer. If pressed, give a range whose *bottom* is your target — recruiters negotiate down from the number you say, and the bottom of your range is the only part they hear.
2. **Counter once, specifically, with a reason.** "Based on the scope we discussed and what I'm seeing for this level, $172k base would make this an easy yes" beats "can you do better?" A single concrete number with a rationale is the standard ask; it is not aggressive, and the offer is essentially never withdrawn over it.
3. **When base is genuinely capped, price the other levers.** Sign-on bonus, equity refresh, an early review date at a defined raise, title (which sets your band at the *next* company), remote flexibility, PTO. Ask which are flexible — the recruiter usually knows and will tell you.

**The asymmetry.** The downside of a polite counter is a "no" and a mildly awkward call. The upside, as above, is six figures. Very few decisions in a career have that payoff ratio.

## 19:02 - [Wildcard] Home Network Segmentation: Why Your Smart TV Should Not See Your NAS

A flat home network means every device can reach every other device. Your budget IP camera with firmware from 2019 sits on the same broadcast domain as your NAS, your homelab, and your laptop's SMB shares. One compromised device is a compromised network. VLANs fix this by splitting one physical switch into several isolated logical networks, with the router deciding what may cross between them.

**A workable four-VLAN layout:**

| VLAN | Purpose | Subnet | Internet | Can initiate to |
|---|---|---|---|---|
| 10 | Trusted (laptops, phones) | 10.0.10.0/24 | yes | all VLANs |
| 20 | Servers / NAS / homelab | 10.0.20.0/24 | yes | none |
| 30 | IoT (TV, plugs, cameras) | 10.0.30.0/24 | yes* | none |
| 40 | Guest | 10.0.40.0/24 | yes | none |

The rule that does the real work is default-deny between VLANs, plus one stateful allow from Trusted outward. Because the firewall is stateful, return traffic flows automatically — VLAN 20 never needs an inbound rule to answer VLAN 10. IoT gets internet but no lateral access, so a cheap camera cannot scan port 445 on your NAS.

**Three things that break on day one:**

- **mDNS/Bluetooth discovery.** Chromecast, AirPlay, and printers announce themselves via multicast, which does not cross subnets. Enable an mDNS reflector (Avahi on OPNsense/pfSense, "Multicast DNS" on UniFi) between Trusted and IoT only — never to Guest.
- **DHCP.** Each VLAN needs its own scope and gateway. A device pulling a 169.254.x.x address means the interface has no DHCP server bound.
- **Trunk vs access ports.** The uplink between router and switch must be a trunk carrying all tagged VLANs; device ports are access ports with a single untagged VLAN. Tagging the AP port but forgetting the router port is the classic "SSID works, no internet" symptom.

Verify from a Trusted client, then from an IoT one:

```
ping 10.0.20.10          # NAS: should answer from Trusted only
nmap -sn 10.0.20.0/24    # from IoT: should return zero hosts
```

Start with two VLANs — Trusted and IoT — and expand once discovery works. Segmentation you disable out of frustration protects nothing.

*IoT internet access is optional; many devices work fully local and can be blocked outbound entirely.*
