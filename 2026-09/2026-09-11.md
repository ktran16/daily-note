## 00:04 - [Data Engineering] Bridge Tables: The Weighting Factor That Stops Many-to-Many Double Counting

Kimball's star schema assumes every fact row points at exactly one row per dimension. Reality disagrees: a bank account has several owners, a support ticket carries several tags, a hospital claim lists several diagnoses. Join the dimension on directly and you fan out — one $1,000 account with three owners becomes three $1,000 rows, and your total deposits triple.

A **bridge table** absorbs the many-to-many. Its grain is one row per (group, member):

```sql
-- dim_account.owner_group_key -> bridge
create table bridge_account_owner (
  owner_group_key  bigint,
  customer_key     bigint,
  weighting_factor numeric(10,6)   -- sums to 1.0 within each group
);
-- group 42: three equal owners
-- (42, 101, 0.333333), (42, 102, 0.333333), (42, 103, 0.333334)
```

The weighting factor is the whole point. It gives you **two legitimate answers** to the same question, and you must pick deliberately:

```sql
-- Impact reporting: "how much balance does customer 101 touch?"
-- No weight. Does NOT sum to the grand total. That's correct, not a bug.
select c.customer_name, sum(f.balance)
from fct_account_balance f
join bridge_account_owner b on f.owner_group_key = b.owner_group_key
join dim_customer c        on b.customer_key = c.customer_key
group by 1;

-- Allocated reporting: "split balance across owners."
-- Sums exactly to the grand total.
select c.customer_name, sum(f.balance * b.weighting_factor)
from fct_account_balance f
join bridge_account_owner b on f.owner_group_key = b.owner_group_key
join dim_customer c        on b.customer_key = c.customer_key
group by 1;
```

Two rules keep this honest. First, the weights are a **business decision** — equal split, ownership percentage, revenue share — so document them in the model's YAML description, not in a stakeholder's head. Second, guard the invariant with a dbt singular test, because drifting weights silently distort every allocated metric:

```sql
-- tests/assert_bridge_weights_sum_to_one.sql
select owner_group_key, sum(weighting_factor) as total
from {{ ref('bridge_account_owner') }}
group by 1
having abs(sum(weighting_factor) - 1.0) > 0.0001
```

If a BI tool can't express the weighted join, build two marts — `_impact` and `_allocated` — and name them so nobody averages them together.

## 05:04 - [Data Analytics] Set Operations for Data Diffs: Why `EXCEPT` Says Two Tables Match When They Don't

The standard migration sign-off: rebuild a table on a new pipeline, then prove the output is identical.

```sql
select * from legacy.orders except select * from new.orders;   -- 0 rows
select * from new.orders except select * from legacy.orders;   -- 0 rows
```

Two empty results, ship it. This check is weaker than it looks, in three ways.

**1. `EXCEPT` deduplicates.** It is a *set* operator: both sides are collapsed to distinct rows before the difference. If legacy has one order row three times (a fan-out bug you were hoping to catch) and the new table has it once, both directions return zero rows. A 10,000,001-row table and a 10,000,003-row table pass cleanly. `EXCEPT ALL` keeps multiplicity and is the operator you actually want — available in Postgres, DuckDB and Spark, but not in Snowflake, where `MINUS`/`EXCEPT` are distinct-only.

**2. It matches columns by position, not name.** `select *` on two tables whose `shipped_at` and `ordered_at` columns were swapped during a refactor compares timestamp to timestamp without complaint. Always enumerate columns explicitly on both sides.

**3. It hides *where* the difference is.** Empty is a pass; non-empty tells you a row differs, not which column.

A portable diff that survives all three — group to counts, then full-outer-join on the key:

```sql
with l as (select order_id, status, amount, count(*) n from legacy.orders group by 1,2,3),
     r as (select order_id, status, amount, count(*) n from new.orders    group by 1,2,3)
select coalesce(l.order_id, r.order_id) as order_id,
       l.n as legacy_n, r.n as new_n,
       l.status, r.status, l.amount, r.amount
from l full outer join r
  on  l.order_id is not distinct from r.order_id
  and l.status   is not distinct from r.status
  and l.amount   is not distinct from r.amount
where l.n is distinct from r.n;
```

`IS NOT DISTINCT FROM` matters: `=` returns NULL when either side is NULL, so plain joins drop exactly the rows most likely to be wrong. `EXCEPT` already treats NULLs as equal — switching to a join silently changes that semantic unless you switch the comparison too.

Run the diff on a hashed subset first (`where mod(abs(hash(order_id)), 100) = 0`) to keep the full-table version for the final pass.
