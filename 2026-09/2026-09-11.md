# Daily Notes - 2026-09-11

## 00:04 - [Data Engineering] Bridge Tables: The Weighting Factor That Stops Many-to-Many Double Counting

Kimball's star schema assumes every fact row points at exactly one row per dimension. Reality disagrees: a bank account has several owners, a support ticket carries several tags, a hospital claim lists several diagnoses. Join the dimension on directly and you fan out — one $1,000 account with three owners becomes three $1,000 rows, and your total deposits triple.

A **bridge table** absorbs the many-to-many. Its grain is one row per (group, member):

```sql
-- dim_account.owner_group_key -> bridge
create table bridge_account_owner (
  owner_group_key  bigint,
  customer_key     bigint,
  weighting_factor numeric(10,6)   -- sums to 1.0 within each group
);
-- group 42: three equal owners
-- (42, 101, 0.333333), (42, 102, 0.333333), (42, 103, 0.333334)
```

The weighting factor is the whole point. It gives you **two legitimate answers** to the same question, and you must pick deliberately:

```sql
-- Impact reporting: "how much balance does customer 101 touch?"
-- No weight. Does NOT sum to the grand total. That's correct, not a bug.
select c.customer_name, sum(f.balance)
from fct_account_balance f
join bridge_account_owner b on f.owner_group_key = b.owner_group_key
join dim_customer c        on b.customer_key = c.customer_key
group by 1;

-- Allocated reporting: "split balance across owners."
-- Sums exactly to the grand total.
select c.customer_name, sum(f.balance * b.weighting_factor)
from fct_account_balance f
join bridge_account_owner b on f.owner_group_key = b.owner_group_key
join dim_customer c        on b.customer_key = c.customer_key
group by 1;
```

Two rules keep this honest. First, the weights are a **business decision** — equal split, ownership percentage, revenue share — so document them in the model's YAML description, not in a stakeholder's head. Second, guard the invariant with a dbt singular test, because drifting weights silently distort every allocated metric:

```sql
-- tests/assert_bridge_weights_sum_to_one.sql
select owner_group_key, sum(weighting_factor) as total
from {{ ref('bridge_account_owner') }}
group by 1
having abs(sum(weighting_factor) - 1.0) > 0.0001
```

If a BI tool can't express the weighted join, build two marts — `_impact` and `_allocated` — and name them so nobody averages them together.
