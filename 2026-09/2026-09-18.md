## 00:03 - [Data Engineering] `incremental_predicates`: Why Your "Incremental" Model Still Scans the Whole Table

An incremental model with `merge` feels cheap — you filter the source to a few hours of new rows and expect a few-hour bill. Then the run takes 40 minutes on a 3 TB table. The filter you wrote applies to the *source* side; the merge still has to match those rows against the **entire destination table**.

dbt's merge compiles to roughly:

```sql
merge into analytics.events as DBT_INTERNAL_DEST
using (select ... from source where occurred_at > (select max(occurred_at) from ...)) as DBT_INTERNAL_SOURCE
    on DBT_INTERNAL_DEST.event_id = DBT_INTERNAL_SOURCE.event_id
when matched then update set ...
when not matched then insert ...
```

Nothing in that `on` clause mentions a partition or clustering column, so the warehouse cannot prune the target. It scans every micro-partition of `events` looking for matching `event_id`s.

`incremental_predicates` injects extra conditions into the `on` clause, scoped to the destination:

```sql
{{ config(
    materialized = 'incremental',
    incremental_strategy = 'merge',
    unique_key = 'event_id',
    incremental_predicates = [
        "DBT_INTERNAL_DEST.occurred_at >= dateadd(day, -3, current_date)"
    ],
    cluster_by = ['occurred_at']
) }}
```

Now the target scan is limited to three days of partitions. On a well-clustered table this routinely turns a full-table merge into a small one — the same query, one or two orders of magnitude less data read.

**The correctness rule:** the predicate must cover every row the incoming batch could possibly match. If a late-arriving event carries `occurred_at` from 10 days ago, the merge won't see the existing row, `when not matched` fires, and you get a **duplicate** — silently, since `unique_key` is not a database constraint. So size the window to your real late-arrival tail (check `max(loaded_at - occurred_at)` in your source), not to what looks fast, and re-check it after upstream changes.

Two practical notes: use the literal alias `DBT_INTERNAL_DEST` (dbt substitutes the real relation), and always `--full-refresh` after widening or narrowing the window so the table isn't left carrying dupes from the old bound.

## 05:03 - [Data Analytics] Tableau LOD Expressions: Why `{FIXED}` Ignores the Filter You Just Applied

Level-of-Detail expressions let a calculation aggregate at a grain other than the viz. The bug that eats hours is that the three flavors run at **different points in Tableau's order of operations**:

```
extract filters → context filters → FIXED → dimension filters
  → INCLUDE / EXCLUDE → measure filters → table calcs
```

`FIXED` is computed *before* dimension filters. So a filter on the sheet does not reach it.

**The failure.** You want average customer lifetime spend by region:

```
Avg Customer Value = AVG({ FIXED [Customer ID] : SUM([Sales]) })
```

Filter the sheet to Region = West. The per-customer totals were already computed across *all* regions, so a customer who spent $400 in West and $1,000 in East contributes $1,400 to West's average. On a 10k-customer dataset where ~18% of customers buy cross-region, this reported $1,840 against a true West-only figure of $1,120 — inflated 64%, and it barely moved when the region filter changed.

**That's the tell:** if a number refuses to respond to a dimension filter, suspect `FIXED`.

**Three fixes, in order of preference:**

1. **Use `INCLUDE`** — it runs *after* dimension filters, so it just works:
   `AVG({ INCLUDE [Customer ID] : SUM([Sales]) })`
2. **Add the dimension to the FIXED key** — `{ FIXED [Region], [Customer ID] : SUM([Sales]) }` makes the grain explicit rather than relying on filter timing.
3. **Promote the filter to a context filter** (right-click → Add to Context). This works, but it materializes a temp table per context change and slows large workbooks — reach for it last.

**Where `FIXED` is the right tool:** de-duplicating a fan-out. If orders are joined to line items, `SUM([Order Amount])` counts each order once per line. Instead:

```
SUM({ FIXED [Order ID] : MIN([Order Amount]) })
```

Here you *want* immunity to the viz grain — which is exactly what `FIXED` sells.

In SQL terms, `FIXED` is a windowed aggregate over the unfiltered source; `INCLUDE` is one over the filtered set. Ask which one you meant before writing the brace.
