## 00:03 - [Data Engineering] `incremental_predicates`: Why Your "Incremental" Model Still Scans the Whole Table

An incremental model with `merge` feels cheap — you filter the source to a few hours of new rows and expect a few-hour bill. Then the run takes 40 minutes on a 3 TB table. The filter you wrote applies to the *source* side; the merge still has to match those rows against the **entire destination table**.

dbt's merge compiles to roughly:

```sql
merge into analytics.events as DBT_INTERNAL_DEST
using (select ... from source where occurred_at > (select max(occurred_at) from ...)) as DBT_INTERNAL_SOURCE
    on DBT_INTERNAL_DEST.event_id = DBT_INTERNAL_SOURCE.event_id
when matched then update set ...
when not matched then insert ...
```

Nothing in that `on` clause mentions a partition or clustering column, so the warehouse cannot prune the target. It scans every micro-partition of `events` looking for matching `event_id`s.

`incremental_predicates` injects extra conditions into the `on` clause, scoped to the destination:

```sql
{{ config(
    materialized = 'incremental',
    incremental_strategy = 'merge',
    unique_key = 'event_id',
    incremental_predicates = [
        "DBT_INTERNAL_DEST.occurred_at >= dateadd(day, -3, current_date)"
    ],
    cluster_by = ['occurred_at']
) }}
```

Now the target scan is limited to three days of partitions. On a well-clustered table this routinely turns a full-table merge into a small one — the same query, one or two orders of magnitude less data read.

**The correctness rule:** the predicate must cover every row the incoming batch could possibly match. If a late-arriving event carries `occurred_at` from 10 days ago, the merge won't see the existing row, `when not matched` fires, and you get a **duplicate** — silently, since `unique_key` is not a database constraint. So size the window to your real late-arrival tail (check `max(loaded_at - occurred_at)` in your source), not to what looks fast, and re-check it after upstream changes.

Two practical notes: use the literal alias `DBT_INTERNAL_DEST` (dbt substitutes the real relation), and always `--full-refresh` after widening or narrowing the window so the table isn't left carrying dupes from the old bound.

## 05:03 - [Data Analytics] Tableau LOD Expressions: Why `{FIXED}` Ignores the Filter You Just Applied

Level-of-Detail expressions let a calculation aggregate at a grain other than the viz. The bug that eats hours is that the three flavors run at **different points in Tableau's order of operations**:

```
extract filters → context filters → FIXED → dimension filters
  → INCLUDE / EXCLUDE → measure filters → table calcs
```

`FIXED` is computed *before* dimension filters. So a filter on the sheet does not reach it.

**The failure.** You want average customer lifetime spend by region:

```
Avg Customer Value = AVG({ FIXED [Customer ID] : SUM([Sales]) })
```

Filter the sheet to Region = West. The per-customer totals were already computed across *all* regions, so a customer who spent $400 in West and $1,000 in East contributes $1,400 to West's average. On a 10k-customer dataset where ~18% of customers buy cross-region, this reported $1,840 against a true West-only figure of $1,120 — inflated 64%, and it barely moved when the region filter changed.

**That's the tell:** if a number refuses to respond to a dimension filter, suspect `FIXED`.

**Three fixes, in order of preference:**

1. **Use `INCLUDE`** — it runs *after* dimension filters, so it just works:
   `AVG({ INCLUDE [Customer ID] : SUM([Sales]) })`
2. **Add the dimension to the FIXED key** — `{ FIXED [Region], [Customer ID] : SUM([Sales]) }` makes the grain explicit rather than relying on filter timing.
3. **Promote the filter to a context filter** (right-click → Add to Context). This works, but it materializes a temp table per context change and slows large workbooks — reach for it last.

**Where `FIXED` is the right tool:** de-duplicating a fan-out. If orders are joined to line items, `SUM([Order Amount])` counts each order once per line. Instead:

```
SUM({ FIXED [Order ID] : MIN([Order Amount]) })
```

Here you *want* immunity to the viz grain — which is exactly what `FIXED` sells.

In SQL terms, `FIXED` is a windowed aggregate over the unfiltered source; `INCLUDE` is one over the filtered set. Ask which one you meant before writing the brace.

## 10:03 - [ML & AI] Warmup and Cosine Decay: Why the First 2% of Steps Decides the Run

A training run that diverges at step ~200 and a run that plateaus 1.5 points short usually have the same root cause: the learning rate schedule, not the architecture.

**Why warmup exists.** Adam divides each update by `sqrt(v)`, the running second moment of the gradient. Both `m` and `v` start at zero, so in the first few dozen steps `v` is estimated from almost no samples and is wildly noisy. Bias correction fixes the *expectation*, not the *variance* — so early updates are near-full-size steps in a direction chosen by a handful of minibatches, from a random initialization. One bad step blows up the activations, and with a transformer's residual stream that spike often never recovers. Warmup keeps the step size small until `v` has stabilized.

**The schedule** (linear warmup over `W` steps, cosine decay over the remaining `T - W`):

```
lr(t) = lr_max * t / W                                      t < W
lr(t) = lr_min + 0.5*(lr_max - lr_min)*(1 + cos(pi*(t-W)/(T-W)))   t >= W
```

```python
import math
from torch.optim.lr_scheduler import LambdaLR

def schedule(W, T, floor=0.1):
    def f(t):                      # returns a MULTIPLIER on lr_max
        if t < W:
            return t / W
        p = (t - W) / max(1, T - W)
        return floor + (1 - floor) * 0.5 * (1 + math.cos(math.pi * p))
    return f

sched = LambdaLR(opt, schedule(W=2000, T=100_000))
```

With `lr_max=3e-4`, `W=2000`, `T=100_000`: step 500 → `7.5e-5`; step 2000 → `3e-4` (the peak); step 51,000 (halfway through decay) → `1.65e-4`; step 100,000 → `3e-5`.

**Three bugs that cost more than any hyperparameter search:**

1. **`T` is not your real step count.** Set `T` too high and you stop mid-curve at a high LR — the model never anneals, and you lose the final convergence that cosine's flat tail buys. Set it too low and you burn compute at the floor. `T = steps_per_epoch * epochs`, computed, not guessed.
2. **Stepping per epoch instead of per batch.** `sched.step()` belongs next to `opt.step()`. Per-epoch stepping makes `W=2000` mean 2000 epochs and the LR never leaves warmup.
3. **Resuming without scheduler state.** `torch.save` the scheduler alongside the optimizer, or every restart replays warmup from zero and re-shocks a converged model.

Rules of thumb: pretraining, `W` ≈ 1–5% of `T`; fine-tuning, a few hundred steps is plenty. If loss spikes early, lengthen warmup before lowering `lr_max` — you usually want the peak, just later.

## 15:04 - [Crypto & Business] Bookings, Billings, Revenue, ARR: Four Numbers People Call "Sales"

Four different numbers get reported as "how much we sold." They can differ by 3x on the same contract. Conflating them is how a board deck says $2M and the audited statement says $600K.

**One contract, four answers.** Feb 1: a customer signs 3 years at $120K/year, total $360K, and prepays 12 months upfront.

| Number | Value | What it measures |
|---|---|---|
| Bookings (TCV) | $360K | Total value committed, signed |
| Bookings (ACV) | $120K | Annualized contract value |
| Billings | $120K | Invoiced this period |
| Revenue (GAAP) | $110K | Recognized $10K/mo, Feb–Dec |
| ARR | $120K | Run rate at a point in time |
| Deferred revenue | $10K | Billed but not yet earned (a liability) |

Bookings lead, billings follow, revenue lags, ARR is a snapshot.

**Where it goes wrong:**

1. **TCV quoted as revenue.** A 3-year deal inflates the headline 3x versus ACV. Always ask which. "We booked $2M" on 3-year terms is ~$667K of ARR.
2. **A billings spike that isn't growth.** Push customers from monthly to annual prepay and billings jump hard in one quarter while ARR is flat — you pulled cash forward, you didn't sell more. The next quarter looks terrible by comparison.
3. **ARR on usage-based revenue is an estimate.** Annualizing a trailing month (×12) bakes in seasonality; a Black Friday month grosses up the whole year. Annualizing a trailing quarter (×4) is steadier.
4. **Deferred revenue read as a win.** It's an obligation — work owed to customers who already paid.

**Two diligence checks:** deferred revenue growing much faster than revenue usually means a billing-terms change, not demand. And revenue growing while ARR is flat means you're recognizing a backlog you already sold.

Ask "bookings, billings, revenue, or ARR?" before reacting to any growth number.

## 19:02 - [PC Hardware] UPS Sizing: VA Is Not Watts, and Active PFC Hates Stepped Sine

A UPS is the one component people buy by the number on the front of the box. That number is **VA (apparent power)**, not watts, and the gap between them is where the mistakes live.

**VA vs W.** Consumer UPS units advertise VA and derate to watts by a power factor, usually 0.6. So a "1500VA" unit is a **900W** unit. Size on the watts figure only. And size against *measured* draw, not nameplate: plug a Kill-A-Watt inline, or read the PSU's own telemetry, and note the peak under load — not idle.

| System | Idle | Gaming/render load |
|---|---|---|
| Mid-range PC + 1 monitor | 70–110W | 350–500W |
| High-end PC (300W+ GPU) | 110–150W | 600–800W |
| Homelab NAS, 6 spinners | 55–75W | 140W (spin-up surge) |

**Runtime is brutally nonlinear.** Batteries follow Peukert's law: doubling the load more than halves the runtime. That 900W unit gives roughly 12–15 minutes at 200W, but only 3–4 minutes at 600W. A UPS is for a *clean shutdown and a ride-through of brownouts*, not for finishing your raid.

**The waveform trap.** On battery, cheap standby and line-interactive units output a stepped/simulated sine wave. Every 80 Plus PSU uses **active PFC**, and its input stage can misinterpret those square edges — you get loud buzzing, a shutdown on transfer, or a UPS that overload-trips instantly. Symptom: the PC dies the moment the UPS switches to battery, even at 25% load. Fix: buy a **pure sine wave** unit (line-interactive PSW or online double-conversion). This is the spec worth paying for.

**Automate the shutdown**, or the UPS only bought you noise:

```bash
sudo apt install nut          # or apcupsd
sudo nut-scanner -U           # detect the USB UPS
upsc myups                    # battery.charge, ups.load, battery.runtime
```

Trigger shutdown at **50% charge or 5 minutes remaining**, not 10% — graceful shutdown of a NAS with dirty write cache takes longer than you think, and battery capacity fades ~30% by year three. Replace cells every 3–5 years; a UPS with a dead battery is an expensive power strip.
