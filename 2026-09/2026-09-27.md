## 00:04 - [Data Engineering] dbt Source Freshness: The Check That Tells You It's Not Your Model's Fault

Most "the dashboard is wrong" incidents aren't broken SQL — the upstream load never landed. `dbt source freshness` catches that before your models run.

Declare thresholds relative to the source's actual load cadence, not to what feels acceptable:

```yaml
# models/staging/_sources.yml
sources:
  - name: stripe
    database: raw
    freshness:
      warn_after: {count: 6, period: hour}
      error_after: {count: 26, period: hour}   # daily load + 2h slack
    loaded_at_field: _ingested_at
    tables:
      - name: charges
        # narrow the max() scan on a big partitioned table
        loaded_at_field: _ingested_at
        filter: _ingested_at >= dateadd('day', -3, current_timestamp())
      - name: coupons
        freshness: null    # reference data; opt out
```

Two ways dbt measures recency, and the difference matters:

- **`loaded_at_field`** — dbt issues `select max(_ingested_at)`. Measures *data* recency. Costs a query, so use `filter` to keep it from scanning history.
- **Omit it** — dbt reads warehouse metadata (Snowflake, BigQuery, Redshift, Databricks). Free, but it reports the table's *last write time*. A pipeline that runs on schedule and writes zero rows looks perfectly fresh. dbt 1.9+ adds `loaded_at_query` when you need a custom expression instead.

A daily 02:00 load is legitimately 23 hours old at 01:00. Threshold against cadence plus slack, or you'll train the team to ignore warnings.

The real payoff is orchestration. `dbt source freshness` writes `sources.json`; comparing against the previous run lets you build only what actually has new data:

```bash
dbt source freshness                      # exit 1 on error_after
dbt build --select source_status:fresher+ --state ./prod-artifacts
```

Put the freshness check first in the DAG and let a non-zero exit gate the run. Rebuilding marts on stale sources doesn't produce an error — it silently republishes yesterday's numbers with today's timestamp, which is far more expensive to debug.

## 05:04 - [Data Analytics] Multiple Comparisons: The 8 Metrics That Guarantee You a Winner

A single test at α = 0.05 has a 5% false-positive rate. That guarantee evaporates the moment you look at more than one thing. Two variants against control, ten metrics on the dashboard — that's 20 tests, and if all 20 nulls are true:

```
P(at least one "significant" result) = 1 - 0.95^20 = 0.6415
```

64%. You will almost certainly find something to celebrate in an experiment that did nothing.

The two corrections behave very differently. Bonferroni divides α by the number of tests (0.05/8 = 0.00625) and controls the chance of *any* false positive — safe, but it throws away power. Benjamini-Hochberg controls the *false discovery rate*: the expected share of your rejections that are wrong. That's usually the quantity an analyst actually cares about.

```python
def bh_adjust(pvals):
    m = len(pvals)
    order = sorted(range(m), key=lambda i: pvals[i])
    adj, running = [0.0] * m, 1.0
    for rank in range(m, 0, -1):            # walk from largest p downward
        i = order[rank - 1]
        running = min(running, pvals[i] * m / rank)
        adj[i] = running
    return adj

p = [0.001, 0.008, 0.021, 0.038, 0.041, 0.12, 0.30, 0.55]
bh_adjust(p)
# [0.008, 0.032, 0.056, 0.0656, 0.0656, 0.16, 0.3429, 0.55]
```

Same eight p-values, three verdicts at α = 0.05:

| Method | Discoveries |
|---|---|
| Uncorrected | 5 |
| Benjamini-Hochberg | 2 |
| Bonferroni | 1 |

Three of those five "wins" do not survive contact with the correction. (`statsmodels.stats.multitest.multipletests(p, alpha=0.05, method='fdr_bh')` gives the same numbers.)

The practical protocol matters more than the arithmetic:

- **Pre-register one primary metric.** It is tested at full α, uncorrected. This is the decision metric.
- **Secondary metrics get BH.** They are hypothesis generators, not ship criteria — label them "exploratory" in the readout.
- **Do not correct guardrails.** Correction reduces sensitivity, and a guardrail exists precisely to be over-sensitive to harm. Raising the bar on your latency and refund-rate checks is backwards.

The failure mode isn't bad math, it's an unwritten metric list. If the primary metric was chosen after seeing the results, no correction can save the readout.
