## 00:04 - [Data Engineering] dbt Source Freshness: The Check That Tells You It's Not Your Model's Fault

Most "the dashboard is wrong" incidents aren't broken SQL — the upstream load never landed. `dbt source freshness` catches that before your models run.

Declare thresholds relative to the source's actual load cadence, not to what feels acceptable:

```yaml
# models/staging/_sources.yml
sources:
  - name: stripe
    database: raw
    freshness:
      warn_after: {count: 6, period: hour}
      error_after: {count: 26, period: hour}   # daily load + 2h slack
    loaded_at_field: _ingested_at
    tables:
      - name: charges
        # narrow the max() scan on a big partitioned table
        loaded_at_field: _ingested_at
        filter: _ingested_at >= dateadd('day', -3, current_timestamp())
      - name: coupons
        freshness: null    # reference data; opt out
```

Two ways dbt measures recency, and the difference matters:

- **`loaded_at_field`** — dbt issues `select max(_ingested_at)`. Measures *data* recency. Costs a query, so use `filter` to keep it from scanning history.
- **Omit it** — dbt reads warehouse metadata (Snowflake, BigQuery, Redshift, Databricks). Free, but it reports the table's *last write time*. A pipeline that runs on schedule and writes zero rows looks perfectly fresh. dbt 1.9+ adds `loaded_at_query` when you need a custom expression instead.

A daily 02:00 load is legitimately 23 hours old at 01:00. Threshold against cadence plus slack, or you'll train the team to ignore warnings.

The real payoff is orchestration. `dbt source freshness` writes `sources.json`; comparing against the previous run lets you build only what actually has new data:

```bash
dbt source freshness                      # exit 1 on error_after
dbt build --select source_status:fresher+ --state ./prod-artifacts
```

Put the freshness check first in the DAG and let a non-zero exit gate the run. Rebuilding marts on stale sources doesn't produce an error — it silently republishes yesterday's numbers with today's timestamp, which is far more expensive to debug.

## 05:04 - [Data Analytics] Multiple Comparisons: The 8 Metrics That Guarantee You a Winner

A single test at α = 0.05 has a 5% false-positive rate. That guarantee evaporates the moment you look at more than one thing. Two variants against control, ten metrics on the dashboard — that's 20 tests, and if all 20 nulls are true:

```
P(at least one "significant" result) = 1 - 0.95^20 = 0.6415
```

64%. You will almost certainly find something to celebrate in an experiment that did nothing.

The two corrections behave very differently. Bonferroni divides α by the number of tests (0.05/8 = 0.00625) and controls the chance of *any* false positive — safe, but it throws away power. Benjamini-Hochberg controls the *false discovery rate*: the expected share of your rejections that are wrong. That's usually the quantity an analyst actually cares about.

```python
def bh_adjust(pvals):
    m = len(pvals)
    order = sorted(range(m), key=lambda i: pvals[i])
    adj, running = [0.0] * m, 1.0
    for rank in range(m, 0, -1):            # walk from largest p downward
        i = order[rank - 1]
        running = min(running, pvals[i] * m / rank)
        adj[i] = running
    return adj

p = [0.001, 0.008, 0.021, 0.038, 0.041, 0.12, 0.30, 0.55]
bh_adjust(p)
# [0.008, 0.032, 0.056, 0.0656, 0.0656, 0.16, 0.3429, 0.55]
```

Same eight p-values, three verdicts at α = 0.05:

| Method | Discoveries |
|---|---|
| Uncorrected | 5 |
| Benjamini-Hochberg | 2 |
| Bonferroni | 1 |

Three of those five "wins" do not survive contact with the correction. (`statsmodels.stats.multitest.multipletests(p, alpha=0.05, method='fdr_bh')` gives the same numbers.)

The practical protocol matters more than the arithmetic:

- **Pre-register one primary metric.** It is tested at full α, uncorrected. This is the decision metric.
- **Secondary metrics get BH.** They are hypothesis generators, not ship criteria — label them "exploratory" in the readout.
- **Do not correct guardrails.** Correction reduces sensitivity, and a guardrail exists precisely to be over-sensitive to harm. Raising the bar on your latency and refund-rate checks is backwards.

The failure mode isn't bad math, it's an unwritten metric list. If the primary metric was chosen after seeing the results, no correction can save the readout.

## 10:02 - [ML & AI] Macro vs Micro vs Weighted F1: The Average That Hides Your Worst Class

Multiclass `f1_score` requires an `average=` argument, and the three common choices can differ by 35 points on the same predictions. Pick carelessly and your report says the model works while the class you built it for is broken.

A 3-class model, 1000 samples, rows = true / cols = predicted:

```
        pred A  pred B  pred C   support
true A     880      15       5       900
true B      40      38       2        80
true C      14       3       3        20
```

Per-class:

| class | P | R | F1 | support |
|---|---|---|---|---|
| A | 0.942 | 0.978 | **0.960** | 900 |
| B | 0.679 | 0.475 | **0.559** | 80 |
| C | 0.300 | 0.150 | **0.200** | 20 |

Now the three averages:

- **micro** — pool counts across classes first: TP = 921, FP = FN = 79, so P = R = F1 = **0.921**. In single-label multiclass every error is simultaneously one FP and one FN, so micro-F1 is *identically accuracy*. It carries no information accuracy didn't.
- **weighted** — mean of per-class F1 weighted by support: (900·0.960 + 80·0.559 + 20·0.200)/1000 = **0.912**. Class A holds 90% of the weight, so this tracks accuracy too.
- **macro** — unweighted mean: (0.960 + 0.559 + 0.200)/3 = **0.573**. Every class votes once, so class C's collapse is visible.

```python
f1_score(y_true, y_pred, average='micro')     # 0.921  == accuracy
f1_score(y_true, y_pred, average='weighted')  # 0.912
f1_score(y_true, y_pred, average='macro')     # 0.573
```

A gotcha worth internalizing: **macro-F1 is not the F1 of the macro averages.** Harmonic mean of macro-P (0.640) and macro-R (0.534) is 0.583, not 0.573. F1 is non-linear, so averaging order changes the answer — don't recompute it from a reported P/R pair.

Practical rules: report `classification_report` per class always; use **macro** when rare classes matter as much as common ones (defect types, intent classification, error taxonomies); use **weighted** only when you genuinely care about a random sample's chance of being right; never report micro for single-label problems — say "accuracy" and stop dressing it up. In **multilabel** settings micro is no longer accuracy and is a legitimate choice, since it weights each positive label equally across a variable number of labels per row.

## 15:03 - [Crypto & Business] Solo 401(k) vs SEP-IRA: Why the Same $120K of Freelance Profit Shelters $24,500 More in One of Them

If you consult, freelance, or sell a productized service, this is the highest-return hour of admin you will do all year. Both accounts take pre-tax dollars off your Schedule C profit. They do not shelter remotely the same amount.

**The worked example.** Sole proprietor, $120,000 net profit (Schedule C line 31), no employees, under 50.

```
Net earnings         120,000 × 0.9235 = 110,820
SE tax               110,820 × 0.153  =  16,955   (under the 184,500 SS wage base)
Deductible half                       =   8,478
Adjusted profit      120,000 − 8,478  = 111,522
Employer share       111,522 × 20%    =  22,304
```

That 20% is the part people get wrong: the "25% of compensation" rule becomes **20% of adjusted profit** for a sole proprietor, because your own contribution reduces the compensation base it's computed on.

| | 2026 shelter |
|---|---|
| SEP-IRA | employer only → **$22,304** |
| Solo 401(k) | $24,500 deferral + $22,304 employer → **$46,804** |

Same profit, same paperwork burden, **$24,500 more deductible** — roughly $5,900 in federal tax at a 24% marginal rate. Both sit far under the $72,000 combined cap; the SEP simply has no employee-deferral bucket to fill. Catch-up at 50+ adds $8,000, and only the 401(k) offers it.

Three mechanics that decide it in practice:

- **Deadlines differ.** A SEP can be opened *and* funded up to your filing deadline including extensions. A Solo 401(k) generally must exist by Dec 31 to take deferrals — SECURE 2.0 relaxed this only for a sole proprietor's first plan year.
- **Roth.** The 401(k) accepts Roth deferrals. SEPs are traditional in practice.
- **Backdoor Roth.** SEP-IRA balances count in the pro-rata calculation and can tax your conversions. 401(k) balances don't. This alone pushes many high earners to the 401(k).

The 401(k) breaks if you hire a non-spouse employee, and needs Form 5500-EZ past $250,000 in assets. Below that, it's a one-page annual filing of nothing.

## 19:02 - [PC Hardware] Mouse and Keyboard Latency: Where the Milliseconds Actually Go

Peripherals are marketed on polling rate and DPI. Neither is usually your bottleneck.

**The latency budget.** Click-to-photon on a typical 144 Hz setup is 30–60 ms. Roughly where it goes:

| Stage | Typical | Notes |
|---|---|---|
| Mouse sensor + firmware | 1–3 ms | Sensor processing, independent of polling |
| USB polling wait | 0.5 ms avg @ 1000 Hz | Half the polling interval |
| Game render queue | 7–30 ms | 1–3 buffered frames — the big one |
| Display scanout + panel response | 7–12 ms @ 144 Hz | Frame time plus pixel transition |

Polling is the smallest term in the budget. Moving 1000 Hz → 8000 Hz saves about 0.44 ms on average and costs real CPU time: the driver services 8× the interrupts, which has measured 2–6% FPS loss in CPU-limited scenarios. By contrast, enabling NVIDIA Reflex or AMD Anti-Lag drops queued frames and saves 10–20 ms — an order of magnitude more, for free. Fix the pipeline before you buy the 8K dongle.

**DPI does not affect latency.** CPI is just a sensitivity multiplier. What matters is staying under the sensor's max tracking speed (modern sensors do 500–750 IPS, well beyond any human flick) and turning off OS-level acceleration and smoothing. Verify the report rate you actually get rather than trusting the box:

```bash
sudo evhz                      # measured Hz per input device
cat /proc/bus/input/devices    # confirm which device is which
```

Stability beats peak. A mouse advertising 1000 Hz that intermittently drops to 500 produces visible microstutter that a rock-steady 500 Hz does not.

**On keyboards, debounce is the real number.** Metal contacts bounce, so firmware ignores further input for a debounce window — commonly 5 ms, and often fixed with no way to change it. That single setting dwarfs polling interval. Hall-effect and optical switches have no contact bounce, so they operate in the 0.1–1 ms range and expose adjustable actuation depth (roughly 0.1–3.4 mm) plus rapid trigger, which re-arms on a small upward movement instead of at a fixed reset point.

**Wireless is not the penalty people assume.** Proprietary 2.4 GHz dongles land within ~1 ms of wired, and a few beat it. Bluetooth is the one to avoid for input: it adds roughly 10–25 ms with poor consistency.

Buy peripherals for shape, weight, and switch feel. Buy latency back in the render pipeline.
