## 00:03 - [Data Engineering] Junk Dimensions: Collapsing a Dozen Flags Into One Surrogate Key

Every fact table accumulates orphan attributes: `is_gift`, `is_expedited`, `payment_status`, `order_channel`, `is_first_order`. Each has two to six values. None deserves its own dimension table — a `dim_is_gift` with two rows is absurd — but leaving them all as columns on the fact bloats the row and scatters low-cardinality filters across the widest table you own.

A **junk dimension** is Kimball's answer: take the cross-product of those low-cardinality flags, store each distinct combination once, and put a single foreign key on the fact.

```sql
-- dim_order_junk.sql
{{ config(materialized='table') }}

with combos as (
    select distinct
        coalesce(is_gift, false)                    as is_gift,
        coalesce(is_expedited, false)               as is_expedited,
        coalesce(payment_status, 'unknown')         as payment_status,
        coalesce(order_channel, 'unknown')          as order_channel
    from {{ ref('stg_orders') }}
)
select
    {{ dbt_utils.generate_surrogate_key(
        ['is_gift', 'is_expedited', 'payment_status', 'order_channel']
    ) }} as order_junk_key,
    *,
    -- decode columns: what BI users actually want on a filter shelf
    case when is_gift then 'Gift' else 'Standard' end as gift_label
from combos
```

The fact joins back on the same hashed key, so no lookup is needed at load time:

```sql
select
    o.order_id,
    {{ dbt_utils.generate_surrogate_key(
        ['o.is_gift', 'o.is_expedited', 'o.payment_status', 'o.order_channel']
    ) }} as order_junk_key,
    o.order_total
from {{ ref('stg_orders') }} o
```

**Sizing is the whole decision.** 2 × 2 × 4 × 5 = 80 rows — trivial. Add one 10,000-value field and you have a fact table with extra steps. Two rules keep it honest:

- **Cardinality ceiling:** only combine attributes with a handful of values each; target a few thousand rows maximum.
- **Build from observed combinations, not the full cross-product.** `select distinct` from the source gives you the ~30 combos that actually occur instead of all 80 theoretical ones.

Generate the surrogate key by hashing the attributes rather than a sequence — it stays deterministic across full refreshes, so a rebuilt dimension never orphans existing facts.

Guard it with a uniqueness test and a row-count ceiling that fails loudly the day someone slips a high-cardinality column in:

```yaml
models:
  - name: dim_order_junk
    tests:
      - dbt_utils.expression_is_true:
          expression: "(select count(*) from {{ this }}) < 5000"
    columns:
      - name: order_junk_key
        tests: [unique, not_null]
```

The payoff is narrower facts, one join instead of five filter columns, and a natural home for the decode labels BI tools need.

## 05:03 - [Data Analytics] Sample Size and MDE: Run the Number Before You Launch, Not After

Most A/B tests don't fail on analysis — they fail because they were never big enough to answer the question. A flat result then gets read as "no effect" when it actually means "we couldn't have seen it."

For a two-arm proportion test at α = 0.05 two-sided and 80% power:

```
n per arm = 2 · (z_0.975 + z_0.80)² · p̄(1−p̄) / δ²
          = 2 · (1.960 + 0.842)² · p̄(1−p̄) / δ²
          = 15.70 · p̄(1−p̄) / δ²      (the z term squares to 7.85)
```

```python
import math
K = (1.959964 + 0.841621) ** 2          # 7.849

def n_per_arm(baseline, abs_lift):
    p = baseline + abs_lift / 2
    return 2 * K * p * (1 - p) / abs_lift**2

def mde(baseline, n):                    # invert it
    p = baseline
    return math.sqrt(2 * K * p * (1 - p) / n)

n_per_arm(0.05, 0.0025)   # 5% baseline, +5% relative -> 122,125 per arm
mde(0.05, 70_000)         # 0.0033 abs = 6.6% relative
```

At a 5% baseline conversion, detecting a **5% relative** lift (0.25 pp absolute) needs ~122k users *per arm* — 244k total. At 10k eligible visitors/day that is 24 days, not "we'll check Friday."

Two habits that make this useful:

**Invert it.** The more honest question isn't "how long for my hoped-for lift" but "given the traffic I actually have, what's the smallest effect I can see?" Two weeks at 10k/day is 70k per arm → an MDE of 6.6% relative. If the team wouldn't ship for a 6% lift anyway, the test is pointless before it starts.

**Watch the split.** Power is driven by the harmonic mean, `2/(1/n₁ + 1/n₂)`, not the total. Split 100k users 50/50 and you have the power of 50k per arm. Split it 90/10 and you have the power of **18k per arm** — a cautious rollout costs roughly two-thirds of your sensitivity.

Compute δ from what's worth shipping, and quote lifts as absolute or relative explicitly — conflating the two is the most common off-by-20× in this formula.

## 10:02 - [ML & AI] Point-in-Time Joins: The Feature Store's Actual Job

Most feature stores are sold as a cache. Their real job is stopping a leak that unit tests never catch: joining a feature's *current* value onto a *historical* label.

The failure looks like this. You have a churn label for customer 1 dated `2026-03-01`, and a `customer_features` table refreshed nightly. You `LEFT JOIN ... ON entity_id`, grab `orders_90d = 47`, and train. But 47 is today's value. On 2026-03-01 that customer had 12 orders. The model is reading the future, offline AUC jumps, and production quietly reverts to the mean.

The fix is an **as-of join**: for each label row, take the last feature value whose timestamp is at or before the event.

```python
import pandas as pd

labels = pd.DataFrame({
    "entity_id": [1, 1, 2],
    "event_ts":  pd.to_datetime(["2026-03-01", "2026-06-01", "2026-03-01"]),
    "churned":   [0, 1, 0],
})
features = pd.DataFrame({
    "entity_id":  [1, 1, 1, 2],
    "feature_ts": pd.to_datetime(["2026-02-25", "2026-03-15", "2026-05-28", "2026-02-20"]),
    "orders_90d": [12, 30, 47, 8],
})

train = pd.merge_asof(
    labels.sort_values("event_ts"),
    features.sort_values("feature_ts"),
    left_on="event_ts", right_on="feature_ts",
    by="entity_id",
    direction="backward",             # never look forward
    tolerance=pd.Timedelta("30D"),    # stale -> NaN, not silently wrong
)
```

Customer 1's 2026-03-01 row now gets `orders_90d = 12` instead of `47` — while its 2026-06-01 row does get `47`, because by that date the value was genuinely known. Same entity, same feature, two different correct answers: that is the whole point. `direction="backward"` is the correctness knob. `tolerance` is the honesty knob — without it, a feature computed six months earlier joins on looking fresh.

Two things worth internalizing:

**Feature freshness is part of the feature.** If serving reads a value refreshed hourly, training rows built from daily snapshots describe a different variable. Log the actual served feature vector at inference and diff its distribution against the offline one — that diff is the only reliable skew detector.

**Windowed aggregates need the window pinned to the event, not the query.** `COUNT(*) WHERE ts > NOW() - 30 days` is correct in serving and leakage in training. Parameterize the anchor.

Cheap check before you trust any offline score: shuffle `event_ts` within each entity and retrain. If AUC barely moves, time carries no information in your pipeline — which means your join lost it.

## 15:03 - [Crypto & Business] Tax-Loss Harvesting: A Deferral With a 61-Day Trap

Harvesting a loss means selling a position that's underwater, booking the loss for tax purposes, and immediately buying something similar — so you keep the market exposure and get a deduction. It only works in a taxable brokerage account; inside an IRA or 401(k) there is nothing to harvest.

**The offset ladder (US rules).** Realized losses first cancel realized gains dollar-for-dollar, long against long and short against short. Whatever is left offsets up to **$3,000** of ordinary income per year. Anything beyond that carries forward indefinitely.

**Worked example.** You put $30,000 into a broad index fund; it's now worth $24,000. Sell, and you realize a $6,000 loss. Say you also had $4,000 of long-term gains that year, and you're at a 24% ordinary / 15% long-term bracket:

- $4,000 of loss cancels the gains → $600 saved
- $2,000 offsets ordinary income → $480 saved
- Year-one benefit: **$1,080**

**The catch nobody mentions.** Your replacement shares have a $24,000 basis. When the fund climbs back to $30,000 and you eventually sell, you owe tax on that $6,000 gain. You didn't erase tax — you deferred it. The real gain is the time value of money on that deferral, plus rate arbitrage: deducting at 24% ordinary today and repaying at 15% long-term later is a genuine 9-point spread. If your future bracket is higher, harvesting can cost you.

**The wash sale rule (IRC §1091)** disallows the loss if you buy a "substantially identical" security within **30 days before or after** the sale — a 61-day window centered on the trade. Three ways people trip it without noticing:

1. **Automatic dividend reinvestment** in the same fund. Turn it off first.
2. **Buying in another account**, including your spouse's — the rule looks across all of them.
3. **Rebuying inside an IRA**, which is the worst case: the loss is disallowed *and* there's no basis add-back, so it vanishes permanently.

A disallowed loss in a taxable account isn't destroyed — it's added to the replacement shares' basis. Swap into a different index (S&P 500 → total market) rather than the same fund at another broker, and never let harvesting push you into a worse or pricier fund; the tax tail shouldn't wag the portfolio.

## 19:02 - [PC Hardware] HDR Monitors: Why Turning HDR On Often Looks Worse Than SDR

Enabling HDR on a cheap monitor usually makes the image *worse* — washed-out blacks, crushed shadows, dull colors. That isn't a bug. It's what happens when a panel accepts an HDR signal it has no hardware to display.

**HDR needs three things**: high peak brightness, deep blacks (contrast), and wide color gamut. A "HDR-compatible" panel may deliver none of them and still legally accept the signal.

**VESA DisplayHDR tiers, decoded:**

| Tier | Peak nits | Local dimming | Verdict |
|---|---|---|---|
| DisplayHDR 400 | 400 | **None required** | Marketing sticker. Ignore it |
| DisplayHDR 600 | 600 | Required (edge-lit ok) | Entry-level real HDR |
| DisplayHDR 1000 | 1000 | Required, typically FALD | Genuinely good |
| True Black 400/500 | 400–500 | Per-pixel (OLED) | Excellent despite low nits |

Note the inversion: an OLED at 450 nits beats an LCD at 600 because contrast, not brightness, carries HDR. OLED blacks are true zero; a typical IPS panel sits near 1000:1 static contrast, so "black" is dark gray no matter how bright the highlights get.

**Local dimming zone count is the number to hunt for.** Edge-lit panels with 8–16 zones produce visible halos ("blooming") around bright objects on dark backgrounds — a mouse cursor on a black screen lights up a whole bar. Mini-LED panels with 500–2000+ zones shrink halos to near-invisible. Zone count is rarely on the spec sheet; reviews measure it.

**Checks before you blame the monitor:**

- Windows: enable HDR *per-display*, then run the **Windows HDR Calibration** app. Uncalibrated SDR-in-HDR content is the usual cause of "washed out."
- Verify 10-bit and full RGB in your GPU control panel — some cables/modes silently fall back to 8-bit or 4:2:0 chroma, which smears text.
- Many panels only reach rated peak nits in a specific picture mode with local dimming forced on; the default mode often caps far lower.

If the panel can't hit ~600 nits with real local dimming, leave HDR off and enjoy a correct SDR image.
