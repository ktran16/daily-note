## 00:02 - [Data Engineering] Surrogate Keys by Hashing: NULLs, Delimiters, and the Silent Duplicate

Dimensional models need a single-column key for joins, but the business identity is often a composite (`order_id` + `line_number`, or `source_system` + `customer_code`). The standard answer is a hashed surrogate key. It is a four-line macro that goes wrong in three predictable ways.

```sql
-- models/marts/dim_customer.sql
select
    {{ dbt_utils.generate_surrogate_key(['source_system', 'customer_code']) }} as customer_sk,
    source_system,
    customer_code,
    ...
from {{ ref('stg_customers') }}
```

**NULLs.** A raw `md5(a || b)` returns NULL in most warehouses if any input is NULL — so every row with a missing component collapses to one NULL key, and your `not_null` test fires downstream instead of here. `generate_surrogate_key` handles this by coercing NULL to the literal `'_dbt_utils_surrogate_key_null_'` before hashing. (The older `surrogate_key` macro did *not*; if you still have calls to it, they are a live bug.) Rolling your own means writing the `coalesce` yourself:

```sql
md5(coalesce(cast(source_system as varchar), '_null_') || '-' ||
    coalesce(cast(customer_code  as varchar), '_null_'))
```

**Delimiter collisions.** Without a separator, `('ab', 'c')` and `('a', 'bc')` hash identically — two distinct customers, one key, and a fan-out on join. The macro inserts `-` between fields. That is not airtight: if a value can itself contain `-`, pick a separator your data cannot produce, such as `'||'` or a control character.

**Unstable casting.** The hash is over *string* representations, so anything that changes formatting changes the key: a timestamp cast that gains microseconds, a warehouse migration that renders dates differently, trailing whitespace, or `'ACME'` vs `'acme'`. Normalize in staging — `trim`, `lower`, explicit date formats — never inside the key macro. Column *order* matters too, so treat the argument list as a contract.

Then prove it, every run:

```yaml
models:
  - name: dim_customer
    columns:
      - name: customer_sk
        data_tests: [unique, not_null]
```

`md5` gives 128 bits; genuine collisions are not your risk. Your inputs are.

## 05:03 - [Data Analytics] NaN Join Keys in pandas: GroupBy Deletes Them, Merge Multiplies Them

A missing key behaves in exactly opposite ways in the two pandas operations you reach for most. Neither raises. Both change your numbers.

**GroupBy silently drops them.** `groupby` defaults to `dropna=True`, so rows with a null key leave the result entirely:

```python
orders = pd.DataFrame({
    "order_id": [1, 2, 3, 4, 5],
    "region":   ["US", "EU", None, "US", None],
    "revenue":  [100, 200, 300, 400, 500],
})

orders.revenue.sum()                          # 1500
orders.groupby("region").revenue.sum().sum()  # 700
```

800 of 1500 — 53% of revenue — vanished, and the per-region numbers are individually correct, so nothing looks broken. Pass `dropna=False` to get an explicit `NaN` bucket, then decide what it means. An unexpectedly large null group is usually a broken upstream join, not a data-entry problem.

**Merge treats them as equal.** SQL's `ON a.k = b.k` never matches NULL to NULL. pandas does the opposite — `NaN` is just another key value, so nulls on both sides form a cartesian product:

```python
a = pd.DataFrame({"k": ["x", None, None], "a": [1, 2, 3]})
b = pd.DataFrame({"k": ["x", None, None], "b": [10, 20, 30]})
a.merge(b, on="k", how="inner")   # 5 rows, not 3
```

One real match plus a 2×2 block of nonsense. At warehouse scale this is how a 10k-row lookup becomes 400M rows.

**Guardrails:**

- `validate="one_to_one"` / `"one_to_many"` on every merge. It raises `MergeError` on the example above instead of returning the fan-out.
- `indicator=True`, then check `_merge.value_counts()` — `left_only` counts are the unmatched rows you assumed didn't exist.
- Drop or fill null keys *before* joining: `df.dropna(subset=["k"])`.
- Assert row counts across a join you expect to preserve cardinality.

One more: for a Categorical grouper, `observed` controls whether unused categories appear as zero rows. pandas 2.x defaulted to `False` (they appear); 3.0 defaults to `True` (they don't). Set it explicitly rather than inheriting whichever version is installed.

## 10:03 - [ML & AI] Log-Transforming the Target: Why `exp(prediction)` Is Systematically Too Low

Skewed targets — revenue, claim size, session length — get log-transformed so the model sees something roughly symmetric. You fit on `log(y)`, predict, then call `np.exp()` to get back to dollars. That last step quietly biases every prediction downward, and nobody notices because the log-space RMSE looks great.

The reason is Jensen's inequality: `exp` is convex, so `E[exp(z)] > exp(E[z])`. Concretely, if `log y = Xβ + ε` with `ε ~ N(0, σ²)`, then

```
E[y | X] = exp(Xβ) · exp(σ²/2)
```

Naive `exp(ŷ)` estimates the conditional **median**, not the mean. The gap is the residual spread, and it is not small:

| σ (residual SD in log space) | correction factor | naive is low by |
|---|---|---|
| 0.3 | 1.046 | 4.4% |
| 0.5 | 1.133 | 11.8% |
| 0.8 | 1.377 | 27.4% |
| 1.0 | 1.649 | 39.3% |

Simulated check at `Xβ = 2`, `σ = 0.5`: naive `exp(2) = 7.39`, true mean `8.37`.

This matters most when you **sum** predictions. Every row is low by the same factor, so a revenue forecast over 50k rows at σ=0.5 lands ~12% under budget — a systematic miss, not noise that averages out.

The fix that doesn't assume normality is **Duan's smearing estimator**: average `exp(residual)` over training residuals and multiply.

```python
import numpy as np

model.fit(X_train, np.log(y_train))
resid = np.log(y_train) - model.predict(X_train)   # log space
smear = np.mean(np.exp(resid))                     # ≈ 1.135 at σ=0.5

y_pred = np.exp(model.predict(X_test)) * smear
```

Compute it on out-of-fold residuals, not in-sample ones: an overfit model has artificially small training residuals, which shrinks the factor toward 1 and leaves the bias in place.

Three practical rules:

1. **Decide which functional you want.** If the business cares about typical value, the median is fine and needs no correction — just say so. If it cares about totals or expected cost, you need the mean.
2. **Evaluate in the original units.** Log-space RMSE is a *relative* error metric; a 2x miss on a $10 row costs the same as on a $10k row.
3. **Consider skipping the transform.** A Poisson or Gamma GBM objective (`objective="gamma"` in LightGBM/XGBoost) models the mean on the original scale directly, and sidesteps retransformation entirely.

## 15:03 - [Crypto & Business] Burn Multiple and the Rule of 40: Measuring Whether Growth Is Worth What It Costs

Revenue growth alone says nothing about quality. Two companies both grew ARR by $4M last year — one burned $4M doing it, the other burned $14M. Same top line, completely different businesses. Two metrics separate them.

**Burn multiple = net burn ÷ net new ARR.** It answers: how many dollars of cash did we destroy to add one dollar of recurring revenue?

- Company A: burned $6M, net new ARR $4M → **1.5x**
- Company B: burned $6M, net new ARR $2M → **3.0x**

Rough reading: under 1x is exceptional, 1–1.5x good, 1.5–2x fine, 2–3x needs an explanation, above 3x means the engine isn't converting cash into durable revenue.

The critical word is *net*. A company landing $5M of gross new ARR while losing $3M to churn and downgrades has net new ARR of $2M. Gross-new dashboards make that look like a $5M year; the burn multiple prices the leak in.

**Rule of 40 = growth rate % + FCF margin % ≥ 40.** A company growing 60% at a –15% FCF margin scores 45 and passes. One growing 15% at a 20% margin scores 35 and fails. It formalizes the trade: burning is acceptable if it buys proportionate growth.

**When each applies.** Burn multiple works at any stage, including pre-profitability, because it needs only cash out and ARR added. Rule of 40 needs a real revenue base — a $1M ARR company growing 300% passes trivially and tells you nothing.

**The shared failure mode:** both are trivially gamed for one quarter. Cut sales and marketing in Q1 and burn multiple improves immediately while pipeline quietly empties; growth collapses in Q3. Always compute on trailing four quarters.

**Tie it to runway.** With $18M in the bank, a 2.0x burn multiple, and a plan to add $9M of ARR, the implied burn is $18M — you hit the target exactly as the account empties. Either the multiple improves or the plan doesn't survive contact with the bank balance.

## 19:03 - [PC Hardware] Hybrid and Multi-CCD CPUs: When the Scheduler Puts Your Game on the Wrong Cores

Modern desktop CPUs are no longer uniform. Intel splits P-cores and E-cores; AMD's 12- and 16-core parts split two CCDs, and on X3D-plus-standard chips only *one* CCD carries the stacked cache. Every core is not equal anymore, and which one your thread lands on is decided by software you don't normally think about.

**Why it bites.** A game's render thread on an E-core, or on the non-cache CCD of a 9950X3D, doesn't halve your average FPS — it produces a stutter that shows up only in 1% lows. Worse, cross-CCD communication costs real time: an inter-core latency test on a dual-CCD Ryzen shows roughly **15–25 ns within a CCD versus 75–80 ns across the Infinity Fabric**. A workload whose threads get split across both CCDs pays that on every synchronization.

**The stack that decides placement.**

| Layer | What it does | How it fails |
|---|---|---|
| Intel Thread Director | Feeds per-thread IPC/class hints to the OS | Misclassifies background-looking game threads |
| Windows scheduler | Consumes those hints | Older builds ignore them; needs current Windows |
| Xbox Game Bar (AMD) | Flags a process as a game so the non-cache CCD gets parked | Doesn't recognize the launcher or emulator you use |
| Chipset driver / power plan | Enables core parking at all | Stale AMD chipset driver = no parking |

**Diagnose before you fiddle.** Run the workload and watch *per-core* load — Task Manager → Performance → right-click → Logical processors, or `btop` / `htop` on Linux. On a 9950X3D, cores 0–7 are the cache CCD; heavy game load on 8–15 is the bug. On Intel, E-cores are the trailing logical processors.

**Fixes, cheapest first:**

1. Update chipset drivers and Windows, and keep the Balanced power plan — AMD's parking logic lives there.
2. Make sure the game is recognized by Game Bar (add it manually if launched through a third-party launcher).
3. Pin explicitly: `start /affinity FF game.exe` restricts to the first 8 logical processors. Process Lasso automates this persistently.
4. Only last, and rarely worth it: disable E-cores in BIOS. You trade away real multithreaded throughput to fix a scheduling bug that a driver update usually solves.

**Also check Linux.** `lscpu -e` prints core-to-CPU mapping; on hybrid parts confirm `MAXMHZ` differs between P and E cores before assuming your taskset is right.
