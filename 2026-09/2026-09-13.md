## 00:03 - [Data Engineering] Airflow Dynamic Task Mapping: Fanning Out When You Don't Know the Count Until Runtime

Classic Airflow forces you to know your parallelism at **parse time** — a `for` loop over a hardcoded list. But you usually don't know how many files landed in S3 or how many tenants need a backfill until the DAG is already running. Dynamic task mapping (`.expand()`, Airflow 2.3+) creates one task instance per element of a list produced by an upstream task.

```python
@task
def list_files(bucket: str) -> list[str]:
    return S3Hook().list_keys(bucket, prefix="raw/")   # length unknown at parse time

@task
def load_file(key: str, bucket: str) -> int:
    return ingest(bucket, key)                         # returns row count

files = list_files("events")
counts = load_file.partial(bucket="events").expand(key=files)
```

`partial()` pins the arguments that stay constant; `expand()` takes the one that varies. Airflow renders N `load_file` instances in the UI under a single node, each retryable on its own. Downstream tasks that consume `counts` receive the collected list — a natural reduce step.

**The three things that bite people:**

1. **The mapped list travels through XCom.** The default backend writes to the metadata database, so a task returning 50,000 S3 keys bloats Postgres and slows the scheduler. Return *references* (prefixes, ID ranges), not payloads — or configure a custom XCom backend that spills to object storage.

2. **`max_map_length` defaults to 1024.** Exceed it and the mapping fails outright rather than truncating. Chunk upstream:
   ```python
   @task
   def chunk(keys: list[str], size: int = 100) -> list[list[str]]:
       return [keys[i:i+size] for i in range(0, len(keys), size)]
   ```
   Then map over chunks and loop inside the task — fewer, fatter tasks also cut scheduler overhead.

3. **Mapped tasks still obey concurrency limits.** 500 mapped instances with `max_active_tasks=16` means 484 sit in `queued`. Use `max_active_tis_per_dag` on the mapped task to protect a fragile API from your own fan-out.

For multiple varying arguments, use `expand_kwargs()` with a list of dicts — it maps over the zipped rows rather than the Cartesian product that stacked `expand()` arguments would produce. That distinction silently explodes task counts if you get it wrong.

## 05:02 - [Data Analytics] Row-Level Security: The LEFT JOIN That Leaks Other Regions

Row-level security in a BI tool is usually one line — `region = {{ _user_attributes['region'] }}` in Looker, a DAX table filter in Power BI, a Metabase sandbox column. The leak is never in that line. It's in where the generated SQL puts it.

**The leak.** A rep should see only EMEA orders. The RLS predicate lands in the `ON` clause of a LEFT JOIN:

```sql
SELECT o.order_id, o.revenue, r.region
FROM orders o
LEFT JOIN sales_reps r
  ON o.rep_id = r.rep_id
 AND r.region = 'EMEA';        -- filter in ON, not WHERE
```

A LEFT JOIN keeps every left row regardless of what the `ON` clause rejects. APAC orders survive with `region` NULL — order IDs and revenue intact. `SUM(revenue)` returns the global $4.2M, not EMEA's $1.1M, and the drill-through table shows the other regions' rows.

Move it to `WHERE r.region = 'EMEA'` and the LEFT JOIN collapses to an inner join, which is what you wanted. Better: inner-join a pre-filtered dimension so intent is explicit.

**The over-correction.** Filtering in `WHERE` also drops orders with `rep_id IS NULL`. That's usually 1–3% of rows, and the totals now reconcile to nothing. Decide deliberately: assign an `rep_id = -1` "unassigned" member at load time and grant it to everyone, or accept the gap and document it. Silently losing rows is how an RLS rollout gets blamed for "the numbers changed."

**The many-to-many case.** If a rep covers several regions through a bridge table, joining to it fans out and double-counts revenue. Filter with `EXISTS` — it tests without multiplying rows:

```sql
WHERE EXISTS (
  SELECT 1 FROM rep_regions rr
  WHERE rr.rep_id = o.rep_id
    AND rr.region = 'EMEA'
);
```

**Test it like a constraint, not a feature.** As a privileged user, run the query once per region value and assert two things: each partition's `SUM(revenue)` is non-zero where it should be, and the partitions sum to the unrestricted total minus the unassigned bucket. If they sum to *more*, you have fan-out. If they sum to the full total *and* each partition looks complete, your filter isn't applying at all.
