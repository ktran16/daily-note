## 00:03 - [Data Engineering] Snowflake Warehouse Sizing: Why a Bigger Warehouse Is Often Cheaper

Snowflake credits scale linearly with warehouse size: XS burns 1 credit/hour, S burns 2, M burns 4, and so on. Because billing is per-second (with a 60-second minimum per resume), a query that takes 8 minutes on an M costs exactly the same as one that takes 4 minutes on an L — *if* the work parallelizes. Most scan-and-aggregate work does. So the reflex to "shrink the warehouse to save money" frequently costs the same and delivers results twice as slowly.

The real waste is elsewhere. Two failure modes dominate:

**Remote spilling.** When a warehouse runs out of memory it spills to local SSD, then to remote storage. Remote spill is catastrophically slow and scales *worse* than linearly — this is where undersizing actually costs money. Find it:

```sql
select query_id, warehouse_size,
       bytes_spilled_to_local_storage   as local_spill,
       bytes_spilled_to_remote_storage  as remote_spill,
       total_elapsed_time/1000          as secs
from snowflake.account_usage.query_history
where start_time > dateadd('day', -7, current_timestamp())
  and bytes_spilled_to_remote_storage > 0
order by remote_spill desc
limit 20;
```

Any remote spill means size up one step (memory doubles with each step) — or fix the join that's exploding rows.

**Idle time.** A warehouse left running between queries bills the full rate for doing nothing.

```sql
alter warehouse transforming set
  auto_suspend = 60          -- seconds; default is 600
  auto_resume  = true
  min_cluster_count = 1
  max_cluster_count = 3;     -- multi-cluster fixes *queuing*, not slow queries
```

Sixty seconds is the sweet spot for most transform warehouses. Going lower re-pays the 60-second resume minimum repeatedly; cache warmth also dies on suspend.

**The diagnostic rule:** `queued_overload_time` high → add clusters (concurrency problem). `bytes_spilled_to_remote_storage` high → size up (memory problem). Both near zero and the query is still slow → it's the SQL, and no warehouse size will save you.

Separate warehouses per workload (BI, transforms, ad-hoc) so one runaway analyst query can't queue your production dbt run — and so `QUERY_HISTORY` attributes cost to a team, not a black box.

## 05:02 - [Data Analytics] Percentiles Don't Average: The Rollup That Quietly Fakes Your p95

Averaging percentiles is the most common wrong number on a latency dashboard, and it fails silently — no error, no null, just a plausible line that understates the tail.

**Why it breaks.** Sums and counts are *additive*: the weekly total is the sum of the daily totals. Percentiles are not. A p95 is a *position* in a sorted distribution, and you cannot recover the position in a merged distribution from the positions in its parts.

Concretely — Monday: 1,000 requests, p95 = 200ms. Tuesday: 1,000 requests, but a bad deploy put 80 of them at 5,000ms, so Tuesday's slow bucket is the top 8% and p95 = 5,000ms. The mean of the two p95s is 2,600ms. Now merge: 2,000 requests, of which the 80 slow ones are the top 4%. The 95th percentile is row 1,900 of 2,000 — it lands *below* the slow bucket, back in the fast distribution, around 350ms. Averaging overstated the real number by roughly 7x.

Reverse the shape — a thin slow tail present on *every* day rather than concentrated in one — and averaging understates instead. The error has no reliable direction, which is what makes it dangerous: you cannot correct for it with a fudge factor.

**The fix: aggregate raw, not rolled up.**

```sql
-- Correct: one pass over the base rows
select date_trunc('week', ts) as wk,
       percentile_cont(0.95) within group (order by latency_ms) as p95
from requests
where ts >= current_date - interval '28 days'
group by 1;
```

Never `avg(daily_p95)`. If a nightly rollup is unavoidable because the base table is too big to rescan, store a mergeable *sketch* per day instead of a scalar — the sketch merges correctly, the number doesn't:

```sql
-- Snowflake: t-digest state that can be recombined over any date range
create table daily_latency as
select date_trunc('day', ts)                as d,
       approx_percentile_accumulate(latency_ms) as st
from requests group by 1;

select approx_percentile_estimate(approx_percentile_combine(st), 0.95)
from daily_latency
where d >= current_date - 28;
```

ClickHouse spells this `quantileTDigestState` / `quantileTDigestMerge`; Postgres needs the `tdigest` extension. DuckDB and BigQuery have approximate quantiles (`approx_quantile`, `APPROX_QUANTILES`) but no mergeable quantile sketch — there, either rescan the base rows or store a fixed-bucket histogram (counts per latency bucket) and re-derive the percentile from the summed counts, since *counts* do add up.

**Two corollaries.** Don't average p95 across *segments* either (regions, tenants) — same math. And when a BI tool auto-aggregates a `p95` column on drill-up, it is almost certainly averaging; define it as a semantic-layer measure computed from base rows, or mark it non-additive so the tool refuses to roll it up.

## 10:02 - [ML & AI] Random Forest vs Gradient Boosting: Opposite Errors, Opposite Hyperparameters

Both are ensembles of decision trees, and people tune them the same way. That's the bug. They attack **opposite halves of the bias-variance decomposition**, so the settings that help one actively hurt the other.

**Random Forest reduces variance.** It averages `N` deep trees fit on bootstrap samples. The variance of the average of `N` identically-distributed trees with pairwise correlation `ρ` is:

```
Var = ρσ² + (1 - ρ)σ²/N
```

Note what `N` can and can't do. With `σ² = 1.0` and `ρ = 0.6`, going to `N = 100` gives `0.6 + 0.004 = 0.604` — the second term vanishes but `ρσ²` is a **floor**. Adding trees past a few hundred buys nothing. Cutting correlation does: `max_features='sqrt'` forces trees to split on different columns, and if that drops `ρ` to `0.3`, variance falls to `0.3 + 0.007 = 0.307`. That roughly halves the variance — something 10,000 more trees could never deliver.

Because averaging only kills variance, each RF tree must be **low-bias** — grow them deep and unpruned (`max_depth=None`). A shallow RF underfits and no amount of trees will save it.

**Gradient Boosting reduces bias.** Each tree fits the *gradient of the loss* left by the ensemble so far, so bias shrinks with every round while variance accumulates. Its trees must therefore be **weak**: `max_depth=3–8`, with `learning_rate` shrinking each contribution.

|  | Random Forest | Gradient Boosting |
|---|---|---|
| Tree depth | deep (`None`) | shallow (3–8) |
| More trees | plateaus, safe | **overfits** — needs early stopping |
| Main knob | `max_features` | `learning_rate` × `n_estimators` |
| Parallel? | yes (independent) | no (sequential) |

```python
# RF: deep trees, decorrelate, trees are free
RandomForestClassifier(n_estimators=500, max_depth=None,
                       max_features='sqrt', n_jobs=-1)

# GBM: shallow trees, low LR, let validation pick n_estimators
lgb.LGBMClassifier(n_estimators=5000, learning_rate=0.03, max_depth=6).fit(
    X_tr, y_tr, eval_set=[(X_val, y_val)],
    callbacks=[lgb.early_stopping(100)])
```

**The rule of thumb:** halving `learning_rate` roughly doubles the `n_estimators` you need — so never grid-search them independently. Fix a small LR, set `n_estimators` high, and let early stopping choose it.
