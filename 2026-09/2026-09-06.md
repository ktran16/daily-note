# Daily Notes - 2026-09-06

## 00:03 - [Data Engineering] Snowflake Warehouse Sizing: Why a Bigger Warehouse Is Often Cheaper

Snowflake credits scale linearly with warehouse size: XS burns 1 credit/hour, S burns 2, M burns 4, and so on. Because billing is per-second (with a 60-second minimum per resume), a query that takes 8 minutes on an M costs exactly the same as one that takes 4 minutes on an L — *if* the work parallelizes. Most scan-and-aggregate work does. So the reflex to "shrink the warehouse to save money" frequently costs the same and delivers results twice as slowly.

The real waste is elsewhere. Two failure modes dominate:

**Remote spilling.** When a warehouse runs out of memory it spills to local SSD, then to remote storage. Remote spill is catastrophically slow and scales *worse* than linearly — this is where undersizing actually costs money. Find it:

```sql
select query_id, warehouse_size,
       bytes_spilled_to_local_storage   as local_spill,
       bytes_spilled_to_remote_storage  as remote_spill,
       total_elapsed_time/1000          as secs
from snowflake.account_usage.query_history
where start_time > dateadd('day', -7, current_timestamp())
  and bytes_spilled_to_remote_storage > 0
order by remote_spill desc
limit 20;
```

Any remote spill means size up one step (memory doubles with each step) — or fix the join that's exploding rows.

**Idle time.** A warehouse left running between queries bills the full rate for doing nothing.

```sql
alter warehouse transforming set
  auto_suspend = 60          -- seconds; default is 600
  auto_resume  = true
  min_cluster_count = 1
  max_cluster_count = 3;     -- multi-cluster fixes *queuing*, not slow queries
```

Sixty seconds is the sweet spot for most transform warehouses. Going lower re-pays the 60-second resume minimum repeatedly; cache warmth also dies on suspend.

**The diagnostic rule:** `queued_overload_time` high → add clusters (concurrency problem). `bytes_spilled_to_remote_storage` high → size up (memory problem). Both near zero and the query is still slow → it's the SQL, and no warehouse size will save you.

Separate warehouses per workload (BI, transforms, ad-hoc) so one runaway analyst query can't queue your production dbt run — and so `QUERY_HISTORY` attributes cost to a team, not a black box.
