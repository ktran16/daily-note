## 00:03 - [Data Engineering] BigQuery Partition Pruning: Why Your Filtered Query Still Scans the Whole Table

BigQuery bills on bytes scanned, and partitioning is the main lever. But a `WHERE` clause on the partition column does not guarantee pruning — the planner must resolve the filter to a constant *before* the query runs. When it can't, you pay for every partition.

```sql
CREATE TABLE analytics.orders (
  order_id STRING,
  ordered_at TIMESTAMP,
  customer_id STRING,
  status STRING
)
PARTITION BY DATE(ordered_at)
CLUSTER BY customer_id, status
OPTIONS (require_partition_filter = TRUE);
```

`require_partition_filter` is the cheapest guardrail you will ever add: any query without a partition filter fails outright instead of quietly scanning 4 TB.

**The three ways pruning silently fails:**

*A subquery in the filter.* The planner cannot evaluate it at planning time:

```sql
-- full scan
WHERE DATE(ordered_at) = (SELECT MAX(load_date) FROM analytics.watermark)
```

Fix it with scripting, which resolves the value first:

```sql
DECLARE target_date DATE DEFAULT (
  SELECT MAX(load_date) FROM analytics.watermark);

SELECT * FROM analytics.orders
WHERE DATE(ordered_at) = target_date;  -- one partition
```

*Wrapping the partition column in a function.* `PARTITION BY DATE(ordered_at)` prunes on `DATE(ordered_at)` or on a literal range of `ordered_at`, but not on expressions like `FORMAT_TIMESTAMP('%Y-%m', ordered_at) = '2026-09'`. Express the filter as a half-open range on the raw column:

```sql
WHERE ordered_at >= TIMESTAMP('2026-09-01')
  AND ordered_at <  TIMESTAMP('2026-10-01')
```

*Filtering only through a join.* A predicate that reaches the partition column via another table's column is evaluated after the scan. Push a literal range onto the partitioned side too, even if it looks redundant.

**Clustering is different.** Up to four columns, and order matters — it's a sort prefix, so `CLUSTER BY customer_id, status` prunes on `customer_id`, or on both, but poorly on `status` alone. Put the column you filter on most selectively first. Note that `bq query --dry_run` does *not* account for cluster pruning; its estimate is an upper bound, and real cost is often far lower. Use `INFORMATION_SCHEMA.JOBS` for actuals.

In dbt, both live in the model config:

```sql
{{ config(
    materialized='incremental',
    partition_by={'field': 'ordered_at', 'data_type': 'timestamp',
                  'granularity': 'day'},
    cluster_by=['customer_id', 'status'],
    require_partition_filter=true
) }}
```

Cap the blast radius globally with `--maximum_bytes_billed`.

## 05:02 - [Data Analytics] Join Fan-Out: The Silent Row Multiplication That Inflates Every Metric

The most common cause of a wrong revenue number isn't bad math — it's a join to a dimension you assumed was unique on its key.

```sql
select sum(o.amount) as revenue
from orders o
join dim_customer c on c.customer_id = o.customer_id
```

If `dim_customer` is SCD-2, or just picked up duplicate rows from a re-run, each duplicate multiplies its order row. 1,000 orders where 340 match two dimension rows becomes 1,340 rows — revenue overstated by 34%. Nothing errors. The dashboard reads high, and it reads high consistently, which is what makes it survive review.

**Check the grain before you trust the join:**

```sql
select customer_id, count(*) as n
from dim_customer
group by customer_id
having count(*) > 1
order by n desc limit 20;
```

Make it a standing `unique` test on the join key of every dimension you join to, not a one-time check.

**Verify after the fact with the measure, not the row count.** Row counts can hide lost rows offsetting duplicated ones; the sum can't:

```sql
select
  (select sum(amount) from orders)          as before_join,
  sum(o.amount)                             as after_join
from orders o
join dim_customer c using (customer_id);
```

If those differ, the join changed the grain. Full stop.

**In pandas, make it fail loudly instead of silently:**

```python
df = orders.merge(dim_customer, on="customer_id",
                  how="left", validate="m:1", indicator=True)
print(df["_merge"].value_counts())
```

`validate="m:1"` raises `MergeError` when the right side isn't unique on the key — the assertion you'd otherwise never write. `indicator=True` surfaces the other half of the bug: `left_only` counts the fact rows that matched nothing, which an inner join would have dropped along with their revenue.

**When the dimension legitimately has many rows per key**, don't dedupe blindly — join to the version valid at event time:

```sql
join dim_customer c
  on  c.customer_id = o.customer_id
 and  o.ordered_at >= c.valid_from
 and  o.ordered_at <  c.valid_to
```

Half-open interval so a row landing exactly on a boundary matches once, and store the open-ended row as `valid_to = '9999-12-31'` rather than `NULL` — `NULL` fails the comparison and silently drops every current-version order.

Rule of thumb: aggregate to the grain first, or join only on a key you have proven unique.
