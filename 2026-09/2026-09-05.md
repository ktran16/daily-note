## 00:03 - [Data Engineering] BigQuery Partition Pruning: Why Your Filtered Query Still Scans the Whole Table

BigQuery bills on bytes scanned, and partitioning is the main lever. But a `WHERE` clause on the partition column does not guarantee pruning — the planner must resolve the filter to a constant *before* the query runs. When it can't, you pay for every partition.

```sql
CREATE TABLE analytics.orders (
  order_id STRING,
  ordered_at TIMESTAMP,
  customer_id STRING,
  status STRING
)
PARTITION BY DATE(ordered_at)
CLUSTER BY customer_id, status
OPTIONS (require_partition_filter = TRUE);
```

`require_partition_filter` is the cheapest guardrail you will ever add: any query without a partition filter fails outright instead of quietly scanning 4 TB.

**The three ways pruning silently fails:**

*A subquery in the filter.* The planner cannot evaluate it at planning time:

```sql
-- full scan
WHERE DATE(ordered_at) = (SELECT MAX(load_date) FROM analytics.watermark)
```

Fix it with scripting, which resolves the value first:

```sql
DECLARE target_date DATE DEFAULT (
  SELECT MAX(load_date) FROM analytics.watermark);

SELECT * FROM analytics.orders
WHERE DATE(ordered_at) = target_date;  -- one partition
```

*Wrapping the partition column in a function.* `PARTITION BY DATE(ordered_at)` prunes on `DATE(ordered_at)` or on a literal range of `ordered_at`, but not on expressions like `FORMAT_TIMESTAMP('%Y-%m', ordered_at) = '2026-09'`. Express the filter as a half-open range on the raw column:

```sql
WHERE ordered_at >= TIMESTAMP('2026-09-01')
  AND ordered_at <  TIMESTAMP('2026-10-01')
```

*Filtering only through a join.* A predicate that reaches the partition column via another table's column is evaluated after the scan. Push a literal range onto the partitioned side too, even if it looks redundant.

**Clustering is different.** Up to four columns, and order matters — it's a sort prefix, so `CLUSTER BY customer_id, status` prunes on `customer_id`, or on both, but poorly on `status` alone. Put the column you filter on most selectively first. Note that `bq query --dry_run` does *not* account for cluster pruning; its estimate is an upper bound, and real cost is often far lower. Use `INFORMATION_SCHEMA.JOBS` for actuals.

In dbt, both live in the model config:

```sql
{{ config(
    materialized='incremental',
    partition_by={'field': 'ordered_at', 'data_type': 'timestamp',
                  'granularity': 'day'},
    cluster_by=['customer_id', 'status'],
    require_partition_filter=true
) }}
```

Cap the blast radius globally with `--maximum_bytes_billed`.
