# Daily Notes - 2026-09-01

## 00:03 - [Data Engineering] Log-Based CDC: Why Query-Based Change Capture Silently Loses Rows

Most teams start Change Data Capture with a query against the source:

```sql
SELECT * FROM orders WHERE updated_at > '{{ last_run_ts }}'
```

This is **query-based CDC**, and it has three failure modes that don't announce themselves:

1. **Deletes are invisible.** A row removed from the source never appears in any `updated_at` window. Your warehouse keeps it forever.
2. **Intermediate states are lost.** If a row changes three times between polls, you see only the final value. Fine for a current-state mart, fatal for an audit trail or an SCD Type 2 snapshot.
3. **Clock and commit-order races.** `updated_at` is usually set at statement time, but the row becomes visible at commit time. A long transaction can commit a row with `updated_at` *older* than your high-water mark — and you skip it permanently. Overlapping windows (`> last_run_ts - INTERVAL '15 minutes'`) reduce this but never eliminate it.

**Log-based CDC** reads the database's write-ahead log instead (Postgres logical replication, MySQL binlog, Oracle redo). Debezium is the common implementation, emitting one event per committed row change:

```json
{
  "op": "u",
  "before": {"id": 42, "status": "pending",   "amount": 100},
  "after":  {"id": 42, "status": "confirmed", "amount": 100},
  "source": {"lsn": 24857392, "ts_ms": 1756684800000, "table": "orders"}
}
```

You get deletes (`op: "d"`), every intermediate state, and commit-order guarantees — for free, with near-zero query load on the source.

The catch: delivery is **at-least-once**, so duplicates are normal. Dedupe on the log position, never on the timestamp:

```sql
-- Collapse a raw CDC stream to current state
SELECT * EXCEPT (op, lsn, rn)
FROM (
  SELECT *, ROW_NUMBER() OVER (
           PARTITION BY id ORDER BY lsn DESC
         ) AS rn
  FROM raw.orders_cdc
)
WHERE rn = 1
  AND op != 'd'   -- drop rows whose last event was a delete
```

**Operational rules that bite people:**

- **Never let a replication slot go unconsumed.** Postgres retains WAL until every slot advances; a paused connector will fill the source's disk and take production down. Alert on `pg_replication_slots.confirmed_flush_lsn` lag.
- **Snapshot + stream must be seamless.** The initial table snapshot and the log stream have to overlap, not gap. Debezium handles this; hand-rolled connectors usually don't.
- **`REPLICA IDENTITY FULL`** is required in Postgres if you want the `before` image on updates and deletes — the default only gives you the primary key.

Reach for query-based CDC only when you cannot get log access. It is the fallback, not the default.
