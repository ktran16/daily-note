## 00:03 - [Data Engineering] Log-Based CDC: Why Query-Based Change Capture Silently Loses Rows

Most teams start Change Data Capture with a query against the source:

```sql
SELECT * FROM orders WHERE updated_at > '{{ last_run_ts }}'
```

This is **query-based CDC**, and it has three failure modes that don't announce themselves:

1. **Deletes are invisible.** A row removed from the source never appears in any `updated_at` window. Your warehouse keeps it forever.
2. **Intermediate states are lost.** If a row changes three times between polls, you see only the final value. Fine for a current-state mart, fatal for an audit trail or an SCD Type 2 snapshot.
3. **Clock and commit-order races.** `updated_at` is usually set at statement time, but the row becomes visible at commit time. A long transaction can commit a row with `updated_at` *older* than your high-water mark — and you skip it permanently. Overlapping windows (`> last_run_ts - INTERVAL '15 minutes'`) reduce this but never eliminate it.

**Log-based CDC** reads the database's write-ahead log instead (Postgres logical replication, MySQL binlog, Oracle redo). Debezium is the common implementation, emitting one event per committed row change:

```json
{
  "op": "u",
  "before": {"id": 42, "status": "pending",   "amount": 100},
  "after":  {"id": 42, "status": "confirmed", "amount": 100},
  "source": {"lsn": 24857392, "ts_ms": 1756684800000, "table": "orders"}
}
```

You get deletes (`op: "d"`), every intermediate state, and commit-order guarantees — for free, with near-zero query load on the source.

The catch: delivery is **at-least-once**, so duplicates are normal. Dedupe on the log position, never on the timestamp:

```sql
-- Collapse a raw CDC stream to current state
SELECT * EXCEPT (op, lsn, rn)
FROM (
  SELECT *, ROW_NUMBER() OVER (
           PARTITION BY id ORDER BY lsn DESC
         ) AS rn
  FROM raw.orders_cdc
)
WHERE rn = 1
  AND op != 'd'   -- drop rows whose last event was a delete
```

**Operational rules that bite people:**

- **Never let a replication slot go unconsumed.** Postgres retains WAL until every slot advances; a paused connector will fill the source's disk and take production down. Alert on `pg_replication_slots.confirmed_flush_lsn` lag.
- **Snapshot + stream must be seamless.** The initial table snapshot and the log stream have to overlap, not gap. Debezium handles this; hand-rolled connectors usually don't.
- **`REPLICA IDENTITY FULL`** is required in Postgres if you want the `before` image on updates and deletes — the default only gives you the primary key.

Reach for query-based CDC only when you cannot get log access. It is the fallback, not the default.

## 05:03 - [Data Analytics] Robust Anomaly Detection: Why the Z-Score Misses the Spike You're Hunting

The default anomaly check is a z-score: flag any day more than 3 standard deviations from the mean. It has a self-defeating flaw — **the outlier is inside the statistics used to judge it**. A large spike drags the mean toward itself and inflates the standard deviation, so the spike scores as unremarkable.

Take 10 quiet days averaging 100 signups, then one day at 400. Mean jumps to 127.3, sample stddev to 90.5, and the spike's z-score is **3.01** — barely over the line. Add a *second* 400 day and it gets worse: stddev climbs to 116.8 and each spike now scores **2.14**, comfortably under a threshold of 3. Two outliers hide each other. This is called *masking*, and it's why "we have alerting" often coexists with "nobody caught the outage."

The fix is to build the baseline from statistics outliers can't move: the **median** and the **median absolute deviation (MAD)**.

```sql
WITH med AS (
  SELECT d, signups, MEDIAN(signups) OVER () AS m
  FROM daily_signups
),
mad AS (
  SELECT d, signups, m, MEDIAN(ABS(signups - m)) OVER () AS mad_val
  FROM med
)
SELECT d, signups,
       ROUND(0.6745 * (signups - m) / NULLIF(mad_val, 0), 1) AS robust_z
FROM mad
WHERE ABS(0.6745 * (signups - m) / NULLIF(mad_val, 0)) > 3.5
ORDER BY d;
```

On the two-spike data: median 100.5, MAD 2.0, and each 400 day scores a robust z of **101.0**. Quiet days land between −1.2 and 0.8. The signal is now unmissable.

Notes on using it:

- **0.6745** rescales MAD so a robust z is comparable to a normal-distribution z. **3.5** is the standard threshold (Iglewicz & Hoaglin).
- **`NULLIF(mad_val, 0)` is not optional.** If more than half your values are identical — common for sparse or zero-heavy counters — MAD is exactly 0 and every non-median row divides by zero.
- Swap `OVER ()` for a trailing frame (e.g. `ROWS BETWEEN 28 PRECEDING AND 1 PRECEDING`) so the baseline is recent history and excludes the day being judged. Verified on DuckDB 1.5; `MEDIAN` is available in Snowflake and BigQuery, while Postgres needs `PERCENTILE_CONT(0.5) WITHIN GROUP`.

## 10:03 - [ML & AI] LLM-as-a-Judge: Why 85% Agreement Can Mean Your Eval Is Worthless

Using an LLM to grade another LLM's output is the default eval strategy now. It scales, it's cheap, and it is quietly easy to get wrong in ways that make a broken judge look fine.

**Position bias is the first trap.** In pairwise comparison ("which response is better, A or B?"), most models favour whichever answer appears first — the gap is often 10–20 points of win rate on identical content. The fix is cheap: run every comparison twice with the order swapped, and only count it as a win if the judge agrees with itself.

```python
def pairwise(judge, prompt, a, b):
    first  = judge(prompt, a, b)   # -> "A" or "B"
    second = judge(prompt, b, a)   # -> "A" or "B"
    if first == "A" and second == "B":  return "a_wins"
    if first == "B" and second == "A":  return "b_wins"
    return "tie"  # judge contradicted itself — not a signal
```

The tie rate is itself a diagnostic. If more than ~30% of your comparisons flip on reordering, the rubric is too vague to be measuring anything.

**Raw agreement flatters you.** Say you validate a pass/fail judge against 100 human-labelled items and get 85% agreement. Humans passed 80, the judge passed 85. Chance agreement is:

$$p_e = (0.80 \times 0.85) + (0.20 \times 0.15) = 0.68 + 0.03 = 0.71$$

$$\kappa = \frac{p_o - p_e}{1 - p_e} = \frac{0.85 - 0.71}{1 - 0.71} = 0.48$$

Cohen's kappa of 0.48 is *moderate* — a judge that blindly answered "pass" every time would already score 80%. On skewed distributions, which is exactly what quality evals look like, raw accuracy is nearly uninformative. Report kappa (`sklearn.metrics.cohen_kappa_score`), and treat below ~0.6 as not yet trustworthy.

**Practical rules:**

- Ask for a **binary or 3-point** verdict, not a 1–10 score. Judges cluster on 7 and 8 and the extra resolution is noise.
- Require the reasoning **before** the verdict in the output schema — ordering matters, since the tokens are generated in sequence.
- Keep a **frozen human-labelled set** of 50–100 items. Every time you edit the judge prompt, re-measure kappa against it; a prompt tweak that raises scores without raising kappa has only made the judge more generous.
- Never let the judge be the same model *and* prompt version as the generator without checking self-preference bias on a held-out set.
