## 00:02 - [Data Engineering] Flink Checkpoints vs Savepoints: Two Snapshots That Are Not Interchangeable

Both write your operator state to durable storage, and people use the words interchangeably until an upgrade eats a week. They are built for opposite jobs.

**Checkpoints** are the runtime's automatic fault-tolerance mechanism. Flink takes them on a timer, keeps them in a format optimized for fast writes (incremental RocksDB SST uploads), and — by default — *deletes them when the job stops*. They exist so a crashed job can resume in seconds.

**Savepoints** are operator-triggered, self-contained, and owned by you. They use a canonical format that survives Flink version upgrades and state-backend changes. They exist so you can stop a job, change something, and start again from the same position.

```yaml
# flink-conf.yaml
execution.checkpointing.interval: 60s
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.min-pause: 30s
# The single most-forgotten line:
execution.checkpointing.externalized-checkpoint-retention: RETAIN_ON_CANCELLATION
state.backend.type: rocksdb
state.checkpoints.dir: s3://lake/flink/checkpoints
state.savepoints.dir: s3://lake/flink/savepoints
```

Without `RETAIN_ON_CANCELLATION`, cancelling a job discards every checkpoint. The restarted job re-reads from the Kafka `auto.offset.reset` policy, not from where it left off — which is how "we only lost the state, not the data" turns into a silent replay or a silent gap.

The routine upgrade path:

```bash
# Stop the job and take a savepoint atomically (drains in-flight records)
flink stop --savepointPath s3://lake/flink/savepoints <job-id>

# Deploy new JAR, resume from that exact point
flink run -s s3://lake/flink/savepoints/savepoint-abc123 -d new-job.jar
```

Two practical rules. First, **pin your `uid()`s**. State is restored by operator UID, and Flink auto-generates them from the job graph's topology — add one `map()` upstream and every downstream UID shifts, so the restore silently drops that operator's state.

```java
stream.keyBy(e -> e.userId)
      .process(new SessionAggregator())
      .uid("session-aggregator-v1")   // never change this
      .name("session aggregator");
```

Second, if a restore *must* tolerate a removed operator, pass `--allowNonRestoredState` — but only deliberately, since it turns "your state is gone" from an error into a warning.

## 05:02 - [Data Analytics] Ratio Metrics in A/B Tests: The Delta Method, or a 16% False Positive Rate

You randomize by **user**, but report click-through rate as `SUM(clicks) / SUM(impressions)`. The analysis pipeline then computes a standard error as if each *impression* were an independent coin flip. It isn't — impressions from the same user share that user's taste, and the SE comes out far too small.

How bad? An A/A simulation (5,000 users per arm, ~20 impressions each, per-user CTR drawn from Beta(2,18)), run 2,000 times with no true effect:

```
naive  FPR @ alpha=0.05:  16.2%     <- should be 5%
delta  FPR @ alpha=0.05:   4.8%
mean SE naive: 0.000926   delta: 0.001308   (naive understates by 1.41x)
```

One in six A/A tests "wins." Ship that pipeline and your experiment program manufactures results.

**The fix: the delta method.** Aggregate to the randomization unit first, then treat the ratio `R = x̄/ȳ` as a function of two correlated means:

```
Var(R) ≈ ( Var(x) - 2R·Cov(x,y) + R²·Var(y) ) / ( n · ȳ² )
```

where `n` is the number of **users**, and `x_i`, `y_i` are each user's clicks and impressions.

```python
import numpy as np

def ratio_se(x, y):           # x, y are per-USER arrays
    R = x.sum() / y.sum()
    n = len(x)
    cov = np.cov(x, y, ddof=1)
    var = (cov[0,0] - 2*R*cov[0,1] + R**2 * cov[1,1]) / (n * y.mean()**2)
    return R, np.sqrt(var)

Ra, sa = ratio_se(x_ctrl, y_ctrl)
Rb, sb = ratio_se(x_treat, y_treat)
z = (Rb - Ra) / np.sqrt(sa**2 + sb**2)
```

Note the `-2R·Cov(x,y)` term: clicks and impressions are positively correlated, so it *subtracts* variance. Drop it and you overcorrect.

**Practical rules**

- The denominator of your metric is not your unit of analysis. Ask "what did I randomize?" and aggregate to that grain before any variance math.
- Per-user metrics (`AVG(clicks_per_user)`) need no delta method — a plain t-test is fine. The correction is only for ratios whose denominator varies per user.
- Heavier denominator skew means a worse naive SE. Power users are the whole problem.
- Sanity-check with A/A tests. If your false positive rate isn't near alpha, the stats engine is broken, not the feature.

## 10:03 - [ML & AI] Structured Output: Your JSON Schema's Field Order Is the Model's Thinking Order

An LLM generates tokens left to right and cannot revise. Under constrained decoding, the decoder masks out any token that would violate the schema — and in most engines (OpenAI Structured Outputs, `outlines`, vLLM guided JSON, llama.cpp GBNF) the JSON object's keys are emitted **in the order the schema declares them**. So schema order is not cosmetic metadata. It is the order in which the model is forced to commit.

Compare two Pydantic models for a support-ticket classifier:

```python
from pydantic import BaseModel, Field
from typing import Literal

# BAD: label is generated first
class BadOut(BaseModel):
    label: Literal["billing", "bug", "churn_risk"]
    reasoning: str

# GOOD: reasoning tokens exist before the commit
class GoodOut(BaseModel):
    evidence: str = Field(description="Quote the ticket spans that decide this")
    reasoning: str
    label: Literal["billing", "bug", "churn_risk"]
    confidence: float = Field(ge=0, le=1)
```

With `BadOut`, the label token is sampled with zero intermediate computation available — the model must decide in one forward pass, and the `reasoning` field that follows is post-hoc rationalization of a choice already fixed in the context. It will read persuasively and tell you nothing about why the decision was made. With `GoodOut`, the evidence and reasoning tokens are in context when `label` is sampled; the decision conditions on them. Same model, same prompt, different generation order.

Two corollaries:

- **Tight enums are free accuracy.** `Literal[...]` lets the decoder mask every token outside the allowed set, so "ivalid" typos and invented classes become structurally impossible. Don't validate what you can make unrepresentable.
- **Constrained decoding beats retry-and-parse on tail latency.** If free-form parse success is 92%, a retry-once loop lands at 1 − 0.08² = 99.4% — but 8% of requests now pay two full round trips. At p50 800 ms that's a p95 near 1.6 s, and 0.6% still fail. Constraining is 100% by construction with no second call.

Test it on your own data before trusting either ordering: run both schemas over a labeled set of ~200 tickets and compare accuracy directly. The effect size depends on how much reasoning your task actually needs — trivial classifications won't move, multi-hop ones will.

## 15:03 - [Crypto & Business] EIP-1559 Gas: Base Fee, Priority Fee, and Why Your Transaction Sits Pending

Most "my transaction is stuck" problems come from misreading the two-part fee model Ethereum adopted in EIP-1559. Understanding it saves real money.

**The three numbers in your wallet**

- **Base fee** — set by the protocol, not by you. It is *burned*, not paid to anyone.
- **Priority fee** (tip) — what you pay the block proposer to include you.
- **Max fee** — the ceiling you authorize. You pay `base fee + priority fee`, and the difference is refunded.

**How the base fee moves.** Each block has a 15M gas target and a 30M cap. If a block lands above target, the next base fee rises; below target, it falls. The adjustment is capped at **±12.5% per block**. At ~12-second blocks, that means the base fee can roughly double in about 6 blocks (1.125⁶ ≈ 2.03), or ~72 seconds. It cannot spike 10x instantly — but sustained demand compounds fast.

**Worked example.** A simple ERC-20 transfer costs 65,000 gas. Base fee 20 gwei, tip 1 gwei, max fee set to 50 gwei:

- Paid: 65,000 × 21 gwei = 1,365,000 gwei = **0.001365 ETH**
- Refunded: 65,000 × 29 gwei = 0.001885 ETH

You are not charged your max fee. Setting it high is a *buffer against base-fee drift*, not an overpayment — this is the single most common misconception.

**Why transactions stick.** Two distinct causes:

1. **Max fee below current base fee.** Your transaction is not even eligible for inclusion. It will sit until the base fee falls back under your ceiling. A high max fee prevents this entirely at no extra cost.
2. **Tip too low.** You are eligible but outbid. Raising the tip is what fixes this.

**The fix:** resubmit with the *same nonce* and a higher fee — most wallets label this "speed up." Note the replacement requires at least a ~10% bump on both fields to be accepted by the mempool. A "cancel" is the same trick sending 0 ETH to yourself.

**Practical habit:** check the base fee before signing anything non-urgent. Weekend and off-peak base fees routinely run a fraction of weekday-afternoon levels — the identical transaction, materially cheaper.
