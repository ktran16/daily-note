# Daily Notes - 2026-09-03

## 00:03 - [Data Engineering] Kafka Exactly-Once: Why `enable.idempotence` Alone Doesn't Give You EOS

"Exactly-once" in Kafka is three separate mechanisms, and turning on the first one — which most teams do — buys you far less than the name suggests.

**1. The idempotent producer** (`enable.idempotence=true`, default since 3.0). The producer stamps each batch with a producer ID and a monotonic sequence number per partition. If an ack is lost and the client retries, the broker sees a duplicate sequence and drops it. This kills *producer retry* duplicates only, and only within a single producer session on a single partition. It does nothing about your application re-processing a message after a crash.

**2. Transactions** make a set of writes atomic across partitions, and — critically — let you commit *consumer offsets inside the same transaction* as the output records. That closes the read-process-write loop: either the output and the offset advance together, or neither does.

```java
props.put("transactional.id", "enrich-orders-v1");  // stable across restarts
producer.initTransactions();

while (true) {
  var records = consumer.poll(Duration.ofMillis(200));
  producer.beginTransaction();
  for (var r : records) producer.send(transform(r));
  producer.sendOffsetsToTransaction(offsetsOf(records), consumer.groupMetadata());
  producer.commitTransaction();
}
```

Two details decide whether this works. `transactional.id` must be **stable per logical task** — if it's random on restart, zombie fencing never happens and a stalled old instance can keep writing. And the consumer must set `isolation.level=read_committed`, or it will read aborted records anyway.

**3. Downstream sinks.** Transactions cover Kafka-to-Kafka. The moment you write to Postgres, S3, or Snowflake, exactly-once depends on that sink being idempotent — a `MERGE` on a natural key, or a dedupe on `(topic, partition, offset)` stored alongside the row.

The practical takeaway: transactions cost throughput (extra round trips, and `read_committed` consumers wait for the LSO). For most analytical pipelines, at-least-once delivery plus an idempotent upsert at the sink is cheaper, simpler, and equally correct. Reach for EOS when the processing itself is stateful and non-replayable — counters, joins, ledger balances — not by default.
