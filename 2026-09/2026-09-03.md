## 00:03 - [Data Engineering] Kafka Exactly-Once: Why `enable.idempotence` Alone Doesn't Give You EOS

"Exactly-once" in Kafka is three separate mechanisms, and turning on the first one — which most teams do — buys you far less than the name suggests.

**1. The idempotent producer** (`enable.idempotence=true`, default since 3.0). The producer stamps each batch with a producer ID and a monotonic sequence number per partition. If an ack is lost and the client retries, the broker sees a duplicate sequence and drops it. This kills *producer retry* duplicates only, and only within a single producer session on a single partition. It does nothing about your application re-processing a message after a crash.

**2. Transactions** make a set of writes atomic across partitions, and — critically — let you commit *consumer offsets inside the same transaction* as the output records. That closes the read-process-write loop: either the output and the offset advance together, or neither does.

```java
props.put("transactional.id", "enrich-orders-v1");  // stable across restarts
producer.initTransactions();

while (true) {
  var records = consumer.poll(Duration.ofMillis(200));
  producer.beginTransaction();
  for (var r : records) producer.send(transform(r));
  producer.sendOffsetsToTransaction(offsetsOf(records), consumer.groupMetadata());
  producer.commitTransaction();
}
```

Two details decide whether this works. `transactional.id` must be **stable per logical task** — if it's random on restart, zombie fencing never happens and a stalled old instance can keep writing. And the consumer must set `isolation.level=read_committed`, or it will read aborted records anyway.

**3. Downstream sinks.** Transactions cover Kafka-to-Kafka. The moment you write to Postgres, S3, or Snowflake, exactly-once depends on that sink being idempotent — a `MERGE` on a natural key, or a dedupe on `(topic, partition, offset)` stored alongside the row.

The practical takeaway: transactions cost throughput (extra round trips, and `read_committed` consumers wait for the LSO). For most analytical pipelines, at-least-once delivery plus an idempotent upsert at the sink is cheaper, simpler, and equally correct. Reach for EOS when the processing itself is stateful and non-replayable — counters, joins, ledger balances — not by default.

## 05:04 - [Data Analytics] Sample Size and MDE: Why Most A/B Tests Are Powered to Find Nothing

Most failed experiments aren't inconclusive because the feature didn't work. They're inconclusive because the test never had a chance of detecting the effect it was looking for. "No significant difference" and "no difference" are not the same statement, and the gap between them is **power**.

The number that matters before launch is the **minimum detectable effect (MDE)** — the smallest lift your sample size can reliably distinguish from noise. For a two-proportion test:

```python
from statistics import NormalDist

def n_per_arm(p1, rel_lift, alpha=0.05, power=0.80):
    p2 = p1 * (1 + rel_lift)
    z_a = NormalDist().inv_cdf(1 - alpha / 2)   # 1.960
    z_b = NormalDist().inv_cdf(power)           # 0.842
    var = p1 * (1 - p1) + p2 * (1 - p2)
    return (z_a + z_b) ** 2 * var / (p2 - p1) ** 2

for lift in (0.05, 0.10, 0.20):
    print(lift, round(n_per_arm(0.05, lift)))
# 0.05 -> 122121
# 0.10 ->  31231
# 0.20 ->   8155
```

At a 5% baseline conversion, detecting a **20% relative lift** takes 8,155 users per arm. Detecting a **5% lift** takes 122,121 — 15× more, because sample size scales with **1/MDE²**. Halving the effect you want to catch quadruples the traffic you need.

That quadratic is the whole planning conversation. At 20,000 users per arm per day, the 5% test needs 6.1 days; a 2% test would need 38. If you can't run that long, you cannot detect 2% — so don't pretend the readout will tell you anything about it.

Three things quietly break this calculation in practice:

- **Absolute vs relative lift.** "5% lift" on a 5% baseline means 5.25%, not 10%. Mixing these up understates required sample size by ~4×.
- **Randomizing on accounts, measuring on events.** Sessions within a user are correlated, so the true variance is larger than the formula assumes. Inflate n by the design effect, `1 + (m-1)·ICC`, or run the test on user-level aggregates.
- **Heavy-tailed metrics.** Revenue per user is dominated by a few whales. Winsorize at the 99th percentile, or test log-revenue / conversion instead — the variance reduction often beats any traffic increase you could buy.

Write the MDE and the planned duration into the test doc **before** launch. It converts "we'll see what happens" into a falsifiable commitment, and it kills underpowered tests while they're still cheap.

## 10:03 - [ML & AI] Scaled Dot-Product Attention: What the √d Is Actually For

Attention is one line: `softmax(QKᵀ/√d_k)·V`. Every token emits a **query** ("what am I looking for?"), a **key** ("what do I offer?"), and a **value** ("what I'll contribute if picked"). The dot product `q·k` scores relevance, softmax turns scores into weights summing to 1, and the output is a weighted average of value vectors. Attention is *soft lookup*: a differentiable dictionary where you retrieve a blend of every entry.

```python
def attention(Q, K, V, mask=None):
    d_k = Q.shape[-1]
    scores = Q @ K.T / np.sqrt(d_k)          # (n_q, n_k)
    if mask is not None:                      # causal: no peeking ahead
        scores = np.where(mask, scores, -np.inf)
    w = np.exp(scores - scores.max(-1, keepdims=True))
    w /= w.sum(-1, keepdims=True)             # stable softmax
    return w @ V, w
```

Worked example, `d_k = 4`. One query `q = [1,0,1,0]` against three keys:

| key | `q·k` | scaled (÷2) | weight |
|---|---|---|---|
| `[1,0,1,0]` | 2.0 | 1.0 | **0.507** |
| `[0,1,0,1]` | 0.0 | 0.0 | 0.186 |
| `[.5,.5,.5,.5]` | 1.0 | 0.5 | 0.307 |

With values `[[1,0],[0,1],[.5,.5]]` the output is `[0.660, 0.340]` — over half of key 1, the rest blended in.

**Why divide by √d_k?** If `q` and `k` have roughly independent unit-variance components, `q·k` is a sum of `d_k` such products, so its **variance is d_k** and its magnitude grows like `√d_k`. Empirically: at `d=4` the dot products have std 2.0; at `d=128`, std 11.3. Feed logits with std 11 into softmax and the largest one wins almost every time — the distribution saturates to near-one-hot, and softmax's gradient (`p(1−p)`) collapses toward zero. Training stalls. Dividing by `√d_k` renormalizes logit variance back to ~1 so gradients keep flowing.

Note the same effect above: unscaled, the weights sharpen to `[0.665, 0.090, 0.245]`. That's the mechanism in miniature — the scale factor is a temperature control, not cosmetics.

## 15:04 - [Crypto & Business] Optimistic vs ZK Rollups: What You Actually Trade Away for Cheap Fees

A rollup executes transactions off-chain, then posts compressed data + proof back to Ethereum L1. You inherit L1 security while paying a fraction of L1 gas. The two families differ in *how* they convince L1 the off-chain state is honest — and that single choice cascades into cost, latency, and withdrawal risk.

**Optimistic rollups (Arbitrum, Base, OP Mainnet)** assume batches are valid and let anyone submit a *fraud proof* during a challenge window — typically **7 days**. Cheap to compute (no proof to generate), but your funds are provably safe only after the window closes.

**ZK rollups (zkSync, Starknet, Linea)** post a *validity proof* (a SNARK/STARK) with every batch. L1 verifies it mathematically, so state is final in minutes to an hour. The catch: generating proofs is compute-heavy, and full EVM equivalence is harder to achieve.

**Where the cost actually goes.** Since EIP-4844 (blobs, March 2024), the dominant cost is L1 *data availability*, not execution. A swap that costs ~$3–15 on L1 mainnet often lands at **$0.01–0.20** on an L2. Rough model:

```
L2 fee ≈ (your share of blob/calldata cost) + (small L2 execution fee) + sequencer margin
```

Batching 500 transactions into one blob splits the fixed L1 posting cost 500 ways — that's the whole savings mechanism.

**Practical implications:**
- **Withdrawals:** native optimistic withdrawal = wait ~7 days, or pay a *liquidity bridge* a fee (often 0.05–0.3%) to front you funds instantly. ZK withdrawals settle in ~hours.
- **Sequencer risk:** most L2s run a single centralized sequencer today. It can't steal funds (L1 settlement protects you) but can censor or reorder short-term. "Escape hatches" to force-include a tx on L1 are your backstop.
- **Bridged ≠ native:** a token bridged via a third-party bridge carries that bridge's smart-contract risk, separate from the rollup's.

*Educational content, not financial advice.*

## 19:03 - [PC Hardware] Undervolting and Power Limits: 95% of the Performance for 70% of the Power

Modern CPUs and GPUs ship with voltage curves tuned for the *worst* silicon that passed binning, plus a safety margin. Your specific chip is almost always better than that. Undervolting reclaims the margin — and because power scales roughly with V² × f, small voltage cuts pay outsized dividends.

**The efficiency curve is brutally non-linear.** The last 5–8% of clock speed typically costs 30–40% of total power. Real-world shape on a modern 350 W-class GPU:

| Power limit | Typical perf | Perf/watt |
|---|---|---|
| 100% (350 W) | 100% | 1.00× |
| 85% (300 W) | ~97% | 1.13× |
| 70% (245 W) | ~92% | 1.31× |
| 55% (190 W) | ~82% | 1.51× |

Losing 3% of frames to drop 50 W — and the fan noise and case heat that come with it — is usually the right trade.

**GPU, the lazy way (2 minutes):** just cap the power limit. Windows: MSI Afterburner, drag Power Limit to 80%. Linux: `sudo nvidia-smi -pl 250`. Done — no stability risk, since you're only removing headroom.

**GPU, the proper way (30 minutes):** Afterburner's curve editor (Ctrl+F). Pick a target like 2700 MHz @ 950 mV, drag that point up, flatten everything to its right, apply. This holds higher sustained clocks than a power cap because the card stops wasting budget on voltage.

**CPU:** AMD Ryzen uses **PBO Curve Optimizer** — start at all-core `-15`, test, then per-core tune (best-boosting cores are usually least tolerant). Intel uses a negative **core voltage offset**, typically `-50` to `-125 mV`.

**Validate or you're just gambling.** Undervolt instability is sneaky: it shows up under *light* loads at high boost, not stress tests. Run OCCT or `y-cruncher` for 30 min, plus Cinebench, plus a few hours of real use. Silent WHEA errors and rare app crashes are the tell — check Windows Event Viewer, or `journalctl -k | grep -i mce` on Linux.

Back off 2–3 steps from your first failure, not one.
