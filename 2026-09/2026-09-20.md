## 00:02 - [Data Engineering] One Big Table vs Star Schema: When Denormalization Actually Wins

Columnar warehouses broke an old assumption. Kimball's star schema exists partly because row-store joins were expensive and storage was scarce. On Snowflake/BigQuery/Databricks, columnar pruning means unread columns cost nothing at query time, and storage is cheap — which is why **One Big Table (OBT)**, a fully denormalized wide mart, became a credible pattern rather than a rookie mistake.

**The OBT shape:** one row per fact, with every dimension attribute flattened in.

```sql
-- models/marts/obt_orders.sql
select
    o.order_id,
    o.ordered_at,
    o.order_total,
    -- customer attributes, flattened
    c.customer_name,
    c.customer_segment,
    c.country,
    -- product attributes, flattened
    p.product_name,
    p.category,
    p.brand
from {{ ref('fct_orders') }} o
left join {{ ref('dim_customers') }} c using (customer_id)
left join {{ ref('dim_products') }}  p using (product_id)
```

**What OBT buys you:** no joins at query time, so BI tools and analysts can't get them wrong. Fan-out double counting disappears. Query planners have less to do, and the table clusters cleanly on a date column.

**What it costs you:**

| Concern | Star schema | OBT |
|---|---|---|
| Attribute change | Update one dim row | Rebuild/backfill the whole mart |
| Storage | Minimal | Duplicated across every fact row |
| Multi-grain analysis | Natural | Needs a second OBT per grain |
| Conformed dimensions | Shared by design | Re-flattened per table, drifts apart |

The killer is **history semantics**. A star schema with a Type 2 dimension lets you choose as-of-transaction vs as-of-today by which key you join on. An OBT freezes one choice at build time — and if you rebuild it fully each night from current dimension values, you have silently converted every attribute to Type 1 and destroyed historical accuracy. Snapshot-join deliberately if history matters:

```sql
left join {{ ref('dim_customers_snapshot') }} c
    on  c.customer_id = o.customer_id
    and o.ordered_at >= c.dbt_valid_from
    and o.ordered_at <  coalesce(c.dbt_valid_to, '9999-12-31')
```

**The practical answer is both.** Keep conformed facts and dimensions as your governed core in the intermediate/mart layer — that is where tests, contracts, and SCD logic live. Then build OBTs on top as consumption-layer views for specific dashboards or ML feature sets. The star schema is your source of truth; the OBT is a cache of one join path. Treat it as derived, never as the place where business logic is defined.

## 05:02 - [Data Analytics] Forecast Baselines: Seasonal Naive First, and Why MAPE Picks the Wrong Model

Most forecasting projects skip the only step that tells you whether the model is worth anything: a baseline. "Our model has 8% MAPE" is meaningless until you know what copying last week scores.

**The baseline is seasonal naive.** Predict each day with the value from `m` periods ago — `m=7` for daily business data, `12` for monthly. It costs one line and is startlingly hard to beat on weekly-seasonal series like orders, logins, or tickets.

```python
import numpy as np, pandas as pd

rng  = pd.date_range("2026-01-01", periods=120, freq="D")
week = np.array([1.00, 0.98, 1.02, 1.05, 1.30, 0.70, 0.60])   # Mon..Sun
y    = pd.Series((1000 + np.arange(120) * 2) * week[rng.dayofweek], index=rng)

train, test = y[:-28], y[-28:]
snaive = y.shift(7).loc[test.index]        # the baseline
```

**Then score against it, not against zero.** MASE divides your MAE by the in-sample seasonal-naive MAE, so the number has a fixed meaning: **1.0 = tied with the baseline, >1.0 = worse than copying last week.**

```python
def mase(actual, pred, train, m=7):
    scale = np.mean(np.abs(train.values[m:] - train.values[:-m]))
    return np.mean(np.abs(actual - pred)) / scale

mase(test, snaive, train)     # ~1.0 by construction
```

**Why not MAPE?** Two reasons it quietly misleads.

*It is asymmetric.* Under-forecasting caps at 100% error (predict 0 against an actual of 100 → 100%), while over-forecasting is unbounded (predict 300 → 200%). Any model tuned on MAPE drifts low. If you forecast inventory or capacity on it, you will systematically under-stock.

*It explodes near zero.* One quiet day with 2 actual units and a forecast of 10 contributes 400% to the average and swamps 90 good days.

| Metric | Scale-free | Safe at zero | Symmetric | Baseline-anchored |
|---|---|---|---|---|
| MAE | no | yes | yes | no |
| MAPE | yes | **no** | **no** | no |
| MASE | yes | yes | yes | **yes** |

**Practical rule:** report MAE in business units for the stakeholder ("off by 40 orders/day") and MASE for the model decision. If MASE ≥ 1, ship the naive forecast — it is free, explainable, and never breaks. Beating the baseline by 15–20% on genuinely seasonal data is a real result; most first attempts land above 1.0 and nobody notices because MAPE looked respectable.

## 10:02 - [ML & AI] Walk-Forward Validation: Why K-Fold Quietly Trains on the Future

`cross_val_score(model, X, y, cv=5)` shuffles by default. On time-ordered data that means four folds of training rows dated *after* the rows you're scoring. The model learns the level of a trend it hasn't reached, the volatility of a regime it hasn't entered, and reports a score you will never reproduce in production. This isn't feature leakage — the features are clean. The *split* is the leak.

**The fix is an expanding (or rolling) window.** Train on 1..t, test on t+1..t+h, slide forward, repeat:

```python
from sklearn.model_selection import TimeSeriesSplit, cross_val_score

tscv = TimeSeriesSplit(n_splits=5, test_size=30, gap=7)
scores = cross_val_score(pipe, X, y, cv=tscv,
                         scoring="neg_mean_absolute_error")
```

With 365 daily rows the five test blocks are the final 150 days, and training sets grow 208 → 238 → 268 → 298 → 328 days (each ends `gap` rows before its test block starts). Every test block is strictly later than its training block.

**`gap` is the part people skip.** If your target is "churned within 7 days," the label for day *t* is only knowable at day *t+7*. Training on day *t* and testing on day *t+1* means the training label encoded information from the test period. `gap=7` (López de Prado's *embargo*) drops the overlapping rows. Rule: **gap ≥ the label horizon**, plus any feature lookahead in rolling aggregates.

**Two consequences worth planning for:**

1. **Folds aren't exchangeable.** Fold 1 trains on 208 days, fold 5 on 328. Their scores differ partly because of data volume, not model quality. Report the *last* fold or a recency-weighted mean when you care about deployment performance; the plain average flatters the early, easy regimes.
2. **Variance is real signal.** MAE of `[4.1, 4.3, 9.8, 4.0, 4.2]` isn't noise to average away — fold 3 hit a regime shift. Plot per-fold error against fold start date before you touch hyperparameters.

**Final holdout:** reserve the most recent block *before* any tuning, and never let `TimeSeriesSplit` see it. Tuned walk-forward CV still measures the search (covered previously under nested CV); the trailing block is the only estimate that hasn't been optimized against.

If shuffled K-fold beats walk-forward by a wide margin, that gap *is* the measurement — it's the amount of your score that came from seeing the future.

## 15:02 - [Crypto & Business] Price Oracles: How a Lending Protocol Learns What ETH Costs — and How Attackers Lie to It

A smart contract cannot make an HTTP call. So every lending market, perp exchange, and stablecoin vault needs an oracle to answer "what is ETH worth?" — and that answer is the single most attacked surface in DeFi.

**Push oracles** (Chainlink-style): a node network aggregates exchange prices off-chain and writes the median on-chain when one of two triggers fires — a *deviation threshold* (0.5% for ETH/USD on mainnet) or a *heartbeat* (e.g. 3600s). Implication: between updates the on-chain price is legitimately stale by up to the threshold. Consumers must read `updatedAt` from `latestRoundData()` and revert if it's older than the heartbeat. A long list of exploits is just contracts ignoring that field.

**Pull oracles** (Pyth-style): the price is signed off-chain continuously; the *caller* submits the signed update inside their own transaction. Sub-second freshness, but the user pays the update fee and gas.

**DEX spot price**: the classic mistake. Take a constant-product pool holding 1,000 ETH and 2,000,000 USDC — spot price $2,000, k = 2×10⁹. An attacker flash-borrows 5,000,000 USDC and swaps it in. USDC reserve → 7,000,000; ETH reserve → 2×10⁹ / 7×10⁶ ≈ 285.7. Spot price is now 7,000,000 / 285.7 ≈ **$24,500** — a 12× move, in one transaction, borrowed and repaid atomically. Any protocol valuing collateral at that spot price hands over its treasury.

**TWAP** is the mitigation: a 30-minute time-weighted average forces the attacker to hold the fake price across many blocks while arbitrageurs bleed them each block, so manipulation cost scales with duration. The trade-off is lag — during a genuine fast drawdown, a 30-minute TWAP liquidates late and the protocol eats bad debt.

**What to check on any protocol**: which oracle, its heartbeat and deviation threshold, whether staleness reverts, whether there's a min/max price bound or circuit breaker, and what happens if the feed dies.

## 19:02 - [PC Hardware] Variable Refresh Rate: The FPS Cap That Makes G-Sync Actually Work

A VRR monitor makes the display wait for the GPU instead of the other way around. Without it you get two failure modes: VSync on, where a frame that misses the 6.94 ms budget at 144 Hz waits a full refresh (144 → 72 fps, a visible hitch), or VSync off, where the scanout switches mid-screen and you get tearing.

**The range is the spec that matters.** A panel advertised as "48–144 Hz VRR" only varies inside that window. Below 48 fps the hardware can't stretch a refresh further, so drivers use **Low Framerate Compensation**: at 30 fps they draw each frame twice at 60 Hz, keeping it inside the range. LFC needs max ≥ 2.0–2.5× min, so 48–144 works and 60–144 does not — a 60 Hz floor means anything under 60 fps falls back to tearing or stutter. Check the range, not just the logo.

**The top of the range is where people get it wrong.** Once your frame rate reaches the panel's max, VRR is saturated and you're back to plain VSync (input lag) or tearing. The fix is a cap a few frames below max:

| Panel max | Cap to |
|---|---|
| 144 Hz | 141 |
| 165 Hz | 162 |
| 240 Hz | 236 |

The canonical config: VRR on in the monitor OSD *and* the driver, **VSync on in the driver** (it only engages at the ceiling as a tear guard), VSync **off** in-game, and the cap set in-game if it has a good limiter, otherwise RTSS or the driver's frame limiter. Driver-level caps add roughly a frame of latency versus an engine-level one.

Two gotchas: VRR usually applies to fullscreen-exclusive or a properly flipping borderless window — check the OSD's refresh readout actually moves. And on many panels VRR interacts with overdrive, so a fixed overdrive setting tuned for 144 Hz can smear at 60 fps; look for "variable overdrive" in reviews.

Verify with the pendulum demo or by watching the OSD counter track your frame rate.
