## 00:02 - [Data Engineering] One Big Table vs Star Schema: When Denormalization Actually Wins

Columnar warehouses broke an old assumption. Kimball's star schema exists partly because row-store joins were expensive and storage was scarce. On Snowflake/BigQuery/Databricks, columnar pruning means unread columns cost nothing at query time, and storage is cheap — which is why **One Big Table (OBT)**, a fully denormalized wide mart, became a credible pattern rather than a rookie mistake.

**The OBT shape:** one row per fact, with every dimension attribute flattened in.

```sql
-- models/marts/obt_orders.sql
select
    o.order_id,
    o.ordered_at,
    o.order_total,
    -- customer attributes, flattened
    c.customer_name,
    c.customer_segment,
    c.country,
    -- product attributes, flattened
    p.product_name,
    p.category,
    p.brand
from {{ ref('fct_orders') }} o
left join {{ ref('dim_customers') }} c using (customer_id)
left join {{ ref('dim_products') }}  p using (product_id)
```

**What OBT buys you:** no joins at query time, so BI tools and analysts can't get them wrong. Fan-out double counting disappears. Query planners have less to do, and the table clusters cleanly on a date column.

**What it costs you:**

| Concern | Star schema | OBT |
|---|---|---|
| Attribute change | Update one dim row | Rebuild/backfill the whole mart |
| Storage | Minimal | Duplicated across every fact row |
| Multi-grain analysis | Natural | Needs a second OBT per grain |
| Conformed dimensions | Shared by design | Re-flattened per table, drifts apart |

The killer is **history semantics**. A star schema with a Type 2 dimension lets you choose as-of-transaction vs as-of-today by which key you join on. An OBT freezes one choice at build time — and if you rebuild it fully each night from current dimension values, you have silently converted every attribute to Type 1 and destroyed historical accuracy. Snapshot-join deliberately if history matters:

```sql
left join {{ ref('dim_customers_snapshot') }} c
    on  c.customer_id = o.customer_id
    and o.ordered_at >= c.dbt_valid_from
    and o.ordered_at <  coalesce(c.dbt_valid_to, '9999-12-31')
```

**The practical answer is both.** Keep conformed facts and dimensions as your governed core in the intermediate/mart layer — that is where tests, contracts, and SCD logic live. Then build OBTs on top as consumption-layer views for specific dashboards or ML feature sets. The star schema is your source of truth; the OBT is a cache of one join path. Treat it as derived, never as the place where business logic is defined.
