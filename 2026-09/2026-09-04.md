## 00:03 - [Data Engineering] Airflow Deferrable Operators: Stop Paying a Worker Slot to Sleep

A classic Airflow sensor in default `poke` mode holds a worker slot for its entire life. Waiting six hours for an upstream S3 prefix means six hours of a slot doing nothing but `sleep(60)`. Thirty such sensors on a 32-slot pool and your DAGs deadlock — the tasks that would satisfy the sensors can't get a slot to run.

**The half-fix: `mode="reschedule"`.** The sensor exits between pokes and Airflow re-queues it later, freeing the slot while it waits. But every poke pays full task startup (process spawn, DAG parse, DB writes), so a 30-second poke interval is wasteful and the scheduler carries the churn.

**The real fix: deferrable operators.** A deferrable task runs until it hits a wait, then raises `TaskDeferred` with a *trigger* — a small asyncio coroutine — and releases its slot entirely. The trigger runs in the `triggerer` process, where thousands of them share one event loop. When it fires, the task is re-queued and resumes at a designated method.

```python
from airflow.providers.amazon.aws.sensors.s3 import S3KeySensor

wait_for_drop = S3KeySensor(
    task_id="wait_for_drop",
    bucket_key="s3://raw/orders/{{ ds }}/_SUCCESS",
    deferrable=True,          # provider-wide convention
    poke_interval=60,
    timeout=60 * 60 * 6,      # always set one
)
```

Most modern providers accept `deferrable=True`; you can flip the default globally:

```ini
[operators]
default_deferrable = True
```

This applies beyond sensors. `DatabricksRunNowOperator`, `BigQueryInsertJobOperator`, `KubernetesPodOperator` and friends all have deferrable modes — submit the job, defer, wake on completion. Long-running external jobs are where the biggest slot savings are.

**Practical notes:**

- You must actually run `airflow triggerer`. Without it, deferred tasks hang forever in `deferred` state. Check `triggerer_heartbeat` in your monitoring.
- Trigger arguments are serialized to the metadata DB — pass connection *IDs*, not connection objects or clients.
- Deferring resets the task's execution timeout accounting in some versions; rely on the operator's own `timeout`, and set `execution_timeout` as a backstop.
- Triggers must never block the event loop. Custom triggers using a sync HTTP client will stall every other trigger on that triggerer.

Rule of thumb: if a task's job is to wait, it should be deferrable.

## 05:04 - [Data Analytics] DAX Filter Context: Why Your "% of Total" Measure Always Returns 100%

Almost every Power BI bug traces back to one idea: a DAX measure is evaluated once per cell, inside whatever **filter context** that cell inherits from the visual. Get that, and `CALCULATE` stops being magic.

Say `Sales` has 1,000,000 rows across 4 regions, `SUM(Sales[Amount])` = $8.4M total, North = $2.1M.

```dax
Total Sales = SUM(Sales[Amount])
```

In a table sliced by region, the North row evaluates that measure with `Region = "North"` already applied — you get $2.1M, not $8.4M. Nothing in the formula says "North"; the visual supplied it.

Now the classic mistake:

```dax
Pct of Total = DIVIDE([Total Sales], [Total Sales])   -- always 1.00
```

Both halves see the same context. The denominator must **escape** it. That is `CALCULATE`'s only job — run an expression under a modified filter context:

```dax
Pct of Total =
DIVIDE(
    [Total Sales],
    CALCULATE([Total Sales], REMOVEFILTERS(Sales[Region]))
)
```

North now returns 2.1 / 8.4 = **25.0%**.

Pick the remover deliberately — this is where numbers quietly go wrong:

| Modifier | Effect on the denominator |
|---|---|
| `REMOVEFILTERS(Sales[Region])` | Clears region only; a Year slicer still applies → % within the selected year |
| `REMOVEFILTERS(Sales)` | Clears the whole table → % of all time, ignores slicers |
| `ALLSELECTED(Sales[Region])` | Respects the user's slicer selection but ignores the visual's own row grouping |

If your percentages sum to 100% inside a page but a stakeholder insists they should sum to less, you almost certainly want `ALLSELECTED` where you used `REMOVEFILTERS`, or vice versa.

**The other half: row context.** A calculated *column* has row context but no filter context — it's computed at refresh, frozen into the model, and blind to slicers. A measure is computed at query time. If a value must react to what the user clicks, it has to be a measure. Writing it as a column is the #1 cause of "the number doesn't change when I filter."

`CALCULATE` also converts row context to filter context (context transition), which is why `CALCULATE(SUM(...))` inside `SUMX` behaves differently than the bare aggregate — worth knowing before you debug an iterator at 5pm.
