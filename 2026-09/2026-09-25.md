## 00:04 - [Data Engineering] `insert_overwrite`: The Incremental Strategy That Replaces Partitions Instead of Rows

`merge` is dbt's default incremental strategy on most warehouses, and on a wide partitioned fact table it is often the wrong one. A merge matches every incoming row against the target by `unique_key`. If the engine can't prune partitions from that join, you pay a full-table scan on every run — and you still need a genuinely unique key, or the merge either errors or silently keeps the wrong row.

`insert_overwrite` sidesteps the key entirely. It computes which partitions the new batch touches, deletes those partitions wholesale, and inserts the batch. The grain of the operation is the partition, not the row.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={'field': 'event_date', 'data_type': 'date'},
) }}

select event_date, user_id, count(*) as events
from {{ ref('stg_events') }}
{% if is_incremental() %}
  where event_date >= date_sub(current_date(), interval 3 day)
{% endif %}
group by 1, 2
```

The property that matters: **re-running is idempotent**. A backfill of the same three days produces the same table, because the old partitions are dropped before the new ones land. Under `merge`, a rerun after an upstream fix leaves orphaned rows for keys that no longer exist in the source — the merge has no way to know a row was deleted.

Two footguns:

**Dynamic vs. static partitions.** By default dbt runs a scripted statement that queries your SELECT to discover the partition list, then overwrites those. Setting `partitions` explicitly (e.g. `partitions=dbt.partition_range(var('dates'))` on BigQuery) skips the discovery query and is cheaper — but you must supply the exact list, and anything outside it is silently not written.

**Partial partitions.** If your filter cuts mid-partition, you overwrite a whole day with a fraction of its rows. Always align the incremental `where` clause to partition boundaries.

Rule of thumb: append-only event data with a partition column → `insert_overwrite`. Dimension-like tables with real updates on a true primary key → `merge`.

## 05:04 - [Data Analytics] Dual-Axis Charts: The Correlation You Manufactured by Sliding One Scale

A dual-axis chart puts two series with different units on one canvas — revenue on the left, support tickets on the right — and the implied claim is "these move together." The problem is that nothing in that claim is measured. The right-hand axis range is a free parameter, and whoever picks it decides how tightly the two lines hug.

Take twelve months where revenue goes 1.20M → 1.26M (+5%) and tickets go 400 → 520 (+30%). Anchor the right axis at 0–600 and the lines diverge dramatically. Set it to 380–540 instead and they trace nearly the same path. Same data, opposite story, and neither version is "wrong" — the axis was never specified by the data.

The tell: Pearson's *r* is invariant under affine rescaling. Sliding the right axis cannot change the correlation by a single decimal place, yet it changes what a reader sees completely. That gap between what the eye reads (slope proximity) and what the data says (*r*) is the whole failure mode.

Three honest replacements:

```python
import pandas as pd

df = pd.DataFrame({"revenue": rev, "tickets": tix})

# 1. Index both to 100 at the first period — one axis, comparable growth
idx = df.div(df.iloc[0]).mul(100)
idx.plot(ylabel="Index (month 1 = 100)")

# 2. If the relationship IS the metric, plot it directly
(df["tickets"] / (df["revenue"] / 1_000)).plot(ylabel="Tickets per $1k revenue")

# 3. Report the number you are implying
print(df["revenue"].corr(df["tickets"]).round(2))
```

Option 3 is the discipline check. With n=12 monthly points, r = 0.55 carries p ≈ 0.06 — you do not have the evidence the chart is projecting. You need roughly r ≥ 0.58 at n=12 to clear p < 0.05, and monthly data rarely gives you more points than that.

Small multiples — two stacked panels sharing an x-axis — beat a dual axis nearly every time: the reader compares shapes without being handed a manufactured overlap.

Dual axis is defensible in one case: when the right axis is a fixed, deterministic transform of the left (°C/°F, USD/EUR at a pegged rate). Then it is a second set of tick labels, not a second claim.
