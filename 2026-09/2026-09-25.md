# Daily Notes - 2026-09-25

## 00:04 - [Data Engineering] `insert_overwrite`: The Incremental Strategy That Replaces Partitions Instead of Rows

`merge` is dbt's default incremental strategy on most warehouses, and on a wide partitioned fact table it is often the wrong one. A merge matches every incoming row against the target by `unique_key`. If the engine can't prune partitions from that join, you pay a full-table scan on every run — and you still need a genuinely unique key, or the merge either errors or silently keeps the wrong row.

`insert_overwrite` sidesteps the key entirely. It computes which partitions the new batch touches, deletes those partitions wholesale, and inserts the batch. The grain of the operation is the partition, not the row.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={'field': 'event_date', 'data_type': 'date'},
) }}

select event_date, user_id, count(*) as events
from {{ ref('stg_events') }}
{% if is_incremental() %}
  where event_date >= date_sub(current_date(), interval 3 day)
{% endif %}
group by 1, 2
```

The property that matters: **re-running is idempotent**. A backfill of the same three days produces the same table, because the old partitions are dropped before the new ones land. Under `merge`, a rerun after an upstream fix leaves orphaned rows for keys that no longer exist in the source — the merge has no way to know a row was deleted.

Two footguns:

**Dynamic vs. static partitions.** By default dbt runs a scripted statement that queries your SELECT to discover the partition list, then overwrites those. Setting `partitions` explicitly (e.g. `partitions=dbt.partition_range(var('dates'))` on BigQuery) skips the discovery query and is cheaper — but you must supply the exact list, and anything outside it is silently not written.

**Partial partitions.** If your filter cuts mid-partition, you overwrite a whole day with a fraction of its rows. Always align the incremental `where` clause to partition boundaries.

Rule of thumb: append-only event data with a partition column → `insert_overwrite`. Dimension-like tables with real updates on a true primary key → `merge`.
