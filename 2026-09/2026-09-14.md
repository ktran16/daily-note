## 00:03 - [Data Engineering] Airflow's Data Interval: Why Today's Run Has Yesterday's Date

A daily DAG scheduled at 02:00 fires on 2026-09-14, but its logical date is **2026-09-13**. This confuses nearly everyone once. Airflow schedules a run *after* its data interval has closed — the run that starts at 02:00 on the 14th is the one that processes the 13th. It is a batch system: you cannot summarize a day until the day is over.

Two fields express this, and they are the only ones you should use:

| Template var | Daily DAG firing 2026-09-14 02:00 |
|---|---|
| `data_interval_start` | 2026-09-13 00:00 |
| `data_interval_end` | 2026-09-14 00:00 |
| `ds` (logical date) | 2026-09-13 |

`execution_date` is the old name for the interval *start*, and its "date of execution" reading is exactly backwards. It was deprecated in Airflow 2.2 and removed in Airflow 3 — use `logical_date` or the interval fields.

The practical rule: **never let a task read the wall clock.** `CURRENT_DATE` or `datetime.now()` inside a task means a rerun produces different output than the original run, which quietly destroys backfills.

```sql
-- Wrong: a rerun next week reprocesses the wrong window
WHERE event_at >= CURRENT_DATE - 1

-- Right: bound by the run's own interval, half-open
WHERE event_at >= '{{ data_interval_start }}'
  AND event_at <  '{{ data_interval_end }}'
```

Half-open bounds (`>=` start, `<` end) matter — `BETWEEN` double-counts the boundary row in adjacent runs.

`catchup` decides what happens for intervals that elapsed while the DAG was off:

```python
with DAG(
    dag_id="daily_revenue",
    start_date=datetime(2026, 1, 1),
    schedule="0 2 * * *",
    catchup=True,        # backfill every interval since start_date
    max_active_runs=1,   # ...but one at a time
):
```

With `catchup=True`, unpausing a DAG that sat idle for three weeks queues 21 runs at once — enough to saturate a warehouse. Always pair it with `max_active_runs`. Set `catchup=False` for jobs that only care about current state (a full-refresh snapshot, a health check), where replaying history has no meaning.

## 05:04 - [Data Analytics] Conditional Aggregation: Pivoting Without PIVOT, and the `ELSE 0` That Breaks COUNT

Every warehouse ships some `PIVOT` syntax and almost nobody uses it — it still requires hardcoding the column list, and it doesn't compose with the rest of your query. The portable pattern is conditional aggregation: push a `CASE` *inside* the aggregate.

```sql
SELECT
  region,
  SUM(CASE WHEN status = 'paid'     THEN amount END) AS paid_amt,
  SUM(CASE WHEN status = 'refunded' THEN amount END) AS refunded_amt,
  COUNT(CASE WHEN status = 'paid'   THEN 1 END)      AS paid_orders
FROM orders
GROUP BY region;
```

One row per region, one column per status. Two traps, both silent.

**1. `ELSE 0` breaks COUNT.** `COUNT` counts non-NULL values, and `0` is not NULL:

```sql
COUNT(CASE WHEN status='paid' THEN 1 ELSE 0 END)  -- counts EVERY row
COUNT(CASE WHEN status='paid' THEN 1 END)         -- correct
```

On a region with 1000 orders of which 300 are paid, the first returns **1000**, the second **300**. No error, no warning — just a conversion rate pinned at 100%.

`SUM` is the opposite: `ELSE 0` is harmless there, which is exactly why the habit spreads to `COUNT`. And `AVG` is worse than either — `AVG(CASE WHEN status='paid' THEN amount END)` gives the mean paid order (10.00); adding `ELSE 0` drags all 700 unpaid rows in as zeros and returns **3.00**.

**2. Empty buckets return NULL, not 0.** A region with zero refunds gets `refunded_amt = NULL`, and that NULL then poisons everything downstream: `paid_amt - refunded_amt` for that region is `NULL`, not `3000`. Wrap any column you'll do arithmetic on in `COALESCE(SUM(...), 0)`.

Where it exists, `FILTER` states the intent directly and sidesteps trap 1 entirely:

```sql
SUM(amount) FILTER (WHERE status = 'paid') AS paid_amt,
COUNT(*)    FILTER (WHERE status = 'paid') AS paid_orders
```

Postgres, DuckDB, SQLite (3.30+), and Spark SQL support it. BigQuery has `COUNTIF(cond)`. Snowflake and MySQL need `CASE`.

Conditional aggregation only works for a known, small set of buckets — dynamic columns need generated SQL. Past ~20 columns, take the hint: long format was the right shape.

## 10:03 - [ML & AI] Cosine vs Dot Product: The Vector Search Bug That Ranks Long Documents First

Every vector database asks you to pick a distance metric, and the default is rarely the one you want. The three choices are not interchangeable — but they *collapse into each other* under one condition, and understanding that condition is the whole topic.

For unit-length vectors, cosine similarity **is** the dot product, and Euclidean distance is a monotonic function of it:

```
‖a − b‖² = ‖a‖² + ‖b‖² − 2(a·b) = 2 − 2·cos(a, b)
```

So if everything is normalized, all three metrics produce the **same ranking**. If anything is not normalized, dot product silently starts rewarding vector *magnitude* — which usually correlates with document length, not relevance.

A two-dimensional example makes the failure concrete. Query `q = [1, 0]`:

| Doc | Vector | ‖v‖ | Dot | Cosine |
|---|---|---|---|---|
| A | `[0.900, 0.436]` | 1.00 | **0.90** | **0.90** |
| B | `[1.500, 1.500]` | 2.12 | **1.50** | **0.71** |

Dot product ranks B first; cosine ranks A first. A points almost exactly at the query. B wins on dot product only because it is longer. That is the verbose-document bug, and at 1536 dimensions you will never spot it by eye.

```python
import numpy as np

def l2_normalize(X):
    return X / np.linalg.norm(X, axis=-1, keepdims=True)

emb = l2_normalize(np.asarray(raw_embeddings, dtype=np.float32))
scores = emb @ l2_normalize(query)   # now a true cosine, and fast
```

Three places normalization quietly breaks:

- **Mean-pooling chunk embeddings** into a document vector. The average of unit vectors is not a unit vector. Re-normalize after pooling.
- **Dimension truncation** (Matryoshka-style shortening, e.g. slicing 1536 → 256). A slice of a unit vector has norm < 1. Re-normalize after slicing.
- **Index/operator mismatch.** In pgvector, `<->` is L2, `<#>` is negative inner product, `<=>` is cosine, and an index built with `vector_l2_ops` will not serve a `<=>` query. Postgres does not error — it falls back to a sequential scan. Results stay correct while p99 latency quietly goes to seconds.

**Rule:** normalize at write time, store unit vectors, then use dot product. You get cosine semantics at inner-product speed, and the metric choice stops mattering.

## 15:04 - [Crypto & Business] Volatility Drag: Why an "8% Average Return" Doesn't Compound at 8%

A fund advertises an 8% average annual return. You hold it 30 years. You will not end up with 8% compounded — and the gap is not fees. It is arithmetic.

The cleanest demonstration: an asset gains 50%, then loses 50%.

```
$100 → $150 → $75
Arithmetic mean of returns: (+50% − 50%) / 2 =   0.0%
Actual compounded (CAGR):   √0.75 − 1        = −13.4%
```

Zero "average" return, and a quarter of the money is gone. Losses compound against a smaller base than gains compound on, so the geometric mean is always ≤ the arithmetic mean. The gap widens with volatility, and a lognormal approximation prices it:

```
geometric ≈ arithmetic − σ² / 2
```

| Arithmetic μ | Volatility σ | Drag (σ²/2) | Compounded |
|---|---|---|---|
| 8% | 10% | 0.5% | 7.5% |
| 8% | 20% | 2.0% | 6.0% |
| 8% | 40% | 8.0% | 0.0% |
| 8% | 60% | 18.0% | −10.0% |

The drag is quadratic. Doubling volatility quadruples what it costs you.

**Why this makes diversification a return story, not just a risk story.** Take two assets, each μ = 8%, σ = 20%, uncorrelated. Held alone, each compounds at 8% − 2% = **6%**. A rebalanced 50/50 mix has σ = 20% / √2 ≈ 14.1%, so drag falls to 1% and it compounds at **7%** — same average return, same inputs, higher terminal wealth. On $100,000 over 30 years: $574,000 vs $761,000. That extra $187,000 came from lowering variance, not from picking better assets.

The same math explains why daily-rebalanced leveraged products decay in choppy markets. A 3× fund on a σ = 20% index runs at σ ≈ 60%: triple the arithmetic return, nine times the drag. Before financing costs and fees, that's roughly a wash at 20% volatility and strictly negative above it.

**Two practical reads.** When a marketing sheet quotes "average annual return," check whether it means arithmetic average or CAGR — they differ by σ²/2, and only CAGR describes what an investor actually received. And when comparing two strategies, compare compounded returns; a higher-average, higher-variance strategy routinely finishes behind.

*Educational content, not financial advice. Volatility drag is a mathematical identity, not a forecast — expected returns and correlations are estimates and can change.*
