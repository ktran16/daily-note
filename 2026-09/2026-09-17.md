## 00:03 - [Data Engineering] Delta Lake VACUUM vs Time Travel: The Two Retention Knobs People Conflate

Delta Lake has two independent retention settings, and almost everyone assumes one controls the other. It doesn't, and the failure mode is a stack trace instead of a clean error.

- `delta.logRetentionDuration` (default `interval 30 days`) — how long commit log JSON entries survive.
- `delta.deletedFileRetentionDuration` (default `interval 7 days`) — how long *data files* that a newer version no longer references stay on object storage before `VACUUM` may delete them.

Time travel to version *N* needs **both**: the log entry describing version *N*, and every Parquet file it points at. With the defaults, the log advertises 30 days of history while `VACUUM` is free to delete the underlying files after 7. Reading a 20-day-old version then dies with `FileNotFoundException`, not "version expired."

```sql
DESCRIBE HISTORY delta.`s3://lake/events`;   -- version 412 exists in the log
SELECT * FROM delta.`s3://lake/events` VERSION AS OF 412;
-- java.io.FileNotFoundException: .../part-00007-....snappy.parquet
```

Set them together, and set the data one to whatever you actually promise:

```sql
ALTER TABLE events SET TBLPROPERTIES (
  'delta.logRetentionDuration'         = 'interval 30 days',
  'delta.deletedFileRetentionDuration' = 'interval 30 days'
);
```

The other half of the trap: `OPTIMIZE` compacts small files but **leaves the originals on disk** — they're still referenced by older versions. Until `VACUUM` runs, an OPTIMIZE roughly doubles the table's storage footprint. If you schedule compaction without cleanup, your bill climbs and nobody can explain why.

```sql
OPTIMIZE events ZORDER BY (user_id);
VACUUM events RETAIN 720 HOURS DRY RUN;  -- always dry-run first: lists candidates
VACUUM events RETAIN 720 HOURS;
```

`RETAIN` is in hours. Delta refuses values under 168 hours (7 days) on purpose: a long-running reader or a concurrent writer may still hold references to those files, and deleting them corrupts in-flight queries. `spark.databricks.delta.retentionDurationCheck.enabled = false` disables the guard — reach for it only on a table you know is quiesced, never as a standing config.

**Rule of thumb:** pick your time-travel SLA first, set *both* properties to it, then schedule `OPTIMIZE` and `VACUUM` as a pair.

## 05:03 - [Data Analytics] ROLLUP Subtotals: The NULL That Means "Total" and the NULL That Means "Unknown"

`GROUP BY ROLLUP` and `GROUPING SETS` give you subtotals in one pass instead of three `UNION ALL` blocks. The trap: subtotal rows mark their collapsed columns with `NULL` — the same `NULL` your data already uses for missing values. The two are indistinguishable in the result set.

Six orders, where some rows genuinely have no channel:

```sql
SELECT region, channel, SUM(amount) AS revenue
FROM orders
GROUP BY ROLLUP (region, channel)
ORDER BY 1, 2;
```

```
EU    web     250.00
EU    NULL    200.00   <- real: channel is unknown
EU    NULL    450.00   <- subtotal: all EU channels
US    web     300.00
US    app     250.00
US    NULL     50.00   <- real
US    NULL    600.00   <- subtotal
NULL  NULL   1050.00   <- grand total
```

Two failure modes follow. Sum the `revenue` column in a BI tool and you get 3,150 — exactly 3× the true 1,050, because every dollar appears at the detail, region, and grand-total level. Filter `WHERE channel IS NOT NULL` to "clean up" and you drop the subtotals *and* the legitimate unknown-channel revenue, losing $250 silently.

The fix is `GROUPING()`, which returns 1 when a column was collapsed for that row and 0 otherwise:

```sql
SELECT
  CASE WHEN GROUPING(region)  = 1 THEN 'All regions'  ELSE region END               AS region,
  CASE WHEN GROUPING(channel) = 1 THEN 'All channels'
       ELSE COALESCE(channel, '(unknown)') END                                      AS channel,
  SUM(amount) AS revenue,
  GROUPING(region) * 2 + GROUPING(channel) AS lvl
FROM orders
GROUP BY ROLLUP (region, channel)
ORDER BY lvl, region, channel;
```

`lvl` is the bitmask: `0` = detail, `1` = region subtotal, `3` = grand total. Expose it to your BI layer and filter on `lvl = 0` for charts, `lvl = 3` for the headline number — never on the dimension's nullability.

Two more notes. `ROLLUP (a, b)` is hierarchical and yields only `(a,b)`, `(a)`, `()`; for independent breakdowns use `GROUPING SETS ((region), (channel), ())`, and for every combination use `CUBE`. And verified in DuckDB 1.5: `GROUPING SETS` can emit two rows that both read `NULL, NULL` — one the grand total, one the real-NULL group. Without `GROUPING()` you cannot tell them apart.

## 10:03 - [ML & AI] Speculative Decoding: Free Tokens, Paid for in Draft Passes

Autoregressive decoding wastes a GPU. Generating one token means streaming every weight from HBM to do a single token's worth of arithmetic — it is memory-bandwidth bound, and the compute units idle. But verifying *many* candidate tokens costs almost the same single weight-streaming pass. That gap is the whole trick.

Speculative decoding runs a small **draft** model to propose `k` tokens, then does **one** forward pass of the big **target** model over all `k` at once. Each proposal is accepted or rejected by rejection sampling. Crucially this is *lossless*: the accepted stream is distributed exactly as if the target had sampled alone. It is not an approximation, so it needs no quality eval — only a speed one.

The payoff is governed by the acceptance rate α (probability the target keeps a drafted token). Accepted tokens are a truncated geometric draw, plus one free bonus token the target always emits:

```
E[tokens per cycle] = (1 - α^(k+1)) / (1 - α)
```

With α = 0.8, k = 4, and a draft model 1/10 the cost of the target:

```python
a, k, c = 0.8, 4, 0.1
tokens = (1 - a**(k+1)) / (1 - a)   # 3.36 tokens
cost   = k * c + 1                  # 1.40 target-passes
tokens / cost                       # 2.40x speedup
```

Now drop α to 0.4 — a poorly matched draft model. Expected tokens fall to 1.65 against the same 1.40 cost: **1.18x**. Nearly all the win evaporates, because you still pay for all `k` draft passes whether or not they are accepted.

Two practical consequences. First, α is a property of the *pair*, not the draft model alone — use a small model from the same family and tokenizer, and α is highest on predictable text (code, JSON, boilerplate) and lowest on open-ended prose. Second, raising `k` has diminishing returns (terms decay as α^i) while draft cost grows linearly, so `k` = 3–5 is typically optimal; measure α on your real traffic before tuning it.

This helps latency-bound single-stream decoding. Under heavy batching the GPU is already compute-saturated, and speculative decoding can make throughput *worse*.

## 15:03 - [Crypto & Business] Token Approvals: The Standing Permission That Drains Wallets Months Later

Most wallet drains aren't stolen seed phrases. They're signatures the victim gave voluntarily — and then forgot about.

**The mechanic.** ERC-20 tokens live in the token contract, not your wallet. Your wallet only holds a balance entry. So a DEX can't move your USDC directly; you must first call `approve(spender, amount)` on the USDC contract, which writes `allowance[you][spender] = amount`. The spender can then call `transferFrom` on your balance, up to that amount, **at any time, forever, with no further signature from you.**

```
USDC.approve(0xRouter…, 115792089237316195423570985008687907853269984665640564039457584007913129639935)
```

That number is `2^256 - 1` — the "unlimited" default many dapps request so you only pay gas for approval once. It is a standing withdrawal authorization on your entire current *and future* USDC balance.

**Why it bites later.** The approval survives everything: you leave the protocol, the token price 10×'s, you stop using the dapp. Two years on, the spender contract is exploited or its admin key is compromised, and the attacker sweeps every wallet that still has a live allowance. The Multichain (2023) and Li.Fi (2024) incidents drained users through exactly this path — old, unrevoked approvals on routers people hadn't touched in months.

**Worked cost.** Approving 200 USDC instead of unlimited costs one extra approval (~$0.50–2 on mainnet, cents on an L2) each time you trade. If you swap twice a month, that's ~$50/year on mainnet to cap your worst case at 200 USDC instead of your whole balance.

**Hygiene that actually works:**
1. Set a finite allowance — most wallets let you edit the amount in the approval prompt.
2. Audit live allowances quarterly (Etherscan's Token Approvals tab, or revoke.cash). Revoke anything you don't recognize or no longer use.
3. Revoking costs gas and is a transaction, not a signature. Any site asking you to "revoke" via a free off-chain *signature* is running the scam, not the fix.
4. Keep long-term holdings in a wallet that never signs approvals. Separation of accounts beats vigilance.

Check `allowance(owner, spender)` before you assume it's zero — leaving a protocol does not clear it.

*Educational content, not financial advice.*

## 19:02 - [Wildcard] "No Space Left on Device" but `df` Disagrees with `du`: Four Causes

The classic 3 a.m. page: writes fail with `ENOSPC`, `df -h` says 100% full, and `du -sh /` reports far less. They measure different things — `du` walks directory entries, `df` asks the filesystem. Anything consuming blocks without a directory entry is invisible to `du`. Four causes, in the order worth checking.

**1. Deleted files still held open.** A process opens a log, something deletes it, but the process keeps its descriptor. The link count hits 0, the name vanishes, the blocks stay allocated until the last descriptor closes. Find them by link count:

```bash
lsof +L1 | sort -k7 -n | tail
# python3 474 root 3w REG 254,0 50000000 0 1884204 /tmp/bigtest (deleted)
#                                        ^ NLINK=0
```

Restarting the process frees the space. If you can't restart it, truncate through its descriptor — space is reclaimed immediately, no restart:

```bash
: > /proc/474/fd/3
```

**2. Inode exhaustion.** Millions of tiny files (session caches, unrotated mail queues) exhaust inodes while blocks remain free. `df -h` may even look fine here — the error is still `ENOSPC`:

```bash
df -i /          # IUse% at 100% with plenty of free blocks
```

Only deleting files fixes it; ext4 fixes its inode count at mkfs time. XFS and btrfs allocate inodes dynamically and don't hit this.

**3. Reserved blocks.** ext4 reserves 5% for root by default, so non-root writes fail at 95%. On a 4 TB data volume that is 200 GB withheld for no reason — reserve is there to stop fragmentation and keep root able to log in, which matters on `/`, not on a data disk:

```bash
tune2fs -l /dev/vda1 | grep -i 'reserved block count'
tune2fs -m 1 /dev/vda1        # online, instant, no remount
```

**4. Mount shadowing.** Files written to `/data` *before* the real filesystem was mounted over it still occupy the root filesystem, hidden under the mountpoint. Bind-mount the root elsewhere to see them:

```bash
mount --bind / /mnt && du -sh /mnt/data && umount /mnt
```

**Order of attack:** `df -i` first (instant), then `lsof +L1`, then the bind-mount check. Reach for `du` last — it's the slowest and the only one that lies.
