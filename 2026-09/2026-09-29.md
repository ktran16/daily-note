## 00:03 - [Data Engineering] Dagster Partitions: Declaring Time Once Instead of Threading Dates Through Every Task

In Airflow you pass dates around. Every task interpolates `{{ data_interval_start }}` into its own SQL, and each one has its own chance to get the boundary wrong. Dagster inverts this: you declare the partitioning on the asset, and the framework hands each run its slice.

```python
from dagster import asset, DailyPartitionsDefinition, AssetExecutionContext

daily = DailyPartitionsDefinition(start_date="2026-01-01")

@asset(partitions_def=daily)
def stg_events(context: AssetExecutionContext) -> None:
    start, end = context.partition_time_window  # tz-aware datetimes
    context.log.info(f"loading [{start}, {end})")
    warehouse.execute("""
        DELETE FROM stg_events WHERE event_at >= %s AND event_at < %s;
        INSERT INTO stg_events SELECT * FROM raw.events
        WHERE event_at >= %s AND event_at < %s
    """, [start, end, start, end])
```

The delete-then-insert on the *same* window is what makes the partition idempotent. Re-running `2026-03-04` touches only `2026-03-04`.

**The real payoff is dependency mapping.** A weekly rollup that reads seven daily partitions is a declaration, not arithmetic:

```python
from dagster import AssetIn, TimeWindowPartitionMapping, WeeklyPartitionsDefinition

@asset(
    partitions_def=WeeklyPartitionsDefinition(start_date="2026-01-01"),
    ins={"stg_events": AssetIn(partition_mapping=TimeWindowPartitionMapping())},
)
def weekly_active(context, stg_events): ...
```

Dagster now knows a week depends on exactly those dailies. Backfill the week and it schedules the missing days first. Nothing computes against a partial upstream.

**Backfills.** `dagster asset backfill --select stg_events --partition-range 2026-03-01...2026-03-31` launches 31 runs by default — parallel, individually retryable, but 31x the query overhead. For warehouse work that's usually wrong:

```python
from dagster import BackfillPolicy

@asset(partitions_def=daily, backfill_policy=BackfillPolicy.single_run())
def stg_events(context):
    start, end = context.partition_time_window  # spans the WHOLE range
```

With `single_run`, one run receives the full window and issues one query. The tradeoff: a failure loses the whole range, so keep the write atomic.

**Gotcha:** partition keys are date *strings* in the partition set's timezone (default UTC). Pass `timezone="America/New_York"` to `DailyPartitionsDefinition` rather than shifting timestamps inside the asset — otherwise your partition key and your data boundary drift apart during DST.

## 05:03 - [Data Analytics] Looker Symmetric Aggregates: The Hash That Fixes Fan-Out, and the `primary_key` That Breaks It

Join one order to five line items and `SUM(orders.amount)` counts that order five times. The obvious patch is `SUM(DISTINCT orders.amount)` — and it is wrong, because two different $49.00 orders collapse into one. Looker's fix, "symmetric aggregates," is to make each row's contribution unique before deduping it: hash the row's primary key, add the hashed number to the scaled value, `SUM(DISTINCT ...)` that, then subtract the summed hashes back out.

The generated SQL is unreadable, but the idea is three lines:

```sql
-- what Looker emits, conceptually
SELECT c.region,
       ( SUM(DISTINCT h.hash + CAST(FLOOR(COALESCE(o.amount,0) * 1000000) AS DECIMAL(38,0)))
       - SUM(DISTINCT h.hash) ) / 1000000.0 AS revenue
FROM orders o
JOIN LATERAL (SELECT CAST(('x'||LEFT(MD5(o.id::TEXT),15))::BIT(60)::BIGINT AS DECIMAL(38,0)) AS hash) h ON TRUE
JOIN order_items oi ON oi.order_id = o.id
JOIN customers   c  ON c.id = o.customer_id
GROUP BY 1;
```

Two silent failure modes follow directly from that mechanism:

**A non-unique `primary_key` undercounts.** The hash is only unique if the declared key is. Declare `primary_key: yes` on an order-line view keyed by `order_id` and every duplicate row hashes identically, so `DISTINCT` throws real rows away. Nothing errors. Check before you trust a dashboard:

```sql
SELECT id, COUNT(*) FROM orders GROUP BY 1 HAVING COUNT(*) > 1;
```

**A wrong `relationship` overcounts.** Symmetric aggregates only engage when Looker believes fan-out is possible — `one_to_many` or `many_to_many`. Mislabel the join `many_to_one` and Looker emits a plain `SUM`, restoring the 5× inflation. The relationship parameter is a correctness declaration, not documentation.

Also note the scale factor: values are floored at 1e-6, so a per-unit cost of `0.0000004` becomes zero. And the `DISTINCT` blocks pre-aggregation, which is why these queries scan and sort hard — pre-aggregate to order grain in dbt when the row count hurts. MIN/MAX and `COUNT(DISTINCT pk)` need none of this; they are fan-out-safe already.

## 10:03 - [ML & AI] Monotonic Constraints: Making a GBM Agree With the Thing Everyone Knows

Gradient boosting fits whatever the data says, including the parts that are noise. Train a default-risk model and the partial dependence on income will mostly slope downward — and then wiggle upward somewhere around $95k, because forty borrowers in that bucket happened to default. Nobody will approve the model. Not because 0.002 AUC is at stake, but because a reviewer can now point at a chart where earning more raises your predicted risk.

Monotonic constraints fix this at the split level rather than in post-hoc smoothing. When a tree splits on a constrained feature, the library forces the left child's output below the right child's (for direction `+1`) and pushes that bound down to every descendant, so no later split anywhere in the tree can reintroduce the reversal.

```python
import lightgbm as lgb

features = ["income", "credit_age", "n_inquiries", "utilization"]
#            -1 lower risk   0 free     +1 higher   +1 higher
constraints = [-1, 0, 1, 1]

model = lgb.train(
    {"objective": "binary",
     "monotone_constraints": constraints,
     "monotone_constraints_method": "advanced",  # basic | intermediate | advanced
     "learning_rate": 0.05},
    lgb.Dataset(X_train, y_train), num_boost_round=600)
```

XGBoost takes the same list as `monotone_constraints=(-1,0,1,1)`.

Three things worth knowing:

**The method matters.** `basic` is the default and the bluntest — it clamps aggressively and can cost real accuracy. `advanced` computes tighter per-node bounds, keeps more signal, and trains slower. If a constraint tanks your validation score, try `advanced` before concluding the constraint is wrong.

**The constraint applies to the raw margin**, i.e. log-odds for binary objectives. Sigmoid is monotone increasing, so it carries through to probability unchanged — but it does *not* survive an arbitrary post-processing step.

**It is global.** If the true relationship is U-shaped (risk rises at both very low and very high utilization), forcing `+1` makes the model worse in a way validation AUC may barely register. Constrain only where domain logic is genuinely one-directional.

Verify rather than assume:

```python
import numpy as np
grid = np.linspace(X["income"].quantile(.01), X["income"].quantile(.99), 100)
probe = X_val.sample(500)
curve = [model.predict(probe.assign(income=v)).mean() for v in grid]
assert np.all(np.diff(curve) <= 1e-9), "monotonicity violated"
```

Typical cost: a few thousandths of AUC. Typical benefit: the model ships.

## 15:04 - [Crypto & Business] Liquidation Preferences: Why a $25M Exit Can Pay the Founders Nothing

Dilution math tells you what percentage you own. The preference stack tells you what that percentage is actually worth at exit — and below a certain sale price, the answer is zero regardless of the percentage.

**The mechanic.** Preferred stock gets paid *before* common. A "1x non-participating" preference means each investor takes the greater of (a) their money back, or (b) their as-converted pro-rata share. They pick whichever is bigger, per round.

**Worked example.** A company raises $12M total across seed/A/B, all 1x non-participating. Investors hold 40% as-converted; founders and employees hold 60% in common.

| Exit price | Investors take | Common gets | Common's effective share |
|---|---|---|---|
| $12M | $12M (pref) | $0 | 0% |
| $20M | $12M (pref) | $8M | 40% |
| $30M | $12M (either) | $18M | 60% |
| $50M | $20M (convert) | $30M | 60% |

The number that matters is the **indifference point** — where converting beats taking the preference:

```
indifference = total preference ÷ investor ownership
             = $12M ÷ 0.40 = $30M
```

Below $30M, every incremental dollar of sale price is worth *less* than 60 cents to common. That's why a $25M "successful acquisition" can leave a founding team with a rounding error.

**Participating preferred is worse.** Investors take the $12M off the top, *then* also take 40% of what's left. At a $50M exit: $12M + 40% × $38M = **$27.2M**, versus $20M non-participating. Common drops from $30M to $22.8M — a $7.2M swing from one word in the term sheet.

**What to actually check in a term sheet:** the multiple (1x is standard; 2x+ is a distress signal), participating vs non-participating, whether participation has a cap (e.g. "3x cap"), and **seniority** — stacked (later rounds paid first) versus pari passu (everyone shares pro-rata among preferred). Stacked seniority makes the last round in the first one out.

A high valuation with heavy preference terms is usually worse than a lower valuation on clean 1x non-participating. Price is the headline; the stack is the deal.

## 19:03 - [PC Hardware] NVMe Thermal Throttling: The Fastest Drive in Your Build Can Be the Slowest Under Load

A Gen5 NVMe drive advertises 14,000 MB/s. It will hit that for about 20 seconds. Sequential specs are burst numbers measured on an open-air test bench with a fan pointed at the drive; the number you live with is whatever the controller allows once it heats up.

**Where the heat comes from.** Not the NAND — the controller. A Gen5 controller draws 8-11 W under load versus ~4 W for a Gen4 part, in a package the size of a fingernail with no airflow. The NAND itself actually *wants* to be warm (~40-50 °C) for write endurance; it's the controller that cooks.

**The two-stage throttle.** Every drive publishes its own trip points. Read them rather than guessing:

```bash
sudo nvme id-ctrl /dev/nvme0 | grep -E 'wctemp|cctemp'   # warning / critical, in Kelvin
sudo nvme smart-log /dev/nvme0 | grep -E 'temperature|thermal'
sudo smartctl -a /dev/nvme0 | grep -i throttle
```

`wctemp` is typically 358 K (85 °C) and `cctemp` 273+95 = 368 K. Crossing the warning point drops the controller a power state — you go from 14 GB/s to roughly 2-3 GB/s. The critical point is a hard clock stop. `smart-log` counts seconds spent in each: `Thermal Management T1 Total Time` climbing during normal use means you are throttling constantly, not occasionally.

**What actually fixes it, in order of effect:**

| Fix | Typical drop |
|---|---|
| Move off the M.2 slot directly under the GPU | 8-15 °C |
| Motherboard heatsink with a fresh thermal pad (the factory pad is often not contacting) | 10-20 °C |
| Any case airflow at all across the board | 5-10 °C |
| Aftermarket finned heatsink + 40 mm fan | another 5-8 °C |

**The slot that matters more than the heatsink.** The top M.2 slot is CPU-attached and usually sits between socket and GPU — the hottest real estate on the board. Chipset-attached slots are cooler but add ~1-2 µs latency and share bandwidth. For a boot drive, the difference is unmeasurable in daily use; for a scratch disk taking sustained writes, cooler wins.

**Sanity check before you spend money.** Most desktop workloads never write 50 GB in one go. Run `fio --name=t --filename=/mnt/test --rw=write --bs=1M --size=64G --direct=1` while watching `nvme smart-log` in another terminal. If you can't make it throttle, a Gen5 drive with a giant heatsink is solving a problem you don't have — buy the good Gen4 drive and spend the difference on RAM.
