## 00:03 - [Data Engineering] Dagster Partitions: Declaring Time Once Instead of Threading Dates Through Every Task

In Airflow you pass dates around. Every task interpolates `{{ data_interval_start }}` into its own SQL, and each one has its own chance to get the boundary wrong. Dagster inverts this: you declare the partitioning on the asset, and the framework hands each run its slice.

```python
from dagster import asset, DailyPartitionsDefinition, AssetExecutionContext

daily = DailyPartitionsDefinition(start_date="2026-01-01")

@asset(partitions_def=daily)
def stg_events(context: AssetExecutionContext) -> None:
    start, end = context.partition_time_window  # tz-aware datetimes
    context.log.info(f"loading [{start}, {end})")
    warehouse.execute("""
        DELETE FROM stg_events WHERE event_at >= %s AND event_at < %s;
        INSERT INTO stg_events SELECT * FROM raw.events
        WHERE event_at >= %s AND event_at < %s
    """, [start, end, start, end])
```

The delete-then-insert on the *same* window is what makes the partition idempotent. Re-running `2026-03-04` touches only `2026-03-04`.

**The real payoff is dependency mapping.** A weekly rollup that reads seven daily partitions is a declaration, not arithmetic:

```python
from dagster import AssetIn, TimeWindowPartitionMapping, WeeklyPartitionsDefinition

@asset(
    partitions_def=WeeklyPartitionsDefinition(start_date="2026-01-01"),
    ins={"stg_events": AssetIn(partition_mapping=TimeWindowPartitionMapping())},
)
def weekly_active(context, stg_events): ...
```

Dagster now knows a week depends on exactly those dailies. Backfill the week and it schedules the missing days first. Nothing computes against a partial upstream.

**Backfills.** `dagster asset backfill --select stg_events --partition-range 2026-03-01...2026-03-31` launches 31 runs by default — parallel, individually retryable, but 31x the query overhead. For warehouse work that's usually wrong:

```python
from dagster import BackfillPolicy

@asset(partitions_def=daily, backfill_policy=BackfillPolicy.single_run())
def stg_events(context):
    start, end = context.partition_time_window  # spans the WHOLE range
```

With `single_run`, one run receives the full window and issues one query. The tradeoff: a failure loses the whole range, so keep the write atomic.

**Gotcha:** partition keys are date *strings* in the partition set's timezone (default UTC). Pass `timezone="America/New_York"` to `DailyPartitionsDefinition` rather than shifting timestamps inside the asset — otherwise your partition key and your data boundary drift apart during DST.

## 05:03 - [Data Analytics] Looker Symmetric Aggregates: The Hash That Fixes Fan-Out, and the `primary_key` That Breaks It

Join one order to five line items and `SUM(orders.amount)` counts that order five times. The obvious patch is `SUM(DISTINCT orders.amount)` — and it is wrong, because two different $49.00 orders collapse into one. Looker's fix, "symmetric aggregates," is to make each row's contribution unique before deduping it: hash the row's primary key, add the hashed number to the scaled value, `SUM(DISTINCT ...)` that, then subtract the summed hashes back out.

The generated SQL is unreadable, but the idea is three lines:

```sql
-- what Looker emits, conceptually
SELECT c.region,
       ( SUM(DISTINCT h.hash + CAST(FLOOR(COALESCE(o.amount,0) * 1000000) AS DECIMAL(38,0)))
       - SUM(DISTINCT h.hash) ) / 1000000.0 AS revenue
FROM orders o
JOIN LATERAL (SELECT CAST(('x'||LEFT(MD5(o.id::TEXT),15))::BIT(60)::BIGINT AS DECIMAL(38,0)) AS hash) h ON TRUE
JOIN order_items oi ON oi.order_id = o.id
JOIN customers   c  ON c.id = o.customer_id
GROUP BY 1;
```

Two silent failure modes follow directly from that mechanism:

**A non-unique `primary_key` undercounts.** The hash is only unique if the declared key is. Declare `primary_key: yes` on an order-line view keyed by `order_id` and every duplicate row hashes identically, so `DISTINCT` throws real rows away. Nothing errors. Check before you trust a dashboard:

```sql
SELECT id, COUNT(*) FROM orders GROUP BY 1 HAVING COUNT(*) > 1;
```

**A wrong `relationship` overcounts.** Symmetric aggregates only engage when Looker believes fan-out is possible — `one_to_many` or `many_to_many`. Mislabel the join `many_to_one` and Looker emits a plain `SUM`, restoring the 5× inflation. The relationship parameter is a correctness declaration, not documentation.

Also note the scale factor: values are floored at 1e-6, so a per-unit cost of `0.0000004` becomes zero. And the `DISTINCT` blocks pre-aggregation, which is why these queries scan and sort hard — pre-aggregate to order grain in dbt when the row count hurts. MIN/MAX and `COUNT(DISTINCT pk)` need none of this; they are fan-out-safe already.
