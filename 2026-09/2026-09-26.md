## 00:02 - [Data Engineering] Liquid Clustering: Why Databricks Wants You to Stop Partitioning

Hive-style partitioning forces one irreversible choice: the partition column set is baked into the physical directory layout. Pick `date` and your `customer_id` filters scan everything. Pick both and you get thousands of tiny files. Change your mind and you rewrite the table.

Liquid clustering (Delta Lake 3.x / Databricks Runtime 13.3+) replaces directories with metadata. Files are organized by clustering keys recorded in the transaction log, and the keys are changeable at any time without rewriting existing data.

```sql
-- New table: no PARTITIONED BY at all
CREATE TABLE sales.orders (
  order_id      BIGINT,
  customer_id   BIGINT,
  order_ts      TIMESTAMP,
  amount        DECIMAL(18,2)
)
CLUSTER BY (order_ts, customer_id);

-- Change your mind later - metadata-only, no rewrite
ALTER TABLE sales.orders CLUSTER BY (customer_id);

-- Let Databricks choose keys from observed query predicates
ALTER TABLE sales.orders CLUSTER BY AUTO;
```

New data lands unclustered, so clustering is applied incrementally:

```sql
OPTIMIZE sales.orders;   -- clusters only the new/unclustered files
```

That incremental property is the real win over `ZORDER BY`. Z-ordering is not idempotent — each `OPTIMIZE ... ZORDER BY` rewrites files it has already processed, so recurring jobs re-shuffle the whole table. Liquid clustering tracks what is already organized and touches only the delta.

Practical guidance:

- **Up to 4 clustering keys.** Order them by filter selectivity, not cardinality. Unlike Z-order, key order matters less, but leading with your most common predicate still helps.
- **Do not combine with partitioning or Z-order.** `CLUSTER BY` is mutually exclusive with `PARTITIONED BY`; the two concepts fight over file layout.
- **High-cardinality keys are fine** — this is where partitioning fails hardest. `customer_id` is a legitimate clustering key; it is a terrible partition key.
- **Schedule `OPTIMIZE`** after ingestion, or enable predictive optimization so Databricks runs it for you.
- **Migration** requires a rewrite: `CREATE TABLE ... CLUSTER BY ... AS SELECT * FROM old_table`. `ALTER TABLE` only converts tables that are not already partitioned.

In dbt, set it in the model config:

```sql
{{ config(
    materialized='incremental',
    file_format='delta',
    liquid_clustered_by=['order_ts', 'customer_id']
) }}
```

The mental shift: partitioning is a schema decision you live with; clustering is a tuning knob you turn.

## 05:03 - [Data Analytics] Polars Lazy Frames: Why `.lazy()` After `read_parquet` Optimizes Nothing

Polars has two entry points that look interchangeable and are not:

```python
import polars as pl

# Eager: reads all 40 columns, all row groups, into RAM. Then filters.
df = pl.read_parquet("events.parquet").lazy() \
       .filter(pl.col("event_date") == "2026-09-01") \
       .select("user_id", "revenue")

# Lazy: builds a plan first, then reads only what the plan needs.
lf = pl.scan_parquet("events.parquet") \
       .filter(pl.col("event_date") == "2026-09-01") \
       .select("user_id", "revenue")
```

The first is the common mistake. `read_parquet` has already materialized the file by the time `.lazy()` is called — the wrapper optimizes the *remaining* operations, not the I/O. On a 2.1 GB file that is 2.1 GB of decompression you pay for to keep 2 columns.

`scan_parquet` defers everything, so the optimizer can apply:

- **Projection pushdown** — only `user_id`, `revenue`, `event_date` are decoded.
- **Predicate pushdown** — the filter reaches the reader, which uses per-row-group min/max statistics to skip groups entirely.
- **Slice pushdown** — a trailing `.head(1000)` stops the scan early.

Verify rather than assume. `lf.explain()` prints the optimized plan, and the scan node states exactly what survived:

```
Parquet SCAN [events.parquet]
PROJECT 3/40 COLUMNS
SELECTION: [(col("event_date")) == (String(2026-09-01))]
```

If `PROJECT */40 COLUMNS` appears, pushdown broke — usually because a `.collect()` landed mid-chain, or a `map_elements` UDF made the plan opaque to the optimizer.

Two things that surprise people:

**Predicate pushdown skips row groups, not rows.** Statistics are per row group, and a row group is commonly 128 MB of data (Spark's default `parquet.block.size`) — millions of rows. If the data is unsorted, nearly every group's min/max straddles your filter value and nothing is skipped — pushdown "works" and reads the whole file. Sorting or Hive-partitioning by the filter column is what makes skipping real.

**One `.collect()`, at the end.** Each call is a full execution barrier. For data larger than RAM, use `lf.collect(engine="streaming")` (older versions: `streaming=True`) so the plan runs in batches instead of materializing intermediates.

## 10:03 - [ML & AI] Logistic Regression Coefficients Are Log-Odds, and Two of Them Lie by Default

A stakeholder asks what `age` does to churn. You point at `coef_ = 0.7` and say "it raises churn." That is the only safe sentence you can say without doing three checks first.

**The scale is log-odds, not probability.** The model is `log(p / (1-p)) = β₀ + Σβᵢxᵢ`. So `exp(β)` is an *odds ratio*: a one-unit increase multiplies the odds, and `exp(0.7) = 2.01`. What that does to the probability depends entirely on where you start:

| baseline p | odds | ×2.01 | new p | probability change |
|---|---|---|---|---|
| 0.02 | 0.0204 | 0.0411 | **0.0395** | 1.97× — "doubles" is fair |
| 0.60 | 1.50 | 3.02 | **0.751** | 1.25× — "doubles" is nonsense |

Odds ratios only approximate risk ratios when the event is rare. Above ~10% base rate, stop translating them into "twice as likely."

**Lie #1: units.** Coefficient magnitude is per one unit of the raw feature. `age` in years and `age` in decades give coefficients differing by 10×, same model. Ranking features by `|coef_|` on unstandardized inputs ranks your unit choices. Standardize first if you want comparability.

**Lie #2: sklearn regularizes silently.** `LogisticRegression()` defaults to L2 with `C=1.0`. Coefficients are shrunk toward zero, so every odds ratio is biased toward 1 — and the shrinkage is uneven across features with different variances.

```python
from sklearn.linear_model import LogisticRegression
import numpy as np, pandas as pd

# For inference, turn the penalty off and standardize.
m = LogisticRegression(penalty=None, max_iter=1000).fit(Xz, y)

pd.DataFrame({
    "feature": Xz.columns,
    "log_odds": m.coef_[0],
    "odds_ratio": np.exp(m.coef_[0]),          # per 1 SD, now comparable
}).sort_values("odds_ratio", key=abs, ascending=False)
```

Keep the regularized model for *predicting*; fit an unpenalized one for *explaining*. They answer different questions, and reporting the first as if it were the second understates every effect you were asked about.
