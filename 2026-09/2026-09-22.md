## 00:02 - [Data Engineering] Iceberg Hidden Partitioning: Why You Stop Writing `WHERE dt = '2026-09-22'`

In Hive-style tables, the partition column is a real column you must physically materialize and then filter on. Miss it and you full-scan:

```sql
-- Hive layout: event_date is a separate derived column
SELECT * FROM events WHERE event_ts >= '2026-09-22';  -- full scan, no pruning
SELECT * FROM events WHERE event_date = '2026-09-22'; -- prunes, but only if you remember
```

That gap between "the column people query" and "the column that prunes" is the single most common source of accidental full-table scans. Iceberg closes it with **hidden partitioning**: you declare a *transform* over a real column, and the engine derives the partition value itself.

```sql
CREATE TABLE events (
  event_ts  TIMESTAMP,
  user_id   BIGINT,
  payload   STRING
) USING iceberg
PARTITIONED BY (days(event_ts), bucket(16, user_id));
```

There is no `event_date` column. Queries filter the natural column and prune automatically:

```sql
SELECT * FROM events
WHERE event_ts >= TIMESTAMP '2026-09-22 00:00:00';  -- prunes to one day's files
```

Available transforms: `years`, `months`, `days`, `hours`, `bucket(N, col)`, `truncate(N, col)`, and `identity`. Use `bucket` for high-cardinality join/filter keys (it produces a fixed file count, unlike identity on `user_id`, which would create millions of directories). Use `truncate(10, zip_code)` for prefix filters.

**Partition evolution** is the second half. Iceberg stores the partition spec in metadata, not in directory paths, so you can change it without rewriting history:

```sql
ALTER TABLE events ADD PARTITION FIELD hours(event_ts);
ALTER TABLE events DROP PARTITION FIELD days(event_ts);
```

Old files keep their old spec; new writes use the new one. A single query plans against both specs transparently. Contrast with Hive, where changing partitioning means rewriting the whole table.

Two caveats worth knowing:

- Pruning needs the predicate on the **source column**. `WHERE date(event_ts) = '2026-09-22'` may not prune on older engine versions — filter the raw column with a range.
- Evolution doesn't reorganize existing data. If you need old files in the new layout, run a rewrite (`CALL system.rewrite_data_files`) explicitly.

The practical rule: partition on the column analysts actually filter, let the transform do the derivation, and treat the spec as something you can tune later rather than a one-shot decision at table creation.

## 05:03 - [Data Analytics] CTE Materialization: The Optimization Fence That Runs Your Scan Three Times

A CTE looks like a variable. It isn't. In most engines it's a *name for a subquery*, and every reference to that name can re-run the whole thing.

```sql
WITH heavy AS (
  SELECT customer_id, SUM(amount) AS rev
  FROM orders                      -- 2B rows
  WHERE order_ts >= DATEADD(year, -1, CURRENT_DATE)
  GROUP BY 1
)
SELECT
  (SELECT AVG(rev)  FROM heavy),
  (SELECT MAX(rev)  FROM heavy),
  (SELECT COUNT(*)  FROM heavy);
```

On Snowflake, BigQuery, and Redshift this commonly plans as **three scans and three aggregations** of `orders`, not one. A 40-second CTE becomes a 2-minute query, and you pay compute for all three.

**PostgreSQL is the opposite trap.** Through v11 every CTE was materialized — a hard optimization fence, so predicates from the outer query could never push down:

```sql
WITH recent AS (SELECT * FROM orders WHERE order_ts >= now() - interval '1 year')
SELECT * FROM recent WHERE customer_id = 42;   -- pre-v12: materializes ALL of last year, then filters
```

v12 flipped the default: a CTE that is non-recursive, side-effect-free, and referenced exactly once gets inlined. Both behaviors are now explicit:

```sql
WITH recent AS NOT MATERIALIZED (...)  -- force inlining, let the filter push down
WITH heavy  AS MATERIALIZED     (...)  -- compute once, reuse
```

**How to decide.** Materialize when the CTE is expensive *and* referenced more than once, or when it's nondeterministic — a CTE calling `random()` or `uuid_generate_v4()` that gets inlined twice produces *different values per reference*, which silently breaks sampling and dedup logic. Inline when the CTE is a thin filter/projection you want the planner to fuse with the outer query.

Outside Postgres there is no keyword. The portable equivalents:

- **Snowflake / Redshift / SQL Server:** `CREATE TEMPORARY TABLE heavy AS ...`, then query it.
- **BigQuery:** a temp table in a script, or accept the recompute for cheap CTEs.
- **Spark:** `df.cache()` / `CACHE TABLE`.

Diagnose it before rewriting: check the plan for the CTE's base table appearing more than once. Reference count in the plan, not in the SQL text, is what you're paying for.
