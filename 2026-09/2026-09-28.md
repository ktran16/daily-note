## 00:03 - [Data Engineering] Column-Level Lineage: Why Table-Level Graphs Fail Impact Analysis

Most lineage tools show you table edges: `orders` → `stg_orders` → `fct_revenue`. That graph answers "what breaks if this table disappears?" but not the question you actually get paged about: *"we're dropping `orders.discount_cents` — who cares?"* Table-level lineage says everything downstream cares. Column-level lineage says three dashboards do.

The difference is real cost. On a 400-model project, a table-level blast radius is routinely 10x the true one, so every schema change turns into a week of manual grep.

**OpenLineage** is the open standard that carries this. Producers (Airflow, dbt, Spark, Flink) emit run events to a backend (Marquez, DataHub, OpenMetadata) with a `columnLineage` facet:

```json
{
  "eventType": "COMPLETE",
  "job": {"namespace": "dbt", "name": "fct_revenue"},
  "outputs": [{
    "namespace": "snowflake://acct", "name": "analytics.fct_revenue",
    "facets": {"columnLineage": {"fields": {
      "net_revenue": {
        "inputFields": [
          {"namespace": "snowflake://acct", "name": "analytics.stg_orders",
           "field": "gross_cents", "transformations": [{"type": "DIRECT", "subtype": "TRANSFORMATION"}]},
          {"namespace": "snowflake://acct", "name": "analytics.stg_orders",
           "field": "discount_cents", "transformations": [{"type": "DIRECT", "subtype": "TRANSFORMATION"}]}
        ]}}}}}]
}
```

Wire it up in Airflow with the provider — no DAG changes needed:

```bash
pip install apache-airflow-providers-openlineage
export AIRFLOW__OPENLINEAGE__TRANSPORT='{"type":"http","url":"http://marquez:5000"}'
export AIRFLOW__OPENLINEAGE__NAMESPACE=prod
```

For dbt, `dbt-ol run` wraps the CLI and parses `manifest.json` + `catalog.json` into events.

Two things that bite:

1. **`SELECT *` destroys precision.** SQL parsers can only resolve the star if the catalog is populated, so run `dbt docs generate` (or equivalent) before emitting.
2. **Distinguish DIRECT from INDIRECT.** A column used only in a `WHERE` or `GROUP BY` is an `INDIRECT` dependency — it still breaks the model if dropped, but it won't show up in a naive "which columns feed this value" query. Include both in impact analysis; separate them in the UI.

The payoff is an automated pre-merge check: parse the PR's changed columns, query lineage, and comment with the actual downstream consumers instead of guessing.

## 05:03 - [Data Analytics] ASOF Joins: The Rate Lookup That Silently Multiplies or Leaks

You have `orders(order_id, currency, ordered_at, amount)` and `fx_rates(currency, rate, valid_from)` published irregularly. You need the rate *in effect at order time*. Both obvious joins are wrong.

**Attempt 1 — equi-join on the day:**

```sql
JOIN fx_rates r ON r.currency = o.currency
               AND r.valid_from::date = o.ordered_at::date
```

Rates don't publish on weekends, so every Saturday and Sunday order drops out. Silent row loss: 5,000 orders in, 3,570 out, and nothing errors.

**Attempt 2 — open range join:**

```sql
JOIN fx_rates r ON r.currency = o.currency
               AND r.valid_from <= o.ordered_at
```

Every *historical* rate matches. With 500 rate rows per currency, one order becomes ~250 rows and `SUM(amount)` inflates by two orders of magnitude.

**The portable fix — close the interval with `LEAD`:**

```sql
WITH rate_windows AS (
  SELECT currency, rate, valid_from,
         LEAD(valid_from) OVER (
           PARTITION BY currency ORDER BY valid_from
         ) AS valid_to
  FROM fx_rates
)
SELECT o.order_id, o.amount * r.rate AS amount_usd
FROM orders o
JOIN rate_windows r
  ON r.currency = o.currency
 AND o.ordered_at >= r.valid_from
 AND (o.ordered_at < r.valid_to OR r.valid_to IS NULL);
```

Three details carry the whole query. The interval is **half-open** (`>=` / `<`) — use `<=` on both ends and an order landing exactly on a publish timestamp matches two windows. The `valid_to IS NULL` branch keeps the open-ended latest row; drop it and every order after the last publish vanishes. And DuckDB, Snowflake, and ClickHouse have this built in:

```sql
FROM orders o ASOF LEFT JOIN fx_rates r
  ON o.currency = r.currency AND o.ordered_at >= r.valid_from
```

`ASOF JOIN` alone is an *inner* join — orders predating the first rate disappear. `ASOF LEFT JOIN` surfaces them as NULL, which is a bug you can see.

**The leak:** never match on *nearest* timestamp (`ORDER BY ABS(o.ordered_at - r.valid_from)`). Nearest can be a rate published after the order, so a model trained on that feature learned from the future. Feature stores call the correct behavior point-in-time correctness.

**Invariant to assert:** with a LEFT join, output rows must equal input orders exactly. Any drift means your intervals overlap or gap.

## 10:03 - [ML & AI] Missing Values: The Reason a Row Is NaN Is Usually the Best Feature in It

`df.fillna(df.mean())` is the most common one-line accuracy leak in tabular ML. It assumes missingness is random noise. It almost never is.

Three mechanisms, and only one of them is safe to impute away:

- **MCAR** — a sensor dropped packets. Imputation is fine.
- **MAR** — missingness depends on *observed* columns (older customers skip the web form). Recoverable from the other features.
- **MNAR** — missingness depends on the *unobserved value itself*. `months_employed` is NULL because the applicant has no job; `income` is blank because it's embarrassing. The NaN **is** the signal.

### A worked case

Credit default model, `months_employed` missing on 12% of rows. Base default rate 4%; among the missing rows, 31%. Mean-impute and every one of those applicants is assigned median tenure — you have taken your single sharpest predictor and overwritten it with "average." Adding a binary `months_employed_isna` column recovers it: AUC 0.71 → 0.79, entirely from that one indicator.

```python
from sklearn.pipeline import Pipeline
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression

pipe = Pipeline([
    # add_indicator appends a 0/1 column per feature that had NaNs in fit
    ("imp", SimpleImputer(strategy="median", add_indicator=True)),
    ("clf", LogisticRegression(max_iter=1000)),
])
```

Keep the imputer *inside* the pipeline. A median computed on the full frame before splitting leaks test-set distribution into training.

### For gradient boosting, don't impute at all

XGBoost and LightGBM handle NaN natively: at each split they try sending missing rows left and right, and keep whichever direction reduces loss more. That learns a *per-split* treatment, strictly more expressive than one global fill value — and it makes the indicator column redundant.

```python
xgb.XGBClassifier(...).fit(X, y)   # pass NaN straight through; no imputer
```

Never use the `fillna(-999)` sentinel. Trees tolerate it; any linear, distance, or gradient-based model treats it as a real, enormous value and it wrecks scaling.

One production gotcha: monitor your **missingness rate per column**, not just feature drift. An upstream schema change that pushes a field from 2% NaN to 90% keeps every value in range — so drift checks on the observed distribution stay green while the model quietly collapses.

## 15:04 - [Crypto & Business] Finality: Why "6 Confirmations" and "Finalized" Are Completely Different Guarantees

A block explorer showing "confirmed" tells you a transaction is *in* a block. It does not tell you the block can never be replaced. Those are different properties, and chains provide them differently.

**Bitcoin: probabilistic finality.** No block is ever final — a longer competing chain always wins. Safety comes from how expensive it gets to build one. From the whitepaper's own math, an attacker with 10% of hashrate has roughly a 1-in-4,000 chance of reversing a transaction buried 6 blocks deep. At 30% hashrate, that same 6 confirmations is ~18% — the guarantee is a function of the attacker, not the number. Six blocks ≈ 60 minutes on average, but block times are exponentially distributed: it's routine to wait 25 or 100 minutes.

**Ethereum: economic finality.** Slots are 12 seconds, epochs are 32 slots (6.4 min). A checkpoint is *justified* when validators holding 2/3 of staked ETH attest to it, and *finalized* one epoch later — so 2 epochs, roughly 13 to 19 minutes depending where in the epoch you land. Reverting a finalized block requires 1/3 of all staked ETH to be slashed and burned. With tens of millions of ETH staked, that's a deliberate multi-billion-dollar sacrifice, not a probability.

**The practical mechanic:** Ethereum JSON-RPC exposes a `finalized` block tag. Polling for a fixed confirmation count is a Bitcoin-era habit; on Ethereum, read `finalized` and get the actual guarantee.

**Rollups add a third clock.** An optimistic rollup transaction is quick and cheap on L2, but withdrawing to L1 waits out a ~7-day fraud-proof window. Third-party "fast bridges" that skip it aren't accelerating finality — they're lending you the money and charging for the risk.
