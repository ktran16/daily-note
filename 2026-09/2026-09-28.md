## 00:03 - [Data Engineering] Column-Level Lineage: Why Table-Level Graphs Fail Impact Analysis

Most lineage tools show you table edges: `orders` → `stg_orders` → `fct_revenue`. That graph answers "what breaks if this table disappears?" but not the question you actually get paged about: *"we're dropping `orders.discount_cents` — who cares?"* Table-level lineage says everything downstream cares. Column-level lineage says three dashboards do.

The difference is real cost. On a 400-model project, a table-level blast radius is routinely 10x the true one, so every schema change turns into a week of manual grep.

**OpenLineage** is the open standard that carries this. Producers (Airflow, dbt, Spark, Flink) emit run events to a backend (Marquez, DataHub, OpenMetadata) with a `columnLineage` facet:

```json
{
  "eventType": "COMPLETE",
  "job": {"namespace": "dbt", "name": "fct_revenue"},
  "outputs": [{
    "namespace": "snowflake://acct", "name": "analytics.fct_revenue",
    "facets": {"columnLineage": {"fields": {
      "net_revenue": {
        "inputFields": [
          {"namespace": "snowflake://acct", "name": "analytics.stg_orders",
           "field": "gross_cents", "transformations": [{"type": "DIRECT", "subtype": "TRANSFORMATION"}]},
          {"namespace": "snowflake://acct", "name": "analytics.stg_orders",
           "field": "discount_cents", "transformations": [{"type": "DIRECT", "subtype": "TRANSFORMATION"}]}
        ]}}}}}]
}
```

Wire it up in Airflow with the provider — no DAG changes needed:

```bash
pip install apache-airflow-providers-openlineage
export AIRFLOW__OPENLINEAGE__TRANSPORT='{"type":"http","url":"http://marquez:5000"}'
export AIRFLOW__OPENLINEAGE__NAMESPACE=prod
```

For dbt, `dbt-ol run` wraps the CLI and parses `manifest.json` + `catalog.json` into events.

Two things that bite:

1. **`SELECT *` destroys precision.** SQL parsers can only resolve the star if the catalog is populated, so run `dbt docs generate` (or equivalent) before emitting.
2. **Distinguish DIRECT from INDIRECT.** A column used only in a `WHERE` or `GROUP BY` is an `INDIRECT` dependency — it still breaks the model if dropped, but it won't show up in a naive "which columns feed this value" query. Include both in impact analysis; separate them in the UI.

The payoff is an automated pre-merge check: parse the PR's changed columns, query lineage, and comment with the actual downstream consumers instead of guessing.

## 05:03 - [Data Analytics] ASOF Joins: The Rate Lookup That Silently Multiplies or Leaks

You have `orders(order_id, currency, ordered_at, amount)` and `fx_rates(currency, rate, valid_from)` published irregularly. You need the rate *in effect at order time*. Both obvious joins are wrong.

**Attempt 1 — equi-join on the day:**

```sql
JOIN fx_rates r ON r.currency = o.currency
               AND r.valid_from::date = o.ordered_at::date
```

Rates don't publish on weekends, so every Saturday and Sunday order drops out. Silent row loss: 5,000 orders in, 3,570 out, and nothing errors.

**Attempt 2 — open range join:**

```sql
JOIN fx_rates r ON r.currency = o.currency
               AND r.valid_from <= o.ordered_at
```

Every *historical* rate matches. With 500 rate rows per currency, one order becomes ~250 rows and `SUM(amount)` inflates by two orders of magnitude.

**The portable fix — close the interval with `LEAD`:**

```sql
WITH rate_windows AS (
  SELECT currency, rate, valid_from,
         LEAD(valid_from) OVER (
           PARTITION BY currency ORDER BY valid_from
         ) AS valid_to
  FROM fx_rates
)
SELECT o.order_id, o.amount * r.rate AS amount_usd
FROM orders o
JOIN rate_windows r
  ON r.currency = o.currency
 AND o.ordered_at >= r.valid_from
 AND (o.ordered_at < r.valid_to OR r.valid_to IS NULL);
```

Three details carry the whole query. The interval is **half-open** (`>=` / `<`) — use `<=` on both ends and an order landing exactly on a publish timestamp matches two windows. The `valid_to IS NULL` branch keeps the open-ended latest row; drop it and every order after the last publish vanishes. And DuckDB, Snowflake, and ClickHouse have this built in:

```sql
FROM orders o ASOF LEFT JOIN fx_rates r
  ON o.currency = r.currency AND o.ordered_at >= r.valid_from
```

`ASOF JOIN` alone is an *inner* join — orders predating the first rate disappear. `ASOF LEFT JOIN` surfaces them as NULL, which is a bug you can see.

**The leak:** never match on *nearest* timestamp (`ORDER BY ABS(o.ordered_at - r.valid_from)`). Nearest can be a rate published after the order, so a model trained on that feature learned from the future. Feature stores call the correct behavior point-in-time correctness.

**Invariant to assert:** with a LEFT join, output rows must equal input orders exactly. Any drift means your intervals overlap or gap.
