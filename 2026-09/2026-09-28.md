# Daily Notes - 2026-09-28

## 00:03 - [Data Engineering] Column-Level Lineage: Why Table-Level Graphs Fail Impact Analysis

Most lineage tools show you table edges: `orders` → `stg_orders` → `fct_revenue`. That graph answers "what breaks if this table disappears?" but not the question you actually get paged about: *"we're dropping `orders.discount_cents` — who cares?"* Table-level lineage says everything downstream cares. Column-level lineage says three dashboards do.

The difference is real cost. On a 400-model project, a table-level blast radius is routinely 10x the true one, so every schema change turns into a week of manual grep.

**OpenLineage** is the open standard that carries this. Producers (Airflow, dbt, Spark, Flink) emit run events to a backend (Marquez, DataHub, OpenMetadata) with a `columnLineage` facet:

```json
{
  "eventType": "COMPLETE",
  "job": {"namespace": "dbt", "name": "fct_revenue"},
  "outputs": [{
    "namespace": "snowflake://acct", "name": "analytics.fct_revenue",
    "facets": {"columnLineage": {"fields": {
      "net_revenue": {
        "inputFields": [
          {"namespace": "snowflake://acct", "name": "analytics.stg_orders",
           "field": "gross_cents", "transformations": [{"type": "DIRECT", "subtype": "TRANSFORMATION"}]},
          {"namespace": "snowflake://acct", "name": "analytics.stg_orders",
           "field": "discount_cents", "transformations": [{"type": "DIRECT", "subtype": "TRANSFORMATION"}]}
        ]}}}}}]
}
```

Wire it up in Airflow with the provider — no DAG changes needed:

```bash
pip install apache-airflow-providers-openlineage
export AIRFLOW__OPENLINEAGE__TRANSPORT='{"type":"http","url":"http://marquez:5000"}'
export AIRFLOW__OPENLINEAGE__NAMESPACE=prod
```

For dbt, `dbt-ol run` wraps the CLI and parses `manifest.json` + `catalog.json` into events.

Two things that bite:

1. **`SELECT *` destroys precision.** SQL parsers can only resolve the star if the catalog is populated, so run `dbt docs generate` (or equivalent) before emitting.
2. **Distinguish DIRECT from INDIRECT.** A column used only in a `WHERE` or `GROUP BY` is an `INDIRECT` dependency — it still breaks the model if dropped, but it won't show up in a naive "which columns feed this value" query. Include both in impact analysis; separate them in the UI.

The payoff is an automated pre-merge check: parse the PR's changed columns, query lineage, and comment with the actual downstream consumers instead of guessing.
