## 00:03 - [Data Engineering] Redshift Distribution Styles: The Join That Ships Your Table Across the Cluster

A Redshift query that scans 200MB and runs for four minutes is almost never an I/O problem. It's a **data movement** problem: the join keys live on the wrong slices, so the cluster copies rows over the network before it can join them.

Redshift splits every table across slices. `DISTSTYLE` decides how:

- **KEY** — hash on one column; equal values land on the same slice.
- **ALL** — a full copy of the table on every node.
- **EVEN** — round-robin, no key affinity.
- **AUTO** (default) — Redshift starts ALL for small tables and switches to EVEN, or to KEY if it detects a dominant join pattern.

A join is *collocated* only when both sides are distributed on the join key (or one side is ALL). Otherwise Redshift redistributes at runtime.

### Read it in EXPLAIN

```sql
EXPLAIN
SELECT o.order_id, c.segment
FROM fact_orders o
JOIN dim_customer c ON c.customer_id = o.customer_id;
```

The line to look for:

| Plan node | Meaning |
|---|---|
| `DS_DIST_NONE` | Collocated. This is the goal. |
| `DS_DIST_INNER` | Inner table redistributed across the network. |
| `DS_BCAST_INNER` | Inner table **broadcast to every node**. Worst case. |
| `DS_DIST_BOTH` | Both sides reshuffled. |

`DS_BCAST_INNER` on a large inner table is the classic four-minute query.

### Fixing it

```sql
CREATE TABLE fact_orders (
    order_id     BIGINT,
    customer_id  BIGINT,
    order_ts     TIMESTAMP,
    amount       NUMERIC(18,2)
)
DISTSTYLE KEY
DISTKEY (customer_id)
SORTKEY (order_ts);

-- small dimension: replicate instead of shuffle
CREATE TABLE dim_customer (...) DISTSTYLE ALL SORTKEY (customer_id);
```

Three rules that cover most cases:

1. **One DISTKEY per table** — pick the join key used by your heaviest fact-to-fact or fact-to-large-dimension join, not the one that appears most often.
2. **DISTSTYLE ALL for dimensions under ~2–3M rows.** Storage is multiplied by node count, and every write goes everywhere, so keep it to slow-changing tables.
3. **Never DISTKEY a low-cardinality or skewed column** (`country`, `status`, a nullable FK). Rows pile onto a few slices and one straggler holds the whole query.

Check skew before blaming the plan:

```sql
SELECT slice, SUM(rows) AS row_count
FROM stv_tbl_perm
WHERE name = 'fact_orders'
GROUP BY slice
ORDER BY row_count DESC;
```

If the top slice holds 10x the median, the DISTKEY is the bug — not the query.

## 05:03 - [Data Analytics] Anti-Joins and NULL: Why `NOT IN` Silently Returns Zero Rows

You want customers who have never ordered. The obvious query:

```sql
SELECT count(*) FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders);
```

It returns `0`. Not "no such customers" — the query is broken. If **any** row in `orders` has a NULL `customer_id`, the whole predicate collapses.

`x NOT IN (a, b, NULL)` expands to `x <> a AND x <> b AND x <> NULL`. That last comparison is `UNKNOWN`, never `FALSE`, so the AND can only ever be `UNKNOWN` or `FALSE` — never `TRUE`. Every row is filtered out. One NULL among 50 million order rows silently zeroes your result, and there is no warning.

The three safe patterns:

```sql
-- 1. NOT EXISTS: correlated, NULL-immune, usually the fastest
SELECT count(*) FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);

-- 2. LEFT JOIN + IS NULL: the classic anti-join
SELECT count(*) FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.customer_id IS NULL;

-- 3. EXCEPT: set-based, but note it also de-duplicates
SELECT customer_id FROM customers
EXCEPT
SELECT customer_id FROM orders;
```

Why `NOT EXISTS` is the default choice: Postgres, Snowflake, and BigQuery all plan it as a true anti-join (hash anti-join), so it short-circuits on the first match per outer row. `NOT IN` with a nullable column blocks that rewrite — the planner must materialize the full subquery and evaluate three-valued logic row by row. On a 5M x 50M join I have seen `NOT EXISTS` finish in ~4s where `NOT IN` ran 90s and returned zero.

Two traps in the alternatives. `LEFT JOIN + IS NULL` breaks if you test a nullable column instead of the join key — pick the key, or a literal via `LEFT JOIN (SELECT DISTINCT customer_id, 1 AS m FROM orders)`. And `EXCEPT` (`MINUS` in Oracle) removes duplicates on both sides, so counts from it will not match a row-level anti-join.

Rule of thumb: reach for `NOT IN` only against a column with a `NOT NULL` constraint. Otherwise write `NOT EXISTS` — it is correct whether or not the NULL ever shows up.

## 10:04 - [ML & AI] Nested Cross-Validation: Your Tuned CV Score Measures the Search, Not the Model

You run `GridSearchCV`, print `best_score_`, and put 0.94 in the slide. That number is biased upward, and the bias is not small.

Each config's CV score is `true skill + noise`. Taking the **max** over many configs preferentially selects configs that got lucky on those particular folds. You have optimized against your validation folds, so they are no longer held out — the same leakage as tuning on a test set, just harder to see.

**Demonstration on data with no signal at all.** 150 rows, 40 features, labels drawn independently of the features — true accuracy is exactly 0.50:

```python
X = rng.normal(size=(150, 40))
y = rng.randint(0, 2, size=150)          # labels independent of X

rs = RandomizedSearchCV(RandomForestClassifier(random_state=0),
                        grid, n_iter=60, cv=KFold(5, shuffle=True))
rs.fit(X, y)
rs.cv_results_["mean_test_score"].max()  # 0.600  <- reported
                                         # 0.510  <- mean across the 60 configs
```

Ten points of accuracy conjured out of pure noise. Note the mean across configs sits at 0.510, right at truth — it is the `max` that does the damage.

**The fix is nested CV.** An outer loop estimates performance; the entire search is refit inside each outer fold, so no fold ever scores a config it helped choose:

```python
cross_val_score(RandomizedSearchCV(est, grid, cv=inner), X, y, cv=outer).mean()
# 0.540 on the same noise data
```

Still not 0.500 on a single draw — nested CV is unbiased in expectation, not per-dataset — but it removes most of the gap, and averaged over repeated datasets it lands near truth.

**Practical rules:**

- The bias grows with the number of configs searched and with CV noise, so it is worst exactly where people search hardest: small `n`, wide grids, 500-trial Optuna runs.
- `best_score_` is valid for *ranking* configs. It is not an estimate of anything.
- Cost is `outer x inner` fits. When that is too expensive, a genuinely untouched holdout set gives the same protection for one extra fit.
- The selected hyperparameters are still fine to keep — it is only the reported score that is contaminated.
