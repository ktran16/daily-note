## 00:03 - [Data Engineering] Schema Registry Compatibility: BACKWARD Decides Who Upgrades First

Most teams set `BACKWARD` on their Schema Registry because it is the default, then get surprised when a deploy breaks. The mode is not a quality setting — it is a statement about **deployment order**.

**BACKWARD** = a consumer using the *new* schema can read data written with the *old* one. So consumers must be deployed **first**, then producers. Legal changes: delete a field, or add a field *that has a default*.

**FORWARD** = a consumer still on the *old* schema can read data written with the *new* one. Producers deploy first. Legal changes: add a field, or delete a field that has a default.

**FULL** = both, so order doesn't matter — and almost every change must carry a default.

```json
// v1
{"type":"record","name":"Order","fields":[
  {"name":"id","type":"string"},
  {"name":"total_cents","type":"long"}
]}

// v2 — BACKWARD-compatible: new field has a default
{"type":"record","name":"Order","fields":[
  {"name":"id","type":"string"},
  {"name":"total_cents","type":"long"},
  {"name":"currency","type":"string","default":"USD"}
]}
```

Drop the `"default"` and the registry rejects it: an old record has no `currency`, and the new reader has nothing to fill in.

### The transitive trap

Non-transitive modes check the candidate schema **only against the latest version**. So you can remove `total_cents` in v2, re-add it as a `string` in v3, and every check passes — while a consumer pinned to v1 dies on a type mismatch. Kafka topics retain data for days or weeks, so "the latest version" is not what is actually on the wire.

If consumers replay history — and Flink/Spark jobs restarting from an early offset do exactly that — use the transitive variant:

```bash
curl -X PUT -H "Content-Type: application/json" \
  --data '{"compatibility":"BACKWARD_TRANSITIVE"}' \
  http://schema-registry:8081/config/orders-value
```

Set it **per subject**, not globally, and test with the registry's dry-run endpoint (`/compatibility/subjects/<subject>/versions/latest`) in CI before a schema ever reaches production.

## 05:04 - [Data Analytics] Multi-Touch Attribution in SQL: Why First-Touch and Last-Touch Disagree

Every channel report you have ever seen is an attribution model in disguise. When paid search claims 40% of revenue and the CMO's dashboard says 22%, nobody is lying — they picked different rules for splitting one conversion across many touches.

Start from a touch log: one row per (user, channel, touched_at), plus a conversion table. The three baseline models are all one window function apart.

```sql
WITH touches AS (
  SELECT
    c.conversion_id,
    c.revenue,
    t.channel,
    ROW_NUMBER() OVER (PARTITION BY c.conversion_id ORDER BY t.touched_at)      AS touch_asc,
    ROW_NUMBER() OVER (PARTITION BY c.conversion_id ORDER BY t.touched_at DESC) AS touch_desc,
    COUNT(*)    OVER (PARTITION BY c.conversion_id)                             AS n_touches
  FROM conversions c
  JOIN touchpoints t
    ON t.user_id = c.user_id
   AND t.touched_at <= c.converted_at
   AND t.touched_at >  c.converted_at - INTERVAL '30 days'   -- lookback window
)
SELECT
  channel,
  SUM(revenue) FILTER (WHERE touch_asc  = 1)        AS first_touch_revenue,
  SUM(revenue) FILTER (WHERE touch_desc = 1)        AS last_touch_revenue,
  SUM(revenue / n_touches)                          AS linear_revenue
FROM touches
GROUP BY channel;
```

Three numbers, one query, and they will not match. On a typical B2C funnel, paid social and display collect first touches while brand search and email collect last touches — so last-touch systematically overpays the channels that sit closest to the purchase and underpays discovery. A channel with 15% first-touch credit and 3% last-touch credit is not underperforming; it is upstream.

Two details decide whether the output is defensible:

**The lookback window is a modeling choice, not a technicality.** Widening 30 days to 90 pulls in more touches, which shrinks every per-touch share under linear. Publish the window next to the number.

**The join can fan out.** One user with 12 touches and 3 conversions produces 36 rows. `n_touches` is computed per conversion, so linear still sums to exactly `revenue` per conversion — but any `SUM(revenue)` you add without that guard will trip. Always assert `SUM(linear_revenue) = SUM(total revenue)` as a test.

Ship all three columns. A single attributed number invites the argument; three columns side by side turn it into a conversation about where the channel sits in the funnel.
