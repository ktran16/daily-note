# Daily Notes - 2026-09-07

## 00:03 - [Data Engineering] Schema Registry Compatibility: BACKWARD Decides Who Upgrades First

Most teams set `BACKWARD` on their Schema Registry because it is the default, then get surprised when a deploy breaks. The mode is not a quality setting — it is a statement about **deployment order**.

**BACKWARD** = a consumer using the *new* schema can read data written with the *old* one. So consumers must be deployed **first**, then producers. Legal changes: delete a field, or add a field *that has a default*.

**FORWARD** = a consumer still on the *old* schema can read data written with the *new* one. Producers deploy first. Legal changes: add a field, or delete a field that has a default.

**FULL** = both, so order doesn't matter — and almost every change must carry a default.

```json
// v1
{"type":"record","name":"Order","fields":[
  {"name":"id","type":"string"},
  {"name":"total_cents","type":"long"}
]}

// v2 — BACKWARD-compatible: new field has a default
{"type":"record","name":"Order","fields":[
  {"name":"id","type":"string"},
  {"name":"total_cents","type":"long"},
  {"name":"currency","type":"string","default":"USD"}
]}
```

Drop the `"default"` and the registry rejects it: an old record has no `currency`, and the new reader has nothing to fill in.

### The transitive trap

Non-transitive modes check the candidate schema **only against the latest version**. So you can remove `total_cents` in v2, re-add it as a `string` in v3, and every check passes — while a consumer pinned to v1 dies on a type mismatch. Kafka topics retain data for days or weeks, so "the latest version" is not what is actually on the wire.

If consumers replay history — and Flink/Spark jobs restarting from an early offset do exactly that — use the transitive variant:

```bash
curl -X PUT -H "Content-Type: application/json" \
  --data '{"compatibility":"BACKWARD_TRANSITIVE"}' \
  http://schema-registry:8081/config/orders-value
```

Set it **per subject**, not globally, and test with the registry's dry-run endpoint (`/compatibility/subjects/<subject>/versions/latest`) in CI before a schema ever reaches production.
