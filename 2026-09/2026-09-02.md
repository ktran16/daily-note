## 00:04 - [Data Engineering] Copy-on-Write vs Merge-on-Read: The Update Mode That Decides Your Latency

Parquet files are immutable. So when an Iceberg, Delta, or Hudi table handles a `DELETE` or `MERGE`, it has to choose *when* to pay the rewrite cost. That choice is copy-on-write vs merge-on-read, and it is the single biggest lever on write latency in a lakehouse.

**Copy-on-write (CoW).** Updating one row rewrites the entire data file containing it. A 512 MB file, one changed row, 512 MB rewritten. Writes are slow and amplify badly; reads are as fast as a plain Parquet scan because there is nothing to reconcile.

**Merge-on-read (MoR).** The writer leaves the data file alone and appends a small *delete file* recording which rows are dead. Writes are fast and proportional to the change. Readers must now scan data files *and* apply every outstanding delete file — so read cost grows with the backlog until compaction clears it.

Iceberg sets this per operation, not per table:

```sql
ALTER TABLE db.orders SET TBLPROPERTIES (
  'write.update.mode'  = 'merge-on-read',
  'write.delete.mode'  = 'merge-on-read',
  'write.merge.mode'   = 'copy-on-write'
);
```

That combination is a common shape: fast streaming upserts, but keep the big periodic `MERGE` rewriting cleanly.

Iceberg's MoR has two delete-file flavors, and the difference matters:

- **Position deletes** — "rows 5, 17, 900 of `file-a.parquet` are dead." Cheap to apply; the writer already knows the positions.
- **Equality deletes** — "any row where `order_id = 42` is dead." Written when the producer *doesn't* know row positions, which is exactly the streaming CDC case. Readers must anti-join every matching data file against them. These are the ones that quietly destroy query performance.

The operational rule: **MoR is a loan, and compaction is the repayment.** If you enable merge-on-read, you must schedule rewrites or reads degrade steadily.

```sql
CALL catalog.system.rewrite_data_files(
  table => 'db.orders',
  options => map('delete-file-threshold', '5')
);
```

Choose CoW for batch-loaded tables read far more than written. Choose MoR for streaming CDC sinks and late-arriving corrections — then treat the compaction job as part of the pipeline, not as cleanup you'll get to later.

## 05:04 - [Data Analytics] Metric Trees: Making a North-Star Number Explainable

A north-star metric that only goes up or down is a smoke alarm with no address. A metric tree fixes that by decomposing it into factors that **multiply back to the original**, so every movement lands on exactly one branch.

The rule: decompose multiplicatively, and make each factor owned by a different team.

```
Weekly Revenue = Active Users x Order Rate x Avg Order Value
                 (growth)      (product)    (pricing/merch)
```

Each factor is a real metric someone can move. Contrast with additive "drivers" like `revenue = web + mobile`, which tell you *where* but never *why*.

### Attributing a change

Say revenue fell from $2.40M to $2.20M week over week — down 8.3%:

| Factor | W1 | W2 | Change |
|---|---|---|---|
| Buyers | 50,000 | 48,000 | −4.0% |
| Orders per buyer | 1.200 | 1.176 | −2.0% |
| Avg order value | $40.00 | $39.00 | −2.5% |

Percent changes don't sum to −8.3% (they compound), so use logs — log contributions *are* additive:

```sql
select
  ln(48000.0/50000)  as d_buyers,     -- -0.0408
  ln(1.176/1.200)    as d_orders,     -- -0.0202
  ln(39.0/40.0)      as d_aov,        -- -0.0253
  ln((48000*1.176*39.0)/(50000*1.200*40.0)) as d_total  -- -0.0863
;
```

The three parts sum to the total exactly. Share of the drop: buyers 47%, AOV 29%, orders per buyer 23%. Now the alert routes itself.

### Building it in the warehouse

Compute factors from one grain, never from separate queries — that's how a tree stops reconciling:

```sql
with weekly as (
  select date_trunc('week', order_ts) as wk,
         count(distinct user_id)      as buyers,
         count(*)                     as orders,
         sum(amount)                  as revenue
  from fct_orders group by 1
)
select wk, revenue,
       buyers,
       orders::float / buyers   as orders_per_buyer,
       revenue / orders         as aov,
       buyers * (orders::float/buyers) * (revenue/orders) as rebuilt  -- = revenue
from weekly order by wk;
```

That `rebuilt = revenue` check is the tree's unit test. Add it as a dbt test with a tolerance of 0.01 — if the identity ever breaks, a definition drifted and every downstream attribution is now fiction.

Keep trees shallow. Three levels is usually the limit before leaf metrics get too noisy weekly to distinguish signal from variance.

## 10:03 - [ML & AI] RMSE vs MAE: Your Regression Metric Silently Chooses a Different Model

Picking a regression metric is not a reporting decision made after training — it decides *what your model predicts*. Every loss has a statistical minimizer, and they are not the same number.

- **Squared error (RMSE/MSE)** is minimized by the **conditional mean**.
- **Absolute error (MAE)** is minimized by the **conditional median**.
- **Pinball loss** at quantile τ is minimized by the **τ-th quantile**.

On skewed data those diverge badly. Take five days of demand: `[10, 12, 14, 16, 100]` — four normal days and one viral spike.

| Constant prediction | RMSE | MAE |
|---|---|---|
| mean = 30.40 | **34.86** | 27.84 |
| median = 14.00 | 38.52 | **18.80** |

Each metric crowns a different winner, and the gap is not cosmetic: 30.4 vs 14 is a 2.2× difference in forecasted demand. Train with MSE and you get a model that hedges toward rare spikes on every ordinary day. Train with MAE and you get one that models the typical day and simply eats the spike.

So choose by asking what the error *costs*:

- Errors hurt **proportionally to size** (energy load, latency budgets) → RMSE.
- A few wild outliers are noise you refuse to chase → MAE.
- Costs are **asymmetric** → quantile loss. Stockouts cost 4× overstock? Forecast the 80th percentile, not the mean.

```python
# pinball / quantile loss — tau=0.5 reduces to MAE (up to a factor of 2)
def pinball(y, yhat, tau):
    u = y - yhat
    return max(tau * u, (tau - 1) * u)

# sklearn: native quantile objectives
from sklearn.ensemble import GradientBoostingRegressor
GradientBoostingRegressor(loss="quantile", alpha=0.8).fit(X, y)
# LightGBM: objective="quantile", alpha=0.8
```

**Avoid MAPE.** It divides by the actual, so it explodes near zero and punishes over-forecasts harder than under-forecasts — it is minimized by a value *below* the median (12.0 on the data above, under the median of 14). That is a built-in downward bias that quietly guarantees you understock. If you need a relative metric, prefer MASE or WAPE.

Rule: pick the loss from the cost function, then report that same metric. Training on MSE and reporting MAE means you optimized a model you never evaluated.
