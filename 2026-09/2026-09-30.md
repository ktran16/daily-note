## 00:02 - [Data Engineering] BigQuery Slots: Why the Same Query Takes 8 Seconds Today and 4 Minutes Tomorrow

Most BigQuery tuning advice is about bytes scanned — partition, cluster, stop `SELECT *`. That controls your **on-demand bill**. It does not control your **latency**. Latency is decided by slots, and the two are independent enough that a query can scan identical bytes and run 30× slower.

A slot is a unit of CPU + memory that executes one shard of one stage. A query is planned into stages; each stage needs N slots to run its N parallel workers. If only 200 slots are free and the stage wants 2,000, the remaining 1,800 units queue and the stage serializes. Nothing about your SQL changed — your neighbours got busy.

Which regime you're in matters:

- **On-demand**: you pay per TB scanned. Slots come from a shared pool with a soft per-project ceiling (~2,000). Concurrency is invisible and unguaranteed.
- **Capacity (editions)**: you buy a baseline of slots per reservation and pay per slot-hour. Autoscaling adds slots up to `max_slots`. Bytes scanned become free — you're now paying for time.

Diagnose before you buy. `total_slot_ms / elapsed_ms` is the average slot count the query actually got:

```sql
SELECT
  job_id,
  query,
  total_bytes_processed / POW(1024, 4) AS tb_scanned,
  total_slot_ms / 1000                  AS slot_seconds,
  TIMESTAMP_DIFF(end_time, start_time, MILLISECOND) AS elapsed_ms,
  SAFE_DIVIDE(total_slot_ms,
    TIMESTAMP_DIFF(end_time, start_time, MILLISECOND)) AS avg_slots
FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_PROJECT
WHERE creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
  AND job_type = 'QUERY' AND state = 'DONE'
ORDER BY total_slot_ms DESC
LIMIT 50;
```

Read it this way: **high `slot_seconds`** means the query is genuinely expensive — fix the SQL. **Low `avg_slots` with high `elapsed_ms`** means it was starved — fix capacity or scheduling. Same symptom, opposite remedy.

Two practical levers once you're on reservations: put dbt's nightly build and your BI layer in *separate* reservations so a backfill can't starve dashboards, and set `ignore_idle_slots = false` on the interactive one so it can borrow when batch is quiet. The cheapest slot is the one already paid for.

## 05:04 - [Data Analytics] Sample Ratio Mismatch: The Check That Invalidates the Test Before You Read It

Before you look at a single metric in an A/B test, check that the split you asked for is the split you got. A 50/50 assignment that lands 10,300 / 9,700 looks like rounding. It isn't.

The test is a chi-square goodness-of-fit against your intended ratio:

```sql
WITH counts AS (
  SELECT variant, COUNT(DISTINCT user_id) AS n
  FROM experiment_exposures
  WHERE experiment_id = 'checkout_redesign_v2'
  GROUP BY variant
),
totals AS (SELECT SUM(n) AS total FROM counts)
SELECT c.variant, c.n,
       t.total * 0.5                           AS expected,
       ROUND(c.n / (t.total * 0.5) - 1, 4)     AS pct_deviation,
       SUM(POWER(c.n - t.total * 0.5, 2) / (t.total * 0.5))
         OVER ()                               AS chi_square
FROM counts c CROSS JOIN totals t;
```

With 10,300 / 9,700 out of 20,000, χ² = 18.0 on 1 degree of freedom — p ≈ 2.2 × 10⁻⁵, roughly a 1-in-45,000 event. A 3% deviation is not noise. Confirm in Python:

```python
from scipy.stats import chisquare
chisquare([10300, 9700])   # statistic=18.0, pvalue=2.21e-05
```

Use a strict threshold — **p < 0.0005**, not 0.05. You run this on every experiment, so a lenient cutoff buries you in false alarms.

The point of SRM is not that the imbalance biases the average. It's that a broken split means assignment or exposure logging is broken, and you have no idea which users are missing or why. Usual culprits:

- **Redirect-based assignment** — treatment loads a second page, some users bail, and their absence correlates with slow connections.
- **Exposure logged after render** — treatment throws a JS error for a subset, so they never get counted.
- **Bot filtering applied post-assignment** with variant-dependent rules.
- **Wrong unit** — counting sessions when you randomized on users.

Every one of those drops users *non-randomly*, so the surviving groups aren't comparable. When SRM fires, don't adjust for it — fix the pipeline and rerun. A statistically significant lift on a broken split is not a result.

## 10:03 - [ML & AI] Retraining Triggers: Measure Your Model's Decay Rate Before You Pick a Schedule

"Retrain monthly" is almost always a number someone picked in a meeting. The honest version is a measurement you can run today with data you already have.

**Backtest the decay.** Freeze a model trained on everything up to time `T`, then score it against successive holdout slices *after* `T` without refitting. The curve tells you how fast the world moves:

```python
model.fit(X[dates < T], y[dates < T])          # frozen once

for wk in range(0, 12, 2):
    lo = T + pd.Timedelta(weeks=wk)
    hi = lo + pd.Timedelta(weeks=2)
    sl = (dates >= lo) & (dates < hi)
    print(wk, roc_auc_score(y[sl], model.predict_proba(X[sl])[:, 1]))
```

A typical result: 0.812 → 0.806 → 0.798 → 0.781 over eight weeks. That is ~0.004 AUC per week, accelerating. If the business tolerates 0.01 AUC of drift, your cadence is ~3 weeks — not 4, and definitely not quarterly. Run the same loop on a *second* frozen origin `T'` to confirm the slope isn't one bad month.

**Label latency is the hard ceiling.** If chargebacks mature in 60 days, a weekly retrain re-fits nearly the same labels with extra compute and a new model version to audit. Effective cadence can never be much shorter than label maturity plus pipeline lag. Check that before optimizing anything.

**Three trigger types, and how they compose:**

| Trigger | Signal | Latency | Failure mode |
|---|---|---|---|
| Calendar | none | n/a | retrains when nothing changed |
| Performance | AUC/logloss on matured labels | label latency | tells you late |
| Drift (PSI, KS) | input distributions | immediate | fires on harmless shift |

Use drift as an **alarm**, matured performance as the **trigger**, and calendar as a **floor** so a stale model can't sit forever behind a quiet monitor.

One caveat worth internalizing: retraining on fresher rows fixes *covariate* shift — the inputs moved, the relationship didn't. If a retrain doesn't recover the metric, you have concept drift, and no amount of new data will help. That's a signal to add features, not to shorten the schedule.

## 15:03 - [Crypto & Business] Business Idea: Unbilled-Work Recovery for Managed Service Providers

**Customer:** Owner-operators of managed IT service providers (MSPs) with 8–40 technicians and $2M–$12M revenue, running ConnectWise Manage, Autotask, or HaloPSA. There are roughly 25,000 such firms in the US.

**The problem:** MSPs sell flat-rate contracts — say $145/seat/month covering "standard support." Anything outside that scope (server migrations, after-hours work, a client's third-party app nobody agreed to support) is billable. In practice technicians close the ticket and nobody invoices it. The data proving it happened is sitting in the PSA: time entries, work types, ticket categories, contract coverage flags.

**Worked example.** A 22-tech MSP logs ~3,100 time entries/month. Audit 6 months and a typical result is 4–7% of logged hours are out-of-scope but billed at $0. At 3,100 entries × 0.65 hrs avg × 5% × $165/hr, that's **$16,600/month** leaking — $199K/year on a $7M business whose net margin is maybe 12%. It is close to pure profit.

**Product:** a read-only PSA integration that scores every time entry against contract coverage, flags likely out-of-scope work with the evidence line, and emails the service manager a Friday review queue. An LLM classifier on ticket notes handles the messy part — "installed QuickBooks plugin" is out of scope, "reset password" is not. Humans approve; you never touch invoicing.

**Pricing:** $600–$1,800/month by tech count, or 15% of recovered revenue for the first year (easier first sale, worse retention economics — pick tiered SaaS once you have proof).

**Startup cost:** ~$8K–$15K. PSA sandbox access is free for partners, LLM classification runs ~$40/month per client, and the real spend is 3–4 months of your own time plus a $2K accountant/attorney setup.

**Main risk:** not technical. It's that MSP owners *know* they leak and have decided billing clients is worse than losing the money. You are selling a conversation they avoid. Scope creep as a relationship strategy is a real business model.

**First validation step:** get three MSP owners to export 6 months of time entries to CSV. Classify them by hand in a weekend. If you cannot find >3% leakage in at least two of three, the market isn't there — and you learned it for $0.

## 19:02 - [PC Hardware] IOMMU Groups: Why GPU Passthrough Fails Before the VM Ever Boots

Passing a GPU into a VM looks like a software problem. It is mostly a motherboard topology problem, and you can predict failure before you buy parts.

The IOMMU (Intel VT-d, AMD-Vi) gives each device its own DMA address space so a guest can drive hardware directly without being able to scribble on host memory. Enable it in BIOS alongside **Above 4G Decoding**, then on the host add `iommu=pt` (plus `intel_iommu=on` on older Intel kernels; AMD-Vi comes up automatically when firmware advertises it).

The blocker is granularity. **You pass through an entire IOMMU group, never a single device.** List yours:

```bash
for d in /sys/kernel/iommu_groups/*/devices/*; do
  g=${d#*/iommu_groups/}; g=${g%%/*}
  printf 'Group %3s: ' "$g"; lspci -nns "${d##*/}"
done | sort -k2 -n
```

Groups are decided by PCIe topology and whether upstream bridges implement **ACS (Access Control Services)**. Without ACS, two devices behind the same switch can peer-to-peer DMA to each other, so the kernel cannot prove isolation and lumps them together. In practice:

| Slot | Typical outcome |
|---|---|
| CPU-attached x16 (top slot) | Own group — usually clean |
| Chipset-attached x4/x1 slots | Shared group with USB, SATA, NIC |
| Consumer B/H-series boards | Coarse chipset grouping, few ACS bridges |
| HEDT / Threadripper / Xeon-W | Per-slot groups, ACS on root ports |

So: **put the passthrough GPU in the primary CPU-attached x16 slot.** That one decision resolves most cases.

Three gotchas that cost evenings:

- A GPU is multi-function. Bind *every* function — `01:00.0` (video), `01:00.1` (HDMI audio), and on some cards `.2`/`.3` (USB-C, UCSI). Leaving audio on the host driver breaks the guest.
- You need output for the host too: a second GPU, an iGPU, or run headless over SSH. Binding your only GPU to `vfio-pci` gives you a black screen at boot.
- Older Radeon cards (Polaris, Vega, Navi 10) have the reset bug — they work once, then fail on VM reboot until the host power-cycles. The `vendor-reset` kernel module fixes it.

The `pcie_acs_override=downstream,multifunction` patch splits groups artificially. It works, and it genuinely removes the isolation guarantee. Acceptable for a homelab you control; not for guests you do not trust.

Bind cleanly with `driverctl set-override 0000:01:00.0 vfio-pci` rather than hand-editing modprobe files — it survives kernel upgrades.
