# Daily Notes - 2026-09-30

## 00:02 - [Data Engineering] BigQuery Slots: Why the Same Query Takes 8 Seconds Today and 4 Minutes Tomorrow

Most BigQuery tuning advice is about bytes scanned — partition, cluster, stop `SELECT *`. That controls your **on-demand bill**. It does not control your **latency**. Latency is decided by slots, and the two are independent enough that a query can scan identical bytes and run 30× slower.

A slot is a unit of CPU + memory that executes one shard of one stage. A query is planned into stages; each stage needs N slots to run its N parallel workers. If only 200 slots are free and the stage wants 2,000, the remaining 1,800 units queue and the stage serializes. Nothing about your SQL changed — your neighbours got busy.

Which regime you're in matters:

- **On-demand**: you pay per TB scanned. Slots come from a shared pool with a soft per-project ceiling (~2,000). Concurrency is invisible and unguaranteed.
- **Capacity (editions)**: you buy a baseline of slots per reservation and pay per slot-hour. Autoscaling adds slots up to `max_slots`. Bytes scanned become free — you're now paying for time.

Diagnose before you buy. `total_slot_ms / elapsed_ms` is the average slot count the query actually got:

```sql
SELECT
  job_id,
  query,
  total_bytes_processed / POW(1024, 4) AS tb_scanned,
  total_slot_ms / 1000                  AS slot_seconds,
  TIMESTAMP_DIFF(end_time, start_time, MILLISECOND) AS elapsed_ms,
  SAFE_DIVIDE(total_slot_ms,
    TIMESTAMP_DIFF(end_time, start_time, MILLISECOND)) AS avg_slots
FROM `region-us`.INFORMATION_SCHEMA.JOBS_BY_PROJECT
WHERE creation_time > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 7 DAY)
  AND job_type = 'QUERY' AND state = 'DONE'
ORDER BY total_slot_ms DESC
LIMIT 50;
```

Read it this way: **high `slot_seconds`** means the query is genuinely expensive — fix the SQL. **Low `avg_slots` with high `elapsed_ms`** means it was starved — fix capacity or scheduling. Same symptom, opposite remedy.

Two practical levers once you're on reservations: put dbt's nightly build and your BI layer in *separate* reservations so a backfill can't starve dashboards, and set `ignore_idle_slots = false` on the interactive one so it can borrow when batch is quiet. The cheapest slot is the one already paid for.
