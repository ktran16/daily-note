## 00:04 - [Data Engineering] dbt Ephemeral Models: The CTE That Gets Pasted Into Every Consumer

`materialized: ephemeral` is the one dbt materialization that builds nothing in the warehouse. Instead, the model's SQL is interpolated into every downstream model as a CTE at compile time.

```yaml
models:
  - name: stg_orders_cleaned
    config:
      materialized: ephemeral
```

```sql
-- models/marts/fct_orders.sql
select * from {{ ref('stg_orders_cleaned') }}
```

compiles to:

```sql
with __dbt__cte__stg_orders_cleaned as (
  select order_id, customer_id, amount_usd
  from raw.orders
  where not is_test_order
)
select * from __dbt__cte__stg_orders_cleaned
```

**The cost nobody budgets for: the work happens once per consumer.** A table or view is computed once and read N times. An ephemeral model is re-executed inside each of the N models that `ref` it. Three marts referencing an ephemeral that scans 400 GB costs you 1.2 TB. Find your multi-consumer ephemerals before the bill does:

```bash
dbt ls --select stg_orders_cleaned+1 --resource-type model
```

**You can't inspect it.** There is no relation to query. `dbt run --select stg_orders_cleaned` builds nothing — dbt skips ephemeral nodes. Debugging means reading the compiled SQL of a *consumer*:

```bash
dbt compile --select fct_orders
# target/compiled/<project>/models/marts/fct_orders.sql
```

Tests defined on an ephemeral model do run (dbt wraps the test query around the CTE), but a Python model cannot `ref()` one — Python models need a real relation and will error.

**Chains compound.** Ephemeral referencing ephemeral referencing ephemeral yields one enormous compiled query that no one can read. Engines also differ on CTEs: Snowflake and BigQuery generally inline them, a CTE referenced twice in the same query can be evaluated twice, and Postgres before v12 always materialized CTEs as an optimization fence.

Use it for thin, cheap glue — a recast/rename layer, a filter, a single-use intermediate you don't want cluttering the warehouse with objects nobody queries. Avoid it for anything expensive, anything with more than a couple of consumers, or anything you will need to debug under pressure. Default to `view` for cheap-and-inspectable and `table` for expensive-and-reused. Ephemeral saves warehouse objects, not compute.

## 05:05 - [Data Analytics] Axis Baselines: When Truncating Y Is Honest, and When It's a 48x Lie

Whether a y-axis must include zero is not a matter of taste. It follows from what the mark encodes.

**Bars and areas encode value as length** from the baseline. The eye compares the lengths, so a truncated baseline breaks proportionality. **Lines and dots encode value as position.** Nothing is being compared to the axis, so forcing zero just wastes plot height.

Tufte's lie factor makes the damage measurable: the apparent size of the effect divided by its actual size.

```python
def lie_factor(v1, v2, axis_min):
    data = (v2 - v1) / v1
    graphic = (v2 - axis_min) / (v1 - axis_min) - 1
    return graphic / data

lie_factor(4.8, 5.0, 4.7)   # 48.0
lie_factor(4.8, 5.0, 4.0)   # 6.0
lie_factor(4.8, 5.0, 0.0)   # 1.0
```

Conversion moving 4.8% → 5.0% is a 4.2% relative lift. Drawn as bars on an axis starting at 4.7, one bar is three times the height of the other — the chart says +200%. Lie factor 48. Tufte's rule of thumb is to stay between 0.95 and 1.05, which for bars means zero, every time.

The converse is just as real. DAU oscillating between 2.41M and 2.45M is a 1.6% swing. Force that line chart to zero and the entire signal occupies 1.6% of the plot height — a flat line that hides a week of movement. A zero baseline there isn't honesty, it's a resolution loss.

**When you genuinely need to show a small difference, change the encoding, not the axis.** Options that stay at lie factor 1.0:

- A dot plot with a reference line at the baseline value.
- Plot the delta or percent change directly, so the 0.2-point gap gets a scale built for it and zero means "no change."
- Keep the bars honest and put the lift in a label.

Check your tools: Power BI exposes Y-axis **Start** on bar visuals, Tableau has an **Include Zero** toggle, and matplotlib's `set_ylim` will happily crop a bar chart that autoscaled correctly. Each one is a single click between a defensible chart and a 48x exaggeration — and the reader cannot see which one you picked.

## 10:03 - [ML & AI] Successive Halving: Explore 9x More Configs for the Same Compute

Random search over hyperparameters wastes most of its budget training configurations that were obviously bad after two epochs. Successive halving fixes this: train many candidates cheaply, kill the worst, give survivors more resource, repeat.

**The budget arithmetic.** Let full training be 27 epochs and your budget be 2700 epochs (100 full fits).

Random search spends it on **100 configs**, each trained to completion.

Successive halving with reduction factor η=3, starting at 1 epoch, promotes through rungs 1 → 3 → 9 → 27, keeping the top 1/3 each time. Starting with `n` configs, and resuming from checkpoints so each rung only pays the *increment*:

| Rung | Configs | Added epochs each | Cost |
|---|---|---|---|
| 0 | n | 1 | n |
| 1 | n/3 | 2 | 2n/3 |
| 2 | n/9 | 6 | 2n/3 |
| 3 | n/27 | 18 | 2n/3 |

Total = `n(1 + 3·2/3)` = **3n**, so 2700 epochs buys **n = 900 configs** — 9x the search space for identical compute.

The general form: rung `i` holds `n/η^i` configs at resource `r_min·η^i`, so every rung past the first adds `n·r_min·(η-1)/η` and the total is

```
cost = n · r_min · [1 + (k-1)(η-1)/η]
```

That 3n assumes you **resume from a checkpoint**, paying only the increment. scikit-learn does not — it refits each survivor from scratch, so every rung costs the full `n·r_min` and the total is `k·n·r_min` = 4n, or 675 configs. Still 6.75x random search, but know which one you are buying.

```python
from sklearn.experimental import enable_halving_search_cv  # noqa
from sklearn.model_selection import HalvingRandomSearchCV

search = HalvingRandomSearchCV(
    estimator, param_distributions,
    factor=3,                 # eta: keep top 1/3
    resource="n_estimators",  # or "n_samples" (default)
    min_resources=20,         # must clear the warmup phase
    max_resources=540,
    aggressive_elimination=True,
    cv=5, random_state=0,
).fit(X, y)
```

**The failure mode.** Halving assumes early rank correlates with final rank. It does not when a config is *designed* to start slow: a small learning rate, strong weight decay, or a warmup schedule all look terrible at epoch 1 and win at epoch 27. Halving eliminates exactly those.

Two defenses: set `min_resources` past the warmup (if warmup is 5 epochs, never judge at 1), and use `resource="n_samples"` for tabular models, where data subsets rank configs more stably than truncated epochs do.

**Parallelism.** Synchronous halving stalls — the rung can't promote until the slowest trial finishes. ASHA (Optuna's `SuccessiveHalvingPruner`, Ray Tune's `ASHAScheduler`) promotes asynchronously the moment a trial clears the rung's current threshold, which is what you want on more than a couple of workers.

## 15:05 - [Crypto & Business] Deferred Revenue and RPO: The Balance Sheet Knew Two Quarters Before the P&L

A subscription P&L is a trailing average. If you bill a customer $120K upfront for twelve months, ASC 606 lets you recognize $10K a month — so this quarter's revenue is mostly the product of sales that closed *last* year. Revenue growth can stay positive for two or three quarters after new sales have already collapsed. The forward signal sits on the balance sheet instead.

**The mechanic.** Cash collected but not yet earned becomes a liability: deferred revenue. Each month, $10K moves from that liability into revenue. So:

`calculated billings = revenue + Δ deferred revenue`

That's the standard reconstruction, because almost no SaaS company reports billings directly.

**Worked example.** A company with $12M ARR:

| | Q3 | Q4 |
|---|---|---|
| Revenue | $3.00M | $3.10M (+3%) |
| Deferred revenue, end | $6.00M | $5.40M |

Q4 billings = 3.10 + (5.40 − 6.00) = **$2.50M**. Revenue grew 3% while billings fell ~19%. Nothing in the income statement says so, but the pipeline that feeds the next four quarters of revenue has already shrunk. Three quarters later the revenue line catches up and everyone calls it a surprise.

**The better metric.** Remaining performance obligation (RPO) is contracted revenue not yet recognized — including the *unbilled* years of a multi-year deal, which deferred revenue excludes. Current RPO (cRPO, the portion due within 12 months) is the cleanest near-term demand read, since total RPO swings wildly on one large five-year contract.

**The false alarm.** Billings and deferred revenue also crater when a company shifts from annual-prepay to monthly billing — same ARR, same customers, a third of the cash upfront. Before calling a decline, check whether billing-terms mix changed. Compare cRPO or ARR instead; both are billing-agnostic.

*Educational content on financial mechanics, not investment advice.*

## 19:04 - [Wildcard] The Linux OOM Killer: Why Your Process Died With No Error at All

A process vanishes. No traceback, no log line, just `Killed` in the shell or exit code **137** (128 + SIGKILL's 9). That is the kernel's out-of-memory killer, and it leaves no evidence in your application because `SIGKILL` cannot be caught.

**Why it happens:** Linux overcommits. `malloc()` hands back address space, not physical pages — so allocation succeeds for memory that does not exist. The reckoning comes when the process first *touches* those pages and there is nothing left to back them with.

**Confirm it was the OOM killer:**

```bash
journalctl -k --since "1 hour ago" | grep -i -e oom -e "killed process"
systemctl status myservice        # look for: Result: oom-kill
dmesg -T | grep -A4 "Out of memory"
```

**The victim is usually not the culprit.** The kernel scores each process roughly by RSS + swap + page tables, then kills the *largest* one. So a runaway `cargo build` or a Chrome tab gets your database killed instead. Inspect and bias the scores:

```bash
cat /proc/$(pidof postgres)/oom_score      # current badness
sudo choom -n -500 -p $(pidof postgres)    # protect it (-1000..1000)
```

Persist it in a unit file with `OOMScoreAdjust=-500`, and set `+500` on the known memory hogs.

**Better: contain the hog instead of ranking it.** cgroup v2 keeps the blast radius inside one job:

```bash
systemd-run --user --scope -p MemoryMax=4G -p MemorySwapMax=0 ./big-build.sh
```

Now only that scope gets killed. `MemoryHigh=` throttles with reclaim pressure *before* `MemoryMax=` kills — useful when you would rather a job run slowly than die.

**Two knobs worth knowing:**

| Setting | Effect |
|---|---|
| `vm.overcommit_memory=2` + `vm.overcommit_ratio` | `malloc()` fails honestly instead of lying; breaks apps that reserve huge sparse address space (JVMs, some DBs) |
| `vm.panic_on_oom=1` | Reboot rather than limp on — correct for HA cluster nodes |

**And do not run swapless.** The kernel's hard OOM fires only after the box has already spent minutes thrashing and unresponsive. A little swap plus `systemd-oomd` or `earlyoom` — which act on PSI pressure stalls, not exhaustion — kills the offender while you can still SSH in.
