## 00:03 - [Data Engineering] Spark AQE: Why Tuning `shuffle.partitions` Backwards Makes Jobs Faster

The old Spark tuning ritual was to guess `spark.sql.shuffle.partitions` — too high and you get thousands of 2 MB tasks with scheduler overhead dominating; too low and tasks spill to disk. Adaptive Query Execution (on by default since Spark 3.2) inverts the advice: set it **high** and let Spark coalesce down.

AQE re-plans at shuffle boundaries using real `MapOutputStatistics`, not estimates. Three optimizations matter:

```python
# These are defaults in Spark 3.2+ — shown to make the knobs visible
spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
spark.conf.set("spark.sql.adaptive.advisoryPartitionSizeInBytes", "64MB")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")

# Counter-intuitive: make this LARGE. It is now only the *initial* count.
spark.conf.set("spark.sql.shuffle.partitions", "2000")
```

1. **Coalescing.** 2000 initial partitions holding 8 GB get merged into ~128 tasks of ~64 MB each. A filter that drops 99% of rows no longer produces 2000 nearly-empty tasks.
2. **Join strategy switching.** A sort-merge join whose build side turns out to be 30 MB after filtering is rewritten into a broadcast hash join mid-flight — something static planning misses because it only sees pre-filter table stats.
3. **Skew join splitting.** A partition larger than both `skewedPartitionThresholdInBytes` (256 MB) and `skewedPartitionFactor` × median (5×) is split into sub-partitions, with the other side replicated.

The traps:

- **AQE only re-optimizes at shuffle boundaries.** A scan → filter → write job has no exchange, so AQE does nothing. Skew there is a file-layout problem.
- **Skew splitting covers joins, not aggregations.** A `GROUP BY` on a key where one value is 60% of rows still has a straggler — salt it manually.
- **Setting `shuffle.partitions` low defeats AQE.** Coalescing can merge partitions, never split them. Leaving the old hand-tuned `200` caps how fine-grained AQE can get.

Confirm it fired: the Spark UI SQL tab shows `AQEShuffleRead` nodes labeled `coalesced` or `skewed`, and the final plan differs from the initial one.

## 05:03 - [Data Analytics] Rolling-Origin Backtesting: Why Shuffled K-Fold Says Your Forecast Is 1.8x Better Than It Is

`KFold(shuffle=True)` is the default reflex for validation, and on a time series it quietly answers the wrong question. Shuffling puts test days *between* training days, so the model only has to interpolate — but a forecast has to extrapolate past the last row it ever saw. Any feature carrying a monotone level (a date index, `cumulative_signups`, an autoincrement id) turns that gap into a fantasy score.

Two years of trending, weekly-seasonal daily revenue, a random forest on `day` and `dow`:

```python
import numpy as np, pandas as pd
from sklearn.ensemble import RandomForestRegressor
from sklearn.model_selection import KFold, TimeSeriesSplit
from sklearn.metrics import mean_absolute_error

rng = np.random.default_rng(7); n = 730; t = np.arange(n)
y = 1000 + 2.0*t + 150*np.sin(2*np.pi*t/7) + rng.normal(0, 80, n)
df = pd.DataFrame({"day": t, "dow": t % 7, "y": y})
X, yv = df[["day", "dow"]].values, df.y.values

def cv(sp):
    e = [mean_absolute_error(yv[te],
         RandomForestRegressor(n_estimators=200, random_state=0)
             .fit(X[tr], yv[tr]).predict(X[te]))
         for tr, te in sp.split(X)]
    return np.mean(e)

print(cv(KFold(5, shuffle=True, random_state=0)))  #  70.5
print(cv(TimeSeriesSplit(n_splits=5)))             # 165.9
```

Train on the first 640 days and forecast the last 90 — the thing you actually ship — and MAE is **124.8**. Shuffled K-fold promised 70.5: off by 1.8x, and off in the flattering direction. Trees cannot predict above their training range, so every forecast beyond day 640 flatlines while the real trend keeps climbing. K-fold never tested that because it always had a future row in the training set.

`TimeSeriesSplit` reported 165.9 — pessimistic, because its first folds train on only ~120 days. That is the right kind of wrong: it errs toward caution instead of selling you a model. Read the per-fold spread (173, 149, 149, 155, 204), not just the mean; a fold that blows up is usually one regime change.

Two rules that follow:

- **Size the test fold like your real horizon.** Validating one-day-ahead when the business forecasts a quarter measures a different model.
- **Build features from the past only.** `y.shift(1).rolling(7).mean()` is a feature; `y.rolling(7, center=True).mean()` reads three days into the future and will not exist at prediction time. For multi-step horizons, add a gap between train and test so lag features can't straddle the boundary.
