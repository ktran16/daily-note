# Daily Notes - 2026-10-25

## 00:03 - [Data Engineering] Debezium Incremental Snapshots: Backfilling a Table Without Stopping the Stream

You add a table to `table.include.list` and restart the connector. New changes flow. The 400 million rows that already existed never appear. The usual fix — re-snapshot the whole connector — is worse: a classic snapshot emits **zero streaming events until it finishes**, so every other table in the connector goes dark for hours while the Postgres replication slot pins WAL and the disk fills.

Incremental snapshots (Debezium 1.6+, based on Netflix's DBLog paper) interleave the backfill with normal streaming instead.

### Triggering one

You don't restart anything. You insert a row into the signaling table:

```sql
-- connector config: signal.data.collection=public.debezium_signal
--                   incremental.snapshot.chunk.size=4096
INSERT INTO public.debezium_signal (id, type, data) VALUES (
  gen_random_uuid()::text,
  'execute-snapshot',
  '{"data-collections": ["public.orders"],
    "type": "incremental",
    "additional-conditions": [
      {"data-collection": "public.orders",
       "filter": "created_at >= ''2026-01-01''"}]}'
);
```

The connector reads chunks ordered by primary key, emitting read (`op: "r"`) events into the same topic as the live `c`/`u`/`d` events. Around each chunk it writes open/close watermark signals; any log event seen inside that window for a key in the chunk wins, and the stale snapshot row is dropped before emission. That's the whole deduplication mechanism — no locks, no table-level freeze.

### What this changes downstream

- Your sink must treat `r` as an **upsert**, not "initial load only". Keyed topics plus last-write-wins makes this free; append-only consumers will double-count.
- The table needs a primary key, or set `surrogate-key` in the signal payload.
- Progress is stored in connector offsets, so a restart mid-backfill resumes at the last chunk rather than starting over.
- You can send `pause-snapshot` / `resume-snapshot` / `stop-snapshot` signals when the source database is under load.
- The signaling table must be visible to the connector (included in the capture list), since the signal arrives via the log. MySQL additionally supports a read-only variant driven by a Kafka signal topic.

Reach for this for backfills, newly added tables, and re-syncs after a bad transform. Reserve the blocking snapshot for the very first connector start.
