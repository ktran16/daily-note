## 00:03 - [Data Engineering] Debezium Incremental Snapshots: Backfilling a Table Without Stopping the Stream

You add a table to `table.include.list` and restart the connector. New changes flow. The 400 million rows that already existed never appear. The usual fix — re-snapshot the whole connector — is worse: a classic snapshot emits **zero streaming events until it finishes**, so every other table in the connector goes dark for hours while the Postgres replication slot pins WAL and the disk fills.

Incremental snapshots (Debezium 1.6+, based on Netflix's DBLog paper) interleave the backfill with normal streaming instead.

### Triggering one

You don't restart anything. You insert a row into the signaling table:

```sql
-- connector config: signal.data.collection=public.debezium_signal
--                   incremental.snapshot.chunk.size=4096
INSERT INTO public.debezium_signal (id, type, data) VALUES (
  gen_random_uuid()::text,
  'execute-snapshot',
  '{"data-collections": ["public.orders"],
    "type": "incremental",
    "additional-conditions": [
      {"data-collection": "public.orders",
       "filter": "created_at >= ''2026-01-01''"}]}'
);
```

The connector reads chunks ordered by primary key, emitting read (`op: "r"`) events into the same topic as the live `c`/`u`/`d` events. Around each chunk it writes open/close watermark signals; any log event seen inside that window for a key in the chunk wins, and the stale snapshot row is dropped before emission. That's the whole deduplication mechanism — no locks, no table-level freeze.

### What this changes downstream

- Your sink must treat `r` as an **upsert**, not "initial load only". Keyed topics plus last-write-wins makes this free; append-only consumers will double-count.
- The table needs a primary key, or set `surrogate-key` in the signal payload.
- Progress is stored in connector offsets, so a restart mid-backfill resumes at the last chunk rather than starting over.
- You can send `pause-snapshot` / `resume-snapshot` / `stop-snapshot` signals when the source database is under load.
- The signaling table must be visible to the connector (included in the capture list), since the signal arrives via the log. MySQL additionally supports a read-only variant driven by a Kafka signal topic.

Reach for this for backfills, newly added tables, and re-syncs after a bad transform. Reserve the blocking snapshot for the very first connector start.

## 05:03 - [Data Analytics] Year-over-Year on Daily Grain: Shift 364 Days, Not 365

`order_date - interval '1 year'` is the most common bug in a YoY dashboard, and it never throws an error.

A normal year is 365 days = 52 weeks + 1 day. So subtracting a calendar year lands you on **the previous weekday**. Every Monday in 2026 gets compared against a Sunday: Monday 2026-10-26 maps to Sunday 2025-10-26. If weekend volume runs 40% of a weekday — typical for B2B — every Monday prints as a fake +150% and every Sunday as a fake −60%. Worse, if the one-year span contains a Feb 29 the gap is 366 days and the shift is *two* weekdays: Wednesday 2023-03-01 → Friday 2024-03-01.

The fix is to shift by whole weeks:

```sql
with daily as (
  select order_date, sum(amount) as revenue
  from orders
  group by 1
)
select
  c.order_date,
  c.revenue,
  p.revenue as revenue_ly,
  round(100.0 * (c.revenue / nullif(p.revenue, 0) - 1), 1) as pct_yoy
from daily c
left join daily p
  on p.order_date = c.order_date - interval '364 days'  -- 52 weeks
where c.order_date >= date '2026-10-01';
```

364 days always preserves the weekday. The trade-off: it drifts off the calendar. Chain it five times and 2026-12-25 lands on 2021-12-31 — six days adrift, so Christmas-anchored seasonality no longer lines up. Use 364 for one-year lookbacks and day/week grain; for multi-year, align on ISO week (`extract(week ...)`, `extract(isoyear ...)`) or a retail 4-5-4 calendar. Fixed-date holidays never align either way, so flag them rather than explaining the spike every year.

Monthly grain has the mirror problem: unequal weekday counts. October 2026 has five Saturdays, October 2025 has four. For a weekday-driven metric that is a built-in ~3% headwind. Divide by business days, or count the weekdays explicitly, before calling it a trend:

```sql
-- revenue per business day, from the `daily` CTE above, grouped by month
sum(revenue)  filter (where extract(dow from order_date) between 1 and 5)
/ count(*)    filter (where extract(dow from order_date) between 1 and 5)
```

## 10:02 - [ML & AI] DBSCAN: `eps` Is in Raw Distance Units, Which Is the Whole Difficulty

k-means asks how many clusters. DBSCAN asks how close is close, and that question has units — which is why it so often returns one giant blob or labels 90% of your data as noise.

**The two parameters.** A point is a *core point* if at least `min_samples` points lie within `eps` of it (scikit-learn counts the point itself). Core points within `eps` chain into clusters; reachable non-core points join as borders; everything else gets label `-1`. Unlike k-means, not every point is assigned.

**Why unscaled features destroy it.** Two customers:

| | age | income |
|---|---|---|
| A | 30 | 52,000 |
| B | 58 | 52,400 |

Raw Euclidean distance: `sqrt(28² + 400²) = sqrt(784 + 160,000) ≈ 401.0`. A 28-year age gap moved the distance from 400 to 401 — 0.24%. The clustering is on income alone.

Standardize (age sd ≈ 12, income sd ≈ 20,000): `sqrt((28/12)² + (400/20000)²) = sqrt(5.44 + 0.0004) ≈ 2.33`. Now age dominates, correctly. **Always scale before DBSCAN**, and prefer `RobustScaler` when outliers are the thing you're hunting.

**Choosing the parameters.** Start with `min_samples ≈ 2 × n_features` (Sander et al., 1998; floor of `n_features + 1`). Then let the data pick `eps` via a k-distance plot — the knee is where points stop having close neighbors:

```python
from sklearn.neighbors import NearestNeighbors
from sklearn.preprocessing import StandardScaler
from sklearn.cluster import DBSCAN
import numpy as np

Xs = StandardScaler().fit_transform(X)
m = 2 * Xs.shape[1]                       # min_samples
d, _ = NearestNeighbors(n_neighbors=m).fit(Xs).kneighbors(Xs)
kdist = np.sort(d[:, m - 1])              # m-1 excludes self
# plot kdist; eps = y-value at the elbow

labels = DBSCAN(eps=0.5, min_samples=m).fit_predict(Xs)
print((labels == -1).mean())              # noise fraction — sanity-check this
```

**Two failure modes `eps` cannot fix.** Clusters at different densities (one `eps` can't serve both) and high dimensions (past ~10–20 features distances concentrate and every `eps` is wrong). For the first, use `sklearn.cluster.HDBSCAN` (1.3+), which drops `eps` for `min_cluster_size`. For the second, reduce with PCA first — and remember UMAP distorts density, so cluster on PCA output, not on the UMAP plot you made for humans.

## 15:05 - [Crypto & Business] Estimated Quarterly Taxes: The Safe Harbor That Caps Your Penalty No Matter What You Actually Owe

The first year of freelance or side income catches people because US income tax is **pay-as-you-go**. There is no "settle up in April" option — owing a large balance on time still triggers an underpayment penalty for the quarters you skipped.

**The safe harbor is the escape hatch.** Pay the *lesser* of:

- **90%** of this year's total tax, or
- **100%** of last year's total tax — **110%** if last year's AGI exceeded $150,000 ($75,000 married filing separately)

Hit either and the penalty is zero, however large the April balance.

**Worked example.** Last year: total tax $28,000, AGI $160,000. Safe harbor is 110% × $28,000 = **$30,800**, or $7,700 per quarter. This year your business triples and actual tax lands at $62,000. You still owe **no penalty** — the remaining $31,200 is simply due at filing. The prior-year route is powerful precisely because it ignores your growth.

Going the other way, if income is *falling*, the 90%-of-current-year route is cheaper: expect $18,000 of tax, pay $16,200 across four installments.

**Three mechanics people miss:**

1. **The quarters are not quarters.** Due dates are Apr 15, Jun 15, Sep 15, and Jan 15 — covering 3, 2, 3, and 4 months of income respectively.
2. **Withholding is treated as paid evenly all year; estimated payments count when made.** Discover a shortfall in November and a large Q4 estimated payment does *not* cure Q1–Q3. Increasing W-2 withholding (yours or a spouse's) retroactively does.
3. **Self-employment tax is the usual shortfall.** 15.3% on 92.35% of net profit (Social Security portion capped at the wage base, Medicare uncapped) *on top of* income tax. On $120,000 of net profit that is roughly $17,000 before a dollar of income tax.

The penalty itself is interest-like, not punitive: at a ~7% annual rate, being $5,000 short for one quarter costs about $88. Non-deductible, but survivable. For genuinely lumpy income — nothing in Q1, a large Q4 project — the **annualized income installment method** (Form 2210, Schedule AI) matches payments to when income actually arrived. Most states run parallel rules with their own thresholds.

## 19:03 - [PC Hardware] GPU Idle Power: Why a Second Monitor Costs You 30W and Kills Zero-RPM Mode

You add a cheap 1080p60 panel next to your 4K144 main display. Nothing about your workload changed, but idle board power jumps from ~15W to ~45W and the fans never stop spinning again. The GPU is fine. Its **memory clock is stuck at maximum** and will stay there until you reboot into a different display config.

### Why the driver refuses to downclock

Changing VRAM clock requires briefly halting memory traffic, so the driver can only do it inside a display's vertical blanking interval. With one monitor that is easy. With two monitors at different refresh rates, the blanking windows drift in and out of phase and there is no common gap wide enough — so the driver gives up and pins the card to its highest memory P-state. Same thing happens when total pixel bandwidth crosses an internal threshold, even at matched refresh.

The delta is not trivial. GDDR6/6X idles near 50–400 MHz and runs 10,000+ MHz effective at full tilt; on a 300W-class card that is a 25–40W difference, and on a 3090-class card with three displays it has been measured near 100W. Running 24/7, 30W is ~260 kWh/year — multiply by your own electricity rate to see whether it matters to you. It also defeats zero-RPM fan modes, because the card never drops below the fan-stop temperature.

### Diagnose it

```bash
nvidia-smi --query-gpu=clocks.mem,clocks.gr,power.draw,pstate \
           --format=csv -l 1
```

Sitting at an idle desktop, `pstate` should read `P8` and `clocks.mem` should be low. If you see `P0` and full memory clock with nothing running, this is your problem. On Windows, watch **GPU Memory Clock** in HWiNFO64. AMD cards show the same behavior, often alongside an elevated SoC/FCLK.

### Fixes, cheapest first

1. **Match refresh rates** across all displays. 144 + 144 downclocks; 144 + 60 frequently will not.
2. If you must mix, **increase the vertical blanking** on the odd display with Custom Resolution Utility (Windows) — a larger VBlank gives the driver the gap it needs. This is the standard fix and usually recovers the full idle state.
3. **Update the driver.** Both vendors have shipped real improvements here; it is worth re-testing before buying a different monitor.

Verify after each change with the same command — don't assume, measure.
