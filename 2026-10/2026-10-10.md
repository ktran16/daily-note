## 00:02 - [Data Engineering] Snowflake Streams: An Offset, Not a Queue — and the Staleness That Eats Your Changes

A Snowflake stream looks like a change queue, so people reason about it like Kafka. It isn't one. A stream stores **no data** — it is a bookmark: a table version offset plus a view that computes the delta between that offset and the table's current version.

```sql
create stream orders_stream on table raw.orders;

select metadata$action,      -- INSERT | DELETE
       metadata$isupdate,    -- TRUE when the pair is an UPDATE
       metadata$row_id,      -- stable row identity
       order_id, status, amount
from orders_stream;
```

Four consequences bite in production.

**1. Only DML advances the offset.** A `SELECT` from a stream is non-destructive — you can run it a hundred times and see the same rows. The offset moves when the stream is consumed inside a committed DML statement. So the read-then-merge pattern must be one statement, not two:

```sql
merge into mart.orders t
using orders_stream s on t.order_id = s.order_id
when matched and s.metadata$action = 'DELETE'
     and s.metadata$isupdate = 'FALSE' then delete
when matched then update set t.status = s.status, t.amount = s.amount
when not matched and s.metadata$action = 'INSERT' then insert ...;
```

If you `SELECT` into a temp table and merge from that, the offset still advances — and the rows you read before the commit are the rows you keep. Mixing both patterns double-processes.

**2. One stream, one consumer.** Consuming advances the offset for everybody. Two pipelines reading the same table need two streams.

**3. Standard streams show net effect, not history.** A row inserted and deleted between two consumptions appears in neither — the delta is empty. If you need every intermediate event, you need append-only streams (`append_only = true`) or event capture upstream.

**4. Staleness silently loses data.** The offset must stay inside the source table's time-travel window. Snowflake extends retention for unconsumed streams up to `MAX_DATA_EXTENSION_TIME_IN_DAYS` (default 14), but when that lapses the stream goes stale, unconsumed changes are gone, and you must recreate it — starting from "now."

```sql
show streams like 'orders_stream';  -- check STALE and STALE_AFTER
```

Monitor `STALE_AFTER`, and gate the consuming task so it only burns credits when there is work:

```sql
create task load_orders
  warehouse = etl_wh
  schedule = '5 minute'
  when system$stream_has_data('orders_stream')
as merge into mart.orders ...;
```

A paused task on a 1-day-retention table is a data-loss incident on a timer.

## 05:02 - [Data Analytics] Composite Index Column Order: Why Your Three-Column Index Is Only Doing One Column of Work

A B-tree index on `(a, b, c)` is one sorted list, ordered by `a`, then `b`, then `c` — like a phone book sorted by last name, then first, then middle. You can look someone up by last name, or last+first, but you cannot use the book to find everyone whose middle name is "Ray". Indexes obey the same **leftmost-prefix rule**: the engine seeks using a contiguous run of leading columns, and that run stops at the first column with a range predicate (`>`, `<`, `BETWEEN`, `LIKE 'x%'`) or the first column you skipped.

Columns past that point don't disappear — they just stop narrowing the scan, and become a filter applied to every row read.

```sql
-- 50M rows, 2,000 tenants, 18 months of history
SELECT event_id, occurred_at
FROM events
WHERE tenant_id = 42
  AND status = 'failed'
  AND occurred_at >= '2026-10-01'
ORDER BY occurred_at;
```

With `CREATE INDEX ON events (occurred_at, tenant_id, status)`, the leading column is the range, so the seek covers **all 2,000 tenants** for those 10 days — roughly 1.6M index entries read to return ~900 rows. Flip it:

```sql
CREATE INDEX events_tenant_status_time
  ON events (tenant_id, status, occurred_at);
```

Now both equalities seek into one slice and the range reads a contiguous ~900 entries. Same three columns, ~1,700x less index traffic — and because `occurred_at` is last *within* a pinned slice, the rows come out pre-sorted, so the `ORDER BY` costs nothing and the `Sort` node disappears.

**The rule:** equality columns first, then the one range-or-sort column last.

**How to verify,** not guess — run `EXPLAIN (ANALYZE, BUFFERS)` and read where each column landed:

- in `Index Cond:` → used for the seek
- in `Filter:` with `Rows Removed by Filter: 1598xxx` → read, then thrown away

That `Rows Removed` number is the cost of the wrong order, in rows.

Two caveats. Adding a column to `INCLUDE (...)` makes the index covering (index-only scan) but contributes nothing to the seek. And some engines — Postgres 18+, Oracle — can "skip scan" a low-cardinality leading column; treat that as a rescue, not a design.

## 10:03 - [ML & AI] KV Cache Arithmetic: Why Your Throughput Collapses at Long Context

You size a GPU by model weights, deploy, and watch concurrency fall off a cliff when users paste long documents. The weights never moved — the KV cache did. Every token already in a sequence keeps a key and value vector *per layer*, forever, so cache grows linearly in context and in batch size while weights stay fixed.

The formula, per token, per sequence:

```
bytes/token = 2 (K and V) × n_layers × n_kv_heads × head_dim × dtype_bytes
```

Note `n_kv_heads`, not `n_heads`. That is what grouped-query attention (GQA) shrinks.

```python
def kv_bytes_per_token(n_layers, n_kv_heads, head_dim, dtype_bytes=2):
    return 2 * n_layers * n_kv_heads * head_dim * dtype_bytes

# Llama-3-8B: 32 layers, 8 KV heads (32 query heads), head_dim 128, fp16
kv_bytes_per_token(32, 8, 128)      # 131_072 -> 128 KiB/token
# at 8k context: 128 KiB × 8192 = exactly 1 GiB per sequence
```

Run the counterfactual. With plain multi-head attention (32 KV heads) the same model costs 512 KiB/token — **4 GiB** per 8k sequence. GQA's 4× saving is not an accuracy footnote; it is the reason the model serves a batch at all.

Now budget an 80 GB H100. Weights at fp16 are ~16 GB, leaving ~60 GB for cache and activations: roughly **60 concurrent 8k sequences**. Scale the same math to Llama-3-70B (80 layers, 8 KV heads) and you get 320 KiB/token — **10 GiB for a single 32k-token request**. One long-context user can consume the budget of thirty short ones.

Three practical consequences:

- **Admission control beats a bigger GPU.** Cap `max_model_len` to what you actually serve. Reserving 128k when p99 is 6k prices every request at the worst case.
- **Quantize the cache, not just the weights.** fp8 KV halves cache with far less quality cost than fp8 weights — often the cheapest throughput you can buy.
- **Measure tokens-in-flight, not requests.** Requests-per-second hides the variable that fills memory; `sum(prompt + generated tokens)` across active sequences is the real utilization number, and the one to alert on.

## 15:02 - [Crypto & Business] Upgradeable Proxies: The Contract You Audited Isn't the One Running Tomorrow

Most DeFi protocols you interact with are not the contract holding your funds. They are a **proxy**: a thin contract that owns the storage and the balance, and forwards every call via `delegatecall` to a separate *implementation* address kept in one storage slot.

```solidity
fallback() external payable {
    address impl = _implementation();          // read from the EIP-1967 slot
    assembly {
        calldatacopy(0, 0, calldatasize())
        let ok := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
        returndatacopy(0, 0, returndatasize())
        if iszero(ok) { revert(0, returndatasize()) }
        return(0, returndatasize())
    }
}
```

`delegatecall` runs the implementation's bytecode *in the proxy's storage context*. So overwriting that one address swaps out every function in the protocol — withdraw, transfer, fee logic — while your deposit sits untouched in the proxy. The security of your position is the security of whoever can write that slot.

EIP-1967 fixes the slot at `keccak256("eip1967.proxy.implementation") - 1`, so you can check any address yourself:

```bash
cast storage 0xPROXY \
  0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc
```

A four-question diligence pass:

1. **Is it upgradeable?** Nonzero in that slot means yes. Many "audited" protocols are.
2. **Who upgrades it?** Read the admin slot (`0xb531...6103` under EIP-1967) or `owner()`. A plain EOA means one leaked key replaces the protocol. A 2-of-3 multisig held by three colleagues is barely stronger than one key.
3. **Is there a timelock?** If upgrades route through a timelock with, say, a 48-hour delay, the queued implementation is public and you can exit before it lands. No timelock means the swap is atomic with the theft.
4. **Does the audit cover the deployed implementation?** Reports name a commit hash. Compare it to the address in the slot today, not at launch.

Two recurring footguns: proxies use `initialize()` instead of constructors, and an implementation left uninitialized lets a stranger claim ownership — the 2017 Parity multisig freeze began exactly that way and locked roughly 500,000 ETH permanently. And because storage is shared, reordering state variables in a new implementation silently reinterprets existing slots.
