## 00:02 - [Data Engineering] Spark Broadcast Joins: Why Your 20 MB Dimension Still Shuffled

A broadcast hash join ships the small side to every executor and avoids a shuffle entirely. A sort-merge join shuffles *both* sides across the network. On a 2 TB fact joined to a tiny dimension, that's the difference between four minutes and forty. The frustrating part is that Spark often picks sort-merge for a table you know is small.

**The threshold is on an estimate, not the file.** `spark.sql.autoBroadcastJoinThreshold` defaults to 10 MB and is compared against the optimizer's `sizeInBytes` statistic. Two failure modes:

- **No stats** → Spark falls back to `spark.sql.defaultSizeInBytes` (`Long.MaxValue`), so nothing broadcasts. Fix with `ANALYZE TABLE dim_store COMPUTE STATISTICS`.
- **Compressed stats** → For Parquet, the estimate is on-disk size. A 40 MB on-disk table can deserialize to 400 MB of JVM rows, so raising the threshold to "just fit it" is how you OOM the driver.

Check what the planner decided before tuning anything:

```python
df = fact.join(dim, "store_id")
df.explain("formatted")   # look for BroadcastHashJoin vs SortMergeJoin
```

**Force it when you know better than the stats:**

```python
from pyspark.sql.functions import broadcast
fact.join(broadcast(dim), "store_id")
# SQL equivalent: SELECT /*+ BROADCAST(d) */ ... FROM fact f JOIN dim d ...
```

The hint bypasses the threshold but not the semantics. Join type restricts which side is broadcastable: a `LEFT OUTER` join can only broadcast the **right** side, `RIGHT OUTER` only the left, and `FULL OUTER` can't use a broadcast hash join at all. Hinting the wrong side is silently ignored — the plan still says `SortMergeJoin` and people assume the hint "didn't work."

**Let AQE catch the runtime case.** When a filter shrinks a side below the threshold at runtime, static planning never sees it. Adaptive Query Execution re-plans using actual shuffle map output sizes:

```
spark.sql.adaptive.enabled=true
spark.sql.adaptive.autoBroadcastJoinThreshold=32MB
```

Finally, `spark.sql.broadcastTimeout` (default 300s) kills the job if collecting the small side is slow — a timeout there usually means the "small" side isn't small, not that the timeout is too low.

## 05:03 - [Data Analytics] Guardrail Metrics: Why "p = 0.31, No Harm Detected" Is Not a Safety Check

Your primary metric wins. You check the guardrails — retention, latency, unsubscribes — see `p > 0.05` on all of them, and ship. That reasoning is backwards: absence of significance is not evidence of safety, and guardrails are almost never powered to prove it.

**The failure.** 7-day retention as a guardrail, baseline 40%, 20,000 users per arm:

```
treatment 39.5% vs control 40.0%
diff = -0.50 pp   SE = 0.0049
95% CI = [-1.46, +0.46] pp     z = -1.02, p = 0.307
```

"Not significant." But read the interval, not the p-value: the data are entirely consistent with a **1.4 pp retention loss** — a serious regression. The test was sized to detect the primary metric's expected lift, so on the guardrail it can only rule out harm larger than ~1.5 pp. You proved nothing about the range you actually care about.

**The fix: declare a non-inferiority margin δ before launch** — the largest harm you'd knowingly accept. Then the rule is one-sided and lives on the CI bound:

```python
from math import sqrt
from statistics import NormalDist

def cleared(p_c, p_t, n, delta, alpha=0.05):
    se = sqrt(p_c*(1-p_c)/n + p_t*(1-p_t)/n)
    lb = (p_t - p_c) - NormalDist().inv_cdf(1-alpha)*se
    return lb > -delta, lb

print(cleared(0.400, 0.395, 20_000, delta=0.010))
# (False, -0.0130)  -> cannot rule out a 1.0 pp loss
```

Lower bound −1.30 pp against a 1.0 pp margin: **not cleared.** Clearing it with 80% power needs ~29,700/arm; a tighter 0.5 pp margin needs ~118,700/arm. That number is the real cost of a guardrail, and it belongs in the test plan, not the readout.

**Two asymmetries worth internalizing:**

- Guardrails take **one-sided** tests. You care about harm, not about a surprise improvement.
- Do **not** apply a multiple-comparison correction to guardrails. Correction widens intervals, which makes a guardrail *easier* to pass — exactly the wrong direction. Bonferroni protects you from false winners on primary metrics; on safety checks it manufactures false reassurance.

If a guardrail is underpowered, say so explicitly: "retention could be down as much as 1.3 pp; we can't tell." That sentence is honest and actionable. "No significant change" is neither.

## 10:03 - [ML & AI] RoPE: Position as a Rotation, and Why It Breaks Past the Training Length

A transformer has no built-in notion of order — attention is a sum over a *set*. Early models added a learned or sinusoidal vector to each token embedding. Nearly every modern LLM instead uses **RoPE** (rotary position embedding), which *rotates* queries and keys rather than adding to them.

Split each `d`-dimensional head into `d/2` coordinate pairs. For pair `i` at position `m`, rotate by angle `m·θ_i`, where

```
θ_i = base^(-2i/d),    base = 10000 (typical)
```

Rotating `q` at position `m` and `k` at position `n` makes their dot product depend only on `m − n`:

```
q_m · k_n = f(q, k, m − n)
```

That is the whole trick: *absolute* rotations yield *relative* attention, with zero added parameters and no learned position table to run out of.

```python
import torch

def rope(x, base=10000.0):                           # x: (seq, dim), dim even
    seq, dim = x.shape
    pos = torch.arange(seq).unsqueeze(1)             # (seq, 1)
    inv = base ** (-torch.arange(0, dim, 2) / dim)   # θ_i, (dim/2,)
    ang = pos * inv
    cos, sin = ang.cos(), ang.sin()
    x1, x2 = x[:, 0::2], x[:, 1::2]
    return torch.stack([x1 * cos - x2 * sin,
                        x1 * sin + x2 * cos], dim=-1).flatten(1)
```

**The failure mode is wavelength.** The slowest pair has period `2π·base ≈ 62,800` tokens, so RoPE is mathematically defined arbitrarily far out. But the model only ever *saw* rotations up to its training length. Train at 8k and positions past it are angles the network was never calibrated on — quality collapses rather than degrading gracefully.

Every context-extension trick is just a change to those angles:

- **Linear interpolation (PI)** — divide positions by `s`; 8k→32k is `s=4`. Keeps everything in-range but compresses fine detail, hurting local precision.
- **NTK-aware** — raise the base instead (`10000 · s^(d/(d-2))`). Stretches low frequencies, leaves high ones nearly intact.
- **YaRN** — per-frequency: interpolate the slow pairs, leave fast pairs alone, plus an attention temperature correction. The usual choice for current long-context models.

Two practical consequences. A "128k context" label often means a base model trained at 4–8k with YaRN bolted on, so measure retrieval at *your* real length — advertised window ≠ usable window. And if you change `base` or scaling at inference time, every KV cache entry computed under the old angles is silently invalid.
