## 00:03 - [Data Engineering] dbt Indirect Selection: Why `--select my_model` Runs Tests About Other Models

You change one model, run `dbt build --select fct_orders`, and CI fails on a `relationships` test pointing at `dim_customers` — a model you never touched. That is **indirect selection**, and it is the default.

A test is a node with parents. `--select` picks models; dbt then decides which tests to pull in based on those models. The rule is set by `--indirect-selection`:

| Mode | A test runs if… |
|---|---|
| `eager` (default) | **any** parent is selected |
| `cautious` | **all** parents are selected |
| `buildable` | all parents are selected **or** are ancestors of something selected |
| `empty` | never — only tests selected by name |

A single-column `not_null` test has one parent, so every mode includes it. The divergence is multi-parent tests: `relationships`, and any singular test joining two models.

```yaml
# models/marts/schema.yml
models:
  - name: fct_orders
    columns:
      - name: customer_id
        tests:
          - relationships:
              to: ref('dim_customers')
              field: customer_id
```

Under `eager`, `dbt build --select fct_orders` runs that test — but `dim_customers` was not built in this invocation. It resolves to whatever sits in the target schema: a stale dev table, or nothing at all. The failure tells you about your environment, not your change.

```bash
# only tests whose every parent is in this run
dbt build --select fct_orders --indirect-selection=cautious

# project-wide (dbt 1.8+)
# dbt_project.yml
flags:
  indirect_selection: cautious
```

Also available as `DBT_INDIRECT_SELECTION`, and settable per-definition inside a YAML selector.

**Which to pick.** For Slim CI (`--select state:modified+ --defer`), `eager` is usually right: unselected parents resolve to prod via deferral, so the cross-model test is meaningful and catches real referential breakage. For local iteration against a half-built dev schema, `cautious` stops the noise. `buildable` is the middle ground on `--select model+`: downstream tests whose other parents are upstream ancestors still run.

The trap is assuming `--select` is a filter on what *you* named. It is a seed for graph traversal, and tests get pulled along.

## 05:02 - [Data Analytics] Nested Loop vs Hash Join: The Stale Row Estimate That Turns 20 Seconds Into 40 Minutes

Most "the query got slow and nothing changed" incidents are the planner flipping join algorithms. Knowing the three shapes tells you which number to go fix.

**Nested loop** — for each row of the outer side, probe the inner side (ideally via index). Cost scales as `outer_rows × probe_cost`. Fast when the outer side is genuinely tiny: 50 rows × a 4-page index probe is ~200 page reads. Catastrophic when "tiny" was a guess: 2M rows × 4 reads is 8M reads.

**Hash join** — build a hash table on the smaller side, stream the larger side past it. One pass each, no index needed. Fixed startup cost for the build, then near-linear. The right choice for warehouse-scale joins.

**Merge join** — sort both sides, walk them in lockstep. Wins when both inputs are *already* sorted (clustered key, index scan order); otherwise the sorts usually cost more than hashing.

The planner picks by estimated row count, and estimates come from statistics. The classic failure:

```sql
-- Postgres: find the actual vs estimated gap
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.order_id, c.region
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.placed_at >= '2026-10-01'
  AND o.status = 'shipped';
```

Read the outer node:

```
Nested Loop  (cost=0.43..8912 rows=1 width=18) (actual rows=1841022 loops=1)
  ->  Index Scan on orders  (rows=1) (actual rows=1841022 loops=1)
```

`rows=1` estimated, 1.8M actual — a 1,800,000× miss. The planner chose nested loop because it believed one row would come out. Two causes, both common:

1. **Correlated predicates.** `placed_at` and `status` are not independent; recent orders are mostly `shipped`. Postgres multiplies selectivities (0.04 × 0.02 = 0.0008) and underestimates badly. Fix: `CREATE STATISTICS ord_corr (dependencies) ON placed_at, status FROM orders; ANALYZE orders;`
2. **Stale stats after a bulk load.** Autovacuum hasn't caught up, so a fresh partition looks empty. Fix: `ANALYZE` in the load job, as the final step — not a nightly cron.

Verification habit: in any plan, find the node with the largest estimated-to-actual ratio. That node, not the slowest one, is the root cause — everything above it inherited a bad decision. Resist `SET enable_nestloop = off`; it hides the broken estimate and misroutes the next query too.

## 10:03 - [ML & AI] Transfer Learning: Freezing Is a Learning Rate of Zero

Fine-tuning a pretrained encoder has one dominant failure mode: a learning rate that is correct for a randomly initialized head destroys the pretrained features in the first few hundred steps. The pretrained weights sit in a good basin, and a 1e-3 step is large enough to leave it. The head, initialized at random, needs exactly that step size.

So the two parts want different learning rates. Freezing is just the extreme case — `requires_grad = False` is a learning rate of zero.

A ResNet-50 holds ~25.6M parameters; its ImageNet head (`fc`, 2048 → 1000) is ~2.05M of them. Swap in a 2048 → 5 head and you have 10,245 trainable parameters out of 23.5M — 0.04%. That is a linear probe, and it is the right first move: it trains in minutes, can barely overfit, and gives you the baseline any full fine-tune has to beat.

Discriminative learning rates, in PyTorch:

```python
backbone = [p for n, p in model.named_parameters() if not n.startswith("fc")]
opt = torch.optim.AdamW([
    {"params": backbone,              "lr": 1e-5},   # ~100x smaller
    {"params": model.fc.parameters(), "lr": 1e-3},
], weight_decay=1e-2)
```

A 10–100x ratio between backbone and head is the usual range. Pair it with warmup: the head's gradients are huge on step 1, and they backpropagate straight into the backbone.

Two quieter traps:

1. **BatchNorm keeps updating while frozen.** `requires_grad = False` stops gradients, not the running mean/variance buffers — those update on every forward pass in train mode. With small batches or a domain shift, the statistics drift and your "frozen" features change underneath you. Fix: call `model.backbone.eval()` inside the loop, after `model.train()`.
2. **Weight decay on the backbone** pulls pretrained weights toward zero even when the loss is already satisfied. Exclude norm layers and biases from decay.

Decision rule: under ~1k labeled examples per class, linear probe. Above that, or with a real domain shift (satellite, medical, non-English), unfreeze the top block or two at a small LR. Full fine-tuning is the last option, not the first.

## 15:05 - [Crypto & Business] Cohort Retention Curves: The Plateau Sets Your LTV, Not the Churn Rate

The standard LTV shortcut is `ARPU × gross margin ÷ monthly churn`. It assumes a constant hazard rate — that a month-1 user and a month-30 user are equally likely to leave. They never are, and the error runs in both directions.

**What a real curve looks like.** Take 1,000 signups and track the share still paying each month:

| Month | 1 | 2 | 3 | 4 | 6 | 9 | 12 | 24 |
|---|---|---|---|---|---|---|---|---|
| Retained | 60% | 45% | 38% | 34% | 31% | 30% | 30% | 27% |

Two regimes. Early months purge wrong-fit users who never activated. Then the curve *flattens* — the plateau is the fraction that found durable value, and it decays slowly (here ~1%/month relative).

**The right multiplier is area under the curve**, in "retention-months" per acquired signup:

- Months 1–12: 0.60+0.45+0.38+0.34+0.32+0.31+0.305+0.30+0.30+0.30+0.30+0.30 ≈ **4.2**
- Month 13 onward: plateau 0.30 decaying 1%/mo → 0.30 ÷ 0.01 = **30**
- Total ≈ **34.2 retention-months**

At $50 ARPU and 70% gross margin, that's 34.2 × $35 = **$1,197 LTV per signup**.

**Why this changes decisions.** Measure churn at month 12 and you see ~1%/month, implying a 100-month life and $3,500 LTV — nearly 3× too high, because it ignores the 70% who already left before the curve settled. Conversely, averaging blended churn across all cohorts (~8%/month here) understates the plateau's value.

Payback is the sharper lesson. At $400 CAC you need 11.4 retention-months. Year 1 delivers 4.2; each later year adds ~3.5. Payback lands around **month 37** — a three-year cash hole the naive formula hides entirely.

**The two levers are not equal.** Raising the plateau from 30% to 40% (activation, onboarding, better-qualified signups) adds 10 retention-months in the tail alone — about +33% LTV. Cutting late-stage decay from 1.0% to 0.8% adds ~7. Early activation work compounds across the whole tail.

**Diagnostic:** if your oldest cohort hasn't visibly flattened by month 9–12, you have no measured plateau. Don't extrapolate LTV from a curve still falling — model it as decaying to zero until a cohort proves otherwise.

## 19:03 - [PC Hardware] DDR5 Memory Training: Why a Healthy Build Takes 90 Seconds to POST

You finish a build, enable EXPO, hit save, and the screen stays black for a minute. Most people assume the board is dead and start pulling DIMMs. It usually is not dead — it is **training memory**, and knowing the difference saves you from disassembling a working PC.

DDR5 runs at data rates where trace-length differences of a few millimeters matter. At boot the memory controller sweeps per-bit read/write delays, drive strength, and termination values for every lane on every rank, then stores the winning values. That sweep is the long black screen. It is slowest on AM5 (first POST after a memory change routinely 60–120s, occasionally longer with 4 DIMMs or 96GB kits) and faster on Intel, which caches results aggressively by default.

**Rule of thumb:** after changing RAM, CPU, or any memory setting, give it **five minutes** before concluding anything. Reseating mid-training is how people turn a slow boot into a corrupted setting.

Two settings control the retraining:

| Setting | Effect |
|---|---|
| Memory Context Restore (AMD) | Reuses cached timings; cold boot drops from ~60s to ~10–15s |
| MRC Fast Boot (Intel) | Same idea, usually enabled by default on Z-series |
| Power Down Enable | Often required alongside MCR; small idle-latency cost |

MCR is tempting, but it has a real trade-off: a set of cached timings that was marginal gets reused forever, and some AM5 configurations see cold-boot hangs or random reboots with it on. Validate stability *with MCR off* first, then enable it and re-test. If instability appears only afterward, MCR is your suspect.

Three things worth knowing:

- **Training failure is self-correcting.** Boards retry ~3 times, then fall back to JEDEC defaults (4800/5600 MT/s). If you are suddenly at stock speed, training failed — it did not "forget" your profile.
- **Only cold boots retrain.** Validate with 10 full power-off cycles (switch off the PSU), not warm restarts.
- **Measure it.** On Linux, `systemd-analyze` reports a `firmware` time that includes training — a jump there after a BIOS update tells you training got slower, not that your OS regressed.
