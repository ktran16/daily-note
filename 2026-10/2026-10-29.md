## 00:02 - [Data Engineering] Semi-Additive Facts: The Measures You Must Never SUM Across Time

Most fact measures are **fully additive** — order revenue sums correctly across customer, product, and time. A `SUM` is always right. But a whole class of measures is **semi-additive**: additive across every dimension *except* time. Account balances, inventory on hand, headcount, open positions, policy counts in force. These are levels, not flows, and summing them over time multiplies your number by the number of periods.

The bug looks like a reasonable query:

```sql
-- WRONG: daily balance snapshots rolled up to a month
select
  account_id,
  date_trunc('month', snapshot_date) as month,
  sum(balance_usd) as balance        -- ~30x too large
from fct_account_balance_daily
group by 1, 2;
```

Nothing errors. The dashboard just reports $300M in deposits against a $10M book, and someone notices in a board meeting.

Summing across *accounts* is fine — within a single date:

```sql
select snapshot_date, sum(balance_usd) as total_assets
from fct_account_balance_daily
where snapshot_date = date '2026-10-28'
group by 1;
```

Across time you must **pick** a period value instead of adding: period-end (most common for balance sheets) or period-average (common for interest and capacity).

```sql
-- period-end balance per account per month
select account_id, date_trunc('month', snapshot_date) as month, balance_usd
from fct_account_balance_daily
qualify row_number() over (
  partition by account_id, date_trunc('month', snapshot_date)
  order by snapshot_date desc
) = 1;
```

Don't rely on every analyst remembering this. Encode it in the semantic layer. dbt's MetricFlow has a config for exactly this shape:

```yaml
measures:
  - name: account_balance
    agg: sum
    agg_time_dimension: snapshot_date
    non_additive_dimension:
      name: snapshot_date
      window_choice: max          # period-end; use `min` for period-start
      window_groupings:
        - account_id
```

Now the metric sums across accounts and takes the last snapshot across time, automatically, no matter who queries it.

A third category is **non-additive**: ratios, percentages, and distinct counts. These can't be aggregated at all — never average an average. Store the numerator and denominator as separate additive measures and divide after aggregation.

**Practical habit:** suffix the columns (`_balance`, `_on_hand`, `_level`) or tag them in the YAML, so "is this safe to SUM over time?" is answerable by looking.

## 05:02 - [Data Analytics] Stacked Area Charts: The Flat Series That Looks Like It Grew 80%

Only the **bottom** band of a stacked area chart has a flat baseline. Every band above it is drawn between two moving lines, so its visual shape is its own values *plus* all the noise underneath. Readers track the top edge, not the thickness.

```python
import math
import matplotlib.pyplot as plt

m = list(range(12))
a = [400 + 150 * math.sin(i / 1.5) for i in m]   # volatile
b = [300 + 80 * math.cos(i / 2) for i in m]      # volatile
c = [100.0] * 12                                 # perfectly flat

fig, ax = plt.subplots(1, 2, figsize=(11, 3.5))
ax[0].stackplot(m, a, b, c, labels=["A", "B", "C"])
ax[0].legend(loc="upper right"); ax[0].set_title("stacked: is C growing?")
ax[1].plot(m, c); ax[1].set_ylim(0, 150); ax[1].set_title("C alone")
plt.tight_layout(); plt.savefig("stacked.png")
```

Channel C is exactly 100 in all twelve months. But the baseline it sits on (`a + b`) runs 475 → 889 — a **414-unit swing, over 4× C's own height**. C's band visibly climbs, dips, and climbs again. Ask a reader for C's trend and you will hear "up maybe 80%, then a dip." The entire movement belongs to A.

Two effects compound it. The moving baseline is the main one. The second is the **sine illusion**: on a sloping band the eye judges the perpendicular gap between the edges, which is shorter than the true vertical height, so bands on steep slopes read as thinner than they are.

Match the chart to the question:

- **"What's the total?"** → stacked area is correct. That's the one question it answers well.
- **"How is each series doing?"** → small multiples: one panel per series, shared y-axis. Four small line charts beat one stack.
- **"What's the mix?"** → 100% stacked, labeled as share — but note every band then moves when any other series changes.
- **Must stack?** Order by volatility, steadiest at the bottom, cap it at ~5 bands, and give the flat baseline to the series under scrutiny.

**Guardrail:** pick any non-bottom series and ask whether you could state its month-over-month change within 10% from the picture alone. If not, the chart doesn't answer the question in its title.

## 10:03 - [ML & AI] SHAP: Additivity Lives in Log-Odds, and the Two Tree Estimators Disagree

SHAP's whole appeal is one exact identity: for every row,

```
base_value + Σ shap_values = the model's raw output
```

Not approximately — exactly, to floating point. That makes it the only check worth running first:

```python
import numpy as np, shap
ex = shap.TreeExplainer(model)          # default: feature_perturbation="tree_path_dependent"
sv = ex(X_test)
raw = model.predict(X_test, output_margin=True)   # xgboost; sklearn: decision_function
assert np.allclose(sv.base_values + sv.values.sum(axis=1), raw, atol=1e-4)
```

If that assertion fails, you have the wrong output space and every plot downstream is decoration.

**The log-odds trap.** For a binary classifier, `raw` is log-odds, so SHAP values are log-odds too. A churn row:

| term | log-odds |
|---|---|
| base_value | −2.20 |
| `late_payments` | +1.50 |
| `utilization` | +0.60 |
| `tenure_months` | −0.10 |
| **total** | **−0.20** |

σ(−2.20) = 0.10, σ(−0.20) = 0.45. So the row moved from a 10% to a 45% risk. But `late_payments` alone is *not* "+1.5 risk" and not even a fixed number of points: σ(−2.20 + 1.50) = 0.33, so applied first it's worth +23 points, while applied last — σ(−0.20) = 0.45 against σ(−1.70) = 0.15 for the same row without it — it's +30. Probabilities don't add. Report log-odds, or report the single before/after pair, never per-feature percentage points.

**The estimator you didn't choose.** `tree_path_dependent` is free (it reuses the stored node counts) but hands credit to features *correlated* with the ones the tree split on, including features the model never used. `interventional` breaks those correlations against a background sample, which is usually what you mean by "what did this feature do":

```python
ex = shap.TreeExplainer(model, data=shap.sample(X_train, 200),
                        feature_perturbation="interventional")
```

Cost is O(background × trees), hence the 100–200 row sample. The two modes routinely swap the top-3 ranking on correlated tabular data — so pick one deliberately and record it, because `mean(|SHAP|)` global importance inherits whichever you picked.

## 15:34 - [Crypto & Business] Bond Duration: The One Number That Explains Why Your "Safe" Fund Lost 13%

People buy a total bond market fund as the conservative sleeve, then watch it drop double digits in a year with zero defaults. Nothing broke. They just bought a rate bet without reading its size, and that size has a name: **duration**.

Duration is the weighted average time until you receive a bond's cash flows, in years — but its practical use is as a price-sensitivity multiplier:

```
% price change ≈ -duration × (change in yield)
```

A fund with 6.5-year duration, rates up 2.0 points: `-6.5 × 2.0 = -13%` in price. Add ~2% of coupon income and you land near -11% total return. That is the whole mechanism.

It works both directions. Same fund, yielding 4.6%, rates fall 1 point: `+6.5%` price `+ 4.6%` income ≈ **+11%**. Convexity makes the real move slightly better than linear in both cases — gains a bit bigger, losses a bit smaller — but the first-order estimate is close enough to size the risk.

**Where to look.** Every fund page lists "average effective duration." Rough tiers: short-term ~2, intermediate ~6, long-term ~15. A long Treasury fund is credit-risk-free and still loses ~30% on a 2-point rate move. "Safe" describes credit risk only; duration is the other, separate risk.

**Match duration to horizon.** Money needed in 3 years sitting in a duration-15 fund is a mismatch no credit rating fixes. An individual bond held to maturity locks its purchase yield — price swings in between don't matter if you don't sell. A fund never matures, but it rolls: roughly after its duration in years, the higher reinvestment income has offset the price hit. Duration is thus both the risk gauge *and* the rough recovery horizon.

**Use SEC yield, not distribution yield.** The 30-day SEC yield is forward-looking and net of expenses — the better estimate of what you'll earn. Distribution yield is trailing payouts, inflatable by old high coupons or return of capital.

One check before buying any bond fund: duration, SEC yield, credit quality. Three numbers, two minutes.

*Educational content only, not financial advice.*

## 19:04 - [PC Hardware] Multi-GPU for ML: The Interconnect Decides Whether a Second Card Helps

Adding a second GPU rarely doubles training throughput, because data-parallel training spends time on **gradient all-reduce** that single-GPU training doesn't. Per optimizer step, ring all-reduce moves roughly:

```
bytes ≈ 2 × (N-1)/N × params × bytes_per_param
```

A 1B-parameter model in fp16 on two GPUs: 2 × 0.5 × 1e9 × 2 = **2 GB per step**. Over PCIe 4.0 x16 (~25 GB/s real, not the 32 GB/s theoretical) that's ~80 ms of sync. If the compute step is 120 ms, you've turned a 2× into roughly 1.5×.

Three hardware facts decide how bad this gets:

**Slot width is usually halved.** Consumer boards split the CPU's 16 lanes into x8/x8 when the second slot is populated, so each card gets ~12.5 GB/s. A third card typically lands on a chipset slot at x4 — now sharing one x4 uplink with your NVMe drives. Check actual negotiated width, not the slot's physical size:

```bash
nvidia-smi --query-gpu=pcie.link.gen.current,pcie.link.width.current --format=csv
nvidia-smi topo -m          # PIX/PXB/NODE/SYS — SYS means it crosses sockets
```

**Peer-to-peer is not universal.** `SYS` paths and most GeForce cards route transfers through host memory instead of card-to-card, which doubles traffic and adds latency. NVLink exists only on specific parts — RTX 3090 (~112 GB/s bidirectional), data-center A100/H100 (600–900 GB/s). The 4090 and 5090 dropped it entirely. Verify before you plan around it:

```bash
# from CUDA samples
./p2pBandwidthLatencyTest
```

**Mitigations beat hardware here.** Gradient accumulation raises compute per sync, bf16/fp16 gradient compression halves the bytes, and sharded optimizers (ZeRO/FSDP) trade more communication for less memory — the wrong choice on x4 slots.

Practical rule: for a two-card workstation, one GPU with more VRAM usually beats two smaller ones unless your model genuinely won't fit. Buy the second card when VRAM capacity is the wall, not when you want speed.
