# Daily Notes - 2026-10-29

## 00:02 - [Data Engineering] Semi-Additive Facts: The Measures You Must Never SUM Across Time

Most fact measures are **fully additive** — order revenue sums correctly across customer, product, and time. A `SUM` is always right. But a whole class of measures is **semi-additive**: additive across every dimension *except* time. Account balances, inventory on hand, headcount, open positions, policy counts in force. These are levels, not flows, and summing them over time multiplies your number by the number of periods.

The bug looks like a reasonable query:

```sql
-- WRONG: daily balance snapshots rolled up to a month
select
  account_id,
  date_trunc('month', snapshot_date) as month,
  sum(balance_usd) as balance        -- ~30x too large
from fct_account_balance_daily
group by 1, 2;
```

Nothing errors. The dashboard just reports $300M in deposits against a $10M book, and someone notices in a board meeting.

Summing across *accounts* is fine — within a single date:

```sql
select snapshot_date, sum(balance_usd) as total_assets
from fct_account_balance_daily
where snapshot_date = date '2026-10-28'
group by 1;
```

Across time you must **pick** a period value instead of adding: period-end (most common for balance sheets) or period-average (common for interest and capacity).

```sql
-- period-end balance per account per month
select account_id, date_trunc('month', snapshot_date) as month, balance_usd
from fct_account_balance_daily
qualify row_number() over (
  partition by account_id, date_trunc('month', snapshot_date)
  order by snapshot_date desc
) = 1;
```

Don't rely on every analyst remembering this. Encode it in the semantic layer. dbt's MetricFlow has a config for exactly this shape:

```yaml
measures:
  - name: account_balance
    agg: sum
    agg_time_dimension: snapshot_date
    non_additive_dimension:
      name: snapshot_date
      window_choice: max          # period-end; use `min` for period-start
      window_groupings:
        - account_id
```

Now the metric sums across accounts and takes the last snapshot across time, automatically, no matter who queries it.

A third category is **non-additive**: ratios, percentages, and distinct counts. These can't be aggregated at all — never average an average. Store the numerator and denominator as separate additive measures and divide after aggregation.

**Practical habit:** suffix the columns (`_balance`, `_on_hand`, `_level`) or tag them in the YAML, so "is this safe to SUM over time?" is answerable by looking.
