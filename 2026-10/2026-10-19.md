## 00:03 - [Data Engineering] Kafka Log Compaction: Tombstones, the Active Segment, and the Key That Came Back

Retention by time throws away old records. Compaction throws away *superseded* records: for every key, the log keeps at least the latest value. That makes a topic a replayable table — the backbone of Debezium CDC topics, Kafka Streams changelogs, and `__consumer_offsets`.

```bash
kafka-configs.sh --bootstrap-server localhost:9092 --alter \
  --entity-type topics --entity-name customers.public.orders \
  --add-config cleanup.policy=compact,min.cleanable.dirty.ratio=0.1,segment.ms=600000,delete.retention.ms=86400000,max.compaction.lag.ms=604800000
```

**Deletes are tombstones.** A record with a non-null key and a `null` value marks the key deleted. Consumers must handle it explicitly — a sink that treats `null` as "no change" will never delete the row:

```python
for msg in consumer:
    if msg.value is None:          # tombstone
        table.delete(key=msg.key)
    else:
        table.upsert(key=msg.key, value=deserialize(msg.value))
```

Note the corollary: **null-key records are illegal on a compacted topic.** The broker rejects them (`InvalidRecordException`) because there is no key to compact on.

**Why compaction looks broken.** Three defaults catch everyone:

| Config | Default | Effect when you forget it |
|---|---|---|
| active segment | n/a | The segment currently being written is *never* compacted |
| `min.cleanable.dirty.ratio` | `0.5` | Cleaner waits until half the log is duplicate bytes |
| `min.compaction.lag.ms` | `0` | Fine, but `max.compaction.lag.ms` is effectively infinite |

On a low-throughput topic the active segment may not roll for days, so you keep reading duplicates and conclude compaction is off. Lower `segment.ms`, not the ratio, first.

**The key that came back.** Tombstones are themselves deleted after `delete.retention.ms` (default 24h). A consumer that is down — or a new sink bootstrapping from offset 0 — longer than that window never sees the tombstone. If it holds the pre-delete value in a state store or target table, the row resurrects and silently drifts forever. Raise `delete.retention.ms` to comfortably exceed your worst-case consumer outage, and treat a full reload as the only safe recovery past it.

For windowed changelogs use `cleanup.policy=compact,delete`: latest value per key, *and* drop anything older than `retention.ms`. Compaction alone bounds the log by cardinality, which for a high-cardinality key space is not a bound at all.
