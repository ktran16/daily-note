## 00:03 - [Data Engineering] Kafka Log Compaction: Tombstones, the Active Segment, and the Key That Came Back

Retention by time throws away old records. Compaction throws away *superseded* records: for every key, the log keeps at least the latest value. That makes a topic a replayable table — the backbone of Debezium CDC topics, Kafka Streams changelogs, and `__consumer_offsets`.

```bash
kafka-configs.sh --bootstrap-server localhost:9092 --alter \
  --entity-type topics --entity-name customers.public.orders \
  --add-config cleanup.policy=compact,min.cleanable.dirty.ratio=0.1,segment.ms=600000,delete.retention.ms=86400000,max.compaction.lag.ms=604800000
```

**Deletes are tombstones.** A record with a non-null key and a `null` value marks the key deleted. Consumers must handle it explicitly — a sink that treats `null` as "no change" will never delete the row:

```python
for msg in consumer:
    if msg.value is None:          # tombstone
        table.delete(key=msg.key)
    else:
        table.upsert(key=msg.key, value=deserialize(msg.value))
```

Note the corollary: **null-key records are illegal on a compacted topic.** The broker rejects them (`InvalidRecordException`) because there is no key to compact on.

**Why compaction looks broken.** Three defaults catch everyone:

| Config | Default | Effect when you forget it |
|---|---|---|
| active segment | n/a | The segment currently being written is *never* compacted |
| `min.cleanable.dirty.ratio` | `0.5` | Cleaner waits until half the log is duplicate bytes |
| `min.compaction.lag.ms` | `0` | Fine, but `max.compaction.lag.ms` is effectively infinite |

On a low-throughput topic the active segment may not roll for days, so you keep reading duplicates and conclude compaction is off. Lower `segment.ms`, not the ratio, first.

**The key that came back.** Tombstones are themselves deleted after `delete.retention.ms` (default 24h). A consumer that is down — or a new sink bootstrapping from offset 0 — longer than that window never sees the tombstone. If it holds the pre-delete value in a state store or target table, the row resurrects and silently drifts forever. Raise `delete.retention.ms` to comfortably exceed your worst-case consumer outage, and treat a full reload as the only safe recovery past it.

For windowed changelogs use `cleanup.policy=compact,delete`: latest value per key, *and* drop anything older than `retention.ms`. Compaction alone bounds the log by cardinality, which for a high-cardinality key space is not a bound at all.

## 05:04 - [Data Analytics] K-Means Segmentation: Your Three Features Are One Feature Wearing a Disguise

You cluster customers on recency, frequency, and monetary value, get three tidy segments, and name them. But k-means minimizes squared Euclidean distance in *raw units*. Spend runs 0–10,000 dollars; order count runs 1–40. The distance metric never sees the second one.

A 1,200-customer synthetic set with three genuine segments (loyal/frequent, rare/big-ticket, lapsed):

```python
import numpy as np, pandas as pd
from sklearn.cluster import KMeans
from sklearn.preprocessing import StandardScaler
from sklearn.metrics import adjusted_rand_score

X = df[["recency_days", "frequency", "monetary"]].values
v = X.var(axis=0); print(v / v.sum())
# recency 0.43%   frequency 0.00%   monetary 99.57%

raw = KMeans(3, n_init=10, random_state=0).fit_predict(X)
```

Monetary carries 99.57% of total variance, so it decides essentially every assignment. Measure how far the centroids actually separate, in standard deviations per feature:

| feature | unscaled | log + scaled |
|---|---|---|
| recency_days | 0.60σ | 1.89σ |
| frequency | 0.50σ | 1.78σ |
| monetary | 3.64σ | 1.18σ |

The unscaled "segments" are a spend tercile with two decorative columns. Against the known ground truth, adjusted Rand index is **0.13** — barely better than chance.

**Fix one: standardize.** `StandardScaler` puts every feature at unit variance. ARI climbs to 0.36.

**Fix two: log first.** Standardizing does not fix *skew*. Monetary and frequency are gamma-shaped with long right tails, so a handful of whales sit 6σ out and still pull centroids toward themselves. Compress the tail before scaling:

```python
df2 = df.assign(monetary=np.log1p(df.monetary),
                frequency=np.log1p(df.frequency))
lab = KMeans(3, n_init=10, random_state=0).fit_predict(
          StandardScaler().fit_transform(df2.values))
```

ARI: **0.58**. Same algorithm, same k, same seed — four times the signal from two preprocessing lines.

**Practical rules.** Print the variance share before you cluster; anything above ~80% on one feature means you have a univariate split. Always `log1p` monetary and count columns. Fit the scaler on training data only, or next quarter's refresh silently redefines every segment boundary.

## 10:06 - [ML & AI] Gradient Accumulation: The Divide-by-k Everyone Gets Wrong Twice

You want batch size 32 but only 8 sequences fit in VRAM. Gradient accumulation runs 4 microbatches, lets gradients pile up in `.grad`, then steps once. The intent is that this is numerically identical to a true batch of 32. It usually isn't, for two separate reasons.

**Bug 1: the missing division.** `nn.CrossEntropyLoss()` defaults to `reduction='mean'`, so each microbatch loss is already an average over its own samples. Backward *accumulates* — `.grad` sums across the four calls. You end up with the sum of four means, i.e. **4× the gradient** of a real batch-32 step. Your effective learning rate is silently 4× what you set, and the run diverges or plateaus high.

```python
K = 4
opt.zero_grad()
for i, mb in enumerate(microbatches):
    loss = criterion(model(mb.x), mb.y)
    (loss / K).backward()          # <- the fix
opt.step()
```

**Bug 2: the one that survives the fix.** Dividing by `K` assumes every microbatch carries equal weight. With variable-length sequences it doesn't. Say token counts are 100, 100, 100, 1000. A true batch-32 mean weights each *token* equally: each of the 1000 tokens gets 1/1300. The divide-by-4 version gives the long microbatch 1/4 of the gradient spread over 1000 tokens — **1/4000 per token**, roughly a third of its proper weight — while each short-microbatch token gets 1/400, over 3× too much. Your gradient is now a different objective than batch-32 optimizes.

The fix is to normalize by the accumulation window's real token count:

```python
import torch.nn.functional as F

opt.zero_grad()
total = sum(mb.n_tokens for mb in microbatches)   # count the window first
for mb in microbatches:
    logits = model(mb.x)
    loss = F.cross_entropy(logits.view(-1, V), mb.y.view(-1),
                           ignore_index=-100, reduction='sum')
    (loss / total).backward()
opt.step()
```

**Why it matters.** This is the bug behind "my 8×A100 run and my 1×A100 run with accumulation give different curves." The gradient *norm* also differs, so gradient clipping kicks in at different points, compounding the divergence.

**Checks.** Compare one accumulated step against one true large-batch step on fixed data — gradients should match to ~1e-6. And log `grad_norm` before clipping: if it scales with `K`, you have bug 1.
