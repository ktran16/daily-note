## 00:03 - [Data Engineering] dbt Materialized Views and Dynamic Tables: The Materialization That Manages DDL, Not Data

Every other dbt materialization is a **data** operation: dbt issues SQL that moves rows. `materialized_view` is a **DDL** operation — dbt creates and alters an object, then the warehouse refreshes it on its own schedule. `dbt run` on a healthy materialized view moves zero rows.

That inversion is the whole lesson, and it breaks habits:

```sql
-- models/marts/fct_orders_mv.sql
{{ config(
    materialized='materialized_view',
    on_configuration_change='apply',
    snowflake_warehouse='TRANSFORM_XS',
    target_lag='15 minutes'
) }}

select
    order_date,
    store_id,
    count(*)        as orders,
    sum(net_amount) as revenue
from {{ ref('stg_orders') }}
group by 1, 2
```

No `{% if is_incremental() %}`. There is no incremental block to write, because there is no dbt-side run to filter. Freshness is `target_lag` (Snowflake dynamic tables) or `max_staleness`/auto-refresh (BigQuery) — a config, not SQL.

**`on_configuration_change` is the parameter people miss.** When you edit `target_lag` or a cluster key, dbt compares the project config against the live object and acts:

| Value | Behaviour on drift |
|---|---|
| `apply` (default) | Issue `ALTER` where the platform allows it; full-refresh where it does not |
| `continue` | Log a warning, leave the object alone — silent drift |
| `fail` | Error the run |

Default `continue` on older adapters is how teams end up with a production object whose definition no longer matches the repo. Set `apply`, or `fail` in CI.

Two constraints decide whether this fits at all:

- **SQL support is narrow.** BigQuery materialized views reject outer joins, window functions, `UNION ALL`, and most non-additive aggregates. Snowflake dynamic tables are far more permissive. Porting a model between the two is not mechanical.
- **Changing the `select` requires a rebuild.** You cannot `ALTER` a view's query, so a logic change is a drop-and-create — a full scan of the upstream table, charged at refresh time.

Reach for it when latency matters more than control and the aggregate is cheap to maintain. Stay on `incremental` when you need backfill windows, late-arriving-data lookbacks, or deduplication — anything requiring you to decide *which* rows get processed.

## 05:03 - [Data Analytics] Novelty Effects: The +12% Lift That Decays to +1.5% by Week Two

A redesigned feed ships to 50% of users. Day one: clicks per user up 12%, p < 0.001. You call it and roll out. Six weeks later the metric is flat against the pre-launch baseline.

Nothing was wrong with the statistics. The effect was real — it just wasn't the effect you shipped. **Novelty**: returning users notice something changed and poke at it. **Primacy**: the opposite — users fluent in the old UI get slower before they adapt, so the true win is understated early. Both mean the first days measure *reaction to change*, not steady-state value.

**Calendar date won't show you this.** On calendar day 7 your treatment group is a blend of users on their 7th day of exposure and users enrolled this morning on their 1st. The signal averages out. Index on *days since first exposure* instead:

```sql
WITH exposure AS (
  SELECT user_id, variant, MIN(event_date) AS first_exposed
  FROM experiment_assignment
  WHERE experiment = 'new_feed_v2'
  GROUP BY 1, 2
),
-- Only users with a full 14-day observation window, or the
-- tenure_day = 13 bucket contains nothing but early enrollees.
eligible AS (
  SELECT * FROM exposure
  WHERE first_exposed <= DATE_SUB(CURRENT_DATE(), INTERVAL 14 DAY)
),
per_user_day AS (
  SELECT e.variant,
         DATE_DIFF(a.event_date, e.first_exposed, DAY) AS tenure_day,
         e.user_id,
         COUNTIF(a.event = 'click') AS clicks
  FROM eligible e
  JOIN activity a USING (user_id)
  WHERE a.event_date BETWEEN e.first_exposed
                         AND DATE_ADD(e.first_exposed, INTERVAL 13 DAY)
  GROUP BY 1, 2, 3
)
SELECT tenure_day,
       COUNT(DISTINCT user_id) AS users,
       SAFE_DIVIDE(AVG(IF(variant = 'treatment', clicks, NULL)),
                   AVG(IF(variant = 'control',   clicks, NULL))) - 1 AS lift
FROM per_user_day
GROUP BY 1
ORDER BY 1;
```

Read the shape, not the average. A lift of +12% at `tenure_day` 0–2 settling to +1.5% at 7–13 is novelty; the ship decision is the +1.5%. A rise from −3% to +6% is primacy — shipping on the early read would have killed a winner.

Two practical notes. Users who enrolled *after* launch have no prior experience to react to, so restricting to them gives an unconfounded steady-state estimate — just a smaller one. And tenure slicing splits your sample across 14 buckets, so each is underpowered relative to the pooled test: plan the extra runtime up front rather than discovering mid-test that the tail is noise.

## 10:02 - [ML & AI] SVM with an RBF Kernel: `C` and `gamma` Are Measured in Your Feature Units

The RBF kernel is a similarity based on raw distance:

```
K(x, x') = exp(-gamma * ||x - x'||^2)
```

That `||x - x'||^2` is computed in whatever units your columns happen to be in. Give an SVM `income` (~50,000) and `age` (~40) unscaled, and a 1-year age gap contributes `1` to the squared distance while a $1,000 income gap contributes `1,000,000`. The kernel sees exactly one feature. No value of `gamma` fixes this — it is a single scalar multiplying a distance that is already dominated. **Scaling is not a tuning step for an SVM; it is a correctness step.**

```python
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.svm import SVC

pipe = make_pipeline(StandardScaler(), SVC(kernel="rbf"))  # scaler inside the CV fold
```

**What the two knobs actually do.** `gamma` sets the *reach* of one training point: it is `1/(2*sigma^2)`, so high `gamma` means each support vector only influences its immediate neighborhood — the boundary grows islands around individual points. Low `gamma` makes the decision surface nearly linear. `C` sets the price of a margin violation: low `C` buys a wide margin by tolerating misclassified training rows, high `C` insists on fitting them.

They are not independent. High `gamma` *and* high `C` is the memorization corner of the grid — perfect training accuracy, chance-level test accuracy. Tune them jointly on a log grid (`C` and `gamma` each over `1e-3 … 1e3`), never one at a time.

sklearn's default `gamma="scale"` is `1 / (n_features * X.var())`, which adapts to overall variance but not to *per-column* variance — it does not rescue unscaled data.

**Two production traps.**

- `SVC` training is roughly O(n²)–O(n³) in rows. Past ~50k rows, switch to `LinearSVC`, or approximate the kernel with `Nystroem` + `SGDClassifier`.
- `probability=True` does not expose the model's internal scores. It runs 5-fold Platt scaling — a second, much slower fit — and its `predict_proba` can disagree with the sign of `decision_function`. If you only need ranking or a tuned threshold, use `decision_function` and skip the refit entirely.

## 15:04 - [Crypto & Business] Asset Location: The Same Portfolio, $3K/Year Apart

Asset *allocation* is what you hold. Asset *location* is which account holds it. Most people optimize the first and ignore the second, leaving a few thousand dollars a year on the table without changing their risk at all.

**Why it matters.** Different assets throw off different *kinds* of income, and accounts tax those kinds differently:

| Income type | Taxable account | Tax-deferred (401k/IRA) | Roth |
|---|---|---|---|
| Bond interest, REIT dividends | Ordinary rates (up to 37% + state) | Deferred | Never taxed |
| Qualified stock dividends | 0/15/20% | Deferred, then **ordinary** on withdrawal | Never taxed |
| Realized capital gains | 0/15/20%, deferrable by not selling | Deferred, then ordinary | Never taxed |

**Worked example.** $600K at 60/40, split $300K taxable / $300K traditional IRA. Marginal rate 24% federal + 5% state = 29%.

*Bad location* — bonds in taxable: $240K × 4.5% yield = $10,800 interest × 29% = **$3,132/yr** in tax. Plus $60K of equities in taxable paying $780 of dividends × 15% = $117. Total drag: **$3,249**.

*Better location* — bonds in the IRA, equities in taxable: IRA interest is deferred ($0 now). Taxable $300K equities × 1.3% qualified dividend = $3,900 × 15% = **$585**. Total drag: **$585**.

Same allocation, same accounts, ~$2,660/yr saved. Compounded at 7% for 25 years that's roughly $168K.

**The usual hierarchy**
- **Taxable:** broad equity index funds — low turnover, qualified dividends, harvestable losses, step-up in basis at death, and the foreign tax credit on international funds (that credit is *forfeited* inside an IRA).
- **Tax-deferred:** bonds, REITs, high-yield, high-turnover active funds — anything generating ordinary income.
- **Roth:** your highest-expected-return holdings, since that growth is never taxed again.

**Caveats.** This only matters once you hold meaningful balances in two or more account types. Don't buy a worse fund to chase location. And in a low bracket with a small bond sleeve, the gain may be under $200/yr — not worth the complexity. Rebalancing inside tax-advantaged accounts is free of capital gains, which is a second reason to keep the moving parts there.

*Educational content, not investment advice.*

## 19:03 - [PC Hardware] SSD Endurance: TBW, Write Amplification, and the SMART Fields Worth Watching

Drives are rated in **TBW** (terabytes written) or **DWPD** (drive writes per day). Convert before you worry:

```
GB/day budget = TBW * 1000 / (365 * warranty_years)
```

A 2 TB consumer drive rated 1200 TBW over 5 years allows ~660 GB/day. A typical desktop writes 10–30 GB/day; a busy dev box with Docker builds and game installs might hit 100 GB. At 30 GB/day that drive lasts ~110 years on paper. **Endurance is almost never what kills a consumer SSD — sudden controller or firmware failure is.**

Check actual wear rather than guessing:

```bash
sudo smartctl -a /dev/nvme0      # NVMe, needs smartmontools
sudo nvme smart-log /dev/nvme0   # nvme-cli, same data
sudo smartctl -A /dev/sda        # SATA
```

| Field | Means | Act when |
|---|---|---|
| `Percentage Used` (NVMe) | Vendor estimate of rated endurance consumed | >80%: plan replacement. It can read 120% and still work fine |
| `Data Units Written` | Multiply by 512,000 to get bytes written by the host | Use it to compute your real GB/day |
| `Available Spare` | Reserve blocks left | <10% raises a critical warning — replace |
| `Media and Data Integrity Errors` | Uncorrectable ECC events | Any nonzero value: back up immediately |
| `Reallocated_Sector_Ct` (SATA) | Remapped sectors | Nonzero *and growing* means replace |

**Write amplification (WAF)** is NAND writes divided by host writes. With healthy free space it sits around 1.1–3×. On a drive kept 98% full doing small random writes it can exceed 10×, because garbage collection must relocate valid pages just to erase one block. That is the one scenario where endurance math stops being comfortable.

So: leave 10–20% of the drive free (or simply leave that much unpartitioned as overprovisioning), and confirm TRIM actually runs — `systemctl status fstrim.timer`, or `sudo fstrim -av` to check manually. Windows does this via Optimize Drives weekly.

None of this replaces backups. A drive at 40% rated life can die at 09:00 with no warning in any SMART field.
