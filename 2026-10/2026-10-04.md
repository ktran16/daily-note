## 00:02 - [Data Engineering] Parquet Row Groups: Why Predicate Pushdown Skips Nothing

Parquet is columnar, so people assume `WHERE event_date = '2026-10-01'` reads only the matching rows. It doesn't. The unit of skipping is the **row group** — typically ~128 MB of rows — and the engine decides whether to read one by comparing your predicate against the min/max statistics stored in the footer.

The structure: file → row groups → one column chunk per column → pages. The footer carries min, max, and null count for every column chunk, and often per page too.

**The failure mode is unsorted data.** If rows arrive interleaved, every row group's `event_date` range spans the full window, every min/max overlaps your filter, and the reader opens all of them. The file is columnar, so you only read one column — but you read all of it.

Check before you guess:

```python
import pyarrow.parquet as pq

f = pq.ParquetFile("events.parquet")
for i in range(f.metadata.num_row_groups):
    s = f.metadata.row_group(i).column(2).statistics  # event_date
    print(i, s.min, s.max, f.metadata.row_group(i).num_rows)
```

Ranges that all look like `2026-09-01 → 2026-10-04` mean zero skipping is possible.

**The fix is sorting on write**, so ranges become disjoint:

```python
pq.write_table(
    table.sort_by([("event_date", "ascending"), ("tenant_id", "ascending")]),
    "events.parquet",
    row_group_size=1_000_000,     # rows, not bytes — tune to ~128MB
    compression="zstd",
)
```

Sort order is a budget: the first column prunes well, the second only within each first-column value, the third essentially not at all. Pick the two columns your queries actually filter on.

**Min/max is useless for high-cardinality equality** — `user_id = 'u_8812'` falls inside nearly every range. That's what bloom filters are for:

```python
pq.write_table(t, "events.parquet",
               write_bloom_filter=["user_id"])
```

Spark equivalent: `parquet.bloom.filter.enabled#user_id = true`.

**Row group sizing trade-off:** small groups give finer skipping but multiply footer metadata and turn one sequential read into many random ones on object storage; huge groups prune coarsely and inflate reader memory. 128 MB is the default for a reason — change it only with measurements.
