## 00:02 - [Data Engineering] Parquet Row Groups: Why Predicate Pushdown Skips Nothing

Parquet is columnar, so people assume `WHERE event_date = '2026-10-01'` reads only the matching rows. It doesn't. The unit of skipping is the **row group** — typically ~128 MB of rows — and the engine decides whether to read one by comparing your predicate against the min/max statistics stored in the footer.

The structure: file → row groups → one column chunk per column → pages. The footer carries min, max, and null count for every column chunk, and often per page too.

**The failure mode is unsorted data.** If rows arrive interleaved, every row group's `event_date` range spans the full window, every min/max overlaps your filter, and the reader opens all of them. The file is columnar, so you only read one column — but you read all of it.

Check before you guess:

```python
import pyarrow.parquet as pq

f = pq.ParquetFile("events.parquet")
for i in range(f.metadata.num_row_groups):
    s = f.metadata.row_group(i).column(2).statistics  # event_date
    print(i, s.min, s.max, f.metadata.row_group(i).num_rows)
```

Ranges that all look like `2026-09-01 → 2026-10-04` mean zero skipping is possible.

**The fix is sorting on write**, so ranges become disjoint:

```python
pq.write_table(
    table.sort_by([("event_date", "ascending"), ("tenant_id", "ascending")]),
    "events.parquet",
    row_group_size=1_000_000,     # rows, not bytes — tune to ~128MB
    compression="zstd",
)
```

Sort order is a budget: the first column prunes well, the second only within each first-column value, the third essentially not at all. Pick the two columns your queries actually filter on.

**Min/max is useless for high-cardinality equality** — `user_id = 'u_8812'` falls inside nearly every range. That's what bloom filters are for:

```python
pq.write_table(t, "events.parquet",
               write_bloom_filter=["user_id"])
```

Spark equivalent: `parquet.bloom.filter.enabled#user_id = true`.

**Row group sizing trade-off:** small groups give finer skipping but multiply footer metadata and turn one sequential read into many random ones on object storage; huge groups prune coarsely and inflate reader memory. 128 MB is the default for a reason — change it only with measurements.

## 05:03 - [Data Analytics] Distinct Counts Don't Merge: Why DAU Can't Roll Up to MAU

Sums roll up. Counts of *distinct things* do not. This is the bug behind most wrong MAU numbers: someone builds a `daily_active_users` table, then aggregates it to a month.

```sql
-- WRONG: counts each user once per day they appeared
SELECT SUM(dau) AS mau FROM daily_active_users
WHERE day BETWEEN '2026-09-01' AND '2026-09-30';
```

With 100k DAU over 30 days you get 3,000,000. True MAU might be 450,000 — off by 6.7x. `AVG(dau)` is not the fix either; it answers a different question. Distinct counts are not additive because you cannot tell, from the number `100000`, *which* users it represents.

The correct answer requires the raw grain:

```sql
SELECT COUNT(DISTINCT user_id) AS mau FROM events
WHERE day BETWEEN '2026-09-01' AND '2026-09-30';
```

That works but rescans 30 days of events on every query — and nests badly: you cannot build MAU, WAU, and a 90-day trend off one pre-aggregate.

**The real fix is a mergeable sketch.** HyperLogLog stores a fixed-size bitmap of hashed IDs (a few KB) instead of a count. Two sketches combine into the sketch of the union, so daily sketches roll up to any window:

```sql
-- Snowflake: build once per day
CREATE TABLE daily_sketch AS
SELECT day, HLL_ACCUMULATE(user_id) AS sketch
FROM events GROUP BY day;

-- then any window, no rescan of events
SELECT HLL_ESTIMATE(HLL_COMBINE(sketch)) AS mau
FROM daily_sketch
WHERE day BETWEEN '2026-09-01' AND '2026-09-30';
```

BigQuery: `HLL_COUNT.INIT` / `.MERGE` / `.EXTRACT`. DuckDB and most engines expose `approx_count_distinct()` for the one-shot case; Postgres needs the `postgresql-hll` extension.

The tradeoff is accuracy: HLL typically lands within ~2% relative error. Fine for MAU trends, dashboards, and funnel denominators. Not fine for billing, compliance counts, or anything someone will reconcile to the row — use exact `COUNT(DISTINCT)` there.

**Rule of thumb:** never expose a stored distinct count as something a BI tool can aggregate. Define it as a measure that recomputes at whatever grain the user queries — Looker `type: count_distinct`, Power BI `DISTINCTCOUNT()` — so slicing by month recounts from the grain instead of summing days. If you must pre-aggregate for speed, store the sketch, not the number.
