## 00:02 - [Data Engineering] Parquet Row Groups: Why Predicate Pushdown Skips Nothing

Parquet is columnar, so people assume `WHERE event_date = '2026-10-01'` reads only the matching rows. It doesn't. The unit of skipping is the **row group** — typically ~128 MB of rows — and the engine decides whether to read one by comparing your predicate against the min/max statistics stored in the footer.

The structure: file → row groups → one column chunk per column → pages. The footer carries min, max, and null count for every column chunk, and often per page too.

**The failure mode is unsorted data.** If rows arrive interleaved, every row group's `event_date` range spans the full window, every min/max overlaps your filter, and the reader opens all of them. The file is columnar, so you only read one column — but you read all of it.

Check before you guess:

```python
import pyarrow.parquet as pq

f = pq.ParquetFile("events.parquet")
for i in range(f.metadata.num_row_groups):
    s = f.metadata.row_group(i).column(2).statistics  # event_date
    print(i, s.min, s.max, f.metadata.row_group(i).num_rows)
```

Ranges that all look like `2026-09-01 → 2026-10-04` mean zero skipping is possible.

**The fix is sorting on write**, so ranges become disjoint:

```python
pq.write_table(
    table.sort_by([("event_date", "ascending"), ("tenant_id", "ascending")]),
    "events.parquet",
    row_group_size=1_000_000,     # rows, not bytes — tune to ~128MB
    compression="zstd",
)
```

Sort order is a budget: the first column prunes well, the second only within each first-column value, the third essentially not at all. Pick the two columns your queries actually filter on.

**Min/max is useless for high-cardinality equality** — `user_id = 'u_8812'` falls inside nearly every range. That's what bloom filters are for:

```python
pq.write_table(t, "events.parquet",
               write_bloom_filter=["user_id"])
```

Spark equivalent: `parquet.bloom.filter.enabled#user_id = true`.

**Row group sizing trade-off:** small groups give finer skipping but multiply footer metadata and turn one sequential read into many random ones on object storage; huge groups prune coarsely and inflate reader memory. 128 MB is the default for a reason — change it only with measurements.

## 05:03 - [Data Analytics] Distinct Counts Don't Merge: Why DAU Can't Roll Up to MAU

Sums roll up. Counts of *distinct things* do not. This is the bug behind most wrong MAU numbers: someone builds a `daily_active_users` table, then aggregates it to a month.

```sql
-- WRONG: counts each user once per day they appeared
SELECT SUM(dau) AS mau FROM daily_active_users
WHERE day BETWEEN '2026-09-01' AND '2026-09-30';
```

With 100k DAU over 30 days you get 3,000,000. True MAU might be 450,000 — off by 6.7x. `AVG(dau)` is not the fix either; it answers a different question. Distinct counts are not additive because you cannot tell, from the number `100000`, *which* users it represents.

The correct answer requires the raw grain:

```sql
SELECT COUNT(DISTINCT user_id) AS mau FROM events
WHERE day BETWEEN '2026-09-01' AND '2026-09-30';
```

That works but rescans 30 days of events on every query — and nests badly: you cannot build MAU, WAU, and a 90-day trend off one pre-aggregate.

**The real fix is a mergeable sketch.** HyperLogLog stores a fixed-size bitmap of hashed IDs (a few KB) instead of a count. Two sketches combine into the sketch of the union, so daily sketches roll up to any window:

```sql
-- Snowflake: build once per day
CREATE TABLE daily_sketch AS
SELECT day, HLL_ACCUMULATE(user_id) AS sketch
FROM events GROUP BY day;

-- then any window, no rescan of events
SELECT HLL_ESTIMATE(HLL_COMBINE(sketch)) AS mau
FROM daily_sketch
WHERE day BETWEEN '2026-09-01' AND '2026-09-30';
```

BigQuery: `HLL_COUNT.INIT` / `.MERGE` / `.EXTRACT`. DuckDB and most engines expose `approx_count_distinct()` for the one-shot case; Postgres needs the `postgresql-hll` extension.

The tradeoff is accuracy: HLL typically lands within ~2% relative error. Fine for MAU trends, dashboards, and funnel denominators. Not fine for billing, compliance counts, or anything someone will reconcile to the row — use exact `COUNT(DISTINCT)` there.

**Rule of thumb:** never expose a stored distinct count as something a BI tool can aggregate. Define it as a measure that recomputes at whatever grain the user queries — Looker `type: count_distinct`, Power BI `DISTINCTCOUNT()` — so slicing by month recounts from the grain instead of summing days. If you must pre-aggregate for speed, store the sketch, not the number.

## 10:02 - [ML & AI] Conformal Prediction: A Coverage Guarantee You Don't Have to Trust the Model For

Calibration fixes the *probabilities* a classifier reports. It does nothing for regression, and it still assumes your model's own uncertainty estimate means something. Split conformal prediction sidesteps that: it wraps any fitted model — GBM, linear, neural net, an API you can't see inside — in intervals that cover the true value at a rate you choose, with no distributional assumptions.

**The recipe (regression).** Hold out a calibration set the model never trained on. Score each point with a *nonconformity* measure — the absolute residual. Then take a specific order statistic of those scores:

```
q = the ⌈(n+1)(1−α)⌉-th smallest residual
interval = ŷ ± q
```

```python
import numpy as np
# model fit on X_train only; cal is a held-out split the model never saw
s = np.sort(np.abs(y_cal - model.predict(X_cal)))   # nonconformity scores
n, alpha = len(s), 0.10
k = int(np.ceil((n + 1) * (1 - alpha)))             # the +1 matters
q = s[k - 1]                                        # k-th smallest residual
lo, hi = model.predict(X_test) - q, model.predict(X_test) + q
```

**Worked example.** n = 1000, α = 0.10. ⌈1001 × 0.90⌉ = 901, so q is the 901st smallest residual, not the 900th. If that value is \$4,200, every prediction gets ±\$4,200 and ≥90% of future points land inside — a 3,000-trial simulation lands at 90.1% coverage. Indexing the sorted array is the exact form. `np.quantile(s, k/n, method="higher")` is valid but can land one value higher, so it is slightly conservative; plain `np.quantile(s, 0.9)` is not valid at all — linear interpolation returns a value below the 901st residual and undercovers, visibly so at small n.

**What it costs you.** Three things worth knowing before you ship it:

- **It needs data.** The guarantee requires ⌈(n+1)(1−α)⌉ ≤ n, so n ≥ 1/α − 1: at minimum 9 calibration points for 90%, and realistically hundreds for a stable q.
- **Coverage is marginal, not conditional.** 90% overall can be 97% on your easy segment and 70% on the hard one. Fix it by conformalizing *within* groups, or by normalizing residuals by a predicted-difficulty model (`s = |y − ŷ| / σ̂(x)`) so the band widens where the model is weak.
- **Exchangeability, not independence.** Time series break it. Use the most recent block as your calibration set and re-fit q on a rolling basis.

For classification, swap the score for `1 − p̂(true class)` and you get prediction *sets* — one label where the model is sure, five where it isn't. That's often the more honest output.

## 15:03 - [Crypto & Business] Perpetual Funding Rates: How a "0.01%" Number Becomes 11% a Year

A perpetual future has no expiry date, so nothing forces it to converge to spot the way a quarterly contract does. **Funding** is the mechanism that does that job: a periodic payment between longs and shorts, sized to punish whichever side is pushing the perp away from the index price.

**Direction.** If the perp trades above the index, the premium is positive and **longs pay shorts**. Below the index, shorts pay longs. It is peer-to-peer — the venue generally isn't the counterparty, it just computes the rate. Most major venues settle every 8 hours (00:00, 08:00, 16:00 UTC); some settle hourly. You pay only if you hold the position through the settlement timestamp — flat before it, and you pay nothing.

**The rate has two parts** on a typical venue: a premium component (a time-weighted average of perp mark minus index, as a fraction of index) plus a flat interest-rate component, usually 0.01% per 8 hours. The result is then clamped, commonly at ±0.075% per 8h.

**The trap: funding accrues on notional, not on margin.**

Worked example — $50,000 long on BTC perp, 10x leverage, so $5,000 of margin posted. Funding is +0.01% per 8h:

- Per settlement: $50,000 × 0.0001 = **$5**
- Per day (3 settlements): **$15**
- Annualized: 0.01% × 3 × 365 = **10.95%** → $5,475/yr

That $5,475 is 11% of the notional but **109% of your margin**. At the clamp of 0.075% per 8h, the annualized rate is 82%, and your $5,000 margin is gone in roughly 12 days of flat price action.

**Annualize anything you see:** `rate_per_8h × 3 × 365`. So 0.01% → ~11%/yr, 0.03% → ~33%/yr.

Persistently positive funding is also a sentiment reading — it means leveraged longs are crowded and paying to stay there. That crowding is what makes those positions a liquidation cascade waiting for a trigger, which is why funding spikes and sharp liquidation wicks tend to arrive together.
