## 00:03 - [Data Engineering] Redshift Sort Keys: Zone Maps, the Unsorted Region, and Why Pruning Quietly Stops

Redshift stores each column in 1 MB blocks and keeps a **zone map** — the min/max value per block — in memory. A scan skips any block whose range can't satisfy the predicate. The sort key is what makes those ranges tight; without it, every block spans the whole domain and nothing is skipped.

```sql
CREATE TABLE fct_orders (
  order_id      BIGINT,
  order_ts      TIMESTAMP ENCODE RAW,   -- leading sortkey: keep it uncompressed
  region_id     SMALLINT,
  amount        DECIMAL(18,2)
)
DISTSTYLE KEY DISTKEY (order_id)
COMPOUND SORTKEY (order_ts, region_id);
```

**Compound is sorted left-to-right**, like a phone book. `WHERE order_ts >= '2026-10-01'` prunes hard; `WHERE region_id = 3` alone prunes almost nothing, because region values are scattered across every timestamp block. Order the columns by how often they appear in range filters, most selective *leading* predicate first — not by cardinality.

Interleaved sort keys give every column equal weight and help genuinely unpredictable filter combinations, but they need `VACUUM REINDEX` (a full rewrite) to stay useful and degrade fast under incremental loads. Treat them as a last resort; AWS's own default is now `SORTKEY AUTO`, which lets the advisor pick and rewrite based on observed queries.

**The silent failure is the unsorted region.** A `COPY` into an empty table writes sorted. Every later insert appends to the tail, unsorted, and those blocks have wide zone maps that must be scanned in full. Pruning doesn't break — it erodes.

```sql
SELECT "table", size, unsorted, vacuum_sort_benefit, sortkey1
FROM svv_table_info
WHERE unsorted > 10
ORDER BY vacuum_sort_benefit DESC;
```

Auto-vacuum handles this in the background when the cluster is idle, which on a busy cluster means never. `vacuum_sort_benefit` is the estimated percentage of scan time you'd recover — above ~20% on a large table, schedule it yourself:

```sql
VACUUM SORT ONLY fct_orders TO 100 PERCENT;
ANALYZE fct_orders;   -- vacuum does not refresh statistics
```

Two practical notes: compressing the leading sort key column packs more rows per block and coarsens its zone map, so leave it `RAW`; and `ALTER TABLE fct_orders ALTER SORTKEY (order_ts, region_id)` changes the key in place, so you can test an ordering without a deep copy and a table swap.

## 05:03 - [Data Analytics] Power BI Bidirectional Relationships: The Slicer Fix That Makes Your Totals Non-Deterministic

A dimension slicer returns blanks, someone flips the relationship's cross-filter direction from `Single` to `Both`, the slicer works, and the model is now quietly broken. Bidirectional relationships are the most common self-inflicted wound in a Power BI semantic model.

**What goes wrong.** In a star schema, filters flow dimension → fact. Set `Customer ↔ Sales` to Both and a filter on `Product` now reaches `Customer` via `Sales`. Add a second fact table and you get two routes between the same pair of tables — an *ambiguous path*. Power BI either refuses to save the relationship or picks one route by internal heuristics, so `Total Budget` changes depending on which slicer is touched. Nothing errors; the number just shifts.

**Do it per measure, not per model.** `CROSSFILTER` turns the direction on for one calculation only:

```dax
Customers Who Bought =
CALCULATE (
    DISTINCTCOUNT ( Customer[CustomerKey] ),
    CROSSFILTER ( Sales[CustomerKey], Customer[CustomerKey], BOTH )
)
```

For the "show only dimension members with activity" case — the usual reason people reach for Both — don't change direction at all:

```dax
Active Products =
CALCULATE (
    COUNTROWS ( Product ),
    CROSSFILTER ( Sales[ProductKey], Product[ProductKey], BOTH )
)
-- or, cheaper, filter the slicer visual by a measure:
Has Sales = IF ( NOT ISEMPTY ( Sales ), 1 )
```

**Two costs people miss.** First, row-level security: a bidirectional relationship is ignored under RLS unless you tick *Apply security filter in both directions*, and when you do, every query pays an extra filter propagation. Second, performance: each bidirectional hop becomes an additional semi-join in the VertiPaq query plan. The order of magnitude to expect: on a 1.2M-row customer dimension joined to a 400M-row fact, a single Both relationship can turn a sub-second visual into a ten-second one, because the engine materializes the distinct customer keys before it can evaluate the measure. Check it yourself in Performance Analyzer or DAX Studio's server timings rather than trusting the estimate.

**Rule of thumb:** `Single` everywhere, `Both` only on a true many-to-many bridge table where the bridge is the *only* path. Everything else belongs in `CROSSFILTER` or `TREATAS`, scoped to the one measure that needs it.

## 10:03 - [ML & AI] Cost-Complexity Pruning: One Knob That Replaces Your `max_depth` Grid

Most people control tree size with `max_depth` and `min_samples_leaf`. Both prune **uniformly** — the same depth limit applies to the branch that genuinely needed six splits and the branch that was fitting noise after two. Cost-complexity pruning (CCP, the `ccp_alpha` knob) prunes **where it doesn't pay**, and it collapses a 2-D or 3-D grid search into a 1-D curve over a finite, data-derived list of candidates.

**The objective.** Grow the tree fully, then score every subtree `T` by

```
R_α(T) = R(T) + α · |leaves(T)|
```

where `R(T)` is the total **sample-weighted** leaf impurity (in sklearn each node's impurity is weighted by `N_node / N_total`, so root impurity equals plain Gini). Raising α buys fewer leaves at the cost of more impurity.

**Which subtree dies first.** For an internal node `t`, its effective alpha is

```
α_eff(t) = (R(t) − R(T_t)) / (|leaves(T_t)| − 1)
```

the impurity you'd give up by collapsing `t` to a leaf, *per leaf saved*. Weakest link goes first. Worked example: node `t` holds 10% of rows and would have Gini 0.42 as a leaf, so `R(t) = 0.10 × 0.42 = 0.042`. Its subtree's three leaves contribute `0.004 + 0.009 + 0.005 = 0.018`. Then `α_eff = (0.042 − 0.018)/(3 − 1) = 0.012` — collapsing the branch costs 0.024 of impurity and saves 2 leaves, so 0.012 per leaf. Any `ccp_alpha ≥ 0.012` deletes that whole branch.

**Tuning it.** sklearn hands you exactly the α values where the tree changes:

```python
import numpy as np
from sklearn.tree import DecisionTreeClassifier
from sklearn.model_selection import cross_val_score

path   = DecisionTreeClassifier(random_state=0).cost_complexity_pruning_path(X_tr, y_tr)
alphas = path.ccp_alphas[:-1]                 # drop the last: root-only tree
alphas = alphas[:: max(1, len(alphas) // 40)] # thin a long path

scores = [cross_val_score(DecisionTreeClassifier(random_state=0, ccp_alpha=a),
                          X_tr, y_tr, cv=5, scoring="roc_auc").mean()
          for a in alphas]
best = alphas[int(np.argmax(scores))]
```

On a 1,500-row `make_classification` set this picks `ccp_alpha ≈ 0.0056`, taking the tree from **120 leaves to 12** while 5-fold ROC-AUC rises from **0.855 to 0.914** — the pruned tree is both smaller and better, and the whole search was 73 candidates along one axis.

**Two gotchas.** α is in impurity units scaled by your sample weights and row count, so a good value never transfers between datasets — always re-derive the path. And for forests and GBMs, `min_samples_leaf` is still the better lever; CCP earns its keep on the single tree you intend to read.

## 15:03 - [Crypto & Business] Operating Leverage: Why a 10% Revenue Dip Cut Profit 87%

Two companies with identical revenue and identical profit can respond to the same 10% sales swing in completely different ways. The difference is the fixed/variable split of their cost base.

**The worked example.** A B2B software company:

- Revenue: $2.00M
- Variable costs (hosting, payment fees, support credits): 35% of revenue → $0.70M
- **Contribution margin: $1.30M (65%)**
- Fixed costs (salaries, rent, tooling): $1.15M
- Operating profit: **$150K**

Now lose 10% of revenue. Variable costs shrink with it, fixed costs don't:

- Revenue $1.80M → CM $1.17M → minus $1.15M = **$20K profit**

Profit fell 87% on a 10% revenue decline. That multiplier isn't a surprise — it's computable in advance:

**Degree of operating leverage (DOL) = Contribution margin ÷ Operating profit** = $1.30M ÷ $0.15M = **8.7×**

Every 1% move in revenue moves operating profit ~8.7%, in both directions. The same company at +10% revenue earns $280K, up 87%.

**Two numbers to keep on the wall.**

1. **Break-even revenue = Fixed costs ÷ CM%** = $1.15M ÷ 0.65 = **$1.77M**
2. **Margin of safety = (Actual − Break-even) ÷ Actual** = ($2.00M − $1.77M) ÷ $2.00M = **11.5%**

An 11.5% cushion with 8.7× leverage is a business one lost enterprise contract away from losing money.

**DOL decays as you scale.** At $4M revenue with the same $1.15M fixed base: CM $2.60M − $1.15M = $1.45M profit, DOL = 1.8×. High leverage is a feature of being near break-even, not of the industry.

**The lever you actually control.** Moving cost from fixed to variable — contractors instead of FTEs, usage-based cloud instead of reserved capacity, commission-weighted sales comp — lowers DOL. That raises your break-even cushion and caps your upside. Pre-product-market-fit, cheap insurance. At scale with predictable demand, you're paying a premium to avoid a risk you no longer carry.

## 19:04 - [PC Hardware] GPU Temperatures: Edge, Hotspot, and Memory Junction Are Three Different Problems

The number your overlay labels "GPU Temperature" is the **edge** sensor — one fixed point on the die. It is also the sensor your fan curve follows. That combination is why a card can sit at a comfortable 68°C while something inside it is cooking.

Modern GPUs expose three readings worth separating:

| Sensor | Healthy under load | Investigate | Hard behavior |
|---|---|---|---|
| **Edge** ("GPU Temperature") | 60–78°C | >83°C sustained | driver slowdown near 90–93°C |
| **Hotspot / Junction** (hottest of many on-die sensors) | 75–95°C | delta >25°C over edge | AMD RDNA throttles at 110°C junction |
| **Memory junction** (GDDR6/6X) | 80–96°C | >100°C | ~105°C triggers memory throttling |

**The delta is the diagnostic, not the absolute.** On a healthy mount, hotspot runs roughly 10–20°C above edge. A delta above 25–30°C means contact has gone bad: uneven cooler mounting pressure, pump-out on an aging paste joint, or a cold plate that is no longer flat. The card will often still hit advertised clocks, just louder and lower, so nothing obviously breaks — you lose a few percent and gain fan noise.

**Memory is the one that hides.** GDDR6X modules on dense cards (notably 3080/3090-class, where some modules sit on the back of the PCB) commonly read 100–108°C. Because the fan curve watches edge temp, fans stay moderate while memory throttles and error-retries. Symptom: steady core clocks, falling memory bandwidth, inexplicable frametime spikes in VRAM-heavy workloads.

How to actually read them:

```bash
# AMD on Linux — exposes all three directly
sensors | grep -A4 amdgpu     # edge, junction, mem

# NVIDIA — thresholds and whether it is throttling right now
nvidia-smi -q -d TEMPERATURE      # current, slowdown, shutdown, max-operating
nvidia-smi -q -d PERFORMANCE      # SwThermalSlowdown / HwSlowdown flags
```

On Windows, HWiNFO64 is the practical tool — it surfaces "GPU Hot Spot" and "GPU Memory Junction" that most overlays omit. Log a 20-minute sustained load, not a 2-minute benchmark; thermal mass means short runs read low.

Fixes in order of effort: raise case exhaust and intake first, set a more aggressive fan curve keyed to the *highest* available sensor if your tool allows it, then consider repasting and replacing memory pads — the last one voids most warranties, so treat it as a late option on an out-of-warranty card.
