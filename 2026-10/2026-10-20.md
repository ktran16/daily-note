## 00:03 - [Data Engineering] Redshift Sort Keys: Zone Maps, the Unsorted Region, and Why Pruning Quietly Stops

Redshift stores each column in 1 MB blocks and keeps a **zone map** — the min/max value per block — in memory. A scan skips any block whose range can't satisfy the predicate. The sort key is what makes those ranges tight; without it, every block spans the whole domain and nothing is skipped.

```sql
CREATE TABLE fct_orders (
  order_id      BIGINT,
  order_ts      TIMESTAMP ENCODE RAW,   -- leading sortkey: keep it uncompressed
  region_id     SMALLINT,
  amount        DECIMAL(18,2)
)
DISTSTYLE KEY DISTKEY (order_id)
COMPOUND SORTKEY (order_ts, region_id);
```

**Compound is sorted left-to-right**, like a phone book. `WHERE order_ts >= '2026-10-01'` prunes hard; `WHERE region_id = 3` alone prunes almost nothing, because region values are scattered across every timestamp block. Order the columns by how often they appear in range filters, most selective *leading* predicate first — not by cardinality.

Interleaved sort keys give every column equal weight and help genuinely unpredictable filter combinations, but they need `VACUUM REINDEX` (a full rewrite) to stay useful and degrade fast under incremental loads. Treat them as a last resort; AWS's own default is now `SORTKEY AUTO`, which lets the advisor pick and rewrite based on observed queries.

**The silent failure is the unsorted region.** A `COPY` into an empty table writes sorted. Every later insert appends to the tail, unsorted, and those blocks have wide zone maps that must be scanned in full. Pruning doesn't break — it erodes.

```sql
SELECT "table", size, unsorted, vacuum_sort_benefit, sortkey1
FROM svv_table_info
WHERE unsorted > 10
ORDER BY vacuum_sort_benefit DESC;
```

Auto-vacuum handles this in the background when the cluster is idle, which on a busy cluster means never. `vacuum_sort_benefit` is the estimated percentage of scan time you'd recover — above ~20% on a large table, schedule it yourself:

```sql
VACUUM SORT ONLY fct_orders TO 100 PERCENT;
ANALYZE fct_orders;   -- vacuum does not refresh statistics
```

Two practical notes: compressing the leading sort key column packs more rows per block and coarsens its zone map, so leave it `RAW`; and `ALTER TABLE fct_orders ALTER SORTKEY (order_ts, region_id)` changes the key in place, so you can test an ordering without a deep copy and a table swap.

## 05:03 - [Data Analytics] Power BI Bidirectional Relationships: The Slicer Fix That Makes Your Totals Non-Deterministic

A dimension slicer returns blanks, someone flips the relationship's cross-filter direction from `Single` to `Both`, the slicer works, and the model is now quietly broken. Bidirectional relationships are the most common self-inflicted wound in a Power BI semantic model.

**What goes wrong.** In a star schema, filters flow dimension → fact. Set `Customer ↔ Sales` to Both and a filter on `Product` now reaches `Customer` via `Sales`. Add a second fact table and you get two routes between the same pair of tables — an *ambiguous path*. Power BI either refuses to save the relationship or picks one route by internal heuristics, so `Total Budget` changes depending on which slicer is touched. Nothing errors; the number just shifts.

**Do it per measure, not per model.** `CROSSFILTER` turns the direction on for one calculation only:

```dax
Customers Who Bought =
CALCULATE (
    DISTINCTCOUNT ( Customer[CustomerKey] ),
    CROSSFILTER ( Sales[CustomerKey], Customer[CustomerKey], BOTH )
)
```

For the "show only dimension members with activity" case — the usual reason people reach for Both — don't change direction at all:

```dax
Active Products =
CALCULATE (
    COUNTROWS ( Product ),
    CROSSFILTER ( Sales[ProductKey], Product[ProductKey], BOTH )
)
-- or, cheaper, filter the slicer visual by a measure:
Has Sales = IF ( NOT ISEMPTY ( Sales ), 1 )
```

**Two costs people miss.** First, row-level security: a bidirectional relationship is ignored under RLS unless you tick *Apply security filter in both directions*, and when you do, every query pays an extra filter propagation. Second, performance: each bidirectional hop becomes an additional semi-join in the VertiPaq query plan. The order of magnitude to expect: on a 1.2M-row customer dimension joined to a 400M-row fact, a single Both relationship can turn a sub-second visual into a ten-second one, because the engine materializes the distinct customer keys before it can evaluate the measure. Check it yourself in Performance Analyzer or DAX Studio's server timings rather than trusting the estimate.

**Rule of thumb:** `Single` everywhere, `Both` only on a true many-to-many bridge table where the bridge is the *only* path. Everything else belongs in `CROSSFILTER` or `TREATAS`, scoped to the one measure that needs it.
