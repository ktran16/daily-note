## 00:03 - [Data Engineering] Dagster Asset Checks: The `blocking` Flag Decides Whether Bad Data Reaches Downstream

A data test that runs as its own task tells you the data was wrong *after* the mart built on it. Dagster's asset checks fix the ordering problem by attaching the test to the asset in the graph, so the orchestrator knows a check belongs to `orders` and can refuse to continue.

```python
from dagster import (
    asset_check, AssetCheckResult, AssetCheckSeverity,
)

@asset_check(asset=orders, blocking=True, description="No negative amounts")
def orders_amount_non_negative(duckdb: DuckDBResource) -> AssetCheckResult:
    with duckdb.get_connection() as conn:
        bad = conn.execute(
            "select count(*) from orders where amount < 0"
        ).fetchone()[0]
    return AssetCheckResult(
        passed=bad == 0,
        severity=AssetCheckSeverity.ERROR,
        metadata={"bad_rows": bad},
    )
```

**The flag that actually matters is `blocking`.** Severity controls how the failure is *displayed* and alerted on; `blocking=True` controls whether the run *stops*. A non-blocking `ERROR` check turns the asset red in the UI and still lets every downstream asset materialize off the bad partition in the same run. That is the single most common misconfiguration — teams set `ERROR`, see red, and assume they are protected.

Blocking checks execute after the asset materializes and before downstream steps are launched. Note the implication: the bad data *is written*. Blocking buys you containment, not prevention — pair it with write-audit-publish if the table must never be readable while wrong.

**Checks you already own.** `dagster-dbt` maps dbt tests onto asset checks automatically, so a `not_null` in `schema.yml` shows up as a check on the corresponding Dagster asset rather than a mystery step. You get dbt's test suite plus Dagster's dependency awareness, without rewriting assertions.

**Freshness without a cron.** `build_last_update_freshness_checks` asserts an asset was updated within a window, which catches the stalled upstream that passes every row-level test because yesterday's rows are all perfectly valid.

Reach for `check_specs` on the asset itself when the assertion is cheap and computable during compute — one warehouse query instead of two.

## 05:03 - [Data Analytics] Triggered Analysis: The Dilution That Buries a 10% Lift, and the Filter That Invents One

A feature that only renders on the checkout page was shipped to 50% of users. The test reads **+0.4%, p = 0.42**. The team calls it flat and kills it. But only 20% of assigned users ever reached checkout during the window — the other 80% could not possibly respond, and they are sitting in both arms diluting the signal.

**The dilution math.** If the true lift among exposed users is 10% and exposure is 20%, the intent-to-treat effect is roughly `0.20 × 10% = 2%`. Sample size scales with `1/MDE²`, so detecting 2% instead of 10% needs **25x the users**. The test was never powered to see the thing it was measuring.

**The fix, and the trap inside it.** Restrict to users who hit the trigger point — but the trigger must be computable *identically in both arms* and must not be affected by the treatment. Filtering treatment on `widget_clicked` and comparing against all of control is the classic self-own: clicking is post-treatment and selects engaged users, which manufactures lift out of nothing.

```sql
-- Trigger = reached checkout (exists in both arms), NOT "clicked the widget".
with triggered as (
  select a.user_id, a.variant, min(e.ts) as trigger_ts
  from assignments a
  join events e
    on  e.user_id = a.user_id
    and e.ts >= a.assigned_at
    and e.name  = 'checkout_page_view'
  group by 1, 2
)
select t.variant,
       count(*)                                      as users,
       avg(case when o.user_id is null then 0 else 1 end) as conv
from triggered t
left join orders o
  on  o.user_id    = t.user_id
  and o.created_at >= t.trigger_ts   -- outcomes after exposure only
group by 1;
```

Two details carry the weight: `e.ts >= a.assigned_at` keeps pre-assignment history out, and `o.created_at >= t.trigger_ts` stops you crediting a purchase that happened before the user could see anything.

**When you must not do this.** If the treatment changes the *probability of triggering* — a banner that drives people to checkout — the triggered population differs between arms and the comparison is no longer randomized. There, report ITT on everyone and accept the dilution.

Decide the trigger before launch and log it as an event. Choosing it after seeing the numbers is just p-hacking with extra steps.

## 10:03 - [ML & AI] Weight Initialization: ReLU Throws Away Half the Variance, and Xavier Doesn't Know It

Initialization is a variance-budgeting problem. For a linear layer `y = Wx` with `n_in` inputs and i.i.d. zero-mean weights:

```
Var(y) = n_in · Var(w) · Var(x)
```

To keep activation variance constant layer to layer you need `Var(w) = 1 / n_in`. **Xavier/Glorot** uses `Var(w) = 2/(n_in + n_out)` — the harmonic compromise between preserving the forward signal (`1/n_in`) and the backward gradient (`1/n_out`). It was derived for `tanh`, which is roughly linear and symmetric near zero.

ReLU breaks that derivation. If `x` is symmetric about zero, ReLU zeroes half of it, so `E[relu(x)²] = ½·E[x²]`. Every layer multiplies the variance budget by ½. **He/Kaiming** init just pays that back: `Var(w) = 2 / n_in`.

**The arithmetic of getting it wrong.** Use Xavier in a plain ReLU net and activation *variance* shrinks by 2^-L, so the std shrinks by 2^(-L/2):

| Depth L | std ratio |
|---|---|
| 6 | 1/8 |
| 20 | ~1/1000 |
| 30 | ~1/32000 |

By layer 30 the forward signal is numerical noise and gradients are proportionally dead. This is exactly why He et al. could train 30-layer plain nets that Xavier-initialized ones failed on.

```python
import torch, torch.nn as nn
for name, init in [("xavier", nn.init.xavier_normal_),
                   ("he", lambda w: nn.init.kaiming_normal_(w, nonlinearity="relu"))]:
    x = torch.randn(512, 256)
    for _ in range(20):
        lin = nn.Linear(256, 256, bias=False)
        init(lin.weight)
        x = torch.relu(lin(x))
    print(name, f"{x.std().item():.2e}")
# xavier ~7e-04    he ~5.8e-01   (ratio ~800x; exact values vary by seed)
```

**The gotcha nobody expects.** `nn.Linear`'s *default* is not He init, despite calling `kaiming_uniform_(w, a=sqrt(5))`. That `a` collapses the gain to `U(±1/√n_in)`, i.e. `Var(w) = 1/(3·n_in)` — six times smaller than He. It's a legacy Torch7 choice. Call `kaiming_normal_` explicitly.

**When it stops mattering.** LayerNorm/BatchNorm renormalizes variance each block, and residual streams add rather than multiply, so modern nets are forgiving. The residual trick replaces it: GPT-2-style models scale output-projection init by `1/√(2L)` so that summing `2L` residual branches doesn't blow the stream's variance up. Pick `mode="fan_in"` to protect the forward pass, `fan_out` to protect gradients; for conv layers `fan_in = in_channels × k × k`.

## 15:03 - [Crypto & Business] Marginal CAC: Your Blended $5,000 Hides a $18,000 Next Customer

Blended CAC answers "what did last quarter cost?" It cannot answer "what will the next customer cost?" — and that second question is the only one a budget decision depends on. The gap between them is where growth plans die.

**The decomposition.** Same quarter, same $300K of fully-loaded S&M, same 60 new customers, blended CAC $5,000:

```
Channel              New custs   Cost      CAC
Referral / organic      24      $20K     $  833
Paid search (brand)     16      $60K     $3,750
Paid search (non-brand) 14     $110K     $7,857
Outbound (2 AEs+tools)   6     $110K    $18,333
                        --     ----     -------
Blended                 60     $300K    $ 5,000
```

Now apply the LTV math from the usual unit-economics stack — $500 ARPA, 80% margin, so $400/month of contribution, LTV $20,000:

| | Blended | Marginal (outbound) |
|---|---|---|
| CAC | $5,000 | $18,333 |
| LTV:CAC | 4.0:1 | **1.1:1** |
| Payback | 12.5 mo | **45.8 mo** |

The dashboard says 4:1 and a healthy year of payback. The next dollar buys a customer who barely repays acquisition cost and sits as a cash hole for nearly four years.

**Why referral poisons the average.** Referrals scale with the *installed base*, not with budget. You cannot buy 48 of them by spending $40K. But they sit in the numerator of blended CAC dragging it down, which makes paid channels look affordable by association.

**Saturation inside a channel.** Doubling non-brand search from $110K to $220K does not buy 14 more customers — you buy lower-intent keywords. If it yields 8:

```
Marginal CAC = ΔSpend / ΔNew customers
             = $110,000 / 8 = $13,750   (vs $7,857 average)
```

Marginal CAC rises monotonically inside every paid channel. The average always lags it.

**The operating rule.** Set a payback ceiling you can actually finance — say 18 months, which at $400/month contribution caps CAC at $7,200 — then fund channels only up to the spend level where *marginal* CAC hits that ceiling. In the table above, that funds brand search fully, non-brand partially, and outbound not at all until ACV rises or the sales cycle shortens.

Report blended. Decide on marginal.

## 19:03 - [PC Hardware] PWM Backlight Dimming: Why Your Monitor Gives You Headaches at Low Brightness

An LED backlight can't be dimmed much by lowering its drive current — color temperature shifts and low-current behavior gets non-linear. So most panels dim by *strobing*: the LED runs at full current but is switched on and off at a fixed frequency, and brightness is set by duty cycle. At 100% brightness the LED is simply always on. At 20% it is off roughly 80% of every cycle.

What makes this a health issue rather than trivia is the frequency. Rough bands:

| PWM frequency | Who notices |
|---|---|
| 60–240 Hz | Most people; visible shimmer, eye strain, headaches |
| 240–1000 Hz | Sensitive users, especially with eye movement |
| 1–5 kHz | Few people, but still measurable flicker |
| >5 kHz or true DC | Effectively flicker-free |

Two things make it worse than the raw number suggests. First, flicker *depth* matters as much as rate — a panel that drops to zero each cycle (100% modulation) is far harsher than one dipping to 40%. Second, on some monitors the PWM frequency is derived from refresh rate, so enabling VRR drags the flicker frequency down with your framerate — the one setting you turned on for smoothness.

**Test your own panel in 30 seconds.** Set a white full-screen image and drop brightness to ~20%. Wave a pencil rapidly in front of it: a smooth blur means no flicker, a row of discrete pencil "ghosts" means strobing. Confirm with a phone camera in pro mode at 1/1000s shutter — PWM shows as dark horizontal banding that moves as you tilt the phone.

**Mitigations, in order of effectiveness:**

1. Run the backlight at or near 100%, where duty cycle is 100%, and cut perceived brightness instead with bias lighting behind the monitor and brighter room ambient.
2. Reduce apparent brightness in software (GPU gamma/contrast, or a tool like `redshift`/Windows Night Light) rather than the backlight slider.
3. When buying, treat "Flicker-Free" marketing as unverified — it often just means PWM above some internal threshold. Check an independent flicker measurement for the exact model.

OLED is not automatically safe: desktop QD-OLED monitors are typically near-DC, but OLED laptops and phones frequently use 240–480 Hz PWM. Also check that any "black frame insertion" / backlight-strobing motion-clarity mode is off — that is deliberate flicker at refresh rate.
