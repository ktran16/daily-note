## 00:03 - [Data Engineering] Kafka Connect Dead Letter Queues: The Connector That Stays Green While Dropping Every Record

One malformed record stops a sink connector dead. With `errors.tolerance=none` (the default), the first deserialization failure fails the task, the lag chart climbs, and someone gets paged. So you set `errors.tolerance=all` and add a dead letter queue. Now the pipeline never stops — which is exactly the new problem.

### The mechanism

Connect wraps three stages in its error handler: **conversion** (Avro/JSON deserialization), **transformation** (SMTs), and **sink delivery**. With tolerance `all`, a failure in any of them diverts the record to the DLQ topic and the task keeps consuming.

```properties
errors.tolerance=all
errors.deadletterqueue.topic.name=dlq.pg-sink.orders
errors.deadletterqueue.topic.replication.factor=3
errors.deadletterqueue.context.headers.enable=true
errors.log.enable=true
errors.log.include.messages=false

# retriable errors (broker timeouts, sink unavailable) get retried first
errors.retry.timeout=300000
errors.retry.delay.max.ms=60000
```

Three things trip people up:

**DLQ is sink-only.** Source connectors have no DLQ; their `errors.tolerance=all` just logs and skips. There is no replay for what a source dropped.

**`replication.factor` defaults to 3.** On a single-broker dev cluster the connector fails at startup creating the topic. Set it to `1` there.

**The task reports RUNNING while diverting 100% of traffic.** A rotated Schema Registry credential makes *every* record fail conversion. Nothing is red. The destination table simply stops growing. Alert on the DLQ topic's *produce rate*, not on connector state:

```
sum(rate(kafka_connect_sink_task_metrics_deadletterqueue_produce_requests[5m])) > 0
```

### Replaying

`context.headers.enable` writes `__connect.errors.topic`, `.partition`, `.offset`, `.exception.class.name` and `.exception.message` onto each DLQ record — read those first, since the payload is the original raw bytes. Consume the DLQ with `ByteArrayConverter`, not the schema'd converter that just rejected it.

Then don't blind-replay. The same poison pill fails identically. Fix the schema or the SMT, deploy, *then* pipe the DLQ back to the source topic — and accept that those records arrive out of order relative to the keys they belong to. If per-key ordering matters, replaying a DLQ is a correctness decision, not a cleanup chore.

## 05:04 - [Data Analytics] Looker Aggregate Awareness: The Rollup Table Your Distinct Count Silently Ignores

Aggregate awareness lets Looker rewrite an Explore query against a small pre-aggregated table instead of the raw fact table. You declare it inside the explore:

```lkml
explore: events {
  aggregate_table: daily_country {
    query: {
      dimensions: [events.created_date, events.country]
      measures: [events.order_count, events.revenue]
    }
    materialization: { datagroup_trigger: nightly }
  }
}
```

On a 2.1B-row events table that aggregate is roughly 1.8M rows. "Revenue by month by country" rewrites to it: 95 s and 1.4 TB scanned becomes 0.6 s and ~40 MB. Looker rolls `created_date` up to month itself — a finer-grained table can serve coarser queries, never the reverse, so a month-grain aggregate cannot answer a daily question.

The trap is which measures survive a rollup. Sum, count, min and max are additive: adding daily revenue gives monthly revenue. Count-distinct, median and percentile are not — you cannot add distinct user counts per day to get monthly distinct users. Looker knows this, so it uses the aggregate table for those measures only when the table's dimensions match the query's exactly, with no further grouping. Swap `revenue` for a `count_distinct` of `user_id`, group by month, and the query silently drops back to the 95 s full scan. No error, no warning — just one dashboard tile 150x slower than the one beside it.

Verify instead of assuming: in the Explore, open the SQL tab. A rewritten query reads from a scratch-schema table (`LR$...`) with a comment naming the aggregate table used; an unrewritten one hits your raw table. Filters behave the same way — filtering on `device_type` when the aggregate holds only date and country disqualifies the rewrite, because the rows needed to apply that filter were already collapsed away.

Two fixes. Add a second aggregate table at month/country grain carrying the distinct count, and list every field your dashboards filter on in the aggregate's `dimensions`. One aggregate per real query shape beats one wide table you hope covers everything.
