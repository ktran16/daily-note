## 00:03 - [Data Engineering] Prefect Cache Policies: Why Your Task Skipped on Retry but Re-ran the Next Day

A Prefect task that costs 20 minutes of API calls gets cached on a retry inside the same flow run, then re-runs from scratch when the flow runs again tomorrow. That is not a bug — it is the default cache policy doing exactly what it says.

In Prefect 3, `@task` caching is driven by a composable `cache_policy`. The default is:

```python
DEFAULT = INPUTS + TASK_SOURCE + RUN_ID
```

Three components, each a reason to invalidate:

- `INPUTS` — a hash of the arguments. Change `start_date`, get a new cache key.
- `TASK_SOURCE` — a hash of the function body. Edit the task, invalidate the cache. This is what stops a stale result surviving a logic fix.
- `RUN_ID` — the flow run id. **This is the one that bites.** It scopes every cache entry to a single flow run, so retries reuse work but the next scheduled run never does.

Drop `RUN_ID` to share results across runs:

```python
from datetime import timedelta
from prefect import task
from prefect.cache_policies import INPUTS, TASK_SOURCE

@task(
    cache_policy=INPUTS + TASK_SOURCE,
    cache_expiration=timedelta(hours=6),
    retries=3,
)
def fetch_vendor_extract(extract_date: str) -> str:
    ...  # returns a path, not a DataFrame
```

Two practical consequences.

**Caching rides on result persistence.** A cache hit returns a *persisted* result, so the value is read back from result storage — local `~/.prefect/storage` unless you configure otherwise. Run the same flow on a different worker and the "shared" cache is cold. For cross-run caching that actually holds, point result storage at object storage (S3/GCS) rather than the worker's disk.

**Unhashable arguments silently break `INPUTS`.** Pass a DataFrame or a client object and the key is unstable. Subtract the offender instead of abandoning the policy:

```python
@task(cache_policy=(INPUTS - "debug") + TASK_SOURCE)
def transform(df_path: str, debug: bool = False): ...
```

Use `NO_CACHE` deliberately for tasks whose value is the side effect — a warehouse `MERGE`, a Slack alert. Caching those means skipping the write while reporting success, which is the worst failure mode available: green flow, empty table.

## 05:03 - [Data Analytics] Reporting Lag: Why the Last Bar on Every Dashboard Points Down

Someone pings you at 9am: "revenue is down 28%, what happened?" Nothing happened. You're looking at a partial day. Events arrive late — mobile SDKs batch, offline clients sync on reconnect, payment webhooks retry, the warehouse load runs hourly — so the newest bucket is always the most incomplete one, and it always looks like a decline.

Quantify the lag before you argue about it. Measure the gap between when an event *happened* and when it *landed*, over days old enough to have settled:

```sql
with lag_profile as (
  select date_diff('day', date(event_at), date(loaded_at)) as lag_days,
         count(*) as events
  from events
  where event_at >= current_date - interval 90 day
    and event_at <  current_date - interval 14 day   -- settled days only
  group by 1
)
select lag_days,
       sum(events) over (order by lag_days) * 1.0
         / sum(events) over () as pct_complete
from lag_profile
order by lag_days;
```

A typical result:

| lag_days | pct_complete |
|---|---|
| 0 | 0.72 |
| 1 | 0.94 |
| 2 | 0.985 |
| 3 | 0.997 |
| 7 | 1.000 |

So today-so-far holds 72% of its eventual events and yesterday 94%. That "28% drop" is the 0.72 — exactly. Two fixes:

**Cut the tail.** Make the reporting window end where completeness crosses your tolerance (`where event_date <= current_date - interval 3 day` for 99.7%). Trailing 7-day sums hide this; daily bars don't.

**Or nowcast, labelled.** Divide by the completeness factor and mark the point as an estimate — dashed line, different shade, never bare:

```sql
select d.event_date, d.revenue,
       d.revenue / c.pct_complete as revenue_nowcast
from daily_revenue d
join completeness c
  on c.lag_days = date_diff('day', d.event_date, current_date);
```

Two caveats that bite. The lag profile is per-segment: iOS may be 0.55 at lag 0 while web is 0.98, so a channel mix shift breaks one global factor — compute it per source. And never nowcast an A/B readout. If one arm's clients report slower, lag itself is a treatment effect, and scaling bakes the bias in instead of removing it.

Before escalating any drop, re-ask the question: is the metric down, or is the data just not here yet?

## 10:06 - [ML & AI] Knowledge Distillation: The T² Your KD Loss Is Probably Missing

Distilling a big teacher into a small student, you soften both logit sets with a temperature `T`, take the KL divergence, and mix it with the ordinary hard-label loss at `alpha=0.9` because you mostly want the teacher's signal. Then the student trains almost as if the teacher weren't there. The weight is right; the gradient isn't.

The soft-loss gradient w.r.t. a student logit is `(1/T)(q_i - p_i)`, where `q = softmax(z/T)` and `p = softmax(v/T)`. But dividing the logits by `T` also compresses the gap `q_i - p_i` by roughly `1/T`. Both factors land on the same term, so the gradient decays as `1/T²`. Measured on one 5-class example:

```
T= 1.0  |grad|_1 = 0.559093   x T^2 = 0.559093
T= 4.0  |grad|_1 = 0.039024   x T^2 = 0.624389
T= 8.0  |grad|_1 = 0.009366   x T^2 = 0.599426
```

Raising `T` from 1 to 4 cost 14× of gradient magnitude (asymptotically `T² = 16`); multiplying by `T²` holds it steady. So `alpha=0.9` at `T=4` really contributes `0.9/16 = 0.056` against the hard loss's `0.1` — an effective teacher share of **0.36**, not 0.9. You asked for 90% teacher and got a third.

Hence the `T * T` in the standard loss:

```python
import torch.nn.functional as F

def kd_loss(student_logits, teacher_logits, labels, T=4.0, alpha=0.9):
    soft = F.kl_div(
        F.log_softmax(student_logits / T, dim=-1),
        F.log_softmax(teacher_logits / T, dim=-1),
        reduction="batchmean",   # NOT "mean"
        log_target=True,
    ) * (T * T)
    hard = F.cross_entropy(student_logits, labels)
    return alpha * soft + (1 - alpha) * hard
```

Two more traps in four lines of code. `reduction="mean"` divides by `batch × vocab` instead of `batch`, shrinking the soft term by another factor of the vocabulary size — with a 32k vocab that is a complete erasure, and it looks like a working run. And `T` belongs to training only: inference uses `T=1`, so a tuned `T` never ships.

Diagnostic: log the two loss terms' gradient norms separately, not just the total. If the teacher's is orders of magnitude below the hard loss's, you are paying for a teacher forward pass and distilling nothing.
