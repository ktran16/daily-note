## 00:03 - [Data Engineering] Early-Arriving Facts: Inferred Dimension Members and the -1 Key

An order lands in the fact table at 02:00 referencing `customer_id = 88412`. The customer dimension loads at 03:00. For one hour that order points at a dimension row that does not exist — an **early-arriving fact**, and the three instinctive fixes are all wrong.

Dropping the row loses revenue. Setting the FK to `NULL` makes every downstream join lossy and breaks `not_null`. Worst of all is the quiet `INNER JOIN` in a mart: the order simply vanishes from the dashboard, and nothing fails.

Kimball's answer is two rows and a rule.

**The unknown member.** Seed every dimension with a reserved key for genuinely unresolvable references, and resolve FKs through `coalesce` so the fact row survives:

```sql
-- models/marts/fct_orders.sql
select
    o.order_id,
    coalesce(c.customer_sk, -1) as customer_sk,
    o.order_total
from {{ ref('stg_orders') }} o
left join {{ ref('dim_customers') }} c
    on o.customer_id = c.customer_id
```

With `-1` always present in the dimension, the mart can join inner-style without losing rows, and `not_null` plus `relationships` tests stay green and meaningful.

**The inferred member.** For a key that is merely *late*, not unknown, insert a placeholder row now and let the real load fill it in:

```sql
-- models/marts/dim_customers.sql
{{ config(materialized='incremental', unique_key='customer_sk') }}

select customer_id, name, segment, false as is_inferred
from {{ ref('stg_customers') }}

union all

-- keys seen in facts but absent from the source
select distinct o.customer_id, 'Unknown', 'Unknown', true
from {{ ref('stg_orders') }} o
left join {{ ref('stg_customers') }} c using (customer_id)
where c.customer_id is null
```

The critical rule: when the real attributes arrive, **overwrite the inferred row as Type 1 — do not open a Type 2 version.** `'Unknown' → 'Enterprise'` is not a business change; it is the same fact becoming known. A new version would attribute every order from the gap window to a segment the customer never had.

Monitor `count(*) where is_inferred` as a data-quality metric. A steady trickle is normal in CDC pipelines. A spike means an upstream dimension load failed — and the facts kept flowing.

## 05:03 - [Data Analytics] Time Zone Bucketing: Why Your "Daily" Metric Starts at 8pm

`CAST(event_at AS DATE)` on a UTC timestamp does not give you a day. It gives you a UTC day — and for a US-facing product, UTC midnight is 8pm Eastern. The entire evening usage peak gets filed under *tomorrow*.

Five events, bucketed both ways (DuckDB, actual output):

```sql
CREATE TABLE events AS SELECT * FROM (VALUES
  (1, TIMESTAMPTZ '2026-10-07 00:30:00+00'),
  (2, TIMESTAMPTZ '2026-10-07 02:15:00+00'),
  (3, TIMESTAMPTZ '2026-10-07 03:45:00+00'),
  (4, TIMESTAMPTZ '2026-10-07 14:00:00+00'),
  (5, TIMESTAMPTZ '2026-10-07 23:50:00+00')
) AS t(user_id, event_at);

-- UTC:   2026-10-07 -> 5
SELECT CAST(event_at AS DATE) AS d, count(*) FROM events GROUP BY 1;

-- Local: 2026-10-06 -> 3,  2026-10-07 -> 2
SELECT CAST(event_at AT TIME ZONE 'America/New_York' AS DATE) AS d, count(*)
FROM events GROUP BY 1;
```

Three of five events changed days. The timestamps are identical; only the bucket boundary moved. This is why the dashboard and the ops team's own numbers never reconcile — and why "Monday is always slow" is sometimes just Sunday evening leaking in.

**Per-engine conversion:**

```sql
-- BigQuery
DATE(event_at, 'America/New_York')
-- Snowflake
TO_DATE(CONVERT_TIMEZONE('UTC','America/New_York', event_at))
-- Postgres (event_at is timestamptz)
(event_at AT TIME ZONE 'America/New_York')::date
```

**Then the second trap: DST days aren't 24 hours.**

```
2026-03-08  -> 23 hours   (spring forward)
2026-11-01  -> 25 hours   (fall back)
```

So any per-day rate — events/hour, revenue/hour — divided by a hardcoded 24 is **understated ~4.2% on March 8** (the real divisor is 23) and **overstated ~4.2% on November 1** (the real divisor is 25). Hour-over-hour comparisons see a missing 2am and a duplicated 1am.

**What to do:**

1. Store UTC (`timestamptz`), always. Never store naive local time.
2. Convert **once**, in the staging layer, into an explicit `event_date_local` column. Don't scatter `AT TIME ZONE` across 40 dashboards.
3. Pick the reporting zone deliberately and write it in the metric definition. For a global product, UTC is a defensible choice *if stated*; silently inherited UTC is not.
4. Watch `DATE_TRUNC('week', ...)`: Postgres starts Monday, BigQuery starts Sunday, Snowflake depends on the `WEEK_START` session parameter. WoW comparisons across tools drift for this reason alone.

## 10:03 - [ML & AI] Poisson and Tweedie Objectives: Why Squared Error Is the Wrong Loss for Counts

You are predicting claims per policy, support tickets per account, or units sold per SKU-week. The target is a non-negative count, mostly small, occasionally huge, with a pile of zeros. You reach for `LGBMRegressor()` and get squared error by default. Two things go wrong, and only one of them is visible.

The visible one: the model predicts `-0.3` tickets. Squared error on an identity link has no idea the target is bounded below.

The invisible one matters more. Gradient boosting takes **Newton steps**, so a leaf's value is roughly `−Σg / Σh`. Under squared error, `g = ŷ − y` and `h = 1`, so the step is the raw residual. Under Poisson with a log link (`ŷ = e^f`), `g = ŷ − y` and `h = ŷ`, so the step is `(ŷ − y) / ŷ` — the **relative** error.

Two rows, each off by 2:

```
row A:  y = 12     ŷ = 10      row B:  y = 1002   ŷ = 1000
squared error step:  2    vs  2        (equal pull)
Poisson step:  2/10 = 0.200  vs  2/1000 = 0.002   (A pulls 100x harder)
```

Squared error spends the whole model's capacity on high-volume rows, because that is where the absolute residuals live. A 20% miss on a low-volume SKU is invisible to it. Poisson treats both as 20%.

**Tweedie generalizes this** via `Var(Y) = φ·μᵖ`: `p=0` is Gaussian, `p=1` Poisson, `p=2` Gamma. For `1 < p < 2` you get a compound Poisson–Gamma — an exact point mass at zero plus a skewed positive tail. That is insurance pure premium, revenue per user, demand with stockout zeros. Start at `p=1.5` and tune it.

```python
import numpy as np, lightgbm as lgb
from sklearn.metrics import mean_tweedie_deviance

m = lgb.LGBMRegressor(objective="tweedie", tweedie_variance_power=1.5,
                      n_estimators=600, learning_rate=0.05)
m.fit(X_tr, y_tr, init_score=np.log(exposure_tr))   # offset, not a feature

# gotcha: LightGBM does NOT add init_score back at predict time
pred = np.exp(m.predict(X_va, raw_score=True) + np.log(exposure_va))
mean_tweedie_deviance(y_va, pred, power=1.5)
```

Three rules:

1. **Exposure is an offset, not a feature.** 2 claims in 1 year and 2 in 10 years are different rates; `log(exposure)` as `init_score` (or `base_margin` in XGBoost) forces the coefficient to exactly 1.
2. **Score with the matching deviance.** Poisson deviance is `2·Σ[y·log(y/ŷ) − (y − ŷ)]` (the first term is 0 at `y=0`). Ranking models by RMSE after training on Tweedie just reintroduces the bias you removed.
3. XGBoost's `count:poisson` ships with `max_delta_step=0.7` to stop the exponential link from exploding. Don't zero it out because a tuner suggests it.

## 15:05 - [Crypto & Business] The HSA Is the Only Triple-Tax-Free Account — and Payroll Deferral Makes It Quadruple

Every other tax-advantaged account picks two of three: deduct now (Traditional 401(k)), or grow and withdraw free (Roth). An HSA does all three — deductible going in, tax-free growth, tax-free out for qualified medical expenses.

**2026 limits** (Rev. Proc. 2025-19): contribute **$4,400** self-only, **$8,750** family, plus a **$1,000** catch-up at 55+. Requires HDHP coverage: minimum deductible $1,700/$3,400, out-of-pocket max $8,500/$17,000.

**The fourth benefit nobody mentions.** Contributions made through an employer's cafeteria plan via payroll also escape FICA — 7.65% that a 401(k) deferral still pays. On $8,750 at a 24% marginal rate:

- Payroll route: 24% + 7.65% = **$2,769** saved
- Writing a check yourself, deducted on Form 1040: 24% only = **$2,100**

Same contribution, $669 apart. If your employer offers payroll HSA deferral, using it is free money.

**Treat it as a retirement account, not a checking account.** There is no deadline to reimburse yourself. Pay a $3,000 procedure out of pocket in 2026, keep the receipt, and reimburse tax-free in 2050 — the expense just has to be incurred after the HSA was opened. Meanwhile $8,750/year for 20 years at 7% compounds to roughly **$359,000**, withdrawable tax-free against those banked receipts.

**Four traps:**

1. **The cash sleeve.** Most custodians park everything in a near-zero-yield cash account and require $1,000–$2,000 before you can invest. Unelected, that's the whole thesis wasted.
2. **California and New Jersey** don't recognize HSAs — contributions and earnings are state-taxable, and you owe tax on interest and dividends annually.
3. **Medicare's 6-month lookback.** Part A enrollment is retroactive up to six months, so stop contributing six months before you enroll or face excise tax on the overage.
4. **Non-medical withdrawals** before 65 cost income tax *plus* a 20% penalty. After 65 the penalty vanishes and it behaves like a Traditional IRA — a worst case, not a trap.

## 19:04 - [PC Hardware] Hardware Video Encoders: Session Caps, Preset Numbers, and Why Transcoding Is Mostly Decode

Every modern GPU has a fixed-function video engine that is physically separate from the shader cores. It does not compete with your game or your training job for compute — but it is also not free, and the specs people shop on are usually the wrong ones.

**The silicon, roughly:**

| Vendor | Engine | AV1 encode | Notes |
|---|---|---|---|
| NVIDIA | NVENC | Ada (RTX 40) and newer | Top-tier SKUs ship 2–3 encoder units; mid-range ships 1 |
| Intel | QuickSync | Arc dGPU + Arc-era iGPUs | Low-profile A310/A380 are the budget transcode favorites |
| AMD | VCN | RDNA 3 (RX 7000) and newer | Historically weakest at low bitrate; much closer now |

**Three things that actually bite:**

1. **Encode sessions are capped on consumer drivers.** NVIDIA limited GeForce cards to 2 concurrent NVENC sessions for years, later raising it to 3+ on current drivers. *Decode is uncapped.* For Plex/Jellyfin this is the whole ballgame: direct-play clients only need decode, so a cheap card serves many more streams than the encode cap suggests.
2. **Check decode support, not encode marketing.** A library of HEVC 10-bit or AV1 files on a GPU without that decoder falls back to software and pegs the CPU. Verify the generation's decode matrix before buying.
3. **More encoder units ≠ faster single stream.** They enable parallel streams (or split-frame encoding in supported apps), not higher fps on one job.

**Quality vs. CPU:** fixed-function encoders trade compression efficiency for near-zero CPU cost and low latency. At equal bitrate, x264 `slow` still beats H.264 NVENC. But switching codec generation beats tuning: AV1 NVENC at ~6 Mbps looks roughly like H.264 at 9–10 Mbps, so use AV1 wherever the destination accepts it.

```bash
# NVENC AV1, quality-targeted (p1=fastest ... p7=slowest/best)
ffmpeg -i in.mkv -c:v av1_nvenc -preset p5 -rc vbr -cq 30 -b:v 0 -c:a copy out.mkv

# Intel QuickSync AV1, full hardware decode+encode path
ffmpeg -hwaccel qsv -i in.mkv -c:v av1_qsv -global_quality 28 out.mkv
```

**Prove it is actually offloading.** `nvidia-smi dmon -s u` prints `enc`/`dec` utilization columns — if both read 0 while a transcode runs, you are on the CPU. On Intel, `intel_gpu_top` shows the Video and VideoEnhance engines separately.
