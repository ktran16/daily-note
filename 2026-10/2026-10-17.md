## 00:03 - [Data Engineering] Iceberg Table Maintenance: Why Deleting Rows Made Your Table Bigger

You ran `DELETE FROM events WHERE dt < '2026-01-01'` on an Iceberg table and storage went *up*. Nothing is broken. Iceberg is immutable: a delete writes new metadata (and possibly delete files) describing a new snapshot, while every old data file stays on disk because an older snapshot still references it. Storage only drops when you expire those snapshots.

Four maintenance procedures, and the order matters:

```sql
-- 1. Compact small files into ~512 MB targets
CALL catalog.system.rewrite_data_files(
  table => 'db.events',
  strategy => 'sort', sort_order => 'dt, user_id',
  options => map('min-input-files','10','target-file-size-bytes','536870912')
);

-- 2. Collapse manifest bloat (cheap, metadata only)
CALL catalog.system.rewrite_manifests('db.events');

-- 3. Unreference old snapshots -> this is what frees data files
CALL catalog.system.expire_snapshots(
  table => 'db.events',
  older_than => TIMESTAMP '2026-10-10 00:00:00',
  retain_last => 10
);

-- 4. Delete files no snapshot ever referenced (failed writes)
CALL catalog.system.remove_orphan_files(table => 'db.events');
```

Compaction *before* expiry temporarily doubles storage — it writes new files while snapshots still pin the old ones. That is the step people run on a schedule and then wonder about the bill.

Two traps worth internalizing:

- **`remove_orphan_files` defaults to a 3-day `older_than` guard for a reason.** Writers stage data files before committing metadata. Shorten that window and you can delete a concurrent writer's in-flight files, failing its commit.
- **Expiry is the hard ceiling on time travel.** `FOR TIMESTAMP AS OF` and snapshot-id incremental reads only work inside your retention window. If a downstream job does incremental reads off snapshot ids, retention must exceed its worst-case lag.

Set the policy declaratively so it holds even when nobody calls the procedures:

```sql
ALTER TABLE db.events SET TBLPROPERTIES (
  'history.expire.max-snapshot-age-ms' = '604800000',   -- 7 days
  'history.expire.min-snapshots-to-keep' = '10',
  'write.metadata.delete-after-commit.enabled' = 'true',
  'write.metadata.previous-versions-max' = '50'
);
```

That last pair matters on streaming tables: without it, every commit leaves a `metadata.json` behind forever, and a table with a 1-minute commit cadence accumulates half a million metadata files a year.

## 05:04 - [Data Analytics] Bayesian A/B Tests: "90% Chance B Wins" Is Not a Stopping Rule

Teams switch to Bayesian A/B testing because `P(B > A) = 90%` reads like something you can tell an exec, while `p = 0.20` does not. Both numbers come from the same data — and only one of them is a decision.

Take A: 100/1,000 conversions (10.0%), B: 118/1,000 (11.8%). With a uniform `Beta(1,1)` prior, the posteriors are conjugate — just add successes and failures:

```python
import random
random.seed(0)
N = 400_000
draws = [(random.betavariate(1+100, 1+900),   # A: Beta(101, 901)
          random.betavariate(1+118, 1+882))   # B: Beta(119, 883)
         for _ in range(N)]

p_b_wins  = sum(b > a for a, b in draws) / N
loss_if_b = sum(max(a - b, 0) for a, b in draws) / N  # regret from shipping B
print(p_b_wins, loss_if_b)   # 0.9015  0.00065
```

`P(B > A) = 90.2%`. The two-proportion z-test on the same rows gives `z = 1.29`, `p = 0.197`. No contradiction: 90% one-sided posterior probability *is* roughly `1 - p/2`. The Bayesian framing didn't add evidence, it relabeled it.

**The number worth acting on is the second one.** Expected loss is the average conversion rate you give up if you ship B and B is actually worse: 0.00065 absolute, or **6.5 conversions per 10,000 visitors**. Compare that to a threshold of caring you set *before* launch — a region of practical equivalence (ROPE). At a 0.1pp threshold, 0.065pp is comfortably inside it: ship. At a 0.02pp threshold, keep running.

Two traps:

- **Bayesian methods are not peek-proof.** Checking `P(B > A) > 95%` daily and stopping on the first crossing inflates your error rate much like frequentist peeking does. What expected loss bounds is your *regret*, not your false-positive rate. If you want to stop early on significance, use a sequential design.
- **Priors are not free.** `Beta(1,1)` says a 0.4% conversion rate and a 97% one are equally plausible. With thousands of trials the data drowns it out; on a 40-conversion test it will not. A weakly informative prior centered on your historical rate — `Beta(20, 180)` for a 10% baseline — is both more honest and more stable.

Decide on expected loss against a pre-registered threshold, not on a probability crossing a round number.

## 10:03 - [ML & AI] Cross-Encoder Reranking: Retrieve 50, Keep 5

The most common RAG upgrade isn't a better embedding model — it's retrieving *more* and then throwing most of it away.

**Why two models?** A bi-encoder (your embedding model) compresses each document into a vector *before it has ever seen the query*. Similarity is then a dot product over that lossy summary. A cross-encoder feeds `[query, document]` through the transformer **together**, so attention runs across both; it outputs a single relevance score. Jointly attending beats comparing two independent compressions.

The catch is arithmetic. A bi-encoder is O(1) per query at search time because document vectors are precomputed. A cross-encoder cannot precompute anything — scoring is O(n) forward passes. Over 2M documents that's impossible; over 50 candidates it's one batched GPU call.

Hence the funnel: cheap retriever casts a wide net, expensive model sorts it.

```python
from sentence_transformers import CrossEncoder
ce = CrossEncoder("BAAI/bge-reranker-v2-m3")  # or cohere/voyage rerank API

candidates = vector_search(query, k=50)       # cheap, high recall
scores = ce.predict([(query, c.text) for c in candidates])  # one batch
top = [c for _, c in sorted(zip(scores, candidates),
                            key=lambda p: -p[0])][:5]
```

**Typical numbers** on an internal-docs corpus:

| Stage | recall@5 | p50 latency |
|---|---|---|
| Vector only, k=5 | 0.72 | ~15 ms |
| Vector k=50 → rerank → 5 | 0.91 | ~70 ms |

You bought +19 points of recall for ~55 ms — almost always worth it next to a 2-second LLM generation.

**The ceiling that bites people:** reranking can only reorder what stage one returned. Your accuracy is hard-capped by *recall@50*, not recall@5. So measure recall@k first:

```python
recall_at_k = sum(gold_id in [c.id for c in vector_search(q, k)]
                  for q, gold_id in eval_set) / len(eval_set)
```

If recall@50 is 0.94, a perfect reranker tops out at 0.94. Raise k until that curve flattens, then rerank. Tuning the reranker while stage one is leaking relevant documents is wasted effort.

Rule of thumb: `k ≈ 10×` your final context slots, capped by your latency budget.

## 15:02 - [Crypto & Business] Business Idea: OR Block-Release Analytics for Ambulatory Surgery Centers

**Customer:** Administrator or managing partner of a physician-owned multi-specialty ambulatory surgery center (ASC) — 3–6 ORs, 4,000–9,000 cases/year, $12–35M net revenue. Not hospital-owned outpatient departments, where decisions route through a health-system VP.

**The problem.** ASCs allocate recurring "block time" to surgeons — one surgeon owns Tuesdays 7am–1pm. Surgeons chronically under-fill their blocks, and the release policy ("unused block reverts 7 days out") fires too late for another surgeon's staff to book a patient, who needs 10–14 days for pre-op clearance and insurance auth. The room sits dark while nurses and techs are already staffed. The administrator sees one monthly number — "82% utilization" — computed on *scheduled* minutes rather than prime-time capacity, which hides the problem.

**The math.** Prime-time utilization here typically runs 55–68% against a 75–80% target. One OR hour carries roughly $1,800–2,600 of contribution margin (case revenue less implants, supplies, anesthesia). A 4-OR center at 8 prime hours × 250 days = 8,000 OR-hours, so closing a 10-point gap is ~800 hours ≈ **$1.4–2.1M of annual contribution** on staffing already paid for. Assume you capture a third of it.

**The product.** Nightly pull from the ASC's scheduling system (HST Pathways, Surgical Information Systems, Nextech — SQL or flat-file export). Two outputs: a weekly scorecard of each surgeon's prime-time utilization, abandonment rate, and turnover minutes; and a daily release queue of blocks predicted under 60% full, flagged at 14 days out while another surgeon can still fill them. The model stays plain — historical fill rate by surgeon × day-of-week × days-to-date, plus current bookings.

**Revenue model.** $1,500/OR/month on an annual contract ($72K/year at four ORs), plus $6–10K integration. Subscription, not gainshare — a revenue share invites a year-long fight over the baseline.

**Startup cost.** ~$12K cash (cloud and BI ~$200/mo, entity and E&O ~$3K, HIPAA-compliant hosting plus an attorney-reviewed BAA ~$4K) and 350–500 hours of build. Ingest only scheduling metadata — surgeon, room, times, CPT, payer — never clinical notes; a small PHI surface keeps the BAA conversation short.

**Main risk:** this is a political product, not an analytic one. Your report names the partner wasting the most room time, and that partner co-owns the center. Where the worst offender is also the highest-volume producer, nobody acts and your renewal dies. Qualify by asking whether the board has ever actually revoked a block.

**First validation step.** Pull 20 independent ASCs from state licensure lists or the ASCA directory across two metros. Offer a free one-time "where your prime time went" analysis from a 12-month case-log export (surgeon, room, scheduled in/out, actual in/out). The signal is whether they send the export — and whether the administrator can recite the current release window from memory. One who can't has no policy to improve; one who can and still shows 58% utilization is a buyer.
