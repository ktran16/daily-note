# Daily Notes - 2026-10-17

## 00:03 - [Data Engineering] Iceberg Table Maintenance: Why Deleting Rows Made Your Table Bigger

You ran `DELETE FROM events WHERE dt < '2026-01-01'` on an Iceberg table and storage went *up*. Nothing is broken. Iceberg is immutable: a delete writes new metadata (and possibly delete files) describing a new snapshot, while every old data file stays on disk because an older snapshot still references it. Storage only drops when you expire those snapshots.

Four maintenance procedures, and the order matters:

```sql
-- 1. Compact small files into ~512 MB targets
CALL catalog.system.rewrite_data_files(
  table => 'db.events',
  strategy => 'sort', sort_order => 'dt, user_id',
  options => map('min-input-files','10','target-file-size-bytes','536870912')
);

-- 2. Collapse manifest bloat (cheap, metadata only)
CALL catalog.system.rewrite_manifests('db.events');

-- 3. Unreference old snapshots -> this is what frees data files
CALL catalog.system.expire_snapshots(
  table => 'db.events',
  older_than => TIMESTAMP '2026-10-10 00:00:00',
  retain_last => 10
);

-- 4. Delete files no snapshot ever referenced (failed writes)
CALL catalog.system.remove_orphan_files(table => 'db.events');
```

Compaction *before* expiry temporarily doubles storage — it writes new files while snapshots still pin the old ones. That is the step people run on a schedule and then wonder about the bill.

Two traps worth internalizing:

- **`remove_orphan_files` defaults to a 3-day `older_than` guard for a reason.** Writers stage data files before committing metadata. Shorten that window and you can delete a concurrent writer's in-flight files, failing its commit.
- **Expiry is the hard ceiling on time travel.** `FOR TIMESTAMP AS OF` and snapshot-id incremental reads only work inside your retention window. If a downstream job does incremental reads off snapshot ids, retention must exceed its worst-case lag.

Set the policy declaratively so it holds even when nobody calls the procedures:

```sql
ALTER TABLE db.events SET TBLPROPERTIES (
  'history.expire.max-snapshot-age-ms' = '604800000',   -- 7 days
  'history.expire.min-snapshots-to-keep' = '10',
  'write.metadata.delete-after-commit.enabled' = 'true',
  'write.metadata.previous-versions-max' = '50'
);
```

That last pair matters on streaming tables: without it, every commit leaves a `metadata.json` behind forever, and a table with a 1-minute commit cadence accumulates half a million metadata files a year.
