## 00:02 - [Data Engineering] Mini-Dimensions: Taming the Rapidly Changing Monster Dimension

You have a `dim_customer` with 60 columns and 5M rows. Four of those columns — age band, income band, credit score, risk tier — change for a meaningful slice of customers every month. Put Type 2 history on the whole dimension and every one of those changes writes a new 60-column row. Within a year the dimension has 40M rows and is larger than some of the facts pointing at it. That is Kimball's "rapidly changing monster dimension."

The fix is not more SCD2. It is to **split the volatile attributes out into a mini-dimension** with its own surrogate key.

### Band first, then cross-join

A mini-dimension only works if its attributes are low cardinality, so continuous values must be banded before they go in. Store `age_band`, not `age`; `income_band`, not `income`. Then the dimension is just the cross product of the bands — built once, a few hundred rows, Type 1 with no history of its own:

```sql
-- models/marts/dim_customer_demographics.sql
{{ config(materialized='table') }}

select
    {{ dbt_utils.generate_surrogate_key(
         ['age_band','income_band','credit_band','risk_tier']) }} as demographics_key,
    age_band, income_band, credit_band, risk_tier
from {{ ref('seed_age_bands') }}
cross join {{ ref('seed_income_bands') }}
cross join {{ ref('seed_credit_bands') }}
cross join {{ ref('seed_risk_tiers') }}
-- 6 x 8 x 5 x 3 = 720 rows, total, forever
```

### History moves into the fact

The fact table now carries **both** keys. Each fact row records the profile the customer had at the moment of the event, so you get point-in-time accuracy with no Type 2 rows anywhere:

```sql
select
    f.order_date_key,
    c.customer_key,
    d.demographics_key,   -- profile as of the order
    f.order_amount
from {{ ref('stg_orders') }} f
join {{ ref('dim_customer') }} c on c.customer_id = f.customer_id
join {{ ref('dim_customer_demographics') }} d
  on  d.age_band    = f.age_band_at_order
  and d.income_band = f.income_band_at_order
  and d.credit_band = f.credit_band_at_order
  and d.risk_tier   = f.risk_tier_at_order
```

### Keep an outrigger for "as-is"

Joining through the fact answers "revenue by the income band customers had *then*." For "by their income band *now*," add `current_demographics_key` to `dim_customer` as an outrigger and join from there instead. Two join paths, two legitimate questions — the same as-was/as-is split SCD Type 6 solves, but without the row explosion.

**Watch for:** re-banding. Change a band's boundaries and historical `demographics_key` values silently mean something new. Version the band definitions in seeds and treat a boundary change as a restatement, not a config tweak.

## 05:04 - [Data Analytics] Ranking by Rate: The 1-of-1 Product That Tops Your Conversion Leaderboard

Every "top performers by conversion rate" dashboard has the same bug. Sort by `conversions / visits` and the winner is a product with one visit and one purchase: a flawless 100%. The rate is arithmetically correct and informationally worthless.

The usual patch is a floor — `HAVING visits >= 100` — which trades one problem for another. It hides the long tail entirely, and the threshold is arbitrary: a product at 99 visits is invisible, one at 100 is ranked as confidently as one at 50,000.

Rank by the **Wilson score lower bound** instead: the pessimistic end of the confidence interval. Small samples get a wide interval, so their lower bound sits low; large samples converge on the raw rate.

```sql
WITH stats AS (
  SELECT product_id,
         COUNT(*)                                       AS visits,
         SUM(CASE WHEN converted THEN 1 ELSE 0 END)     AS conversions
  FROM product_visits
  GROUP BY product_id
)
SELECT product_id, visits, conversions,
       conversions * 1.0 / visits AS raw_rate,
       ( (conversions * 1.0 / visits) + 3.8416 / (2 * visits)
         - 1.96 * SQRT( (conversions * 1.0 / visits)
                        * (1 - conversions * 1.0 / visits) / visits
                        + 3.8416 / (4.0 * visits * visits) ) )
       / (1 + 3.8416 / visits) AS wilson_lower
FROM stats
ORDER BY wilson_lower DESC;
```

`3.8416` is z² at 95% (1.96²). What it does to a leaderboard:

| conversions / visits | raw rate | Wilson lower |
|---|---|---|
| 450 / 1000 | 45.0% | **41.9%** |
| 45 / 100 | 45.0% | **35.6%** |
| 3 / 4 | 75.0% | **30.1%** |
| 38 / 100 | 38.0% | **29.1%** |
| 9 / 20 | 45.0% | **25.8%** |
| 1 / 1 | 100.0% | **20.7%** |

The 1-of-1 drops to last. 3-of-4 lands mid-table — still visible, no longer first. And the three products at an identical 45% now order by how much evidence backs the number.

**Two traps.** First, integer division: without `* 1.0`, Postgres and MySQL return 0 for every rate and the whole expression collapses. Second, `visits = 0` divides by zero — filter it in `stats` or wrap in `NULLIF`.

A cheaper approximation is additive smoothing: `(conversions + 10) / (visits + 25)` pulls sparse rows toward a 40% prior. Good enough for sorting, but it gives you no interval, so it can't answer "is this difference real?"
