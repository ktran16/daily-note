## 00:02 - [Data Engineering] dbt Identifier Quoting: Why `source()` Can't Find a Table That Clearly Exists

You add a source, run `dbt build`, and Snowflake says `Object 'RAW.ORDERS' does not exist or not authorized` — while you can see `orders` sitting in `RAW` in the UI. Nothing is wrong with your grants. The table was created with a *quoted* lowercase name, and dbt rendered the reference unquoted.

### The mechanism

Warehouses fold unquoted identifiers to a canonical case: Snowflake upper-cases, Postgres and Redshift lower-case. A *quoted* identifier skips folding and must be quoted forever after. So `create table "orders"` and `create table orders` are two different objects in Snowflake, and only the second answers to `RAW.ORDERS`.

dbt's `quoting` config decides whether it wraps each part of a relation in quotes. Defaults differ per adapter (dbt-snowflake ships with quoting off for database/schema/identifier; the Postgres-family adapters quote by default), so don't memorize it — compile and look:

```bash
dbt compile -s stg_orders && cat target/compiled/jaffle/models/staging/stg_orders.sql
```

Fix it at the narrowest scope that works — the source, or a single table:

```yaml
sources:
  - name: raw
    database: analytics
    quoting:
      identifier: true     # renders "orders", not ORDERS
    tables:
      - name: orders
      - name: customers
        quoting:
          identifier: false   # this one was created unquoted
```

Prefer this over flipping `quoting` globally in `dbt_project.yml`: a project-wide change rewrites every relation dbt generates, including existing models, and can orphan tables your incremental runs expect to find.

### The second bite: macros

Metadata APIs return identifiers in stored case, so string comparisons in Jinja silently fail on Snowflake, where columns come back upper-cased:

```sql
{% for column in adapter.get_columns_in_relation(source('raw','orders')) %}
  {% if column.name | lower == 'order_id' %}   {# not == 'order_id' #}
    ...
  {% endif %}
{% endfor %}
```

**Rule of thumb:** let loaders create unquoted identifiers if you control them, quote at the source definition when you don't, and always `| lower` before comparing an identifier you got back from the warehouse.

## 05:05 - [Data Analytics] Stale Categories in pandas: The Filter That Leaves Phantom Rows Behind

Casting a column to `category` saves memory and speeds up grouping. It also attaches a **fixed list of categories to the column**, and that list does not shrink when you filter rows. Every downstream count, chart, and feature matrix keeps answering for groups that are no longer in your data.

```python
import pandas as pd
df = pd.DataFrame({
    "region": pd.Categorical(["US", "US", "EU", "APAC"]),
    "rev":    [0, 100, 120, 0],
})

us = df[df.region == "US"]          # 2 rows, one region
print(us.region.value_counts())
# region
# US      2
# APAC    0      <- not in the data
# EU      0      <- not in the data
```

Two rows of real data produced a three-row result. Feed that into a bar chart and you ship two empty bars; feed it into `pd.get_dummies(us["region"])` and you get three columns — `APAC` and `EU` arrive as all-zero features that your model happily assigns coefficients to.

The fix is one call, applied right after the filter:

```python
us = us.assign(region=us.region.cat.remove_unused_categories())
us.region.value_counts()   # US  2
```

**The `observed` flag is the same bug at scale.** `groupby` on two categoricals with `observed=False` returns the full cross product, not the groups that exist. On 5,000 sales rows across 2,000 SKUs and 150 stores:

| | rows | mean units |
|---|---|---|
| `observed=True` | 4,958 | 4.52 |
| `observed=False` | 300,000 | 0.07 |

Totals survive — `sum()` is identical, since the padding rows are zeros. **Averages do not.** The mean fell 64x because 295,042 fabricated zero rows landed in the denominator. Any `mean`, `median`, or percentile over that frame is wrong, and nothing warns you.

pandas 3.0 flipped the `groupby` default to `observed=True`, so new code is safe there — but `value_counts()` and `get_dummies` still honor the stale category list, and pandas 2.x notebooks still default to `False`.

**Rule:** `remove_unused_categories()` is part of filtering, not a cleanup step. And when you see a suspiciously round group count, check whether it factors into your cardinalities — 300,000 is 2,000 x 150, not a number your data chose.

## 10:03 - [ML & AI] Continuous Batching: The 60% of Your GPU That Static Batching Throws Away

Static batching is the habit you bring from training: collect N requests, run them together, return when done. For LLM decode this is quietly disastrous, because every sequence in the batch generates a different number of tokens — and the batch runs until the *longest* one finishes.

Count the slot-steps. Eight concurrent requests with output lengths `[30, 50, 120, 60, 200, 40, 90, 70]`:

```python
lens = [30, 50, 120, 60, 200, 40, 90, 70]
useful = sum(lens)              # 660 token-steps actually produced
paid   = len(lens) * max(lens)  # 8 * 200 = 1600 slot-steps held
print(useful / paid)            # 0.41
```

59% of the GPU's decode capacity went to sequences that had already emitted their EOS and were sitting in the batch as padding. The request that finished at step 30 waited 170 extra steps to be *returned*, too — so you paid for the waste twice, in throughput and in p99 latency.

**Continuous batching** (iteration-level scheduling; vLLM, TGI, SGLang, originally Orca) reschedules at every decode step: finished sequences are evicted immediately and queued requests are admitted into the freed slots. Utilization goes to near 100%, and real-world throughput gains of 2–4x over static batching at the same latency are routine.

Two consequences worth internalizing:

**Your limit is now KV cache memory, not slot count.** `max_num_seqs` caps concurrency, but `gpu_memory_utilization` and KV cache size decide what actually fits. Oversubscribe and the scheduler *preempts* — swapping or recomputing a victim's KV cache, which shows up as throughput that collapses under load rather than degrading. Watch the preemption counter; it's the real saturation signal.

**Prefill still blocks decode.** A 32k-token prefill is one enormous forward pass, and every decoding request stalls behind it — visible as inter-token latency spikes while other users are mid-stream. `enable_chunked_prefill` splits prefill into token-budgeted pieces mixed into decode batches, trading a little TTFT for a much flatter ITL.

**Rule:** if you wrote the batching loop yourself, you built static batching. Measure utilization as `tokens_generated / (slots × steps)` — if it's under 70%, the scheduler is the bug, not the model.
