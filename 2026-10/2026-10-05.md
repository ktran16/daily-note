## 00:03 - [Data Engineering] Airflow Retries, Timeouts, and SLAs: Three Knobs People Think Do the Same Thing

A task hangs for six hours instead of running for ten minutes. Nobody is paged, the DAG run never completes, and downstream models silently serve yesterday's data. This happens because three independent settings get confused for one another.

### `retries` — how many times to try again

```python
from datetime import timedelta
from airflow.sdk import task  # Airflow 3; airflow.decorators in 2.x

@task(
    retries=4,
    retry_delay=timedelta(minutes=2),
    retry_exponential_backoff=True,   # 2m, 4m, 8m, 16m
    max_retry_delay=timedelta(minutes=30),
)
def load_orders(): ...
```

Without `retry_exponential_backoff`, all retries use the same `retry_delay` — four attempts hammering a rate-limited API two minutes apart usually fail the same way. Retries only help when the task is idempotent; a non-idempotent loader turns one transient 503 into duplicated rows.

### `execution_timeout` — how long one attempt may run

```python
@task(retries=2, execution_timeout=timedelta(minutes=20))
def load_orders(): ...
```

This is the knob that catches hangs. It raises `AirflowTaskTimeout`, which counts as a failure and consumes a retry — so a 20-minute timeout with 2 retries means up to ~60 minutes of runtime. **Without it, a task blocked on a socket read waits forever.** Set a per-DAG default so you never rely on remembering:

```python
with DAG(..., default_args={"execution_timeout": timedelta(minutes=30)},
         dagrun_timeout=timedelta(hours=3)) as dag:
```

`dagrun_timeout` bounds the whole run, not one task.

### `sla` — lateness alerting, which kills nothing

In Airflow 2.x, `sla=timedelta(hours=2)` is measured from the DAG run's **`data_interval_start`**, not from when the task started. A DAG that begins three hours after its interval start misses a two-hour SLA before the task even runs — the classic false alarm. `sla_miss_callback` fires out of band in the scheduler; the task keeps running.

Airflow 3 removed task SLAs in favor of **Deadline Alerts**, which let you anchor the deadline to the queued time or run start rather than the data interval.

**Rule of thumb:** `execution_timeout` to bound work, `retries` for transient faults, `on_failure_callback` to page, and SLA/deadline alerts only for "this should have landed by 6am" freshness promises.

## 05:05 - [Data Analytics] Dashboard Caching: The TTL That Recomputes 23 Times for One Daily Refresh

Someone complains the dashboard is slow, so you enable caching with a 1-hour TTL. It is still slow, the warehouse bill goes up, and occasionally the number is wrong. All three come from the same mistake: **TTL is a guess about freshness, and your data already knows exactly when it changed.**

**The cost of a mismatched TTL.** Your pipeline lands once a day at 06:00. A 1-hour TTL recomputes every chart 24 times a day to discover 23 times that nothing moved:

```
10 charts × 24 expirations × 8 region cache keys = 1,920 queries/day
10 charts ×  1 refresh     × 8 region cache keys =    80 queries/day
```

The fix is event-based: set a long TTL (24h+) and have the pipeline's last step purge and **warm** the cache. The first user of the day then hits a warm cache instead of paying for the cold one.

**Row-level security multiplies the cache key.** If user attributes are interpolated into the SQL, the key includes them, and every user gets a private cache entry:

```sql
-- One cache entry per user: 400 users = 400 cold queries
where region = {{ _user_attributes['region'] }}
```

Hit rate collapses to roughly `1/users`. Scope the attribute to the *role or region* rather than the user id and 400 keys become 8 — same isolation, 50× the reuse.

**Non-deterministic SQL disables caching silently.** Both BigQuery's free 24-hour result cache and Snowflake's result reuse require a syntactically identical query and refuse anything evaluated at execution time:

```sql
where event_at >= current_timestamp() - interval '7 days'  -- never cache-hits
where event_at >= current_date - 7                          -- stable all day
```

A `current_timestamp()` in a dashboard filter means every user, every page load, pays full compute. Snowflake also drops result reuse the moment an underlying micro-partition changes — which is the invalidation you actually wanted, for free.

**Check your layers.** BI result cache, warehouse result cache, and pre-aggregated table are three separate caches with three separate staleness windows. When a stakeholder says the number is wrong, ask which one they're looking at before you debug the SQL.
