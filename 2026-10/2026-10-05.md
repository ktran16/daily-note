## 00:03 - [Data Engineering] Airflow Retries, Timeouts, and SLAs: Three Knobs People Think Do the Same Thing

A task hangs for six hours instead of running for ten minutes. Nobody is paged, the DAG run never completes, and downstream models silently serve yesterday's data. This happens because three independent settings get confused for one another.

### `retries` — how many times to try again

```python
from datetime import timedelta
from airflow.sdk import task  # Airflow 3; airflow.decorators in 2.x

@task(
    retries=4,
    retry_delay=timedelta(minutes=2),
    retry_exponential_backoff=True,   # 2m, 4m, 8m, 16m
    max_retry_delay=timedelta(minutes=30),
)
def load_orders(): ...
```

Without `retry_exponential_backoff`, all retries use the same `retry_delay` — four attempts hammering a rate-limited API two minutes apart usually fail the same way. Retries only help when the task is idempotent; a non-idempotent loader turns one transient 503 into duplicated rows.

### `execution_timeout` — how long one attempt may run

```python
@task(retries=2, execution_timeout=timedelta(minutes=20))
def load_orders(): ...
```

This is the knob that catches hangs. It raises `AirflowTaskTimeout`, which counts as a failure and consumes a retry — so a 20-minute timeout with 2 retries means up to ~60 minutes of runtime. **Without it, a task blocked on a socket read waits forever.** Set a per-DAG default so you never rely on remembering:

```python
with DAG(..., default_args={"execution_timeout": timedelta(minutes=30)},
         dagrun_timeout=timedelta(hours=3)) as dag:
```

`dagrun_timeout` bounds the whole run, not one task.

### `sla` — lateness alerting, which kills nothing

In Airflow 2.x, `sla=timedelta(hours=2)` is measured from the DAG run's **`data_interval_start`**, not from when the task started. A DAG that begins three hours after its interval start misses a two-hour SLA before the task even runs — the classic false alarm. `sla_miss_callback` fires out of band in the scheduler; the task keeps running.

Airflow 3 removed task SLAs in favor of **Deadline Alerts**, which let you anchor the deadline to the queued time or run start rather than the data interval.

**Rule of thumb:** `execution_timeout` to bound work, `retries` for transient faults, `on_failure_callback` to page, and SLA/deadline alerts only for "this should have landed by 6am" freshness promises.

## 05:05 - [Data Analytics] Dashboard Caching: The TTL That Recomputes 23 Times for One Daily Refresh

Someone complains the dashboard is slow, so you enable caching with a 1-hour TTL. It is still slow, the warehouse bill goes up, and occasionally the number is wrong. All three come from the same mistake: **TTL is a guess about freshness, and your data already knows exactly when it changed.**

**The cost of a mismatched TTL.** Your pipeline lands once a day at 06:00. A 1-hour TTL recomputes every chart 24 times a day to discover 23 times that nothing moved:

```
10 charts × 24 expirations × 8 region cache keys = 1,920 queries/day
10 charts ×  1 refresh     × 8 region cache keys =    80 queries/day
```

The fix is event-based: set a long TTL (24h+) and have the pipeline's last step purge and **warm** the cache. The first user of the day then hits a warm cache instead of paying for the cold one.

**Row-level security multiplies the cache key.** If user attributes are interpolated into the SQL, the key includes them, and every user gets a private cache entry:

```sql
-- One cache entry per user: 400 users = 400 cold queries
where region = {{ _user_attributes['region'] }}
```

Hit rate collapses to roughly `1/users`. Scope the attribute to the *role or region* rather than the user id and 400 keys become 8 — same isolation, 50× the reuse.

**Non-deterministic SQL disables caching silently.** Both BigQuery's free 24-hour result cache and Snowflake's result reuse require a syntactically identical query and refuse anything evaluated at execution time:

```sql
where event_at >= current_timestamp() - interval '7 days'  -- never cache-hits
where event_at >= current_date - 7                          -- stable all day
```

A `current_timestamp()` in a dashboard filter means every user, every page load, pays full compute. Snowflake also drops result reuse the moment an underlying micro-partition changes — which is the invalidation you actually wanted, for free.

**Check your layers.** BI result cache, warehouse result cache, and pre-aggregated table are three separate caches with three separate staleness windows. When a stakeholder says the number is wrong, ask which one they're looking at before you debug the SQL.

## 10:04 - [ML & AI] Mixture of Experts: Compute Scales With Active Params, Memory Doesn't

A dense 70B model multiplies all 70B weights for every token. A Mixture-of-Experts model replaces each FFN block with `E` parallel FFNs and a router that sends each token to the top `k` of them. Total parameters go up; parameters *touched per token* go way down.

```python
def moe_layer(x, router, experts, k=2):          # x: [T, d]
    p = router(x).softmax(-1)                    # [T, E] routing probs
    w, idx = torch.topk(p, k)                    # [T, k]
    w = w / w.sum(-1, keepdim=True)              # renormalize the k kept
    out = torch.zeros_like(x)
    for slot in range(k):
        for e in range(len(experts)):
            m = idx[:, slot] == e                # tokens routed to expert e
            if m.any():
                out[m] += w[m, slot, None] * experts[e](x[m])
    return out
```

### The two numbers that never move together

| | Dense 70B | MoE: 100B total, 8B active |
|---|---|---|
| Weights @ fp16 | 140 GB | **200 GB** |
| FLOPs/token (fwd ≈ 2·params) | ~140 GFLOP | **~16 GFLOP** |
| Bytes read per decode step, batch=1 | ~140 GB | **~16 GB** |

Compute and decode bandwidth track *active* params. VRAM tracks *total* params, because routing is decided per token at runtime — you cannot know which experts the next token needs, so all of them must be resident.

### What this buys you in practice

**Local inference.** Quantize that 100B-total model to 4-bit: ~56 GB of weights, fits a 64 GB machine, and decodes at roughly 8B-model speed. This is why MoE dominates consumer-hardware releases — you trade RAM (cheap) for bandwidth (the actual bottleneck).

**Serving at scale, less so.** The batch-1 advantage erodes as batch size grows: 64 tokens with top-2 of 128 experts touch up to 128 distinct experts, so bytes-read-per-step climbs toward the *total* parameter count. MoE's throughput edge is largest at low batch, smallest when you are already saturating a GPU.

**Load balancing is not optional.** Without an auxiliary balance loss, routers collapse onto a few experts — you pay 200 GB of memory to run a 16B model. Log the per-expert token share during training or fine-tuning; a healthy top-2-of-128 router keeps max expert share under roughly 3-4× the uniform 1.6%.

## 15:04 - [Crypto & Business] Business Idea: Rate & ECRI Analytics for Independent Self-Storage Operators

**Customer.** Owner-operators of 3–15 self-storage facilities — the independent segment that still holds roughly 70% of US facilities. They have a property manager, no analyst, and a PMS (storEDGE, SiteLink, Easy Storage Solutions) full of unit-level history nobody queries.

**Problem.** Two pricing levers get set by gut. *Street rates* on vacant units are reviewed quarterly, by hand, often one number per facility instead of per unit type. *ECRI* — the existing-customer rate increase — runs on a flat rule like "+10% at month 9, everyone." The REITs do neither: they re-price daily by unit type and stagger ECRI by tenant tenure, measuring move-out elasticity each cycle. A 10x5 non-climate tenant at month 14 tolerates a far bigger bump than a 10x20 climate tenant at month 7, and the flat rule prices both wrong in opposite directions.

**The money.** A 60,000 rentable sq ft facility at 90% occupancy and $1.15/sq ft/mo bills ~$745K/yr. Rate lift is nearly pure NOI — no added labor, no added utilities — so a 4% lift is ~$30K/yr of NOI per facility. Across six facilities that's ~$180K/yr, which at a 6% cap rate is roughly $3M of appraised value. Against that, $450/facility/month ($32K/yr for six) is trivial.

**Model.** $350–600 per facility per month on a 12-month term. Resist the "% of incremental revenue" structure — attribution fights are brutal once occupancy moves for unrelated reasons.

**Startup cost.** $3–8K. CSV exports, Postgres, aggregated competitor street rates from public listing pages, ~$200/mo infra.

**Main risk.** Data access. Several PMS vendors gate their API, leaving you with manual CSV onboarding that caps you around 20 clients before ops eats the margin.

**First validation step.** Build nothing. Get two operators to send 24 months of unit-level rent roll plus move-in/move-out dates. Backtest a tenure-and-unit-type ECRI cadence against what they actually billed, and show the dollar delta. Under 2% and the thesis is dead — find out for $0.

## 19:04 - [PC Hardware] AIO Coolers: Tube Orientation, Permeation, and Diagnosing a Dying Pump

An air cooler degrades gracefully — dust builds up, temps creep a few degrees. An AIO fails *suddenly*, and most of its failure modes are decided at install time. Cooler-class performance is one question; keeping the loop alive for five years is a separate one.

### Orientation: the pump must never be the highest point

Every loop collects a small air pocket. Air migrates to the highest point in the loop, and wherever it ends up, that part runs dry. If it ends up in the pump, you get rattle, cavitation, and a dead unit in months.

| Mount | Verdict |
|---|---|
| Top radiator, tubes exiting **down** | Best — air sits in the radiator's top channel |
| Front radiator, tubes at the **bottom** | Good — air rises into the upper radiator tank |
| Front radiator, tubes at the **top** | Risky — short tube run puts air near the pump inlet |
| Radiator **below** pump level (bottom mount) | Worst — pump is the high point; avoid |

The rule in one line: the radiator should sit at or above the pump, and the tubes should leave from the low side of the radiator.

### Permeation is a clock you can't reset

Rubber tubing loses coolant by vapor permeation — roughly **1–3 mL/year** on a sealed consumer AIO. It is not a leak and it is not refillable on most units. After 4–6 years the air pocket grows enough to produce gurgling and a slow temperature creep. Budget an AIO as a ~5-year part; a tower cooler has no such clock.

### Telling a pump failure from a paste problem

They look similar on a graph but differ in *speed*:

- **Pump failure**: package temp spikes to Tjmax within **5–15 seconds** of any load, even a 40W one, and the coolant temp sensor barely moves — heat isn't reaching the radiator at all.
- **Bad mount / dried paste**: temps climb over **1–3 minutes** and scale with load. A 40W load stays cool.

Wire the pump to the dedicated `AIO_PUMP`/`W_PUMP` header at a **fixed 100%**, not a PWM curve — a throttled pump saves no meaningful noise and hides its own decline. Then enable the BIOS fan-fail alarm for that header, which is the only thing that will warn you before a shutdown.

```bash
sudo sensors-detect   # once
sensors | grep -iE 'pump|fan[0-9]|coolant'   # pump RPM should be rock steady
```

A healthy pump holds RPM within ~2% indefinitely. Drift, or a reading that wanders by hundreds of RPM, means replace it now.

### Radiator fan direction is a trade, not a best practice

Intake through the radiator gives the **lowest CPU temps** (ambient air hits the fins first) but dumps CPU heat into the case, raising GPU and VRM temps a few degrees. Exhaust through the radiator reverses both. Pick based on which component is actually closest to its limit — check the GPU hotspot and VRM sensors before deciding, not the CPU number alone.
