## 00:02 - [Data Engineering] dbt Config Precedence: Why Your `dbt_project.yml` Setting Is Silently Ignored

You set `+materialized: table` in `dbt_project.yml`, ran `dbt build`, and got a view. No error, no warning. dbt resolves configs through a layered hierarchy, and almost every "my config did nothing" bug is a layer you forgot about or a path that never matched.

**Precedence, lowest to highest:**

1. `dbt_project.yml` — least specific path loses to more specific path
2. The `config:` block in a properties file (`models/.../_models.yml`)
3. `{{ config() }}` inside the model's own SQL

```yaml
# dbt_project.yml
name: jaffle_shop
models:
  jaffle_shop:          # <-- the PROJECT NAME, not a folder
    +materialized: view
    marts:
      +materialized: table
      +tags: ['nightly']
```

The single most common silent failure: omitting that project-name key. Write `models: marts: +materialized: table` and dbt looks for a *package* called `marts`, finds nothing, and applies nothing — no error. Same trap for a folder you renamed or a path typo. Directory keys must mirror the real tree under `models/`.

**Not every config overrides. Some accumulate:**

| Config | Inheritance |
|---|---|
| `materialized`, `schema`, `alias` | clobber — most specific wins |
| `tags` | union across all levels |
| `meta` | shallow dict merge, key by key |
| `pre-hook` / `post-hook` | append; project hooks run first |
| `grants` | clobber, unless the privilege is `+`-prefixed |

So a model tagged `finance` in its `config()` block *keeps* the inherited `nightly` tag — `--select tag:nightly` still picks it up. But `grants` replaces by default:

```yaml
    marts:
      +grants:
        +select: ['analyst']   # ADDS to inherited grantees
         select: ['analyst']   # REPLACES them
```

**Stop guessing — ask dbt what it resolved:**

```bash
dbt ls --resource-type model --select marts \
       --output json --output-keys name materialized tags schema
```

That prints post-resolution config straight from the manifest, so it proves whether your YAML ever landed. `dbt compile` only shows you SQL; it won't tell you a materialization lost a precedence fight.

Rule of thumb: put defaults in `dbt_project.yml`, per-model exceptions in `config()`, and nothing in the middle layer unless a whole folder shares it.

## 05:03 - [Data Analytics] Notebook Hidden State: The Cell You Deleted Is Still in Your Numbers

A notebook has two states: the code you can see, and the kernel's memory. Nothing keeps them in sync. You define `revenue`, refine the filter, delete the first cell — and the old `revenue` is still bound in the kernel, still feeding every chart below it. The notebook renders beautifully and is unreproducible.

The scale of this isn't anecdotal. Pimentel et al. (MSR 2019) executed 1.4M public Jupyter notebooks: only **24%** ran to completion without error, and just **4%** reproduced their stored outputs.

**Diagnostic: execution counts are the audit log.** `In [14]` above `In [7]` means the top cell ran *after* the bottom one. Check it mechanically instead of squinting:

```python
import nbformat

nb = nbformat.read("analysis.ipynb", as_version=4)
counts = [c.execution_count for c in nb.cells
          if c.cell_type == "code" and c.source.strip()]
ran = [c for c in counts if c is not None]

if None in counts:
    print(f"never ran: {counts.count(None)} code cell(s)")
if ran != sorted(ran):
    print(f"out of order: {ran}")
```

Wire that into pre-commit and a stale notebook stops reaching review.

**The only proof is a cold run.** Restart & Run All locally; in CI, do it headlessly:

```bash
jupyter nbconvert --to notebook --execute --inplace \
  --ExecutePreprocessor.timeout=600 analysis.ipynb
```

Non-zero exit means the narrative depends on state you can't recover. Fix it before anyone acts on the number.

**Habits that keep it honest:**

- **Never mutate in place across cells.** `df = df[df.amount > 0]` is idempotent-looking but isn't — re-run it after an upstream edit and you've filtered a different frame. Use a new name: `paid = df[df.amount > 0]`.
- **Pin the extract.** `pd.read_sql(q, con)` against live tables means Tuesday's run can't match Monday's. Snapshot to Parquet, commit the hash.
- **Push logic into an importable module** plus `%load_ext autoreload` / `%autoreload 2`. Functions in `src/` get tested and diffed; cells don't.
- **Strip outputs from git** (`nbstripout`) so diffs show code, not base64 PNGs.

A notebook is a lab bench, not a deliverable. If the conclusion matters, the final artifact should be something that runs top to bottom from a clean kernel.

## 10:03 - [ML & AI] Stacking: In-Fold Predictions Make the Meta-Learner Worship Your Most Overfit Model

Stacking trains a meta-learner on the predictions of several base models. The step everyone gets wrong is *which* predictions it trains on.

The naive version: fit the base models on the training set, predict on that same training set, feed those columns to a logistic regression. It scores beautifully in CV and underperforms a plain average in production.

**Why.** Base models don't err uniformly on data they were fit on. Say a random forest and a logistic regression both hit 0.85 test accuracy, but on training rows the forest hits 0.99 (it nearly memorizes) and the LR hits 0.86. The meta-learner sees one near-oracle column and one mediocre one, and assigns the forest ~all the weight. At inference the forest is back down to 0.85 and the diversity you were paying for is gone. You didn't learn how to blend models; you learned which model overfits hardest.

**Fix: out-of-fold predictions.** Every row's base prediction must come from a model that never saw that row.

```python
from sklearn.model_selection import cross_val_predict, StratifiedKFold
import numpy as np

cv = StratifiedKFold(5, shuffle=True, random_state=0)
oof = np.column_stack([
    cross_val_predict(m, X, y, cv=cv, method="predict_proba")[:, 1]
    for m in (rf, lr, gbm)
])
meta.fit(oof, y)                      # honest signal
base = [m.fit(X, y) for m in (rf, lr, gbm)]   # refit on all data for serving
```

`StackingClassifier(estimators=..., final_estimator=..., cv=5)` does exactly this internally — the manual version is worth knowing so you recognize when a hand-rolled pipeline skipped it.

**Three details that matter:**

- Pass `predict_proba`, not `predict`. Hard labels throw away the confidence the meta-learner needs to arbitrate disagreements.
- Keep the meta-learner tiny — logistic regression or ridge, ideally with non-negative coefficients. With 3–5 input columns, a GBM on top just overfits the OOF noise.
- Use the *same* splitter your problem demands. On time series, `cross_val_predict` with a shuffled KFold hands each fold the future; `TimeSeriesSplit` is the only correct choice, and it leaves the earliest rows without OOF predictions.

## 15:03 - [Crypto & Business] Seed Phrases and Derivation Paths: Why the Same 12 Words Show a Zero Balance

You restore a wallet from the correct 12 words and the balance reads 0.00. The funds are almost never gone — you're looking at different addresses derived from the same secret.

**What the words actually are.** BIP-39 encodes raw entropy as words from a fixed 2048-word list, so each word carries 11 bits. 12 words = 128 bits of entropy + a 4-bit checksum (132/11 = 12). 24 words = 256 bits + 8 bits of checksum. The 128 bits is already unbreakable; 24 words buys margin, not practical security.

The mnemonic is then stretched: `PBKDF2-HMAC-SHA512(password = words, salt = "mnemonic" + passphrase, 2048 iterations)` → a 512-bit seed. BIP-32 turns that seed into an infinite tree of keys, and a **derivation path** names one branch.

**The path is the whole problem.** BIP-44 format is `m / purpose' / coin_type' / account' / change / index`:

| Path | Produces |
|---|---|
| `m/44'/60'/0'/0/0` | Ethereum, MetaMask account 1 |
| `m/44'/60'/1'/0/0` | Ethereum, Ledger Live account 2 |
| `m/44'/0'/0'/0/0` | Bitcoin legacy, `1...` |
| `m/84'/0'/0'/0/0` | Bitcoin native segwit, `bc1q...` |
| `m/86'/0'/0'/0/0` | Bitcoin taproot, `bc1p...` |

Note rows 1–2: MetaMask increments the **last** number for new accounts, Ledger Live increments the **account'** field. Same seed, two disjoint address sets. Restore one into the other and you see an empty, perfectly valid wallet.

**The passphrase is not a password.** BIP-39's optional passphrase (the "25th word") goes into the salt, so every passphrase yields a *different* seed. There is no "wrong passphrase" error — a typo silently opens an empty wallet. Write it down with the same care as the words.

**Practical checks when a restore looks empty:** confirm the address against a block explorer, not the balance; try account indices 0–5 and the alternate path layout; try the derivation path your original wallet documented; re-check the passphrase. The checksum means a mistyped word usually fails validation outright — so if the words were accepted, entropy is intact and this is a path problem.
