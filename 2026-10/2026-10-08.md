## 00:02 - [Data Engineering] `--full-refresh`: The Flag That Drops Your Table, and the Config That Refuses

`dbt run --full-refresh` is not "recompute the incremental window." For an incremental model it issues a `create or replace` — the existing table is **dropped and rebuilt from scratch**. `is_incremental()` returns false, so your lookback filter is skipped and the model scans every row of its source.

That is the intended escape hatch when model logic changes: `on_schema_change` handles new or dropped *columns*, but nothing repairs rows already written under old business logic. A full refresh is the only fix.

The danger is that `--full-refresh` is a **run-wide flag**. It applies to every selected model, so one person rebuilding a small staging table can also rebuild the 4 TB event fact sitting downstream of it.

**Guard the expensive ones.** The `full_refresh` config overrides the flag per model:

```sql
{{ config(
    materialized='incremental',
    unique_key='event_id',
    full_refresh=false
) }}
```

With this set, `dbt run --full-refresh` runs that model incrementally anyway and logs that it was skipped. Rebuilding it then requires a deliberate `dbt run -s fct_events --vars '{force: true}'` plus your own logic, or dropping the table by hand — which is the point: the rebuild becomes a decision, not a side effect.

**The irreversible case.** If the source is a truncate-and-load landing table or a CDC stream with retention shorter than your table's history, a full refresh does not rebuild — it *deletes history you cannot recover*. Always set `full_refresh=false` on those, regardless of size.

**Branch inside Jinja** when you need custom behavior. `should_full_refresh()` is true when the flag is set *and* the config permits it:

```sql
{% if not should_full_refresh() %}
  where updated_at >= (select max(updated_at) from {{ this }})
{% endif %}
```

Use this instead of `flags.FULL_REFRESH`, which ignores the model-level config and will diverge from what dbt actually does.

**Practical rule:** keep `full_refresh=false` on anything that is expensive or whose history is not reproducible from source, and reach for `--full-refresh` with an explicit `-s` selector rather than against a whole directory.

## 05:05 - [Data Analytics] pandas Copy-on-Write: The Filtered Assignment That Updates Zero Rows

Copy-on-Write became opt-in in pandas 2.0 and the default in 3.0. The headline win is fewer defensive copies; the headline break is that **chained assignment now never works** — and it fails by warning, not by raising.

```python
import pandas as pd
df = pd.DataFrame({"region": list("AABBC"),
                   "revenue": [100, 200, 300, 400, 500],
                   "flag": [0]*5})

df[df.revenue > 250]["flag"] = 1   # ChainedAssignmentError (a *Warning*)
df.flag.sum()                      # 0  — expected 3
```

Two `__getitem__` calls means pandas builds an intermediate object, writes into it, and discards it. Verified on pandas 3.0.5: 0 of 3 rows updated. The same trap with the operands swapped (`df["flag"][df.revenue > 250] = 1`) and with `.loc` in the middle (`df.loc[df.revenue > 250]["flag"] = 7`) also updates nothing.

The fix is one indexing call, with rows and columns in the same `.loc`:

```python
df.loc[df.revenue > 250, "flag"] = 1
df.flag.sum()                      # 3
```

**Why this bites in migration.** `ChainedAssignmentError` subclasses `Warning`, so it never halts a run. Under legacy pandas the old `SettingWithCopyWarning` was genuinely ambiguous — the write sometimes landed, depending on whether the slice happened to be a view. Pipelines written against that behaviour can silently stop applying a correction after upgrade, and a count that drops from 3 to 0 looks like a data change, not a library change.

The second break is slice independence. A filtered or column-subset frame is now always detached from its parent:

```python
sub = df[df.revenue > 250]
sub["flag"] = 1
sub.flag.sum(), df.flag.sum()      # (3, 0)
```

So a helper that mutates a frame handed to it still affects the caller when passed `df`, but is a no-op when passed `df[mask]`.

**What to do before upgrading:** grep for `\]\[` adjacency in the codebase, and make the warning fatal in your test suite so CI catches the rest. Set it in `conftest.py`:

```python
import warnings, pandas as pd
warnings.filterwarnings("error", category=pd.errors.ChainedAssignmentError)
```

Note that the command-line form `-W error::pandas.errors.ChainedAssignmentError` does *not* work — Python cannot resolve the category before `pandas` is imported, so the filter is silently dropped and the warning stays non-fatal. Plain `-W error` does catch it, at the cost of every other warning. Finally, treat a filtered frame you intend to keep and mutate as an explicit `.copy()` rather than relying on what pandas decides underneath.

## 10:02 - [ML & AI] `Adam(weight_decay=...)` Is Not Weight Decay: The Regularizer That Scales Backwards

With plain SGD, an L2 penalty and weight decay are the same thing. Adding `λ/2·‖w‖²` to the loss adds `λw` to the gradient, so the update becomes:

```
w ← w − η(g + λw)  =  w − ηg − ηλw
```

The penalty's effect falls out as a clean, uniform shrink toward zero. People generalized from this and assumed it holds for any optimizer. It does not hold for Adam.

**Adam normalizes the gradient per parameter.** Its update divides by the running RMS of recent gradients, `v̂`:

```
w ← w − η · m̂ / (√v̂ + ε)
```

If you fold `λw` into `g`, it goes through that same division. The shrink actually applied to parameter *i* is `ηλwᵢ / (√v̂ᵢ + ε)` — **inversely proportional to that parameter's gradient magnitude**. Parameters with large, noisy gradients get barely regularized; quiet parameters get hammered. That is exactly backwards from the intent, and it couples your regularization strength to optimizer state you never chose.

**A worked case.** `η=1e-3`, `λ=0.01`, two parameters both sitting at `w=1.0`. Param A has `√v̂=0.1`; param B has `√v̂=10`.

| | coupled L2 (`Adam`) | decoupled (`AdamW`) |
|---|---|---|
| A | `1e-3·0.01·1/0.1` = **1e-4** | 1e-5 |
| B | `1e-3·0.01·1/10` = **1e-6** | 1e-5 |

A 100× spread in effective regularization between two identically-valued weights.

**AdamW** applies the decay outside the adaptive term:

```
w ← w − η · m̂/(√v̂ + ε) − η · λ · w
```

Uniform again. In PyTorch, `torch.optim.Adam(weight_decay=λ)` is the coupled version; `AdamW` is the fix — and they are different algorithms, not aliases.

**Two things to do:**

1. Use `AdamW`, and **re-tune λ when you switch**. Decoupled decay bites much harder, so typical AdamW values (0.01–0.1) are orders of magnitude above the `1e-4`-ish L2 people carried over from Adam.
2. Exclude biases and norm parameters. They have one degree of freedom per channel and shrinking them just fights the layer:

```python
decay, no_decay = [], []
for n, p in model.named_parameters():
    if not p.requires_grad:
        continue
    (no_decay if p.ndim <= 1 or n.endswith(".bias") else decay).append(p)

opt = torch.optim.AdamW(
    [{"params": decay,    "weight_decay": 0.01},
     {"params": no_decay, "weight_decay": 0.0}],
    lr=3e-4,
)
```

The `p.ndim <= 1` test catches LayerNorm/BatchNorm weights and biases together — every 1-D parameter in a standard transformer is one or the other.

## 15:03 - [Crypto & Business] The Cash Conversion Cycle: Why a Profitable Company Needs a Loan to Grow

Profit tells you whether a sale was worth making. The **cash conversion cycle (CCC)** tells you how long your money is trapped before that sale turns back into cash. Three components, all in days:

- **DIO** = Inventory ÷ COGS × 365 — days your money sits as stuff on a shelf
- **DSO** = Accounts Receivable ÷ Revenue × 365 — days customers hold your money after delivery
- **DPO** = Accounts Payable ÷ COGS × 365 — days you hold your suppliers' money

**CCC = DIO + DSO − DPO.**

### Worked example

A distributor does $12M revenue, $8M COGS. Balance sheet: inventory $1.6M, AR $1.8M, AP $0.9M.

- DIO = 1.6 ÷ 8 × 365 = **73 days**
- DSO = 1.8 ÷ 12 × 365 = **55 days**
- DPO = 0.9 ÷ 8 × 365 = **41 days**
- **CCC = 73 + 55 − 41 = 87 days**

Working capital tied up = 1.6 + 1.8 − 0.9 = **$2.5M**.

Now grow 40%. Those balances scale with volume, so working capital goes to ~$3.5M. Growing consumed **$1.0M of cash** this year — cash the income statement never mentions, because it is sitting in a warehouse and in customers' pockets. This is exactly why fast-growing, genuinely profitable companies draw on a credit line.

### The levers, priced

Each day removed frees roughly one day of the relevant flow:

- DSO 55 → 40 (net-30 terms, autopay, invoicing on ship date not month-end): 15 × ($12M ÷ 365) = **$493K**
- DIO 73 → 60 (kill slow SKUs, tighter reorder points): 13 × ($8M ÷ 365) = **$285K**
- DPO 41 → 55 (renegotiated terms, not late payment): 14 × ($8M ÷ 365) = **$307K**

Total ≈ **$1.08M** — the entire growth need, self-financed, instead of a line of credit at 9% (~$97K/year in interest).

### The trap

Stretching DPO by simply paying late usually costs more than it saves. Forgoing a 2/10 net 30 discount to hold cash 20 extra days costs 2 ÷ 98 = 2.04% per 20 days ≈ **37% annualized** — far above any borrowing rate. Negotiate terms; don't just pay slowly.

Some models run a *negative* CCC: a restaurant collects instantly (DSO ≈ 1), holds 7 days of food, pays suppliers in 30 → CCC = −22 days. Growth there generates cash instead of consuming it.

## 19:02 - [Wildcard] Split-Horizon DNS: Why Your Self-Hosted Service Works on Cellular but Not on Your Own Wi-Fi

You point `nas.example.com` at your home IP, open port 443, and it loads perfectly from your phone on LTE. Then you walk in the front door, join Wi-Fi, and it times out. Nothing is broken — you have hit **NAT hairpinning**.

From inside, DNS hands your laptop the router's *public* WAN address. The packet leaves for an IP that belongs to the router you just left, so the router must turn it around, rewrite both source and destination, and send it back inside. Many consumer routers simply will not do that (or do it only for some port ranges), and the connection dies with no error worth reading.

**Diagnose it in two commands.** Compare what each resolver answers:

```bash
dig +short nas.example.com                 # your LAN resolver
dig +short nas.example.com @1.1.1.1        # public view
```

A public IP from the first command is the smoking gun. Confirm the service itself is fine by bypassing DNS entirely:

```bash
curl -sv --resolve nas.example.com:443:192.168.1.50 https://nas.example.com
```

If that succeeds and the hostname fails, it is routing, not the app.

**The fix is split-horizon DNS**: let the same name resolve to the LAN IP for clients inside, and the public IP for everyone else. Traffic then never leaves the subnet. In Pi-hole or any dnsmasq-backed resolver:

```
# /etc/dnsmasq.d/99-local.conf
address=/nas.example.com/192.168.1.50
```

Unbound wants a stub zone instead, because it validates DNSSEC and will reject a bare override:

```
local-zone: "example.com." transparent
local-data: "nas.example.com. A 192.168.1.50"
```

Two things bite people afterward. First, use a **real domain you own**, not `.local` (reserved for mDNS) or an invented TLD — you need a public CA to issue the certificate. Second, issue that certificate over **DNS-01**, not HTTP-01: DNS-01 proves ownership via a TXT record, so it works for a host that is never reachable from the internet at all.

That last point is the real payoff. Split-horizon plus DNS-01 gets you valid TLS on services you never expose publicly — no port forwarding, no self-signed warnings.
