## 00:02 - [Data Engineering] Airflow XCom: Pass References, Not DataFrames

XCom ("cross-communication") is how Airflow tasks hand values to each other — and the single most common way teams quietly wreck their scheduler. The reason is in the storage: every XCom value is serialized to JSON and written as a row in the `xcom` table of the **metadata database**, the same database the scheduler hammers hundreds of times per second.

That table is not a data channel. The value column is a `LargeBinary`, which on MySQL maps to a `BLOB` capped at **64 KB** — so a DataFrame return blows up with a truncation error. On Postgres the cap is ~1 GB, which is worse: it *works*, and you only find out months later when the metadata DB is 300 GB and task scheduling has gone slow.

The TaskFlow API makes the mistake easy, because returning a value pushes an XCom implicitly:

```python
@task
def extract() -> pd.DataFrame:          # BAD: whole frame into the metadata DB
    return pd.read_sql(QUERY, conn)

@task
def extract(ds: str) -> str:            # GOOD: push the pointer
    df = pd.read_sql(QUERY, conn)       # `ds` is injected from the task context
    uri = f"s3://lake/staging/orders/{ds}/part.parquet"
    df.to_parquet(uri, index=False)
    return uri

@task
def transform(uri: str):
    df = pd.read_parquet(uri)
    ...

transform(extract())
```

Rule of thumb: XCom carries **control-plane** data — a path, a row count, a watermark, a list of partition keys. The data itself lives in object storage or the warehouse.

When you genuinely need bigger payloads, don't hand-roll it — configure an object-storage XCom backend, which transparently offloads values above a threshold and leaves small ones in the DB:

```ini
[core]
xcom_backend = airflow.providers.common.io.xcom.backend.XComObjectStorageBackend

[common.io]
xcom_objectstorage_path = s3://my-bucket/xcom
xcom_objectstorage_threshold = 1048576   # default -1 = never offload
xcom_objectstorage_compression = zstd
```

Two related gotchas:

- Suppress unwanted pushes with `do_xcom_push=False` on operators whose return value you never read (`BashOperator` pushes its last stdout line by default).
- Dynamic task mapping pulls its fan-out list from XCom, so a huge list is both an XCom and a mapping problem — `max_map_length` defaults to 1024 and the DAG fails hard above it. Map over partition keys, not rows.

## 05:03 - [Data Analytics] Outer Join Filters: The WHERE Clause That Silently Makes It an INNER JOIN

You write a `LEFT JOIN` specifically so customers with zero orders still appear. Then you add a date filter in `WHERE` and they vanish — and the query returns no error.

```sql
-- 5,000 customers in the table. This returns 1,284 rows.
SELECT c.customer_id, COUNT(*) AS q4_orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_date >= DATE '2026-10-01'
GROUP BY c.customer_id;
```

`WHERE` runs *after* the join. For a customer with no Q4 orders, the join emits a NULL-extended row, and `NULL >= DATE '2026-10-01'` evaluates to UNKNOWN — not true — so `WHERE` discards it. A filter on the optional side in `WHERE` degrades the outer join to an inner join. Move the predicate into `ON`, where it restricts *which rows match* instead of which rows survive:

```sql
-- 5,000 rows, as intended.
SELECT c.customer_id, COUNT(o.order_id) AS q4_orders
FROM customers c
LEFT JOIN orders o
       ON o.customer_id = c.customer_id
      AND o.order_date >= DATE '2026-10-01'
GROUP BY c.customer_id;
```

### The second bug hiding in the same query

Note the aggregate changed too. `COUNT(*)` counts rows, and the NULL-extended row *is* a row — so every zero-order customer reports `q4_orders = 1`. `COUNT(o.order_id)` ignores NULLs and correctly returns 0. Same class of trap for sums: `SUM(o.amount)` over no matching rows returns NULL, not 0, so wrap it — `COALESCE(SUM(o.amount), 0)`.

### Rules that hold

- Predicate on the **optional** (right) table → put it in `ON`.
- Predicate on the **preserved** (left) table → put it in `WHERE`. In `ON` it does nothing useful: left rows are preserved regardless, they just stop matching.
- A `WHERE` clause on the optional table is correct in exactly one case: `WHERE o.order_id IS NULL`, the deliberate anti-join for "customers who ordered nothing."

Cheap verification: the row count of a `LEFT JOIN` result must be **≥** the left table's row count. If it came back smaller, a `WHERE` predicate is eating your preserved rows. Pair that with `COUNT(*)` vs `COUNT(fk)` on any outer join and you catch both bugs in one pass.

## 10:04 - [ML & AI] Your Test Metric Has an Error Bar, and Recall's Is Enormous

A test set is a *sample*. The metric you compute on it is an estimate with sampling error, but it prints as `0.8412` — fifteen digits of false confidence. Most "model B beats model A" decisions are made inside the noise.

### The closed-form case

Accuracy is a proportion, so its standard error is binomial:

```
SE = sqrt(p(1-p)/n)
```

At `p = 0.84`, `n = 2000`: `SE = sqrt(0.1344/2000) = 0.0082`, so the 95% CI is `0.84 ± 1.6pp` → **[0.824, 0.856]**. A rival model at 0.831 is not distinguishable.

### Why recall is far worse than you think

The `n` in that formula is the number of cases the metric is actually computed over. For recall, that's the **positive count**, not the row count. A fraud set with 3% prevalence and 2000 rows has 60 positives:

`SE = sqrt(0.8 × 0.2 / 60) = 0.0516` → recall `0.80 ± 10.1pp` → **[0.70, 0.90]**.

Your recall is known to within ten points. No amount of threshold tuning on that set means anything.

### For AUC, F1, and the rest: bootstrap the *difference*

These have no clean closed form. And comparing two separately-computed CIs is the classic error — overlapping intervals do *not* imply no difference. Resample rows once and score both models on the same rows, which cancels the shared difficulty of each draw:

```python
import numpy as np
from sklearn.metrics import roc_auc_score

def paired_bootstrap(y, p_a, p_b, metric=roc_auc_score, n_boot=2000, seed=0):
    rng, n, out = np.random.default_rng(seed), len(y), []
    for _ in range(n_boot):
        idx = rng.integers(0, n, n)          # SAME rows for both models
        if len(np.unique(y[idx])) < 2:       # AUC undefined on a one-class draw
            continue
        out.append(metric(y[idx], p_b[idx]) - metric(y[idx], p_a[idx]))
    d = np.array(out)
    return d.mean(), np.percentile(d, [2.5, 97.5])
```

If the returned interval straddles 0, you have not shown B is better. Pairing also makes the interval roughly 2× tighter than resampling the two models independently (the more alike the models, the bigger the gain), so it is both the correct test and the one most able to detect a real effect.

**Practical rules.** Report every headline metric with a CI. Size test sets by minority-class count, not rows. Treat gains smaller than the interval as a coin flip — and note that reusing one test set across 40 tuning rounds means your best score is partly a draw you selected for.

## 15:05 - [Crypto & Business] Smart Accounts (ERC-4337): Moving Wallet Rules Out of the Protocol

A normal Ethereum account (an EOA) has rules burned into the protocol: exactly one secp256k1 key, a strictly sequential nonce, and it must hold ETH to pay its own gas. Lose the key and the funds are gone. There is no "require two signatures," no daily limit, no recovery.

ERC-4337 moves those rules into a contract **without changing the protocol**. Instead of a transaction, you sign a *UserOperation* and hand it to a **bundler**. The bundler batches many of them into one call to the **EntryPoint**, a single permissionless contract. EntryPoint then calls your account twice: `validateUserOp` (is this authorized?) and then the execution call.

That first hook is the whole point. `validateUserOp` is code you choose, so it can accept a passkey (secp256r1, i.e. Face ID) instead of a seed phrase, require 2-of-3 signers, enforce a $500/day cap, honor a **session key** scoped to one contract for 24 hours, or allow social recovery behind a 7-day timelock.

**Paymasters** break the other constraint. A paymaster pre-deposits ETH at the EntryPoint; its `validatePaymasterUserOp` approves your op, gas is paid from that deposit, and a `postOp` callback pulls, say, USDC from you instead. That is how an app onboards someone holding zero ETH.

The cost is real. An EOA sending ETH costs 21,000 gas. The same send through a 4337 account runs roughly 100k–130k gas, plus a one-time ~200–400k to deploy the account (folded into the first op via `initCode`). At 20 gwei on L1 that is ~0.002 ETH versus ~0.0004 — which is why nearly all adoption is on L2s, where the difference is a rounding error. EIP-7702 (Pectra) offers a shortcut: an existing EOA can delegate to contract code and keep its address.

New risks, though: a bug in your `validateUserOp` means *anyone* can drain the account, and a UserOperation renders far less legibly than a transaction — session keys are standing permissions with the same failure mode as token approvals.
