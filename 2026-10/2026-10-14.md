## 00:02 - [Data Engineering] Airflow XCom: Pass References, Not DataFrames

XCom ("cross-communication") is how Airflow tasks hand values to each other — and the single most common way teams quietly wreck their scheduler. The reason is in the storage: every XCom value is serialized to JSON and written as a row in the `xcom` table of the **metadata database**, the same database the scheduler hammers hundreds of times per second.

That table is not a data channel. The value column is a `LargeBinary`, which on MySQL maps to a `BLOB` capped at **64 KB** — so a DataFrame return blows up with a truncation error. On Postgres the cap is ~1 GB, which is worse: it *works*, and you only find out months later when the metadata DB is 300 GB and task scheduling has gone slow.

The TaskFlow API makes the mistake easy, because returning a value pushes an XCom implicitly:

```python
@task
def extract() -> pd.DataFrame:          # BAD: whole frame into the metadata DB
    return pd.read_sql(QUERY, conn)

@task
def extract(ds: str) -> str:            # GOOD: push the pointer
    df = pd.read_sql(QUERY, conn)       # `ds` is injected from the task context
    uri = f"s3://lake/staging/orders/{ds}/part.parquet"
    df.to_parquet(uri, index=False)
    return uri

@task
def transform(uri: str):
    df = pd.read_parquet(uri)
    ...

transform(extract())
```

Rule of thumb: XCom carries **control-plane** data — a path, a row count, a watermark, a list of partition keys. The data itself lives in object storage or the warehouse.

When you genuinely need bigger payloads, don't hand-roll it — configure an object-storage XCom backend, which transparently offloads values above a threshold and leaves small ones in the DB:

```ini
[core]
xcom_backend = airflow.providers.common.io.xcom.backend.XComObjectStorageBackend

[common.io]
xcom_objectstorage_path = s3://my-bucket/xcom
xcom_objectstorage_threshold = 1048576   # default -1 = never offload
xcom_objectstorage_compression = zstd
```

Two related gotchas:

- Suppress unwanted pushes with `do_xcom_push=False` on operators whose return value you never read (`BashOperator` pushes its last stdout line by default).
- Dynamic task mapping pulls its fan-out list from XCom, so a huge list is both an XCom and a mapping problem — `max_map_length` defaults to 1024 and the DAG fails hard above it. Map over partition keys, not rows.
