## 00:04 - [Data Engineering] SCD Type 6: Reporting "As-Was" and "As-Is" From One Dimension

A Type 2 dimension answers *"what was the rep's territory when the deal closed?"* Analysts then ask the opposite question — *"show me last year's sales under the **current** territory map"* — and a pure Type 2 dim cannot do it. Every historical row carries the old territory, so a reorg scatters last year's revenue across regions that no longer exist.

Type 6 ("1 + 2 + 3" hybrid) solves it by putting **both** values on every version row:

| rep_sk | rep_id | territory_as_was | territory_current | valid_from | valid_to | is_current |
|---|---|---|---|---|---|---|
| a1f… | 42 | West | Pacific | 2024-01-01 | 2025-06-30 | false |
| b7c… | 42 | Pacific | Pacific | 2025-07-01 | 9999-12-31 | true |

`rep_id` is the **durable key** — stable across versions. `rep_sk` is the version key the fact table stores.

Build it from a snapshot, then broadcast the current row's values back over all versions:

```sql
-- models/marts/dim_sales_rep.sql  (materialized: table)
with versions as (select * from {{ ref('snap_sales_rep') }}),

latest as (
    select rep_id, territory as territory_current
    from versions
    where dbt_valid_to is null
)

select
    {{ dbt_utils.generate_surrogate_key(['v.rep_id','v.dbt_valid_from']) }} as rep_sk,
    v.rep_id                                as rep_id,
    v.territory                             as territory_as_was,
    l.territory_current,
    v.dbt_valid_from                        as valid_from,
    coalesce(v.dbt_valid_to, timestamp '9999-12-31') as valid_to,
    v.dbt_valid_to is null                  as is_current
from versions v
join latest l using (rep_id)
```

Facts join on `rep_sk` as usual; the analyst chooses the column, and `GROUP BY territory_current` restates history instantly with no re-keying.

**Gotchas worth knowing before you ship it:**

- The `*_current` columns are Type 1 — a reorg rewrites *every* historical row. Materialize the dim as `table`, or `incremental` with `unique_key='rep_sk'` and a `merge` strategy. Append-only incremental will serve stale current values forever.
- Only add `*_current` for attributes analysts actually re-cut by (territory, segment, manager). Doing all 40 columns doubles the dim for no benefit.
- Carry `rep_id` into the fact table too. Durable-key joins let you pivot on current attributes without walking the version chain.
- Test it: `rep_sk` unique, `territory_current` not null, and exactly one `is_current` row per `rep_id`.

## 05:03 - [Data Analytics] Top-N Per Group: Why `LATERAL` Beats `ROW_NUMBER()` by 80x

"The 3 most recent orders per customer" is the most common analytics query nobody tunes. The reflex is a window function:

```sql
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (
           PARTITION BY customer_id ORDER BY ordered_at DESC) AS rn
  FROM orders o            -- 50M rows
) t WHERE rn <= 3;
```

That plan has no choice but to read all 50M rows and sort them, because `rn` can't be evaluated until the partition is fully materialized. The `WHERE rn <= 3` is a filter applied *after* the work, not a limit pushed into it. You discard 99.99% of the rows you just sorted.

`LATERAL` inverts the loop — iterate the 200k customers and fetch 3 rows each:

```sql
SELECT c.customer_id, o.order_id, o.ordered_at, o.amount
FROM customers c
LEFT JOIN LATERAL (
  SELECT order_id, ordered_at, amount
  FROM orders
  WHERE customer_id = c.customer_id   -- correlation: legal only in LATERAL
  ORDER BY ordered_at DESC
  LIMIT 3
) o ON true;
```

With an index on `orders (customer_id, ordered_at DESC)`, each subquery is an index seek that stops after 3 rows. You touch ~600k rows instead of 50M. On Postgres that is routinely 40s → 0.5s. SQL Server spells it `OUTER APPLY`; Snowflake and BigQuery support `LEFT JOIN LATERAL`/`UNNEST` correlation but optimize it as a rewrite, so measure rather than assume.

**Two traps.**

*The join type.* `JOIN LATERAL (...) ON true` is an **inner** join. A customer with zero orders disappears, so `COUNT(*)` on your result silently becomes "customers who have ordered." Use `LEFT JOIN LATERAL ... ON true` unless you mean to filter.

*The index is the whole trick.* Without `(customer_id, ordered_at DESC)`, LATERAL runs 200k separate sorts and is slower than the window function. Check for a seek in the plan, not a scan.

**When the window function still wins:** N is large relative to group size (top 500 of 600), groups are few and huge, or you need other window results from the same pass anyway. Rule of thumb — many small groups favor LATERAL; few large groups favor `ROW_NUMBER()`.

## 10:04 - [ML & AI] Prompt Caching Economics: The Breakpoint That Costs More Than No Cache

Prompt caching is a **prefix match**. The cache key is the exact bytes of the rendered prompt up to each `cache_control` breakpoint, and render order is `tools` → `system` → `messages`. One changed byte at position N invalidates every breakpoint at or after N.

The pricing has three rates, as multiples of base input cost: a **cache write** is 1.25× (5-minute TTL) or 2× (1-hour TTL), and a **cache read** is ~0.1× (0.05× on Claude Opus 5.5, 0.025× on Fable 5.1). For N requests sharing a prefix:

| | 5-min TTL | 1-hour TTL | Uncached |
|---|---|---|---|
| N=1 | 1.25 | 2.0 | 1.0 |
| N=2 | 1.35 | 2.1 | 2.0 |
| N=3 | 1.45 | 2.2 | 3.0 |

So the 5-minute TTL breaks even at two requests, the 1-hour TTL at three. A read also **refreshes the entry's timer for free**, so continuous traffic keeps a 5-minute entry alive indefinitely — the 1-hour TTL buys nothing there except the doubled write. Only a start-to-start gap of 5–60 minutes justifies it.

**The expensive mistake.** Take a 50K-token shared system prompt, 200 requests/hour on Opus 5.5 ($4/MTok in, $0.20/MTok read):

```python
# WRONG: breakpoint lands after the per-request question
messages=[{"role": "user", "content": [
    {"type": "text", "text": shared_context},
    {"type": "text", "text": question,
     "cache_control": {"type": "ephemeral"}},   # unique every request
]}]
```

Every request writes a distinct entry and reads nothing: 10M tokens × $5/MTok = **$50/hr** — *worse than the $40 of not caching at all*. Move the marker to the end of the shared portion and you pay one write plus 199 reads ≈ **$2.24/hr**.

**Verify, don't assume.** Check `usage.cache_read_input_tokens`; zero across identical prefixes means a silent invalidator — `datetime.now()` in the system prompt, `json.dumps` without `sort_keys=True`, a per-user tool list. Note `input_tokens` is only the *uncached remainder*; total prompt size is the sum of all three fields.

Two silent floors: max **4** breakpoints per request, and a prefix below the model's minimum (512 tokens on current models, but 4096 on Opus 4.6) simply won't cache — no error, just `cache_creation_input_tokens: 0`.
