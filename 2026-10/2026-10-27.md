## 00:03 - [Data Engineering] Optimistic Concurrency in Delta and Iceberg: Why Your Compaction Job Keeps Losing

Delta and Iceberg have no lock. Every writer reads a snapshot, writes new data files, then tries to atomically claim the next table version. If someone else claimed it first, the loser re-reads the new snapshot, checks whether the other commit invalidated its assumptions, and either retries or throws. Conflict detection is file-level, not row-level — and that is where the surprises live.

**The classic Delta failure:** a MERGE that doesn't tell Delta which partitions it touched.

```sql
-- Conflicts with ANY concurrent append to the table
MERGE INTO events t
USING updates s ON t.event_id = s.event_id
WHEN MATCHED THEN UPDATE SET *;
```

Delta must assume the merge read every partition, so a harmless append to `dt = '2026-10-27'` raises `ConcurrentAppendException`. Push the partition predicate into the ON clause and the conflict window shrinks to that partition:

```sql
MERGE INTO events t
USING updates s
  ON t.event_id = s.event_id
 AND t.dt = '2026-10-26'          -- partition filter, in ON, not WHERE
WHEN MATCHED THEN UPDATE SET *;
```

**Iceberg's equivalent knob is the isolation level.** `serializable` (the default) fails your UPDATE/DELETE/MERGE if *any* new file landed in the scanned partitions. `snapshot` only fails if files you actually planned to rewrite were deleted underneath you:

```sql
ALTER TABLE events SET TBLPROPERTIES (
  'write.merge.isolation-level' = 'snapshot',
  'commit.retry.num-retries'    = '10',   -- default is 4
  'commit.retry.min-wait-ms'    = '200'
);
```

**Compaction is the usual victim.** `rewrite_data_files` can run for an hour, then lose the commit to a streaming writer that took three seconds — and throw away all of it. Enable partial progress so it commits in batches instead of betting everything on one commit:

```sql
CALL catalog.system.rewrite_data_files(
  table => 'db.events',
  options => map(
    'partial-progress.enabled', 'true',
    'partial-progress.max-commits', '20',
    'max-concurrent-file-group-rewrites', '4'
  )
);
```

**Rules that hold on both engines:** one writer per partition wherever you can arrange it; always pass partition predicates so the engine can narrow the conflict set; schedule maintenance against partitions the live writers have moved past; and treat commit retries as configuration, not as a bug to catch. Schema changes are the exception — `MetadataChangedException` and Iceberg's equivalent are never safely retryable, so run DDL when writers are quiet.

## 05:04 - [Data Analytics] FLOAT Money Columns: The Sum That Changes Between Two Runs of the Same Query

Two dashboards query the same table, same filters, and report revenue three cents apart. Nobody changed the SQL. The cause is usually that the amount column is `DOUBLE`/`FLOAT`, and binary floating point cannot represent most decimal cents exactly.

```python
0.1 + 0.2                      # 0.30000000000000004
(0.1 + 0.2) == 0.3             # False
```

Error accumulates with row count. Summing 1,000,000 rows of `0.07`:

```python
vals = [0.07] * 1_000_000
s = 0.0
for v in vals: s += v
s          # 70000.00000019418, not 70000.00
```

Only 0.0000002 off — invisible until someone reconciles against finance, or a `HAVING total = 70000` filter drops the row.

The nastier property is **order dependence**. Float addition is not associative, so the same multiset summed in a different order gives a different answer:

```python
vals = [1e9] + [0.01] * 100_000
sum_big_first    # 1000000999.9990463
sum_small_first  # 1000001000.0        (diff: 0.00095)
```

Large values absorb small ones. Warehouses sum in parallel and merge partial aggregates in whatever order threads finish, so **the same query can return different trailing digits on re-run** — and a differently-ordered join or a changed cluster size shifts it again. That is the real source of "the number moved but nothing changed."

**Fixes:**

```sql
-- Store money as exact decimal, cast once in staging
SELECT CAST(amount_raw AS DECIMAL(18,2)) AS amount  -- NUMERIC in Postgres
FROM raw.orders;

-- Never equality-filter or join on a float
WHERE ABS(total - 70000) < 0.005   -- not: WHERE total = 70000
```

`DECIMAL(18,2)` holds ~1.7 quadrillion dollars at cent precision — enough. Keep enough scale for intermediate math (unit price × quantity × tax wants `DECIMAL(18,6)`), and round exactly once, at presentation. Rounding twice compounds: note that Python and most warehouses use banker's rounding, so `round(2.675, 2)` is `2.67`, not `2.68`. If a metric must stay float (latency, ratios), compare with a tolerance and document it rather than chasing phantom drift.
