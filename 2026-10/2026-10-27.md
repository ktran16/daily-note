## 00:03 - [Data Engineering] Optimistic Concurrency in Delta and Iceberg: Why Your Compaction Job Keeps Losing

Delta and Iceberg have no lock. Every writer reads a snapshot, writes new data files, then tries to atomically claim the next table version. If someone else claimed it first, the loser re-reads the new snapshot, checks whether the other commit invalidated its assumptions, and either retries or throws. Conflict detection is file-level, not row-level — and that is where the surprises live.

**The classic Delta failure:** a MERGE that doesn't tell Delta which partitions it touched.

```sql
-- Conflicts with ANY concurrent append to the table
MERGE INTO events t
USING updates s ON t.event_id = s.event_id
WHEN MATCHED THEN UPDATE SET *;
```

Delta must assume the merge read every partition, so a harmless append to `dt = '2026-10-27'` raises `ConcurrentAppendException`. Push the partition predicate into the ON clause and the conflict window shrinks to that partition:

```sql
MERGE INTO events t
USING updates s
  ON t.event_id = s.event_id
 AND t.dt = '2026-10-26'          -- partition filter, in ON, not WHERE
WHEN MATCHED THEN UPDATE SET *;
```

**Iceberg's equivalent knob is the isolation level.** `serializable` (the default) fails your UPDATE/DELETE/MERGE if *any* new file landed in the scanned partitions. `snapshot` only fails if files you actually planned to rewrite were deleted underneath you:

```sql
ALTER TABLE events SET TBLPROPERTIES (
  'write.merge.isolation-level' = 'snapshot',
  'commit.retry.num-retries'    = '10',   -- default is 4
  'commit.retry.min-wait-ms'    = '200'
);
```

**Compaction is the usual victim.** `rewrite_data_files` can run for an hour, then lose the commit to a streaming writer that took three seconds — and throw away all of it. Enable partial progress so it commits in batches instead of betting everything on one commit:

```sql
CALL catalog.system.rewrite_data_files(
  table => 'db.events',
  options => map(
    'partial-progress.enabled', 'true',
    'partial-progress.max-commits', '20',
    'max-concurrent-file-group-rewrites', '4'
  )
);
```

**Rules that hold on both engines:** one writer per partition wherever you can arrange it; always pass partition predicates so the engine can narrow the conflict set; schedule maintenance against partitions the live writers have moved past; and treat commit retries as configuration, not as a bug to catch. Schema changes are the exception — `MetadataChangedException` and Iceberg's equivalent are never safely retryable, so run DDL when writers are quiet.

## 05:04 - [Data Analytics] FLOAT Money Columns: The Sum That Changes Between Two Runs of the Same Query

Two dashboards query the same table, same filters, and report revenue three cents apart. Nobody changed the SQL. The cause is usually that the amount column is `DOUBLE`/`FLOAT`, and binary floating point cannot represent most decimal cents exactly.

```python
0.1 + 0.2                      # 0.30000000000000004
(0.1 + 0.2) == 0.3             # False
```

Error accumulates with row count. Summing 1,000,000 rows of `0.07`:

```python
vals = [0.07] * 1_000_000
s = 0.0
for v in vals: s += v
s          # 70000.00000019418, not 70000.00
```

Only 0.0000002 off — invisible until someone reconciles against finance, or a `HAVING total = 70000` filter drops the row.

The nastier property is **order dependence**. Float addition is not associative, so the same multiset summed in a different order gives a different answer:

```python
vals = [1e9] + [0.01] * 100_000
sum_big_first    # 1000000999.9990463
sum_small_first  # 1000001000.0        (diff: 0.00095)
```

Large values absorb small ones. Warehouses sum in parallel and merge partial aggregates in whatever order threads finish, so **the same query can return different trailing digits on re-run** — and a differently-ordered join or a changed cluster size shifts it again. That is the real source of "the number moved but nothing changed."

**Fixes:**

```sql
-- Store money as exact decimal, cast once in staging
SELECT CAST(amount_raw AS DECIMAL(18,2)) AS amount  -- NUMERIC in Postgres
FROM raw.orders;

-- Never equality-filter or join on a float
WHERE ABS(total - 70000) < 0.005   -- not: WHERE total = 70000
```

`DECIMAL(18,2)` holds ~1.7 quadrillion dollars at cent precision — enough. Keep enough scale for intermediate math (unit price × quantity × tax wants `DECIMAL(18,6)`), and round exactly once, at presentation. Rounding twice compounds: note that Python and most warehouses use banker's rounding, so `round(2.675, 2)` is `2.67`, not `2.68`. If a metric must stay float (latency, ratios), compare with a tolerance and document it rather than chasing phantom drift.

## 10:03 - [ML & AI] Delayed Labels: Your Training Set Is Biased Toward Fast Outcomes

Fraud chargebacks arrive 20–120 days after the transaction. Loan defaults take months. Churn is only knowable after the renewal date passes. Yet the query that builds the training set is almost always `WHERE label IS NOT NULL`, and that single clause introduces a bias most people never look for.

The problem isn't missing labels — it's that *recency and label availability are correlated*. A transaction from last week is labeled only if the chargeback happened unusually fast. Everything else looks negative, because nothing has come back yet.

**Worked example.** True fraud rate is 1%. Chargebacks arrive on this maturity curve: 41% by day 30, 76% by day 60, 95% by day 90. Snapshot at day 35 and you observe 0.41% positives. Treat the unlabeled rows as negatives and you've silently relabeled 0.59% of transactions — 59% of all fraud — as legitimate. The model trains on a base rate 2.4× too low, so every predicted probability is systematically too small, and the mislabeled rows are specifically the *slow* frauds: the hard ones.

**The fix is a maturity cutoff.** Measure the curve, then only train on cohorts old enough to be settled:

```python
import pandas as pd

df["days_to_label"] = (df.label_ts - df.event_ts).dt.days

# Of confirmed positives, what fraction has arrived by day d?
pos = df.dropna(subset=["label_ts"])
curve = pos.days_to_label.value_counts(normalize=True).sort_index().cumsum()
print(curve.reindex([30, 60, 90]))   # 0.41  0.76  0.95

MATURITY = 90
asof = df.event_ts.max()
train = df[df.event_ts <= asof - pd.Timedelta(days=MATURITY)].copy()
train["y"] = train.label_ts.notna().astype(int)   # now safe to impute negative
```

You pay for this in staleness: your freshest training data is three months old. That's the honest trade. If you need recency, reweight the immature cohort by its expected maturity, or switch to a survival model that treats unlabeled rows as *censored* rather than negative.

**The evaluation trap is worse.** If your test set also includes immature rows, measured recall is inflated — you're not penalized for missing frauds nobody has reported yet. Apply the same cutoff to the test split.

Re-measure the maturity curve quarterly. It moves when dispute policy, payment mix, or collections processes change — and when it moves, your cutoff is wrong.

## 15:07 - [Crypto & Business] Concentrated Liquidity: The 20× Fee Multiplier and the Bill That Comes With It

Uniswap v2 spread your liquidity across every price from zero to infinity. Almost all of it sat idle. v3-style concentrated liquidity lets you pick a range `[P_a, P_b]` and put the same capital to work only there — earning the same fee share with far less money at risk.

The capital-efficiency multiplier versus full range, at current price `P`:

```
2√P / (2√P − P/√P_b − √P_a)
```

ETH/USDC at $3,000:
- ±50% range (1500–4500): **4.2×**
- ±10% range (2700–3300): **20.4×**
- ±5% range (2850–3150): **40.5×**

A ±10% position earns roughly 20× the fees of the same dollars spread full-range — *while price stays inside the range*.

**What you pay.** Deposit $10,000 at $3,000 into the 2700–3300 range. The pool hands you a specific mix: 1.585 ETH + $5,244 USDC. As ETH rises, the pool sells your ETH; at $3,300 you hold $10,232 and **zero ETH**. Simply holding the original mix would be worth $10,476 — a $243 (2.43%) gap your fees must clear.

The asymmetry is the real lesson: cross the upper bound and you stop earning entirely, fully converted to stablecoins. If ETH continues to $4,000, your position stays frozen at $10,232 while holding would be $11,585 — a 13.5% gap, and it keeps widening. Downside mirrors it: at $2,400 you hold $8,227 of ETH versus $9,049 holding.

**The practical trade-off.** Tight ranges multiply fees and multiply the probability of exiting them. A ±5% range on an asset with 60% annualized volatility exits within days. Rebalancing restores fee income but realizes the divergence loss each time, and costs gas.

Rough screen before providing: estimate days-in-range from the asset's daily volatility, multiply expected fee APR by the efficiency factor, and compare against the divergence loss at your range boundaries. If the fee estimate doesn't beat that boundary number by a wide margin, the narrow range is a losing bet dressed as yield.
