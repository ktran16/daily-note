## 00:03 - [Data Engineering] The Transactional Outbox: Why Dual Writes Lose Events

Your service saves an order and publishes `order.created` to Kafka. Two systems, one request, no shared transaction:

```python
db.commit()                      # succeeded
producer.send("orders", event)   # process dies here
```

The order exists and no downstream system ever hears about it. Reverse the order and you get the opposite failure: an event for an order that rolled back. There is no ordering of these two calls that is safe — this is the **dual-write problem**, and retries don't fix it, because the crash can land between the commit and the retry loop.

**The fix: make the event part of the transaction.** Write it to an outbox table in the same database, in the same commit as the business change.

```sql
CREATE TABLE outbox (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  aggregate_type text NOT NULL,   -- 'order'      -> topic routing
  aggregate_id   text NOT NULL,   -- '1042'       -> partition key
  event_type     text NOT NULL,   -- 'order.created'
  payload        jsonb NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now()
);

BEGIN;
  INSERT INTO orders (id, customer_id, total) VALUES (1042, 77, 250.00);
  INSERT INTO outbox (aggregate_type, aggregate_id, event_type, payload)
  VALUES ('order', '1042', 'order.created',
          '{"order_id":1042,"customer_id":77,"total":250.00}');
COMMIT;
```

One atomic commit: either both rows land or neither does. A separate relay then tails the outbox and publishes. Use log-based CDC (Debezium reading the WAL), not a polling `SELECT ... WHERE published = false` loop — polling adds lag and contention:

```json
"transforms": "outbox",
"transforms.outbox.type": "io.debezium.transforms.outbox.EventRouter",
"transforms.outbox.route.by.field": "aggregate_type",
"transforms.outbox.table.field.event.key": "aggregate_id"
```

**Three things to get right:**

- **Consumers must be idempotent.** The relay guarantees at-least-once, so dedupe on `id` — the row's UUID is a natural idempotency key.
- **Ordering is per-key only.** Keying by `aggregate_id` keeps one order's events in sequence; there is no global order.
- **Prune the table.** Delete rows older than your CDC retention window on a schedule. In Postgres you can even `INSERT` then `DELETE` in the same transaction — logical decoding still emits the insert from the WAL, so the table stays empty.

**Why not just CDC the `orders` table directly?** Because that publishes your internal schema. Rename a column and every consumer breaks. The outbox payload is a deliberate, versioned contract you control, decoupled from how you happen to store the data today.
