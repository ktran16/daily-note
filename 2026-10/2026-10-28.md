## 00:03 - [Data Engineering] dbt Snapshot Hard Deletes: The Row That Stays "Current" Forever

A snapshot's job is to answer "what did this row look like on March 3rd?". The default `timestamp` strategy does that by comparing `updated_at` against the latest record and closing the old one out. But a hard delete at the source doesn't bump `updated_at` — the row simply stops appearing in the query. dbt sees nothing to compare, leaves `dbt_valid_to` as NULL, and that deleted customer stays joinable as the current version indefinitely. Every `WHERE dbt_valid_to IS NULL` downstream silently over-counts.

dbt 1.9 replaced the old `invalidate_hard_deletes: true` flag with a three-way config:

```yaml
snapshots:
  - name: snap_customers
    relation: source('crm', 'customers')
    config:
      unique_key: customer_id
      strategy: timestamp
      updated_at: updated_at
      hard_deletes: new_record   # ignore | invalidate | new_record
```

- `ignore` (default) — the bug above.
- `invalidate` — sets `dbt_valid_to` to the run timestamp for missing keys.
- `new_record` — inserts a tombstone row with `dbt_is_deleted = 'True'`, so the deletion itself is a dated event you can query.

**The trap:** anything other than `ignore` means *absent from the query = deleted*. If your snapshot SQL carries a filter — `WHERE region = 'US'`, or a well-meant `WHERE updated_at > dateadd(day, -7, current_date)` to make it cheap — every row outside that window gets invalidated on the next run. Snapshot the full source relation, unfiltered.

**When there's no reliable `updated_at`,** use the `check` strategy, which diffs column values instead:

```yaml
      strategy: check
      check_cols: ['status', 'plan_tier', 'credit_limit']
```

Be explicit about the columns. `check_cols: 'all'` means a new column added upstream rewrites history for every row, and any audit column like `_loaded_at` makes every run a change. Note also that NULL comparisons count as changes in both directions — a field flipping to NULL and back produces two versions.

The deeper point: snapshots capture history as it happens and cannot be backfilled. If a dimension matters, snapshot it *before* you need the history, not after someone asks.

## 05:04 - [Data Analytics] Histogram Bin Width: The Bimodal Distribution You Invented by Rounding

Someone asks for the distribution of order values, so you write `GROUP BY ROUND(order_total / 10) * 10` and ship a bar chart. That chart has two peaks. Change the `10` to a `25` and it has one. Nothing about the data changed — bin width is a free parameter, and you picked it by typing a round number.

**Trap 1: `ROUND` centers bins, it doesn't start them.** `ROUND(4/10)*10 = 0` and `ROUND(6/10)*10 = 10`, so the bin labeled `0` covers only `[0, 5)` while every other bin spans `[x-5, x+5)`. Your first bar is half-width and every label is shifted by half a bin. Use `FLOOR`:

```sql
-- bin labeled 20 means [20, 30), which is what a reader assumes
SELECT FLOOR(order_total / 10) * 10 AS bin_start, COUNT(*)
FROM orders GROUP BY 1 ORDER BY 1;
```

**Trap 2: bin edges land exactly where human-chosen values pile up.** Prices cluster at $9.99, $19.99, $49.99. A boundary at $10.00 puts the $9.99 mass in the bin below and the $10.00 mass in the bin above, splitting one real spike across two bars. Offset the edges (`FLOOR((order_total + 0.01) / 10)`) or bin on a transform, and check `SELECT order_total, COUNT(*) ... ORDER BY 2 DESC LIMIT 20` first to see if your data is spiky rather than continuous.

**Pick the width from the data.** Freedman–Diaconis: `h = 2 × IQR / n^(1/3)`. It scales with spread and shrinks as you get more rows, and it's robust to outliers in a way that range-based rules are not:

```sql
WITH p AS (
  SELECT 2 * (PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY order_total)
            - PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY order_total))
         / POWER(COUNT(*), 1.0/3) AS h
  FROM orders
)
SELECT FLOOR(order_total / h) * h AS bin_start, COUNT(*) AS orders
FROM orders CROSS JOIN p GROUP BY 1 ORDER BY 1;
```

With n = 100,000 and IQR = $42 (p25 $18, p75 $60), `n^(1/3)` ≈ 46.4, so h ≈ **$1.81** — round to $2. The $10 bins you'd have guessed are 5× too wide and smooth away structure that is actually there.

**Trap 3: `WIDTH_BUCKET(x, low, high, n)` returns `0` for `x < low` and `n+1` for `x >= high`.** Those are your tails, not errors. Filter them out and the chart silently drops every outlier while the total still looks plausible.

Always label the bin width on the chart, and put `p50 / p90 / p99` next to it. Quantiles don't move when someone changes a constant.

## 10:03 - [ML & AI] Isolation Forest: `contamination` Is a Threshold, Not an Estimate

Isolation Forest scores a point by how few random axis-parallel splits it takes to isolate it. Outliers sit in sparse regions, so they fall out of the tree early. The score normalizes the average path length `E(h(x))` against the expected depth of a random binary search tree:

```
s(x) = 2^(-E(h(x)) / c(n)),   c(n) = 2(ln(n-1) + γ) - 2(n-1)/n
```

With sklearn's default `max_samples='auto'` (= min(256, n)), `c(256) ≈ 10.24`. A point isolated at average depth 5 scores `2^(-5/10.24) = 0.713`; one at depth 10 scores `0.508`. Everything above ~0.5 is "easier to isolate than typical."

**The trap is `contamination`.** People read it as "I think about 5% of my data is anomalous." It is not a prior and it does not touch the trees or the scores at all. Fitting is entirely unsupervised; `contamination` only sets `offset_` to that quantile of the training scores afterwards. So `predict()` will flag *exactly* that fraction, by construction:

```python
iso = IsolationForest(contamination=0.05, random_state=0).fit(X)
(iso.predict(X) == -1).mean()   # 0.05, whatever X is
```

Pass 0.10 against a true anomaly rate of 0.1% and you hand your reviewers 100x the real volume — and the model looks like it "found" them. Pass too little and the extras are silently dropped. Either way the ranking underneath is unchanged.

So rank, don't classify:

```python
scores = -iso.score_samples(X)   # higher = more anomalous
top = np.argsort(scores)[-50:]   # what the team can actually review
```

Set the cutoff from review capacity, or from a labeled holdout if you have one — not from a guess typed into the constructor. `contamination='auto'` (the default since 0.22) uses a fixed offset of -0.5 rather than a data quantile, which is at least honest about not knowing.

One structural limit: splits are axis-parallel, so a point inside the normal range of *every* feature but far off the correlation diagonal is nearly invisible. If your anomalies are relational, add the ratio or residual as an explicit feature.
