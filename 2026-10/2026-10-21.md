# Daily Notes - 2026-10-21

## 00:04 - [Data Engineering] `acks=all` Is Not Durable: ISR Shrink and `min.insync.replicas`

Teams set `acks=all` on their Kafka producer, see "waits for all replicas," and consider durability solved. It isn't. `acks=all` waits for all replicas *currently in the in-sync replica set (ISR)* — and the ISR can shrink to one.

### How the ack lies

A topic with `replication.factor=3` normally has ISR = {leader, f1, f2}. If both followers fall behind `replica.lag.time.max.ms` (default 30s — GC pause, disk stall, network blip), the leader shrinks the ISR to itself. `acks=all` now means "acked by the leader alone." If that broker's disk dies before a follower catches up, those acknowledged writes are gone. The producer got a success. The data does not exist.

### The config that actually enforces it

`min.insync.replicas` is the floor. It's a **topic/broker config, not a producer one**, and it only takes effect when the producer sends `acks=all`:

```bash
kafka-configs.sh --bootstrap-server broker:9092 \
  --entity-type topics --entity-name orders \
  --alter --add-config min.insync.replicas=2
```

With `RF=3, min.insync.replicas=2, acks=all`, a write that can't reach two replicas fails with `NotEnoughReplicasException` instead of silently succeeding. You tolerate one broker loss and still accept writes.

The trap on the other side: setting `min.insync.replicas=3` with `RF=3` means **any single broker restart halts all producing** — a rolling upgrade becomes an outage. The standard safe pairing is `RF = min.insync.replicas + 1`.

### The third setting

```properties
# broker / topic
unclean.leader.election.enable=false   # never promote an out-of-sync replica
min.insync.replicas=2
# producer
acks=all
enable.idempotence=true
retries=2147483647
delivery.timeout.ms=120000
```

`unclean.leader.election.enable=true` lets a stale replica become leader when no in-sync replica survives — trading committed data for availability. Leave it off unless you genuinely prefer a lossy topic to a stalled one.

### Checking reality

`kafka-topics.sh --describe --under-min-isr-partitions` lists partitions currently below the floor — those are rejecting `acks=all` writes right now. Alert on the `UnderMinIsrPartitionCount` broker metric; `UnderReplicatedPartitions` alone fires too late to tell you writes are being refused.
