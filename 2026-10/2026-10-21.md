## 00:04 - [Data Engineering] `acks=all` Is Not Durable: ISR Shrink and `min.insync.replicas`

Teams set `acks=all` on their Kafka producer, see "waits for all replicas," and consider durability solved. It isn't. `acks=all` waits for all replicas *currently in the in-sync replica set (ISR)* — and the ISR can shrink to one.

### How the ack lies

A topic with `replication.factor=3` normally has ISR = {leader, f1, f2}. If both followers fall behind `replica.lag.time.max.ms` (default 30s — GC pause, disk stall, network blip), the leader shrinks the ISR to itself. `acks=all` now means "acked by the leader alone." If that broker's disk dies before a follower catches up, those acknowledged writes are gone. The producer got a success. The data does not exist.

### The config that actually enforces it

`min.insync.replicas` is the floor. It's a **topic/broker config, not a producer one**, and it only takes effect when the producer sends `acks=all`:

```bash
kafka-configs.sh --bootstrap-server broker:9092 \
  --entity-type topics --entity-name orders \
  --alter --add-config min.insync.replicas=2
```

With `RF=3, min.insync.replicas=2, acks=all`, a write that can't reach two replicas fails with `NotEnoughReplicasException` instead of silently succeeding. You tolerate one broker loss and still accept writes.

The trap on the other side: setting `min.insync.replicas=3` with `RF=3` means **any single broker restart halts all producing** — a rolling upgrade becomes an outage. The standard safe pairing is `RF = min.insync.replicas + 1`.

### The third setting

```properties
# broker / topic
unclean.leader.election.enable=false   # never promote an out-of-sync replica
min.insync.replicas=2
# producer
acks=all
enable.idempotence=true
retries=2147483647
delivery.timeout.ms=120000
```

`unclean.leader.election.enable=true` lets a stale replica become leader when no in-sync replica survives — trading committed data for availability. Leave it off unless you genuinely prefer a lossy topic to a stalled one.

### Checking reality

`kafka-topics.sh --describe --under-min-isr-partitions` lists partitions currently below the floor — those are rejecting `acks=all` writes right now. Alert on the `UnderMinIsrPartitionCount` broker metric; `UnderReplicatedPartitions` alone fires too late to tell you writes are being refused.

## 05:03 - [Data Analytics] Metabase and Superset Filters: The Predicate That Wraps Your Query Instead of Entering It

A dashboard filter in Metabase or Superset does not edit your SQL. It wraps it:

```sql
SELECT * FROM (
  -- your 60 lines of native SQL
) AS virtual_table
WHERE order_date = DATE '2026-10-20'
```

Whether that costs 1.4 GB or 420 GB depends entirely on whether the engine can push `order_date` through the subquery down to the partition pruner. On a 400M-row table partitioned by day (~1.2M rows/day), the difference is a 2-second query or a 3-minute one.

### What blocks the pushdown

Optimizers push predicates through projections and plain filters. They **cannot** push one through:

- `GROUP BY` on keys that don't include the filtered column
- any window function (`SUM(...) OVER (...)`)
- `DISTINCT`, `LIMIT`, `UNION` with a non-aligned column, or an outer join where the column comes from the nullable side
- a column produced by an expression the engine can't invert — `DATE_TRUNC('month', order_date) AS order_month` is the classic one

So the moment your native SQL aggregates, the filter lands *after* the aggregation and the inner query reads every partition. Caching masks it until someone changes the filter.

### Putting the filter inside

**Metabase** — use a Field Filter variable, and let it be the *entire* condition. This is right:

```sql
WHERE {{order_date}}
  [[AND status = {{status}}]]
```

This is wrong and will not parse — Metabase injects a full clause, not a value:

```sql
WHERE order_date = {{order_date}}
```

The `[[ ]]` brackets make a clause vanish when its variable is empty. A card with no field filter can't be connected to a dashboard filter at all; the widget greys out.

**Superset** — on a virtual dataset, pull the filter into the inner SQL with Jinja:

```sql
WHERE order_date >= '{{ get_filters('order_date', remove_filter=True)[0].val[0] }}'
```

`remove_filter=True` is the important half: without it the predicate is applied twice, inside *and* in the outer wrapper.

### Verifying

Don't trust the wall clock — a warm cache lies. Read bytes scanned (`INFORMATION_SCHEMA.JOBS` on BigQuery, `QUERY_HISTORY.BYTES_SCANNED` on Snowflake) for the same card at two different filter values. If both scan the same volume, nothing pruned, and your filter is decoration.

## 10:04 - [ML & AI] Multicollinearity: It Wrecks Your Coefficients and Leaves Your Predictions Alone

Multicollinearity gets taught as a thing that breaks linear models. It breaks exactly one half of them. Knowing which half tells you whether to care at all.

### A worked example

500 rows. `height_cm`, plus `height_in` (the same measurement in inches with a little noise), plus `age`. Truth is `y = 0.5·height_cm + 0.8·age + ε`.

Variance Inflation Factor — regress each feature on the others, then `VIF = 1/(1-R²)`:

```python
def vif(X):
    return [1 / (1 - LinearRegression().fit(np.delete(X, j, 1), X[:, j])
                 .score(np.delete(X, j, 1), X[:, j]))
            for j in range(X.shape[1])]
# [202.4, 202.4, 1.0]
```

VIF 202 means that coefficient's standard error is `√202 ≈ 14×` larger than it would be with uncorrelated features. Refit OLS on five fresh samples from the same process:

| sample | `height_cm` | `height_in` | `age` |
|---|---|---|---|
| 1 | +0.19 | +0.87 | +0.79 |
| 3 | +0.49 | +0.03 | +0.81 |
| 5 | +0.81 | **−0.78** | +0.80 |

`height_in` flips sign. `age` (VIF 1.0) sits at 0.80 every time, σ = 0.009. The instability is quarantined to the collinear pair — it does not leak into the clean features.

### What survives

The *sum* is identified even when the parts aren't. Converting to common units, `height_cm + height_in/2.54` gives 0.532, 0.518, 0.497, 0.504, 0.504 — σ = 0.013, centered on the true 0.5. OLS knows the total height effect precisely; it just can't attribute it.

Which is why prediction is fine. Held-out RMSE: **4.809** with both columns, **4.849** with the duplicate dropped. Noise.

### So what to do

- **Predicting only?** Ignore VIF. It isn't a bug.
- **Reading coefficients** (effect sizes, regulatory explanations, feature "importance")? Drop one, or combine them. A sign flip you report to a stakeholder is a real error.
- **Keep both and want stability?** Ridge. On standardized features, `alpha=10` cut the across-sample σ from ~1.3 to ~0.3 and split the height signal evenly (2.71 / 2.24) instead of letting one column swing wildly. That's the bias-variance trade made deliberately.
- **Tree models?** VIF is irrelevant to predictions, but correlated features *split* their importance scores, so `feature_importances_` understates both.

Rule of thumb: VIF > 10 is worth a look, > 100 means two columns are near-duplicates. But the number only matters if you plan to read the coefficients.
