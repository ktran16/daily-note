## 00:03 - [Data Engineering] Factless Fact Tables: Counting Events With No Measure, and Things That Never Happened

Every fact table is supposed to have numeric measures you can sum. Some of the most useful ones have none. A **factless fact table** holds only foreign keys and a date — the row *is* the measurement, and the measure is `COUNT(*)`.

**Event tracking.** A student attends a class; a customer views a product; a candidate is interviewed. There is nothing to add up, but the intersection of dimensions is the business question:

```sql
-- fct_class_attendance: grain = one student, one class, one day
select d.semester, c.department, count(*) as attendances
from fct_class_attendance f
join dim_date d on d.date_key = f.date_key
join dim_course c on c.course_key = f.course_key
group by 1, 2
```

Some modelers add a literal `1 as attendance_count` column. It is redundant — `count(*)` gives the same answer — but it makes the table look conventional to BI tools that insist on selecting a measure.

**Coverage.** The harder use is answering *what didn't happen*. Facts record events, so "which promoted products sold nothing last week?" is unanswerable from the sales fact alone: the rows you need don't exist. A coverage factless fact records eligibility — every product on promotion in every store each day — and the answer becomes an anti-join:

```sql
select cov.product_key, cov.store_key
from fct_promotion_coverage cov
left join fct_sales s
  on  s.product_key = cov.product_key
  and s.store_key   = cov.store_key
  and s.date_key    = cov.date_key
where cov.date_key between 20261001 and 20261007
  and s.sale_key is null
```

In dbt this is just a model with a tight grain, and the grain deserves a test:

```yaml
models:
  - name: fct_promotion_coverage
    tests:
      - dbt_utils.unique_combination_of_columns:
          combination_of_columns: [date_key, product_key, store_key]
```

**The cost.** Coverage tables are a cross product of dimensions over time, so they grow far faster than the event tables they explain — daily store × product coverage is millions of rows a day. Keep them incremental, partitioned by date, and retained only as long as the questions look back.

The rule of thumb: if the fact has no measure, make sure it has a *purpose* — tracking an event, or establishing the denominator that absence is measured against.

## 05:02 - [Data Analytics] Overlapping Date Ranges: The Self-Join Predicate Everyone Writes Backwards

Finding overlapping validity windows — double-billed subscriptions, two active price tiers, an SCD2 table with broken history — is a self-join. It is also the self-join most often written wrong, and the wrong version fails *silently by returning nothing*.

The instinct is "does A's start fall inside B?":

```sql
-- WRONG
SELECT a.id, b.id
FROM subscription a
JOIN subscription b
  ON a.customer_id = b.customer_id
 AND a.id < b.id
WHERE a.valid_from BETWEEN b.valid_from AND b.valid_to;
```

With four rows for one customer — `(1, Jan 1 → Apr 1)`, `(2, Feb 1 → Mar 1)`, `(3, Apr 1 → Jun 1)`, `(4, May 15 → NULL)` — that query returns **zero rows**. There are two real overlaps (1 encloses 2; 3 overlaps 4). `BETWEEN` only fires when the *later* range's start sits inside the earlier one, so every hit it finds has `a.id > b.id`, and the `a.id < b.id` dedupe filter wipes them all out. Drop that filter and you get mirrored duplicates plus a false positive on ranges that merely touch.

The correct test is Allen's interval overlap — each range starts before the other ends:

```sql
SELECT a.id AS id_a, b.id AS id_b
FROM subscription a
JOIN subscription b
  ON a.customer_id = b.customer_id
 AND a.id < b.id                                        -- each pair once, no self-match
 AND a.valid_from < COALESCE(b.valid_to, '9999-12-31')  -- open-ended = infinity
 AND b.valid_from < COALESCE(a.valid_to, '9999-12-31');
-- (1,2) and (3,4)
```

Three details carry the whole query. `a.id < b.id` gives each pair once and excludes the row matching itself. `COALESCE(..., '9999-12-31')` keeps open-ended rows in — `NULL` comparisons are `UNKNOWN`, so without it current subscriptions never overlap anything. And strict `<` encodes half-open intervals `[from, to)`, so range 3 starting exactly when range 1 ends is not a conflict; use `<=` only if your end dates are genuinely inclusive.

**At scale, don't join.** The self-join is O(n²) per partition. One ordered pass does the same work:

```sql
WITH flagged AS (
  SELECT id, valid_from,
         MAX(COALESCE(valid_to, '9999-12-31')) OVER (
           PARTITION BY customer_id ORDER BY valid_from
           ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) AS prev_end
  FROM subscription
)
SELECT id FROM flagged WHERE valid_from < prev_end;  -- rows 2 and 4
```

`MAX` over the running frame — not `LAG` — is what makes it correct: the conflicting predecessor is not always the immediately preceding row. This is the shape to put in a dbt test; the self-join is the shape for the ad-hoc investigation that follows.

## 10:05 - [ML & AI] Gini vs Entropy: Where the Two Split Criteria Actually Disagree

A decision tree picks a split by scoring every candidate threshold on **impurity reduction**: parent impurity minus the sample-weighted impurity of the two children. The two standard scores for classification are

- Gini: `1 - Σ pₖ²`
- Entropy: `-Σ pₖ log₂ pₖ`

People pick one by habit. Here is where they differ, with real numbers. Parent node: 100 rows, 40 positive. Gini = `1 - (0.4² + 0.6²)` = **0.48**; entropy = **0.971**.

**Split A** — balanced halves: left 50 rows (70% positive), right 50 rows (10% positive).
**Split B** — carves out a pure region: left 20 rows (100% positive), right 80 rows (25% positive).

| | child Gini | Gini gain | child entropy | info gain |
|---|---|---|---|---|
| A | 0.300 | **0.180** | 0.675 | 0.296 |
| B | 0.300 | **0.180** | 0.649 | **0.322** |

Gini is **exactly indifferent** between them. Entropy prefers B. That is the whole difference: `log p` blows up as `p → 0`, so entropy pays a premium for splits that drive a child toward purity, while Gini — a quadratic — is flatter near the ends and happier with balanced, population-splitting cuts.

In practice this rarely moves test accuracy; the classic comparisons find the two criteria choose different splits in only a small minority of nodes, and the gap is inside cross-validation noise. So don't tune `criterion`. Tune what actually controls the fit:

```python
DecisionTreeClassifier(
    criterion="gini",        # not where your accuracy lives
    min_samples_leaf=20,     # this is
    max_depth=8,
    ccp_alpha=1e-4,          # cost-complexity pruning
)
```

**The gotcha worth remembering.** sklearn's `min_impurity_decrease` is *not* the gain above. It is scaled by the node's share of the data:

```
(N_t / N) * (impurity - (N_tL/N_t)*left_impurity - (N_tR/N_t)*right_impurity)
```

Split A at the root of a 100-row set scores `1.0 × 0.18 = 0.18`. The identical split inside a node holding 10 rows of a 100-row set scores `0.1 × 0.18 = 0.018`. A threshold that prunes sensibly near the root silently forbids every deep split — which is usually what people wanted, but almost never what they thought they wrote.
