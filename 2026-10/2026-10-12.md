## 00:03 - [Data Engineering] dbt Test Severity: Failing the Pipeline on Three Rows Out of Ten Million

A `not_null` test finds 3 bad rows in a 10M-row fact table. dbt returns exit code 1, `dbt build` halts, and every downstream mart is skipped. Three rows just took out the warehouse. The fix is not deleting the test — it is telling dbt *how much* breakage is actually an emergency.

Every test takes `severity`, plus two thresholds compared against the failure count:

```yaml
models:
  - name: fct_orders
    columns:
      - name: shipping_address_id
        data_tests:
          - not_null:
              config:
                severity: error
                error_if: ">1000"   # genuinely broken
                warn_if: ">0"       # tell me, but keep going
```

The evaluation order is the part people get wrong. `error_if` and `warn_if` both default to `!= 0`. When `severity: error`, dbt checks `error_if` first; if that is false it falls through to `warn_if`. So with the config above, 3 failures → **warn**, exit 0, downstream models still build. 2,000 failures → **error**, run stops.

The trap: `error_if` is only consulted when severity is `error`. Set `severity: warn` and your carefully written `error_if: ">1000"` is dead config — the test can never fail, no matter how bad the data gets.

Make severity environment-aware so dev noise doesn't block anyone:

```yaml
          - unique:
              config:
                severity: "{{ 'error' if target.name == 'prod' else 'warn' }}"
```

Set defaults for a whole folder in `dbt_project.yml`:

```yaml
data_tests:
  my_project:
    staging:
      +severity: warn
    marts:
      +severity: error
```

Two things to pair with this. Add `+store_failures: true` so warnings land in a queryable table instead of scrolling past in logs — a warning nobody can inspect is a warning nobody fixes. And in CI, use `dbt build --warn-error-options '{"error": ["all"]}'` deliberately, not reflexively: it promotes every warning to a failure, which is exactly what you want gating a PR and exactly what you don't want in a 3 AM production run.

Severity is a statement about blast radius. Reserve `error` for "serving this data is worse than serving none."

## 05:03 - [Data Analytics] Forward-Filling Sparse Series: `IGNORE NULLS`, and the Portable Trick for Engines Without It

You join a date spine to a sparse `fx_rates` table that only records a row when the rate *changes*. 30 days of spine, 4 actual rates, 26 NULLs. Multiply revenue by that column and 26 days silently become zero or NULL. You need the last known value carried forward.

The one-line fix, where the engine supports it:

```sql
SELECT
  d.day,
  r.rate AS rate_raw,
  LAST_VALUE(r.rate IGNORE NULLS) OVER (
    ORDER BY d.day
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  ) AS rate_filled
FROM date_spine d
LEFT JOIN fx_rates r ON r.day = d.day;
```

Two details carry the whole query:

- **Drop `IGNORE NULLS` and you get nothing.** The default is `RESPECT NULLS`, so `LAST_VALUE` happily returns the NULL sitting on the current row. The symptom is a column that looks completely unfilled — not a subtle error, but easy to misread as a join bug.
- **Write the `ROWS` frame explicitly.** The default frame is `RANGE ... CURRENT ROW`, which includes *peer* rows — every row sharing the same `ORDER BY` value. With two rate updates on the same day, `RANGE` puts both in frame for *each* of those rows, so the morning row gets filled with the evening rate — a value from its own future. `ROWS` stops at the current row. Add a tie-breaker to `ORDER BY` too: `ORDER BY d.day, r.updated_at`.

**Not every engine has it.** BigQuery, Snowflake, Redshift, Databricks, DuckDB and SQL Server 2022+ do. Postgres and MySQL 8 do not — `IGNORE NULLS` is a parse error there. The portable pattern is a two-step "grouped max": `COUNT` over a running frame increments only on non-NULL rows, giving every gap the same group id as the value that should fill it.

```sql
WITH grouped AS (
  SELECT d.day, r.rate,
         COUNT(r.rate) OVER (ORDER BY d.day
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS grp
  FROM date_spine d
  LEFT JOIN fx_rates r ON r.day = d.day
)
SELECT day, MAX(rate) OVER (PARTITION BY grp) AS rate_filled
FROM grouped;
```

Leading NULLs stay NULL in both versions — there is no earlier value to borrow. Decide deliberately whether that day belongs in the report or should be dropped; don't let `COALESCE(rate, 0)` make the call for you.

## 10:05 - [ML & AI] Receptive Field: Why 8 Stacked 3×3 Convolutions Only See 17 Pixels

A conv layer's output size is `floor((n + 2p - k)/s) + 1`. That tells you tensor shapes. It does *not* tell you how much of the input any single output pixel actually looked at — the **receptive field** (RF) — and that is the number that decides whether your network can see the object at all.

The RF recursion tracks two values: the field `r` and the **jump** `j` (the input pixels between adjacent output pixels, i.e. the product of all strides so far):

```python
def rf(layers):                 # layers: (kernel, stride, dilation)
    r, j = 1, 1
    for k, s, d in layers:
        k_eff = d * (k - 1) + 1
        r += (k_eff - 1) * j    # growth is scaled by the jump
        j *= s
    return r, j
```

The `* j` is the whole story. At stride 1 the jump stays 1, so every 3×3 conv adds exactly 2 pixels — linear growth:

| Stack | RF |
|---|---|
| 8 × conv3×3, stride 1 | **17** |
| 4 VGG blocks (same 8 convs + 4 maxpool 2/2) | **76** |
| conv3×3 dilated 1, 2, 4, 8 | **31** |

Eight plain convs on a 224px image see 17px — 7.6% of the width. Interleave four pooling layers and the *same eight convs* reach 76px, because each downsample doubles the jump and makes every later conv count double. Downsampling isn't just a compute saving; it's what buys you global context. Dilation is the third option: 1, 2, 4, 8 reaches 31px in four layers at full resolution — which is why segmentation models (DeepLab's ASPP) prefer it, since they can't afford to throw away spatial detail.

Two practical corrections:

- **Theoretical RF overstates reality.** Contribution from the edge of the field decays roughly Gaussian (Luo et al., 2016), so the *effective* RF grows like √(layers), not linearly. Budget for about half the number you computed.
- **Check your RF against your object size.** If you're detecting 100px defects on a 1024px image with a stride-4 head whose RF is 60px, no amount of training fixes it — the layer physically cannot see the defect. Add stages, dilate, or predict from a deeper pyramid level.

Compute the RF before you tune the learning rate.

## 15:04 - [Crypto & Business] ISOs and the AMT Crossover: The Tax Bill You Owe on Stock You Haven't Sold

Incentive stock options have a feature that reads like a gift and behaves like a trap: exercising them creates **no ordinary income** for regular tax. The spread is still income — just under the parallel system, the Alternative Minimum Tax.

**The mechanics.** On exercise, the bargain element (FMV − strike, × shares) is an AMT preference item. You compute your tax twice and pay the higher number.

Worked example — single filer, $180,000 W-2, exercising 10,000 ISOs at a $2 strike when FMV is $22:

- Cash to exercise: **$20,000**
- Bargain element: 10,000 × $20 = **$200,000**
- Regular taxable income ≈ $165,000 → regular tax ≈ **$29,000**
- AMTI ≈ $180,000 + $200,000 = $380,000, less the AMT exemption (≈$90,000 single, indexed; it now phases out at 50¢ per dollar above $500,000 single / $1M joint) → **$290,000 base**
- AMT: 26% on the first ≈$240,000, 28% above → ≈ **$76,000**

You owe roughly **$47,000 extra in April**, on top of the $20,000 exercise cost, for shares you cannot sell if the company is private. Nothing was liquidated. Nothing hit your bank account.

**Two things soften it.** Your AMT basis is $22, not $2, so a later qualifying sale is taxed on less gain. And the excess creates a minimum tax credit that carries forward — but it only releases in years when regular tax exceeds tentative AMT, often $2–5K at a time. If the stock falls to $3 before you can sell, you paid real cash on a gain that no longer exists and claw it back over a decade.

**Levers that actually matter**

1. **Exercise in January, not December.** A disqualifying disposition — selling in the same calendar year you exercised — erases the AMT adjustment entirely; the spread becomes ordinary compensation income instead. Early exercise keeps that escape hatch open for 11 months.
2. **Find your crossover.** There is a share count at which tentative AMT just equals regular tax; exercising up to it costs zero extra tax. Spreading one large exercise across three Januaries can save tens of thousands.
3. **Model it before the 90-day post-termination window**, not after — miss it and the ISOs convert to NSOs, taxed as ordinary income on exercise.

Exemption and bracket figures are indexed annually — verify the current year's numbers. Educational only; not tax or investment advice.
