## 00:02 - dbt Seeds: Loading Static Reference Data into Your Warehouse

Seeds are CSV files stored in your dbt project's `seeds/` directory that dbt loads as tables in your data warehouse. They're perfect for small, slowly-changing reference datasets that don't have a source system — country codes, fiscal calendars, product category mappings, or feature flag configurations.

### When to Use Seeds

Use seeds when data is:
- Small enough to commit to version control (< a few thousand rows)
- Maintained by analysts, not ingested by a pipeline
- Rarely updated but needs to be under source control for reproducibility

Avoid seeds for large datasets or anything updated frequently — use a source and ingestion pipeline instead.

### Basic Setup

Place a CSV in `seeds/country_codes.csv`:

```
country_code,country_name,region
US,United States,North America
GB,United Kingdom,Europe
DE,Germany,Europe
JP,Japan,Asia Pacific
```

Load it with:

```bash
dbt seed
# or target a specific seed
dbt seed --select country_codes
```

dbt infers column types automatically, but you can override them in `dbt_project.yml`:

```yaml
seeds:
  my_project:
    country_codes:
      +column_types:
        country_code: varchar(2)
        country_name: varchar(100)
```

### Referencing Seeds in Models

Seeds are first-class nodes in the DAG. Reference them the same way you reference models:

```sql
-- models/dim_orders.sql
with orders as (
    select * from {{ ref('stg_orders') }}
),

country_lookup as (
    select * from {{ ref('country_codes') }}
)

select
    o.order_id,
    o.country_code,
    c.country_name,
    c.region
from orders o
left join country_lookup c using (country_code)
```

### Schema & Documentation

Document seeds in a YAML file alongside your models:

```yaml
# seeds/schema.yml
seeds:
  - name: country_codes
    description: "ISO 3166-1 alpha-2 country codes with regional groupings"
    columns:
      - name: country_code
        description: "Two-letter ISO country code"
        tests:
          - unique
          - not_null
      - name: region
        description: "High-level geographic region for reporting"
```

### Key Flags

| Flag | Purpose |
|------|---------|
| `--full-refresh` | Drop and recreate the seed table (use when column types change) |
| `--select <name>` | Run only a specific seed |
| `+enabled: false` | Disable a seed without deleting the file |

Seeds keep static reference data version-controlled, reviewable via PR, and tightly coupled to the models that consume them — a much cleaner alternative to ad-hoc lookup tables loaded by hand.

## 05:03 - dbt Variables: Making Models Configurable with `var()` and `env_var()`

dbt variables let you parameterize your models and macros so the same code can behave differently across environments, runs, or use cases — without hardcoding values in SQL.

### Two Kinds of Variables

| Function | Source | Override mechanism |
|----------|--------|--------------------|
| `var()` | `dbt_project.yml` or `--vars` CLI flag | `--vars '{key: value}'` at run time |
| `env_var()` | OS environment variables | Set in shell, CI secrets, or dbt Cloud env config |

### Defining and Using `var()`

Declare defaults in `dbt_project.yml`:

```yaml
vars:
  start_date: '2024-01-01'
  event_threshold: 10
  target_schema: 'analytics'
```

Reference in a model or macro:

```sql
-- models/fct_events.sql
select *
from {{ ref('stg_events') }}
where
    event_date >= '{{ var("start_date") }}'
    and event_count >= {{ var("event_threshold") }}
```

Override at runtime without touching code:

```bash
dbt run --vars '{"start_date": "2025-01-01", "event_threshold": 5}'
```

Always supply a default so the model works without the flag:

```sql
{{ var("start_date", "2020-01-01") }}
```

### Using `env_var()` for Secrets and Environment-Specific Config

`env_var()` reads from the OS environment — ideal for credentials, target schemas, or anything that differs between dev and prod:

```yaml
# profiles.yml
my_profile:
  target: prod
  outputs:
    prod:
      type: snowflake
      account: "{{ env_var('SNOWFLAKE_ACCOUNT') }}"
      password: "{{ env_var('SNOWFLAKE_PASSWORD') }}"
      schema: "{{ env_var('DBT_SCHEMA', 'analytics') }}"
```

The second argument to `env_var()` is an optional default — useful for local development where the variable may not be set.

### Practical Patterns

**Feature flag / environment gate:**

```sql
{% if var("include_pii", false) %}
    , user_email
    , phone_number
{% endif %}
```

**Dynamic lookback window:**

```sql
where created_at >= dateadd(day, -{{ var("lookback_days", 30) }}, current_date)
```

**Conditional schema routing:**

```yaml
# dbt_project.yml
models:
  my_project:
    staging:
      +schema: "{{ var('staging_schema', 'staging') }}"
```

### Key Rules

- `var()` values are strings by default — cast in SQL or use Jinja filters (`| int`, `| bool`) when needed.
- Never put secrets in `dbt_project.yml` (it's committed to git). Use `env_var()` for anything sensitive.
- `env_var()` fails loudly at compile time if the variable is missing and no default is provided — treat that as a safety net.
- In dbt Cloud, set environment variables per environment in the project settings UI; they inject automatically at run time.

Combining `var()` for logical configuration and `env_var()` for environment-specific secrets gives you clean, portable dbt projects that behave correctly everywhere without duplicating code.

## 10:02 - dbt Model Contracts: Enforcing Schema Guarantees Between Teams

Introduced in dbt Core 1.5, **model contracts** let you declare a binding promise about a model's output schema — column names, data types, and constraints — that dbt verifies at build time. They're the difference between "this model probably has these columns" and "this model is guaranteed to have these columns or the build fails."

### Why Contracts Matter

Without contracts, downstream consumers are silently broken when an upstream model drops a column or changes a type. Contracts make that breakage explicit and immediate, turning a runtime surprise into a compile-time error.

### Enabling a Contract

Add `contract: {enforced: true}` to a model's config block (in YAML — not in the `.sql` file):

```yaml
# models/schema.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: unique
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_total
        data_type: numeric
      - name: order_date
        data_type: date
      - name: status
        data_type: varchar
```

When `enforced: true`, dbt compares the model's actual output schema against this declaration **before** inserting any data. A mismatch — extra column, wrong type, missing column — fails the run immediately.

### Supported Constraints

| Constraint type | What it does | Warehouse support |
|----------------|--------------|-------------------|
| `not_null` | Rejects nulls in that column | All (some enforce post-load) |
| `unique` | Rejects duplicate values | Snowflake, BigQuery, Postgres |
| `primary_key` | Marks PK; implies not_null | Varies (may be advisory only) |
| `foreign_key` | References another model/table | Varies |
| `check` | Custom SQL expression | Postgres, Snowflake |

> Note: Some warehouses (BigQuery, Redshift) treat certain constraints as **advisory** — dbt records them as metadata but doesn't enforce at insert time. Check your adapter docs.

### Contracts and Access / Versioning

Contracts pair naturally with two other dbt features:

**Model access** — mark a model `public` so other projects can `ref()` it across project boundaries:

```yaml
models:
  - name: fct_orders
    access: public
    config:
      contract:
        enforced: true
```

**Model versioning** — when you need to change a contracted model's schema, version it instead of breaking consumers:

```yaml
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 1   # old contract still served to existing consumers
      - v: 2   # new contract with added columns
```

Consumers pinned to `ref('fct_orders', v=1)` keep working while new consumers adopt v2.

### What Contracts Don't Replace

Contracts verify schema structure, not data quality. Continue using dbt tests (`not_null`, `unique`, `accepted_values`, etc.) for row-level data quality. The mental model: contracts = shape of the table; tests = content of the rows.

### Practical Checklist

- Enable contracts on **public-facing or cross-team models** first — the highest-value targets.
- Always specify `data_type` for every column; dbt can't verify the contract without it.
- Use `dbt compile` locally before opening a PR — contract violations surface at compile time, so you catch them before CI runs.
- If your warehouse enforces constraints natively (Snowflake, Postgres), lean into `primary_key` and `foreign_key` for referential integrity that lives in the warehouse, not just in dbt metadata.

Model contracts are the foundation of treating your dbt models as a proper API — with versioning, access control, and enforced schema guarantees that scale across large teams and multi-project dbt deployments.
