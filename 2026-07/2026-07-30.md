## 00:02 - dbt Seeds: Loading Static Reference Data into Your Warehouse

Seeds are CSV files stored in your dbt project's `seeds/` directory that dbt loads as tables in your data warehouse. They're perfect for small, slowly-changing reference datasets that don't have a source system — country codes, fiscal calendars, product category mappings, or feature flag configurations.

### When to Use Seeds

Use seeds when data is:
- Small enough to commit to version control (< a few thousand rows)
- Maintained by analysts, not ingested by a pipeline
- Rarely updated but needs to be under source control for reproducibility

Avoid seeds for large datasets or anything updated frequently — use a source and ingestion pipeline instead.

### Basic Setup

Place a CSV in `seeds/country_codes.csv`:

```
country_code,country_name,region
US,United States,North America
GB,United Kingdom,Europe
DE,Germany,Europe
JP,Japan,Asia Pacific
```

Load it with:

```bash
dbt seed
# or target a specific seed
dbt seed --select country_codes
```

dbt infers column types automatically, but you can override them in `dbt_project.yml`:

```yaml
seeds:
  my_project:
    country_codes:
      +column_types:
        country_code: varchar(2)
        country_name: varchar(100)
```

### Referencing Seeds in Models

Seeds are first-class nodes in the DAG. Reference them the same way you reference models:

```sql
-- models/dim_orders.sql
with orders as (
    select * from {{ ref('stg_orders') }}
),

country_lookup as (
    select * from {{ ref('country_codes') }}
)

select
    o.order_id,
    o.country_code,
    c.country_name,
    c.region
from orders o
left join country_lookup c using (country_code)
```

### Schema & Documentation

Document seeds in a YAML file alongside your models:

```yaml
# seeds/schema.yml
seeds:
  - name: country_codes
    description: "ISO 3166-1 alpha-2 country codes with regional groupings"
    columns:
      - name: country_code
        description: "Two-letter ISO country code"
        tests:
          - unique
          - not_null
      - name: region
        description: "High-level geographic region for reporting"
```

### Key Flags

| Flag | Purpose |
|------|---------|
| `--full-refresh` | Drop and recreate the seed table (use when column types change) |
| `--select <name>` | Run only a specific seed |
| `+enabled: false` | Disable a seed without deleting the file |

Seeds keep static reference data version-controlled, reviewable via PR, and tightly coupled to the models that consume them — a much cleaner alternative to ad-hoc lookup tables loaded by hand.

## 05:03 - dbt Variables: Making Models Configurable with `var()` and `env_var()`

dbt variables let you parameterize your models and macros so the same code can behave differently across environments, runs, or use cases — without hardcoding values in SQL.

### Two Kinds of Variables

| Function | Source | Override mechanism |
|----------|--------|--------------------|
| `var()` | `dbt_project.yml` or `--vars` CLI flag | `--vars '{key: value}'` at run time |
| `env_var()` | OS environment variables | Set in shell, CI secrets, or dbt Cloud env config |

### Defining and Using `var()`

Declare defaults in `dbt_project.yml`:

```yaml
vars:
  start_date: '2024-01-01'
  event_threshold: 10
  target_schema: 'analytics'
```

Reference in a model or macro:

```sql
-- models/fct_events.sql
select *
from {{ ref('stg_events') }}
where
    event_date >= '{{ var("start_date") }}'
    and event_count >= {{ var("event_threshold") }}
```

Override at runtime without touching code:

```bash
dbt run --vars '{"start_date": "2025-01-01", "event_threshold": 5}'
```

Always supply a default so the model works without the flag:

```sql
{{ var("start_date", "2020-01-01") }}
```

### Using `env_var()` for Secrets and Environment-Specific Config

`env_var()` reads from the OS environment — ideal for credentials, target schemas, or anything that differs between dev and prod:

```yaml
# profiles.yml
my_profile:
  target: prod
  outputs:
    prod:
      type: snowflake
      account: "{{ env_var('SNOWFLAKE_ACCOUNT') }}"
      password: "{{ env_var('SNOWFLAKE_PASSWORD') }}"
      schema: "{{ env_var('DBT_SCHEMA', 'analytics') }}"
```

The second argument to `env_var()` is an optional default — useful for local development where the variable may not be set.

### Practical Patterns

**Feature flag / environment gate:**

```sql
{% if var("include_pii", false) %}
    , user_email
    , phone_number
{% endif %}
```

**Dynamic lookback window:**

```sql
where created_at >= dateadd(day, -{{ var("lookback_days", 30) }}, current_date)
```

**Conditional schema routing:**

```yaml
# dbt_project.yml
models:
  my_project:
    staging:
      +schema: "{{ var('staging_schema', 'staging') }}"
```

### Key Rules

- `var()` values are strings by default — cast in SQL or use Jinja filters (`| int`, `| bool`) when needed.
- Never put secrets in `dbt_project.yml` (it's committed to git). Use `env_var()` for anything sensitive.
- `env_var()` fails loudly at compile time if the variable is missing and no default is provided — treat that as a safety net.
- In dbt Cloud, set environment variables per environment in the project settings UI; they inject automatically at run time.

Combining `var()` for logical configuration and `env_var()` for environment-specific secrets gives you clean, portable dbt projects that behave correctly everywhere without duplicating code.

## 10:02 - dbt Model Contracts: Enforcing Schema Guarantees Between Teams

Introduced in dbt Core 1.5, **model contracts** let you declare a binding promise about a model's output schema — column names, data types, and constraints — that dbt verifies at build time. They're the difference between "this model probably has these columns" and "this model is guaranteed to have these columns or the build fails."

### Why Contracts Matter

Without contracts, downstream consumers are silently broken when an upstream model drops a column or changes a type. Contracts make that breakage explicit and immediate, turning a runtime surprise into a compile-time error.

### Enabling a Contract

Add `contract: {enforced: true}` to a model's config block (in YAML — not in the `.sql` file):

```yaml
# models/schema.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: unique
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_total
        data_type: numeric
      - name: order_date
        data_type: date
      - name: status
        data_type: varchar
```

When `enforced: true`, dbt compares the model's actual output schema against this declaration **before** inserting any data. A mismatch — extra column, wrong type, missing column — fails the run immediately.

### Supported Constraints

| Constraint type | What it does | Warehouse support |
|----------------|--------------|-------------------|
| `not_null` | Rejects nulls in that column | All (some enforce post-load) |
| `unique` | Rejects duplicate values | Snowflake, BigQuery, Postgres |
| `primary_key` | Marks PK; implies not_null | Varies (may be advisory only) |
| `foreign_key` | References another model/table | Varies |
| `check` | Custom SQL expression | Postgres, Snowflake |

> Note: Some warehouses (BigQuery, Redshift) treat certain constraints as **advisory** — dbt records them as metadata but doesn't enforce at insert time. Check your adapter docs.

### Contracts and Access / Versioning

Contracts pair naturally with two other dbt features:

**Model access** — mark a model `public` so other projects can `ref()` it across project boundaries:

```yaml
models:
  - name: fct_orders
    access: public
    config:
      contract:
        enforced: true
```

**Model versioning** — when you need to change a contracted model's schema, version it instead of breaking consumers:

```yaml
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 1   # old contract still served to existing consumers
      - v: 2   # new contract with added columns
```

Consumers pinned to `ref('fct_orders', v=1)` keep working while new consumers adopt v2.

### What Contracts Don't Replace

Contracts verify schema structure, not data quality. Continue using dbt tests (`not_null`, `unique`, `accepted_values`, etc.) for row-level data quality. The mental model: contracts = shape of the table; tests = content of the rows.

### Practical Checklist

- Enable contracts on **public-facing or cross-team models** first — the highest-value targets.
- Always specify `data_type` for every column; dbt can't verify the contract without it.
- Use `dbt compile` locally before opening a PR — contract violations surface at compile time, so you catch them before CI runs.
- If your warehouse enforces constraints natively (Snowflake, Postgres), lean into `primary_key` and `foreign_key` for referential integrity that lives in the warehouse, not just in dbt metadata.

Model contracts are the foundation of treating your dbt models as a proper API — with versioning, access control, and enforced schema guarantees that scale across large teams and multi-project dbt deployments.

## 15:02 - dbt Tags: Organizing and Selectively Running Subsets of Your DAG

Tags give you a lightweight, flexible way to group dbt nodes — models, tests, seeds, snapshots, sources — so you can target exactly what you need with `--select` without memorizing folder paths or model names.

### Assigning Tags

Tags can be applied at the project level, directory level, or individual model level.

**In `dbt_project.yml` (directory-wide):**

```yaml
models:
  my_project:
    staging:
      +tags: ['staging', 'hourly']
    marts:
      finance:
        +tags: ['finance', 'daily']
      marketing:
        +tags: ['marketing', 'daily']
```

**In a model's config block (individual):**

```sql
-- models/fct_revenue.sql
{{ config(
    materialized='table',
    tags=['finance', 'critical', 'daily']
) }}

select ...
```

**In YAML (for tests and sources):**

```yaml
models:
  - name: fct_revenue
    config:
      tags: ['finance', 'critical']
    columns:
      - name: revenue_usd
        tests:
          - not_null:
              config:
                tags: ['p0-test']
```

### Selecting by Tag

Use the `tag:` prefix in any `--select` expression:

```bash
# Run all models tagged 'daily'
dbt run --select tag:daily

# Run all finance models that are also tagged 'critical'
dbt run --select tag:finance,tag:critical

# Test only p0-tests
dbt test --select tag:p0-test

# Exclude a tag from a broader selection
dbt run --select staging --exclude tag:experimental

# Combine tags with graph operators — run finance models and all their dependencies
dbt run --select +tag:finance
```

### Common Tagging Strategies

| Tag dimension | Examples | Use case |
|---------------|----------|----------|
| **Frequency** | `hourly`, `daily`, `weekly` | Orchestrator schedules separate DAG runs by cadence |
| **Domain** | `finance`, `marketing`, `ops` | Teams run only their slice in development |
| **Priority** | `critical`, `p0`, `p1` | Alerts and on-call escalation targets |
| **Stage** | `staging`, `intermediate`, `mart` | Partial rebuilds during development |
| **State** | `experimental`, `deprecated` | Govern what's production-ready |

### Orchestration Integration

Tags shine in orchestration (Airflow, Prefect, Dagster, dbt Cloud jobs). Instead of hardcoding model lists that rot as the project grows, parameterize the job by tag:

```bash
# Airflow task for the hourly finance refresh
dbt run --select tag:finance,tag:hourly --target prod
```

Add a new model with `tags: ['finance', 'hourly']` and it automatically slots into the right job — zero orchestration changes needed.

### Introspecting Tags

List all nodes carrying a tag without running them:

```bash
dbt ls --select tag:critical --output name
```

Or check the compiled manifest:

```bash
# jq one-liner: all model names tagged 'daily'
jq '[.nodes | to_entries[] | select(.value.tags | index("daily")) | .value.name]' target/manifest.json
```

Tags are free metadata — use them liberally. The cost of an unused tag is nothing; the cost of not being able to selectively run 20% of your DAG for a hotfix at 2 AM is very real.

## 19:03 - dbt Exposures: Documenting Downstream Consumers in the DAG

Exposures let you declare the dashboards, ML models, applications, and other systems that consume your dbt models. They appear as leaf nodes in the dbt DAG, giving you a complete picture of data lineage from raw source all the way to the end product.

### Why Exposures Matter

Without exposures, the DAG stops at your final mart models. You know *what* the data is but not *who's using it*. Exposures answer the question a data engineer dreads: "If I change `fct_orders`, what breaks downstream?" With exposures declared, `dbt ls` and the documentation site show you exactly which dashboards and apps depend on that model.

### Defining an Exposure

Exposures live in YAML files (usually `models/exposures.yml` or co-located with their domain):

```yaml
# models/exposures.yml
exposures:
  - name: weekly_revenue_dashboard
    type: dashboard
    maturity: high
    url: https://looker.company.com/dashboards/42
    description: >
      Executive-facing weekly revenue dashboard. Refreshes every Monday at 06:00 UTC.
      Owned by the Finance Analytics team.
    depends_on:
      - ref('fct_orders')
      - ref('dim_customers')
      - ref('dim_products')
    owner:
      name: Finance Analytics Team
      email: finance-analytics@company.com

  - name: churn_prediction_model
    type: ml
    maturity: medium
    url: https://mlflow.company.com/models/churn-v3
    description: "Weekly churn propensity model trained on 90-day order history."
    depends_on:
      - ref('fct_orders')
      - ref('fct_customer_activity')
    owner:
      name: Data Science
      email: datascience@company.com
```

### Exposure Types and Maturity

| `type` | Use for |
|--------|---------|
| `dashboard` | BI tools (Looker, Tableau, Metabase, etc.) |
| `notebook` | Jupyter / data science notebooks |
| `analysis` | Ad-hoc SQL analyses |
| `ml` | Machine learning models or pipelines |
| `application` | Operational apps reading from the warehouse |

| `maturity` | Meaning |
|------------|---------|
| `low` | Experimental; may break |
| `medium` | Mostly stable; some changes expected |
| `high` | Production; changes require coordination |

### Selecting with Exposures

The real power is in graph selection. Use `exposure:` prefix to work backwards from an exposure to its upstream models:

```bash
# Rebuild everything feeding the revenue dashboard
dbt run --select +exposure:weekly_revenue_dashboard

# Test only the models the churn model depends on
dbt test --select +exposure:churn_prediction_model

# See what models an exposure needs
dbt ls --select +exposure:weekly_revenue_dashboard --output name
```

This is invaluable for impact analysis: before refactoring `fct_orders`, you can run `dbt ls --select fct_orders+` and cross-reference with `dbt ls --select +exposure:*` to know exactly which downstream products are affected.

### Exposures in the Docs Site

Run `dbt docs generate && dbt docs serve` and each exposure appears with:
- A node in the lineage graph showing its upstream DAG
- Owner contact info
- Maturity signal
- Direct link to the external tool (`url`)

This turns your dbt docs site into a full data catalog that non-engineers can navigate — a product manager can click from a dashboard node back through the DAG to the raw source table.

### Practical Tips

- Add exposures when you **publish** a dashboard, not as an afterthought — that's when the context is freshest.
- Set `maturity: high` deliberately; it signals to model authors that changes need coordination with the exposure owner.
- Use `+exposure:<name>` in CI to run targeted tests on only the models that feed a specific downstream product.
- For dbt Cloud, exposures feed into the **Explorer** lineage view, giving stakeholders self-serve impact analysis without needing CLI access.

Exposures close the lineage loop and make "what breaks if we change X?" a query you can answer in seconds — not a conversation you have to track down across three teams.
