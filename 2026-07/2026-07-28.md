## 00:03 - dbt Model Contracts: Enforcing Column-Level Guarantees at Build Time

Introduced in **dbt v1.5**, model contracts let you declare a formal schema for a model — column names, data types, and constraints — that dbt enforces every time the model builds. Think of it as a compile-time type system for your data warehouse: if the model's output doesn't match the declared contract, the build fails before bad data reaches downstream consumers.

### Why Contracts Matter

Without contracts, a renaming refactor or silent upstream type change can silently break BI dashboards or ML pipelines. A contract turns that silent failure into a loud, early one.

### Defining a Contract

Contracts live in your `.yml` files alongside the model definition:

```yaml
# models/marts/finance/fct_orders.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
      - name: total_amount
        data_type: numeric
      - name: status
        data_type: varchar
```

With `enforced: true`, dbt will:
1. **Check that all declared columns exist** in the model's SELECT output.
2. **Validate data types** match what's declared (adapter-dependent; Snowflake, BigQuery, and Redshift all support this).
3. **Apply constraints** (e.g., `not_null`, `primary_key`, `unique`, `foreign_key`) as database-level constraints where the adapter supports them.

### Supported Constraint Types

| Constraint | Enforced by DB? | Notes |
|---|---|---|
| `not_null` | Yes (most adapters) | Column-level |
| `unique` | Yes (most adapters) | Column-level |
| `primary_key` | Yes (most adapters) | Column or model-level |
| `foreign_key` | Yes (Snowflake, PG) | Requires `to` and `to_columns` |
| `check` | Yes (PG, Redshift) | Custom SQL expression |

```yaml
# Model-level primary key (multi-column)
models:
  - name: fct_order_items
    config:
      contract:
        enforced: true
    constraints:
      - type: primary_key
        columns: [order_id, item_id]
    columns:
      - name: order_id
        data_type: bigint
      - name: item_id
        data_type: bigint
```

### Contracts and Materializations

Contracts are currently supported on **table** and **incremental** materializations only — not views or ephemeral models. If you set `contract.enforced: true` on a view, dbt will raise an error at compile time.

### Contracts in CI/CD

Contracts shine in CI pipelines. Add a `dbt build --select state:modified+` step and any PR that renames a column or changes a type in a contracted model will fail the build, surfacing the breaking change before it merges.

### Key Takeaway

Model contracts are the guardrail that makes it safe to refactor aggressively. Define them on your most critical mart-layer models first — facts tables and dimension tables that BI tools depend on — and expand coverage from there.

## 05:04 - dbt Snapshots: Tracking Slowly Changing Dimensions Over Time

**dbt snapshots** solve one of the most common data warehousing problems: capturing how a record looked at a specific point in time. Without snapshots, a simple `UPDATE` to a source table silently erases history. Snapshots implement **Type 2 Slowly Changing Dimensions (SCD2)** — appending a new row whenever a tracked column changes, with `dbt_valid_from` and `dbt_valid_to` timestamps marking each row's active window.

### When to Use Snapshots

Use snapshots when your source data is **mutable** and you need to answer questions like:
- "What was this customer's status last quarter?"
- "Which pricing tier was applied when this order was placed?"
- "How has this user's address changed over time?"

### Defining a Snapshot

Snapshots live in the `snapshots/` directory and use a special `snapshot` block:

```sql
-- snapshots/orders_snapshot.sql
{% snapshot orders_snapshot %}

{{
  config(
    target_schema='snapshots',
    unique_key='order_id',
    strategy='timestamp',
    updated_at='updated_at'
  )
}}

select
  order_id,
  customer_id,
  status,
  total_amount,
  updated_at
from {{ source('raw', 'orders') }}

{% endsnapshot %}
```

### Two Snapshot Strategies

**1. `timestamp` strategy** — Uses a column (e.g., `updated_at`) to detect changes. Requires the source to reliably update this column on every record change. This is the preferred approach when available.

**2. `check` strategy** — Hashes a list of columns and compares against the previous run. Use this when the source has no reliable `updated_at`:

```sql
{{
  config(
    strategy='check',
    check_cols=['status', 'total_amount', 'shipping_address']
  )
}}
```

### What dbt Adds Automatically

After running `dbt snapshot`, dbt appends four metadata columns:

| Column | Description |
|---|---|
| `dbt_scd_id` | Unique key per snapshot row (hash of `unique_key` + `dbt_updated_at`) |
| `dbt_updated_at` | Timestamp when this row was captured |
| `dbt_valid_from` | When this version of the record became active |
| `dbt_valid_to` | When it was superseded (`NULL` = currently active row) |

### Querying Snapshot Tables

```sql
-- Current state of all records
select * from {{ ref('orders_snapshot') }}
where dbt_valid_to is null;

-- Point-in-time: what did orders look like on 2025-01-01?
select * from {{ ref('orders_snapshot') }}
where dbt_valid_from <= '2025-01-01'
  and (dbt_valid_to > '2025-01-01' or dbt_valid_to is null);
```

### Practical Tips

- **Run snapshots before models** in your pipeline (`dbt snapshot && dbt run`) so models see fresh snapshot data.
- **Snapshot at the source layer** — capture raw data, not transformed data, to avoid compounding business logic on top of historical captures.
- **Add `invalidate_hard_deletes: true`** in the config to close out records that disappear from the source (sets `dbt_valid_to` on deleted rows rather than leaving them as perpetually active).

```sql
{{
  config(
    strategy='timestamp',
    updated_at='updated_at',
    invalidate_hard_deletes=true
  )
}}
```

### Key Takeaway

Snapshots are the lowest-effort path to SCD2 history in dbt. Define them early on mutable source tables — customer status, order state, pricing — and you'll never be caught without the historical record when an analyst asks "what did this look like six months ago?"

## 10:03 - dbt Incremental Model Strategies: Choosing the Right Approach for Your Warehouse

Incremental models are dbt's tool for processing only new or changed rows instead of rebuilding entire tables on every run. But **how** dbt applies those rows is controlled by `incremental_strategy`, and picking the wrong one causes either incorrect data or poor performance. Here's a practical breakdown.

### The Four Core Strategies

**1. `merge` (default on Snowflake, BigQuery, Databricks)**

Performs a SQL `MERGE` (upsert): updates existing rows that match on `unique_key`, inserts new ones. Best when you need true upserts and your warehouse supports `MERGE` efficiently.

```sql
{{ config(
    materialized='incremental',
    unique_key='event_id',
    incremental_strategy='merge'
) }}

select
    event_id,
    user_id,
    event_type,
    occurred_at
from {{ source('app', 'events') }}
{% if is_incremental() %}
  where occurred_at > (select max(occurred_at) from {{ this }})
{% endif %}
```

**2. `delete+insert` (default on Redshift, Spark)**

Deletes matching rows by `unique_key`, then inserts the full new batch. Safer than `merge` on column-store warehouses where updates are expensive. Runs as two separate transactions — factor that into failure-recovery thinking.

```sql
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='delete+insert'
) }}
```

**3. `insert_overwrite` (BigQuery, Spark, Databricks)**

Replaces entire partitions rather than individual rows. No `unique_key` needed — dbt drops and rewrites the affected partitions atomically. Ideal for time-partitioned tables where you reprocess a date range.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={
      'field': 'event_date',
      'data_type': 'date',
      'granularity': 'day'
    }
) }}

select
    date(occurred_at) as event_date,
    event_type,
    count(*) as event_count
from {{ source('app', 'events') }}
{% if is_incremental() %}
  where date(occurred_at) >= date_sub(current_date(), interval 3 day)
{% endif %}
group by 1, 2
```

**4. `microbatch` (dbt v1.9+)**

A new first-class strategy that runs the model in time-based batches automatically — dbt subdivides the lookback window and processes each batch independently. Designed for large event tables where a single incremental run would process too much data at once.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='occurred_at',
    begin='2024-01-01'
) }}
```

### Strategy Decision Matrix

| Scenario | Recommended Strategy |
|---|---|
| Append-only events, no duplicates possible | `append` (or no `unique_key` with `merge`) |
| Upserts on high-cardinality key | `merge` |
| Column-store warehouse (Redshift) | `delete+insert` |
| Time-partitioned aggregates | `insert_overwrite` |
| Huge event tables, multi-day backfills | `microbatch` |

### The `--full-refresh` Escape Hatch

All incremental strategies respect `dbt run --full-refresh`, which drops and rebuilds the table from scratch. Keep this in mind for schema migrations: changing a column type on an incremental model requires a full refresh, not an incremental run.

### Key Takeaway

The default `merge` strategy is the safest starting point, but `insert_overwrite` on partitioned tables often outperforms it by 10x or more on BigQuery and Databricks. Profile your query costs after the first month and switch strategies if partition replacement fits your grain.
