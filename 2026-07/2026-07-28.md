# Daily Notes - 2026-07-28

## 00:03 - dbt Model Contracts: Enforcing Column-Level Guarantees at Build Time

Introduced in **dbt v1.5**, model contracts let you declare a formal schema for a model — column names, data types, and constraints — that dbt enforces every time the model builds. Think of it as a compile-time type system for your data warehouse: if the model's output doesn't match the declared contract, the build fails before bad data reaches downstream consumers.

### Why Contracts Matter

Without contracts, a renaming refactor or silent upstream type change can silently break BI dashboards or ML pipelines. A contract turns that silent failure into a loud, early one.

### Defining a Contract

Contracts live in your `.yml` files alongside the model definition:

```yaml
# models/marts/finance/fct_orders.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
      - name: total_amount
        data_type: numeric
      - name: status
        data_type: varchar
```

With `enforced: true`, dbt will:
1. **Check that all declared columns exist** in the model's SELECT output.
2. **Validate data types** match what's declared (adapter-dependent; Snowflake, BigQuery, and Redshift all support this).
3. **Apply constraints** (e.g., `not_null`, `primary_key`, `unique`, `foreign_key`) as database-level constraints where the adapter supports them.

### Supported Constraint Types

| Constraint | Enforced by DB? | Notes |
|---|---|---|
| `not_null` | Yes (most adapters) | Column-level |
| `unique` | Yes (most adapters) | Column-level |
| `primary_key` | Yes (most adapters) | Column or model-level |
| `foreign_key` | Yes (Snowflake, PG) | Requires `to` and `to_columns` |
| `check` | Yes (PG, Redshift) | Custom SQL expression |

```yaml
# Model-level primary key (multi-column)
models:
  - name: fct_order_items
    config:
      contract:
        enforced: true
    constraints:
      - type: primary_key
        columns: [order_id, item_id]
    columns:
      - name: order_id
        data_type: bigint
      - name: item_id
        data_type: bigint
```

### Contracts and Materializations

Contracts are currently supported on **table** and **incremental** materializations only — not views or ephemeral models. If you set `contract.enforced: true` on a view, dbt will raise an error at compile time.

### Contracts in CI/CD

Contracts shine in CI pipelines. Add a `dbt build --select state:modified+` step and any PR that renames a column or changes a type in a contracted model will fail the build, surfacing the breaking change before it merges.

### Key Takeaway

Model contracts are the guardrail that makes it safe to refactor aggressively. Define them on your most critical mart-layer models first — facts tables and dimension tables that BI tools depend on — and expand coverage from there.
