# Daily Notes - 2026-07-31

## 00:03 - dbt Slim CI: Fast, Cost-Efficient CI Pipelines with State-Based Selection

### What Is Slim CI?

Running your full dbt project on every pull request is slow and expensive. Slim CI is the pattern of using dbt's `state:` selector to run only models that have **changed** since the last production run — shrinking CI from minutes to seconds and cutting warehouse costs dramatically.

### The Core Mechanism: Manifest Diffing

dbt compiles every run into a `manifest.json` artifact that describes every node in your DAG (models, tests, seeds, snapshots). Slim CI works by comparing two manifests:

- **Prod manifest** — the last successful production run, stored in your CI artifact store (S3, GCS, dbt Cloud, etc.)
- **PR manifest** — freshly compiled for the current branch

dbt diffs them and identifies which nodes changed.

### Key Selectors

```bash
# Run only models modified in this PR (and their downstream dependents)
dbt run --select state:modified+

# Test only models that were built in this run
dbt test --select state:modified+

# Include ancestors too (useful for catching breakage upstream)
dbt build --select state:modified+ --defer --state ./prod-artifacts/
```

The `--defer` flag is crucial: for any model **not** selected, dbt resolves its `ref()` against the **production** database instead of the dev schema. This lets your modified models join against existing prod data without rebuilding everything.

### Setting Up Slim CI: Step by Step

**1. Download the prod manifest in CI:**
```yaml
# GitHub Actions example
- name: Download prod manifest
  run: |
    aws s3 cp s3://my-bucket/dbt/prod/manifest.json ./prod-artifacts/manifest.json
```

**2. Compile the PR branch:**
```bash
dbt compile --target ci
```

**3. Run slim CI:**
```bash
dbt build \
  --select state:modified+ \
  --defer \
  --state ./prod-artifacts/ \
  --target ci
```

### What Counts as "Modified"?

dbt detects changes in:
- **Model SQL** — the compiled SQL content hash changed
- **Schema/config** — `schema.yml` changes to a model (new tests, description, config)
- **Upstream sources** — if a source's definition changed

It does **not** automatically detect changes in Jinja macros that a model calls. To catch those, use:
```bash
dbt build --select state:modified+ exposure:* --defer --state ./prod-artifacts/
```
Or explicitly add macro-dependent models to your selection.

### dbt Cloud Slim CI

In dbt Cloud, Slim CI is built in. When you create a CI job:
- Set **Defer to a production job** in the job settings
- dbt Cloud automatically fetches the prod manifest and applies `--defer --state`
- You get a per-PR schema (e.g., `dbt_cloud_pr_123_456`) that is auto-dropped after merge

### Best Practices

- **Always test `state:modified+`**, not just `state:modified` — downstream models break when upstream logic changes.
- **Upload your manifest on every successful prod run** so the baseline stays current.
- **Add `--fail-fast`** in CI to stop early on first test failure and save warehouse credits.
- **Combine with `dbt source freshness`** to gate on stale source data before running models.

Slim CI turns a 30-minute full-project run into a 2–3 minute targeted check, making PR feedback loops fast enough that engineers actually act on them.
