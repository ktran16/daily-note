## 00:03 - dbt Slim CI: Fast, Cost-Efficient CI Pipelines with State-Based Selection

### What Is Slim CI?

Running your full dbt project on every pull request is slow and expensive. Slim CI is the pattern of using dbt's `state:` selector to run only models that have **changed** since the last production run — shrinking CI from minutes to seconds and cutting warehouse costs dramatically.

### The Core Mechanism: Manifest Diffing

dbt compiles every run into a `manifest.json` artifact that describes every node in your DAG (models, tests, seeds, snapshots). Slim CI works by comparing two manifests:

- **Prod manifest** — the last successful production run, stored in your CI artifact store (S3, GCS, dbt Cloud, etc.)
- **PR manifest** — freshly compiled for the current branch

dbt diffs them and identifies which nodes changed.

### Key Selectors

```bash
# Run only models modified in this PR (and their downstream dependents)
dbt run --select state:modified+

# Test only models that were built in this run
dbt test --select state:modified+

# Include ancestors too (useful for catching breakage upstream)
dbt build --select state:modified+ --defer --state ./prod-artifacts/
```

The `--defer` flag is crucial: for any model **not** selected, dbt resolves its `ref()` against the **production** database instead of the dev schema. This lets your modified models join against existing prod data without rebuilding everything.

### Setting Up Slim CI: Step by Step

**1. Download the prod manifest in CI:**
```yaml
# GitHub Actions example
- name: Download prod manifest
  run: |
    aws s3 cp s3://my-bucket/dbt/prod/manifest.json ./prod-artifacts/manifest.json
```

**2. Compile the PR branch:**
```bash
dbt compile --target ci
```

**3. Run slim CI:**
```bash
dbt build \
  --select state:modified+ \
  --defer \
  --state ./prod-artifacts/ \
  --target ci
```

### What Counts as "Modified"?

dbt detects changes in:
- **Model SQL** — the compiled SQL content hash changed
- **Schema/config** — `schema.yml` changes to a model (new tests, description, config)
- **Upstream sources** — if a source's definition changed

It does **not** automatically detect changes in Jinja macros that a model calls. To catch those, use:
```bash
dbt build --select state:modified+ exposure:* --defer --state ./prod-artifacts/
```
Or explicitly add macro-dependent models to your selection.

### dbt Cloud Slim CI

In dbt Cloud, Slim CI is built in. When you create a CI job:
- Set **Defer to a production job** in the job settings
- dbt Cloud automatically fetches the prod manifest and applies `--defer --state`
- You get a per-PR schema (e.g., `dbt_cloud_pr_123_456`) that is auto-dropped after merge

### Best Practices

- **Always test `state:modified+`**, not just `state:modified` — downstream models break when upstream logic changes.
- **Upload your manifest on every successful prod run** so the baseline stays current.
- **Add `--fail-fast`** in CI to stop early on first test failure and save warehouse credits.
- **Combine with `dbt source freshness`** to gate on stale source data before running models.

Slim CI turns a 30-minute full-project run into a 2–3 minute targeted check, making PR feedback loops fast enough that engineers actually act on them.

## 05:02 - dbt Snapshots: Capturing Historical Change with SCD Type 2

Most data warehouses only store current state — when a row changes, the old value is gone. **dbt Snapshots** solve this by automatically maintaining a full history of row changes, implementing the classic **Slowly Changing Dimension Type 2 (SCD2)** pattern without any hand-written merge logic.

### How Snapshots Work

dbt compares the source table's current state against the snapshot table on each run. When a row changes (or disappears), dbt:
1. Closes the old record by setting `dbt_valid_to` to the current timestamp
2. Inserts the new record with `dbt_valid_from` = now and `dbt_valid_to` = null (the "current" record)

Four metadata columns are added automatically:

| Column | Meaning |
|--------|---------|
| `dbt_scd_id` | Unique surrogate key for each snapshot row |
| `dbt_updated_at` | When dbt last evaluated this record |
| `dbt_valid_from` | When this version became active |
| `dbt_valid_to` | When this version was superseded (`null` = still current) |

### Defining a Snapshot

Snapshots live in the `snapshots/` directory:

```sql
-- snapshots/orders_snapshot.sql
{% snapshot orders_snapshot %}

{{
    config(
        target_schema='snapshots',
        unique_key='order_id',
        strategy='timestamp',
        updated_at='updated_at'
    )
}}

select * from {{ source('raw', 'orders') }}

{% endsnapshot %}
```

Run with:

```bash
dbt snapshot
# or target a specific snapshot
dbt snapshot --select orders_snapshot
```

### Two Snapshot Strategies

**`timestamp` strategy** — detect changes by comparing an `updated_at` column. Fast and reliable when the source table has a reliable update timestamp:

```sql
config(
    strategy='timestamp',
    updated_at='updated_at'   -- must be a column in the source query
)
```

**`check` strategy** — detect changes by comparing a list of columns. Use when the source has no reliable timestamp:

```sql
config(
    strategy='check',
    check_cols=['status', 'shipping_address', 'customer_id']
    -- or check_cols='all' to compare every column
)
```

`check` is slower (hashes all specified columns per row) but works on sources you don't control.

### Querying Snapshots

The full history is always available. Filter to current records with `dbt_valid_to is null`:

```sql
-- Current state of all orders
select *
from {{ ref('orders_snapshot') }}
where dbt_valid_to is null;

-- Point-in-time query: order statuses as of 2025-06-01
select *
from {{ ref('orders_snapshot') }}
where dbt_valid_from <= '2025-06-01'
  and (dbt_valid_to > '2025-06-01' or dbt_valid_to is null);

-- Full history for a single order
select order_id, status, dbt_valid_from, dbt_valid_to
from {{ ref('orders_snapshot') }}
where order_id = 12345
order by dbt_valid_from;
```

### Handling Hard Deletes

By default, dbt snapshots don't track rows deleted from the source — they just stop being updated. To invalidate deleted rows, add `invalidate_hard_deletes=true`:

```sql
config(
    strategy='timestamp',
    updated_at='updated_at',
    invalidate_hard_deletes=true
)
```

When enabled, dbt sets `dbt_valid_to` on rows that no longer appear in the source query, so deletions are recorded as closed history rather than silently persisting as "current."

### Best Practices

- **Snapshot raw sources, not transformed models.** Snapshots should sit as close to the source as possible; apply business logic downstream in models that `ref()` the snapshot.
- **Run snapshots on a fixed schedule.** The granularity of your history is the snapshot frequency — daily runs = daily granularity. Gaps in the schedule mean gaps in history.
- **Don't use `check_cols='all'` on wide tables.** It hashes every column on every row and can be slow. Enumerate only the columns that represent meaningful state changes.
- **Keep snapshot target schemas separate** from mart schemas. Snapshots are write-append by design and should live in their own dedicated schema (e.g., `snapshots`).
- **Test snapshots like models.** Apply `not_null` and `unique` tests to `dbt_scd_id` to catch corruption early.

Snapshots turn your data warehouse into a time machine — the same `select * where dbt_valid_to is null` pattern gives you current state, while date-bounded queries answer "what did this record look like on any given day?" with no extra ETL work.
