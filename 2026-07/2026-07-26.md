## 00:03 - dbt Grants: Automated Permission Management When Models Build

Managing database permissions is often an afterthought in analytics engineering — until a dashboard breaks because a BI tool lost access to a freshly rebuilt table. dbt's `grants` configuration solves this by automatically re-applying `GRANT` statements every time a model materializes.

### The Problem Without Grants

When dbt builds a `table` or `incremental` model, it often recreates the underlying object (via `CREATE TABLE AS SELECT` or a swap). Any `GRANT` you issued manually on the old object is silently dropped. You have to remember to re-grant — or automate it yourself with hooks.

### Configuring Grants in dbt

Grants are configured as a dictionary under the `grants` key, where keys are privilege names and values are lists of grantee roles:

```yaml
# dbt_project.yml  — applies to all models in the marts/ folder
models:
  my_project:
    marts:
      +grants:
        select: ['reporter_role', 'bi_service_account']
```

You can also configure grants at the model level:

```yaml
# models/marts/finance/schema.yml
models:
  - name: fct_revenue
    config:
      grants:
        select: ['finance_analysts', 'exec_dashboard_role']
```

Or directly in the model's config block:

```sql
-- models/marts/finance/fct_revenue.sql
{{ config(
    materialized='table',
    grants={'select': ['finance_analysts', 'exec_dashboard_role']}
) }}

select ...
```

### How dbt Applies Grants

After each successful model build, dbt calls `GRANT SELECT ON <relation> TO <role>` for each entry. The key behavior to understand is the `copy_grants` setting:

- **`copy_grants: false` (default):** dbt issues only the grants you declared. Any privileges that existed on the old object but aren't in the config are revoked. This is the "declarative" mode — your config is the source of truth.
- **`copy_grants: true`:** dbt preserves all grants from the previous version of the object and adds any new ones. Safer for migrations, but can leave stale access over time.

```yaml
# dbt_project.yml
models:
  my_project:
    +copy_grants: true
```

### Grants with Incremental Models

Incremental models don't recreate the table on every run, so grants are only applied when the model actually modifies the relation. On a no-op run (nothing to process), dbt skips the grant step. This is usually fine — permissions persist since the table wasn't recreated.

### Supported Privileges

Beyond `select`, most warehouses support additional privilege types:

```yaml
grants:
  select: ['reporter_role']
  insert: ['etl_service_account']
  all privileges: ['dbt_admin_role']
```

Privilege names are passed through to the warehouse verbatim, so use whatever syntax your adapter supports (`INSERT`, `UPDATE`, `ALL PRIVILEGES`, etc.).

### Best Practice: Centralize Grants in `dbt_project.yml`

Rather than scattering grants across dozens of `schema.yml` files, define them centrally by layer:

```yaml
models:
  my_project:
    staging:
      +grants:
        select: ['dbt_dev_role']
    marts:
      +grants:
        select: ['bi_role', 'data_consumers']
    sensitive:
      +grants:
        select: ['data_governance_role']
```

This makes permission policy reviewable in one place and ensures no newly added model ships without appropriate access controls.

## 05:02 - dbt store_failures: Capturing and Investigating Test Failures

When a dbt test fails, the default behavior is to report the failure count and move on. But *which* rows failed? With `store_failures`, dbt writes the failing rows into a dedicated table in your warehouse, letting you query them directly for root-cause analysis.

### Enabling store_failures

Set it globally in `dbt_project.yml` or per-test in `schema.yml`:

```yaml
# dbt_project.yml — enable for all tests
tests:
  +store_failures: true
  +schema: test_failures   # optional: direct failures to a dedicated schema
```

```yaml
# schema.yml — enable for one specific test
models:
  - name: orders
    columns:
      - name: customer_id
        tests:
          - not_null:
              config:
                store_failures: true
          - relationships:
              to: ref('customers')
              field: id
              config:
                store_failures: true
                store_failures_as: view  # 'table' (default) or 'view'
```

### What Gets Stored

dbt creates a relation named after the test in the failures schema. For a `not_null` test on `orders.customer_id`, the table is something like:

```
test_failures.not_null_orders_customer_id
```

Each row in that table is a row that **failed** the test. For a `relationships` test, the failing rows are the ones with no match in the referenced model.

```sql
-- Inspect which orders have a null customer_id
SELECT * FROM analytics_test_failures.not_null_orders_customer_id;

-- Inspect which orders reference non-existent customers
SELECT * FROM analytics_test_failures.relationships_orders_customer_id__id__ref_customers_;
```

### store_failures_as: view vs table

| Setting | Behavior |
|---|---|
| `table` (default) | Persists between runs; stale failures remain until the test re-runs |
| `view` | Always reflects the latest test run; no stale data; slightly slower to query |

`view` is usually the better default — you always see current failures without worrying about cleanup.

### Practical Workflow

1. Add `store_failures: true` to tests covering critical columns (foreign keys, not-null constraints on business keys).
2. After a CI run fails, query the failures table directly instead of re-running the model with debug logging.
3. Use the failures table in an exposure or a BI dashboard to monitor data quality trends over time.

```yaml
# Track failure counts in a singular test
-- tests/assert_no_recent_order_failures.sql
SELECT COUNT(*) AS failure_count
FROM {{ ref('not_null_orders_customer_id') }}
WHERE failure_count > {{ var('max_allowed_failures', 0) }}
```

`store_failures` turns flaky test outputs into queryable data — a much faster feedback loop than parsing log output line by line.

## 10:03 - dbt Packages & dbt-utils: Reusable Macros and Tests for Every Project

dbt packages let you import reusable macros, models, and tests from the community into your own project — like npm or pip for analytics engineering. The most widely used package is **dbt-utils**, maintained by dbt Labs, and it's practically a standard addition to every dbt project.

### Installing a Package

Declare packages in `packages.yml` at the project root, then run `dbt deps` to install:

```yaml
# packages.yml
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.0.0", "<2.0.0"]
  - package: calogica/dbt_expectations
    version: [">=0.10.0", "<0.11.0"]
```

```bash
dbt deps   # downloads packages into dbt_packages/
```

Add `dbt_packages/` to `.gitignore` — you commit `packages.yml`, not the installed contents.

### High-Value dbt-utils Macros

**`generate_surrogate_key`** — creates a deterministic hashed key from one or more columns, handling NULLs consistently across warehouses:

```sql
select
    {{ dbt_utils.generate_surrogate_key(['order_id', 'line_item_id']) }} as surrogate_key,
    order_id,
    line_item_id,
    product_id
from {{ ref('stg_order_items') }}
```

**`date_spine`** — generates a complete date series without gaps, essential for reporting:

```sql
{{ dbt_utils.date_spine(
    datepart="day",
    start_date="cast('2024-01-01' as date)",
    end_date="current_date"
) }}
```

**`star`** — selects all columns from a relation except a list of exclusions:

```sql
select
    {{ dbt_utils.star(from=ref('stg_orders'), except=["_loaded_at", "_row_hash"]) }}
from {{ ref('stg_orders') }}
```

**`union_relations`** — unions a list of relations with identical schemas, adding a `_dbt_source_relation` column automatically:

```sql
{{ dbt_utils.union_relations(
    relations=[ref('orders_us'), ref('orders_eu'), ref('orders_apac')]
) }}
```

### dbt-utils Generic Tests

Beyond macros, dbt-utils ships generic tests you can apply in `schema.yml`:

```yaml
models:
  - name: fct_orders
    columns:
      - name: order_id
        tests:
          - dbt_utils.not_empty_string
          - dbt_utils.expression_is_true:
              expression: "> 0"
      - name: order_date
        tests:
          - dbt_utils.not_null_proportion:
              at_least: 0.99   # fail if >1% null
```

### Best Practice: Pin Package Versions

Always pin to a version range — `[">=1.0.0", "<2.0.0"]` — rather than `latest`. Package updates can introduce breaking changes, and a silent `dbt deps` upgrade can break your CI without a code change on your end.

## 15:02 - dbt Model Contracts: Enforcing Schema Guarantees for Downstream Consumers

As dbt projects grow, models become APIs — downstream teams, BI tools, and reverse-ETL pipelines depend on the schema staying stable. **Model contracts** (introduced in dbt 1.5) let you declare that a model's column names and data types are guaranteed, and dbt will fail the build if the actual output violates that contract.

### Why Contracts Matter

Without a contract, a developer can rename a column, change its type, or remove it — and the model still builds successfully. Downstream breakage only surfaces when dashboards go red or pipelines crash. A contract shifts that failure left, to the moment the model is built.

### Enabling a Contract

Set `contract: enforced: true` in the model config, then declare column types in `schema.yml`:

```yaml
# models/marts/finance/schema.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: varchar
        constraints:
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: varchar
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
      - name: total_amount
        data_type: numeric
      - name: status
        data_type: varchar
```

When `enforced: true`, dbt will:
1. Compare the model's actual output columns against the declared contract.
2. Fail the build if any declared column is missing, has the wrong type, or the column order differs (on some adapters).

### Column-Level Constraints

Beyond type enforcement, contracts support database-level constraints that dbt will emit as DDL:

```yaml
columns:
  - name: order_id
    data_type: varchar
    constraints:
      - type: not_null
      - type: unique
      - type: primary_key
  - name: status
    data_type: varchar
    constraints:
      - type: check
        expression: "status IN ('pending', 'fulfilled', 'cancelled')"
```

**Adapter support varies** — Snowflake, BigQuery, Databricks, and Postgres each support different subsets. Check your adapter's docs; dbt will warn if a constraint type is unsupported rather than silently skipping it.

### Model-Level Constraints

You can also declare constraints at the model level for multi-column keys:

```yaml
models:
  - name: fct_order_items
    config:
      contract:
        enforced: true
    constraints:
      - type: primary_key
        columns: [order_id, line_item_id]
    columns:
      - name: order_id
        data_type: bigint
      - name: line_item_id
        data_type: bigint
      - name: product_id
        data_type: bigint
```

### Contracts + Versioned Models

Contracts become essential when combined with **model versions** (`dbt 1.6+`). A versioned model with a contract gives downstream consumers an explicit upgrade path:

```yaml
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 1
        config:
          contract:
            enforced: true
      - v: 2
        config:
          contract:
            enforced: true
```

Consumers reference `ref('fct_orders', v=1)` until they're ready to migrate to `v=2`, and the contract guarantees each version's schema won't silently drift.

### Best Practice: Contracts on Public Models First

Apply contracts to models that cross team boundaries — anything flagged `access: public` in a multi-project setup, or any model consumed by a BI tool or reverse-ETL connector. Internal staging models don't need the overhead; the payoff is in stabilizing the interface models that others depend on.
