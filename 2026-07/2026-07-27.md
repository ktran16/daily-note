## 00:02 - dbt Custom Schema, Database & Alias: Controlling Where Models Land

By default, dbt builds models into a schema derived from your profile's `target.schema`. Every model lands in `<target_schema>.<model_name>`. That's fine for small projects, but production setups almost always need finer-grained control — separating raw, staging, and mart layers into different schemas, or even different databases.

### The Three Config Knobs

**`schema`** — appended to `target.schema` (by default) to create a sub-schema:
```yaml
# dbt_project.yml
models:
  my_project:
    staging:
      +schema: staging
    marts:
      +schema: marts
```
This builds staging models into `<target_schema>_staging` and marts into `<target_schema>_marts`.

**`database`** — routes a model to a different database entirely:
```sql
-- models/marts/finance/revenue.sql
{{ config(database='analytics_prod') }}
SELECT ...
```

**`alias`** — overrides the relation name (the table/view name itself):
```sql
{{ config(alias='dim_customers') }}
SELECT ...
```
Useful when the model filename (`customers.sql`) differs from what downstream consumers expect (`dim_customers`).

### Overriding the Schema Generation Macro

The default `generate_schema_name` macro produces `<target_schema>_<custom_schema>`. In production you usually want just `<custom_schema>` — no prefix. Override it in `macros/`:

```sql
-- macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) -%}
  {%- if custom_schema_name is none -%}
    {{ target.schema }}
  {%- else -%}
    {{ custom_schema_name | trim }}
  {%- endif -%}
{%- endmacro %}
```

Now `+schema: staging` produces the schema `staging` regardless of `target.schema`. This is the most common production pattern — dev and prod use the same schema names, with the environment separated by the target itself.

### Generating Database Names

Similarly, `generate_database_name` controls cross-database routing:
```sql
{% macro generate_database_name(custom_database_name, node) -%}
  {%- if custom_database_name is none -%}
    {{ target.database }}
  {%- else -%}
    {{ custom_database_name | trim }}
  {%- endif -%}
{%- endmacro %}
```

### Practical Folder → Schema Mapping Pattern

A common convention maps the first subdirectory under `models/` to the schema name automatically, keeping your `dbt_project.yml` clean:

```sql
-- macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) -%}
  {%- set parts = node.fqn -%}
  {%- if custom_schema_name is not none -%}
    {{ custom_schema_name | trim }}
  {%- elif parts | length > 2 -%}
    {{ parts[1] }}
  {%- else -%}
    {{ target.schema }}
  {%- endif -%}
{%- endmacro %}
```

With this macro, `models/staging/stg_orders.sql` automatically lands in the `staging` schema — no per-model config needed.

### Key Takeaways

- Use `schema` + `generate_schema_name` for layer separation (staging, marts, etc.)
- Override `generate_schema_name` in production to strip the target prefix
- Use `alias` when the filename and desired relation name differ
- Use `database` for cross-database writes (Snowflake, BigQuery, Redshift all support this via dbt)
- These configs cascade: set them in `dbt_project.yml` for folders, override in `config()` blocks for individual models

## 05:03 - dbt Artifacts: Understanding manifest.json, catalog.json, and run_results.json

Every `dbt run`, `dbt test`, or `dbt compile` writes a set of JSON files to `target/`. These **artifacts** are the machine-readable record of your project and its executions — the foundation of dbt Docs, the dbt Cloud UI, and most third-party integrations.

### The Three Core Artifacts

**`manifest.json`** — compiled at `dbt compile` / any run command. It is the complete graph of your project: every node (model, test, snapshot, seed, source), its compiled SQL, config, dependencies, and metadata.

```json
{
  "nodes": {
    "model.my_project.stg_orders": {
      "unique_id": "model.my_project.stg_orders",
      "depends_on": { "nodes": ["source.my_project.raw.orders"] },
      "compiled_code": "select order_id, ... from raw.orders",
      "config": { "materialized": "view", "schema": "staging" },
      "columns": { "order_id": { "data_type": "integer" } }
    }
  },
  "sources": { ... },
  "exposures": { ... },
  "metrics": { ... }
}
```

Use `manifest.json` for: slim CI (`dbt build --select state:modified+`), impact analysis, custom lineage tools, and documentation generation.

**`catalog.json`** — produced by `dbt docs generate`. Contains the actual schema as it exists in your warehouse — column names, types, row counts. Cross-reference with `manifest.json` to catch schema drift (columns defined in YAML but missing in the warehouse).

```json
{
  "nodes": {
    "model.my_project.stg_orders": {
      "metadata": { "type": "VIEW", "schema": "staging", "name": "stg_orders" },
      "columns": {
        "ORDER_ID": { "type": "NUMBER", "index": 1 }
      },
      "stats": { "row_count": { "value": 125430 } }
    }
  }
}
```

**`run_results.json`** — written after every execution. Records timing, status, and row counts for each node that ran.

```json
{
  "results": [
    {
      "unique_id": "model.my_project.fct_orders",
      "status": "success",
      "execution_time": 4.23,
      "adapter_response": { "rows_affected": 98210 }
    },
    {
      "unique_id": "test.my_project.not_null_fct_orders_order_id",
      "status": "fail",
      "failures": 3
    }
  ]
}
```

### Practical Uses

**Slim CI** — pass `manifest.json` from a production run as the state artifact so `dbt build --select state:modified+` only runs models and their downstream dependencies that changed:

```bash
# In CI, fetch prod manifest first
dbt ls --select state:modified+ --state prod/
dbt build --select state:modified+ --state prod/
```

**Observability** — parse `run_results.json` in a post-run hook or pipeline step to emit execution metrics to your monitoring platform:

```python
import json

with open("target/run_results.json") as f:
    results = json.load(f)

for r in results["results"]:
    if r["status"] == "fail":
        alert(f"{r['unique_id']} failed with {r['failures']} failures")
```

**Schema drift detection** — compare `manifest.json` columns (declared) vs `catalog.json` columns (actual) to find undocumented columns or columns that were dropped.

### Key Takeaways

- `manifest.json` = your project's compiled DAG; use it for state-based builds and tooling
- `catalog.json` = the warehouse's actual schema; use it for drift detection and docs
- `run_results.json` = execution history; use it for monitoring, alerting, and SLA tracking
- All three are versioned (check `metadata.dbt_schema_version`) — schema changes across dbt versions, so pin your parsing logic to a version range
- In dbt Cloud, artifacts are stored per-run and accessible via the Discovery API — no need to manage files manually
