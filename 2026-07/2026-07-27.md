## 00:02 - dbt Custom Schema, Database & Alias: Controlling Where Models Land

By default, dbt builds models into a schema derived from your profile's `target.schema`. Every model lands in `<target_schema>.<model_name>`. That's fine for small projects, but production setups almost always need finer-grained control — separating raw, staging, and mart layers into different schemas, or even different databases.

### The Three Config Knobs

**`schema`** — appended to `target.schema` (by default) to create a sub-schema:
```yaml
# dbt_project.yml
models:
  my_project:
    staging:
      +schema: staging
    marts:
      +schema: marts
```
This builds staging models into `<target_schema>_staging` and marts into `<target_schema>_marts`.

**`database`** — routes a model to a different database entirely:
```sql
-- models/marts/finance/revenue.sql
{{ config(database='analytics_prod') }}
SELECT ...
```

**`alias`** — overrides the relation name (the table/view name itself):
```sql
{{ config(alias='dim_customers') }}
SELECT ...
```
Useful when the model filename (`customers.sql`) differs from what downstream consumers expect (`dim_customers`).

### Overriding the Schema Generation Macro

The default `generate_schema_name` macro produces `<target_schema>_<custom_schema>`. In production you usually want just `<custom_schema>` — no prefix. Override it in `macros/`:

```sql
-- macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) -%}
  {%- if custom_schema_name is none -%}
    {{ target.schema }}
  {%- else -%}
    {{ custom_schema_name | trim }}
  {%- endif -%}
{%- endmacro %}
```

Now `+schema: staging` produces the schema `staging` regardless of `target.schema`. This is the most common production pattern — dev and prod use the same schema names, with the environment separated by the target itself.

### Generating Database Names

Similarly, `generate_database_name` controls cross-database routing:
```sql
{% macro generate_database_name(custom_database_name, node) -%}
  {%- if custom_database_name is none -%}
    {{ target.database }}
  {%- else -%}
    {{ custom_database_name | trim }}
  {%- endif -%}
{%- endmacro %}
```

### Practical Folder → Schema Mapping Pattern

A common convention maps the first subdirectory under `models/` to the schema name automatically, keeping your `dbt_project.yml` clean:

```sql
-- macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) -%}
  {%- set parts = node.fqn -%}
  {%- if custom_schema_name is not none -%}
    {{ custom_schema_name | trim }}
  {%- elif parts | length > 2 -%}
    {{ parts[1] }}
  {%- else -%}
    {{ target.schema }}
  {%- endif -%}
{%- endmacro %}
```

With this macro, `models/staging/stg_orders.sql` automatically lands in the `staging` schema — no per-model config needed.

### Key Takeaways

- Use `schema` + `generate_schema_name` for layer separation (staging, marts, etc.)
- Override `generate_schema_name` in production to strip the target prefix
- Use `alias` when the filename and desired relation name differ
- Use `database` for cross-database writes (Snowflake, BigQuery, Redshift all support this via dbt)
- These configs cascade: set them in `dbt_project.yml` for folders, override in `config()` blocks for individual models

## 05:03 - dbt Artifacts: Understanding manifest.json, catalog.json, and run_results.json

Every `dbt run`, `dbt test`, or `dbt compile` writes a set of JSON files to `target/`. These **artifacts** are the machine-readable record of your project and its executions — the foundation of dbt Docs, the dbt Cloud UI, and most third-party integrations.

### The Three Core Artifacts

**`manifest.json`** — compiled at `dbt compile` / any run command. It is the complete graph of your project: every node (model, test, snapshot, seed, source), its compiled SQL, config, dependencies, and metadata.

```json
{
  "nodes": {
    "model.my_project.stg_orders": {
      "unique_id": "model.my_project.stg_orders",
      "depends_on": { "nodes": ["source.my_project.raw.orders"] },
      "compiled_code": "select order_id, ... from raw.orders",
      "config": { "materialized": "view", "schema": "staging" },
      "columns": { "order_id": { "data_type": "integer" } }
    }
  },
  "sources": { ... },
  "exposures": { ... },
  "metrics": { ... }
}
```

Use `manifest.json` for: slim CI (`dbt build --select state:modified+`), impact analysis, custom lineage tools, and documentation generation.

**`catalog.json`** — produced by `dbt docs generate`. Contains the actual schema as it exists in your warehouse — column names, types, row counts. Cross-reference with `manifest.json` to catch schema drift (columns defined in YAML but missing in the warehouse).

```json
{
  "nodes": {
    "model.my_project.stg_orders": {
      "metadata": { "type": "VIEW", "schema": "staging", "name": "stg_orders" },
      "columns": {
        "ORDER_ID": { "type": "NUMBER", "index": 1 }
      },
      "stats": { "row_count": { "value": 125430 } }
    }
  }
}
```

**`run_results.json`** — written after every execution. Records timing, status, and row counts for each node that ran.

```json
{
  "results": [
    {
      "unique_id": "model.my_project.fct_orders",
      "status": "success",
      "execution_time": 4.23,
      "adapter_response": { "rows_affected": 98210 }
    },
    {
      "unique_id": "test.my_project.not_null_fct_orders_order_id",
      "status": "fail",
      "failures": 3
    }
  ]
}
```

### Practical Uses

**Slim CI** — pass `manifest.json` from a production run as the state artifact so `dbt build --select state:modified+` only runs models and their downstream dependencies that changed:

```bash
# In CI, fetch prod manifest first
dbt ls --select state:modified+ --state prod/
dbt build --select state:modified+ --state prod/
```

**Observability** — parse `run_results.json` in a post-run hook or pipeline step to emit execution metrics to your monitoring platform:

```python
import json

with open("target/run_results.json") as f:
    results = json.load(f)

for r in results["results"]:
    if r["status"] == "fail":
        alert(f"{r['unique_id']} failed with {r['failures']} failures")
```

**Schema drift detection** — compare `manifest.json` columns (declared) vs `catalog.json` columns (actual) to find undocumented columns or columns that were dropped.

### Key Takeaways

- `manifest.json` = your project's compiled DAG; use it for state-based builds and tooling
- `catalog.json` = the warehouse's actual schema; use it for drift detection and docs
- `run_results.json` = execution history; use it for monitoring, alerting, and SLA tracking
- All three are versioned (check `metadata.dbt_schema_version`) — schema changes across dbt versions, so pin your parsing logic to a version range
- In dbt Cloud, artifacts are stored per-run and accessible via the Discovery API — no need to manage files manually

## 10:03 - dbt Source Freshness: Monitoring Data Staleness Before Your Models Build

Raw data arrives on schedules — hourly ELT jobs, nightly exports, webhook streams. When that pipeline silently fails, your models happily rebuild on stale data and users trust numbers that are hours or days old. **Source freshness checks** let dbt detect this before your models run.

### Declaring Freshness on a Source

Freshness is configured in `sources:` YAML alongside the source definition:

```yaml
# models/staging/_sources.yml
sources:
  - name: raw
    database: raw_db
    schema: public
    loaded_at_field: _loaded_at  # column dbt queries to determine recency

    freshness:
      warn_after: { count: 6, period: hour }
      error_after: { count: 24, period: hour }

    tables:
      - name: orders
      - name: customers
        freshness:                        # table-level override
          warn_after: { count: 1, period: hour }
          error_after: { count: 4, period: hour }
      - name: reference_data
        freshness: null                   # explicitly opt out (static table)
```

`loaded_at_field` must be a timestamp column present in every table under that source (or overridden per table). dbt runs `SELECT MAX(<loaded_at_field>) FROM <table>` and compares it against the current timestamp.

### Running the Check

```bash
# Check all sources
dbt source freshness

# Check only specific sources
dbt source freshness --select source:raw.orders

# Check freshness then run models — abort if any error threshold is breached
dbt source freshness && dbt build
```

Results are written to `target/sources.json` — another artifact you can parse in observability pipelines.

### Integrating Freshness into CI/CD

A common pattern gates your dbt run on freshness so stale data never reaches marts:

```bash
# In your CI/CD pipeline or Airflow task
dbt source freshness --select source:raw \
  && dbt build --select +marts \
  || (echo "Source freshness check failed — aborting build" && exit 1)
```

In **dbt Cloud**, source freshness checks can be a dedicated job step with its own schedule — run it before the transformation job and configure the job to abort downstream steps on error.

### Per-Table `loaded_at_field` Overrides

When tables have different timestamp column names, override at the table level:

```yaml
tables:
  - name: events
    loaded_at_field: event_timestamp
  - name: sessions
    loaded_at_field: created_at
```

### What Freshness Does Not Cover

- It only queries the maximum value of `loaded_at_field` — it won't catch gaps (data missing for a specific hour within an otherwise fresh table).
- It doesn't validate row counts or record volume. Pair it with a singular test or dbt Expectations for volume anomaly detection.
- Tables without a reliable timestamp column (append-only logs with no metadata column) need a different strategy, such as a custom macro that queries an audit log table.

### Key Takeaways

- Declare `loaded_at_field` and `freshness` thresholds in your `_sources.yml` to get automated staleness detection
- Use `warn_after` for alerting and `error_after` to block builds on critically stale sources
- Set `freshness: null` on intentionally static tables (seed-like reference data) to skip the check
- `dbt source freshness` writes `sources.json` — parse it in your monitoring stack to track freshness history over time
- Gate production `dbt build` runs on a passing freshness check to prevent downstream models from materializing on stale inputs

## 15:02 - dbt Exposures: Documenting Downstream Consumers in the DAG

dbt models don't live in isolation — dashboards, ML pipelines, and external APIs all depend on them. **Exposures** let you declare those downstream consumers directly in your dbt project, making them first-class citizens of your DAG and enabling impact analysis ("if I change `fct_orders`, which dashboards break?").

### Declaring an Exposure

Exposures are defined in YAML files, typically alongside the models they reference:

```yaml
# models/marts/finance/_exposures.yml
version: 2

exposures:
  - name: revenue_dashboard
    label: "Revenue Dashboard"
    type: dashboard              # dashboard | notebook | analysis | ml | application
    maturity: high               # low | medium | high
    url: https://bi.company.com/dashboards/revenue
    description: >
      Executive revenue dashboard showing MRR, ARR, and cohort retention.
      Refreshes nightly from the finance marts.

    depends_on:
      - ref('fct_revenue')
      - ref('dim_customers')
      - ref('dim_date')

    owner:
      name: Finance Analytics Team
      email: analytics@company.com

  - name: churn_prediction_model
    type: ml
    maturity: medium
    description: >
      Weekly churn propensity model trained on customer engagement signals.
    depends_on:
      - ref('fct_user_events')
      - ref('dim_customers')
    owner:
      name: Data Science
      email: datascience@company.com
```

### What You Get

**Lineage in dbt Docs** — exposures appear at the far right of your DAG. You can trace a dashboard back through marts → intermediate → staging → sources in one view, making it easy to communicate data lineage to non-technical stakeholders.

**Impact analysis via node selection** — select models that feed a specific exposure:

```bash
# See all models that flow into the revenue dashboard
dbt ls --select +exposure:revenue_dashboard

# Rebuild only what the revenue dashboard depends on
dbt build --select +exposure:revenue_dashboard

# In slim CI: rebuild modified models that affect any exposure
dbt build --select state:modified+,exposure:*
```

**`maturity` as a trust signal** — `low` means experimental, `high` means production-critical. Combine with `dbt build --select +exposure:revenue_dashboard` in your deployment pipeline so high-maturity exposures are always rebuilt and tested before the dashboard refreshes.

### Practical Patterns

**Tag your most critical exposures** and build them with extra test coverage in CI:

```yaml
- name: revenue_dashboard
  type: dashboard
  maturity: high
  config:
    tags: ['critical', 'finance']
```

```bash
dbt build --select tag:critical
```

**Use `depends_on` with sources too** — exposures can reference sources directly when a BI tool queries raw tables:

```yaml
depends_on:
  - ref('fct_orders')
  - source('raw', 'payments')  # BI tool hits this directly
```

**Notebook exposures** document ad-hoc analyses so colleagues know which models power a shared Jupyter notebook, preventing someone from "cleaning up" a model that's quietly depended on.

### Why This Matters

Without exposures, the dbt DAG ends at your final mart models. Stakeholders can't see what uses those marts, and engineers don't know the blast radius of a schema change. Exposures close that gap — they make the full data flow, from raw source to business consumer, visible in a single lineage graph.

### Key Takeaways

- Declare exposures in `_exposures.yml` files using `type`, `maturity`, `depends_on`, and `owner`
- Use `+exposure:<name>` in node selection to scope builds and tests to what a specific consumer needs
- `maturity: high` signals production-critical paths; use it to prioritize rebuilds and alerting
- Exposures appear in `dbt docs generate` / dbt Cloud's lineage view — share the docs URL with stakeholders instead of drawing manual diagrams
- They also appear in `manifest.json` under the `exposures` key, enabling custom tooling to extract consumer relationships programmatically

## 19:03 - dbt Model Contracts: Enforcing Schema Guarantees

Introduced in dbt 1.5, **model contracts** let you declare an explicit schema contract for a model — locking down column names, data types, and constraints so that changes to the model's output are caught at build time rather than silently breaking downstream consumers.

### Why Contracts Matter

Without contracts, any dbt model can silently drop a column, change a data type, or rename a field. Downstream models, BI tools, and reverse-ETL pipelines break at query time — often in production. Contracts shift that failure left, to the moment the model is built.

### Enabling a Contract

Contracts are declared in the model's `config` block or in YAML:

```yaml
# models/marts/finance/schema.yml
models:
  - name: fct_revenue
    config:
      contract:
        enforced: true          # turn the contract on

    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key   # documented constraint (not enforced by all adapters)

      - name: revenue_usd
        data_type: numeric
        constraints:
          - type: not_null

      - name: order_date
        data_type: date

      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
```

When `enforced: true`, dbt compiles the model and verifies that:
1. Every column listed in the contract exists in the SELECT output.
2. The declared `data_type` matches what the adapter reports.

If either check fails, `dbt run` exits with an error before any data is written.

### Constraints

Constraints express data guarantees in the contract YAML. Support varies by adapter:

| Constraint type | BigQuery | Snowflake | Redshift | DuckDB |
|---|---|---|---|---|
| `not_null` | enforced | enforced | enforced | enforced |
| `primary_key` | documented only | documented only | documented only | enforced |
| `unique` | documented only | documented only | documented only | enforced |
| `foreign_key` | documented only | enforced | enforced | enforced |

"Documented only" means dbt writes the constraint to `manifest.json` and shows it in docs, but the adapter doesn't create a database-level constraint — it's still useful for documentation and tooling that reads the manifest.

### Model-Level vs Column-Level Constraints

You can also attach constraints to the model itself (table-level):

```yaml
- name: fct_revenue
  config:
    contract:
      enforced: true
  constraints:
    - type: primary_key
      columns: [order_id, order_date]   # composite key
```

### Access Modifiers and Contracts Together

Contracts pair naturally with **access modifiers** (also dbt 1.5+). Mark a model `public` to signal it has a stable, contracted interface that other projects can depend on:

```yaml
- name: fct_revenue
  access: public          # importable by downstream dbt projects via cross-project ref()
  config:
    contract:
      enforced: true
```

A `public` model with an enforced contract is the closest dbt gets to a proper API — external teams can depend on it knowing the schema won't silently change.

### What Contracts Don't Do

- They don't enforce row-level data quality (use `dbt test` or dbt Expectations for that).
- They don't prevent adding new columns — only removing or renaming declared ones.
- `not_null` and `unique` constraints are enforced at the database level only on adapters that support them; on others they're documentation.

### Key Takeaways

- Set `contract.enforced: true` in a model's config to activate schema enforcement at build time
- Declare `data_type` on every contracted column — dbt validates it against the adapter's reported type
- Use constraints (`not_null`, `primary_key`, `foreign_key`) for both enforcement (where supported) and documentation
- Combine `access: public` + `contract.enforced: true` for stable cross-project interfaces
- Contracts catch breaking schema changes before they reach production, shifting failure left from runtime to build time
