## 00:02 - dbt Variables & Environment Variables: Parameterizing Your Project

One of dbt's most underused features is its ability to accept runtime variables and environment variables, letting you write models that behave differently across environments without duplicating code.

### dbt Variables (`var()`)

Variables are passed at the CLI level and consumed in Jinja with `var()`. They're ideal for things like date ranges, feature flags, or controlling the scope of a backfill.

Define defaults in `dbt_project.yml`:

```yaml
# dbt_project.yml
vars:
  start_date: '2024-01-01'
  environment: 'dev'
  enable_pii_masking: true
```

Use them in a model:

```sql
-- models/marts/orders.sql
select
  order_id,
  {% if var('enable_pii_masking') %}
    md5(customer_email) as customer_email
  {% else %}
    customer_email
  {% endif %},
  created_at
from {{ ref('stg_orders') }}
where created_at >= '{{ var("start_date") }}'
```

Override at runtime:

```bash
dbt run --vars '{"start_date": "2025-06-01", "enable_pii_masking": false}'
```

Variables are evaluated at **compile time**, not runtime — they're baked into the SQL before it hits your warehouse.

### Environment Variables (`env_var()`)

For secrets or config that differs by deployment context (dev vs. prod), use `env_var()`. These read from the shell environment, making them a natural fit for CI/CD pipelines.

```yaml
# profiles.yml
my_project:
  target: "{{ env_var('DBT_TARGET', 'dev') }}"
  outputs:
    dev:
      type: snowflake
      database: "{{ env_var('DBT_DATABASE', 'analytics_dev') }}"
      schema: dbt_{{ env_var('DBT_USER', 'default') }}
```

You can also use `env_var()` directly in models or macros:

```sql
-- Dynamically select schema based on environment
select *
from {{ env_var('UPSTREAM_DB', 'raw') }}.orders.events
```

The optional second argument is a **default value** — critical for local dev where the variable may not be set:

```jinja
{{ env_var('SLACK_WEBHOOK_URL', '') }}
```

### Practical Pattern: Environment-Aware Limiting

A common pattern for fast dev iteration is to limit row counts in non-production runs:

```sql
-- models/marts/events.sql
select *
from {{ ref('stg_events') }}
{% if var('environment', 'dev') != 'prod' %}
limit 10000
{% endif %}
```

This keeps dev builds fast without maintaining separate model files.

### Key Differences

| Feature | `var()` | `env_var()` |
|---|---|---|
| Set via | `--vars` CLI flag or `dbt_project.yml` | Shell environment |
| Best for | Business logic params, dates, flags | Secrets, DB credentials, deployment context |
| Default value | Second arg to `var()` | Second arg to `env_var()` |
| Available in | Models, macros, schema.yml | Profiles, models, macros, schema.yml |

Lean on `var()` for anything a data engineer might legitimately want to tweak at runtime, and `env_var()` for anything that varies by deployment environment or should never appear in source control.

## 05:03 - dbt Debugging Techniques: Finding and Fixing Problems Fast

Debugging in dbt means knowing which tools to reach for at each stage — whether you're chasing a Jinja rendering issue, a bad SQL query, or a failing test you can't reproduce.

### 1. `dbt compile` — See the SQL Before You Run It

The single most useful debugging command. It renders all Jinja and writes the compiled SQL to `target/compiled/` without executing anything.

```bash
dbt compile --select my_model
```

Then inspect the output:

```bash
cat target/compiled/my_project/models/marts/my_model.sql
```

This is invaluable when `ref()`, `var()`, or a macro produces unexpected SQL. You can paste the compiled query directly into your warehouse console.

### 2. `dbt debug` — Verify Your Connection and Config

Run this first when a project won't start at all. It checks your `profiles.yml`, warehouse connection, dbt version compatibility, and project structure.

```bash
dbt debug
```

Look for any `FAIL` or `ERROR` lines — they pinpoint whether the problem is credentials, a missing adapter, or a malformed YAML file.

### 3. `{{ log() }}` — Print Values During Compilation

When a macro isn't behaving as expected, insert `log()` calls to print variable values to the console. Set `info=True` to see output even when `--log-level` is at the default.

```jinja
{% macro my_macro(event_type) %}
  {{ log("event_type received: " ~ event_type, info=True) }}
  select * from events where type = '{{ event_type }}'
{% endmacro %}
```

Run any command that invokes the macro and the value appears in your terminal output.

### 4. Isolate Failing Tests with `--select`

When a test suite fails, narrow down to just the broken model rather than re-running everything:

```bash
# Run only tests touching a specific model
dbt test --select my_model

# Run only a specific test type
dbt test --select test_type:not_null

# Run tests on a model and everything upstream
dbt test --select +my_model
```

### 5. Inspect the `target/` Directory

dbt writes several useful artifacts after every run:

| Path | Contents |
|---|---|
| `target/compiled/` | Rendered Jinja SQL (post-compile) |
| `target/run/` | The actual SQL that was executed |
| `target/manifest.json` | Full DAG metadata for every node |
| `target/run_results.json` | Timing and status of the last run |

The `run/` folder is especially useful — if a model compiled fine but failed at execution, the `run/` SQL shows exactly what hit the warehouse.

### 6. `dbt run --fail-fast`

When running many models, stop at the first failure instead of waiting for everything to finish:

```bash
dbt run --fail-fast
```

Pairs well with `--select +failing_model` to quickly iterate on a broken node.

### 7. Check YAML with `dbt parse`

Malformed `schema.yml` can produce cryptic errors. Run `dbt parse` to validate all YAML and Jinja in your project without executing any SQL:

```bash
dbt parse
```

It's fast (under a second for most projects) and surfaces syntax errors immediately.

### Quick Debugging Checklist

1. `dbt debug` — Is the connection working?
2. `dbt parse` — Is the YAML valid?
3. `dbt compile --select <model>` — Is the rendered SQL correct?
4. Check `target/run/<model>.sql` — What actually executed?
5. `{{ log(..., info=True) }}` — What value does that variable hold?
6. `dbt test --select <model>` — Which specific assertion is failing?

Mastering these six steps handles the vast majority of dbt issues without needing to dig into warehouse query history.

## 10:02 - dbt CI/CD with GitHub Actions: Slim CI and State-Based Builds

One of the biggest dbt workflow improvements is setting up a proper CI/CD pipeline that only runs what changed — not every model on every PR. This is called **slim CI**, and it uses dbt's `state:` selection syntax against a production manifest artifact.

### How Slim CI Works

dbt compares your current project against a previously compiled `manifest.json` (your production state). It can then select only models that are **new or modified** since that manifest was generated.

The key selection syntax:

```bash
# Run only models that changed vs. production manifest
dbt run --select state:modified+ --defer --state ./prod-manifest

# Test only what was just built
dbt test --select state:modified+ --defer --state ./prod-manifest
```

- `state:modified` — nodes whose SQL or config changed
- `state:modified+` — those nodes **plus all their downstream dependencies**
- `--defer` — for unmodified upstream refs, use the production relations instead of rebuilding them in CI

### GitHub Actions Workflow

```yaml
# .github/workflows/dbt-ci.yml
name: dbt CI

on:
  pull_request:
    branches: [main]

jobs:
  dbt-slim-ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - name: Install dbt
        run: pip install dbt-snowflake==1.8.0

      - name: Download production manifest
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
        run: |
          mkdir -p prod-manifest
          aws s3 cp s3://my-dbt-artifacts/manifest.json prod-manifest/manifest.json

      - name: dbt compile (current branch)
        env:
          DBT_SNOWFLAKE_ACCOUNT: ${{ secrets.SNOWFLAKE_ACCOUNT }}
          DBT_SNOWFLAKE_USER: ${{ secrets.SNOWFLAKE_USER }}
          DBT_SNOWFLAKE_PASSWORD: ${{ secrets.SNOWFLAKE_PASSWORD }}
        run: dbt compile --target ci

      - name: dbt run (changed models only)
        run: |
          dbt run \
            --select state:modified+ \
            --defer \
            --state prod-manifest \
            --target ci

      - name: dbt test (changed models only)
        run: |
          dbt test \
            --select state:modified+ \
            --defer \
            --state prod-manifest \
            --target ci
```

### Production Manifest Upload (Deployment Job)

Your production deploy job should upload the manifest after each successful run so the CI job always has a fresh reference:

```yaml
      - name: Upload manifest to S3
        if: github.ref == 'refs/heads/main' && success()
        run: |
          aws s3 cp target/manifest.json s3://my-dbt-artifacts/manifest.json
```

### CI-Specific Profile Target

Keep a separate `ci` target in `profiles.yml` that writes to a PR-specific schema, preventing CI builds from polluting your dev or prod environments:

```yaml
# profiles.yml
my_project:
  outputs:
    ci:
      type: snowflake
      schema: "dbt_ci_pr_{{ env_var('GITHUB_PR_NUMBER', 'local') }}"
      threads: 8
      # ... connection details
```

### Why This Matters

| Approach | Runtime on large project |
|---|---|
| `dbt run` (all models) | 45–90 minutes |
| Slim CI (`state:modified+`) | 2–10 minutes |

Slim CI makes dbt PR feedback fast enough to be useful — a 5-minute check that only tests what changed is far more actionable than a 60-minute full run that blocks merges all day.

## 15:02 - dbt Cross-Database Macros: Writing Adapter-Agnostic SQL

One of dbt's most powerful but underappreciated features is the ability to write macros that generate different SQL depending on which warehouse adapter is active. This lets you build a single codebase that runs on Snowflake, BigQuery, Redshift, DuckDB, and others without a forest of `{% if target.type == ... %}` checks cluttering your models.

### The `adapter.dispatch()` Pattern

`adapter.dispatch()` is dbt's polymorphism mechanism. You define a default macro implementation plus optional adapter-specific overrides, and dbt automatically calls the right one at compile time.

```jinja
-- macros/safe_divide.sql

-- Default (fallback for any adapter not explicitly listed)
{% macro safe_divide(numerator, denominator) %}
    {{ return(adapter.dispatch('safe_divide', 'my_project')(numerator, denominator)) }}
{% endmacro %}

{% macro default__safe_divide(numerator, denominator) %}
    case when {{ denominator }} = 0 then null
         else {{ numerator }} / nullif({{ denominator }}, 0)
    end
{% endmacro %}

-- BigQuery override (uses SAFE_DIVIDE built-in)
{% macro bigquery__safe_divide(numerator, denominator) %}
    SAFE_DIVIDE({{ numerator }}, {{ denominator }})
{% endmacro %}

-- Snowflake override (DIV0 handles zero division natively)
{% macro snowflake__safe_divide(numerator, denominator) %}
    DIV0({{ numerator }}, {{ denominator }})
{% endmacro %}
```

Use it in a model like any other macro:

```sql
-- models/marts/conversion_rate.sql
select
    campaign_id,
    {{ safe_divide('conversions', 'impressions') }} as conversion_rate
from {{ ref('stg_ad_events') }}
```

dbt picks the right implementation automatically — no conditional logic in the model itself.

### Common Cross-Database Patterns

**Date truncation** — BigQuery uses `DATE_TRUNC(date, WEEK)` while most others use `DATE_TRUNC('week', date)`:

```jinja
{% macro date_trunc(datepart, date) %}
    {{ return(adapter.dispatch('date_trunc', 'my_project')(datepart, date)) }}
{% endmacro %}

{% macro default__date_trunc(datepart, date) %}
    date_trunc('{{ datepart }}', {{ date }})
{% endmacro %}

{% macro bigquery__date_trunc(datepart, date) %}
    date_trunc({{ date }}, {{ datepart }})
{% endmacro %}
```

**String concatenation** — older Redshift doesn't support `||` in all contexts, preferring `CONCAT()`:

```jinja
{% macro concat(fields) %}
    {{ return(adapter.dispatch('concat', 'my_project')(fields)) }}
{% endmacro %}

{% macro default__concat(fields) %}
    {{ fields | join(' || ') }}
{% endmacro %}

{% macro redshift__concat(fields) %}
    concat({{ fields | join(', ') }})
{% endmacro %}
```

### Using `target.type` for Simple Conditionals

For one-off differences that don't warrant a full dispatch pattern, `target.type` is available in any Jinja context:

```sql
select
    {% if target.type == 'bigquery' %}
        TIMESTAMP_MILLIS(created_at_ms) as created_at
    {% elif target.type == 'snowflake' %}
        TO_TIMESTAMP_NTZ(created_at_ms / 1000) as created_at
    {% else %}
        to_timestamp(created_at_ms / 1000.0) as created_at
    {% endif %}
from {{ ref('stg_events') }}
```

Use `adapter.dispatch()` when the pattern repeats across multiple models; use `target.type` for truly one-off differences.

### dbt-utils Already Does the Heavy Lifting

Before writing your own cross-database macros, check [dbt-utils](https://github.com/dbt-labs/dbt-utils). It ships adapter-agnostic implementations for dozens of common operations:

| dbt-utils macro | What it abstracts |
|---|---|
| `dbt.date_trunc()` | Date truncation across adapters |
| `dbt.datediff()` | Date difference calculations |
| `dbt.concat()` | String concatenation |
| `dbt.current_timestamp()` | UTC timestamp, adapter-safe |
| `dbt.type_string()` / `dbt.type_int()` | Portable data type casting |

```sql
-- Uses dbt-utils for full portability
select
    {{ dbt.date_trunc('month', 'created_at') }} as month,
    count(*) as event_count
from {{ ref('stg_events') }}
group by 1
```

### When This Matters Most

Cross-database macros pay off in three situations:

1. **Multi-warehouse organizations** — analytics team on Snowflake, ML team on BigQuery, both sharing the same dbt repo.
2. **Package authors** — if you publish a dbt package, you need adapter-agnostic macros or you'll alienate most of your users.
3. **Local development with DuckDB** — many teams run dbt locally against DuckDB for speed, then deploy to Snowflake/BigQuery in CI. Cross-database macros make this seamless.

The `adapter.dispatch()` pattern keeps your models clean and your warehouse-specific logic centralized in one place — the macros directory.

## 19:03 - dbt Snapshots: Tracking History with Type 2 Slowly Changing Dimensions

Most source data shows only the current state of a record — when a customer changes their plan tier or a ticket changes status, the previous value is simply overwritten. dbt **snapshots** solve this by capturing a historical record of every change, implementing the classic data warehousing pattern known as a **Type 2 Slowly Changing Dimension (SCD2)**.

### How Snapshots Work

A snapshot is a special dbt node (`.sql` file in the `snapshots/` directory) that runs incrementally. Each execution:
1. Reads the **current state** of the source table.
2. Compares it against the last snapshot.
3. Closes out changed rows by setting `dbt_valid_to`.
4. Inserts new rows for current values with `dbt_valid_to = null`.

The result is a table where **every historical state of every record** is preserved as its own row.

### Snapshot File Structure

```sql
-- snapshots/customer_snapshot.sql
{% snapshot customer_snapshot %}

{{
  config(
    target_schema='snapshots',
    unique_key='customer_id',
    strategy='timestamp',
    updated_at='updated_at',
    invalidate_hard_deletes=True
  )
}}

select
    customer_id,
    name,
    email,
    plan_tier,
    updated_at
from {{ source('crm', 'customers') }}

{% endsnapshot %}
```

### The Two Snapshot Strategies

**`timestamp` strategy** — compares an `updated_at` column. Use this when your source reliably updates a timestamp on every change. This is the preferred approach.

```yaml
strategy: timestamp
updated_at: updated_at
```

**`check` strategy** — hashes a list of columns and detects changes even without a timestamp. More expensive but works on sources that don't maintain an `updated_at` field.

```yaml
strategy: check
check_cols: ['name', 'email', 'plan_tier']
# or check_cols: 'all'  # hashes every column
```

### What dbt Adds to Your Snapshot Table

dbt automatically adds four metadata columns to every snapshot:

| Column | Description |
|---|---|
| `dbt_scd_id` | Unique surrogate key for each snapshot row |
| `dbt_updated_at` | When this row was captured by the snapshot |
| `dbt_valid_from` | When this version of the record became active |
| `dbt_valid_to` | When this version was superseded (`null` = current) |

### Querying Snapshot History

```sql
-- All historical states for a single customer
select
    customer_id,
    plan_tier,
    dbt_valid_from,
    dbt_valid_to,
    coalesce(dbt_valid_to, current_timestamp()) as effective_until
from {{ ref('customer_snapshot') }}
where customer_id = 'cust_001'
order by dbt_valid_from;
```

```sql
-- Current state only (equivalent to the source table)
select *
from {{ ref('customer_snapshot') }}
where dbt_valid_to is null;
```

```sql
-- Point-in-time lookup: what plan was each customer on at 2025-12-31?
select
    customer_id,
    plan_tier
from {{ ref('customer_snapshot') }}
where '2025-12-31' between dbt_valid_from and coalesce(dbt_valid_to, '9999-12-31');
```

### Hard Deletes

By default, rows deleted from the source table are **not** tracked — the snapshot row simply stays open (`dbt_valid_to = null`). Setting `invalidate_hard_deletes=True` closes those rows when the source record disappears:

```sql
{{
  config(
    ...
    invalidate_hard_deletes=True
  )
}}
```

### Running Snapshots

```bash
# Run all snapshots
dbt snapshot

# Run a specific snapshot
dbt snapshot --select customer_snapshot
```

Snapshots should run **before** your downstream models so that staging and mart models can join against the latest snapshot state. In a typical production schedule: `dbt snapshot && dbt run && dbt test`.

### When to Use Snapshots vs. Incremental Models

| Use Snapshots when... | Use Incremental Models when... |
|---|---|
| You need to track *every change* to a record | You're accumulating new rows (events, transactions) |
| Source data overwrites in place (no history) | Source already contains full history |
| You need point-in-time lookups | You're optimizing for append performance |

Snapshots are one of dbt's most valuable features for analytical use cases — they transform mutable OLTP sources into the immutable historical record that analytics and ML workflows depend on.
