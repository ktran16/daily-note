# Daily Notes - 2026-07-29

## 00:02 - dbt Semantic Layer & MetricFlow: Defining Metrics Once, Querying Everywhere

The **dbt Semantic Layer** (powered by MetricFlow) lets you define business metrics in your dbt project and serve them consistently to any downstream BI tool — eliminating the "metric sprawl" problem where `revenue` means something slightly different in every dashboard.

### Core Concepts

The Semantic Layer introduces two new YAML configuration types alongside your models:

**Semantic Models** — describe the physical shape of a model and declare its *entities*, *dimensions*, and *measures*:

```yaml
# models/marts/semantic/sem_orders.yml
semantic_models:
  - name: orders
    model: ref('fct_orders')
    entities:
      - name: order_id
        type: primary
      - name: customer_id
        type: foreign
    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day
      - name: status
        type: categorical
    measures:
      - name: order_amount
        agg: sum
        expr: amount
      - name: order_count
        agg: count_distinct
        expr: order_id
```

**Metrics** — built on top of measures and optionally filtered or combined:

```yaml
metrics:
  - name: revenue
    type: simple
    label: "Gross Revenue"
    type_params:
      measure: order_amount

  - name: completed_revenue
    type: simple
    label: "Revenue from Completed Orders"
    type_params:
      measure: order_amount
    filter: |
      {{ Dimension('orders__status') }} = 'completed'

  - name: avg_order_value
    type: ratio
    label: "Average Order Value"
    type_params:
      numerator: revenue
      denominator: order_count
```

### Querying the Semantic Layer

With dbt Cloud, you can query metrics via the **Semantic Layer APIs** or the **dbt Cloud CLI**:

```bash
# Query revenue broken down by month and status
dbt sl query \
  --metrics revenue \
  --group-by metric_time__month,orders__status \
  --limit 50
```

BI tools like Tableau, Looker, and Mode can connect directly to the Semantic Layer endpoint, always reading from the same canonical metric definitions.

### Why It Matters

| Old world | Semantic Layer |
|---|---|
| Metric logic duplicated per dashboard | Defined once in YAML |
| `revenue` differs across reports | Single source of truth |
| Analyst must know SQL | BI tool queries metrics by name |
| Ad hoc joins, inconsistent grain | MetricFlow handles joins automatically |

### Key Limitations to Know

- Semantic Layer requires **dbt Cloud** (Team/Enterprise) for the hosted API; dbt Core users can use MetricFlow locally via `dbt sl` commands but cannot serve it to BI tools without the Cloud endpoint.
- Semantic models must reference **a single model** — you cannot join across semantic models in the definition itself; MetricFlow handles multi-hop joins through entity relationships at query time.
- Time dimensions require explicit `time_granularity`; without it, `metric_time` grouping won't work.

The Semantic Layer is the clearest path to consistent, trustworthy metrics across a large organization — worth the YAML overhead as soon as the same metric appears in more than one place.
