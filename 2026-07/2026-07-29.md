## 00:02 - dbt Semantic Layer & MetricFlow: Defining Metrics Once, Querying Everywhere

The **dbt Semantic Layer** (powered by MetricFlow) lets you define business metrics in your dbt project and serve them consistently to any downstream BI tool — eliminating the "metric sprawl" problem where `revenue` means something slightly different in every dashboard.

### Core Concepts

The Semantic Layer introduces two new YAML configuration types alongside your models:

**Semantic Models** — describe the physical shape of a model and declare its *entities*, *dimensions*, and *measures*:

```yaml
# models/marts/semantic/sem_orders.yml
semantic_models:
  - name: orders
    model: ref('fct_orders')
    entities:
      - name: order_id
        type: primary
      - name: customer_id
        type: foreign
    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day
      - name: status
        type: categorical
    measures:
      - name: order_amount
        agg: sum
        expr: amount
      - name: order_count
        agg: count_distinct
        expr: order_id
```

**Metrics** — built on top of measures and optionally filtered or combined:

```yaml
metrics:
  - name: revenue
    type: simple
    label: "Gross Revenue"
    type_params:
      measure: order_amount

  - name: completed_revenue
    type: simple
    label: "Revenue from Completed Orders"
    type_params:
      measure: order_amount
    filter: |
      {{ Dimension('orders__status') }} = 'completed'

  - name: avg_order_value
    type: ratio
    label: "Average Order Value"
    type_params:
      numerator: revenue
      denominator: order_count
```

### Querying the Semantic Layer

With dbt Cloud, you can query metrics via the **Semantic Layer APIs** or the **dbt Cloud CLI**:

```bash
# Query revenue broken down by month and status
dbt sl query \
  --metrics revenue \
  --group-by metric_time__month,orders__status \
  --limit 50
```

BI tools like Tableau, Looker, and Mode can connect directly to the Semantic Layer endpoint, always reading from the same canonical metric definitions.

### Why It Matters

| Old world | Semantic Layer |
|---|---|
| Metric logic duplicated per dashboard | Defined once in YAML |
| `revenue` differs across reports | Single source of truth |
| Analyst must know SQL | BI tool queries metrics by name |
| Ad hoc joins, inconsistent grain | MetricFlow handles joins automatically |

### Key Limitations to Know

- Semantic Layer requires **dbt Cloud** (Team/Enterprise) for the hosted API; dbt Core users can use MetricFlow locally via `dbt sl` commands but cannot serve it to BI tools without the Cloud endpoint.
- Semantic models must reference **a single model** — you cannot join across semantic models in the definition itself; MetricFlow handles multi-hop joins through entity relationships at query time.
- Time dimensions require explicit `time_granularity`; without it, `metric_time` grouping won't work.

The Semantic Layer is the clearest path to consistent, trustworthy metrics across a large organization — worth the YAML overhead as soon as the same metric appears in more than one place.

## 05:03 - dbt Unit Tests: Testing Model Logic with Mock Data

**dbt Unit Tests** (introduced in dbt 1.8) let you verify the SQL logic inside a model without relying on real warehouse data. You define mock input rows and the expected output rows in YAML — dbt compiles everything into a CTE-based test query and runs it during `dbt test`.

### Why Unit Tests Over Data Tests?

Data tests (`not_null`, `unique`, custom SQL) validate *the data in your warehouse*. Unit tests validate *your model's transformation logic* in isolation. This means:

- You can test edge cases (null inputs, boundary values, division-by-zero guards) without seeding your warehouse.
- Tests run fast — no full model build required, just `dbt test --select <model_name>`.
- Regressions in business logic are caught before deployment.

### Basic Example

Suppose you have a model `fct_orders` that categorizes orders by size:

```sql
-- models/marts/fct_orders.sql
select
    order_id,
    customer_id,
    amount,
    case
        when amount < 50  then 'small'
        when amount < 500 then 'medium'
        else                   'large'
    end as order_tier
from {{ ref('stg_orders') }}
```

Define a unit test in YAML (place alongside the model or in a `tests/` YAML file):

```yaml
# models/marts/fct_orders.yml
unit_tests:
  - name: test_order_tier_classification
    model: fct_orders
    given:
      - input: ref('stg_orders')
        rows:
          - {order_id: 1, customer_id: 10, amount: 25.00}
          - {order_id: 2, customer_id: 11, amount: 100.00}
          - {order_id: 3, customer_id: 12, amount: 750.00}
          - {order_id: 4, customer_id: 13, amount: 49.99}
          - {order_id: 5, customer_id: 14, amount: 500.00}
    expect:
      rows:
        - {order_id: 1, order_tier: 'small'}
        - {order_id: 2, order_tier: 'medium'}
        - {order_id: 3, order_tier: 'large'}
        - {order_id: 4, order_tier: 'small'}
        - {order_id: 5, order_tier: 'large'}
```

Run it with:

```bash
dbt test --select fct_orders --indirect-selection=cautious
# or specifically:
dbt test --select "fct_orders,test_type:unit"
```

### Key Behaviours & Tips

| Feature | Detail |
|---|---|
| **Column subsetting** | `expect.rows` only needs the columns you care about — other columns are ignored in the comparison. |
| **Overriding `ref()` / `source()`** | Each `given.input` maps to one upstream ref or source; you can omit inputs not needed for the logic under test. |
| **`format: csv`** | For many rows, use `format: csv` under `given.input` and supply a multiline CSV string instead of YAML lists. |
| **Incremental models** | Add `overrides: {is_incremental: true}` in the unit test to simulate an incremental run and test your `{% if is_incremental() %}` branch. |
| **`config.tags`** | Tag unit tests with `tags: [unit]` so you can run all unit tests in CI with `--select tag:unit`. |

### Testing the Incremental Branch

```yaml
unit_tests:
  - name: test_incremental_dedup
    model: fct_events
    overrides:
      is_incremental: true   # forces the {% if is_incremental() %} path
    given:
      - input: ref('stg_events')
        rows:
          - {event_id: 'abc', event_ts: '2024-01-02'}
      - input: this          # the existing table snapshot
        rows:
          - {event_id: 'abc', event_ts: '2024-01-01'}
    expect:
      rows:
        - {event_id: 'abc', event_ts: '2024-01-02'}  # newer row wins
```

Unit tests are one of the highest-ROI additions in recent dbt releases — add them whenever a model contains branching logic (`CASE`, `IFF`, `COALESCE`) or business rules that would be painful to debug after a bad deploy.

## 10:03 - dbt Model Contracts: Enforcing Schemas Between Producers and Consumers

**Model contracts** (introduced in dbt 1.5) let you declare a binding schema for a model — column names, data types, and constraints — that dbt enforces at build time. They're the backbone of reliable data contracts in a dbt project where multiple teams consume the same models.

### Why Contracts Matter

Without contracts, a model's column structure is implicit. A developer can rename `customer_id` to `cust_id` or change a column type, and downstream consumers only find out when their dashboards break. Contracts make the schema explicit and enforced.

### Enabling a Contract

Add `contract: {enforced: true}` to a model's config block, then list every column with its `data_type`:

```yaml
# models/marts/fct_orders.yml
models:
  - name: fct_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: bigint
        constraints:
          - type: not_null
          - type: primary_key  # informational only in most adapters
      - name: customer_id
        data_type: bigint
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
      - name: amount
        data_type: numeric
      - name: status
        data_type: varchar
```

When you run `dbt run`, dbt compares the contract's declared columns against the model's actual SELECT output. If there's a mismatch — missing column, wrong type, extra undeclared column — **the run fails before any data is written**.

### Supported Constraints

| Constraint type | Enforced in warehouse? | Notes |
|---|---|---|
| `not_null` | Yes (most adapters) | Fails insert if null appears |
| `unique` | Varies | BigQuery / Snowflake support it |
| `primary_key` | Informational | Rarely enforced at DB level |
| `foreign_key` | Informational | Useful for documentation |
| `check` | Adapter-specific | Supported on Postgres/Redshift |

Use `enforced: true` on constraints you want the warehouse to reject at write time; leave others as documentation.

### Contracts + Versions

Contracts pair naturally with **model versioning** (`versions:` in dbt 1.6+). When you release `fct_orders_v2` with a schema change, you keep `fct_orders` (v1) contractually stable for existing consumers while allowing an opt-in migration path:

```yaml
models:
  - name: fct_orders
    latest_version: 2
    versions:
      - v: 1
        config:
          contract: {enforced: true}
      - v: 2
        config:
          contract: {enforced: true}
```

Downstream models reference `ref('fct_orders', version=1)` until they're ready to migrate.

### Practical Tips

- **Start with high-fan-out models** — marts consumed by BI tools or external teams are the best first candidates.
- **`data_type` must match the adapter's dialect** — use `bigint` for BigQuery/Snowflake, `integer` for Postgres; dbt does not normalize type names across adapters.
- **Contracts block column reordering** — SELECT column order must match the YAML declaration order on some adapters (Snowflake, Redshift). Use `dbt compile` to verify before a first run.
- **Seed and snapshot models** do not yet support contracts — contracts only apply to SQL models and Python models.

Model contracts shift schema governance left — catching breaking changes in CI rather than in production dashboards.

## 15:03 - dbt Node Selection & Graph Operators: Targeting Exactly What You Need

The `--select` flag (aliased as `-s`) is the most powerful lever for controlling which models, tests, seeds, and snapshots dbt touches. Mastering it turns a full-project run into a surgical operation.

### Basic Selection Syntax

```bash
# Single model
dbt run --select fct_orders

# All models in a directory (recursive)
dbt run --select models/marts/

# All models in a package
dbt run --select package:dbt_utils
```

### Graph Operators

Operators extend a node selector to include its upstream/downstream neighbors:

| Operator | Meaning | Example |
|---|---|---|
| `+model` | model + all its **parents** (upstream) | `+fct_orders` |
| `model+` | model + all its **children** (downstream) | `fct_orders+` |
| `+model+` | model + full upstream **and** downstream graph | `+fct_orders+` |
| `1+model` | model + exactly 1 level of parents | `1+fct_orders` |
| `model+2` | model + exactly 2 levels of children | `fct_orders+2` |
| `@model` | model + all parents + all tests of those parents | `@stg_orders` |

```bash
# Rebuild fct_orders and everything it depends on
dbt run --select +fct_orders

# Run only models downstream of a changed staging model (1 level)
dbt run --select stg_customers+1

# The @ operator: great for testing — builds the model plus its full
# upstream graph so all tests have the data they need
dbt test --select @fct_revenue
```

### Set Operators

Combine selectors with set logic using spaces (union), commas (intersection), and `--exclude`:

```bash
# UNION: run fct_orders AND stg_customers (and their deps separately)
dbt run --select fct_orders stg_customers

# EXCLUDE: run all marts except one heavy model
dbt run --select models/marts/ --exclude fct_large_events

# INTERSECTION: models tagged 'nightly' that are also tables
dbt run --select tag:nightly,config.materialized:table
```

### Selector Qualifiers

Qualifiers let you filter by metadata rather than node names:

```bash
# By tag
dbt run --select tag:finance

# By config property
dbt run --select config.materialized:incremental
dbt run --select config.schema:reporting

# By source (upstream raw table)
dbt run --select source:salesforce

# By path
dbt run --select path:models/staging/salesforce/

# By exposure (everything that feeds a specific BI exposure)
dbt run --select +exposure:weekly_revenue_report
```

### State-Based Selection (Slim CI)

The most powerful production pattern: only build models whose code or upstream dependencies have **changed** since the last successful run:

```bash
# Download the previous run's manifest.json to a 'state/' folder, then:
dbt run --select state:modified+ --defer --state ./state

# state:modified    — models whose SQL/YAML changed
# state:modified+   — those models plus all downstream
# state:new         — models that didn't exist in the previous state
```

This is the foundation of **Slim CI**: your CI pipeline only runs the models actually affected by a PR, cutting run times from hours to minutes.

### Reusable Selectors (YAML)

For complex selectors you use repeatedly, encode them in `selectors.yml` at the project root:

```yaml
# selectors.yml
selectors:
  - name: nightly_finance
    definition:
      union:
        - method: tag
          value: finance
        - method: tag
          value: nightly
      exclude:
        - method: config.materialized
          value: ephemeral

  - name: changed_and_downstream
    default: true   # used when no --select is given
    definition:
      method: state
      value: modified+
```

```bash
dbt run --selector nightly_finance
```

Investing time in node selection pays off at every scale — it's the difference between a 45-minute full run and a 3-minute targeted one.
