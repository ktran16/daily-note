## 00:03 - [Data Engineering] Dagster I/O Managers: When Returning Data Is the Wrong Move

In Dagster, whatever an asset function *returns* is handed to an **I/O manager**, which decides where that value is persisted and how downstream assets load it back. This is the piece people skip, and it produces two classic failures.

**Failure 1: the pointless round trip.** If your asset already writes to the warehouse — a dbt model, a Spark SQL `INSERT`, a `CREATE TABLE AS` — returning a DataFrame makes Dagster pickle the data a second time, somewhere else. Now you have two copies and one is a lie. Declare the dependency without passing the data:

```python
from dagster import asset, MaterializeResult

@asset(deps=["raw_orders"])          # edge in the graph, no data handoff
def stg_orders(snowflake: SnowflakeResource) -> MaterializeResult:
    with snowflake.get_connection() as conn:
        conn.cursor().execute("""
            CREATE OR REPLACE TABLE stg_orders AS
            SELECT * FROM raw_orders WHERE status IS NOT NULL
        """)
    return MaterializeResult(metadata={"dagster/row_count": 1_250})
```

`deps=[...]` gives ordering and lineage. A function *parameter* means "load the upstream value through an I/O manager" — only use it when you actually want the data in Python memory.

**Failure 2: the default that works only on your laptop.** The default `fs_io_manager` pickles to local disk. Under `multiprocess_executor` on one box that's fine; on Kubernetes, each step is a separate pod, and the downstream step finds nothing. Point it at shared storage:

```python
from dagster import Definitions
from dagster_aws.s3 import S3PickleIOManager, S3Resource

defs = Definitions(
    assets=[...],
    resources={"io_manager": S3PickleIOManager(
        s3_resource=S3Resource(), s3_bucket="dagster-io", s3_prefix="prod"
    )},
)
```

Two practical notes. Override per asset with `@asset(io_manager_key="warehouse_io")` — mixing a Parquet manager and a pickle manager in one graph is normal. And for partitioned assets, the manager receives `context.partition_key`, so each partition lands on its own path and a backfill overwrites exactly one slice instead of the whole table.

Rule of thumb: **data small enough to pass through Python, return it; data that lives in the warehouse, keep it there and pass only the edge.**

## 05:05 - [Data Analytics] TABLESAMPLE: SYSTEM Is Fast, BERNOULLI Is Random, and Only One of Them Can Be Quoted

Sampling a big table is the cheapest way to iterate on a query. Picking the wrong sampling method turns it into a number you shouldn't report.

```sql
-- Postgres: block-level. Reads ~1% of pages, returns every row in them.
SELECT * FROM events TABLESAMPLE SYSTEM (1) REPEATABLE (42);

-- Postgres: row-level. Scans ALL pages, keeps each row with p=0.01.
SELECT * FROM events TABLESAMPLE BERNOULLI (1) REPEATABLE (42);
```

`SYSTEM` is the fast one because it skips pages — on a 500 GB table it touches ~5 GB. `BERNOULLI` still does a full scan; it only shrinks what comes out. BigQuery's `TABLESAMPLE SYSTEM (1 PERCENT)` works the same way and actually lowers bytes billed. Snowflake offers both as `SAMPLE SYSTEM (1)` / `SAMPLE BERNOULLI (1)`; DuckDB uses `USING SAMPLE 1% (bernoulli)`.

The catch is that pages are not randomly composed. Rows land on disk in insert order, or in whatever order a `CLUSTER BY` imposed, so a block sample is a **cluster sample**. If a page holds ~200 rows that were all written in the same hour by the same few accounts, your 10,000-row `SYSTEM` sample contains roughly 50 independent units, not 10,000. The standard error on a 50% conversion rate goes from ±0.5pp to about ±7pp — and nothing in the result set warns you.

Two more traps:

- **Neither returns a fixed row count.** `SYSTEM (1)` gives you *about* 1%. For exactly N rows use `tsm_system_rows` in Postgres, `SAMPLE (1000 ROWS)` in Snowflake, or `USING SAMPLE reservoir(1000 ROWS)` in DuckDB. `ORDER BY random() LIMIT 1000` is unbiased but sorts the whole table.
- **Never sample both sides of a join.** Two independent 1% samples retain ~0.01% of matching pairs, so your join looks broken. Sample on the key instead, which keeps every row for the chosen entities:

```sql
WHERE MOD(ABS(HASH(user_id)), 100) = 0   -- 1% of users, all their events
```

Always pass `REPEATABLE`/`SEED` so a rerun reproduces the same rows.

**Rule of thumb:** `SYSTEM` for "does this query work and what shape is the data"; hash-on-key or `BERNOULLI` for any number that reaches a slide.

## 10:03 - [ML & AI] Matryoshka Embeddings: Truncate to 512 Dims, Keep 97% of the Recall

Vector search cost is linear in dimension — in RAM, in index build time, and in every distance computation. 10M vectors at 3072 dims in fp32 is 10e6 × 3072 × 4 = **123 GB**. The same corpus at 512 dims is **20.5 GB**, and HNSW traversal gets ~6x cheaper per hop. The tempting move is to just slice `vec[:512]`.

For most embedding models that destroys them. A standard contrastive objective spreads information arbitrarily across dimensions, so the first 512 are not a summary — they're a random 1/6th. **Matryoshka Representation Learning** (Kusupati et al., 2022) fixes this by training with a *sum* of losses over nested prefixes:

```
L = Σ_{d ∈ {64,128,256,512,1024,...,D}}  w_d · L_contrastive(vec[:d])
```

Every prefix is optimized to be a usable embedding on its own, which front-loads variance into the early dimensions. OpenAI's `text-embedding-3-*`, Nomic's `embed-text-v1.5`, and Gemini's embedding models are all trained this way; OpenAI reports `text-embedding-3-large` truncated to 256 dims still beating `ada-002` at its full 1536.

**The bug everyone hits:** truncating a unit vector leaves it with norm < 1. Cosine is scale-invariant so it survives, but dot-product/inner-product indexes and anything assuming unit norm silently degrade. Renormalize:

```python
import numpy as np

def truncate(emb, d):
    v = emb[..., :d]
    return v / np.linalg.norm(v, axis=-1, keepdims=True)

# Or server-side, which also cuts egress:
client.embeddings.create(model="text-embedding-3-large",
                         input=docs, dimensions=512)  # already normalized
```

**Adaptive retrieval** is the pattern worth stealing: ANN-search 1000 candidates on 256-dim vectors, then rerank those exactly against the full 3072-dim vectors you kept on disk. You pay small-index memory and large-index accuracy.

Before shipping any truncation, sweep `d ∈ {64,128,256,512,1024,full}` and plot recall@10 on *your* queries. The curve is flat then falls off a cliff, and where the cliff sits is corpus-specific — not a number you can read off a model card.
