## 00:03 - [Data Engineering] Spark `foreachBatch`: The Sink That Quietly Gives Up Exactly-Once

Structured Streaming's built-in sinks are exactly-once. The moment you reach for `foreachBatch` — to upsert, to write two tables, to call an external system — you drop to **at-least-once**, and nothing warns you.

```python
def write_batch(df, batch_id):
    df.write.format("delta").mode("append").save(PATH)

(spark.readStream.format("kafka").option("subscribe", "orders").load()
   .writeStream.foreachBatch(write_batch)
   .option("checkpointLocation", CKPT).start())
```

The checkpoint records batch *N* as complete only **after** your function returns. Lose the driver between the append and that commit and batch *N* replays on restart — same offsets, same rows, appended twice. The job looks healthy; your revenue is 2% high for one window.

Two fixes, and the choice depends on whether rows have a key.

**Append-only: let Delta dedupe the batch.** Delta records a `SetTransaction(appId, version)` in the table log and ignores any write whose version it has already seen:

```python
def write_batch(df, batch_id):
    (df.write.format("delta")
       .option("txnAppId", "orders_ingest")   # stable across restarts
       .option("txnVersion", batch_id)        # monotonic per batch
       .mode("append").save(PATH))
```

Because `batch_id` is deterministic for a given checkpoint, the replay becomes a no-op. The tracking is per table, so the same pair is fine across two different tables — but two appends to the *same* table inside one batch with the same pair means **the second is silently dropped**. Give each write its own `txnAppId`.

**Keyed data: MERGE.** Dedupe within the batch first, or the merge fails on multiple source matches:

```python
from pyspark.sql import Window, functions as F

def upsert(df, batch_id):
    w = Window.partitionBy("order_id").orderBy(F.col("ts").desc())
    latest = df.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")
    (DeltaTable.forName(spark, "orders").alias("t")
       .merge(latest.alias("s"), "t.order_id = s.order_id")
       .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())
```

Two more traps. `df` inside `foreachBatch` is lazy — two writes means two scans of the source, so `df.persist()` before the first and `unpersist()` after. And external sinks (an HTTP API, a non-transactional table) have no log to dedupe against: you need an idempotency key derived from `batch_id`, not a retry wrapper.

Test it rather than trusting it: stop the query, roll the checkpoint back one batch, restart, and compare row counts. If the count moves, the sink isn't idempotent.

## 05:04 - [Data Analytics] The Chasm Trap: Two Fact Tables, One Shared Key, Every Measure Wrong by a Different Factor

Fan-out — a fact row duplicated by a one-to-many dimension — is the join bug everyone has been burned by. The chasm trap is its less-discussed sibling, and it inflates *every* measure by a different factor.

Two fact tables, one shared key:

```sql
select c.customer_id,
       sum(o.amount)      as revenue,
       count(t.ticket_id) as tickets
from customers c
join orders           o on o.customer_id = c.customer_id
join support_tickets  t on t.customer_id = c.customer_id
group by 1;
```

Customer 88 has 3 orders of $100 and 4 tickets. The join emits 3 x 4 = 12 rows. `revenue` returns $1,200 instead of $300 — multiplied by 4, the ticket count — and `tickets` returns 12 instead of 4, multiplied by 3, the order count. Each measure is scaled by the *other* table's cardinality, which varies per customer. So there is no constant you can divide out, and the total stays plausible enough to ship.

Dedup tricks only half-work. `sum(distinct ...)` over a hashed primary key recovers additive measures, and Looker's symmetric aggregates extend that to `average` by dividing a distinct sum by a distinct count. What they cannot fix: a hand-written `avg(o.amount)` still averages 12 rows, any ratio spanning both facts inherits both inflations, and a row-level drill-down or CSV export is 12 rows of fiction.

The fix is to aggregate each fact to the shared grain *before* joining:

```sql
with o as (
  select customer_id, sum(amount) as revenue, count(*) as orders
  from orders group by 1
), t as (
  select customer_id, count(*) as tickets
  from support_tickets group by 1
)
select c.customer_id,
       coalesce(o.revenue, 0) as revenue,
       coalesce(t.tickets, 0) as tickets
from customers c
left join o using (customer_id)
left join t using (customer_id);
```

Now each join is one-to-one, and `left join` keeps customers with no tickets — the inner joins above dropped those silently too.

A properly built star schema does not have this problem: in Power BI or any tabular model, `SUM(Orders[Amount])` and `COUNTROWS(Tickets)` evaluate in separate filter contexts and never see each other's rows. The trap reappears the moment you flatten both facts into one table in Power Query, or flip a relationship to bidirectional.

Detection is cheap: log `count(*)` after each join in a pipeline. If the row count grows, a measure just changed.

## 10:02 - [ML & AI] Native Categoricals vs One-Hot: Why 3,000 Dummies Starve a GBM

One-hot encoding a high-cardinality column into a gradient-boosted tree is the default move, and it quietly guts the model. The reason is arithmetic, not taste.

Take 200,000 rows and 3,000 ZIP codes. One-hot gives 3,000 binary columns averaging **67 rows each — 0.03% of the data**. A split's gain is bounded by how much loss it can move, and a column that touches 0.03% of rows can move almost none. So the tree never picks it. Your ZIP signal exists in the matrix and is never used; the model spends its depth budget on `income` instead.

Worse, a one-hot split is strictly *one category vs the other 2,999*. Expressing "these 40 ZIPs are expensive" needs 40 stacked splits. At `max_depth=6` you cannot say it at all.

LightGBM's `categorical_feature` solves the shape problem. For each candidate feature it ranks categories by a smoothed gradient statistic (≈ `Σg / (Σh + cat_smooth)`), then cuts that sorted order — one split yielding `zip ∈ {bitset}`. Fisher's optimal-partitioning trick: O(k log k), not 2^k.

```python
import lightgbm as lgb
X["zip"] = X["zip"].astype("category")      # auto-detected; codes must be stable
m = lgb.LGBMRegressor(
    max_cat_to_onehot=4,     # ≤4 levels: plain one-vs-rest, no bitset
    max_cat_threshold=32,    # cap candidate cut points
    min_data_per_group=100,  # a category needs this many rows to matter
    cat_smooth=10, cat_l2=10,
).fit(X, y, categorical_feature=["zip"])
```

The defaults above are LightGBM's own, and they are *regularization* — a k-way split can carve out a single 3-row ZIP with a huge residual and fit it perfectly. If the gap between train and validation widens when you switch from one-hot to native, raise `min_data_per_group` and `cat_smooth` before blaming the encoding.

Two traps worth more than the tuning:

- **The int mapping must be frozen.** `astype("category")` assigns codes from the values *present*. Re-fit the encoder on a new month and ZIP 94110 becomes a different integer — the model reads the wrong bitset and returns confident nonsense. Pin the categories (`pd.CategoricalDtype(known_zips)`).
- **Unseen levels.** New categories become `NaN`/`-1` and go down the default branch. Decide that behavior deliberately; don't discover it in production.

Rule of thumb: ≤10 levels, one-hot is fine. Above ~50, use native categoricals or target encoding — one-hot is no longer a representation, it's dilution.
