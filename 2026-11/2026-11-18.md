## 00:02 - [Data Engineering] Kafka Partition Count: Why Adding Partitions Breaks Key Ordering

Partitions are Kafka's unit of both parallelism and ordering. Ordering is guaranteed *within* a partition only, and a keyed record's partition is computed by the producer:

```
partition = murmur2(serialized_key) % numPartitions   // Java default partitioner
```

That modulo is the trap. The mapping depends on `numPartitions`, so the moment you expand a topic, most keys land somewhere new.

### The failure

```bash
# 6 -> 12 partitions. Allowed, instant, irreversible.
kafka-topics.sh --alter --topic orders --partitions 12 --bootstrap-server broker:9092
```

`order-4711` produced its `created` event to partition 3. After the expansion its `cancelled` event hashes to partition 7. Two consumers in the group now own those partitions and process the events concurrently — a consumer keeping per-key state (last status, running balance, a Flink/Streams keyed store) can apply `cancelled` before `created`, or never reconcile them at all.

On a **compacted** topic it's worse: compaction runs per partition, so the stale `order-4711` record in partition 3 is never tombstoned by the new writes in partition 7. The old value stays readable forever, and a consumer that replays from the beginning sees whichever partition it reads last.

Kafka Streams is stricter — it requires co-partitioning between joined topics and between input and state. Changing an input topic's partition count invalidates existing state stores and generally forces an application reset and full reprocess.

### What you cannot do

There is no shrink. `--partitions 3` on a 6-partition topic fails with `InvalidPartitionsException`. Reducing means a new topic plus a reprocess.

### Doing it safely

Treat partition count as a schema-level decision, not a tuning knob:

1. Create `orders.v2` with the target count.
2. Mirror or dual-write with the **same key and partitioner**.
3. Drain `orders`, cut consumers over at a known offset, then cut producers.

Size it once, with headroom:

```
partitions >= ceil(target_MB_s / per_partition_MB_s)
partitions >= max_consumers_in_group        # extra consumers idle otherwise
```

Over-partitioning isn't free either: more open file handles, smaller producer batches, more producer buffer memory (`batch.size` is per partition), and slower failover. And adding partitions never fixes a hot key — one key is one partition at any count. For that you need a composite key or a custom partitioner.

Check before you touch anything: `kafka-topics.sh --describe --topic orders`.

## 05:02 - [Data Analytics] Multi-Touch Attribution: The Same Quarter Says Brand Search Drove $420K or $150K

One touchpoint table, one conversions table, three defensible attribution models — and a 2.8x disagreement on which channel to fund. The model isn't a detail you pick at the end; it *is* the answer.

Build the journey once, then score it three ways (Postgres/DuckDB):

```sql
WITH journey AS (
  SELECT c.user_id, c.ts AS conv_ts, c.revenue,
         COALESCE(t.channel, '(unattributed)') AS channel,
         ROW_NUMBER() OVER (PARTITION BY c.user_id, c.ts ORDER BY t.ts) AS step,
         COUNT(t.ts)  OVER (PARTITION BY c.user_id, c.ts)               AS n_touches
  FROM conversions c
  LEFT JOIN touchpoints t
         ON t.user_id = c.user_id
        AND t.ts <= c.ts
        AND t.ts >  c.ts - INTERVAL '30 days'
)
SELECT channel,
       SUM(CASE WHEN step = GREATEST(n_touches, 1) THEN revenue ELSE 0 END) AS last_touch,
       SUM(CASE WHEN step = 1         THEN revenue ELSE 0 END) AS first_touch,
       SUM(revenue::numeric / GREATEST(n_touches, 1))          AS linear
FROM journey
GROUP BY channel
ORDER BY linear DESC;
```

Typical output on a 5-touch average journey:

| channel | last_touch | first_touch | linear |
|---|---|---|---|
| brand search | $420K | $60K | $150K |
| paid social | $75K | $390K | $205K |
| email | $190K | $45K | $160K |

Last-touch pays the closer. Brand search sits next to the checkout button, so it wins every time — and defunding paid social on that table starves the top of the funnel that created the brand searches.

Three bugs that make the numbers quietly wrong:

1. **`JOIN` instead of `LEFT JOIN`** drops conversions with no touchpoint in the window. Your attributed total silently falls below actual revenue, and the gap — real direct/dark traffic — vanishes instead of showing up as a line item.
2. **Integer division eats the remainder.** In Postgres, Redshift and SQL Server, `revenue / n_touches` on two `INT` columns truncates: a $9 order across 5 touches credits `9/5 = 1` five times, so $5 lands and $4 disappears. DuckDB and BigQuery return a float here, which is exactly why the bug survives dev and shows up in prod. Cast regardless.
3. **Repeat buyers re-credit old touches.** A plain lookback window gives January's touches credit for March's order too. Bound the window at the previous conversion — which needs its own CTE, since you can't put a window function in a `JOIN` condition:

```sql
WITH conv AS (
  SELECT user_id, ts, revenue,
         LAG(ts) OVER (PARTITION BY user_id ORDER BY ts) AS prev_conv_ts
  FROM conversions
)
-- ... then in the LEFT JOIN:
--   AND (c.prev_conv_ts IS NULL OR t.ts > c.prev_conv_ts)
```

The reconciliation that catches all three: each column must sum to `SELECT SUM(revenue) FROM conversions` within rounding. If they don't, stop and fix the join.

And note what none of this is: correlational credit-splitting, not causal lift. Only a holdout or geo test tells you what a channel *added*.
