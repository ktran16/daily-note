## 00:02 - [Data Engineering] Unknown and Inferred Members: The INNER JOIN in Your Fact Load That Deletes Revenue

A fact load has to turn natural keys into dimension surrogate keys, and almost everyone writes that lookup as a join. The default join is the one that loses data:

```sql
-- fct_orders.sql — the bug
select o.order_id, c.customer_sk, o.amount
from {{ ref('stg_orders') }} o
join {{ ref('dim_customer') }} c on c.customer_id = o.customer_id
```

If a customer row hasn't landed yet — CDC lag, a dimension model that runs after the fact model, a signup in the same second as the order — the order vanishes. Nobody notices, because the row count still looks plausible. Worse, in an incremental fact table it never comes back: the next run filters on `order_id > max(order_id)` or an updated-at watermark, so the dropped row is permanently behind the cursor. The revenue is gone until someone does a full refresh.

Two fixes, and they compose.

**Reserved members.** Give every dimension explicit rows for the states a join can't resolve, then `LEFT JOIN` and coalesce:

```sql
select
  o.order_id,
  coalesce(c.customer_sk, '-1') as customer_sk,  -- -1 unknown, -2 not applicable
  o.amount
from {{ ref('stg_orders') }} o
left join {{ ref('dim_customer') }} c using (customer_id)
```

Union those rows into the dimension (or load them as a seed) so `dim_customer` always has them and reports render "Unknown" instead of silently under-counting.

**Inferred members.** Better: if your surrogate key is a hash of the natural key, you don't need the join at all — `{{ dbt_utils.generate_surrogate_key(['customer_id']) }}` gives the fact the correct key for a customer the dimension hasn't seen. Then have the dimension emit a stub row for any natural key present in facts but absent upstream, flagged `is_inferred = true`, and let the real attributes overwrite it on a later run.

Monitor it rather than hard-failing:

```yaml
# models/marts/_marts.yml
- name: customer_sk
  tests:
    - not_null
    - relationships:            # passes, because -1 is a real dim row
        to: ref('dim_customer')
        field: customer_sk
```

```sql
-- tests/unknown_customer_spike.sql
{{ config(severity='warn', warn_if='>100', error_if='>10000') }}
select order_id
from {{ ref('fct_orders') }}
where customer_sk = '-1'
  and order_date >= current_date - 1
```

A steady trickle of unknowns is normal. A spike means an upstream load broke — which is exactly the signal the INNER JOIN was hiding.

## 05:02 - [Data Analytics] Hash Spill: The GROUP BY That Runs 10x Slower Because 4 MB Wasn't Enough

A dashboard query ran in 9 seconds for a year, then crossed into 95 seconds with no code change. Row counts grew ~15%. Nothing in `EXPLAIN` changed — because plain `EXPLAIN` cannot show this. The aggregate started spilling to disk.

**Find it.** You need `ANALYZE`, and `BUFFERS` to see the temp I/O:

```sql
EXPLAIN (ANALYZE, BUFFERS, SETTINGS)
SELECT customer_id, date_trunc('day', ordered_at) AS d,
       sum(amount) AS rev, count(*) AS orders
FROM orders
GROUP BY 1, 2;
```

In-memory looks like this:

```
HashAggregate  ... Peak Memory Usage: 6321 kB
```

Spilled looks like this:

```
HashAggregate  (actual time=... rows=11847302)
  Planned Partitions: 64  Batches: 261
  Peak Memory Usage: 8273 kB  Disk Usage: 1842560 kB
  Buffers: temp read=230320 written=230448
```

`Batches: 261` with 64 planned means it re-partitioned repeatedly — the planner badly underestimated distinct groups. Sorts announce it differently: `Sort Method: external merge  Disk: 72448kB` instead of `quicksort  Memory: 2032kB`.

**Why 4 MB.** `work_mem` (default 4 MB) is a budget *per node per parallel worker*, not per query. A plan with two sorts and a hash join across four workers can legitimately use `4 MB × 3 nodes × 5 processes = 60 MB`. Since PG 13 hash aggregates respect that budget by spilling instead of eating RAM; hash nodes get `work_mem × hash_mem_multiplier`, which defaults to 2.0 from PG 15 on.

**Fix in this order.**

1. **Fix the estimate.** `ANALYZE orders;` and, for correlated group keys, `CREATE STATISTICS ON customer_id, ordered_at FROM orders;` (n_distinct). A planner that knows there are 12M groups may choose a cheaper plan outright.
2. **Shrink the group set** — pre-aggregate to daily in a rollup table, or narrow the date range. Fewer groups beats more memory.
3. **Raise `work_mem` for the session only**: `SET LOCAL work_mem = '256MB';`. Never globally — the multiplier above is how servers OOM.

Spill is not a bug, it's a budget overrun. Check `Disk Usage` before you tune anything else.

## 10:03 - [ML & AI] ZeRO Stages: A 7B Model Needs 112 GB to Fine-Tune, and Stage 2 Is Free

The reason a 7B model won't full fine-tune on an 80 GB GPU isn't the weights. It's the optimizer. Count bytes per parameter for mixed-precision AdamW:

| State | Bytes/param | 7B total |
|---|---|---|
| bf16 params | 2 | 14 GB |
| bf16 gradients | 2 | 14 GB |
| fp32 master weights | 4 | 28 GB |
| Adam momentum (fp32) | 4 | 28 GB |
| Adam variance (fp32) | 4 | 28 GB |
| **Total** | **16** | **112 GB** |

So `16Ψ`, and plain DDP replicates all of it on every GPU. Eight GPUs hold eight copies of the same 112 GB.

ZeRO shards it in three stages. With `N` GPUs, per-GPU model states are:

- **Stage 1** — shard optimizer states: `2Ψ + 2Ψ + 12Ψ/N`
- **Stage 2** — also shard gradients: `2Ψ + 14Ψ/N`
- **Stage 3** — also shard parameters: `16Ψ/N`

At 7B on 8 GPUs: **112 → 38.5 → 26.25 → 14 GB**.

The part that decides your config is communication volume per step, not memory:

- DDP all-reduce: `2Ψ`
- Stage 1 and 2: reduce-scatter `Ψ` + all-gather `Ψ` = `2Ψ` — **identical to DDP**
- Stage 3: adds an all-gather of parameters in the forward pass = `3Ψ`, i.e. **1.5× DDP**

Stage 2 is a 4.3× memory cut at zero communication cost. Always turn it on. Stage 3 is the one you pay for, and on PCIe-only nodes without NVLink that 50% extra traffic shows up directly in step time.

In FSDP2 the stage is one flag:

```python
from torch.distributed.fsdp import fully_shard

for block in model.layers:                      # shard per-block, not whole-model
    fully_shard(block, reshard_after_forward=False)  # ≈ ZeRO-2 (keep params gathered)
fully_shard(model, reshard_after_forward=True)       # ≈ ZeRO-3
```

(FSDP1's equivalents: `ShardingStrategy.SHARD_GRAD_OP` and `FULL_SHARD`.)

**The trap:** ZeRO shards *model states only*. Activations are untouched, so stage 3 still OOMs on long sequences — that's what gradient checkpointing and sequence parallelism are for. If dropping to stage 3 didn't help, your memory was never in the optimizer.
