## 00:03 - [Data Engineering] Snowflake Auto-Suspend: The Cost Knob That Throws Away Your Warm Cache

The instinct when a Snowflake bill arrives is to set `AUTO_SUSPEND = 60` everywhere. For batch ELT that is right. For an interactive BI warehouse it often makes things both slower *and* more expensive, because suspending a warehouse destroys a cache you were already paying for.

Snowflake has three caches, and only one of them survives suspension:

| Cache | Where it lives | Survives suspend? | TTL |
|---|---|---|---|
| Result cache | Cloud services layer | Yes | 24h (reset on reuse, max 31 days) |
| Local disk (SSD) cache | Warehouse compute nodes | **No** | Life of the warehouse |
| Metadata / micro-partition stats | Cloud services layer | Yes | Always |

The local disk cache holds the actual micro-partition columns your queries read. A dashboard hitting the same 200 GB fact table all morning is mostly served from warehouse SSD. Suspend between every query and each one re-fetches from remote storage — the classic symptom is `BYTES_SCANNED` staying flat while `PERCENTAGE_SCANNED_FROM_CACHE` collapses.

Then there's billing granularity. Snowflake bills per second, but **each resume carries a 60-second minimum charge**. A warehouse with `AUTO_SUSPEND = 60` serving a query every 90 seconds pays 60s of compute plus a cold cache, every time. Leaving it up for 10 minutes can cost less than ten cold starts.

```sql
-- Interactive / BI: keep the SSD cache warm
ALTER WAREHOUSE bi_wh SET
  AUTO_SUSPEND = 600          -- 10 min
  AUTO_RESUME  = TRUE
  STATEMENT_TIMEOUT_IN_SECONDS = 3600;

-- Batch ELT (dbt): nothing to reuse between runs
ALTER WAREHOUSE transform_wh SET AUTO_SUSPEND = 60;
```

Measure before you tune. This shows how much your cache is actually earning:

```sql
SELECT warehouse_name,
       COUNT(*)                                        AS queries,
       AVG(percentage_scanned_from_cache) * 100        AS pct_from_ssd,
       SUM(IFF(query_type = 'SELECT'
               AND execution_time = 0, 1, 0))          AS result_cache_hits
FROM snowflake.account_usage.query_history
WHERE start_time > DATEADD(day, -7, CURRENT_TIMESTAMP())
GROUP BY 1
ORDER BY queries DESC;
```

Rule of thumb: `AUTO_SUSPEND = 60` for warehouses whose queries never repeat (ELT, ad-hoc loads), 300–900 for anything a human or dashboard polls. And never set it to `0`/`NULL` unless you intend to pay for an idle warehouse forever.

## 05:03 - [Data Analytics] Data Skew: The One Hot Key That Makes 199 Workers Wait for One

A distributed join or `GROUP BY` hashes rows by key and sends every row with the same key to the same worker. Total runtime is the *slowest* partition, not the average. One fat key means one worker does all the work while the rest idle.

The symptom is unmistakable: the query is 99% complete in 90 seconds, then the last task runs for 38 minutes. In Spark UI, look at the stage's task duration — median 4s, max 2,280s. Snowflake and BigQuery hide the partitioning, but it surfaces the same way: one stage with huge "bytes spilled to local storage."

**Find it before you tune anything.** Skew is a property of the data, so one cheap query tells you:

```sql
SELECT user_id,
       COUNT(*) AS rows,
       COUNT(*) * 100.0 / SUM(COUNT(*)) OVER () AS pct
FROM events
GROUP BY 1
ORDER BY rows DESC
LIMIT 10;
```

On a 400M-row table with 2M users, the average key holds 200 rows. If `user_id = 0` (the guest sentinel) holds 90M rows — 22% of the table — no amount of cluster scaling helps. 200 partitions, one of which has 90M rows.

**The culprits are almost always sentinels**, not real heavy users: `NULL`, `''`, `0`, `-1`, `'unknown'`, `'anonymous'`. Two fixes, in order of preference:

1. **Drop them from the join.** `NULL` keys never match anything in an inner join, yet in Spark they all hash to the same partition and get shuffled anyway. Filtering `WHERE user_id IS NOT NULL AND user_id <> 0` upstream can cut the stage from 40 minutes to 90 seconds with no change in results.

2. **Salt the key** when the hot values are legitimate. Add a random bucket to the big side, replicate the small side across all buckets:

```sql
WITH salted AS (
  SELECT e.*, MOD(ABS(HASH(e.event_id)), 16) AS salt
  FROM events e
),
fanned AS (
  SELECT u.*, s.salt
  FROM dim_user u, UNNEST(GENERATE_ARRAY(0, 15)) AS s(salt)
)
SELECT f.segment, COUNT(*)
FROM salted e
JOIN fanned f USING (user_id, salt)
GROUP BY 1;
```

That spreads the hot key over 16 workers for 16x the small table — a good trade when the small side is 50K rows.

Spark's adaptive execution (`spark.sql.adaptive.skewJoin.enabled`, on by default since 3.2) splits skewed partitions automatically, but only for joins. A skewed `GROUP BY` or a custom aggregate still serializes on one task.

## 10:03 - [ML & AI] Mean Pooling Embeddings: The Padding Tokens You Forgot to Mask

A transformer encoder returns one hidden state *per token*. To get one vector per document you pool them, and the pooling is not a free choice — it has to match how the model was trained. Sentence-transformers checkpoints like `all-MiniLM-L6-v2` were trained with **mean pooling**; raw BERT's `[CLS]` vector was never trained as a sentence representation and performs near-randomly on similarity tasks. Decoder-only embedding models use the **last non-padding token**.

The silent bug lives in the mean:

```python
# WRONG - averages over pad positions too
emb = model(**batch).last_hidden_state.mean(dim=1)
```

`mean(dim=1)` divides by the padded sequence length, not the real one. Padding hidden states are not zero — the pad embedding plus positional encoding plus 6 layers of attention produces a perfectly ordinary vector — so you are averaging real content with junk.

**The arithmetic.** An 8-token query padded to the batch's longest sequence at 128 tokens contributes 8/128 = **6.25%** real signal; 93.75% of the vector is padding. Worse, the dilution depends on *batch composition*. Embed the same query in a batch padded to 32, then to 128, and cosine similarity between the two vectors typically lands around 0.6–0.8 instead of 1.0. Your index and your query encoder now disagree for reasons that have nothing to do with meaning, and nothing ever raises an error — cosine still returns a plausible number.

**The fix** — mask, sum, divide by the true token count:

```python
out = model(**batch).last_hidden_state          # (B, L, H)
mask = batch["attention_mask"].unsqueeze(-1).float()
emb = (out * mask).sum(1) / mask.sum(1).clamp(min=1e-9)
emb = torch.nn.functional.normalize(emb, dim=-1)  # cosine == dot
```

The `clamp` guards against an all-padding row; without it you get NaNs that poison the whole batch.

**The regression test worth owning.** Encode one string alone, then inside a batch with a long sibling, and assert the cosine is ≥ 0.999. That single assertion catches masked-pooling bugs, accidental `.mean(dim=1)` refactors, and left- vs right-padding mismatches in decoder embedders — all failures that otherwise only show up as mysteriously mediocre retrieval recall.

## 15:04 - [Crypto & Business] The Option Pool Shuffle: The 10% Pool That Dilutes Only the Founders

A term sheet says "$4M on a $16M pre-money, with a 10% post-closing option pool." The valuation looks like the thing you negotiated. The pool line is where two points of your company quietly change hands.

**Why it bites.** The new pool is created *pre-money* — before the investor's shares are issued — so it comes out of existing holders only. The investor's 20% is calculated after the pool exists, so they never share in that dilution.

**Worked example.** Founders hold 8,000,000 shares, no existing pool.

| | No pool | 10% pool, pre-money | 10% pool, post-money |
|---|---|---|---|
| Investor | 20.0% | 20.0% | 18.0% |
| Pool | — | 10.0% | 10.0% |
| Founders | 80.0% | **70.0%** | **72.0%** |

Pre-money carve-out costs founders 10 points; shared (post-money) dilution would cost 8. The 2-point gap is a transfer from founders to the investor — ~$400K at the $20M post, ~$4M at a $200M exit.

**It also cuts your price per share.** With no pool, 2,000,000 new shares on 10,000,000 total → **$2.00/share**. With the pre-money pool, the investor needs 2,285,714 shares of an 11,428,571 total → **$1.75/share**, a 12.5% haircut on the headline price. Your effective pre-money is $16M − $2M of pool = **$14M**.

**Four levers, in order of leverage:**

1. **Size it bottom-up.** Build an 18-month hiring plan: 4 hires × 0.5% + refreshes ≈ 5%, not a round 10%. Make them argue against the plan, not the number.
2. **Count the unallocated shares you already have** toward the new pool instead of stacking on top of it.
3. **Ask for post-money pool treatment**, or a top-up at the next round when everyone dilutes together.
4. **If it must be pre-money, reprice it.** To keep a true $16M pre with a 10% pool, you need a stated pre of **$18.2M** (solve V − 0.10(V+4) = 16).

The pool isn't a giveaway — you need equity to hire. The mistake is treating its size as an administrative detail set after the valuation is agreed, when it *is* part of the valuation.
