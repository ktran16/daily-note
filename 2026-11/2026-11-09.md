## 00:02 - [Data Engineering] Schema Registry Compatibility: BACKWARD Protects Consumers, and Only Against the Last Version

Schema Registry's compatibility mode is the single setting that decides whether a schema change deploys cleanly or pages you at 3am. Two things about it are routinely misunderstood: **which direction it protects**, and **how far back it looks**.

### The direction is named for the reader, not the change

- **BACKWARD** (the default): a consumer using the **new** schema can read data written with the **old** one. You may *delete* fields and *add optional* fields (optional = has a default). → **Upgrade consumers first.**
- **FORWARD**: a consumer using the **old** schema can read data written with the **new** one. You may *add* fields and *delete optional* ones. → **Upgrade producers first.**
- **FULL**: both. Effectively only add/remove fields that have defaults. Any upgrade order works.

The trap: teams leave the default BACKWARD, then roll out a new producer before consumers are updated. The registry happily accepts the schema — it was only ever checking the other direction. Old consumers then hit a required field they have no default for.

```json
// v1
{"type":"record","name":"Order","fields":[
  {"name":"order_id","type":"string"},
  {"name":"amount","type":"double"}]}
```

```json
// REJECTED under BACKWARD — no default, so a new reader
// cannot interpret v1 data that lacks the field
{"name":"currency","type":"string"}

// ACCEPTED — union with null plus a default
{"name":"currency","type":["null","string"],"default":null}
```

In Avro, "optional" means **it has a `default`**, not merely that it's nullable. `["null","string"]` without `"default": null` still fails.

### BACKWARD only compares against the latest version

This is the costlier gotcha. `BACKWARD` validates the new schema against **version N-1 only**. A chain of individually-legal changes can produce a schema that cannot read data from six months ago — which still sits in a topic with `retention.ms=-1` or in your Iceberg archive.

The classic break is a field that leaves and comes back with a different type:

| Version | Change | Passes BACKWARD vs. previous? |
|---|---|---|
| v1 | `status: string` (required) | — |
| v2 | drop `status` | Yes — a new reader just ignores the field |
| v3 | add `status: int`, `default: 0` | Yes — adding a field with a default is fine |

Each step is legal. But a **v3 reader against v1 data** finds a `string` where it expects an `int`, and deserialization fails. Nothing in the registry ever compared v3 to v1.

```bash
# Set once, per subject, before anyone evolves anything
curl -X PUT http://registry:8081/config/orders-value \
  -H "Content-Type: application/json" \
  -d '{"compatibility":"BACKWARD_TRANSITIVE"}'
```

`*_TRANSITIVE` checks **all** prior versions. Use it whenever retained data outlives a schema version — which, for an event log or a lakehouse table, is always.

Test it in CI rather than discovering it at deploy time:

```bash
# Exit non-zero if the change is incompatible
curl -X POST \
  "http://registry:8081/compatibility/subjects/orders-value/versions/latest?verbose=true" \
  -H "Content-Type: application/json" \
  -d @schema-payload.json
```

**Rule of thumb:** `BACKWARD_TRANSITIVE` for event streams (consumers are many and lag), `FORWARD_TRANSITIVE` when a fleet of old readers can't be upgraded, `NONE` never on a shared topic.

## 05:02 - [Data Analytics] Capping Revenue Outliers in A/B Tests: Pool the Threshold, or You Bias the Lift

Revenue per user is heavy-tailed, and a t-test's resolving power depends on the coefficient of variation (CV = σ/μ), not on sample size alone:

```
relative MDE ≈ (z_1-α/2 + z_1-β) · √(2/n) · CV     = 2.80 · √(2/n) · CV
```

With 50,000 users per arm, mean $4.20 and σ = $38, CV is 9.0 and the MDE is **16%**. No realistic checkout change moves revenue 16%, so that test is pre-destined to read "not significant." Three users who bought $8,000 pallets are eating the whole experiment.

Winsorizing — clipping at a high percentile rather than deleting rows — fixes the variance. At p99 the σ drops to roughly $14 on a mean of $3.95, so CV = 3.5 and the MDE falls to **6.3%**: a 2.5x gain in sensitivity for 500 clipped users per arm.

The trap is computing the cap **per variant**. If treatment has a fatter tail, its p99 sits higher, you clip the arms at different thresholds, and the measured difference now partly reflects your own preprocessing. Compute one threshold on pooled data and apply it identically:

```sql
WITH user_rev AS (
  SELECT e.user_id, e.variant, COALESCE(SUM(o.revenue), 0) AS revenue
  FROM experiment_assignment e
  LEFT JOIN orders o ON o.user_id = e.user_id
                    AND o.ordered_at >= e.assigned_at
  WHERE e.experiment_id = 'checkout_v3'
  GROUP BY 1, 2
),
cap AS (   -- pooled across arms, NOT per variant
  SELECT PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY revenue) AS p99 FROM user_rev
)
SELECT variant, COUNT(*) AS users,
       AVG(revenue)                                        AS mean_raw,
       AVG(LEAST(revenue, (SELECT p99 FROM cap)))          AS mean_capped,
       STDDEV_SAMP(LEAST(revenue, (SELECT p99 FROM cap)))  AS sd_capped
FROM user_rev GROUP BY variant;
```

Checking the payoff before launch:

```python
Z = 1.96 + 0.84                       # 80% power, two-sided alpha = 0.05
def rel_mde(x, n_per_arm):
    x = np.asarray(x, float)
    return Z * np.sqrt(2 / n_per_arm) * x.std(ddof=1) / x.mean()

cap = np.quantile(pre_period_rev, 0.99)        # from PRE-period, pre-registered
rel_mde(rev, len(rev))                          # 0.160
rel_mde(np.minimum(rev, cap), len(rev))         # 0.063
```

Two guardrails. Pick the percentile from **pre-period** data and write it into the test plan — choosing it after seeing results is p-hacking with extra steps. And capping changes the estimand: you now measure the effect on capped revenue, so a treatment that works by making whales spend more is invisible. Report capped as the powered primary and raw as a directional secondary. Logging the metric is not a substitute — `log(x)` dies on the zeros that are most of your users and silently switches you to a geometric mean.

## 10:03 - [ML & AI] Gaussian Mixtures vs k-means: The 1/σ That Moves the Boundary

k-means is not a different algorithm from a Gaussian mixture — it is the **limiting case** of EM on a GMM where every component is forced to share one isotropic covariance σ²I, σ²→0, and assignments are hardened to 0/1. Every k-means failure mode is a consequence of those three constraints, and GMM relaxes them one at a time.

### The arithmetic of a single boundary

One dimension, two equally-weighted components: **A** at μ=0, σ=1; **B** at μ=6, σ=3. k-means puts the boundary at the midpoint of the centroids, x=3. The GMM boundary solves πₐ·N(x|0,1) = π_b·N(x|6,3):

$$\gamma_A(x)=\frac{\pi_A\,\mathcal{N}(x\mid\mu_A,\Sigma_A)}{\sum_k \pi_k\,\mathcal{N}(x\mid\mu_k,\Sigma_k)}$$

Taking logs reduces to `8x² + 12x − 55.774 = 0`, so the boundaries are **x = 1.995 and x = −3.495**. Three things fall out:

- **x = 2.5** → GMM gives B a 79% responsibility; k-means says A (distance 2.5 vs 3.5). The whole band `1.995 < x < 3` is misassigned by k-means.
- **x = 1.5** → γₐ = **exactly 0.75**. Both components sit 1.5σ away in Mahalanobis distance, so the likelihoods differ only by the 1/σ normalizer — 3:1. Raw distance sees 1.5 vs 4.5 and isn't close.
- A's region is the **interval** (−3.495, 1.995), not a half-line. At x = −4 the wide component wins again. k-means regions are always convex half-spaces; GMM regions need not be.

### What to actually set

```python
from sklearn.mixture import GaussianMixture
gm = GaussianMixture(n_components=3, covariance_type='full',
                     n_init=10, reg_covar=1e-6).fit(X)
gm.predict_proba(X)   # soft responsibilities
gm.bic(X)             # lower is better
```

`covariance_type` is the real knob, and it is a parameter budget: `full` costs K·d(d+1)/2 covariance parameters, `tied` costs d(d+1)/2, `diag` costs K·d, `spherical` costs K. At d=100, `full` with K=5 is 25,250 parameters — use `diag` unless you have the rows.

The payoff is model selection. k-means inertia decreases monotonically in K, so you squint at an elbow; a GMM has a real likelihood, so **BIC = −2·logL + p·ln(n)** actually has a minimum you can read off. Keep `n_init≥10` (EM finds local optima) and never drop `reg_covar` — a `full` component will happily collapse onto one point and send the likelihood to infinity.
