## 00:03 - [Data Engineering] dbt `--defer`: Building One Model Against Production Upstreams

You change one mart model. Your dev schema is empty, so `ref('stg_orders')` resolves to `dev_you.stg_orders` — which doesn't exist. The usual reflex is `dbt build --select +fct_orders`, rebuilding forty upstream models to test a one-line edit.

`--defer` fixes this. Given a production `manifest.json`, any node **not selected in this run** has its `ref()` rewritten to point at the production relation instead of your dev schema:

```bash
# Fetch the manifest produced by the last production run
mkdir -p prod-artifacts
aws s3 cp s3://dbt-artifacts/prod/manifest.json prod-artifacts/

dbt run --select fct_orders --defer --state prod-artifacts
# compiles to: from analytics.stg_orders  (not dev_you.stg_orders)
```

### The gotcha: defer prefers your environment

Default defer is not "always use prod." The rule is: use the deferred relation *only if the node does not already exist in your target schema*. So if you built `stg_orders` in dev three weeks ago, defer silently uses that stale copy, and you debug a discrepancy that doesn't exist in prod.

`--favor-state` inverts it — always take the state manifest's relation, even when a local copy exists:

```bash
dbt run --select fct_orders --defer --favor-state --state prod-artifacts
```

Use `--favor-state` in CI, where leftover relations from earlier runs are common. Leave it off locally when you *intend* to chain onto models you just built.

### Two more things that bite

- **Sources are never deferred.** `source()` always resolves to its configured database/schema. Defer rewrites `ref()` only.
- **`--state` does double duty.** It feeds both `state:modified` selection and defer. When the comparison manifest and the defer target should differ, split them with `--defer-state`.

Slim CI is just these two features composed:

```bash
dbt build --select state:modified+ --defer --favor-state --state prod-artifacts
```

Export `DBT_STATE=prod-artifacts` to stop retyping the path.

## 05:02 - [Data Analytics] Difference-in-Differences: The Pre-Trend Check That Decides Whether Your Number Means Anything

You rolled a feature out to one region because you couldn't randomize. Treated stores went from $1,000 to $1,180 in average daily revenue. The before/after read is **+18%**, and it's almost certainly wrong — Q4 lifted everything.

DiD subtracts the drift using a control group that wasn't treated:

| | pre | post | change |
|---|---|---|---|
| treated | $1,000 | $1,180 | **+$180** |
| control | $1,000 | $1,060 | +$60 |

DiD = $180 − $60 = **+$120 (+12%)**. The 2×2 in SQL is four cell means with alternating signs:

```sql
WITH cells AS (
  SELECT is_treated,
         d >= DATE '2026-10-15' AS is_post,
         AVG(revenue) AS mean_rev
  FROM store_daily
  WHERE d BETWEEN DATE '2026-09-15' AND DATE '2026-11-14'
    AND store_id IN (SELECT store_id FROM balanced_panel)
  GROUP BY 1, 2
)
SELECT   MAX(CASE WHEN     is_treated AND     is_post THEN mean_rev END)
       - MAX(CASE WHEN     is_treated AND NOT is_post THEN mean_rev END)
       - MAX(CASE WHEN NOT is_treated AND     is_post THEN mean_rev END)
       + MAX(CASE WHEN NOT is_treated AND NOT is_post THEN mean_rev END) AS did
FROM cells;
```

### The assumption, and how to interrogate it

DiD is only valid under **parallel trends**: absent treatment, both groups would have moved together. You can't test that in the post period — but you can run the identical query on two *pre*-treatment windows, where the answer should be ≈ 0. If an Aug→Sep placebo returns $70, then most of your $120 is pre-existing divergence, not the feature. Better: an event study — one coefficient per period relative to launch, with the pre-period coefficients flat near zero.

### Two things that silently break it

**Unclustered standard errors.** Each store contributes 60 correlated daily rows. Treating them as 60 independent observations shrinks the CI several-fold and manufactures significance. Cluster on the unit:

```python
import statsmodels.formula.api as smf
m = smf.ols("revenue ~ treated * post", data=df).fit(
        cov_type="cluster", cov_kwds={"groups": df["store_id"]})
print(m.params["treated:post"], m.conf_int().loc["treated:post"])
```

Below roughly 30–40 clusters, even clustered errors run optimistic — use wild-bootstrap CIs.

**An unbalanced panel.** Stores that opened mid-window change the composition of the cell mean, so DiD measures mix shift. Hence `balanced_panel`: restrict to units present in *both* periods before you compute anything.

## 10:06 - [ML & AI] In-Batch Negatives: Your "Effective Batch Size" Is Not Your Negative Count

Contrastive embedding training (InfoNCE) scores each anchor against **the other items in its own batch**:

```
L = -log[ exp(sim(q, p⁺)/τ) / Σ_j exp(sim(q, d_j)/τ) ]
```

A batch of B pairs gives each anchor **B−1 negatives**, for free. That makes batch size a *quality* hyperparameter, not just a throughput one — and it's where two expensive mistakes live.

**Gradient accumulation buys you nothing here.** Four micro-batches of 64 at `accum_steps=4` is an effective batch of 256 *for the optimizer*, but each softmax still ranges over 64 candidates. You get 63 negatives, not 255. The giveaway is the loss floor: a random-init model has all similarities equal, so loss starts at `ln(B)` — `ln(64) = 4.16`, not `ln(256) = 5.55`. If your curve starts at 4.16, you have a batch of 64 no matter what your config says. Same trap in DDP: 8 GPUs × 64 is "batch 512," but without an `all_gather` on the embeddings each replica still sees 63 negatives.

```python
import torch.distributed.nn as dist_nn
# gather WITH gradient flow — plain all_gather silently detaches
k_all = torch.cat(dist_nn.all_gather(k), dim=0)      # (B*world, D)
logits = (q @ k_all.T) / tau
labels = torch.arange(len(q), device=q.device) + rank * len(q)
loss = F.cross_entropy(logits, labels)
```

For large batches on one GPU, use GradCache (two-pass: no-grad embed, then recompute with grad).

**τ decides which negative you actually train on.** Take pos = 0.9, negatives = 0.8, 0.3, 0.3:

| τ | loss | share of negative mass on the 0.8 |
|---|---|---|
| 0.05 | 0.13 | **99.99%** |
| 0.20 | 0.53 | 86% |

At τ=0.05 the gradient is effectively a hard-negative miner — all of it pushes against the single closest item. That is why low τ (0.02–0.07) trains sharp retrievers *and* why it is brutal if that nearest item is a **false negative**. Dedupe near-duplicates within a batch before scaling B to 1024: at that size, a 10k-query corpus with paraphrases will put genuine matches in the same batch and explicitly teach the model to separate them.

## 15:02 - [Crypto & Business] Value-Based Pricing for Consulting: The Three Numbers That Replace Your Hourly Rate

A data consultant quotes $150/hour, estimates 60 hours, and sends a $9,000 proposal. The work will cut the client's wasted ad spend by roughly $45,000 a year. The hourly frame did two bad things: it capped the price at a labor-market number, and it invited the buyer to compare that number against other people's rates instead of against their own savings.

Value pricing reverses the order. Find the dollar impact first, then price a fraction of it.

**The three numbers.** Get them in discovery, in the client's own words:

1. **Baseline** — what the problem costs today. "We spend $380K/yr on paid search."
2. **Delta** — the *conservative* change, not the best case. "A 12% cut in waste" → $45,600/yr.
3. **Duration** — how long the benefit persists. One year minimum; most process fixes run two to three. Three-year value here: $136,800.

**The ratio.** Price at 10–20% of first-year value for pure analysis and advice, 20–33% when you also build and hand over a working artifact. The ad audit includes a reallocation plan and a handover session, so call it 25%: **$11,400**.

Same 60 hours, $190/hour effective — 27% more revenue for identical work. And the incentive now points at finishing *faster*, which hourly billing punishes.

**What makes it hold up:**

- Put the baseline and delta in the proposal using their figures. They supplied them; you are quoting their own arithmetic back.
- Never show an hour count. Hours invite rate math, which is the frame you just escaped.
- Scope the deliverable, not the time: "spend audit + reallocation plan + one 90-minute handover, two revision rounds." Anything beyond that is a change order with its own price.

**Where it fails.** No measurable dollar line (brand work, "modernize our stack"), or a buyer who procures strictly by rate card — public sector, enterprise staff augmentation. There, hourly is the required format; raise the rate instead of reframing it.

## 19:03 - [PC Hardware] eGPUs over Thunderbolt and USB4: Where the 20–30% Goes, and When It Still Wins

An external GPU enclosure gives a laptop or mini PC a desktop graphics card over one cable. The catch is the link. A desktop x16 Gen4 slot moves ~32 GB/s. Thunderbolt 3/4 and USB4 v1 tunnel **PCIe x4 Gen3 — about 32 Gbps allocated, ~2.8–3.2 GB/s in practice**, roughly a tenth of the bandwidth. Thunderbolt 5 / USB4 v2 raises the PCIe tunnel to ~64 Gbps, which roughly doubles it.

**First: confirm the port can do it at all.** A "20 Gbps" USB 3.2 Gen2x2 port carries no PCIe and will never host an eGPU. You need the Thunderbolt bolt logo or USB4 certification. On Linux, `boltctl list` enumerates attached TB devices; `lspci -vv | grep -A2 LnkSta` shows what the card actually negotiated. With NVIDIA:

```
nvidia-smi --query-gpu=pcie.link.gen.current,pcie.link.width.current --format=csv
```

Expect `3, 4`. If you see `1, 4`, the link is degraded — reseat or try a certified 40 Gbps cable.

**Why games lose less than 10×.** PCIe bandwidth mostly carries asset streaming and draw-call traffic, not whole frames. Losses scale with frame rate, not resolution:

| Scenario | Typical loss vs same GPU in a desktop |
|---|---|
| 4K / high settings, 60–80 fps | 5–12% |
| 1440p / high, 100–120 fps | 10–20% |
| 1080p / low, 200+ fps | 30–40% |

**The loopback tax is the big one.** Rendering on the eGPU but displaying on the laptop's internal panel sends every finished frame *back* across the same link, costing another 10–20%. Plug the monitor into the enclosure.

**ML behaves completely differently.** Inference with weights resident in VRAM barely touches PCIe after load — a 14 GB fp16 7B model uploads in ~5 s at 3 GB/s, then runs at full speed. Training with constant host↔device transfer, or any multi-GPU gradient sync, gets punished hard.

**Sizing the enclosure PSU:** it must cover the card's transient peaks *plus* host charging (up to 100 W on TB3/4, 240 W with USB-PD 3.1 EPR). A 550 W enclosure feeding a 320 W GPU and a 100 W laptop has almost no headroom.

Verdict: excellent for a desk-bound machine doing high-resolution gaming or local inference. Poor value for competitive esports frame rates — buy a desktop.
