## 00:03 - [Data Engineering] dbt `--defer`: Building One Model Against Production Upstreams

You change one mart model. Your dev schema is empty, so `ref('stg_orders')` resolves to `dev_you.stg_orders` — which doesn't exist. The usual reflex is `dbt build --select +fct_orders`, rebuilding forty upstream models to test a one-line edit.

`--defer` fixes this. Given a production `manifest.json`, any node **not selected in this run** has its `ref()` rewritten to point at the production relation instead of your dev schema:

```bash
# Fetch the manifest produced by the last production run
mkdir -p prod-artifacts
aws s3 cp s3://dbt-artifacts/prod/manifest.json prod-artifacts/

dbt run --select fct_orders --defer --state prod-artifacts
# compiles to: from analytics.stg_orders  (not dev_you.stg_orders)
```

### The gotcha: defer prefers your environment

Default defer is not "always use prod." The rule is: use the deferred relation *only if the node does not already exist in your target schema*. So if you built `stg_orders` in dev three weeks ago, defer silently uses that stale copy, and you debug a discrepancy that doesn't exist in prod.

`--favor-state` inverts it — always take the state manifest's relation, even when a local copy exists:

```bash
dbt run --select fct_orders --defer --favor-state --state prod-artifacts
```

Use `--favor-state` in CI, where leftover relations from earlier runs are common. Leave it off locally when you *intend* to chain onto models you just built.

### Two more things that bite

- **Sources are never deferred.** `source()` always resolves to its configured database/schema. Defer rewrites `ref()` only.
- **`--state` does double duty.** It feeds both `state:modified` selection and defer. When the comparison manifest and the defer target should differ, split them with `--defer-state`.

Slim CI is just these two features composed:

```bash
dbt build --select state:modified+ --defer --favor-state --state prod-artifacts
```

Export `DBT_STATE=prod-artifacts` to stop retyping the path.

## 05:02 - [Data Analytics] Difference-in-Differences: The Pre-Trend Check That Decides Whether Your Number Means Anything

You rolled a feature out to one region because you couldn't randomize. Treated stores went from $1,000 to $1,180 in average daily revenue. The before/after read is **+18%**, and it's almost certainly wrong — Q4 lifted everything.

DiD subtracts the drift using a control group that wasn't treated:

| | pre | post | change |
|---|---|---|---|
| treated | $1,000 | $1,180 | **+$180** |
| control | $1,000 | $1,060 | +$60 |

DiD = $180 − $60 = **+$120 (+12%)**. The 2×2 in SQL is four cell means with alternating signs:

```sql
WITH cells AS (
  SELECT is_treated,
         d >= DATE '2026-10-15' AS is_post,
         AVG(revenue) AS mean_rev
  FROM store_daily
  WHERE d BETWEEN DATE '2026-09-15' AND DATE '2026-11-14'
    AND store_id IN (SELECT store_id FROM balanced_panel)
  GROUP BY 1, 2
)
SELECT   MAX(CASE WHEN     is_treated AND     is_post THEN mean_rev END)
       - MAX(CASE WHEN     is_treated AND NOT is_post THEN mean_rev END)
       - MAX(CASE WHEN NOT is_treated AND     is_post THEN mean_rev END)
       + MAX(CASE WHEN NOT is_treated AND NOT is_post THEN mean_rev END) AS did
FROM cells;
```

### The assumption, and how to interrogate it

DiD is only valid under **parallel trends**: absent treatment, both groups would have moved together. You can't test that in the post period — but you can run the identical query on two *pre*-treatment windows, where the answer should be ≈ 0. If an Aug→Sep placebo returns $70, then most of your $120 is pre-existing divergence, not the feature. Better: an event study — one coefficient per period relative to launch, with the pre-period coefficients flat near zero.

### Two things that silently break it

**Unclustered standard errors.** Each store contributes 60 correlated daily rows. Treating them as 60 independent observations shrinks the CI several-fold and manufactures significance. Cluster on the unit:

```python
import statsmodels.formula.api as smf
m = smf.ols("revenue ~ treated * post", data=df).fit(
        cov_type="cluster", cov_kwds={"groups": df["store_id"]})
print(m.params["treated:post"], m.conf_int().loc["treated:post"])
```

Below roughly 30–40 clusters, even clustered errors run optimistic — use wild-bootstrap CIs.

**An unbalanced panel.** Stores that opened mid-window change the composition of the cell mean, so DiD measures mix shift. Hence `balanced_panel`: restrict to units present in *both* periods before you compute anything.
