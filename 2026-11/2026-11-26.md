## 00:03 - [Data Engineering] Ragged Hierarchies: The Bridge Table That Rolls Up a Variable-Depth Tree

Org charts, chart-of-accounts trees and product taxonomies are *ragged*: one branch is three levels deep, another is nine. The source gives you a parent-child column:

```sql
-- dim_employee: employee_key, parent_employee_key, name
```

Two instincts both fail. Flattening into `level_1 … level_5` breaks the day someone adds level 6, and forces you to pad short branches by repeating the leaf downward. Recursive CTEs work, but you can't push one into a BI tool's generated `GROUP BY`, and you re-walk the tree on every query.

Kimball's answer is a **hierarchy bridge table**: one row per ancestor/descendant pair, including each node paired with itself. Build it once per run.

```sql
with recursive paths as (
    select employee_key as ancestor_key,
           employee_key as descendant_key,
           0 as depth
    from dim_employee

    union all

    select p.ancestor_key, e.employee_key, p.depth + 1
    from paths p
    join dim_employee e
      on e.parent_employee_key = p.descendant_key
)
select p.ancestor_key,
       p.descendant_key,
       p.depth,
       not exists (
           select 1 from dim_employee c
           where c.parent_employee_key = p.descendant_key
       ) as descendant_is_leaf
from paths p
```

Now any subtree rollup is a plain equijoin — no recursion at query time:

```sql
select sum(f.expense_amount)
from fct_expense f
join bridge_employee_hierarchy b
  on b.descendant_key = f.employee_key
where b.ancestor_key = 42        -- everything under this VP
```

**The gotcha that bites everyone.** The bridge is deliberately one-to-many, so a fact row joined through it appears once *per ancestor*. Constrain `ancestor_key` to a single node, or `group by b.ancestor_key` — anything else silently inflates the total by the average path length. `depth = 0` gives you the node alone; `depth = 1` gives direct reports.

**Two more things.** Size is the sum of all node depths, so a deep, wide tree can explode — check the row count before you ship it. And the bridge is Type 1: rebuilding it restates history. If reorgs must be reportable "as-was", add effective dates to the bridge rows and filter on the fact's date.

## 05:02 - [Data Analytics] The Winner's Curse: Your Best Variant Measured +1.4pp and Is Really Worth +0.3pp

You run a 6-arm test, pick the arm with the highest observed lift, ship it, and the follow-up quarter shows roughly nothing. This is not a false positive — it is **selection bias in the estimate**. Picking the maximum of several noisy numbers picks arms that got lucky, so the winning number is biased upward even when the arm genuinely is the best.

This is distinct from multiple comparisons. That inflates the chance of *any* significant result; the winner's curse inflates the *size* of the one you selected — and it bites even when the winner is real and significant.

```python
import numpy as np
rng = np.random.default_rng(7)
N, K, PRIOR_SD, SE = 200_000, 6, 0.005, 0.010  # true lifts ~N(0,0.5pp), measurement SE 1.0pp

true = true_lifts = rng.normal(0, PRIOR_SD, (N, K))
obs  = true + rng.normal(0, SE, (N, K))
w    = obs.argmax(1); i = np.arange(N)
ow, tw = obs[i, w], true[i, w]

print(ow.mean()*100, tw.mean()*100)        # 1.42 pp observed vs 0.28 pp true  -> 5.0x
print((tw < 0).mean())                     # 0.274  winner is actually harmful
print((w == true.argmax(1)).mean())        # 0.346  it's the best arm only 1 in 3 times
```

In this (deliberately underpowered: SE double the true spread) setup the shipped winner reads **5x its real effect**, and 27% of the time it is net negative. The two-arm case conditioned on p < 0.05 is just as bad: 2.42pp observed, 0.48pp true.

**The fix is shrinkage.** Pull the estimate toward the prior mean by `τ²/(τ² + SE²)`, where `τ` is the spread of lifts your past tests actually produced — pull that from your experiment log, don't guess:

```python
k = PRIOR_SD**2 / (PRIOR_SD**2 + SE**2)    # 0.20
k * ow.mean()*100                          # 0.28 pp — calibrated
```

RMSE against truth drops from 1.35pp to 0.45pp. Practically: forecast the shrunk number in your business case, not the raw winner; report the loser arms' estimates too, since the spread tells you how much noise you selected on; and when the decision is expensive, re-run the winner head-to-head against control — a confirmation test is the only unbiased estimate you will get.

## 10:02 - [ML & AI] Multi-Label Is Not Multi-Class: Softmax Divides Probability You Don't Have

A support ticket can be *billing* **and** *urgent*. That is multi-label, and it is a different problem from multi-class, where exactly one of K classes is true. The two differ in the output layer, the loss, and — the part people forget — in how you turn scores into predictions.

**Multi-class** uses softmax + `CrossEntropyLoss`: the K outputs are coupled and sum to 1, so raising one lowers the rest. **Multi-label** is K independent binary problems: sigmoid + `BCEWithLogitsLoss`, outputs free to sum to anything from 0 to K.

Use softmax for a multi-label task and you cap yourself arithmetically. With 8 labels and ~3 true per example, softmax must split 1.0 across them, so the correct labels average 0.33 and everything else gets scraps. No single threshold recovers 3 positives; `argmax` returns exactly one, forever.

```python
import torch, torch.nn as nn

y = torch.zeros(1, 8); y[0, [1, 4, 6]] = 1.0   # multi-hot, and must be FLOAT
logits = model(x)                               # (1, 8) raw scores
loss = nn.BCEWithLogitsLoss()(logits, y)        # not CrossEntropyLoss
probs = torch.sigmoid(logits)                   # independent; need not sum to 1
```

For rare labels, pass `pos_weight` — the per-label negative/positive ratio. A label at 2% prevalence gets `pos_weight = 0.98/0.02 ≈ 49`.

Then threshold **per label**, on validation data, not 0.5 globally:

```python
import numpy as np
from sklearn.metrics import f1_score

grid = np.linspace(0.05, 0.95, 19)
thresholds = np.array([
    grid[np.argmax([f1_score(y_val[:, k], probs_val[:, k] >= t) for t in grid])]
    for k in range(n_labels)
])
y_pred = (probs_test >= thresholds).astype(int)
```

Rare labels land near 0.15, common ones near 0.6. Tuning 8 thresholds on validation spends that split, so hold out a separate test set.

Pick the metric deliberately. Micro-F1 pools all N×K decisions and is dominated by frequent labels. Macro-F1 averages per label, so one neglected rare label tanks it. Subset accuracy demands all K correct at once — at 90% independent per-label accuracy with K=8, that's 0.9⁸ ≈ 0.43, which is why it rarely makes a good headline number.

## 15:03 - [Crypto & Business] The QBI Deduction: Why Your Solo 401(k) Contribution Is Worth Less Than Your Tax Bracket

Section 199A lets pass-through owners — sole proprietors, LLCs, partnerships, S-corps — deduct up to 20% of qualified business income. It's taken without itemizing, and the 2025 tax law made it permanent. Most freelancers either forget it or badly overstate it, because two separate limits bite before the headline 20% does.

**QBI is not your gross profit.** You subtract the deductible half of self-employment tax, self-employed health insurance, and retirement contributions first. Then a second cap applies: the deduction can't exceed 20% of taxable income minus net capital gains.

**Worked example** — single filer, $120,000 Schedule C net profit, no other income:

- SE tax: $120,000 × 92.35% = $110,820 × 15.3% = **$16,955**; deductible half = $8,478
- Solo 401(k) employee deferral (2026 limit): **$24,500**
- QBI = 120,000 − 8,478 − 24,500 = **$87,022** → 20% = $17,404
- But AGI = $87,022, minus the $16,100 standard deduction = **$70,922** taxable → 20% of that = **$14,184**

The taxable-income cap is lower, so the deduction is $14,184, not $24,000. At a 22% marginal rate that's roughly **$3,120** of tax saved.

**The non-obvious consequence:** every dollar that reduces taxable income also shrinks the QBI base. Your $24,500 deferral doesn't save 22% — it saves about 22% × (1 − 20%) = **17.6%**, roughly $4,310 instead of $5,390. Still worth doing; just not worth what the bracket table implies.

**The S-corp tension.** W-2 wages you pay yourself are *not* QBI. Take a $60,000 salary out of $120,000 of profit and you cut your QBI base roughly in half, costing ~$12,000 of deduction base to chase payroll-tax savings. Run both numbers before electing.

**Above the income threshold** (~$201,800 single / ~$403,550 joint for 2026), consulting, legal, health, and financial-services businesses — "specified service trades" — phase the deduction out entirely over the next $75,000 / $150,000 of income. Other businesses instead get capped by W-2 wages paid or 2.5% of property basis.
