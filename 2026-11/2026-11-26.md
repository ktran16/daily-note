## 00:03 - [Data Engineering] Ragged Hierarchies: The Bridge Table That Rolls Up a Variable-Depth Tree

Org charts, chart-of-accounts trees and product taxonomies are *ragged*: one branch is three levels deep, another is nine. The source gives you a parent-child column:

```sql
-- dim_employee: employee_key, parent_employee_key, name
```

Two instincts both fail. Flattening into `level_1 … level_5` breaks the day someone adds level 6, and forces you to pad short branches by repeating the leaf downward. Recursive CTEs work, but you can't push one into a BI tool's generated `GROUP BY`, and you re-walk the tree on every query.

Kimball's answer is a **hierarchy bridge table**: one row per ancestor/descendant pair, including each node paired with itself. Build it once per run.

```sql
with recursive paths as (
    select employee_key as ancestor_key,
           employee_key as descendant_key,
           0 as depth
    from dim_employee

    union all

    select p.ancestor_key, e.employee_key, p.depth + 1
    from paths p
    join dim_employee e
      on e.parent_employee_key = p.descendant_key
)
select p.ancestor_key,
       p.descendant_key,
       p.depth,
       not exists (
           select 1 from dim_employee c
           where c.parent_employee_key = p.descendant_key
       ) as descendant_is_leaf
from paths p
```

Now any subtree rollup is a plain equijoin — no recursion at query time:

```sql
select sum(f.expense_amount)
from fct_expense f
join bridge_employee_hierarchy b
  on b.descendant_key = f.employee_key
where b.ancestor_key = 42        -- everything under this VP
```

**The gotcha that bites everyone.** The bridge is deliberately one-to-many, so a fact row joined through it appears once *per ancestor*. Constrain `ancestor_key` to a single node, or `group by b.ancestor_key` — anything else silently inflates the total by the average path length. `depth = 0` gives you the node alone; `depth = 1` gives direct reports.

**Two more things.** Size is the sum of all node depths, so a deep, wide tree can explode — check the row count before you ship it. And the bridge is Type 1: rebuilding it restates history. If reorgs must be reportable "as-was", add effective dates to the bridge rows and filter on the fact's date.

## 05:02 - [Data Analytics] The Winner's Curse: Your Best Variant Measured +1.4pp and Is Really Worth +0.3pp

You run a 6-arm test, pick the arm with the highest observed lift, ship it, and the follow-up quarter shows roughly nothing. This is not a false positive — it is **selection bias in the estimate**. Picking the maximum of several noisy numbers picks arms that got lucky, so the winning number is biased upward even when the arm genuinely is the best.

This is distinct from multiple comparisons. That inflates the chance of *any* significant result; the winner's curse inflates the *size* of the one you selected — and it bites even when the winner is real and significant.

```python
import numpy as np
rng = np.random.default_rng(7)
N, K, PRIOR_SD, SE = 200_000, 6, 0.005, 0.010  # true lifts ~N(0,0.5pp), measurement SE 1.0pp

true = true_lifts = rng.normal(0, PRIOR_SD, (N, K))
obs  = true + rng.normal(0, SE, (N, K))
w    = obs.argmax(1); i = np.arange(N)
ow, tw = obs[i, w], true[i, w]

print(ow.mean()*100, tw.mean()*100)        # 1.42 pp observed vs 0.28 pp true  -> 5.0x
print((tw < 0).mean())                     # 0.274  winner is actually harmful
print((w == true.argmax(1)).mean())        # 0.346  it's the best arm only 1 in 3 times
```

In this (deliberately underpowered: SE double the true spread) setup the shipped winner reads **5x its real effect**, and 27% of the time it is net negative. The two-arm case conditioned on p < 0.05 is just as bad: 2.42pp observed, 0.48pp true.

**The fix is shrinkage.** Pull the estimate toward the prior mean by `τ²/(τ² + SE²)`, where `τ` is the spread of lifts your past tests actually produced — pull that from your experiment log, don't guess:

```python
k = PRIOR_SD**2 / (PRIOR_SD**2 + SE**2)    # 0.20
k * ow.mean()*100                          # 0.28 pp — calibrated
```

RMSE against truth drops from 1.35pp to 0.45pp. Practically: forecast the shrunk number in your business case, not the raw winner; report the loser arms' estimates too, since the spread tells you how much noise you selected on; and when the decision is expensive, re-run the winner head-to-head against control — a confirmation test is the only unbiased estimate you will get.
