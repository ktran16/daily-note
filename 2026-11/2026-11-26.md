## 00:03 - [Data Engineering] Ragged Hierarchies: The Bridge Table That Rolls Up a Variable-Depth Tree

Org charts, chart-of-accounts trees and product taxonomies are *ragged*: one branch is three levels deep, another is nine. The source gives you a parent-child column:

```sql
-- dim_employee: employee_key, parent_employee_key, name
```

Two instincts both fail. Flattening into `level_1 … level_5` breaks the day someone adds level 6, and forces you to pad short branches by repeating the leaf downward. Recursive CTEs work, but you can't push one into a BI tool's generated `GROUP BY`, and you re-walk the tree on every query.

Kimball's answer is a **hierarchy bridge table**: one row per ancestor/descendant pair, including each node paired with itself. Build it once per run.

```sql
with recursive paths as (
    select employee_key as ancestor_key,
           employee_key as descendant_key,
           0 as depth
    from dim_employee

    union all

    select p.ancestor_key, e.employee_key, p.depth + 1
    from paths p
    join dim_employee e
      on e.parent_employee_key = p.descendant_key
)
select p.ancestor_key,
       p.descendant_key,
       p.depth,
       not exists (
           select 1 from dim_employee c
           where c.parent_employee_key = p.descendant_key
       ) as descendant_is_leaf
from paths p
```

Now any subtree rollup is a plain equijoin — no recursion at query time:

```sql
select sum(f.expense_amount)
from fct_expense f
join bridge_employee_hierarchy b
  on b.descendant_key = f.employee_key
where b.ancestor_key = 42        -- everything under this VP
```

**The gotcha that bites everyone.** The bridge is deliberately one-to-many, so a fact row joined through it appears once *per ancestor*. Constrain `ancestor_key` to a single node, or `group by b.ancestor_key` — anything else silently inflates the total by the average path length. `depth = 0` gives you the node alone; `depth = 1` gives direct reports.

**Two more things.** Size is the sum of all node depths, so a deep, wide tree can explode — check the row count before you ship it. And the bridge is Type 1: rebuilding it restates history. If reorgs must be reportable "as-was", add effective dates to the bridge rows and filter on the fact's date.
