## 00:02 - [Data Engineering] dbt Seeds: Type Inference, and the Column You Add That Never Appears

Seeds are CSVs in `seeds/` that dbt loads into the warehouse as tables you can `ref()`. They're for small, static, human-maintained lookups — country codes, account-tier mappings, a list of internal test emails to exclude. They are *not* an ingestion tool: dbt builds one giant `INSERT` statement, so a few thousand rows is the practical ceiling. Raw data belongs in a loader (Fivetran, Airbyte, `COPY`) and arrives as a `source()`.

Two behaviours bite almost everyone.

**1. Types are inferred, and inference loses data.** dbt parses the CSV and guesses each column's type. A zip code column of `01234` becomes an integer and silently loses the leading zero. Pin types explicitly:

```yaml
# seeds/properties.yml
seeds:
  - name: zip_to_region
    config:
      column_types:
        zip_code: varchar(5)
        population: integer
    columns:
      - name: zip_code
        tests: [unique, not_null]
```

Or project-wide in `dbt_project.yml`:

```yaml
seeds:
  my_project:
    +quote_columns: true   # needed if headers have mixed case or spaces
    reference_data:
      +schema: reference
```

**2. `dbt seed` truncates; it does not alter.** On a normal run dbt issues `TRUNCATE` then `INSERT`, which means a *new column* in the CSV is never added to the existing table — your model compiles against a schema that no longer matches the file, and nothing errors loudly. Any schema change (added, removed, or retyped column) requires:

```bash
dbt seed --full-refresh --select zip_to_region
```

Also worth knowing: `dbt run` ignores seeds entirely. Only `dbt seed` and `dbt build` load them, so a CI job running `dbt run && dbt test` will test against yesterday's seed data. Prefer `dbt build`, which interleaves seeds, models, snapshots, and tests in dependency order.

A good rule: if a non-engineer needs to edit it and you want the edit to arrive through a pull request, it's a seed. If a machine produces it, it's a source.

## 05:02 - [Data Analytics] Gaps-and-Islands: Collapsing Consecutive Rows Into Ranges

You have one row per day a user was active and want the contiguous stretches — "active Mar 1–3, then Mar 7–8." `MIN`/`MAX` grouped by `user_id` gives you Mar 1–8, silently welding the gap shut.

The classic fix: subtract a row number from the date. Inside a run of consecutive days, that difference is constant.

```sql
with deduped as (
  select distinct user_id, activity_date from daily_activity
),
grouped as (
  select user_id, activity_date,
         dateadd(day,
                 -row_number() over (partition by user_id order by activity_date),
                 activity_date) as grp
  from deduped
)
select user_id,
       min(activity_date) as island_start,
       max(activity_date) as island_end,
       count(*)           as days_active
from grouped
group by user_id, grp
order by user_id, island_start;
```

For user 42 on Mar 1, 2, 3, 7, 8: `rn` is 1–5, and `date - rn` is Feb 28, Feb 28, Feb 28, Mar 2, Mar 2 — two groups, exactly the two islands.

**Trap 1: duplicates.** `ROW_NUMBER()` hands two rows with the same date different `rn` values, which shifts the offset and splits one island into several. Dedupe first (the `distinct` above) or switch to `dense_rank()`.

**Trap 2: tolerance.** If a run may contain small gaps — sessionize clickstream with a 30-minute idle timeout — the offset trick doesn't apply at all. Use a boundary flag plus a running sum:

```sql
select user_id, event_ts,
       sum(is_new) over (partition by user_id order by event_ts
                         rows between unbounded preceding and current row) as session_id
from (
  select user_id, event_ts,
         case when lag(event_ts) over (partition by user_id order by event_ts) is null
                or timestampdiff(minute,
                     lag(event_ts) over (partition by user_id order by event_ts),
                     event_ts) > 30
              then 1 else 0 end as is_new
  from events
) t;
```

Spell out `rows between` — the default frame for an ordered window is `RANGE`, so tied timestamps would all share one running total and merge sessions that should be distinct.

This generalizes: any "start a new group when X" rule becomes a 0/1 flag plus a cumulative sum. Reach for it on status-change runs, streak counts, and consecutive failed logins. (Syntax shown is Snowflake; swap `dateadd`/`timestampdiff` for `date_sub`/`timestamp_diff` on BigQuery.)

## 10:03 - [ML & AI] Label Smoothing: Your Loss Floor Is 1.01, Not Zero

Label smoothing replaces the one-hot target with a blend of one-hot and uniform:

```
y_smooth = (1 - ε) · onehot + ε/K
```

for `K` classes. This is exactly what `nn.CrossEntropyLoss(label_smoothing=0.1)` does. Two consequences surprise people, and both are arithmetic, not intuition.

**1. The loss can no longer reach zero.** Cross-entropy is minimized when predictions equal the targets, so the best achievable loss is the entropy of the smoothed target, not 0. For `K=1000, ε=0.1`:

```python
import math
K, eps = 1000, 0.1
p_true, p_other = 1 - eps + eps/K, eps/K          # 0.9001, 1e-4
floor = -(p_true*math.log(p_true) + (K-1)*p_other*math.log(p_other))
print(floor)        # 1.0148
print(math.log(p_true/p_other))   # 9.11
```

Your train loss asymptotes near **1.01** and that is convergence, not underfitting. The corollary matters more: **loss is not comparable across ε.** At ε=0.05 the floor is 0.543; at ε=0 it is 0. A run with less smoothing always looks better on loss while possibly being a worse model. Compare accuracy, or subtract the floor — never the raw curves.

**2. It caps the logit gap.** Without smoothing, the optimal logit for the true class diverges — the model is rewarded forever for more confidence. With smoothing, the optimum sits at a finite gap of `log(p_true/p_other)` ≈ **9.11** nats. That bounded gap is the whole mechanism: it's a regularizer on logit magnitude, which is why it reduces overconfidence and usually improves ECE on large-K vision and ASR models.

**Where it backfires:** ε is far more aggressive at small K. At `K=2, ε=0.1` the target is 0.95/0.05 and the gap ceiling is only 2.94 — you've hard-capped predicted probability at 0.95, which destroys any ranking task needing confident tails (fraud, retrieval). Scale ε down for binary and few-class problems, or skip it.

Also **don't smooth a teacher you plan to distill from.** Smoothing collapses the relative similarity structure among wrong classes — exactly the "dark knowledge" the student learns from (Müller et al., 2019).
