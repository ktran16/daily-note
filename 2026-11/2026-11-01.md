## 00:03 - [Data Engineering] Terraform Snowflake Grants: `on_all` Applies Once, `future` Applies Forever

You codify Snowflake RBAC in Terraform, grant `SELECT` on all tables in `analytics.marts` to `reporter`, `terraform apply` goes green. Two weeks later an analyst reports they can't query `fct_subscriptions` — a mart dbt created last Tuesday. Terraform says no changes. Nothing drifted; the grant never covered that table.

Snowflake has two distinct grant concepts, and the provider exposes both:

```hcl
# Backfills EXISTING tables. A one-shot GRANT at apply time.
resource "snowflake_grant_privileges_to_account_role" "marts_existing" {
  account_role_name = "REPORTER"
  privileges        = ["SELECT"]
  on_schema_object {
    all {
      object_type_plural = "TABLES"
      in_schema          = "\"ANALYTICS\".\"MARTS\""
    }
  }
}

# Covers tables created in the FUTURE. Stored in Snowflake, applied at CREATE.
resource "snowflake_grant_privileges_to_account_role" "marts_future" {
  account_role_name = "REPORTER"
  privileges        = ["SELECT"]
  on_schema_object {
    future {
      object_type_plural = "TABLES"
      in_schema          = "\"ANALYTICS\".\"MARTS\""
    }
  }
}
```

`all` is imperative: it expands to `GRANT ... ON ALL TABLES IN SCHEMA` once. The provider cannot read it back as state, so it will never notice new objects — and `terraform plan` stays clean while coverage rots. `future` writes a *rule* into Snowflake that fires on every subsequent `CREATE TABLE`. You almost always need both resources: `future` going forward, `all` to sweep up what already exists.

Three follow-on traps:

- **Views are a separate object type.** `TABLES` does not imply `VIEWS`. A dbt project mixing `table` and `view` materializations needs grants for both plural types.
- **`all` won't re-run on its own.** Set `always_apply = true` (optionally toggling `always_apply_trigger`) when you want the sweep re-issued each apply.
- **`CREATE OR REPLACE` drops grants.** Future grants re-apply automatically; `all`-style grants do not. This is why dbt's full-refresh runs silently revoke access on tables not covered by a future grant.

Rule of thumb: let Terraform own roles, warehouses, and future grants — the durable policy — and let dbt's own `grants` config handle the objects it rebuilds.

## 05:02 - [Data Analytics] Rolling Distinct Counts: The One Aggregate a Window Frame Can't Give You

"Unique users in the trailing 7 days, per day" looks like a window function. It isn't. Try it and Postgres answers `DISTINCT is not implemented for window functions`; engines that do accept `COUNT(DISTINCT x) OVER (...)` generally allow it only over a whole partition, not a sliding frame.

The reason is structural. Sliding frames work because `SUM` and `COUNT` are *decomposable*: slide one row and you add one, subtract one. Distinctness isn't. Dropping day `D-7` should only decrement the count if that user appears nowhere else in the frame, and the frame has no way to know.

The usual fallback is a range join against a date spine:

```sql
SELECT s.day, COUNT(DISTINCT e.user_id) AS uniques_7d
FROM date_spine s
LEFT JOIN user_days e ON e.event_date BETWEEN s.day - 6 AND s.day
GROUP BY s.day;
```

Correct, but each user-day row is duplicated once per day whose window contains it — 7x here, 28x for a monthly window. A 120M-row user-day table becomes ~840M rows to hash-aggregate, and 3.4B at 28 days.

The exact linear alternative: count each user once per span of days they stay "live", then sweep. A user-day at `t` whose previous user-day was `p` keeps that user live for `t .. t+6`, minus the days `p` already covered (through `p+6`):

```sql
WITH user_days AS (SELECT DISTINCT user_id, event_date FROM events),
spans AS (
  SELECT GREATEST(event_date,
           COALESCE(LAG(event_date) OVER (PARTITION BY user_id
                                          ORDER BY event_date) + 7,
                    event_date))  AS lo,
         event_date + 6           AS hi
  FROM user_days
),
net AS (
  SELECT day, SUM(delta) AS delta FROM (
      SELECT lo AS day,  1 AS delta FROM spans
      UNION ALL
      SELECT hi + 1,    -1         FROM spans
  ) t GROUP BY day
)
SELECT s.day,
       SUM(COALESCE(n.delta, 0)) OVER (ORDER BY s.day) AS uniques_7d
FROM date_spine s
LEFT JOIN net n ON n.day = s.day
ORDER BY s.day;
```

Two sorts over ~2N rows instead of a 7N-row join, and no approximation. Hand-check it: events on days 1 and 3 give spans 1–7 and 8–9, so the user is counted on days 1 through 9, once each.

Two things to get right. **Keep the spine in the final select.** The deltas only exist on days a span starts or ends; aggregate them alone and quiet days silently disappear from the result rather than reporting a carried-forward value. **Move `7` and `6` together** — they are `window` and `window - 1`.

Only reach for HLL sketches (`APPROX_COUNT_DISTINCT`, `hll_union`) when you need many window lengths at once and can live with a few percent of error.

## 10:04 - [ML & AI] Focal Loss: γ Rescales the Ratio, Not the Loss

Your fraud model sees 1 positive per 1,000 rows. Training loss drops, the model predicts "not fraud" everywhere, and you reach for focal loss. It's worth knowing exactly what the γ term buys before you pay for it.

Binary cross-entropy on the true-class probability `p_t` is `-log(p_t)`. Focal loss adds a modulating factor:

```
FL = -α_t · (1 - p_t)^γ · log(p_t)
```

With γ=2:

| `p_t` | `(1-p_t)²` | BCE | focal |
|---|---|---|---|
| 0.9 (easy) | 0.01 | 0.1054 | 0.00105 |
| 0.6 | 0.16 | 0.5108 | 0.0817 |
| 0.1 (hard) | 0.81 | 2.3026 | 1.8651 |

Every term shrank, so the absolute numbers tell you nothing — your optimizer only sees relative gradient. The real effect is in the ratio. Under BCE the hard example matters 21.9× more than the easy one; under focal, 1,770×. That factor of 81 is just `(0.9/0.1)² = ((1-p_hard)/(1-p_easy))^γ`. **γ is a dial on the dynamic range of your gradient, not a loss scale.**

α and γ do different jobs, which is where this gets misused. α is static class reweighting; γ is dynamic difficulty reweighting. In the RetinaNet paper the best α for the *rare* class was 0.25 — below 0.5, i.e. downweighting it. Once γ is already favouring hard (mostly rare) examples, stacking aggressive α on top overcorrects. Tune them together, never α alone from class frequency.

Numerically stable version, from logits:

```python
import torch
import torch.nn.functional as F

def focal_loss(logits, targets, alpha=0.25, gamma=2.0):
    bce = F.binary_cross_entropy_with_logits(logits, targets, reduction="none")
    p_t = torch.exp(-bce)                      # = p if y==1 else 1-p
    a_t = alpha * targets + (1 - alpha) * (1 - targets)
    return (a_t * (1 - p_t) ** gamma * bce).mean()
```

The catch: focal loss is not a proper scoring rule, so the outputs stop being calibrated probabilities. If a downstream expected-value decision multiplies your score by a dollar amount, you now need isotonic or Platt calibration on a held-out split.

And it was invented for dense detection — 100k anchors per image, overwhelmingly background. On tabular imbalance, tuning the decision threshold on plain BCE often matches it. Measure that baseline first.

## 15:05 - [Crypto & Business] Business Idea: Underwater-Claim and MAC Appeal Analytics for Independent Pharmacy Groups

**Customer:** owner-operators of 3–15 independent retail pharmacies (not chains, not PBM-owned). They fill ~900–1,200 scripts per store per week and run 2–4% net margin.

**The pain.** Generic drugs are reimbursed off a PBM's MAC (Maximum Allowable Cost) list, which the PBM sets and updates unilaterally. When a wholesaler's acquisition price moves — a shortage, a manufacturer exit — the MAC lags. The pharmacy fills the script anyway (they're contractually obligated) and gets paid less than they paid. A $42.10 bottle reimbursed at $33.60 plus a $0.95 dispensing fee is a **-$7.55 claim**. Roughly 45 states have MAC appeal statutes forcing the PBM to review and, if no in-state pharmacy can acquire at that price, correct the MAC — but the appeal window is typically **7–14 days from remittance**. Owners miss it because reconciliation means hand-matching 835 remittance files against wholesaler invoices across 4 PBMs.

**The math.** 4 stores × 1,100 scripts/week ≈ 229,000 claims/year. At 6% underwater and -$9.40 average, that's **~$129,000/year** bleeding out. Appeals win maybe 25–35%, but the real value is forward: a corrected MAC repays every future fill of that NDC, not just the one appealed.

**Product.** Ingest the 835 ERA files, the wholesaler EDI 810 invoices, and a dispensing export from the PMS (PioneerRx, Liberty, QS/1). Join on NDC + fill date, flag every claim below acquisition + a floor dispensing fee, rank by (unit loss × trailing 90-day fill volume), and generate the appeal packet before the window closes.

**Money:** $299/store/month, plus 20% of documented recoveries in year one.

**Startup cost:** ~$10–15k — an 835/810 parser is the bulk of it, hosting runs under $100/month.

**Main risk:** PMS export formats are bespoke per vendor, so integration #2 is nearly as expensive as #1. Pick one PMS and own it.

**First validation step:** ask one owner for 90 days of 835s and invoices, analyze free, and report underwater dollars per store. Below ~$1,500/store/month recoverable, there's no business here.
