## 00:03 - [Data Engineering] Terraform Snowflake Grants: `on_all` Applies Once, `future` Applies Forever

You codify Snowflake RBAC in Terraform, grant `SELECT` on all tables in `analytics.marts` to `reporter`, `terraform apply` goes green. Two weeks later an analyst reports they can't query `fct_subscriptions` — a mart dbt created last Tuesday. Terraform says no changes. Nothing drifted; the grant never covered that table.

Snowflake has two distinct grant concepts, and the provider exposes both:

```hcl
# Backfills EXISTING tables. A one-shot GRANT at apply time.
resource "snowflake_grant_privileges_to_account_role" "marts_existing" {
  account_role_name = "REPORTER"
  privileges        = ["SELECT"]
  on_schema_object {
    all {
      object_type_plural = "TABLES"
      in_schema          = "\"ANALYTICS\".\"MARTS\""
    }
  }
}

# Covers tables created in the FUTURE. Stored in Snowflake, applied at CREATE.
resource "snowflake_grant_privileges_to_account_role" "marts_future" {
  account_role_name = "REPORTER"
  privileges        = ["SELECT"]
  on_schema_object {
    future {
      object_type_plural = "TABLES"
      in_schema          = "\"ANALYTICS\".\"MARTS\""
    }
  }
}
```

`all` is imperative: it expands to `GRANT ... ON ALL TABLES IN SCHEMA` once. The provider cannot read it back as state, so it will never notice new objects — and `terraform plan` stays clean while coverage rots. `future` writes a *rule* into Snowflake that fires on every subsequent `CREATE TABLE`. You almost always need both resources: `future` going forward, `all` to sweep up what already exists.

Three follow-on traps:

- **Views are a separate object type.** `TABLES` does not imply `VIEWS`. A dbt project mixing `table` and `view` materializations needs grants for both plural types.
- **`all` won't re-run on its own.** Set `always_apply = true` (optionally toggling `always_apply_trigger`) when you want the sweep re-issued each apply.
- **`CREATE OR REPLACE` drops grants.** Future grants re-apply automatically; `all`-style grants do not. This is why dbt's full-refresh runs silently revoke access on tables not covered by a future grant.

Rule of thumb: let Terraform own roles, warehouses, and future grants — the durable policy — and let dbt's own `grants` config handle the objects it rebuilds.

## 05:02 - [Data Analytics] Rolling Distinct Counts: The One Aggregate a Window Frame Can't Give You

"Unique users in the trailing 7 days, per day" looks like a window function. It isn't. Try it and Postgres answers `DISTINCT is not implemented for window functions`; engines that do accept `COUNT(DISTINCT x) OVER (...)` generally allow it only over a whole partition, not a sliding frame.

The reason is structural. Sliding frames work because `SUM` and `COUNT` are *decomposable*: slide one row and you add one, subtract one. Distinctness isn't. Dropping day `D-7` should only decrement the count if that user appears nowhere else in the frame, and the frame has no way to know.

The usual fallback is a range join against a date spine:

```sql
SELECT s.day, COUNT(DISTINCT e.user_id) AS uniques_7d
FROM date_spine s
LEFT JOIN user_days e ON e.event_date BETWEEN s.day - 6 AND s.day
GROUP BY s.day;
```

Correct, but each user-day row is duplicated once per day whose window contains it — 7x here, 28x for a monthly window. A 120M-row user-day table becomes ~840M rows to hash-aggregate, and 3.4B at 28 days.

The exact linear alternative: count each user once per span of days they stay "live", then sweep. A user-day at `t` whose previous user-day was `p` keeps that user live for `t .. t+6`, minus the days `p` already covered (through `p+6`):

```sql
WITH user_days AS (SELECT DISTINCT user_id, event_date FROM events),
spans AS (
  SELECT GREATEST(event_date,
           COALESCE(LAG(event_date) OVER (PARTITION BY user_id
                                          ORDER BY event_date) + 7,
                    event_date))  AS lo,
         event_date + 6           AS hi
  FROM user_days
),
net AS (
  SELECT day, SUM(delta) AS delta FROM (
      SELECT lo AS day,  1 AS delta FROM spans
      UNION ALL
      SELECT hi + 1,    -1         FROM spans
  ) t GROUP BY day
)
SELECT s.day,
       SUM(COALESCE(n.delta, 0)) OVER (ORDER BY s.day) AS uniques_7d
FROM date_spine s
LEFT JOIN net n ON n.day = s.day
ORDER BY s.day;
```

Two sorts over ~2N rows instead of a 7N-row join, and no approximation. Hand-check it: events on days 1 and 3 give spans 1–7 and 8–9, so the user is counted on days 1 through 9, once each.

Two things to get right. **Keep the spine in the final select.** The deltas only exist on days a span starts or ends; aggregate them alone and quiet days silently disappear from the result rather than reporting a carried-forward value. **Move `7` and `6` together** — they are `window` and `window - 1`.

Only reach for HLL sketches (`APPROX_COUNT_DISTINCT`, `hll_union`) when you need many window lengths at once and can live with a few percent of error.
