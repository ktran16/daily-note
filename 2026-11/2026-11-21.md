## 00:03 - [Data Engineering] dbt `microbatch`: One Statement Per Batch, and the `begin` That Fires 1,800 Queries

The `microbatch` incremental strategy (dbt 1.9+) replaces the hand-written `is_incremental()` filter with a declared time grain. dbt splits one run into N independent batches and issues a separate statement per batch, each replacing that window's rows.

```sql
-- models/marts/fct_orders.sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='ordered_at',
    batch_size='day',
    begin='2026-10-01',
    lookback=2
) }}

select order_id, customer_id, ordered_at, amount
from {{ ref('stg_orders') }}
-- no is_incremental() block, no unique_key
```

The upstream filter is the real payoff. Declare `event_time` on the parent and dbt rewrites the `ref()` into the batch window for you:

```yaml
models:
  - name: stg_orders
    config:
      event_time: ordered_at
```

Each batch compiles to `ordered_at >= '2026-11-20' and ordered_at < '2026-11-21'` — half-open, so a row lands in exactly one batch. Because each batch overwrites its own window, a rerun is idempotent with no merge key at all.

**Four things that bite:**

1. **`begin` sizes your first run.** On a full refresh dbt builds every batch from `begin` to now. `begin='2021-01-01'` with `batch_size='day'` is ~1,800 sequential statements. Pick the coarsest grain you can tolerate, or set `concurrent_batches: true` where your adapter supports it.
2. **Missing upstream `event_time` silently scans everything.** No `event_time` on the parent means no injected filter — the model still builds, just at full-table cost.
3. **Boundaries are computed in UTC.** If `ordered_at` is stored in local time, rows drift into neighbouring batches and your daily totals are off at both edges.
4. **Partial success is not failure.** One bad batch leaves the others committed; the run exits non-zero as a partial success. `dbt retry` reruns only the failed batches — but a downstream model that ignores exit status will read a half-filled table.

Backfills become a CLI flag instead of a code change:

```bash
dbt run -s fct_orders --event-time-start "2026-09-01" --event-time-end "2026-10-01"
```

Use it when late-arriving data has a known bound; `lookback` reprocesses that many prior batches every run.

## 05:02 - [Data Analytics] Half-Open Intervals: The `BETWEEN` That Drops Your Last Day

`BETWEEN` is inclusive on both ends. On a `DATE` column that is what you want. On a `TIMESTAMP` column it quietly deletes a day.

```sql
-- October revenue. Looks right. Is wrong.
select sum(amount) as revenue
from orders
where ordered_at between '2026-10-01' and '2026-10-31';
```

`'2026-10-31'` is cast to `2026-10-31 00:00:00`, so every order placed after midnight on the 31st is excluded. You get 30 days and one instant out of 31. With evenly spread volume that is a 3.2% undercount — on a $2.93M month, the dashboard reports $2.84M. Small enough to survive review, large enough to miss a target.

The usual patch makes it worse:

```sql
where ordered_at between '2026-10-01' and '2026-10-31 23:59:59'
```

Timestamps carry sub-second precision. Postgres and Snowflake store microseconds, so `23:59:59.482` is now dropped. You traded 24 hours of loss for 1 second — still a bug, and one nobody will ever spot in a diff.

**Write half-open intervals instead: inclusive lower bound, exclusive upper bound.**

```sql
where ordered_at >= '2026-10-01'
  and ordered_at <  '2026-11-01'
```

This is correct at any precision, for `DATE`, `TIMESTAMP`, and `TIMESTAMPTZ`, and it stays sargable — the planner can still use an index or partition-prune on `ordered_at`, which `cast(ordered_at as date) = ...` and `date_trunc('day', ordered_at)` both prevent.

The second payoff is composition. Half-open buckets tile the timeline with no gaps and no overlaps, so adjacent periods can never double-count a row:

```sql
-- monthly buckets that provably sum to the total
select date_trunc('month', d.month_start) as month, sum(o.amount)
from month_spine d
left join orders o
  on o.ordered_at >= d.month_start
 and o.ordered_at <  d.month_start + interval '1 month'
group by 1;
```

Two closed ranges ending and starting on `2026-10-31` both claim that day's rows. Half-open ranges cannot.

Rule of thumb: reserve `BETWEEN` for true `DATE` and integer columns. The moment a column has a time component, switch to `>=` / `<`. Audit it by comparing the two forms — any difference is data you were losing.
