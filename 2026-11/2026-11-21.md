# Daily Notes - 2026-11-21

## 00:03 - [Data Engineering] dbt `microbatch`: One Statement Per Batch, and the `begin` That Fires 1,800 Queries

The `microbatch` incremental strategy (dbt 1.9+) replaces the hand-written `is_incremental()` filter with a declared time grain. dbt splits one run into N independent batches and issues a separate statement per batch, each replacing that window's rows.

```sql
-- models/marts/fct_orders.sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='ordered_at',
    batch_size='day',
    begin='2026-10-01',
    lookback=2
) }}

select order_id, customer_id, ordered_at, amount
from {{ ref('stg_orders') }}
-- no is_incremental() block, no unique_key
```

The upstream filter is the real payoff. Declare `event_time` on the parent and dbt rewrites the `ref()` into the batch window for you:

```yaml
models:
  - name: stg_orders
    config:
      event_time: ordered_at
```

Each batch compiles to `ordered_at >= '2026-11-20' and ordered_at < '2026-11-21'` — half-open, so a row lands in exactly one batch. Because each batch overwrites its own window, a rerun is idempotent with no merge key at all.

**Four things that bite:**

1. **`begin` sizes your first run.** On a full refresh dbt builds every batch from `begin` to now. `begin='2021-01-01'` with `batch_size='day'` is ~1,800 sequential statements. Pick the coarsest grain you can tolerate, or set `concurrent_batches: true` where your adapter supports it.
2. **Missing upstream `event_time` silently scans everything.** No `event_time` on the parent means no injected filter — the model still builds, just at full-table cost.
3. **Boundaries are computed in UTC.** If `ordered_at` is stored in local time, rows drift into neighbouring batches and your daily totals are off at both edges.
4. **Partial success is not failure.** One bad batch leaves the others committed; the run exits non-zero as a partial success. `dbt retry` reruns only the failed batches — but a downstream model that ignores exit status will read a half-filled table.

Backfills become a CLI flag instead of a code change:

```bash
dbt run -s fct_orders --event-time-start "2026-09-01" --event-time-end "2026-10-01"
```

Use it when late-arriving data has a known bound; `lookback` reprocesses that many prior batches every run.
