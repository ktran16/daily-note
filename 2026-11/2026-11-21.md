## 00:03 - [Data Engineering] dbt `microbatch`: One Statement Per Batch, and the `begin` That Fires 1,800 Queries

The `microbatch` incremental strategy (dbt 1.9+) replaces the hand-written `is_incremental()` filter with a declared time grain. dbt splits one run into N independent batches and issues a separate statement per batch, each replacing that window's rows.

```sql
-- models/marts/fct_orders.sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='ordered_at',
    batch_size='day',
    begin='2026-10-01',
    lookback=2
) }}

select order_id, customer_id, ordered_at, amount
from {{ ref('stg_orders') }}
-- no is_incremental() block, no unique_key
```

The upstream filter is the real payoff. Declare `event_time` on the parent and dbt rewrites the `ref()` into the batch window for you:

```yaml
models:
  - name: stg_orders
    config:
      event_time: ordered_at
```

Each batch compiles to `ordered_at >= '2026-11-20' and ordered_at < '2026-11-21'` — half-open, so a row lands in exactly one batch. Because each batch overwrites its own window, a rerun is idempotent with no merge key at all.

**Four things that bite:**

1. **`begin` sizes your first run.** On a full refresh dbt builds every batch from `begin` to now. `begin='2021-01-01'` with `batch_size='day'` is ~1,800 sequential statements. Pick the coarsest grain you can tolerate, or set `concurrent_batches: true` where your adapter supports it.
2. **Missing upstream `event_time` silently scans everything.** No `event_time` on the parent means no injected filter — the model still builds, just at full-table cost.
3. **Boundaries are computed in UTC.** If `ordered_at` is stored in local time, rows drift into neighbouring batches and your daily totals are off at both edges.
4. **Partial success is not failure.** One bad batch leaves the others committed; the run exits non-zero as a partial success. `dbt retry` reruns only the failed batches — but a downstream model that ignores exit status will read a half-filled table.

Backfills become a CLI flag instead of a code change:

```bash
dbt run -s fct_orders --event-time-start "2026-09-01" --event-time-end "2026-10-01"
```

Use it when late-arriving data has a known bound; `lookback` reprocesses that many prior batches every run.

## 05:02 - [Data Analytics] Half-Open Intervals: The `BETWEEN` That Drops Your Last Day

`BETWEEN` is inclusive on both ends. On a `DATE` column that is what you want. On a `TIMESTAMP` column it quietly deletes a day.

```sql
-- October revenue. Looks right. Is wrong.
select sum(amount) as revenue
from orders
where ordered_at between '2026-10-01' and '2026-10-31';
```

`'2026-10-31'` is cast to `2026-10-31 00:00:00`, so every order placed after midnight on the 31st is excluded. You get 30 days and one instant out of 31. With evenly spread volume that is a 3.2% undercount — on a $2.93M month, the dashboard reports $2.84M. Small enough to survive review, large enough to miss a target.

The usual patch makes it worse:

```sql
where ordered_at between '2026-10-01' and '2026-10-31 23:59:59'
```

Timestamps carry sub-second precision. Postgres and Snowflake store microseconds, so `23:59:59.482` is now dropped. You traded 24 hours of loss for 1 second — still a bug, and one nobody will ever spot in a diff.

**Write half-open intervals instead: inclusive lower bound, exclusive upper bound.**

```sql
where ordered_at >= '2026-10-01'
  and ordered_at <  '2026-11-01'
```

This is correct at any precision, for `DATE`, `TIMESTAMP`, and `TIMESTAMPTZ`, and it stays sargable — the planner can still use an index or partition-prune on `ordered_at`, which `cast(ordered_at as date) = ...` and `date_trunc('day', ordered_at)` both prevent.

The second payoff is composition. Half-open buckets tile the timeline with no gaps and no overlaps, so adjacent periods can never double-count a row:

```sql
-- monthly buckets that provably sum to the total
select date_trunc('month', d.month_start) as month, sum(o.amount)
from month_spine d
left join orders o
  on o.ordered_at >= d.month_start
 and o.ordered_at <  d.month_start + interval '1 month'
group by 1;
```

Two closed ranges ending and starting on `2026-10-31` both claim that day's rows. Half-open ranges cannot.

Rule of thumb: reserve `BETWEEN` for true `DATE` and integer columns. The moment a column has a time component, switch to `>=` / `<`. Audit it by comparing the two forms — any difference is data you were losing.

## 10:02 - [ML & AI] Early Stopping Spends Your Validation Set, Then You Report Its Score

`early_stopping_rounds` is not free regularization — it is a hyperparameter search. It evaluates the model on your eval set after every boosting round and keeps the round with the best score. Picking the maximum of ~1,000 noisy evaluations on one dataset is selection, and the selected score is biased upward. If you then report that number, you are reporting the winner of a search on the data you searched over.

```python
import lightgbm as lgb
from sklearn.model_selection import train_test_split
from sklearn.metrics import roc_auc_score

# WRONG: eval_set is also the reported set
X_tr, X_val, y_tr, y_val = train_test_split(X, y, test_size=0.2, random_state=0)
m = lgb.LGBMClassifier(n_estimators=2000, learning_rate=0.05)
m.fit(X_tr, y_tr, eval_set=[(X_val, y_val)], eval_metric='auc',
      callbacks=[lgb.early_stopping(50, verbose=False)])
# m.best_score_ on X_val is optimistic — X_val chose best_iteration_
```

The fix is a three-way split: one set stops the training, a different set scores it.

```python
X_tr, X_tmp, y_tr, y_tmp = train_test_split(X, y, test_size=0.3, random_state=0)
X_es, X_te, y_es, y_te = train_test_split(X_tmp, y_tmp, test_size=0.5, random_state=0)
m.fit(X_tr, y_tr, eval_set=[(X_es, y_es)], eval_metric='auc',
      callbacks=[lgb.early_stopping(50, verbose=False)])
score = roc_auc_score(y_te, m.predict_proba(X_te)[:, 1])   # honest
```

**Scale of the problem.** On a 2,000-row eval set with AUC ≈ 0.80, the standard error is roughly 0.010–0.012. Taking the max over a long, autocorrelated score curve typically buys 0.005–0.010 of AUC that does not exist. Small on its own — and then you run 100 tuning trials, each re-maximizing on the same eval set, and the optimism compounds into the choice of `learning_rate` and `num_leaves` too.

**Inside cross-validation**, early-stop on the fold's own validation part, collect `best_iteration_` per fold, then refit on all data with the mean (times `1/(1-1/k)` to account for the larger training set). Never early-stop against a fixed set shared by all folds — that set leaks into every fold.

Quick check: if `best_iteration_` differs by more than ~2x across folds, your eval set is too small to be choosing anything.

## 15:02 - [Crypto & Business] SDE vs EBITDA: Why the Same Business Prices at 3× One Number and 5× Another

Owners of small businesses often quote a value from the wrong earnings number. There are two, and they answer different questions.

**SDE (Seller's Discretionary Earnings)** asks: *what does this business put in the pocket of one owner-operator?* It assumes the buyer replaces the seller and draws the salary themselves.

**Adjusted EBITDA** asks: *what does this business earn as a standalone asset?* It charges a market-rate manager as a real expense, because the buyer is not going to run it.

Worked example. An LLC with $2.4M revenue and $180K of net income on the tax return:

| Line | Amount |
|---|---|
| Net income | $180,000 |
| + Interest expense | $25,000 |
| + Depreciation & amortization | $60,000 |
| + Owner W-2 salary + payroll tax | $140,000 |
| + Personal auto, health, phone | $18,000 |
| + One-time legal settlement | $35,000 |
| **SDE** | **$458,000** |
| − Market GM salary | ($110,000) |
| **Adjusted EBITDA** | **$348,000** |

Main Street deals (SDE under roughly $1M) price on SDE at about 2.0–4.0×. Lower-middle-market buyers price on EBITDA at roughly 4–7×. Here: 3.0 × $458K = **$1.37M**, versus 4.5 × $348K = **$1.57M**. Same business, same year, both defensible. The spread is the manager's salary and the buyer's cost of capital — not a negotiation win.

Three things that actually move the multiple, more than the earnings do: owner dependence (if you hold the customer relationships, you *are* the asset), customer concentration (one client at 30% of revenue typically costs a half-turn or more), and recurring versus project revenue.

Two practical notes. Add-backs need documentation — a quality-of-earnings review strips anything you can't tie to a statement, and at 3× a $40K add-back you can't prove erases $120K of price. And headline price is not cash: a working-capital peg, a 10–15% seller note, and an earnout routinely move 30%+ of it past closing.

*Educational content on valuation mechanics, not financial or investment advice.*

## 19:02 - [PC Hardware] Benchmarking Discipline: Thermal Soak, Variance, and When a 3% Gain Is Noise

A single benchmark run is not a measurement. Two separate errors corrupt it, and they pull in opposite directions.

**Thermal soak.** Modern silicon boosts hardest when cold. An Intel chip runs at PL2 for its Tau window (28–56s on most desktop boards) before dropping to PL1; a GeForce card loses roughly 15 MHz of boost per 10°C above ~50°C, so a card that opens at 2900 MHz at 40°C settles near 2600–2700 MHz once the heatsink mass saturates. That takes 8–12 minutes, longer for a 360mm AIO. A cold Cinebench pass and a 10-minute loop can differ 10–20%. Discard the first run; loop until temperature drifts under ~1°C/min, then start recording.

**Run-to-run variance.** Report the median of 3–5 runs *and* the spread. Compute the coefficient of variation:

```bash
# scores.txt = one result per line
awk '{s+=$1; a[NR]=$1} END {m=s/NR; for(i=1;i<=NR;i++) v+=(a[i]-m)^2;
  printf "mean %.1f  sd %.2f  CV %.2f%%\n", m, sqrt(v/NR), 100*sqrt(v/NR)/m}' scores.txt
```

If CV exceeds ~2%, the bench is too noisy to judge small deltas. **A difference smaller than your measured spread is not a result** — most "3% uplift" claims die here.

**Control the variables.** Log ambient temperature and reason about delta-T, not absolute temps. Pin a fixed fan curve, because "silent" profiles ramp on a timer and change mid-run. Kill shader compilation, Windows Update, and browsers. Disable VRR and frame caps, which clamp the very number you are measuring.

Useful logging on Linux:

```bash
sudo cpupower frequency-set -g performance          # stop governor drift
sudo turbostat --interval 1                          # pkg power, effective clocks
nvidia-smi --query-gpu=clocks.sm,temperature.gpu,power.draw,\
clocks_event_reasons.active --format=csv -l 1
```

| Log this | Why |
|---|---|
| Effective clock (not requested) | Shows real throttling |
| Power draw vs limit | Distinguishes power from thermal limits |
| Throttle reason flags | Names the actual ceiling |
| Ambient temp | Makes runs comparable across days |

Change one variable per test. Two changes at once produce a story, not data.
