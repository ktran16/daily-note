## 00:03 - [Data Engineering] Flink State TTL: The Checkpoint That Grows Until Recovery Takes an Hour

A streaming job that keys state by `user_id`, `session_id`, or `order_id` accumulates one entry per key forever. The job runs fine for weeks — then a restart takes 40 minutes because the checkpoint is 300 GB, almost all of it keys last touched in March. Keyed state has no expiry unless you ask for one.

### TTL is per state descriptor, not per job

```java
StateTtlConfig ttl = StateTtlConfig
    .newBuilder(Time.days(7))
    .setUpdateType(StateTtlConfig.UpdateType.OnReadAndWrite)
    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
    .cleanupInRocksdbCompactFilter(1000L)   // queries processed per TTL check
    .build();

ValueStateDescriptor<Profile> desc =
    new ValueStateDescriptor<>("profile", Profile.class);
desc.enableTimeToLive(ttl);   // easy to forget on the second state
```

Every `ValueState`, `MapState`, and `ListState` needs its own `enableTimeToLive`. One missed descriptor and the job still leaks.

### Three defaults that bite

**`UpdateType.OnCreateAndWrite` is the default.** Reads do not refresh the timestamp, so a key read on every event but written once expires after 7 days and silently comes back empty. If "active" means read, use `OnReadAndWrite`.

**Expiry is lazy.** An expired entry is dropped when it is next accessed. Keys that never return are never touched, so they never leave — which is exactly the leak you were fixing. You need background cleanup: `cleanupInRocksdbCompactFilter(n)` for RocksDB, `cleanupIncrementally(n, runOnRecord)` for the heap backend. `cleanupFullSnapshot()` shrinks the *snapshot* only; running state keeps growing.

**TTL is part of state schema.** Enabling TTL on state restored from a savepoint that had none — or disabling it — throws `StateMigrationException`. Plan the cutover: drain to a savepoint, or start from a fresh state UID.

### In SQL

```sql
SET 'table.exec.state.ttl' = '7 d';
```

This covers regular joins, dedup, and non-windowed aggregates. Do **not** rely on it for windows and interval joins — those are cleaned by watermark, and a TTL shorter than your window will delete state mid-computation and quietly produce wrong results.

## 05:02 - [Data Analytics] Semi-Additive Measures: The Balance You Can Sum Across Accounts But Not Across Days

Most facts are fully additive: sum revenue across products and across days, both answers are right. Snapshot facts are not. A `daily_balances` table with one row per account per day holds **semi-additive** measures — additive across every dimension *except* time.

Three accounts at \$1,000 each, snapshotted daily for 30 days:

```sql
-- WRONG: $90,000. You summed the same money 30 times.
SELECT date_trunc('month', snapshot_date) AS mo, SUM(balance)
FROM daily_balances GROUP BY 1;
```

The true month-end figure is \$3,000 — a 30x overstatement that scales with your date range, so it looks plausible on a single day and absurd on a quarter.

The fix is to collapse time to one point first, then sum across accounts. The naive version joins to the period's max date:

```sql
WITH last_day AS (
  SELECT date_trunc('month', snapshot_date) AS mo, MAX(snapshot_date) AS d
  FROM daily_balances GROUP BY 1
)
SELECT l.mo, SUM(b.balance) AS closing_balance
FROM daily_balances b JOIN last_day l ON b.snapshot_date = l.d
GROUP BY 1;
```

This silently drops any account whose pipeline missed the last day. Take the latest row *per account* instead:

```sql
SELECT mo, SUM(balance) AS closing_balance
FROM (
  SELECT date_trunc('month', snapshot_date) AS mo, account_id, balance,
         ROW_NUMBER() OVER (
           PARTITION BY date_trunc('month', snapshot_date), account_id
           ORDER BY snapshot_date DESC) AS rn
  FROM daily_balances
) t
WHERE rn = 1 GROUP BY 1;
```

In Power BI, `SUM(Balances[balance])` has the same bug. Use a last-non-blank pattern:

```dax
Closing Balance =
CALCULATE (
    SUM ( Balances[balance] ),
    LASTNONBLANK ( 'Date'[Date], CALCULATE ( COUNTROWS ( Balances ) ) )
)
```

Two notes. First, *closing* is not the only valid aggregate — interest and inventory carrying cost want the **average daily** balance (`AVG` over days, then `SUM` over accounts), and that is a different number. Decide which one the KPI means and write it into the metric definition. Second, headcount, open tickets, inventory on hand, and subscription MRR snapshots are all the same shape. If a measure answers "how much exists right now," it is semi-additive, and a plain `SUM` over a date range is wrong by roughly the number of periods you scanned.

## 10:02 - [ML & AI] Implicit Feedback: Your Recommender's Zeros Are "Unseen," Not "Disliked"

Rating-prediction tutorials train on a sparse matrix of 1–5 stars and minimize RMSE over the *observed* cells. Real logs have no stars — only plays, clicks, and purchases. Reusing the rating recipe on that data breaks in a specific way: if you fit only the observed cells, every target is a positive, so the optimal model is "predict 1 everywhere." The signal lives in the cells you *excluded*.

The fix is to train over the **full** matrix and separate preference from confidence (Hu, Koren & Volinsky 2008):

```
p_ui = 1 if r_ui > 0 else 0          # binary preference
c_ui = 1 + α · r_ui                  # confidence in that preference
min Σ_{u,i} c_ui (p_ui − xᵘ·yⁱ)² + λ(‖xᵘ‖² + ‖yⁱ‖²)
```

Every user–item pair contributes, but with wildly different weight. With `α = 40`: an unobserved pair gets `c = 1`, a pair with 3 plays gets `c = 1 + 40·3 = 121`. A zero is a *weak* negative — nudged toward 0 with weight 1 — not an asserted dislike. That one weighting is what makes the dense sum tractable and correct.

```python
import scipy.sparse as sp
from implicit.als import AlternatingLeastSquares

# counts, NOT 0/1 — alpha scaling needs the magnitude
ui = sp.csr_matrix((plays, (user_idx, item_idx)))
model = AlternatingLeastSquares(factors=64, regularization=0.05, alpha=40)
model.fit(ui)
ids, scores = model.recommend(0, ui[0], N=10, filter_already_liked_items=True)
```

Two consequences people miss.

**RMSE is meaningless here.** The scores aren't calibrated probabilities and nobody sees a number — they see a ranked list. Evaluate with `recall@k`, `MAP@k`, or `NDCG@k`.

**Random cell holdout leaks.** Hiding random (user, item) entries lets the model see a user's *later* behavior while predicting an earlier item. Split by timestamp, or do leave-last-*n*-out per user, and drop users with too little history rather than scoring them from one interaction.

Also log a popularity baseline (top-N most-played, same metric). Implicit-feedback models absorb popularity bias happily, and plenty of "+12% NDCG" wins turn out to be slightly worse than recommending the global top 10.
