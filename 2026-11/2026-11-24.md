## 00:02 - [Data Engineering] dbt `state:modified` Subtypes: The Slim CI Run That Rebuilds Everything

Slim CI rests on one selector:

```bash
dbt build --select "state:modified+" --defer --state ./prod-artifacts
```

It compares each node against the production `manifest.json` and builds only what changed. Then one day a one-line change to a staging model queues 400 models, and the "slim" run costs more than a full refresh.

`state:modified` is not one check. It is the union of several, each selectable on its own:

| Subtype | Fires when |
|---|---|
| `state:modified.body` | the node's SQL changed |
| `state:modified.configs` | any config (materialization, tags, partitioning) changed |
| `state:modified.relation` | database, schema, or alias changed |
| `state:modified.macros` | a macro the node depends on changed |
| `state:modified.contract` | the enforced contract changed |
| `state:modified.persisted_descriptions` | a description changed with `persist_docs` on |

Two of these cause nearly all the surprise rebuilds.

**Macros.** Touch a macro that every model calls — a `cents_to_dollars`, a dispatch shim, anything in a `{{ }}` everyone uses — and every caller is modified. That is correct, not a bug: the compiled SQL could differ. But it means a whitespace fix in a utility macro is a full-project build.

**Environment-dependent config.** Nodes carry the rendered values of `env_var()` and `target`-conditional logic. If prod's manifest was generated with `target: prod` and CI runs with `target: ci`, anything like this marks the model modified on every run:

```sql
{{ config(snowflake_warehouse=env_var('DBT_WAREHOUSE')) }}
```

dbt 1.9 added a behaviour flag that compares the *unrendered* config instead, which removes most of these false positives:

```yaml
# dbt_project.yml
flags:
  state_modified_compare_more_unrendered_values: True
```

Practical steps: turn the flag on; generate the deferral manifest from a job whose target and env vars match CI; and when you want to know what actually changed in SQL, run `dbt ls --select "state:modified.body+" --state ./prod-artifacts` and diff it against plain `state:modified+`. The gap between those two lists is your bill.

## 05:05 - [Data Analytics] Day-of-Week Seasonality: The Detector That Flags Every Saturday and Misses the Outage

Switching an anomaly check from mean/stddev to median/MAD fixes masking, but it keeps a deeper assumption: that the series has *one* baseline. Most business series have seven.

Twelve weeks of orders — weekdays around 1,000, weekends around 400 — with one real incident: Wednesday 2026-10-14 falls to 700, a 30% drop against the Wednesday norm.

A pooled robust baseline over that data gives median 962, MAD 65:

```sql
WITH s AS (SELECT d, orders, MEDIAN(orders) OVER () AS m FROM daily_orders),
t AS (SELECT d, orders, m, MEDIAN(ABS(orders - m)) OVER () AS mad FROM s)
SELECT d, orders, ROUND(0.6745 * (orders - m) / NULLIF(mad, 0), 1) AS rz FROM t;
```

At `|rz| > 3.5` this fires **24 times in 84 days — every weekend in the sample, and nothing else**. The incident scores **−2.7** and never fires. The detector is simultaneously all false positives and blind to the one event that mattered.

No threshold rescues it. Weekend scores run 5.5–6.2 while the incident sits at 2.7, so every cutoff that silences Saturday also hides the outage: at 6 you get three flags (still all weekends), at 10 you get silence.

Score each day against its own weekday instead:

```sql
WITH s AS (
  SELECT d, orders, dayofweek(d) AS dw,
         MEDIAN(orders) OVER (PARTITION BY dayofweek(d)) AS m
  FROM daily_orders),
t AS (SELECT *, MEDIAN(ABS(orders - m)) OVER (PARTITION BY dw) AS mad FROM s)
SELECT d, orders, ROUND(0.6745 * (orders - m) / NULLIF(mad, 0), 1) AS rz
FROM t WHERE ABS(0.6745 * (orders - m) / NULLIF(mad, 0)) > 3.5;
```

Wednesday's baseline is now median 1,003.5, MAD 22.5, and 700 scores **−9.1**. One flag in 84 days: the right one.

Two caveats worth knowing:

- Partitioning over all history puts the day being judged inside its own baseline. A trailing frame (`ORDER BY d ROWS BETWEEN 8 PRECEDING AND 1 PRECEDING`, inside the partition) excludes it — but eight observations make MAD jumpy; in the same run it added three marginal flags at `|rz|` 3.6–4.0 against the incident's 7.0. Rank alerts by `|rz|` rather than trusting the cutoff alone.
- Day-of-week is the easy seasonality. With trend, holidays and monthly cycles stacked on it, decompose instead — `STL(s, period=7, robust=True)` — and score `res.resid`. Recalibrate there: on this series STL fit so tightly that 18 of 84 days cleared 3.5 on noise alone.

Verified on DuckDB 2.0.1 and statsmodels 0.15. `dayofweek()` is DuckDB/Snowflake; use `EXTRACT(DOW FROM d)` on Postgres (where `MEDIAN` is not a window function — use `PERCENTILE_CONT(0.5) WITHIN GROUP` over a grouped join) and `EXTRACT(DAYOFWEEK FROM d)` on BigQuery.

## 10:09 - [ML & AI] Adversarial Validation: Train a Classifier to Tell Train From Test

Your CV says AUC 0.90. Production says 0.78. The usual suspects — leakage, overfit tuning — come up clean. The remaining explanation is that your training rows and your serving rows are not drawn from the same distribution, and there is a direct way to measure that.

**The trick.** Throw away the target. Label training rows 0 and serving rows 1, stack them, and train a classifier to tell them apart. If it can't — cross-validated AUC near 0.5 — the two sets are indistinguishable on your features, which is what you want. If it can, whatever it used is your shift.

```python
import numpy as np, pandas as pd, lightgbm as lgb
from sklearn.model_selection import cross_val_predict, StratifiedKFold
from sklearn.metrics import roc_auc_score

X = pd.concat([train[feats], serve[feats]], ignore_index=True)
is_serve = np.r_[np.zeros(len(train)), np.ones(len(serve))]

clf = lgb.LGBMClassifier(n_estimators=300, learning_rate=0.05)
cv = StratifiedKFold(5, shuffle=True, random_state=0)
p = cross_val_predict(clf, X, is_serve, cv=cv, method="predict_proba")[:, 1]
print(roc_auc_score(is_serve, p))        # 0.87 — separable
```

0.87 means "separable." Fit once more and read the importances to find out *by what*:

```python
clf.fit(X, is_serve)
print(pd.Series(clf.feature_importances_, index=feats).nlargest(5))
```

Top feature: `account_id` — IDs increase with signup date, so it is a thinly disguised timestamp. Drop it and AUC falls to 0.58. That residual is real but mild drift.

**Three uses, in order of safety.**

1. *Diagnose.* Anything that separates train from serve is suspect. IDs, row numbers, and version strings are pure artifacts — drop them.
2. *Build an honest validation set.* Rank training rows by `p` and hold out the most serve-like 20% as your validation fold. It scores lower than random CV, and that lower number is the one that matches production.
3. *Importance-weight.* Train with `w = p / (1 - p)`. Weights explode: `p=0.95` gives 19. Clip at the 99th percentile and check what you have left — effective sample size `ESS = sum(w)**2 / sum(w**2)`. On 50,000 rows this gave ESS 6,400, so 87% of the data stopped counting. Often not worth it.

**The limit.** AUC 0.5 rules out covariate shift only. P(y|x) can change with P(x) untouched — identical feature distributions, inverted relationship. For that you need labels, not this.
