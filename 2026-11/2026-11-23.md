## 00:03 - [Data Engineering] Spark `coalesce(1)`: The "Optimization" That Makes Your Whole Job Single-Threaded

Everyone learns `coalesce` as "like `repartition`, but cheaper — no shuffle." That's true, and it's exactly why `coalesce(1)` is one of the most damaging one-liners in Spark.

**The difference.** `repartition(n)` does a full shuffle: it can increase or decrease partition count and redistributes rows evenly. `coalesce(n)` only reduces, and it does so by *merging existing partitions into the same tasks* — a narrow dependency, no data movement.

**Why narrow is the problem.** A narrow dependency doesn't create a stage boundary. It propagates *backwards* through the lineage. So this:

```python
(spark.read.parquet("s3://events/")   # 2,000 partitions
     .filter(F.col("status") == "paid")
     .withColumn("rev", heavy_udf("payload"))
     .coalesce(1)
     .write.parquet("s3://out/"))
```

does not run the read, filter and UDF across 2,000 tasks and then merge. It runs the **entire chain in one task on one core**. Your 40-executor cluster idles while one JVM streams terabytes. Often it OOMs instead.

**The fix** is counterintuitive: pay for a shuffle.

```python
.repartition(1)   # shuffle boundary → upstream still runs with 2,000 tasks
```

`repartition` inserts a stage boundary, so everything before it keeps full parallelism; only the final write is serial. Better still, don't force one file — write naturally and compact later, or size the output deliberately:

```python
.repartition(200)                      # ~ target_bytes / 128MB
```

**Where `coalesce` is right:** shrinking after a highly selective filter, when the *remaining* work is trivial — e.g. `df.filter(...).coalesce(50).write...`. Reducing 2,000 nearly-empty partitions to 50 avoids 2,000 tiny files at zero shuffle cost.

**Two adjacent traps.**

1. AQE's `spark.sql.adaptive.coalescePartitions.enabled` is *not* this. It coalesces **post-shuffle** partitions after reading real map-output sizes. It's safe and should stay on.
2. Writing partitioned output without a matching repartition gives you `tasks × partitions` files. Align them:

```python
df.repartition("dt").write.partitionBy("dt").parquet(path)   # ~1 file per dt
```

**Rule of thumb:** `coalesce` to clean up *after* the expensive work, `repartition` when the expensive work is still *ahead* of you.

## 05:02 - [Data Analytics] Prediction Intervals vs Confidence Intervals: The "95%" Forecast Band That Holds 36% of Actuals

You ship a forecast with a shaded 95% band. Next quarter, actuals land outside it constantly, and somebody asks whether the model is broken. The model is fine — you plotted the wrong interval.

Two different questions have two different answers:

- **Confidence interval** — "where is the *expected value* at this x?" Scales with `s·√(leverage)`, and shrinks toward zero as n grows.
- **Prediction interval** — "where will the *next actual observation* fall?" Scales with `s·√(1 + leverage)`. That `1 +` is the irreducible noise of a single draw, and no amount of data removes it.

Fit `y = 50 + 0.3x + N(0, 10)` on n=100 points and forecast one step past the end:

```
one step ahead   fit = 79.61   CI ±3.93   PI ±19.88   →  PI is 5.1x wider
31 steps ahead   fit = 88.72   CI ±5.77   PI ±20.33
```

Monte Carlo over 20,000 refits, checking actuals against each nominal-95% band:

```
mean-CI band covers 36.4% of future actuals
prediction interval covers 95.0%   ← correct by construction
```

A "95%" CI band that misses two-thirds of reality. With a flat mean instead of a trend, it's worse: the ratio is exactly `√(n+1) ≈ 10x` at n=100, and the CI band holds **15.5%**.

**Know what your library hands you.** In statsmodels OLS both are available, and the naming is the only thing warning you:

```python
f = res.get_prediction(X_new).summary_frame(alpha=0.05)
f[["mean_ci_lower", "mean_ci_upper"]]   # CI  — the mean
f[["obs_ci_lower",  "obs_ci_upper"]]    # PI  — use this for a forecast band
```

For `ARIMA`/`SARIMAX`, `get_forecast(h).conf_int()` is already a prediction interval despite the name — it includes innovation variance and widens with horizon. Prophet's `yhat_lower`/`yhat_upper` are prediction intervals too, but `interval_width` defaults to **0.8**, not 0.95; plenty of "95% bands" in decks are actually 80%. Plain scikit-learn gives you no interval at all, which is why hand-rolled "bootstrap the predictions" bands are nearly always CIs in disguise.

One caveat even when you pick correctly: these intervals assume the model is right and treat fitted parameters as known. Real-world coverage runs below nominal, so validate empirically with rolling-origin backtesting rather than trusting the band's label.

## 10:02 - [ML & AI] Instruction Prefixes: The Embedding Model That Needs You to Say "query:"

Most modern retrieval embedding models are trained **asymmetrically**. Queries and documents pass through identical weights, but during training each side was shown with a different text prefix that tells the model which role it is playing. Omit the prefix and you still get a 768-dim vector back — just a worse one, with no error, no warning, and no way to tell from the output.

Who needs what:

| Model | Query side | Document side |
|---|---|---|
| `intfloat/e5-*`, `multilingual-e5-*` | `query: ` | `passage: ` |
| `nomic-embed-text-v1.5` | `search_query: ` | `search_document: ` |
| `BAAI/bge-*-en-v1.5` | `Represent this sentence for searching relevant passages: ` | *(none)* |
| Cohere embed v3 | `input_type="search_query"` | `input_type="search_document"` |
| Voyage | `input_type="query"` | `input_type="document"` |
| OpenAI `text-embedding-3-*`, `bge-m3`, `gte-*` | *(none)* | *(none)* |

```python
from sentence_transformers import SentenceTransformer
m = SentenceTransformer("intfloat/e5-base-v2")

docs = ["Refunds are processed within 5 business days."]
q = "how long does a refund take"

# Correct
d_vec = m.encode([f"passage: {d}" for d in docs], normalize_embeddings=True)
q_vec = m.encode([f"query: {q}"],               normalize_embeddings=True)

# Wrong — and this line will never raise
d_vec = m.encode(docs, normalize_embeddings=True)
```

Three failure modes, roughly in order of frequency:

1. **No prefix anywhere.** Retrieval "works," so nobody investigates. Degradation is worst on short keyword-style queries — i.e. most real traffic.
2. **Mismatched prefix.** Index built with `passage:`, query also sent with `passage:` (copy-paste). You are now computing document-to-document similarity with a model trained to do query-to-document, and ranking shifts toward passages that *read like* the query rather than ones that answer it.
3. **Prefix added at query time only**, retrofitted to "fix" retrieval against an index built without it. Strictly worse than either consistent choice.

Note that symmetric tasks — dedup, clustering, STS — want the **same** prefix on both sides; E5's own guidance is `query: ` for both.

Two operational details. The prefix consumes tokens from the model's limit and is included in truncation, so a 512-token E5 gives you ~508 tokens of actual document. And a mismatch is not patchable: fixing it means re-embedding the entire corpus. Assert it at write time instead.

```python
assert all(t.startswith("passage: ") for t in batch), "unprefixed doc in batch"
```
