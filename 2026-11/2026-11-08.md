## 00:03 - [Data Engineering] Role-Playing Dimensions: One `dim_date`, Five Different Meanings

A fact table often references the same dimension several times in different roles. `fct_orders` has `order_date_key`, `ship_date_key`, `delivery_date_key`, and `cancel_date_key` — four foreign keys, one physical `dim_date`. Kimball calls these **role-playing dimensions**, and handling them wrong is one of the most common reasons a semantic layer produces nonsense.

The naive fix — join `dim_date` four times in every query — breaks down fast. Column names collide (`four aliases, all with a column called "month_name"`), and BI tools that auto-generate joins can't tell which role a user meant when they drag "Month" onto a chart. Worse, some tools will silently pick the first join path.

The Kimball answer: build one physical table, then expose a **view per role** with role-prefixed column names.

```sql
-- models/marts/dim_ship_date.sql
{{ config(materialized='view') }}

select
    date_key          as ship_date_key,
    full_date         as ship_date,
    day_of_week_name  as ship_day_of_week,
    month_name        as ship_month_name,
    fiscal_quarter    as ship_fiscal_quarter,
    is_weekday        as ship_is_weekday
from {{ ref('dim_date') }}
```

In dbt, generate these with a macro instead of copy-pasting five near-identical files:

```sql
{% macro date_role_view(role) %}
    select
        date_key as {{ role }}_date_key,
        {%- for col in ['full_date','month_name','fiscal_quarter','is_weekday'] %}
        {{ col }} as {{ role }}_{{ col }}{{ "," if not loop.last }}
        {%- endfor %}
    from {{ ref('dim_date') }}
{% endmacro %}
```

Views cost nothing to store and the warehouse optimizer inlines them, so there's no performance penalty versus aliasing — but you gain unambiguous column names that survive into Looker, Power BI, and the dbt Semantic Layer.

**Two practical notes.** First, this applies beyond dates: `dim_employee` plays "salesperson" and "approver"; `dim_airport` plays "origin" and "destination". Second, keep role views thin — only the attributes that role actually needs. A `ship_date` role rarely needs holiday flags.

The rule: **one conformed dimension, many named roles.** Never two copies of the same truth.

## 05:05 - [Data Analytics] pandas `groupby.apply`: The 250x Tax and the KeyError pandas 3 Added

`groupby.apply` is the first tool most analysts reach for and almost always the wrong one. It is a Python-level loop: pandas slices each group into a real DataFrame, calls your function, then stitches the pieces back together. With 50,000 groups that is 50,000 object constructions. `agg` and `transform` dispatch to a single compiled pass instead.

Measured on 1M rows / 50k groups, pandas 3.1.1:

| Task | `apply` | vectorized | speedup |
|---|---|---|---|
| group total | 1913 ms | 25 ms (`['amount'].sum()`) | 76x |
| share of group | 6184 ms | 25 ms (`transform('sum')`) | 251x |
| two stats per group | 8676 ms | 21 ms (`agg(['sum','size'])`) | 413x |

**The shape bug matters more than the speed.** When your function returns a per-row Series, `apply` hands back a *MultiIndex* (group key, original index). Assign that to a column and you get NaNs or a reindex error. `transform` preserves the original index, so it just works:

```python
# wrong: MultiIndex, 2 levels, won't align
df["share"] = df.groupby("customer_id").apply(lambda d: d.amount / d.amount.sum())

# right: aligns to df.index, one compiled pass
df["share"] = df["amount"] / df.groupby("customer_id")["amount"].transform("sum")
```

**Two things that bite on upgrade.** pandas 3 finished the `include_groups` deprecation: the grouping column is no longer passed to your function, so `d["customer_id"].iloc[0]` inside `apply` now raises `KeyError: 'customer_id'`, and `include_groups=True` raises `ValueError: include_groups=True is no longer allowed`. Read the key from the group label instead (`for key, sub in df.groupby(...)`) or use `transform`.

Second, `apply` and `agg` sum in different orders, so results differ in the last bits — 20,608 of 50,000 group totals differed, max absolute diff `6.8e-13`. Never gate a test on `==` for float aggregates; use `np.allclose`.

**The rule:** reduce with `agg`, broadcast back with `transform`, filter with `filter`. Reach for `apply` only when a group genuinely needs row-order-dependent logic that no built-in covers — and even then, check whether a sort plus `groupby().cumsum()` gets you there.

## 10:02 - [ML & AI] NDCG@k: Your Retriever Scores a Perfect 1.00 If You Compute the Ideal From What It Returned

Recall@k tells you *whether* the right document came back. It says nothing about **where** it landed — recall@10 is identical if the answer is at rank 1 or rank 10. NDCG is the metric that cares about position, and it's the one people most often compute wrong.

**The formula.** Discounted cumulative gain divides each result's relevance by a log of its rank, then normalizes by the best achievable ordering:

```
DCG@k  = Σ(i=1..k)  rel_i / log2(i + 1)
NDCG@k = DCG@k / IDCG@k
```

**The bug.** `IDCG` must be computed from your **full judged candidate set**, not from the documents your retriever happened to return. Otherwise the denominator is capped by the numerator and a retriever that misses the best document still scores 1.00.

```python
from math import log2

def dcg(rels):
    return sum(r / log2(i + 2) for i, r in enumerate(rels))

y_true  = [3, 2, 1, 0, 0, 0]              # graded relevance, full judged set
y_score = [0.9, 0.1, 0.8, 0.7, 0.2, 0.3]  # retriever scores

order = sorted(range(6), key=lambda i: -y_score[i])
top3  = [y_true[i] for i in order[:3]]    # -> [3, 1, 0]

dcg(top3) / dcg(sorted(y_true, reverse=True)[:3])  # 0.7625  correct
dcg(top3) / dcg(sorted(top3,  reverse=True))       # 1.0000  the bug
```

Same retriever, same ranking: **0.76 or 1.00** depending on one `sorted()` argument. It fails worst exactly when your retriever is worst — retrieve only the rel-2 and rel-1 docs and miss the rel-3, and self-normalized NDCG reports 1.00 against a true 0.62.

**Two more traps.** The log discount is gentle, so NDCG forgives mid-list junk: `[3,0,2,0,1]` still scores 0.92. And gain convention isn't universal — scikit-learn's `ndcg_score` uses linear gain `rel_i`, while TREC and most IR papers use `2^rel - 1`. Our example scores 0.7625 linear, 0.8124 exponential. Never compare NDCG across tools without checking which one you're reading.

## 15:02 - [Crypto & Business] Business Idea: Retail Deduction Recovery Analytics for Mid-Size CPG Brands

**Customer:** A $10M–$75M-revenue consumer packaged goods brand selling into Walmart, Target, Kroger, Costco, or Amazon Vendor Central. Food, beverage, supplements, household. They have a controller and maybe one AR clerk — no deductions team.

**The pain:** Retailers don't pay invoices in full. They short-pay and attach a reason code: trade promotion, OTIF fine, shortage claim, price discrepancy, compliance chargeback (wrong pallet label, late ASN). For mid-size brands these deductions run **4–8% of gross shipments**, and industry audits consistently find **10–25% of the dollars are invalid** — duplicate claims, promos deducted twice, shortages where the signed BOL proves full delivery.

Worked example: $30M gross × 6% = **$1.8M deducted**. Fifteen percent invalid = **$270K recoverable**. Most of it evaporates, because disputes must be filed inside the retailer's window (often 6–12 months from deduction date) with specific proof documents, and the clerk is already underwater.

**Why it's a data problem:** The evidence is already in the brand's files — EDI 820 remittance advice, 812 credit/debit adjustments, 856 ASNs, plus PDFs of BOLs and POs. Nobody parses them. You build a pipeline that ingests 820/812 files, normalizes each retailer's reason-code vocabulary into one taxonomy, matches deductions back to invoice and shipment, flags duplicates and provably-invalid claims, and ranks disputes by dollars-per-hour-of-effort against the closing filing window.

**Revenue model:** $1,500–$3,000/month platform fee plus **20% contingency** on recovered dollars. On the example brand that's ~$54K contingency plus $24K subscription in year one. Twelve such accounts is a real business.

**Startup cost:** $8K–$15K. An EDI translator subscription, cloud storage and compute (~$200/month), entity and contracts. The expensive input is your time, not capital.

**Main risk:** Data access. Retailer portals require supplier credentials, dispute filing is semi-manual, and incumbents (iNymbus, Vividly, legacy trade-promotion suites) already serve the enterprise tier. Your wedge is the brand too small for them.

**First validation step:** Get three brands to hand over 12 months of 820/812 detail under NDA. Hand-classify it yourself. If you can't surface $50K+ of defensible invalid deductions per $30M of shipments, the thesis is dead — kill it before writing code.

## 19:02 - [PC Hardware] GPU Memory Overclocking: The Offset That Slows You Down Without Ever Crashing

Most overclocking advice says "push until it crashes, then back off." On GPU memory that rule is actively wrong, and it will leave you running slower than stock while believing you gained performance.

**Why.** GDDR6, GDDR6X and GDDR7 links on modern cards carry error detection with hardware retry. When a transfer fails CRC, the memory controller re-sends it instead of handing corrupt data to the shader cores. You get no artifacts, no black screen, no driver timeout — just retransmissions eating the bandwidth you were trying to buy. Performance rises with the offset, flattens, then falls, and the card stays perfectly stable the whole way down.

**So benchmark, don't stress-test.** Pick something bandwidth-sensitive and repeatable — 3DMark Speed Way/Port Royal graphics score, or a game's built-in benchmark at 4K — and record the score at each step rather than watching for a crash.

| Offset | Score | Read as |
|---|---|---|
| +0 | 12,400 | baseline |
| +500 | 12,610 | +1.7% |
| +1000 | 12,730 | +2.7% |
| +1250 | 12,690 | past the peak |
| +1500 | 12,340 | worse than stock |

Settle one step below the peak, not at it — the margin shrinks as the memory heats up.

**Watch memory junction temp, not edge temp.** GDDR6X commonly throttles around 105 °C junction, and a memory overclock raises it several degrees. Log it in GPU-Z or HWiNFO during a 20-minute soak; a card that peaks at 98 °C stock has very little room.

**Where the real gains are.** On current boost algorithms the power limit is usually a bigger lever than the core offset: raise it to its maximum, then add core clock. Better still, undervolt — a voltage/frequency curve offset that holds higher sustained clocks inside the same power budget typically beats a raw overclock on both performance and noise.

**Don't do this on a compute card.** Consumer GPUs expose no correctable-error counters (`nvidia-smi -q -d ECC` returns nothing useful without real ECC), so a marginal memory clock during training or inference is undetectable. Use `memtest_vulkan` or OCCT's VRAM test to confirm zero errors, and leave memory at stock for anything whose numerical output you care about.
