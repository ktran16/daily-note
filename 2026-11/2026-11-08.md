## 00:03 - [Data Engineering] Role-Playing Dimensions: One `dim_date`, Five Different Meanings

A fact table often references the same dimension several times in different roles. `fct_orders` has `order_date_key`, `ship_date_key`, `delivery_date_key`, and `cancel_date_key` — four foreign keys, one physical `dim_date`. Kimball calls these **role-playing dimensions**, and handling them wrong is one of the most common reasons a semantic layer produces nonsense.

The naive fix — join `dim_date` four times in every query — breaks down fast. Column names collide (`four aliases, all with a column called "month_name"`), and BI tools that auto-generate joins can't tell which role a user meant when they drag "Month" onto a chart. Worse, some tools will silently pick the first join path.

The Kimball answer: build one physical table, then expose a **view per role** with role-prefixed column names.

```sql
-- models/marts/dim_ship_date.sql
{{ config(materialized='view') }}

select
    date_key          as ship_date_key,
    full_date         as ship_date,
    day_of_week_name  as ship_day_of_week,
    month_name        as ship_month_name,
    fiscal_quarter    as ship_fiscal_quarter,
    is_weekday        as ship_is_weekday
from {{ ref('dim_date') }}
```

In dbt, generate these with a macro instead of copy-pasting five near-identical files:

```sql
{% macro date_role_view(role) %}
    select
        date_key as {{ role }}_date_key,
        {%- for col in ['full_date','month_name','fiscal_quarter','is_weekday'] %}
        {{ col }} as {{ role }}_{{ col }}{{ "," if not loop.last }}
        {%- endfor %}
    from {{ ref('dim_date') }}
{% endmacro %}
```

Views cost nothing to store and the warehouse optimizer inlines them, so there's no performance penalty versus aliasing — but you gain unambiguous column names that survive into Looker, Power BI, and the dbt Semantic Layer.

**Two practical notes.** First, this applies beyond dates: `dim_employee` plays "salesperson" and "approver"; `dim_airport` plays "origin" and "destination". Second, keep role views thin — only the attributes that role actually needs. A `ship_date` role rarely needs holiday flags.

The rule: **one conformed dimension, many named roles.** Never two copies of the same truth.

## 05:05 - [Data Analytics] pandas `groupby.apply`: The 250x Tax and the KeyError pandas 3 Added

`groupby.apply` is the first tool most analysts reach for and almost always the wrong one. It is a Python-level loop: pandas slices each group into a real DataFrame, calls your function, then stitches the pieces back together. With 50,000 groups that is 50,000 object constructions. `agg` and `transform` dispatch to a single compiled pass instead.

Measured on 1M rows / 50k groups, pandas 3.1.1:

| Task | `apply` | vectorized | speedup |
|---|---|---|---|
| group total | 1913 ms | 25 ms (`['amount'].sum()`) | 76x |
| share of group | 6184 ms | 25 ms (`transform('sum')`) | 251x |
| two stats per group | 8676 ms | 21 ms (`agg(['sum','size'])`) | 413x |

**The shape bug matters more than the speed.** When your function returns a per-row Series, `apply` hands back a *MultiIndex* (group key, original index). Assign that to a column and you get NaNs or a reindex error. `transform` preserves the original index, so it just works:

```python
# wrong: MultiIndex, 2 levels, won't align
df["share"] = df.groupby("customer_id").apply(lambda d: d.amount / d.amount.sum())

# right: aligns to df.index, one compiled pass
df["share"] = df["amount"] / df.groupby("customer_id")["amount"].transform("sum")
```

**Two things that bite on upgrade.** pandas 3 finished the `include_groups` deprecation: the grouping column is no longer passed to your function, so `d["customer_id"].iloc[0]` inside `apply` now raises `KeyError: 'customer_id'`, and `include_groups=True` raises `ValueError: include_groups=True is no longer allowed`. Read the key from the group label instead (`for key, sub in df.groupby(...)`) or use `transform`.

Second, `apply` and `agg` sum in different orders, so results differ in the last bits — 20,608 of 50,000 group totals differed, max absolute diff `6.8e-13`. Never gate a test on `==` for float aggregates; use `np.allclose`.

**The rule:** reduce with `agg`, broadcast back with `transform`, filter with `filter`. Reach for `apply` only when a group genuinely needs row-order-dependent logic that no built-in covers — and even then, check whether a sort plus `groupby().cumsum()` gets you there.
