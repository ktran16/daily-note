## 00:02 - [Data Engineering] BigQuery Logical vs Physical Storage Billing: The One-Line Dataset Change That Halves Your Storage Bill

Every BigQuery dataset bills storage one of two ways, and the default is usually the wrong one.

**Logical** (the default) charges for *uncompressed* bytes — the size your data would be if BigQuery stored it naively. **Physical** charges for the compressed bytes actually on disk, but at double the rate, and it also bills your time travel and fail-safe bytes, which logical billing gives you free.

In the `us` multi-region:

| | Active (<90d) | Long-term (≥90d untouched) |
|---|---|---|
| Logical | $0.02 /GiB-mo | $0.01 /GiB-mo |
| Physical | $0.04 /GiB-mo | $0.02 /GiB-mo |

Physical is exactly 2× in both tiers, so the decision rule is simple: **switch to physical when your compression ratio exceeds 2×.** Columnar data with low-cardinality strings, repeated JSON, or wide sparse tables routinely compresses 4–8×. That is a 50–75% storage cut for one DDL statement.

Measure it per dataset before changing anything:

```sql
SELECT
  table_schema,
  SUM(total_logical_bytes)  / POW(1024,4) AS logical_tib,
  SUM(total_physical_bytes) / POW(1024,4) AS physical_tib,
  SUM(time_travel_physical_bytes + fail_safe_physical_bytes)
    / POW(1024,4)                         AS recovery_tib,
  SAFE_DIVIDE(SUM(total_logical_bytes),
              SUM(total_physical_bytes))  AS compression_ratio
FROM `region-us`.INFORMATION_SCHEMA.TABLE_STORAGE
WHERE project_id = 'my-project'
GROUP BY table_schema
ORDER BY physical_tib DESC;
```

`total_physical_bytes` already includes time travel and fail-safe, so that ratio is the honest comparison — no extra adjustment needed.

Then flip the dataset:

```sql
ALTER SCHEMA `my-project.analytics`
SET OPTIONS (storage_billing_model = 'PHYSICAL');
```

**The trap is churn.** A table rewritten nightly by a `MERGE` or a dbt `insert_overwrite` accumulates a full copy per day in time travel. A 1 TiB table rebuilt daily with 7-day travel can carry several TiB of recovery bytes, dragging the effective ratio below 2× even though the live data compresses 5×. Check `recovery_tib` against `physical_tib`; if recovery dominates, trim travel first:

```sql
ALTER SCHEMA `my-project.analytics`
SET OPTIONS (max_time_travel_hours = 48);  -- 48–168, default 168
```

Fail-safe is a fixed extra 7 days and cannot be reduced or disabled.

Two operational notes: the change takes up to 24 hours to take effect, and once changed you must wait **14 days** before switching back — so measure first rather than toggling to see what happens. Prices vary by region; verify against the current BigQuery pricing page.

## 05:02 - [Data Analytics] Partition Pruning: The Function Around Your Date Column That Scans All 4 TB

Partitioned tables only save money when the engine can decide *before* reading which partitions it needs. That decision happens during planning, from the literal text of your predicate. Wrap the partition column in anything and planning gives up, the scan goes full-table, and the query still returns the right answer — just at 500x the cost.

A BigQuery table partitioned on `event_date DATE`, 4 TB total, ~11 GB/day:

```sql
-- No pruning: the partition column is inside a function.
-- 4 TB scanned ≈ $25 at $6.25/TiB on-demand.
SELECT user_id, SUM(revenue)
FROM events
WHERE FORMAT_DATE('%Y-%m', event_date) = '2026-11'
GROUP BY user_id;

-- Prunes: the predicate compares the bare column to literals.
-- ~330 GB scanned ≈ $2.
WHERE event_date >= '2026-11-01' AND event_date < '2026-12-01'
```

`CAST(event_date AS STRING) LIKE '2026-11%'` fails the same way. So does the pattern everyone writes for "latest day":

```sql
WHERE event_date = (SELECT MAX(event_date) FROM events)  -- full scan
```

BigQuery cannot prune on a subquery result — the value doesn't exist at planning time. Run that `MAX` as its own cheap query (it reads one column) and pass the result as a query parameter or literal; parameters *do* prune.

Snowflake's micro-partition pruning behaves the same way for expressions it can't fold to constants, and clustering keys buried in functions stop helping.

**Verify, don't assume.** This is one of the few tuning questions with a free, exact answer:

```bash
bq query --dry_run --use_legacy_sql=false 'SELECT ...'
# "Query successfully validated. ... will process 4123456789012 bytes"
```

In Snowflake, compare `partitions_scanned` to `partitions_total` in the query profile or `QUERY_HISTORY`. If the ratio is ~1.0, you aren't pruning.

Then make it structural. `ALTER TABLE events SET OPTIONS (require_partition_filter = TRUE)` rejects any query without a partition predicate — a loud error beats a silent $25 dashboard refresh running hourly. Pair it with a BI tool's date filter mapped to the real partition column, not to a derived timestamp in a view, since a view that computes `DATE(event_ts)` on top of a `TIMESTAMP` partition column can hide pruning from every consumer downstream.

Pricing and pruning rules vary by engine and region; confirm against current docs.

## 10:04 - [ML & AI] Learning Curves: Price the Next 40,000 Labels Before You Buy Them

Your model sits at 0.82 validation AUC. Someone asks: label 40K more rows, or try a bigger model? Most teams guess. A learning curve answers it in one training sweep.

Train the *same* model at increasing subset sizes and record validation error at each. Two shapes, two different bills:

- **Train and validation errors close together, both high, both flat.** Underfitting. The model has already extracted everything it can from this feature set. More rows change nothing — spend on features or capacity.
- **Wide train/validation gap, and the validation curve still descending at your current n.** Overfitting that data buys down. Keep labeling.

The gap alone is not the signal. **The slope of the validation curve at your largest size is.**

### Reading the slope as money

Validation error at doubling sizes:

| n | 5K | 10K | 20K | 40K |
|---|---|---|---|---|
| err | .260 | .220 | .195 | .180 |
| Δ | — | .040 | .025 | .015 |

Each doubling buys ~0.6× what the last one did. Reducible error decays geometrically, so the *entire remaining budget* — all the data you could ever collect — is the sum of that series:

```
0.015 × 0.6 / (1 − 0.6) = 0.0225
```

2.2 points. Not from the next 40K rows: from infinite rows. The next doubling alone buys 0.9 points. If 0.9pp doesn't pay for 40K labels, stop labeling and go change the model.

```python
from sklearn.model_selection import learning_curve, StratifiedKFold
import numpy as np

sizes, tr, va = learning_curve(
    model, X, y,
    train_sizes=[0.125, 0.25, 0.5, 1.0],      # must double
    cv=StratifiedKFold(5, shuffle=True, random_state=0),
    scoring="neg_log_loss", n_jobs=-1,
)
err = -va.mean(axis=1)
d = -np.diff(err)
r = d[-1] / d[-2]
print(f"next doubling: {d[-1]*r:.4f} | all remaining data: {d[-1]*r/(1-r):.4f}")
```

### Three ways to fake a ceiling

- **Hyperparameters tuned at full size.** Regularization sized for 40K rows cripples the 5K fit, flattening the curve into a false bias wall. Retune per size, or at least widen the search.
- **Random subsampling of grouped or temporal data.** Slicing a time series at random leaks future into past — every point reads too optimistic, and the slope is meaningless.
- **A validation fold that shrinks with the training set.** Hold the evaluation set fixed. Otherwise the noise floor rises exactly where you need precision.

And check `r < 1`. If the last two improvements grow instead of shrink, you have noise, not a curve — add seeds and re-fit before extrapolating.
