# Daily Notes - 2026-11-19

## 00:03 - [Data Engineering] Orchestrating dbt: One Task Per Model vs a Single `dbt build`

Every team running dbt under Airflow hits this fork, usually after a 200-model project fails on model 180 and the retry re-runs all 180.

**The monolith.** One operator, one command:

```python
BashOperator(task_id="dbt_build", bash_command="dbt build --target prod")
```

Cheap, one warehouse connection, and dbt's own `--threads` handles intra-DAG parallelism better than Airflow can — it knows the lineage and doesn't pay process startup per node. The cost is granularity: Airflow sees one green or red box. `dbt retry` softens this by reading `target/run_results.json` and resuming at the failed node, but only if that directory survived the task — on ephemeral Kubernetes pods it didn't.

**Task per model.** Parse `manifest.json`, emit one Airflow task per node. Per-model retries, timing, and alerting; failures isolate to the subtree that actually broke. `astronomer-cosmos` is the standard implementation:

```python
from cosmos import DbtTaskGroup, ProjectConfig, RenderConfig, LoadMode

DbtTaskGroup(
    project_config=ProjectConfig(
        "/opt/dbt/jaffle",
        manifest_path="/opt/dbt/jaffle/target/manifest.json",
    ),
    render_config=RenderConfig(load_method=LoadMode.DBT_MANIFEST),
)
```

That `load_method` is the line that matters. The default `AUTOMATIC` will shell out to `dbt ls` at **DAG-parse** time — which the scheduler repeats every `min_file_process_interval` (30s default), per DAG file. You get warehouse credentials required in the scheduler, parse timeouts, and a scheduler that spends its budget running dbt. Build the manifest in CI, ship it with the image, and point at it.

The second cost is real but quieter: each task is a separate `dbt run --select one_model` — a fresh Python process and warehouse session, roughly 5–15s of overhead. Across 300 two-second models, orchestration costs more than the SQL.

**Where to land.** Group by domain, not by node:

```bash
dbt build --select tag:finance
```

One task per mart or tag gives you useful retry boundaries and alert routing while keeping dbt's threading inside each group. Go full task-per-model when per-model SLAs, asset-level lineage in the Airflow UI, or fan-out to downstream non-dbt tasks justify the overhead — not by default.
