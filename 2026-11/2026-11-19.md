## 00:03 - [Data Engineering] Orchestrating dbt: One Task Per Model vs a Single `dbt build`

Every team running dbt under Airflow hits this fork, usually after a 200-model project fails on model 180 and the retry re-runs all 180.

**The monolith.** One operator, one command:

```python
BashOperator(task_id="dbt_build", bash_command="dbt build --target prod")
```

Cheap, one warehouse connection, and dbt's own `--threads` handles intra-DAG parallelism better than Airflow can — it knows the lineage and doesn't pay process startup per node. The cost is granularity: Airflow sees one green or red box. `dbt retry` softens this by reading `target/run_results.json` and resuming at the failed node, but only if that directory survived the task — on ephemeral Kubernetes pods it didn't.

**Task per model.** Parse `manifest.json`, emit one Airflow task per node. Per-model retries, timing, and alerting; failures isolate to the subtree that actually broke. `astronomer-cosmos` is the standard implementation:

```python
from cosmos import DbtTaskGroup, ProjectConfig, RenderConfig, LoadMode

DbtTaskGroup(
    project_config=ProjectConfig(
        "/opt/dbt/jaffle",
        manifest_path="/opt/dbt/jaffle/target/manifest.json",
    ),
    render_config=RenderConfig(load_method=LoadMode.DBT_MANIFEST),
)
```

That `load_method` is the line that matters. The default `AUTOMATIC` will shell out to `dbt ls` at **DAG-parse** time — which the scheduler repeats every `min_file_process_interval` (30s default), per DAG file. You get warehouse credentials required in the scheduler, parse timeouts, and a scheduler that spends its budget running dbt. Build the manifest in CI, ship it with the image, and point at it.

The second cost is real but quieter: each task is a separate `dbt run --select one_model` — a fresh Python process and warehouse session, roughly 5–15s of overhead. Across 300 two-second models, orchestration costs more than the SQL.

**Where to land.** Group by domain, not by node:

```bash
dbt build --select tag:finance
```

One task per mart or tag gives you useful retry boundaries and alert routing while keeping dbt's threading inside each group. Go full task-per-model when per-model SLAs, asset-level lineage in the Airflow UI, or fan-out to downstream non-dbt tasks justify the overhead — not by default.

## 05:03 - [Data Analytics] Association Rules: The 70%-Confidence Rule That Means Customers Buy *Less*

"Customers who bought X also bought Y" is usually built on **confidence**, and confidence alone just rediscovers your bestsellers.

Three numbers, over `N` baskets:

- **support(A→B)** = baskets with both ÷ N — how often the rule even applies
- **confidence(A→B)** = baskets with both ÷ baskets with A — P(B | A)
- **lift(A→B)** = confidence ÷ support(B) — how much A *changes* P(B)

Lift is the one that carries information. Confidence near 1.0 on a ubiquitous B means nothing.

```sql
WITH baskets AS (                      -- DISTINCT first: 2 milks in one order is still one basket
  SELECT DISTINCT order_id, item FROM order_items
),
n AS (SELECT COUNT(DISTINCT order_id) AS total FROM baskets),
item_support AS (
  SELECT item, COUNT(*) * 1.0 / (SELECT total FROM n) AS sup
  FROM baskets GROUP BY item
),
pairs AS (
  SELECT a.item AS ant, b.item AS con, COUNT(*) AS both
  FROM baskets a
  JOIN baskets b ON a.order_id = b.order_id AND a.item <> b.item
  GROUP BY 1, 2
)
SELECT p.ant, p.con,
       p.both * 1.0 / (SELECT total FROM n)        AS support,
       p.both / (sa.sup * (SELECT total FROM n))   AS confidence,
       (p.both / (sa.sup * (SELECT total FROM n))) / sc.sup AS lift
FROM pairs p
JOIN item_support sa ON sa.item = p.ant
JOIN item_support sc ON sc.item = p.con
WHERE p.both >= 30                     -- min-support guard; see below
ORDER BY lift DESC;
```

Run on 1,000 baskets where milk appears in 750:

| rule | both | support | confidence | lift |
|---|---|---|---|---|
| bread → milk | 210 | 0.21 | **0.70** | **0.93** |
| beer → milk | 200 | 0.20 | **1.00** | 1.33 |
| diapers → beer | 60 | 0.06 | 0.60 | **3.00** |
| caviar → truffle | 3 | 0.003 | 1.00 | **250** |

`bread → milk` looks like the strongest rule on the board at 70% confidence — but milk is in 75% of all baskets, so bread buyers are *slightly less* likely to take milk. Lift 0.93. Recommending milk there is worse than recommending nothing. `diapers → beer` fires on only 6% of baskets and is the only rule with real signal.

Two guards:

1. **Low support makes lift explode.** `caviar → truffle` has lift 250 off three baskets. One more basket moves it by a third. Filter on absolute co-occurrence count (`both >= 30`), not on lift.
2. **Confidence is directional, lift is not.** `bread → milk` is 0.70 but `milk → bread` is 0.28 — same lift, 0.93. If your recommender ranks by confidence, it will always point toward the popular item.
