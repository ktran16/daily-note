## 05:02 - [Data Analytics] Log-Scale Axes: Right for Growth, Wrong for Bars

On a linear axis a series going 10 → 100 → 1,000 → 10,000 looks like nothing happened for three periods and then exploded. All four steps are the same event: 10x growth. A log y-axis makes equal *ratios* equal *distances*, so constant growth is a straight line and the slope *is* the growth rate.

Two products, 36 weeks — a small fast grower and a large slow one:

```python
import numpy as np, matplotlib.pyplot as plt

w = np.arange(36)
a = 1_000   * 1.25**w   # 25%/wk, starts at 1k
b = 400_000 * 1.03**w   #  3%/wk, starts at 400k

fig, ax = plt.subplots(1, 2, figsize=(11, 4))
for p in ax:
    p.plot(w, a, label="Product A"); p.plot(w, b, label="Product B")
    p.set_xlabel("week")
ax[0].set_title("linear")
ax[1].set_yscale("log"); ax[1].set_title("log")
ax[1].set_ylabel("users (log scale)"); ax[1].legend()
```

Linear panel: at week 18 A is at 55,511 against B's 680,973 — 2.25% of the axis height, a line pinned to the floor. The crossover at week 31 (1.01M vs 1.00M) is invisible until it happens.

Log panel: both are straight lines from week 0, A's visibly steeper. You can lay a ruler on them and read the crossover **before** you reach it. That extrapolation is the real payoff — and it only works because exponential growth is linear in log space.

**Four rules.**

1. **Never log a bar or area chart.** Bars encode value as length from zero; log breaks that, so a bar twice as long is not twice the value. Log belongs to position encodings only — lines and points.
2. **Label ticks in data units**: `1k, 10k, 100k, 1M`, not `3, 4, 5, 6`. Use `ax.yaxis.set_major_formatter(mpl.ticker.EngFormatter())`.
3. **Zeros and negatives vanish silently.** `log(0)` is undefined and matplotlib just drops those points — no warning, no gap you'd notice. Check `(s <= 0).sum()` first; for data that genuinely crosses zero use `symlog` and say so.
4. **Write "log scale" on the axis.** Readers default to linear, and a 2x jump that renders as a small bump is a real misread, not a subtle one.

The test: if your takeaway sentence says "**%**" or "**times**", log is probably right. If it says "**how much more**", stay linear.

## 10:03 - [ML & AI] Gradient Checkpointing: Trading 33% Compute for 10x Activation Memory

When people OOM fine-tuning an 8B model, it's usually not the weights. It's the *activations* — every intermediate tensor the forward pass saves so backward can compute gradients. Weights are fixed; activations scale with `layers × batch × seq_len × hidden`.

Rough bf16 arithmetic for a 32-layer, d=4096 model at batch 1, seq 4096. One `b×s×d` tensor is 4096 × 4096 × 2 bytes ≈ 34 MB. A transformer block saves roughly 10 such tensors (attention projections, the 4x MLP intermediate, norms, residuals), so ~340 MB per layer:

```
no checkpointing:  32 layers × ~340 MB  ≈ 10.9 GB
checkpointing:     32 boundaries × 34 MB ≈  1.1 GB   (+ one block's worth to recompute)
```

That ~10x is the difference between OOM and fitting on a 24 GB card. (Exact bytes depend on the kernel — FlashAttention already avoids storing the `s²` attention matrix.)

The trick: **don't save, recompute.** Store only each block's input, then during backward re-run that block's forward to regenerate what you discarded.

The cost is one extra forward pass. Backward costs ~2x forward, so a normal step is ~3F; checkpointing every block makes it ~4F — **+33% theoretical, 20–30% in practice.**

```python
model.gradient_checkpointing_enable(
    gradient_checkpointing_kwargs={"use_reentrant": False}
)
model.config.use_cache = False   # KV cache conflicts; HF warns and disables it anyway
```

**Two traps.**

*LoRA + checkpointing crashes.* With a frozen base model, the input to each checkpointed block has `requires_grad=False`, so autograd prunes the recomputed segment and you get `element 0 of tensors does not require grad`. Fix with `use_reentrant=False` (above), or `model.enable_input_require_grads()`.

*Dropout must replay identically.* If the recomputed forward draws different dropout masks than the original, your gradients are wrong — silently, no error. PyTorch's checkpoint stashes and restores RNG state by default (`preserve_rng_state=True`); don't turn it off.

**Reach for it in this order:** batch size 1 + gradient accumulation first (free), then checkpointing (+30% time), then quantized base weights. Checkpointing buys memory with time — the one resource you can usually spare.
