## 00:04 - [Data Engineering] Rerunning Only What Broke: `dbt retry` vs the `result:` Selectors

A 400-model build dies 90% of the way through on one broken model. Rerunning the whole thing wastes 40 minutes of warehouse credits to rebuild 360 tables that were already fine. dbt gives you two ways out, and they are not interchangeable.

**`dbt retry` (1.6+)** reads `target/run_results.json` from the *immediately previous* invocation, then replays that same command — same subcommand, same selection flags — restricted to nodes that errored or were skipped because of an upstream error:

```bash
dbt build --select tag:nightly   # fails at model 361
dbt retry                        # rebuilds the failure + its skipped downstream only
```

It takes no selection arguments; the selection is inherited. If `run_results.json` is missing, or the project has been re-parsed into a different shape, retry refuses rather than guessing.

**`result:` selectors** are the composable version. They read a state directory and let you write a *new* command around the previous outcome:

```bash
cp -r target/ prev/
dbt build --select "result:error+" --state prev/
```

The statuses are distinct, which matters: models produce `result:error` or `result:success`; tests produce `result:fail`, `result:warn`, or `result:pass`. So `result:error+` will not pick up a model whose *test* failed — that is `result:fail`. Union them when you mean both:

```bash
dbt build --select "result:error+" "result:fail+" --state prev/
```

Two traps. First, copy the artifacts to a separate directory before rerunning; pointing `--state target/` at the directory dbt is about to overwrite works by accident (state is read at parse time) and breaks the moment anything writes early. Second, in CI the previous `run_results.json` lives on a different runner — cache or upload it as a build artifact, or retry has nothing to read.

Related: `dbt source freshness` writes `sources.json`, which unlocks `--select "source_status:fresher+"` — build only what sits downstream of data that actually landed.

## 05:02 - [Data Analytics] HLL Sketches: The Mergeable Distinct Count, and the Intersection That Returns Noise

Exact `COUNT(DISTINCT user_id)` cannot be rolled up — 30 daily DAU numbers will never sum to MAU. HyperLogLog sketches can: store one per day, union them later.

```sql
-- BigQuery: one sketch per day, built incrementally
CREATE OR REPLACE TABLE daily_sketch AS
SELECT
  event_date,
  HLL_COUNT.INIT(user_id, 15) AS users_sketch   -- precision 10-24, default 15
FROM events
GROUP BY event_date;

-- 30-day MAU from 30 small rows; no rescan of events
SELECT HLL_COUNT.MERGE(users_sketch) AS mau
FROM daily_sketch
WHERE event_date BETWEEN '2026-10-15' AND '2026-11-13';
```

Snowflake uses `HLL_ACCUMULATE` / `HLL_COMBINE` / `HLL_ESTIMATE`; DuckDB and Postgres (`postgresql-hll`) have equivalents. Reading 30 sketch rows instead of a month of raw events routinely turns a multi-minute MAU query into a sub-second one, and it makes any date range composable.

**Know your error bar.** HLL's relative standard error is about 1.04/√m, where m = 2^precision:

- precision 12 (Snowflake's fixed default): ~1.6%
- precision 15 (BigQuery default): ~0.57%
- precision 18: ~0.2%, but the sketch grows to ~200 KB per row

That is a *standard* error, not a bound — roughly 1 estimate in 20 falls outside 2σ. At precision 12, a reported MAU of 1,000,000 carries about ±16,000 at 1σ. Fine for a trend line. Not fine for per-user billing, SLA reporting, or a leaderboard where #3 and #4 sit 1% apart.

**The real trap is intersections.** There is no HLL intersect, so people reach for inclusion–exclusion:

`|A ∩ B| = |A| + |B| − |A ∪ B|`

Absolute errors add while the answer shrinks. With |A| = |B| = 1M at ±16k each, a true overlap of 900k comes back within a percent or two. A true overlap of 10,000 is pure noise — three terms each carrying ~16k of error, and the subtraction can return a negative count. Feature co-usage, cross-sell overlap, and A/B exposure dedupe need exact IDs, or a bitmap store (ClickHouse `groupBitmap`, Druid, roaring bitmaps) where union *and* intersection are exact.

Rule of thumb: sketches for monotone rollups you read as trends; exact IDs when the number is money, a key, or a small difference.

## 10:03 - [ML & AI] Beam Search and the Length Penalty: Why Width 5 Gives You "No."

Beam search picks the sequence maximizing total log-probability. Log-probs are negative and they *sum*, so every extra token makes a candidate score worse. Left alone, beam search has a structural bias toward short outputs.

Two candidates from a support model:

| Candidate | Tokens | log P (sum) |
|---|---|---|
| A: `No.` | 2 | −0.40 |
| B: `No, orders can't be refunded after 30 days.` | 12 | −2.00 |

Raw score: A wins by a mile (−0.40 > −2.00). The model doesn't prefer A — it just has fewer chances to lose points.

The fix is to normalize. HuggingFace divides by length raised to a power:

```
score = log P / (len ** length_penalty)
```

- `length_penalty=0.0` → raw sum. A wins (−0.40).
- `length_penalty=1.0` → mean per token. A = −0.40/2 = **−0.200**, B = −2.00/12 = **−0.167**. B wins.
- `length_penalty > 1.0` → actively rewards length. Use when your model truncates.

Note the direction, because it trips people constantly: **higher `length_penalty` favors longer output.** The GNMT paper's `((5+|Y|)/6)^α` form does the same thing with a softer curve for short sequences.

```python
out = model.generate(
    **inputs,
    num_beams=4,
    length_penalty=1.0,      # >1 longer, <1 shorter
    no_repeat_ngram_size=3,
    early_stopping=True,
)
```

Two things that follow:

**Beam search is for closed-ended tasks.** Translation, summarization, schema-constrained extraction — anywhere one right answer exists and you want the mode. For open-ended generation it degenerates into bland, repetitive text, because human writing is *not* the highest-probability continuation. High-likelihood text is boring text. Use sampling (`do_sample=True`, top-p) there.

**It costs width.** `num_beams=4` means 4× the decode FLOPs and 4× the KV cache, for latency you pay on every request. Width 4–5 captures nearly all the quality; width 20 mostly buys shorter, worse answers unless you raise the penalty with it.

Tune `length_penalty` on a validation set and look at output *length distribution*, not just BLEU/ROUGE — the symptom shows up there first.

## 16:03 - [Crypto & Business] Business Idea: Fleet Yield Analytics for Independent Equipment Rental Yards

**Customer:** independently owned construction equipment rental companies — one to four yards, $8M–$25M revenue, fleet original equipment cost (OEC) of $12M–$40M, renting excavators, skid steers, boom lifts and compaction to local contractors.

**Problem:** they manage on *time* utilization ("out 64% of days") and ignore *dollar* utilization — trailing-12-month rental revenue ÷ OEC. The company-level number looks fine, so a loss-making tail hides inside it. Worse, when a class runs hot they buy more iron, because the idle units never show up on a company P&L.

**Worked example.** $18M OEC, $5.2M rental revenue = 28.9% dollar utilization. Split by unit:

| Fleet slice | OEC | Revenue | Dollar util |
|---|---|---|---|
| Top 40% of OEC | $7.2M | $3.0M | 42% |
| Middle 35% | $6.3M | $1.7M | 27% |
| Bottom 25% | $4.5M | $0.5M | 11% |

Ownership cost — depreciation, interest, insurance, yard and PM labor — runs roughly 18–22% of OEC per year. At 20%, half of that bottom slice ($2.25M OEC) earns $247K and costs $450K to own: a **$203K annual loss**. Sell it at ~55% of OEC for $1.2M cash, redeploy $600K into the 42% classes, and that $600K earns ~$252K against $120K of ownership cost. Net swing ≈ **$335K/year**, with no rate increase.

**Revenue model:** $9K setup to wire up their rental system (Point of Rental, Wynne RentalMan, Texada), then $1,800/month per yard for the dashboard plus a quarterly buy/sell/transfer recommendation. 15 single-yard clients ≈ $324K ARR.

**Startup cost:** $6K–$10K — DuckDB/Postgres on a small VM, dbt for the models, $2K for entity setup and a contract template, the rest on travel to one ARA Show.

**Main risk:** data access. Hosted rental systems often gate ODBC or API access behind a vendor request the owner must file, and a hand-pulled CSV every month destroys the margin.

**First validation step:** ask five owners for one CSV — unit number, class, OEC, acquisition date, LTM revenue, days on rent — and return a free fleet-tail report. That tests demand *and* the data-access risk at once. If three of five produce the file within a week and two book a paid engagement, build it.

## 19:02 - [PC Hardware] Workstation RAM: RDIMM vs UDIMM, and the Channel Count That Actually Feeds Your Model

The memory in a Threadripper or Xeon W workstation is not the same part as the memory in a gaming PC, and the platforms will not accept each other's modules. This trips up most first-time workstation builders.

**What the register does.** A UDIMM (unbuffered) wires command/address/clock lines straight from the memory controller to the DRAM chips. An RDIMM puts a Register Clock Driver in between, buffering those lines so the controller drives one load per DIMM instead of dozens. That allows more ranks and higher capacity per channel, at the cost of roughly one clock cycle of added command latency — irrelevant for throughput work. LRDIMMs go further and buffer the data lines too, reaching 128–256 GB per module.

| Type | Platforms | Typical max/DIMM |
|---|---|---|
| UDIMM | AM5, LGA1700/1851 desktop | 32–64 GB |
| CUDIMM | Core Ultra 200S (adds a clock driver for 6400+) | 32–64 GB |
| RDIMM | Threadripper 7000/9000, Xeon W-2400/3400, EPYC | 64–128 GB |
| LRDIMM | Server EPYC/Xeon SP | 128–256 GB |

These are not fallback-compatible. A Threadripper board with UDIMMs installed will not POST — no beep, no code, just a memory debug LED.

**Channels beat MT/s.** DDR5 moves 8 bytes per transfer, so per-channel bandwidth is `MT/s × 8` in MB/s:

- Dual-channel DDR5-6000 (desktop): ~96 GB/s
- Quad-channel DDR5-5200 (TR non-PRO): ~166 GB/s
- Eight-channel DDR5-5200 (TR PRO / Xeon W-3400): ~333 GB/s

For CPU-side work that is bandwidth-bound — large joins, pandas/Polars on wide frames, CPU inference of a quantized LLM — that 3.5x gap matters far more than a 10% clock bump. Populate **every** channel, one DIMM per channel. Two DIMMs per channel (2DPC) forces the controller to derate, commonly 5600 → 4400 MT/s, so 8×64 GB beats 16×32 GB for the same 512 GB.

Buy one matched kit off the board's QVL. Mixing RDIMM part numbers across channels is the most common cause of a workstation that trains fine for an hour and then throws a machine check.
