## 00:02 - [Data Engineering] `--warn-error-options`: The Green CI Run That Built Nothing

dbt exits `0` on warnings. That is fine for cosmetic noise and dangerous for one warning in particular: `NoNodesForSelectionCriteria`.

Mistype a selector in CI — a renamed model, a stale tag, a `state:modified` comparison against the wrong manifest — and dbt matches zero nodes, prints a warning, and exits successfully. The pipeline goes green having built and tested nothing. This is the single most common way a Slim CI job stops protecting a repo without anyone noticing.

`--warn-error` fixes it by promoting *every* warning to an error, which is too blunt: one new upstream deprecation and every PR fails. `--warn-error-options` lets you pick.

```bash
# fail only on the warnings that mean "your run was a no-op"
dbt build --select state:modified+ --defer --state ./prod-artifacts \
  --warn-error-options '{"error": ["NoNodesForSelectionCriteria", "UnversionedBreakingChange"]}'
```

Better: put it in `dbt_project.yml` so local runs and CI behave identically.

```yaml
flags:
  warn_error_options:
    error: all                        # strict by default
    warn:                             # ...except these, which stay warnings
      - TestsConfigDeprecation
    silence:                          # ...and these, which we never want to see
      - MissingPlusPrefix
```

Three things worth knowing:

- **The keys were renamed.** dbt 1.10+ uses `error` / `warn` / `silence`. Older projects use `include` / `exclude`, which still work but are deprecated. `silence` is the only way to suppress a warning you have consciously accepted — `warn` still prints it.
- **`error: all` with a `warn` list is the maintainable shape.** An allowlist (`error: [...]`) means every new warning dbt adds arrives silently. A denylist means new warnings break the build loudly, and you triage them deliberately.
- **Find the names from the logs, not from guessing.** Warning identifiers are dbt event names, not message text:

```bash
dbt build --log-format json | jq -r 'select(.info.level=="warn") | .info.name' | sort -u
```

A no-op selector should be a build failure, not a clean run. Promote that one warning today, even if you adopt nothing else here.

## 05:04 - [Data Analytics] Cumulative Charts: The 66% Decline That Fits a Straight Line at R² = 0.97

A running total is monotone non-decreasing. It **cannot** go down. The worst a cumulative chart can do is flatten — so every one of them, on every metric, in every state of the business, looks like progress. That is not a presentation quirk; it is the reason cumulative charts are the house style of vanity metrics.

Twelve weeks of signups, falling hard:

| wk | new | total | total growth | new change |
|---|---|---|---|---|
| 1 | 700 | 700 | — | — |
| 4 | 560 | 2,530 | +28.4% | −8.2% |
| 8 | 360 | 4,240 | +9.3% | −10.0% |
| 12 | 240 | 5,350 | +4.7% | −7.7% |

New signups fell **−65.7%** (700 → 240). Fit a straight line to the *cumulative* series and you get **R² = 0.9747**, slope ~417/wk: it reads as clean, steady, linear growth. And a perfectly **flat** 446/week lands on the identical 5,350 endpoint — the cumulative chart cannot distinguish "flat" from "collapsed by two thirds."

Worse, the growth-rate column is arithmetic, not signal. With a *constant* 446/week, cumulative growth still decays 100% → 9.1% by week 12, because the denominator keeps growing. "Our growth is slowing" read off a cumulative line means nothing.

The rate is the derivative. If your source only stores the total, undo it:

```sql
select week,
       total_signups,
       total_signups - lag(total_signups) over (order by week) as new_signups
from weekly_totals
order by week;
```

### When cumulative is the right chart

Use it when the question is literally "how much so far, versus a target":

- **Pace to goal** — burn-up against a target-pace line; the gap between the two lines is the message.
- **Cumulative cohort LTV / retention revenue** — the *shape* (where it asymptotes) is the finding.
- **Quota or contract attainment**, where only the endpoint is contractual.

In all three, a reference line carries the information, not the curve.

**Rule:** cumulative answers *how much so far*; the rate answers *is it working*. If the y-axis says "Total … to date" and the decision on the table is about trend, you are reading the integral of the number you actually care about. Plot the rate beside it — and if someone resists, that is itself the finding.

## 10:03 - [ML & AI] Lost in the Middle: Rank 5 of 10 Is the Worst Place to Put Your Best Chunk

A model's ability to *use* a fact in its context is not uniform across positions. Plot accuracy against where the answer sits and you get a U: strong at the beginning, strong at the end, weakest in the middle.

Liu et al. (2023) measured this directly on multi-document QA. With 20 documents and one gold document, accuracy was highest when the gold doc was first or last and dropped roughly 20 points when it sat in the middle — for some models, mid-position accuracy fell *below* the closed-book baseline of giving the model no documents at all. Having the right answer in context, badly placed, was worse than not having it.

This collides head-on with how RAG is usually assembled. Retrievers return a ranked list and the default is to paste it in rank order. With `k=10`, you have just stacked your 4th–7th best chunks into the dead zone.

**Fix 1 — reorder so the edges hold the best material.**

```python
def edge_reorder(chunks):          # chunks sorted best-first
    head, tail = [], []
    for i, c in enumerate(chunks):
        (head if i % 2 == 0 else tail).append(c)
    return head + tail[::-1]       # [0,2,4,6,8, 9,7,5,3,1]
```

Rank 1 lands at the start, rank 2 at the very end, and the weakest chunks absorb the middle. Zero extra tokens, zero extra latency.

**Fix 2 — retrieve less.** Padding context with near-misses actively dilutes. Five reranked chunks usually beat twenty raw ones; a cross-encoder in front of a small `k` fixes the ordering *and* the length.

**Fix 3 — restate the question after the documents.** Instructions at the top of a 50K-token prompt are in a strong position, but the task statement adjacent to the evidence helps. Bracketing both ends is cheap.

**Fix 4 — measure it on your own data.** Synthetic needle tests ("the magic number is 42") overstate performance because the needle is lexically obvious. Use real questions against real distractors, sweep the gold chunk through every slot, and report accuracy per position:

```python
for pos in range(k):
    ctx = chunks[:pos] + [gold] + chunks[pos:]
    score[pos] = judge(ask(query, ctx), answer)
```

Newer long-context models have flattened this curve, not removed it. And note what it is *not*: this is an accuracy failure, not the KV-cache throughput problem. The tokens all fit, get billed, and get attended to — they just don't get used equally.

## 15:03 - [Crypto & Business] L2 Sequencers: What Happens to Your Money When the Operator Goes Down

Nearly every major rollup today runs a **single centralized sequencer** — one server that orders transactions and posts batches to the L1. That is not a secret flaw; it is the published design. What matters is knowing which guarantees survive when it misbehaves.

Separate three failure modes:

**1. Liveness failure (sequencer offline).** Your funds are safe — L1 holds them and the state root is already posted — but you cannot transact. Rollups mitigate this with a **forced-inclusion path**: you submit the transaction directly to an L1 contract, and after a delay window (typically on the order of 12–24 hours on the big optimistic rollups) the protocol *must* include it or the chain halts. This is the escape hatch. It costs L1 gas — expect $5–50 depending on the base fee — and it is slow, but it cannot be censored by the operator.

**2. Censorship.** Functionally identical to #1 for you specifically: same escape hatch, same delay.

**3. Withdrawal delay.** Separate clock entirely. On an optimistic rollup the fraud-proof window is **~7 days**, so a native bridge withdrawal is not spendable on L1 until it expires. ZK rollups replace this with proof verification — hours, not days. Third-party bridges let you exit in minutes by fronting you liquidity and charging for it; that swaps the rollup's security for the bridge's.

Practical checks before parking size on an L2:

- Does a forced-inclusion / self-sequencing path exist, and has anyone actually used it? Untested code is a claim, not a feature.
- Who can upgrade the bridge contract, and is there a timelock? A 0-delay admin multisig outranks every other security property — upgradeability, not sequencing, is where most L2 risk actually lives.
- Is the proof system live and permissionless, or is fraud-proving still whitelisted? L2BEAT's stage 0/1/2 framework tracks exactly this.

Treat the rollup's security as `min(proof system, upgrade control, escape hatch)` — not the marketing number. Parameters differ per chain and change with upgrades; verify current values before relying on them.

## 19:02 - [Wildcard] Path MTU Discovery: Why SSH Connects Fine, Then Freezes on `ls`

The symptom is unmistakable once you have seen it: the VPN comes up, `ping` works, SSH authenticates and gives you a prompt — then the first command that returns more than a screenful of text hangs forever. Small packets pass, large ones vanish. That is a broken MTU path, not a flaky link.

Ethernet carries a 1500-byte payload. Every tunnel steals from it: WireGuard needs 60 bytes (IPv4) or 80 (IPv6), leaving 1440/1420. PPPoE takes 8, leaving 1492. IPsec takes 50–90 depending on mode and cipher.

TCP is supposed to cope. The sender marks packets Don't Fragment; a router that cannot forward one replies with ICMP type 3 code 4, "fragmentation needed," carrying the correct MTU; the sender shrinks. That is Path MTU Discovery. It fails whenever someone blocks ICMP wholesale at a firewall — still depressingly common. The sender never hears back, retransmits the same oversized packet, and the connection black-holes. Interactive traffic is small, so the prompt works; a directory listing fills a full segment and dies.

Find the real ceiling by bisecting with DF set. The `-s` value is payload, so add 28 bytes of IP+ICMP header:

```bash
ping -M do -s 1472 10.0.0.1   # 1472+28 = 1500
ping -M do -s 1412 10.0.0.1   # 1412+28 = 1440, typical WireGuard
# macOS: ping -D -s 1472 10.0.0.1
```

The largest size that gets a reply, plus 28, is your path MTU. Set it on the interface:

```bash
sudo ip link set dev wg0 mtu 1420
```

or `MTU = 1420` under `[Interface]` in the WireGuard config.

On a router that forwards traffic for others, you cannot fix every client's MTU, so clamp the TCP handshake instead:

```bash
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu
```

This rewrites the MSS each endpoint advertises, so they never build an oversized segment. It fixes TCP only — UDP (QUIC, DNS over large responses, game traffic) still needs a correct interface MTU. And while you are in the firewall: stop dropping ICMP type 3. It is not a ping; it is the network telling you something.
