## 00:03 - [Data Engineering] Snowpipe File Sizing: The Per-File Charge and the Filename You Can Never Reload

Snowpipe bills two things: serverless compute per second, **plus a flat overhead of ~0.06 credits per 1,000 files** processed. That second line item is where tiny-file pipelines quietly go wrong. A stream landing one 2 KB JSON file per second produces ~2.6M files a month — about 155 credits of pure file overhead, before a single byte is parsed. Batch the same volume into 100 MB files and the overhead rounds to nothing.

Snowflake's guidance: aim for **100–250 MB compressed per file**, staged within about a minute of the data becoming available. Smaller is a cost problem; much larger hurts latency and makes a failed load expensive to retry.

```sql
CREATE OR REPLACE PIPE raw.events_pipe
  AUTO_INGEST = TRUE
AS
COPY INTO raw.events (payload, src_file, loaded_at)
FROM (
  SELECT $1, METADATA$FILENAME, CURRENT_TIMESTAMP()
  FROM @raw.events_stage
)
FILE_FORMAT = (TYPE = JSON);
```

### The footgun: dedup is by filename

Snowpipe keeps load metadata **on the pipe**, retained ~14 days, and skips any file whose *name* it has already seen. It does not re-check size or last-modified time the way `COPY INTO` does. So if an upstream job writes `events.json`, you fix a bug, and re-upload `events.json` with corrected contents — Snowpipe ignores it. No error, no row count, nothing in the logs that looks like a failure.

Diagnose it before assuming the pipe is broken:

```sql
SELECT file_name, status, row_count, first_error_message
FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'raw.events',
  START_TIME => DATEADD(hour, -6, CURRENT_TIMESTAMP())))
ORDER BY last_load_time DESC;

SELECT SYSTEM$PIPE_STATUS('raw.events_pipe');  -- pendingFileCount, lastReceivedMessageTimestamp
```

Fixes, in order of preference: make filenames unique and immutable (`events/dt=2026-11-14/part-0001-<uuid>.json.gz`); or run a one-off `COPY INTO ... FORCE = TRUE` to reload; recreating the pipe also clears history, but then *everything* still in the stage is eligible again.

If you genuinely need sub-minute latency, the answer isn't smaller files — it's **Snowpipe Streaming**, which ingests rows over a channel and has no per-file charge at all.
