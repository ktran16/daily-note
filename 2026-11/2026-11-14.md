## 00:03 - [Data Engineering] Snowpipe File Sizing: The Per-File Charge and the Filename You Can Never Reload

Snowpipe bills two things: serverless compute per second, **plus a flat overhead of ~0.06 credits per 1,000 files** processed. That second line item is where tiny-file pipelines quietly go wrong. A stream landing one 2 KB JSON file per second produces ~2.6M files a month — about 155 credits of pure file overhead, before a single byte is parsed. Batch the same volume into 100 MB files and the overhead rounds to nothing.

Snowflake's guidance: aim for **100–250 MB compressed per file**, staged within about a minute of the data becoming available. Smaller is a cost problem; much larger hurts latency and makes a failed load expensive to retry.

```sql
CREATE OR REPLACE PIPE raw.events_pipe
  AUTO_INGEST = TRUE
AS
COPY INTO raw.events (payload, src_file, loaded_at)
FROM (
  SELECT $1, METADATA$FILENAME, CURRENT_TIMESTAMP()
  FROM @raw.events_stage
)
FILE_FORMAT = (TYPE = JSON);
```

### The footgun: dedup is by filename

Snowpipe keeps load metadata **on the pipe**, retained ~14 days, and skips any file whose *name* it has already seen. It does not re-check size or last-modified time the way `COPY INTO` does. So if an upstream job writes `events.json`, you fix a bug, and re-upload `events.json` with corrected contents — Snowpipe ignores it. No error, no row count, nothing in the logs that looks like a failure.

Diagnose it before assuming the pipe is broken:

```sql
SELECT file_name, status, row_count, first_error_message
FROM TABLE(INFORMATION_SCHEMA.COPY_HISTORY(
  TABLE_NAME => 'raw.events',
  START_TIME => DATEADD(hour, -6, CURRENT_TIMESTAMP())))
ORDER BY last_load_time DESC;

SELECT SYSTEM$PIPE_STATUS('raw.events_pipe');  -- pendingFileCount, lastReceivedMessageTimestamp
```

Fixes, in order of preference: make filenames unique and immutable (`events/dt=2026-11-14/part-0001-<uuid>.json.gz`); or run a one-off `COPY INTO ... FORCE = TRUE` to reload; recreating the pipe also clears history, but then *everything* still in the stage is eligible again.

If you genuinely need sub-minute latency, the answer isn't smaller files — it's **Snowpipe Streaming**, which ingests rows over a channel and has no per-file charge at all.

## 05:04 - [Data Analytics] Month Arithmetic: Why Jan 31 + 1 Month + 1 Month Isn't March 31

Every major engine **clamps** month arithmetic to the last valid day of the target month. That single rule makes `+ 1 month` non-associative, and the bug is silent — you get a date, just not the one you meant.

```sql
-- Postgres / DuckDB (Snowflake, BigQuery, SQL Server behave the same)
SELECT (DATE '2026-01-31' + INTERVAL '1 month')::date                     AS once,   -- 2026-02-28
       (DATE '2026-01-31' + INTERVAL '1 month' + INTERVAL '1 month')::date AS twice,  -- 2026-03-28
       (DATE '2026-01-31' + INTERVAL '2 months')::date                     AS at_once;-- 2026-03-31
```

**1. Iterative schedules drift permanently.** If you build renewal dates by adding a month to the *previous* renewal, a Jan-31 signup goes Feb 28 → Mar 28 → Apr 28 and never climbs back to the 31st. You bill that account three days early for the rest of its life. Always anchor to the original date:

```sql
SELECT (anchor + n * INTERVAL '1 month')::date AS renewal_date
FROM (SELECT DATE '2026-01-31' AS anchor) s,
     generate_series(0, 11) AS t(n);   -- Jan 31, Feb 28, Mar 31, Apr 30, May 31 ...
```

**2. "First of month + 1 month − 1 day" is only safe after truncating.** Applied to an arbitrary date it inherits the clamp. Truncate first:

```sql
SELECT (DATE_TRUNC('month', d + INTERVAL '1 month'))::date - 1 AS month_end
FROM (VALUES (DATE '2026-01-15'), (DATE '2026-01-31')) v(d);   -- both → 2026-01-31
```

Postgres has no `LAST_DAY()`; Snowflake, BigQuery, MySQL and Oracle do — use it there rather than hand-rolling.

**3. Calendar length manufactures month-over-month movement.** A business earning a flat $1,000/day books $31,000 in January and $28,000 in February 2026 — a **−9.7% MoM** that reflects nothing but a short month. February is always the worst month on an unnormalized dashboard, and always the best one for a cost metric. Divide by days in month, or compare equal-length 28-day windows, before anyone reads a trend into it.

Rule of thumb: if a date column feeds billing, cohorts, or a MoM comparison, test it against Jan 31, Feb 29 of a leap year, and Mar 31. Those three inputs catch nearly every clamp bug.

## 10:02 - [ML & AI] Logits, Not Probabilities: Log-Sum-Exp and the Loss Floor at 0.551

Softmax is `exp(x_i) / Σ exp(x_j)`, and `exp` overflows fast: above ~709 in float64, ~88.7 in float32, and **~11.09 in float16**. Logits of 15 are ordinary in a trained network, so a naive softmax in half precision returns `inf/inf = nan`.

The fix is the shift identity — subtracting any constant leaves softmax unchanged:

```python
def softmax(x):
    m = x.max()                      # shift by the max
    e = np.exp(x - m)                # largest term is exactly 1.0
    return e / e.sum()

# logsumexp: log Σ exp(x) = m + log Σ exp(x - m)
```

With `x = [1000, 1001, 1002]`, naive gives `nan`; shifted gives `[-2, -1, 0]` → `[0.0900, 0.2447, 0.6652]`, and `logsumexp = 1002.408`.

### Why you pass raw logits to the loss

`nn.CrossEntropyLoss` and `nn.BCEWithLogitsLoss` do this shift internally, which is the real reason they want logits. Applying softmax yourself first doesn't just duplicate work — it **squashes the loss and the gradients**.

Take a correct, confident prediction, logits `[5, 0, 0]`, true class 0:

| Path | Prob of true class | Loss |
|---|---|---|
| `CrossEntropyLoss(logits, y)` | 0.9867 | **0.0134** |
| `CrossEntropyLoss(softmax(logits), y)` | 0.5712 | **0.5599** |

The second softmax runs over inputs already confined to `[0, 1]`, so the spread it can produce is bounded. Push the logits to infinity and the probabilities approach `[1, 0, 0]`; softmax of *that* is `e/(e+2) = 0.5761`, so the loss **cannot go below 0.551** no matter how right the model is. Compare chance for 3 classes, `ln 3 = 1.099`: your curve drops to ~0.55, flattens, and looks like a model that learned something and stalled. It's a plumbing bug.

Rules of thumb: losses named `*WithLogits` or `CrossEntropyLoss` take raw scores; `NLLLoss` takes `log_softmax`; call `softmax` only at inference, for reporting. In scikit-learn the same split is `decision_function` (scores) vs `predict_proba` (normalized).

## 15:03 - [Crypto & Business] Gasless Signatures: The Wallet Drain That Never Touches the Blockchain

Most people learn to check token approvals. But a large share of modern wallet drains never create an approval transaction at all — they use an **off-chain EIP-712 signature**, and that is why revoke-style tools show a clean wallet right up until the money leaves.

### The mechanic

ERC-20's `permit` (EIP-2612) and Permit2 let you authorize a spender by *signing a message* instead of sending a transaction. You sign a typed struct:

```
Permit {
  owner:    0xYou
  spender:  0xAttacker
  value:    115792089237316195423570985008687907853269984665640564039457584007913129639935
  nonce:    0
  deadline: 1893456000
}
```

The attacker then submits that signature on-chain in their own transaction and pays the gas. The contract recovers your address from the signature and credits the allowance. Economically it is identical to an approval — but three things differ:

1. **No gas, no transaction.** Nothing appears in your wallet history. There is no pending-transaction moment to cancel.
2. **No pre-check surface.** The allowance does not exist until the attacker redeems it, so an allowance dashboard reads zero. Approval-revoking is a *post*-hoc fix at best.
3. **Deadline, not revocation.** That `deadline` above is 1 Jan 2030. A signature sitting in an attacker's pocket stays valid for years. The only kill switch is spending the `nonce` — signing a fresh permit for the same token/spender invalidates the old one.

That `value` is `2^256 − 1`: the max-uint pattern meaning *unlimited*. Wallets increasingly decode it as "Unlimited" rather than a 78-digit number, which is the single most useful thing to look for.

### What to actually check

Signature requests are the dangerous ones because they feel inert — no gas estimate, no "confirm transaction" friction. Before signing, read three fields: the **primary type** (`Permit`, `PermitSingle`, `PermitBatch`, or a marketplace `Order` — all transfer authority), the **spender/taker** address, and the **amount**. A legitimate swap names the router you are using; a drain names a fresh address with no history. Also check the `domain` field's `verifyingContract` — that is the token or protocol the signature binds to, and a mismatch with the site you are on is decisive.

Same rule applies to NFT marketplace orders: a signed `Order` with a price of 0 is a gift, not a listing.

## 19:04 - [PC Hardware] SMT / Hyper-Threading: Measure the Workload Before You Flip the Switch

"Disable Hyper-Threading for gaming" is the most durable piece of bad BIOS advice still circulating. Here's what SMT actually does and when turning it off is defensible.

**What it is.** SMT exposes two logical threads per physical core. They share the front end, execution ports, and L1/L2 — only register state is duplicated. The second thread fills pipeline bubbles left by cache misses, so the gain depends entirely on how often the first thread stalls.

| Workload | SMT on vs off |
|---|---|
| Compile, Blender, x265 encode, Cinebench nT | **+15–30%** with SMT |
| Single-threaded (Cinebench 1T) | ~0% |
| Most games, 8+ core CPU | **0 to ±3% — run-to-run noise** |
| Games on a 4-core CPU | SMT clearly helps frametime stability |
| Hosting untrusted VMs | Off, for side-channel isolation |

**Why people think it helps games.** Disabling SMT lowers package power and temps, so a power-limited CPU may hold 100–200 MHz more all-core clock. That's real but small, and it costs you ~20% of your multicore throughput — a bad trade if you also compile, encode, or run containers.

**Where off is genuinely correct:** multi-tenant virtualization. L1TF and MDS leak across sibling threads, which is why hypervisors ship side-channel-aware schedulers and cloud providers charge for dedicated cores. If untrusted code runs on your box, SMT is attack surface, not a tuning knob.

**Check your topology on Linux:**

```bash
lscpu -e                                              # CPU→CORE mapping
cat /sys/devices/system/cpu/cpu0/topology/thread_siblings_list   # e.g. "0,8"
cat /sys/devices/system/cpu/smt/active                # 1 = on
echo off | sudo tee /sys/devices/system/cpu/smt/control          # reversible, no reboot
```

That runtime toggle is the right way to A/B it — no BIOS trips, no lost XMP profile. On Windows, Task Manager's "Cores: 8, Logical processors: 16" confirms SMT; test with process affinity rather than firmware.

**Protocol:** three runs per config on *your* workload, compare 1% lows and wall-clock, not average FPS. Under ~3% is noise.

Two footnotes: Intel E-cores have no SMT, so the setting only touches P-cores on hybrid chips; and if a specific title regresses, it's usually a scheduler placement bug, better fixed with affinity than by giving up half your threads.
