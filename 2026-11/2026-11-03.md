## 00:02 - [Data Engineering] `merge_exclude_columns`: The Incremental Merge That Overwrites What You Meant to Keep

With `incremental_strategy='merge'`, dbt compiles a `MERGE` whose `WHEN MATCHED` branch updates **every column** in your model to the incoming value. That is usually what you want — but not for columns that should be written once and never touched again.

The classic victim is a first-seen timestamp:

```sql
{{ config(materialized='incremental', unique_key='user_id', incremental_strategy='merge') }}

select
    user_id,
    current_timestamp as first_seen_at,   -- set on insert, clobbered on every match
    email,
    plan
from {{ ref('stg_users') }}
{% if is_incremental() %}
where updated_at > (select max(updated_at) from {{ this }})
{% endif %}
```

Run one inserts `first_seen_at`. Run two matches the same `user_id` and overwrites it with today's timestamp. Nothing errors; the column just quietly means "last time this row was touched." The same thing happens to `original_utm_source`, a manually backfilled flag, or any column downstream of a non-deterministic expression.

Two configs control the `UPDATE SET` list:

```sql
{{ config(
    materialized='incremental',
    unique_key='user_id',
    incremental_strategy='merge',
    merge_exclude_columns=['first_seen_at']
) }}
```

- `merge_exclude_columns` — update everything **except** these. Best when you have one or two protected columns.
- `merge_update_columns` — update **only** these. Best when the row is mostly immutable and a couple of fields churn (`status`, `updated_at`).

They are mutually exclusive; specifying both is a compile error. Neither affects the `WHEN NOT MATCHED` insert, so new rows still get all columns.

Three things to watch:

1. **Both are merge-only.** They are silently ignored by `append`, `delete+insert`, and `insert_overwrite`. Switch strategy or warehouse and your protection disappears without a warning.
2. **`--full-refresh` recomputes the column from scratch.** If the value was genuinely derived once, the real history is gone. Protected-once columns belong in a snapshot or a source table, not in a rebuildable model.
3. **A new column added later** isn't retroactively populated for existing matched rows if it lands outside `merge_update_columns`. Backfill with a one-off `--full-refresh` or an operation macro.

A `dbt show --inline "select ... limit 5"` against the compiled target won't reveal this — the bug only appears across two runs. Add a `dbt_utils.accepted_range` or singular test asserting `first_seen_at <= created_at` so drift fails loudly.

## 05:04 - [Data Analytics] Experiment Assignment: The Unsalted Hash That Makes Two Tests the Same Test

Bucketing users with a hash is the right instinct — it's stateless, deterministic, and reproducible in SQL. The trap is reusing the *same* hash input for every experiment.

```sql
-- Test A (checkout CTA)
ABS(MOD(FARM_FINGERPRINT(user_id), 100)) < 50  AS a_treatment,
-- Test B (shipping banner) -- same expression!
ABS(MOD(FARM_FINGERPRINT(user_id), 100)) < 50  AS b_treatment
```

Every user in A's treatment is also in B's treatment. Run the crosstab on 10,000 users and you get 5,000 / 0 / 0 / 5,000 instead of four cells of ~2,500. The two tests are now one test of both changes at once: you cannot attribute the lift, and you cannot detect an interaction, because the cells needed to measure it are empty.

**Fix: salt the hash with a stable experiment key.**

```sql
ABS(MOD(FARM_FINGERPRINT(CONCAT('checkout_cta_v3', '|', user_id)), 100)) < 50
```

```python
import hashlib
def bucket(exp_key, user_id, n=100):
    h = hashlib.md5(f"{exp_key}|{user_id}".encode()).hexdigest()
    return int(h[:8], 16) % n
```

Now the crosstab gives 2,500 ± 43 per cell (1 SE at n=10,000), and each test reads independently.

**Three more sharp edges.**

1. **Negative modulo.** `FARM_FINGERPRINT` returns a signed INT64 and BigQuery's `MOD(-5, 100)` is `-5`, not `95`. Unprotected, you get buckets −99..99 — 199 of them — and `< 50` captures roughly 75% of users. Write `ABS(MOD(x, 100))`, in that order: `MOD(ABS(x), 100)` overflows on INT64 minimum.
2. **Don't skip the hash.** `MOD(user_id, 100)` on a sequential ID makes bucket membership a function of signup time, so your variants differ by tenure before the change ships.
3. **The salt is permanent.** Renaming the experiment, or folding the variant count into the hash input, reshuffles live users mid-flight — they cross from control to treatment and contaminate both arms.

Before reading any result, print the 2×2 crosstab of concurrent experiments and check each cell against its expected share. Orthogonal salts are the default; use explicit mutual exclusion only when two tests touch the same surface and would genuinely confuse each other.
