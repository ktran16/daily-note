## 00:02 - [Data Engineering] `merge_exclude_columns`: The Incremental Merge That Overwrites What You Meant to Keep

With `incremental_strategy='merge'`, dbt compiles a `MERGE` whose `WHEN MATCHED` branch updates **every column** in your model to the incoming value. That is usually what you want — but not for columns that should be written once and never touched again.

The classic victim is a first-seen timestamp:

```sql
{{ config(materialized='incremental', unique_key='user_id', incremental_strategy='merge') }}

select
    user_id,
    current_timestamp as first_seen_at,   -- set on insert, clobbered on every match
    email,
    plan
from {{ ref('stg_users') }}
{% if is_incremental() %}
where updated_at > (select max(updated_at) from {{ this }})
{% endif %}
```

Run one inserts `first_seen_at`. Run two matches the same `user_id` and overwrites it with today's timestamp. Nothing errors; the column just quietly means "last time this row was touched." The same thing happens to `original_utm_source`, a manually backfilled flag, or any column downstream of a non-deterministic expression.

Two configs control the `UPDATE SET` list:

```sql
{{ config(
    materialized='incremental',
    unique_key='user_id',
    incremental_strategy='merge',
    merge_exclude_columns=['first_seen_at']
) }}
```

- `merge_exclude_columns` — update everything **except** these. Best when you have one or two protected columns.
- `merge_update_columns` — update **only** these. Best when the row is mostly immutable and a couple of fields churn (`status`, `updated_at`).

They are mutually exclusive; specifying both is a compile error. Neither affects the `WHEN NOT MATCHED` insert, so new rows still get all columns.

Three things to watch:

1. **Both are merge-only.** They are silently ignored by `append`, `delete+insert`, and `insert_overwrite`. Switch strategy or warehouse and your protection disappears without a warning.
2. **`--full-refresh` recomputes the column from scratch.** If the value was genuinely derived once, the real history is gone. Protected-once columns belong in a snapshot or a source table, not in a rebuildable model.
3. **A new column added later** isn't retroactively populated for existing matched rows if it lands outside `merge_update_columns`. Backfill with a one-off `--full-refresh` or an operation macro.

A `dbt show --inline "select ... limit 5"` against the compiled target won't reveal this — the bug only appears across two runs. Add a `dbt_utils.accepted_range` or singular test asserting `first_seen_at <= created_at` so drift fails loudly.

## 05:04 - [Data Analytics] Experiment Assignment: The Unsalted Hash That Makes Two Tests the Same Test

Bucketing users with a hash is the right instinct — it's stateless, deterministic, and reproducible in SQL. The trap is reusing the *same* hash input for every experiment.

```sql
-- Test A (checkout CTA)
ABS(MOD(FARM_FINGERPRINT(user_id), 100)) < 50  AS a_treatment,
-- Test B (shipping banner) -- same expression!
ABS(MOD(FARM_FINGERPRINT(user_id), 100)) < 50  AS b_treatment
```

Every user in A's treatment is also in B's treatment. Run the crosstab on 10,000 users and you get 5,000 / 0 / 0 / 5,000 instead of four cells of ~2,500. The two tests are now one test of both changes at once: you cannot attribute the lift, and you cannot detect an interaction, because the cells needed to measure it are empty.

**Fix: salt the hash with a stable experiment key.**

```sql
ABS(MOD(FARM_FINGERPRINT(CONCAT('checkout_cta_v3', '|', user_id)), 100)) < 50
```

```python
import hashlib
def bucket(exp_key, user_id, n=100):
    h = hashlib.md5(f"{exp_key}|{user_id}".encode()).hexdigest()
    return int(h[:8], 16) % n
```

Now the crosstab gives 2,500 ± 43 per cell (1 SE at n=10,000), and each test reads independently.

**Three more sharp edges.**

1. **Negative modulo.** `FARM_FINGERPRINT` returns a signed INT64 and BigQuery's `MOD(-5, 100)` is `-5`, not `95`. Unprotected, you get buckets −99..99 — 199 of them — and `< 50` captures roughly 75% of users. Write `ABS(MOD(x, 100))`, in that order: `MOD(ABS(x), 100)` overflows on INT64 minimum.
2. **Don't skip the hash.** `MOD(user_id, 100)` on a sequential ID makes bucket membership a function of signup time, so your variants differ by tenure before the change ships.
3. **The salt is permanent.** Renaming the experiment, or folding the variant count into the hash input, reshuffles live users mid-flight — they cross from control to treatment and contaminate both arms.

Before reading any result, print the 2×2 crosstab of concurrent experiments and check each cell against its expected share. Orthogonal salts are the default; use explicit mutual exclusion only when two tests touch the same surface and would genuinely confuse each other.

## 10:02 - [ML & AI] Semantic Caching: The 0.95 Threshold That Serves the EU Customer the US Refund Policy

Exact-prefix provider caching only helps when the *same* text repeats. A semantic cache goes further: embed the incoming question, search a vector store of past question→answer pairs, and if the nearest neighbour is above a similarity threshold, return the stored answer and never call the model. Hit rates of 20–40% on support-style traffic are normal, and a hit costs an embedding call instead of a full generation.

The failure mode is that cosine similarity does not respect the distinctions your answer depends on. Entity swaps and negation barely move the vector:

| Query pair | Cosine | Same answer? |
|---|---|---|
| "refund policy for **US** customers" vs "for **EU** customers" | ~0.97 | **No** |
| "is Plan A **included**" vs "is Plan A **not included**" | ~0.96 | **No** |
| "how do I reset my password" vs "password reset steps" | ~0.94 | Yes |

The wrong pairs score *higher* than the right one. No threshold separates them, because the difference isn't semantic distance — it's scope.

**Do the arithmetic before you ship it.** At 100k queries/day and a 30% hit rate, a 4% false-hit rate inside those hits is `100,000 × 0.30 × 0.04 = 1,200` confidently wrong answers per day. If your pipeline was 97% correct, you just bought a 30% cost cut with 1.2 points of absolute accuracy — and these errors are worse than hallucinations, because they are fluent, plausible, and repeat verbatim until the TTL expires.

The fix is to stop asking similarity to do the work. Partition the cache by anything that changes the correct answer, and only search within a partition:

```python
def cache_key_scope(req):
    # Hard equality — never crossed by similarity search.
    return (req.tenant_id, req.locale, req.plan_tier,
            req.model, req.prompt_version, tuple(sorted(req.retrieval_filters)))

def lookup(req, threshold=0.95):
    vec = embed(req.question)
    hit = vstore.search(vec, filter={"scope": cache_key_scope(req)}, k=1)
    if hit and hit.score >= threshold and hit.age < TTL:
        return hit.answer
    return None
```

Then measure, don't guess: log every hit, replay a random 1–2% sample through the real model, and treat disagreement as your false-hit rate. Tune the threshold against *that* number, not against the hit rate. Skip the cache entirely for personalized, write-path, or freshness-sensitive queries — and set a TTL short enough that a policy change can't be served for a week.

## 15:03 - [Crypto & Business] Freemium vs Free Trial: Cost Scales With the Stock, Revenue With the Flow

Both give the product away. They fail for opposite reasons, and the difference is a stock-vs-flow problem.

**Freemium.** Say 10,000 free signups/month, 2.5% convert to paid, and free users leave the free tier at 8%/month. Your free base isn't 10,000 — it's the steady state:

```
free base = signups / (free churn + conversion)
          = 10,000 / (0.08 + 0.025) ≈ 95,000 users
```

Cost to serve one free user: $0.35/mo infra, plus support — if 4% file a ticket at $6 fully loaded, that's $0.24. Call it $0.59.

```
free-tier cost   = 95,000 × $0.59 ≈ $56,000/month
new paid/month   = 10,000 × 2.5%  =  250
cost per paid    = $56,000 / 250  =  $224
```

That $224 sits *on top of* marketing CAC. At $40/mo ARPU and 85% gross margin ($34 contribution), the free tier alone takes 6.6 months to pay back.

**Free trial.** Same 10,000 starts, but 14 days instead of forever and ~18% convert. No base accumulates: roughly 5,000 active trials at a half-month of cost ≈ $2,950/month, or **$1.64 per paid customer**. Trials cost almost nothing to serve — they just need more intent at the top, so that traffic is pricier.

**The three things that actually decide it:**

1. **Does your free base accumulate?** Freemium cost grows with the *stock* of free users; revenue grows with the *flow* of conversions. Flat conversion plus a growing stock is slow margin decay — watch cost-per-paid-conversion monthly, not gross-margin percentage.
2. **Does a free user acquire the next one?** Freemium only beats paid ads when free users generate signups (invites, shared links, indexed content). If 10,000 ad-driven signups at $25 CPA would convert the same, your $224 is a worse deal.
3. **Gate the value metric, not time or features.** Gate the thing that grows as the customer succeeds — seats, rows, projects, history retention. Gating something your buyer never bumps into means they never feel the ceiling, and never upgrade.

Rule of thumb: free trial is a *sales* tactic, freemium is a *distribution* strategy. Pick freemium only if marginal cost per free user is near zero and the free tier is your acquisition channel.

## 19:05 - [PC Hardware] HBAs and IT Mode: Why a RAID Card Ruins a ZFS Pool

ZFS, Btrfs and unRAID all want the same thing from a storage controller: nothing. Give them raw disks and get out of the way. A hardware RAID card does the opposite — it hides disks behind a virtual volume, absorbs SMART data, and acknowledges writes that are still sitting in its DRAM cache. That last one is the real danger: ZFS's transaction groups assume a flush means *on platter*. A controller that lies about flushes can leave an inconsistent pool after a power cut, and a BBU that has quietly died turns a "safe" write cache into a liar.

The fix is an HBA flashed to **IT mode** (Initiator Target) — firmware that strips the RAID logic and presents every disk directly.

**Picking one:**

| Card | ASIC | Link | Ports | Per-drive |
|---|---|---|---|---|
| 9211-8i / M1015 | SAS2008 | PCIe 2.0 x8 | 8 | 6 Gb/s |
| 9207-8i | SAS2308 | PCIe 3.0 x8 | 8 | 6 Gb/s |
| 9300-8i | SAS3008 | PCIe 3.0 x8 | 8 | 12 Gb/s |

The 9211-8i is the classic cheap pick, but PCIe 2.0 x8 caps the card at ~4 GB/s total. Fine for eight HDDs (~250 MB/s each = 2 GB/s). Not fine for eight SATA SSDs. Buy a 9207 or 9300 if there's any chance of SSDs later.

**Three things that bite people:**

1. **Verify the mode, don't trust the listing.** `sas2flash -list` (or `sas3flash -list`) should report a Firmware Product ID of `0x2213` — IR firmware reports `0x2214`. On Linux, `lspci -nn | grep -i lsi` plus `dmesg | grep mpt` confirms the driver bound as `mpt3sas`.
2. **Cooling.** These are server cards designed for ~200 LFM of chassis airflow. In a quiet tower the passive heatsink hits 90–100°C and the card drops drives intermittently. Zip-tie a 40–60mm fan to it. This is not optional.
3. **Cables.** SAS2 cards use SFF-8087, SAS3 use SFF-8643. You want *forward* breakout (controller → 4× SATA). Reverse breakout cables look identical and will not work.

Avoid SATA port multipliers entirely — they share one link across five drives and handle error recovery badly.
