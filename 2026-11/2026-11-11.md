## 00:04 - [Data Engineering] Postgres Replication Slots: The Paused CDC Connector That Fills Your Primary's Disk

Log-based CDC from Postgres depends on a *logical replication slot*. A slot is not a buffer the database manages for you — it is a promise. It records a `restart_lsn`, and Postgres refuses to recycle any WAL segment at or after that position until the consumer confirms it has moved on. Stop the consumer and the promise still holds: WAL accumulates in `pg_wal` on the primary until the disk fills and the database shuts down. A Debezium connector paused for a long weekend is a production outage on the source system, not just a stale warehouse.

Make the retained volume a first-class metric:

```sql
SELECT slot_name, active, wal_status,
       pg_size_pretty(
         pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)
       ) AS retained_wal,
       age(xmin), catalog_xmin
FROM pg_replication_slots;
```

Three columns matter. `active = false` means nobody is consuming — the clock is running. `retained_wal` growing monotonically is the alert you want, with a threshold well under free disk. `wal_status` moves `reserved` → `extended` → `unreserved` → `lost` as pressure rises.

That progression is governed by `max_slot_wal_keep_size` (PG 13+), and it is a deliberate trade. Leave it unset and a dead slot can take the primary down. Set it, and Postgres invalidates the offending slot once the cap is exceeded, protecting the database — but an invalidated slot cannot resume. You will drop it, recreate it, and re-snapshot the whole source table. Pick your failure mode consciously; most teams set the cap *and* page on `retained_wal` long before it trips.

`catalog_xmin` is the subtler cost. A logical slot pins the oldest transaction ID whose catalog rows must remain visible, so autovacuum cannot clean system catalogs past that point. A long-stalled slot therefore bloats `pg_attribute` and friends, slowly degrading planning time across the whole instance.

Two more operational notes: a logical slot lives on one server, so before PG 17 a failover silently lost it (PG 17 adds slot synchronization via `failover = true` and `sync_replication_slots`). And always drop slots for decommissioned pipelines — a forgotten connector that nobody monitors is the most common cause of this outage.

## 05:03 - [Data Analytics] Keyset Pagination: The OFFSET That Scans 200,000 Rows to Return 50

`LIMIT 50 OFFSET 200000` reads like "skip ahead." The engine cannot skip. It produces all 200,050 rows in sort order, discards the first 200,000, and returns the rest. Cost grows linearly with page number: on a 5M-row events table with an index on `(created_at, id)`, page 1 returns in ~2 ms and page 4,001 takes ~900 ms — same query, same index, 400x the work. Every "export all pages" script therefore costs O(n²) in total.

The correctness bug is worse, because it is silent. OFFSET counts *positions*, not rows. Insert 10 rows that sort before your cursor between page 1 and page 2, and ten rows you already saw shift down into page 2 — you see them twice. Delete rows and you skip others entirely. A non-unique `ORDER BY` breaks it even on a static table: ties may come back in any order, so a row can appear on two pages or none.

Keyset (seek) pagination replaces the position with the last row's sort key:

```sql
-- page 1
SELECT id, created_at, amount FROM events
ORDER BY created_at, id
LIMIT 50;

-- next page: pass the last row's (created_at, id) back in
SELECT id, created_at, amount FROM events
WHERE (created_at, id) > (TIMESTAMP '2026-11-04 09:12:03', 88421)
ORDER BY created_at, id
LIMIT 50;
```

The row-value comparison `(a, b) > (x, y)` is lexicographic, matches the index prefix, and the engine seeks straight to the position — ~2 ms on page 1 and on page 4,001.

Three rules make it hold. The `ORDER BY` must end in a unique column, or ties cause skips again. The index must match the `ORDER BY` exactly, including direction. And for `DESC`, flip the operator to `<` — mixing `created_at DESC, id ASC` defeats row-value comparison, so write it as explicit nested `OR` conditions or just keep both columns in the same direction.

The trade: you lose random access. There is no "jump to page 400," and no total count unless you query it separately. For UI feed scrolling and for bulk extracts that is free; for a page-number widget over a small table, OFFSET is still fine.

## 10:03 - [ML & AI] Dropout: The `1/(1-p)` Scaling, and the Bug `torch.no_grad()` Won't Save You From

Dropout zeroes each unit independently with probability `p` during training. The part people forget is the second half: surviving units are divided by `(1-p)`. This is *inverted dropout*, and the division is what makes inference require no special math.

The arithmetic is worth doing once. Take a layer whose 100 activations sum to 100, with `p=0.5`. Roughly 50 survive, summing to ~50 — half the signal the next layer was trained to expect. Scale survivors by `1/(1-0.5) = 2` and the expected sum returns to 100. Expectation is preserved; **variance is not**. The per-batch sum now has a standard deviation of roughly `sqrt(p/(1-p)) · sqrt(Σa²)`, which is exactly the noise that does the regularizing.

Because the scaling lives in the training path, inference is just "stop dropping." That makes the failure mode silent:

```python
model.train()                      # default after construction
with torch.no_grad():              # does NOT disable dropout
    p1 = model(x)
    p2 = model(x)
print(torch.allclose(p1, p2))      # False — same input, different answer

model.eval()                       # this is the switch
with torch.no_grad():
    assert torch.allclose(model(x), model(x))
```

`no_grad()` controls autograd bookkeeping only. `eval()` controls module *behavior* — it turns dropout off and flips BatchNorm from batch statistics to its running estimates. Serving a model left in `train()` mode gives non-reproducible predictions and, with BatchNorm, predictions that depend on whatever else happens to be in the request batch. With `p=0.1` on a few layers the accuracy drop is often only 1–3 points: small enough to pass a smoke test, large enough to matter.

Two practical notes. Modern large transformers are frequently pretrained with `dropout=0.0` — a single pass over a huge corpus leaves little to memorize, and the noise just slows convergence. Dropout earns its place again when you fine-tune on small data, which is why PEFT exposes a separate `lora_dropout`.

And treat `p` and weight decay as one budget. Both shrink effective capacity; raising dropout to 0.5 while keeping a weight decay tuned at `p=0.1` usually underfits. Tune them together, or hold one fixed.

## 15:05 - [Crypto & Business] Address Poisoning: Why the Attacker's Address Matches Yours at Both Ends

Your wallet shows `0x7a2f…c4e1`. The 32 characters in the middle are hidden, and that truncation *is* the attack.

**The grind.** An address is 20 bytes — 40 hex characters. Matching the first four and last four means hitting 8 specific characters: 16^8 ≈ 4.3 billion keypairs on average. GPU vanity generators do 10–100 million keys/second, so a convincing lookalike for *any* address costs a few minutes and pennies of electricity. Attackers watch the chain, see you pay Bob, and grind an address that is visually identical to Bob's at both displayed ends.

**Getting it into your history.** The lookalike has to appear in your activity feed, so it can be copied. Two mechanisms:

- *Zero-value `transferFrom`.* Anyone can call `transferFrom(you, attacker, 0)` on a real ERC-20. Standard implementations check `allowance >= amount`, and 0 ≥ 0 passes — so the call succeeds and emits `Transfer(you → attacker, 0)`. No approval, no signature from you. Explorers index it as an outgoing transfer from your wallet.
- *Fake-token airdrop.* Deploy a contract whose `symbol()` returns `USDT` and send yourself 500 of it from the lookalike address. Your history now reads "received 500 USDT" from something that looks like Bob.

Next time you pay Bob you copy from history, glance at both ends, and sign. In May 2024 a single transfer of ~1,155 WBTC (≈$68M) went out this way; the attacker returned it days later after public negotiation — which is luck, not a control.

**Defenses, in order of value**

1. Never copy a destination out of transaction history. Use an address book you filled out-of-band, or the recipient's own message.
2. Verify the *middle* of the address, not the ends — ideally all 40 characters on your hardware wallet's screen, the one display an attacker cannot influence.
3. For a first large transfer, send dust and have the recipient confirm receipt.
4. Enable "hide zero-value / spam transfers" in your wallet and explorer.
5. Treat any unexpected inbound token as bait, familiar symbol or not. Never swap or approve it.

## 19:02 - [PC Hardware] Modern Standby vs S3: Why Your PC Wakes Up Hot in a Closed Bag

Two machines can both say "asleep" and mean entirely different things. Classic **S3** (suspend-to-RAM) cuts power to the CPU, chipset and most devices; only DRAM self-refresh and a wake circuit stay alive, typically 1–3W. **Modern Standby / S0ix** never leaves S0 — the OS stays running and relies on every component idling into deep low-power states. When that cooperation works, you get phone-like instant resume and background mail sync. When one driver misbehaves, the machine sits at 10–15W in your bag, drains 40% overnight, and comes out warm with the fans having run.

First, find out what you actually have:

```powershell
powercfg /a                 # "Standby (S0 Low Power Idle)" = Modern Standby
powercfg /sleepstudy        # writes an HTML report to the current directory
```

The sleep study report is the diagnostic that matters. Look at each session's **active percentage** and the top offenders list. Healthy Modern Standby sits in DRIPS (Deepest Runtime Idle Platform State) above ~85% of the session. Repeat offenders: Wi-Fi/Bluetooth radios, the `SRUMSVC`/push-notification stack, an external USB hub, and network drivers with wake-on-pattern-match enabled.

Concrete fixes, cheapest first:

```powershell
powercfg /lastwake                      # what woke it last time
powercfg /devicequery wake_armed        # everything allowed to wake it
powercfg /devicedisablewake "Realtek PCIe GbE Family Controller"
```

Also check Device Manager → the NIC → Power Management, and uncheck "Wake on Magic Packet"/pattern match if you don't use WoL.

On desktops you often get a real choice. Many boards expose a BIOS option — look for **Sleep State: S3 / Suspend-to-RAM**, or disable *Modern Standby* / *S0ix* / *Low Power S0 Idle Capability*. S3 gives you a reliably cold, quiet machine at the cost of a 2–4 second resume and no background sync. On most laptops that option doesn't exist; fix the offending device instead.

Linux shows the same split plainly:

```bash
cat /sys/power/mem_sleep     # [s2idle] deep  — brackets mark the active mode
echo deep | sudo tee /sys/power/mem_sleep
```

`s2idle` is the S0ix equivalent; `deep` is S3. If `deep` isn't listed, the firmware didn't expose it — check for a BIOS update or the vendor's sleep-mode toggle.

Rule of thumb: if a sleeping machine loses more than ~2% battery per hour, it isn't sleeping. It's idling with the lights off.
