## 00:03 - [Data Engineering] Query Tagging for Cost Attribution: Finding Which dbt Model Spent the Credits

Your warehouse bill is one number. "Compute cost $4,200 last month" is not actionable — you cannot tell whether one runaway incremental model ate half of it or 300 models each cost a little. The fix is to tag every query dbt issues with the node that issued it, then join spend back to that tag.

dbt already sends a comment on every query. The default includes `node_id`, but you control it:

```yaml
# dbt_project.yml
query_comment:
  comment: "{{ dbt_query_comment() }}"
  append: true      # trailing, not leading — some statements reject a leading comment
  job-label: true   # BigQuery only: turns the dict into job labels
```

```sql
-- macros/dbt_query_comment.sql
{% macro dbt_query_comment() %}
  {%- set c = {
    "app": "dbt",
    "node_id": node.unique_id if node else none,
    "invocation_id": invocation_id,
    "target": target.name,
    "run_reason": env_var("DBT_RUN_REASON", "adhoc")
  } -%}
  {{ tojson(c) }}
{% endmacro %}
```

**Snowflake.** Comments land in `QUERY_HISTORY.QUERY_TEXT`, but the cleaner handle is the session query tag (`query_tag` in your profile, or a pre-hook). Then join to `QUERY_ATTRIBUTION_HISTORY`, which gives credits per query:

```sql
select
  q.query_tag,
  count(*)                              as runs,
  sum(a.credits_attributed_compute)     as credits,
  sum(a.credits_attributed_compute) * 3 as approx_usd
from snowflake.account_usage.query_attribution_history a
join snowflake.account_usage.query_history q using (query_id)
where q.start_time >= dateadd(day, -30, current_timestamp())
group by 1
order by credits desc
limit 25;
```

**BigQuery.** With `job-label: true`, query the labels array:

```sql
select
  (select value from unnest(labels) where key = 'node_id') as node_id,
  sum(total_bytes_billed) / pow(1024, 4) * 6.25            as approx_usd
from `region-us`.INFORMATION_SCHEMA.JOBS
where creation_time >= timestamp_sub(current_timestamp(), interval 30 day)
group by 1 order by 2 desc;
```

Two gotchas: `ACCOUNT_USAGE` views lag up to ~3 hours (and attribution only covers queries over ~100ms), and `invocation_id` is what lets you separate a CI run from production — tag it, or your dev experiments pollute the ranking.

## 05:04 - [Data Analytics] Join Keys That Look Equal: Collation, Case, and Invisible Padding

A revenue join across two systems returns 42,425 of 48,210 CRM accounts. 5,785 rows — 12% — vanish. The keys look identical in the result grid, because the differences are invisible.

**Diagnose before you patch.** Count the three failure modes directly:

```sql
SELECT COUNT(*)                                            AS total,
       COUNT(*) FILTER (WHERE code <> btrim(code))         AS padded,
       COUNT(*) FILTER (WHERE code <> upper(code))         AS mixed_case,
       COUNT(*) FILTER (WHERE code ~ '[^\x20-\x7E]')       AS non_ascii
FROM crm_accounts;
--  total | padded | mixed_case | non_ascii
-- 48210  |  3912  |    1840    |    94
```

Three causes, all silent:

1. **Case.** `'ACME-01' = 'acme-01'` is **false** in Postgres, Snowflake, BigQuery and Redshift, and **true** in MySQL (`utf8mb4_0900_ai_ci`) and SQL Server (`..._CI_AS`) by default. A pipeline ported from MySQL to Snowflake loses rows with no error.
2. **Padding.** `'ACME-01   ' = 'ACME-01'` is false for `text`/`varchar`. It's *true* for Postgres `char(n)`, which blank-pads — so the same data joins or doesn't depending on the column type, and casting `char` to `text` brings the spaces back.
3. **Unicode.** `é` as U+00E9 vs `e`+U+0301 are different strings. So is anything carrying a zero-width space (U+200B) pasted in from a spreadsheet.

**The tempting fix is the wrong one:**

```sql
ON upper(btrim(a.code)) = upper(btrim(b.code))   -- non-sargable
```

Wrapping the key kills index and join-key statistics; on 50M rows this turns a hash join into a full scan of both sides.

**Normalize at write time instead**, store it, index it, and keep the original for display:

```sql
ALTER TABLE crm_accounts ADD COLUMN code_key text
  GENERATED ALWAYS AS (upper(btrim(code))) STORED;
CREATE INDEX ON crm_accounts (code_key);
```

For names, normalize Unicode too: `unicodedata.normalize('NFC', s).strip()` in Python, or `NORMALIZE(code, NFC)` in BigQuery. Postgres users can reach for `citext` or a non-deterministic ICU collation, but an explicit key column is more portable and visible in the plan.

**Then lock it in.** Add a CI assertion that the join's match rate stays above 99.5%. After normalization the 5,785 orphans drop to 61 — and *those* 61 are genuinely missing accounts, which is a data problem worth a ticket rather than a `TRIM()`.
